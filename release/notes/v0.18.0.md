# Registry Stack v0.18.0

Registry Stack v0.18.0 is the beta-28 release. It adds holder-bound Evidence
credentials, an OID4VCI wallet-delivery adapter, reviewed SQLite extraction,
and bounded multi-stage source acquisition.

## Product scope

- Evidence ships `evidence`, `evidencectl`, Registry Mint, and the new
  `evidence-oid4vci` adapter for Linux amd64, Linux arm64, and macOS arm64.
- The OID4VCI adapter implements the frozen OpenID4VCI 1.0 Final profile for
  `dc+sd-jwt`. Evidence remains the credential signer; the adapter holds no
  credential-signing key or holder private key.
- Registry Relay, Registry Manifest, Registryctl, and their public contracts
  have no user-visible changes in this release.
- Crosswalk remains pinned at
  `1d44ec735fdc8a7c719264b339574371e8330337`.

## Breaking Evidence changes

- BREAKING: `registry.assertion-evidence/v1` now always serializes the required
  `subjectBinding`. `audience` and `requestNonce` are optional and mutually
  dependent. Existing requirements without a subject-binding declaration
  continue to issue audience-scoped credentials, but direct wire clients must
  accept the new response shape.
- BREAKING: The request member `holderKey` is now `holderKeys`, including a
  one-element array when requesting one holder-bound credential.
- BREAKING: `ResponseFormat` adds `SdJwtVcBatch` with media type
  `application/vnd.registrystack.evidence.batch+json`.
- BREAKING: `VerificationError` adds `KeyBinding`. Downstream exhaustive
  matches must handle the new case.
- BREAKING: The disclosure-release audit event records bounded `evidenceIds`.
  Audit consumers must accept the revised schema.
- Holder-bound credentials are verified with `evidence verify-presentation`
  and the holder-bound presentation policy. `evidence verify` remains the
  audience-scoped verification path.

## Evidence changes

- Holder-bound issuance derives a credential binding from the authenticated
  holder key, supports bounded atomic batches, and requires an RFC 9901
  key-binding JWT at presentation. Audience-scoped and holder-bound policies
  remain separate and refuse the other mode.
- `evidence-oid4vci` provides issuer metadata, protected offer creation,
  pre-authorized-code token exchange, nonces, and single-use credential
  issuance. Proof validation is closed and local: exact issuer audience,
  inline public JWK or local `did:jwk`, and no remote DID or `x5c` resolution.
- The OID4VCI service uses bounded in-memory state and supports one replica.
  Restarting it invalidates outstanding offers and access tokens. It does not
  provide persistence, a second state backend, deferred issuance, revocation
  or status lists, or draft-13 compatibility.
- Evidence can acquire reviewed immutable SQLite extracts with exact statement
  and extract binding, closed SQL actions, deterministic functions, strict
  result bounds, and value-free failures.
- Fixed acquisition plans can perform declared search, fetch, and fetch-set
  stages with bounded fact handoff and one shared budget. Optional capabilities
  require both operator and bundle opt-in.
- Fixed-source clients can authenticate with private-key JWT. Registry Mint
  verifies assertions against the selected registered client's keys, enforces
  exact issuer, subject, audience, time, and replay bounds, and audits before
  token release.

## Packaging and installation

- The Evidence installer verifies and installs `evidence`, `evidencectl`,
  `mint`, and `evidence-oid4vci` together.
- The release checksum closure covers 12 Evidence binaries, two installer
  scripts, three native Node tarballs, and three native Python wheels. The
  client packages remain GitHub Release assets and are not published to npm or
  PyPI.

## Upgrade requirements

- Update direct Evidence clients from `holderKey` to `holderKeys`, accept the
  required `subjectBinding`, and handle batch response and key-binding errors.
- Update audit consumers for bounded `evidenceIds` and use the presentation
  verifier and holder-bound policy for holder-bound credentials.
- Run the OID4VCI adapter as a single replica and plan for outstanding offers
  and tokens to expire on restart.
- Validate every SQLite extract declaration and every new source-auth identity
  with the v0.18.0 tooling before deployment.

## Release boundaries

- Beta publication promotes one verified candidate from protected `main`
  without rebuilding payloads or the Relay image manifest.
- Hosted publication, external conformance, repeatable-build exercises,
  Scorecard, adopter deployments, and 1.0 readiness remain outside this source
  release's critical path.

# Registry Stack v0.37.0

Registry Stack v0.37.0 is the beta-49 release. BReg holds delegated agents to
a lower ceiling: a standing agent profile may author change-request drafts but
not submit, apply, write directly, or invoke an immediate action, a token
carrying a trusted `act` reaches only an `actorKind: agent` profile, and the
audit journal records the agent behind a delegated request. A BReg record or
query `400` names the request member or query parameter at fault in
`fieldPath`. Registry
Casework selects the source profile only by the `Registry-Source-Profile`
header, parses every mutating request body strictly, and names out-of-range
page limits with their own problem code. Registry Scheduling starts a hold's
time to live once its capacity transaction decides, and answers availability
for a horizon past the last representable instant instead of failing the
request.

Registry Messaging and the BReg citizen MCP gateway and review page are in the
source tree but ship no binaries, images, installers, or client packages in
this release.

Upgrade to v0.37.0 from v0.36.0. No product adds a database migration, and no
runtime file needs editing. A BReg project whose access profiles break the new
agent rules must be fixed and repackaged before the upgrade; any other package
runs unchanged. The Casework request bodies and the BReg problem documents
change for callers, so upgrade every client with its runtime.

## Compatibility and migration

Run the same release on every runtime, tool, and client, and upgrade in the
order [upgrade and retire](https://docs.registrystack.org/operate/advanced/upgrade-and-retire/#upgrade-in-this-order)
describes: BReg first, then Casework, then Evidence, then Scheduling, then the
clients. Take the backups it names first; no product migrates backwards.

### Upgrade Base Registry Engine from v0.36.0

- Replace the `breg` and `bregctl` binaries or images and restart every `breg`
  process. The runtime file and the database need no change, and neither does
  the package unless its project breaks one of the access-profile rules
  below. Run `bregctl check` from v0.37.0 against the project first: `breg`
  rederives the package when it starts, so a project the v0.37.0 compiler
  refuses also stops the runtime. Fix such a project so that it compiles
  under both releases, rebuild it with `bregctl package`, and apply it with
  `bregctl plan` and `bregctl apply` on v0.36.0 before replacing the
  binaries.
- BREAKING: the compiler refuses a standing agent profile, one with
  `actorKind: agent` and no `taskGrant`, that holds `submit_request`,
  `revise_request`, `cancel_request`, or `apply_request`, with
  `access_profile.standing_agent.operation_forbidden`, or that holds `create`
  or `patch` on an entity without a `changeRequest`, or `import`,
  `tombstone`, or `batch` on any entity, with
  `access_profile.standing_agent.direct_mutation_forbidden`. It also refuses a
  standing agent profile that holds an immediate-action permission, with
  `access_profile.standing_agent.action_forbidden`. A standing agent carries
  no human approval, so it may read and author change-request drafts while
  the person submits them. Move the lifecycle operations, direct writes, and
  action permissions to a profile the person uses directly.
- BREAKING: the compiler refuses a module that contributes an access profile
  declaring a `taskGrant`, whether on an entity it adds or on one it extends,
  with `access_profile.task_grant.module_forbidden`. Declare the task-grant
  profile in the project's `accessProfiles`, where task-grant ceilings are
  checked.
- BREAKING: a token carrying a trusted `act` is admitted only on an access
  profile that declares `actorKind: agent`; a profile that declares another
  kind or no `actorKind` refuses it. Such a token is an agent token whatever
  its `registry_actor_kind` claim says, so it no longer satisfies a profile
  that declares `actorKind: human`. Tokens without `act` are admitted as
  before. Mark every profile a delegated caller uses `actorKind: agent`.
- BREAKING: an `act` claim of exactly `{sub, iss}` is accepted when `iss`
  equals the verified token issuer, as an RFC 8693 token exchange writes it,
  beside exactly `{sub}`. Any other member, a different issuer, or a nested
  `act` still refuses the token. See
  [the registry file](https://docs.registrystack.org/configure/breg/#the-registry-file).
- BREAKING: a record or query `400` names the member or parameter at fault in
  `fieldPath`, where it carried none before; `detail` and `code` are
  unchanged. A create body names `/data` for a field the grant does not let
  the caller write, known or not, and `/data/<apiName>` for a missing required
  field or a wrong value of a writable one. A JSON Patch document names
  `/<n>`, `/<n>/op`, `/<n>/path`, or `/<n>/value`. A batch body names
  `/items`, `/changeContext`, `/items/<n>` and its fixed members, and the
  create and patch forms under them. A malformed `Idempotency-Key` names the
  header, and so does an `If-Match` header sent on a batch. A `query.invalid`
  refusal names the parameter, such as `$select`, including the first read
  query option sent to a revision route, which takes none. An unknown and a
  withheld name answer the same problem and are never echoed. The v0.37.0
  Rust, Node.js, and Python BReg clients accept `fieldPath` on
  `request.invalid` and `query.invalid`; a client that rejects an unfamiliar
  problem member must be upgraded with the runtime, and a client that pins
  exact problem bodies drops `fieldPath` before comparing. See
  [Mutations](https://docs.registrystack.org/reference/breg-api/#mutations).
- BREAKING: a JSON Patch `test` of a field the grant does not let the caller
  read answers `400 request.invalid` at `/<n>/path` before the record is
  read, exactly like a `test` of an unknown field. It was refused only after
  the record was read, so a missing record answered `404 resource.not_found`
  and a stale `If-Match` answered `412 precondition.failed` first. Test only
  fields the grant lists in `readableFields`
  (`GET /v1/registry?accessProfile=<id>`), and handle a `400` on such a patch
  as a malformed document, not as a missing record or a stale revision.

### Upgrade Registry Casework from v0.36.0

- Replace the `casework` and `caseworkctl` binaries or images and restart the
  runtime. No schema migration is pending, so `caseworkctl plan` reports
  nothing to apply for the active package.
- BREAKING: the `Registry-Source-Profile` header is the only input that
  selects the source profile on `POST /v1/work-items/{itemId}/decisions` and
  both attempt recovery routes, as on every other source-backed route.
  `DecideRequest` no longer carries `sourceProfileId`, and
  `RecoverAttemptRequest` is a closed empty object (`{}`); a body that still
  sends `sourceProfileId` is refused with 422 `request.unprocessable`. The
  Rust client, the Node.js and Python bindings, and the unified clients
  follow. Callers that send `sourceProfileId` in a decision or recovery body
  must drop it and send the value in `Registry-Source-Profile`.
- BREAKING: every mutating route parses its JSON body with the workspace's
  strict parser. A duplicate object member at any depth, including inside
  free-form members such as a review draft body or a decision result, is
  refused with 422 `request.unprocessable` instead of the last occurrence
  winning, and so is a raw JSON integer that IEEE 754 binary64 cannot
  represent exactly, such as `9007199254740993`; send such a value as a
  string. The whole `Content-Type` value must parse as `application/json` or
  `application/*+json` with every parameter a `name=token` or
  `name="quoted-string"` pair, so a value such as `application/json; charset`
  is refused with 415 `request.unsupported-media-type`. The other rejection
  classes are unchanged: 413 over the body limit, 400 `request.invalid` for
  malformed JSON, and 422 for a document that does not match the request type.
- A zero or over-maximum `limit` on a paged route is refused with the new
  closed problem code `request.limit-out-of-range` (400) instead of
  `request.invalid`. Its detail names the parameter and the accepted ranges,
  1 to 100, and 1 to 1000 on the directory absence list. A client that
  matches on `request.invalid` for a limit refusal matches the new code
  instead.

### Upgrade Scheduling, Evidence, Relay, and Discovery from v0.36.0

- Replace the binaries or images and restart. Scheduling, Evidence, Relay,
  Discovery, and Registry Manifest need no configuration, package, or
  database change in this release.

## Base Registry Engine

- The audit journal records the agent behind a delegated request. A request
  carrying a trusted `act` writes the shared `authorization` object on its
  refusal, mutation, and request lifecycle records, with actor kind `agent`
  and a keyed `actorPseudonym` scoped to the package revision beside the
  principal and client pseudonyms. The raw actor identifier is never stored,
  and task-grant records without `act` are unchanged.
- The audit journal records delegated authority on reads. A read's terminal
  record, for records, lists, lookups, revisions, history, and snapshots,
  carries the `authorization` object for a task-grant or delegated token.
  Direct tokens record no such object, as before.
- A read path answers when the caller's profile holds no permission entry for
  the path's target entity. It returns the records the path grant and the
  generated target policy authorize, the same answer as a target permission
  without `get` or `list`, where it answered `503 source.unavailable` before.
  A profile that does not declare the path is still refused as
  `404 resource.not_found`, like an unknown path.

## Registry Casework

- `GET /v1/review-tasks` sent without `Registry-Source-Profile` answers 400
  `source-profile.required` when the page would be empty, has no
  `nextCursor`, and at least one candidate was skipped only because that
  header is absent, instead of a silent empty page. A page that lists
  anything is unchanged, and an empty page cut short by the source-read
  budget, candidate scan, or page deadline keeps its `nextCursor` and
  `status`.
- `ReviewTaskPage` gains a required `status`, the `PageStatus` the work-item
  page already reports: `complete`, `budget_exhausted`, or
  `source_unavailable`. Either of the last two comes with a `nextCursor`. The
  review result feed and review history default to the inbox policy's
  `defaultPageSize` instead of 25.
- A plain `GET /v1/work-items/{itemId}`, its history, and its clocks return
  the retained item without actions or routing copy when the source's binding
  generation moved or the adapter refused the caller read as a moved binding,
  where they answered 409 `work-item.proposal-changed`. In those two cases a
  superseded item answers 409 `work-item.superseded`. Mutations still refuse a
  moved binding, and current source visibility still gates every read.
- A runtime source binding that breaks an adapter rule is refused at load
  with the member's key path, `sources.<id>.<member>`, and a static reason
  naming the rule and its bound. The configured value is never repeated.
- `caseworkctl check`, `explain`, `simulate`, and `package` name the policy
  key path and the field when `casework.yaml` names a `projection`,
  `contextProjection`, or `displayReference` field the source description
  does not publish, instead of telling you to repeat `source add`.
- `caseworkctl dev token` writes the client's `Registry-Casework-Profile`
  line beneath `Authorization` in `secrets/<client>.header` for a client bound
  to a Casework access profile, so the file is usable as-is with
  `curl --header @file`.
- Each review-producer operation lists only the problems it can return, and
  `caseworkctl attempt mark-uncertain` refuses an item that is not awaiting
  its source outcome with its own sentence.

## Registry Scheduling

- A hold's time to live starts when its capacity transaction decides, after
  the supply and per-caller locks, instead of when the request arrived. A hold
  created under lock contention carries the whole configured
  `holdPolicy.ttlMinutes` in its `expiresAt`, its stored expiry, and its
  `held` history event, and the task grant is re-checked at that same instant.
- Availability for an offering whose `horizonDays` reaches past the last
  representable instant is answered instead of panicking the request, and so
  is a caller-supplied availability or explain `start` at the edge of the
  calendar.
- Each request, and the hold-expiry, retention, and reminder dispatch passes,
  read `now` from the same clock the capacity transaction re-checks grants
  against. Production still reads the system clock.

## Evidence, Relay, Discovery, and Registry Manifest

- Evidence, Relay, Discovery, and Registry Manifest have no user-visible
  changes in this release.

## Shared platform and clients

- `registry-platform-ratelimit` is a new shared crate with two in-memory keyed
  limiters, `TokenBucketLimiter` and `FixedWindowCounter`, each capped at a
  fixed number of tracked keys. Evidence uses it for its request budget and
  failed-selector counter with no change in behavior.
- The shared platform crates gain an optional actor token on an RFC 8693
  exchange (`ExchangeAuthorization::upstream`), authorization code redemption
  with PKCE (`PrivateKeyJwt::redeem_authorization_code`), a deny-by-default
  content security policy builder (`CspBuilder::deny_by_default`,
  `with_form_action`, `with_style_src`), a purpose-free authorization audit
  event (`AuthorizationAuditEvent::without_purpose`), and a local test
  authorization server behind the `test-authorization-server` feature of
  `registry-platform-testing`.
- `registry-platform-dispatch` is a new shared crate: the at-least-once
  dispatch core with a fenced PostgreSQL lease machine, which the
  `registry-platform-hooks` notification delivery worker now runs on.
  `registry-platform-crypto` gains HMAC tags with constant-time
  verification, and `registry-platform-httputil` gains a side-effecting send
  class for data destinations, a typed AWS SigV4 send path,
  `ProductionAddressPolicy`, and a delivery-certainty report on a failed
  send.
- The BReg clients accept `fieldPath` on BReg `request.invalid` and
  `query.invalid` problems, and the Casework clients drop `sourceProfileId`
  from the decision and recovery requests and type the review-task page
  `status` and the `request.limit-out-of-range` problem, as described above.
- The committed Node.js loaders match the `@napi-rs/cli` 3.10.5 output the
  release build already produced, and the binding gates no longer rewrite
  them.

## Held out of this release

- Registry Messaging is in the source tree, with its runtime, operator tool,
  and client crates, but this release ships no Messaging binary, image,
  installer, or client package, and the unified Node.js and Python clients
  carry no Messaging namespace. Its changelog keeps every entry under
  Unreleased until Messaging joins a release.
- The BReg citizen MCP gateway (`breg-mcp`) and review page (`breg-review`)
  are in the source tree with their documentation, but this release ships no
  binary, image, or installer for either; build both from source.

## Release process

- The upgrade rehearsal seeds Casework state with `caseworkctl plan` and
  `apply` when the previous release's `caseworkctl` has an `apply` command, so
  it rehearses the upgrade from v0.36.0.
- The release runbook closes each release with a pull request that opens the
  next development version.

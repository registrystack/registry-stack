# Registry Stack v0.34.0

Registry Stack v0.34.0 is the beta-46 release. It adds consent-gated reads to
Base Registry Engine, lets one Casework source pair every change-request entity
of a BReg registry, and closes the lifecycle gaps found rehearsing a combined
BReg, Evidence, and Casework project, including BReg review recovery,
`bregctl apply`, and Casework review retention.

## Compatibility and migration

- BREAKING: BReg drops the `superseded` change-request state, which no
  transition ever wrote. A request is `draft`, `submitted`, `cancelled`, or
  `applied`, and a hook `when` condition naming `superseded` no longer
  compiles. The review result status `superseded` is unchanged.
- BREAKING: BReg refuses to compile an access profile with a `taskGrant` that
  holds `apply_request` (`access_profile.task_grant.operation_forbidden`). Move
  `apply_request` to a profile without delegated authority.
- BREAKING: BReg offers change-request actions from the settled review result.
  A rejected request offers only `cancel_request`; a send-back or an approval
  that expired before it was applied offers `revise_request` with
  `rebase: false` and `cancel_request`, not `apply_request`. BReg answers
  `409 mutation.conflict` to the shapes it no longer offers.
- BREAKING: `bregctl init --from publicschema` and the BReg starters follow
  PublicSchema `main` at commit `e5cfbbc` (version 0.3.0). The
  `agricultural-holdings` starter renames its holding-operator entities, routes,
  and fields to PublicSchema's agricultural holder names. Projects copied from
  an earlier starter keep working as written. PublicSchema defines `end_date`
  as the last day a period applies, so a period includes its end date.
- BREAKING: `bregctl history erase` requires `--acknowledge-irreversible`.
  Scripts that erase history must pass it.
- `bregctl apply` names what it refused before maintenance instead of
  reporting `apply.migration.failed` or `apply.package.refused`:
  `apply.database.unavailable` (nothing changed, retry),
  `apply.history.coverage_incomplete` (finish a pending erasure or rebaseline
  history), `apply.package.empty_plan`, and `apply.package.binding_mismatch`
  with the differing runtime key. Re-applying the active package now exits 0
  with `activation: already_active`. Update deploy scripts that match these
  codes or expect a repeated apply to fail.
- BReg no longer reports the review recovery code `result-recovery-expired`.
  Update any alert that matches it.
- The `bregctl explain access` JSON contract moves to `v1alpha3`, which adds a
  `consent` block. Update any tool that pins the earlier contract version.
- BReg install refuses a database that still holds review rows from before the
  current review workflow, instead of dropping them.
- BREAKING: the Casework BReg source binding generation now covers only the
  source id, the binding's `eventSource`, and the imported source description
  digest, so rotating a credential or tuning a timeout no longer supersedes
  work. Upgrading from v0.33.0 or earlier supersedes open work items from BReg
  sources once; claims, drafts, and pending attempts on them do not carry over.
  Finish or settle source-backed work before upgrading.
- BREAKING: `caseworkctl source add --apply` writes one lifecycle hook per
  paired BReg request entity, `casework-lifecycle-v1-<entity>`, and the
  Casework BReg source binding no longer accepts `eventType`. To migrate,
  remove `eventType` from each `*.breg-runtime.yaml` binding, which Casework
  otherwise refuses at startup, remove every bare `casework-lifecycle-v1` hook
  from the BReg `registry.yaml`, then repeat `caseworkctl source add --apply`.
  Deliveries BReg queued under the bare hook are refused, and reconciliation
  reads the same work back from the source.
- Casework deletes a review's clock occurrences with the request context of
  their round, at `terminalDays` instead of `accountabilityDays`, and the first
  retention pass after the upgrade removes existing rows past that point. An
  applicant who resubmits after the result window starts a fresh subject
  deadline instead of resuming a paused one.
- Casework keeps every sealed audit file instead of rotating and deleting the
  oldest. Before the first `serve` of v0.34.0, stop every earlier `casework`
  process, and if a numbered file such as `casework.ndjson.1` sits beside the
  audit file, move the audit file and its numbered siblings to an archive
  directory, as the Casework operate guide describes. The audit directory must
  be mode `0700`. Casework refuses to start until both hold.
- Casework reads its log level from `CASEWORK_LOG` (`error`, `warn`, or `info`,
  default `info`) and writes structured JSON. `RUST_LOG` no longer has any
  effect on the `casework` process.
- Run `casework migrate` to apply migration
  `0016_occurrence_identity_excludes_superseded.sql`. Migrate now refuses,
  naming each table and row count, rather than drop retained hosted work, and
  an older binary refuses a database a newer release migrated.
- Evidence requirement revisions no longer cover signing keys or revoked
  caller token keys, so a key rotation or revocation leaves every
  `configurationRevision` unchanged. Rebuilding an existing bundle with v0.34.0
  therefore moves each requirement's `configurationRevision` once. Give relying
  parties that pin those revisions the new values when you deploy the
  rebuilt bundle.
- `evidencectl check` now enforces each requirement's validity against the
  same fixed local signing maximum that `test` and a real target enforce, and
  `check --production` applies the review-marker gate that `package` applies.
  A project those commands would refuse no longer passes `check`.
- Registry Manifest, the shared platform crates, and Registry Scheduling have
  no user-visible changes in this release.

## Base Registry Engine

- Read permissions can require the subject's recorded consent with
  `requireConsent`. A row reaches a declared recipient organization only while
  a live consent for that recipient, purpose, and profile is recorded, and
  PostgreSQL checks it on every read. `bregctl module add consent` generates
  the consent records, actions, and profiles for one subject entity, and
  `bregctl check` reports `access.consent.ungated_client` for an ungated
  profile that reads the same rows.
- Adding a code to a field vocabulary is a compatible additive migration and
  needs no reviewed migration evidence. `bregctl diff` attaches a review reason
  to consent-related access changes.
- A fixed create or patch effect leaves out an optional field whose optional
  input the caller omitted, instead of refusing the request.
- Runtime metadata lists each change request's readable effects: target
  entity, selecting field, and the fields it sets and clears, filtered to what
  the caller may read. The Rust, Node.js, and Python clients expose them.
- BReg names a review's initiator by the configured principal claim rather
  than `sub`, so Casework's `excludeInitiator` refuses the submitter.
- Applying a package older than the active one is refused as
  `apply.package.older_than_active`, which points at rolling forward. A
  recorded post-baseline erasure no longer blocks successor packages.
- Reviewed successor plans drop stale change-request policies, `bregctl
  migration reconcile` fails on an unresolvable assessment, and reviewed
  migration refusals carry distinct `migration.review.*_refused` codes.
- The schema-test rehearsal and `bregctl dev start` activate review authority
  bindings, so a registry that delegates review no longer fails to start
  locally.
- An accepted review that the review authority still reports as pending is
  polled until it settles, so an approval that arrives after the submission
  recovery deadline is still reconciled and, in automatic mode, applied. A
  settled review clears an earlier lookup error instead of showing operator
  attention, and a result-lookup credential outage marks each due review
  `token-unavailable` instead of stalling silently.

## Registry Casework

- One Casework source can pair up to 32 request entities of a BReg registry.
  `caseworkctl source add` pairs them in one pass and writes a
  `casework-source-description/v1alpha2` description; a one-entity source keeps
  `v1alpha1` and its binding generation.
- `source add` accepts reviewer profiles shared with other requester clients,
  pairs create requests that have no `record` field, and reports a finding
  instead of refusing for a string `equals` `rowBoundaries` profile or a
  sibling entity whose review policy this project does not declare.
- `package.expectedPolicyDigest` pins the reviewed package; `casework` refuses
  to start on any other.
- `caseworkctl attempt mark-uncertain` recovers a pending attempt its actor can
  no longer recover, so it can then be settled.
- Review producers may name an `initiatorProfile` through which the initiator
  reads that request's requester-visible history. A decided task read carries
  `decidedByCaller`. Initiator refusals are named
  `403 review.initiator-excluded` and `422 review.initiator-required`.
- A review completion destination may present its secret in a named header,
  and `caseworkctl doctor` checks each destination secret.
- The professional-review starter's display schema matches its source, so its
  tasks reach the inbox, and the kind gains a `changes-requested` outcome.
- `caseworkctl check` and `source add` refuse a source-context review kind whose
  `displaySchema` the imported source description proves would hide its tasks
  from every reviewer, naming the kind, the property, and each rejected value.
- When the paired registry or request entity set changed, `source add --apply`
  names each differing file, writes nothing, and prints the move-aside and
  retry commands. It also refuses while the BReg `registry.yaml` keeps a
  lifecycle hook or `casework-reader` permission for a request entity the
  pairing no longer includes, naming the fragment to remove.

## Evidence

- A path selector value that cannot be carried as a request path segment is
  refused as `request.selector_invalid` before any access-attempt audit or
  source contact, instead of surfacing as `source.unavailable`.
- `evidencectl package` refuses a candidate whose copied `runtime.yaml` names
  another candidate's bundle directory, and a failing fixture run reports the
  cases it evaluated.
- `evidencectl source add` reports a `bregctl` version mismatch with its own
  diagnostic code and machine-readable versions in `--format json`.

## Release process

- Every release pull request now rehearses the upgrade from its predecessor:
  it writes state with the previous release's BReg, Casework, and Evidence
  binaries and fails if the new binaries serve it differently or hold fewer
  rows. The forward state path starts at v0.33.0.
- The release images are built on the current Debian 13 `distroless/cc` and
  `trixie-slim` base images, with their security updates.

[Changes since v0.33.0](https://github.com/registrystack/registry-stack/compare/v0.33.0...v0.34.0).
This remains a pre-1.0 Beta release for self-hosted institutional pilots.

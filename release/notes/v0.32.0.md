# Registry Stack v0.32.0

Registry Stack v0.32.0 is the beta-44 release. It binds exchanged tokens to the
assertion authority that issued their subject, extends token exchange across
the maintained clients, and lets Base Registry Engine re-check Evidence when a
governed request is applied.

## Compatibility and migration

- Local ThunderID development containers are now named and labelled per state
  root, so two worktrees of one project no longer share a container. A
  container started by v0.31.0 tooling is no longer found by `start` or `stop`,
  and `start` refuses because its port is occupied. Remove it once with
  `docker rm -f thunderid-<label>-<id prefix>` and start the session again.
  Retained state is untouched.
- Borrowed local Casework and Evidence development sessions now admit only the
  clients they declare, and check the shared issuer owner's assertion pairing
  at startup. A local project that relied on admitting every client of a
  shared issuer must declare its clients.
- `bregctl examples run` reads the scenarios a project declares in
  `examples/scenarios.json`. The three existing scenario names keep working; an
  unknown name is refused by the project's catalogue rather than by the command
  line parser.
- Production configuration needs no change. New settings are optional, and an
  existing static `tokenRef` Evidence provider binding remains supported.

## Assertion authority binding

Exchanged access tokens carry `registry_assertion_issuer`, derived from the
verified subject-token issuer and protected from configurable claim names and
signer-declared attributes. Evidence, Base Registry Engine, and Casework accept
an `assertionIssuers` map that pairs each client with the assertion issuers it
may present, and refuse a token exchanged through any other authority. When
the map is empty no pairing rule applies, and a token not obtained by exchange
carries no such claim.

## Token exchange in the clients

- The Base Registry Engine, Relay, and Casework clients can obtain RFC 8693
  exchanged tokens bound to one verified person or one approved Casework task
  grant. The tokens do not outlive the authority deadline, and credentials are
  redacted from diagnostics.
- The Rust, Node.js, and Python Evidence clients can authenticate through token
  exchange. An exchange-backed profile must pin its resource and scopes, and
  the client refuses before requesting a token when the pinned client,
  endpoint, issuer, audience, resource, or scopes differ from discovery.
- Evidence clients can pin a definition's revision, type, purpose, assurance,
  and format before requesting, and verify a retained signed result offline
  later.

## Base Registry Engine and Evidence

- Governed requests can declare application preconditions. Base Registry
  Engine re-checks fresh signed Evidence and linked-record state at Apply and
  refuses the whole application when either is stale, changed, or missing.
- Evidence provider bindings accept exactly one of `tokenRef` or a refreshing
  `privateKeyJwt` credential, so long-running governed actions no longer need a
  restart to renew their Evidence access.
- Evidence questions can answer with a governed `bounded-identifier` value:
  a declared prefix followed by a bounded ASCII suffix.

## Development and security

- Local development can compose Base Registry Engine, Evidence, and Casework
  under one shared issuer. `evidencectl access client add` adds task-grant
  (`--grant-bootstrap-scope`) and first-party exchange
  (`--first-party-bootstrap-scope`, `--first-party-bootstrap-resource`,
  `--first-party-issuer`) modes.
- `bregctl dev` can bind local Evidence providers, and `bregctl examples`
  supports action attempt recovery.
- The Base Registry Engine, Casework, Evidence, and Relay runtimes and their
  command-line tools update `rustls` to 0.23.45 for RUSTSEC-2026-0285.
- Candidate publication is plan-driven: `registry-release publish --plan`
  re-verifies the reviewed candidate, pushes only the exact annotated tag, and
  resumes an interrupted publication.

# Registry Stack v0.25.0

Registry Stack v0.25.0 is the beta-36 minor release. It makes an Evidence
fixture run diagnosable by a program rather than only by a person: each case
now carries a closed, value-free account of what the author expected, what the
run observed, and which expectation disagreed. The minor version reflects one
breaking change in adopter tooling, described below. It does not retire a
product, change a runtime API, or require a Registry Manifest format migration.

## Breaking change: `evidencectl fixtures run --json`

- The `trace` field of each fixture report changes from a string to an object.
  It previously carried the verbatim text of `evidence evaluate --explain`;
  it now carries that command's structured JSON document. A consumer that
  reads `trace` as text, or parses it with a line or substring match, must be
  updated to read the document's fields.
- `evidencectl fixtures run --explain` now asks `evidence` for the JSON form
  rather than the text form, and pretty-prints the same value-free document
  under each step line in the human report. The driver totals `evaluatedCases`
  from those documents instead of scraping the summary line, so it interprets
  no Evidence semantics of its own.

## Structured fixture diagnostics

- Each case in the `--explain --explain-format json` document can carry
  `expectedResult`, `observedResult`, `reasonCode`, and `findingCodes`.
  A result has one of eight closed classes: `match`, `no-match`, `ambiguous`,
  `evidence-unavailable`, `source-unavailable`, `service-unavailable`,
  `bundle-refused`, or `selector-refused`.
- A matched value is reduced to a bounded classification such as
  `boolean-true`, `integer`, `bucket`, or `structured`, never to the value
  itself. `reasonCode` names which closed evaluator outcome produced the
  observation, and `findingCodes` names which authored expectation disagreed.
- None of these fields carries a source, selector, SQL statement, credential,
  or governed result value. A fixture's own `diagnosticsExclude` canaries are
  still checked against both rendered forms on every run, including a run that
  stopped early.
- For a controlled-category concept only, `categoryClasses` identifies an
  allowed result by its zero-based concept position in the requirement and its
  zero-based value position in that concept's captured governed codelist. The
  field appears only after the output is proven to belong to that codelist,
  and an arbitrary string keeps only the shape `string`.
- A failed run now reports `evaluatedCases` rather than omitting it. The count
  is the number of cases the run reached, so a reader can tell a fixture that
  failed at its ninth case from a toolchain that produced no document at all.
  The field is absent only when the run failed before it reached any case.

## Selecting one fixture or one case

- `evidence evaluate --case <id>` evaluates only the case with that exact
  identifier, and `evidencectl fixtures run` gains `--fixture <path>` and
  `--case <id>` for the same purpose across a project. `--case` requires
  `--fixture`, so a case identifier is always resolved against one named
  fixture rather than searched for across a project.
- A selector that names nothing is refused: an unreferenced fixture path with
  `selected fixture is not referenced by the project`, and an absent case
  identifier with `selected fixture case is unavailable`. Neither message
  repeats the rejected value. Selectors are operator input and the diagnostics
  stay value-free.

## Documentation

- The Evidence documentation describes both Evidence source transports. The
  v0.24.0 note announced this, but the content was reverted before that tag
  was cut and only lands here.

## Release boundaries

- Beta publication promotes one verified candidate from protected `main`
  without rebuilding binaries, client packages, documentation, or runtime image
  manifests.
- Candidate image scanning must complete successfully and applicable advisory
  decisions must carry the required exposure evidence.
- Exact already-completed image and client-registry operations may be
  reconciled during a retry. A mismatched immutable image or package version
  requires a new release version.
- Hosted deployments, external conformance, and adopter-specific rollout
  exercises remain outside this release's critical path.

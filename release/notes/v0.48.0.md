# Registry Stack v0.48.0

Registry Stack v0.48.0 is the beta-60 release. Base Registry Engine (BReg) can
generate an Evidence source that requires specific returned values, allows
selected facts to be empty, and carries compatible field patterns into its
schemas. A webhook can use `changedAny` when any one of two or more fields must
trigger it. BReg also refuses derived reads whose value can depend on rows the
reader cannot see.

## Compatibility and upgrade

Use matching v0.48.0 runtimes, tools, and clients. Back up each deployment and
follow [upgrade and retire](https://docs.registrystack.org/operate/advanced/upgrade-and-retire/).

The predecessor rehearsal starts from v0.47.0 and covers the retained Evidence
and Messaging state. This release adds no Evidence or Messaging state migration.

BREAKING for generated BReg Evidence sources that return a patterned or decimal
fact. Regenerate and review the source before you import it:

- A fact keeps its declared pattern in the fact and response schemas. A decimal
  fact states its precision and scale as a pattern. These schema bytes enter the
  `behaviorRevision`, so the generated pack version changes.
- The generator refuses a pattern that PostgreSQL and Evidence read differently,
  or one that Evidence cannot compile. Rewrite the pattern with explicit
  characters, such as `[A-Za-z]` or `[^\n]`, or use a reviewed custom Adapter
  pack.

BREAKING for a BReg access profile that reads an incomplete derived value.
`bregctl check` now refuses the profile when its derived SQL can omit source rows
under the reader's row security. It also refuses `LIMIT` or `OFFSET` on the rows
the derived relation returns and in every `FROM` subquery, including a correlated
`LATERAL` subquery. Move row selection into a correlated expression subquery, or
remove the limit. Align the source grants with the reader grant so each value is
derived from all rows the reader may use.

## Base Registry Engine

### Generate bounded Evidence sources

`bregctl generate evidence-source` adds two optional inputs:

- `--require-value <field>=<value>` admits only records whose fact has one of
  the listed values. A refused record and an unknown record give the Evidence
  caller the same answer. The Evidence audit for the single request and the
  `evidence_source_lookups_total` metric distinguish them.
- `--optional-fields <field>,...` omits an explicit null fact without refusing
  the record. An absent response key remains a source protocol error.

A required value is defence in depth inside the generated lookup. It does not
replace the access profile's row boundary. Every rule enters the
`behaviorRevision`, and the generator refuses a schema or lookup script that
Evidence cannot load.

### Trigger a webhook when any field changes

A `fields` hook condition accepts `changedAny` with two or more fields. The hook
matches when at least one listed field differs between the before and after
snapshots. Existing `changed` conditions keep their all-fields meaning.

`changedAny` applies only to the `patched` trigger. It cannot be combined with
`changed`, and encrypted or unknown fields remain refused.

### Refuse incomplete derived reads

Derived SQL runs under the caller's row security. A derived value was previously
served as complete when the reader could see only some linked rows. BReg now
checks every profile and read-path grant that reads, filters, or sorts a derived
field:

- Every other Record type the SQL reads needs a grant that reads rows.
- Its `rowBoundaries` must match the reader grant in the same order.
- Its required purposes must not exclude the purpose under which the read runs.
- SQL that combines or selects among other rows of its own Record type treats
  that type as a source too.

A record condition, membership boundary, consent requirement, or uncorrelated
subquery that can withhold source rows raises a finding for operator review.
BReg cannot prove that linked rows carry the same boundary values, and the
configuration guide records that residual.

## Other changes

- The unreleased reference Helm chart refuses IPv4-mapped IPv6 addresses that
  bypass an IPv4 egress block.
- Runtime and build dependencies move to their current reviewed versions,
  including the security fix in `cookie` 0.18.3.

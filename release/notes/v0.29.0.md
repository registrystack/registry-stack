# Registry Stack v0.29.0

Registry Stack v0.29.0 is the beta-41 release. It adds governed request
attachments, reviewer explanations, and local event inspection to Base Registry
Engine, with attachment APIs in the Rust, Node.js, and Python clients.

## Compatibility and migration

- BREAKING: request-lifecycle webhook bodies add the required boolean
  `request.reasonPresent` and an optional `request.reason` string for rejection
  and revision requests. Update receivers that validate the previous closed
  schema before activating v0.29.0, and review destination classification and
  retention for the explanation text.

- Install `breg`, `bregctl`, and `mint` from the same release. `bregctl dev` now
  refuses mismatched runtime versions before starting the local registry and
  reports the prerequisite that needs replacing.
- Rebuild, rehearse, and activate registry packages through the maintained
  schema-test and migration workflow when upgrading. Standard successor apply
  installs the product-owned attachment tables and decision columns; do not
  apply them by hand. Registries that do not declare attachment slots need no
  attachment runtime configuration.
- Choose attachment storage and verification before the first upload. Omitted
  `attachmentStorage` uses PostgreSQL; omitted `attachmentVerification` disables
  external verification. The first upload pins these bindings for the registry,
  including after content erasure. Changing the storage backend, verification
  endpoint, policy generation, or enabled mode afterward is unsupported.
  Credential rotation and verification timeout changes preserve the binding.
- S3 attachment storage requires a distinct `identity.databaseId` per database,
  an operator-bound endpoint and credentials, and disabled bucket versioning.
  Follow the runtime configuration reference before enabling it. Configure
  backup expiry and external verifier retention separately from registry erasure.
- Reject and request-revision actions accept an optional `reason` of up to 4096
  Unicode characters. Existing action bodies remain valid. Request grants
  default to `readableRequestFields: [reason]`; set it to `[]` on profiles that
  must not receive explanation text. Supplied reasons also enter rejection and
  request-revision lifecycle event payloads independently of this read setting;
  review event classification and destination authority before enabling them.
- For attachment downloads larger than the client's default 8 MiB response
  bound, raise the response-byte limit explicitly. Attachment download responses
  use `Content-Disposition: attachment` without a filename; callers choose their
  own saved filename.

## Request attachments

Declare attachment slots on change-request entities and grant their slot IDs
through the existing readable and writable field controls. Slots define size,
content type, classification, and whether a file is required for submission. The engine owns
upload state, computes size and SHA-256, applies owner and profile authority,
and binds uploads to request concurrency and idempotency controls.

Storage can use PostgreSQL or an operator-configured S3 service. Optional HTTP
verification runs asynchronously: pending or rejected content cannot be downloaded.
Required slots must be filled. When verification is enabled, every filled slot,
including an optional slot, must be approved before the request can be submitted.
Classification is metadata for callers, not an authorization grant.

Request retention now erases attachment references and removes bytes after the
last retained reference is erased. S3 failures remain in a durable deletion
queue; run `bregctl request-retention cleanup-attachments` to retry deletion and
recheck tombstoned keys. Registry erasure does not remove copies held by backups
or an external verifier.

The Rust, Node.js, and Python clients select slots from caller-filtered metadata
and support bounded upload, download, and delete exchanges. Local validation
rejects empty or oversized uploads and unaccepted content types before sending.

## Review and local development

- Request reads expose current and retained proposal decisions, with explanation
  text filtered by the selected access profile. Request-detail erasure removes
  text while retaining decision facts and whether a reason was present. History
  pagination is bounded and preserves whole proposals.
- Journey fixtures can capture the record created by an applied request for a
  later step. Refused logical references and local-start failures name the
  failed check without including authored values.
- `bregctl dev` receives declared webhook events through an owned local receiver.
  `bregctl dev events` shows receipts; `--include-payload` explicitly reveals
  captured development values. Receipts persist across a normal stop and are
  erased with the owned development storage on `dev stop --remove`.
- Create-bearing access grants keep their row-boundary field writable so the
  caller can supply the value constrained by the claim. Validation now explains
  this requirement instead of advising removal of that field.

## Documentation and release delivery

The documentation adds eSignet authentication and OpenFn integration guidance,
with the Relay adaptor described against its supported V1 route surface. The npm
client pages describe the unified package and its platform implementation packages.
Release preparation automates the canonical documentation archive and records
reviewed command content separately from the workspace version.

## Known limitation

The Rust, Node.js, and Python Base Registry Engine clients currently report a
valid immediate-action business refusal as a protocol error. The raw HTTP API
still returns `422 action.refused` with the declared refusal details. This
limitation predates this release; a client correction is tracked in
[#972](https://github.com/registrystack/registry-stack/pull/972). Separately, valid
`request.invalid` responses carrying `fieldPath` are also reported as protocol
errors; that case is outside the scope of #972.

# Registry Stack v0.30.0

Registry Stack v0.30.0 is the beta-42 release. It introduces Registry Casework
and its Rust, Node.js, and Python clients, completes Base Registry Engine client
capability coverage, and updates Evidence and Casework configuration workflows.

## Compatibility and migration

- Registry Mint is retired. This release ships no Mint binary or container.
  Configure a standards-based OAuth issuer; the maintained local development
  commands use pinned stock ThunderID 1.0.1. Mint configuration is not migrated.
  This replacement does not preserve Mint external signing-key custody or its
  durable pre-response issuance audit. Deployments requiring those properties
  must select an issuer that supplies them before upgrading.

- Registry Casework is a new product in this release. The pinned
  `casework-install.sh` installs matching `casework` and `caseworkctl`
  binaries. A Casework deployment needs
  its own PostgreSQL database, token verification, and explicit access profiles.
  A source-backed project also needs a governed Base Registry Engine source and
  a configured source profile. Configure an OAuth issuer for deployed access;
  `caseworkctl dev` uses pinned stock ThunderID 1.0.1 for local development.
- Casework operator configuration uses `casework-runtime/v1alpha1`. Set an
  absolute `package.root` for the authored `casework.yaml`, put network fields
  under `listener`, configure secret providers explicitly, and use
  `audit.hashKeyRef`. Replace the removed runtime OIDC `principalClaim` with
  each applicable `accessProfiles[].principalClaim`. Rebuild any project
  authored against the earlier, unpublished Casework checkpoint shape before
  starting v0.30.0.
- Evidence authoring and deployment commands now use separate project forms.
  Use `evidencectl init`, `check`, `explain`, and `test` while authoring, then
  `evidencectl package` to produce a deployment project. Review scripts that
  assumed one project form or parsed previous diagnostic text. The docs and
  CLI reference carry the updated command sequence.
- Base Registry Engine accepts both RFC 9068 `typ` spellings, `at+jwt` and
  `application/at+jwt`, when either is the configured access-token type. Static
  JWKS operators can use the bounded key-refusal warning to confirm rotation
  and replace a pinned document reference. Other token types remain refused.
- Base Registry Engine request metadata now exposes
  `readableRequestFields` per selected profile. Request action responses
  include `actorReference`, and grants can expose review state and actor
  references. Review client handling and profile disclosure before relying on
  those additional fields.

## Registry Casework

Casework coordinates one accountable inbox over source-owned BReg work or
source-free hosted decisions. It provides caller-visible inbox pages, claim and
release, private drafts, correction requests, approval and separate application,
team assignment, queue routing, working-day clocks, and bounded recovery of
uncertain source attempts. Current source visibility and action authority remain
with BReg. Hosted decision requests have a separate Requester role, declared
display schema and outcome vocabulary, terminal polling, and audited actor
accountability. The maintained Casework clients are included in the unified
Node.js and Python packages.

Casework has no staff-facing UI, bulk decisions, automatic outcomes, or outbound
delivery. Clock events record reminders or move due work under policy; they do
not decide outcomes or change the source. Use the [Casework deployment guide](https://docs.registrystack.org/operate/casework/)
and [first Casework tutorial](https://docs.registrystack.org/tutorials/first-casework/)
for the two supported paths.

## Existing products and clients

- The Rust, Node.js, and Python Base Registry Engine clients now cover the
  maintained read, mutation, batch, lifecycle, immediate-action, GeoJSON, and
  metadata capabilities. A declared immediate-action `action.refused` response
  is a typed business refusal with its bounded reason, rather than an opaque
  protocol error.
- The published BReg problem-code reference includes
  `action.evidence_failed` for an unavailable or rejected Evidence dependency.
  Base Registry Engine also bounds unknown-key warnings to avoid repeated
  diagnostic emission during token verification failures.
- The documentation now covers Casework configuration, operation, retention,
  API, and clients. It also updates the Evidence authoring flow and BReg
  configuration and client references.

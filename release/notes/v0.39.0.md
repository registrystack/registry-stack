# Registry Stack v0.39.0

Registry Stack v0.39.0 is the beta-51 release. It is the first release
without Registry Relay: the `relay` and `relayctl` binaries, the Relay
installer, the Relay image, and the Relay client namespaces are gone, and
v0.38.0 remains the last release that carries them. Every product now reads
only the state v0.38.0 wrote, and the compatibility paths that served older
releases are removed. Base Registry Engine (BReg) adds governed statistical
datasets: count datasets a project declares, read live as exact counts and
published as disclosure-controlled immutable releases. It also closes its
derived SQL grammar, enforces declared types on derived values, matches text
searches without regard to case, stops when a background worker dies, and
publishes worker, queue, and active-package metrics. Registry Casework answers
an empty, recently reconciled inbox as `complete`. A nightly channel publishes
evaluation builds from protected `main`.

Upgrade to v0.39.0 from v0.38.0, and from no earlier release: finish the
v0.38.0 upgrade first. Before upgrading, replace every Relay deployment with a
retained design or keep it pinned to v0.38.0, and remove Relay origins from a
Registry Discovery index. Every BReg project compiles to a new
`registryRevision` and installs the statistical release store: rebuild its
package against the deployed one and apply it once before starting the
upgraded `breg`, and repin a Casework BReg source that pins it. `bregctl dev`
and `caseworkctl dev` take new default database ports, and automation that
matches `bregctl` refusal codes for a held migration lock or an unpinned
package must match new codes.

## Compatibility and migration

Run the same release on every runtime, tool, and client, and upgrade in the
order [upgrade and retire](https://docs.registrystack.org/operate/advanced/upgrade-and-retire/#upgrade-in-this-order)
describes: BReg first, then Casework, then Evidence, then Scheduling, then the
clients. Take the backups it names first; no product migrates backwards.

BREAKING: before 1.0, a release reads only the state its immediate predecessor
wrote. v0.39.0 reads state written by v0.38.0 and nothing older. If you run an
older release, upgrade one release at a time and finish each release's upgrade
steps before starting the next. The product sections below list what this
removes; each product changelog lists every removed path.

### Retire Registry Relay before upgrading

- BREAKING: Registry Relay is retired and absent from v0.39.0. The `relay`
  and `relayctl` binaries, the Relay installer, the
  `ghcr.io/registrystack/relay` image, the `registry-relay-client` Rust crate,
  the `relay` namespace of the unified Rust, Node.js, and Python clients, and
  Relay authoring support in the editors are removed. There is no automatic
  migration, and no deployed container, source database, or credential is
  changed for you. Choose Base Registry Engine, Evidence Gateway, or Registry
  Manifest for each consumer and source, and remove `relay` client imports
  before moving an application to the v0.39.0 clients. These capabilities do
  not reproduce Relay's contract, routes, policy model, or wire formats.
- Relay receives no security fixes once v0.39.0 is released. A deployment
  pinned to v0.38.0 keeps a Relay runtime with no promised remedy for a
  vulnerability found later: treat the pin as a bounded migration state. The
  v0.38.0 release keeps its Relay artifacts and its documentation archive.
  See the
  [Registry Relay retirement decision](https://docs.registrystack.org/decisions/registry-relay-retirement-2026-10-03/).

### Upgrade Base Registry Engine from v0.38.0

- Rebuild the deployed project with the v0.39.0 `bregctl test` and
  `bregctl package`, each naming the deployed package with
  `--baseline-package`, as
  [test and package the successor](https://docs.registrystack.org/operate/breg-changes/#test-and-package-the-successor)
  gives in full. Apply the result with `bregctl plan` and `bregctl apply`
  before restarting every `breg` process on the new binary, in the order step
  4 of
  [Upgrade in this order](https://docs.registrystack.org/operate/advanced/upgrade-and-retire/#upgrade-in-this-order)
  gives. This applies to every project: a package v0.38.0 built no longer
  loads in the v0.39.0 runtime, and the v0.39.0 tooling accepts it only as
  the predecessor of that one apply.
- BREAKING: every project compiles to a new `registryRevision` and a new
  managed schema fingerprint, because every package installs the engine-owned
  statistical release store, including a package that declares no dataset.
  Starting the upgraded `breg` before the rebuilt package is active fails with
  a generic compiler-derivation error: stop it, build and apply the successor
  with the v0.39.0 `bregctl`, then start `breg`. The runtime role cannot
  update or delete the release tables, so keep the separate migration
  credential for the apply. The three entries after this one name what else
  changes in the rebuilt package of the projects they describe.
- BREAKING: a project that declares immediate actions compiles to a new
  `registryRevision`. The generated row policy orders the fields an action
  writes with the `"C"` collation, and the stored action results gain an index
  by target entity, record, and revision. `bregctl test` reports the advisory
  `migration.rehearsal.baseline_fingerprint_drift` finding for the index, and
  the apply installs it. Action contract fingerprints are unchanged, so
  retained idempotent retries still match.
- BREAKING: a project with derived string, text, decimal, integer, or
  vocabulary fields compiles to a new `registryRevision`, because the
  generated views now enforce the declared type before casting. The earlier
  package fails artifact rederivation with the upgraded runtime, so apply the
  successor before switching the runtime. The rehearsal may report
  `migration.rehearsal.baseline_fingerprint_drift`. Successor activation
  replaces every retained compatible derived view, even when its authored SQL
  is unchanged. Existing import and export continuations keep their earlier
  package and fingerprint binding and must not resume under the successor.
- BREAKING: a project whose projected fields of one vocabulary admit different
  codes compiles to a new `registryRevision`, because the generated Registry
  Manifest codelist carries the union of those codes where it carried the last
  field's.
- BREAKING: derived SQL accepts only reviewed PostgreSQL grammar. `JSON_QUERY`,
  `JSON_TABLE`, `XMLTABLE`, SQL/JSON aggregates and constructors, XML
  functions, `NATURAL` and `USING` joins, source and join column alias lists,
  whole-row references, row constructors, attribute-notation function calls,
  and casts to arrays, catalog reference types, XML, money, and
  timestamp-with-time-zone are refused. `JSON_VALUE` and `JSON_EXISTS` stay
  available. Revise derived SQL that uses a refused construct before
  rebuilding.
- A derived value that does not fit its declared type is no longer silently
  truncated or rounded. It raises a value-free database error naming its
  entity and field, and an API read of it answers `503 source.unavailable`.
  Check derived SQL against the declared length, scale, precision, range, and
  vocabulary of each field before upgrading.
- BREAKING: the `contains` and `prefix` text-search operators (`contains` and
  `startswith` in `$filter`) match without regard to case on string, text, and
  vocabulary-code fields, on current and snapshot reads. Their operands may be
  shorter than a string's `minLength` or name part of a vocabulary code, and
  `%`, `_`, and backslash match literally. `equals` and `in` keep exact,
  case-sensitive matching. A caller that relied on case-sensitive `contains`
  or `prefix` results must filter them itself.
- BREAKING: a background worker (webhook delivery, attachment verification,
  review, or subject access-log retention) or the metrics listener that panics
  or returns before shutdown ends `breg` with exit status 1, where the process
  kept serving without the task. Run `breg` under a supervisor that restarts
  it on failure, such as an orchestrator's restart policy, systemd
  `Restart=on-failure`, or Docker `--restart on-failure`.
- BREAKING: `bregctl apply` and `plan` report a migration lock another session
  holds as `apply.database.in_progress`, where they reported
  `apply.database.unavailable`. `history erase`, `history rebaseline`,
  `field-encryption erase-history`, `evidence-retention erase-expired`, the
  `request-retention` commands, the `import-authority` commands, and
  `instance-claim adopt` report the same held lock under their own
  `in_progress` codes. `webhook list`, `replay`, and `discard`, the
  `request-retention` commands, the `import-authority` commands, and
  `evidence-retention erase-expired` refuse a configured package that
  `package.expectedDigest` does not pin under `*.package.refused` codes.
  Automation that retries or matches the earlier codes must match the new
  ones; the BReg changelog lists each pair.
- BREAKING: a reviewed migration's `rehearsal.json` no longer carries
  `proofs`. `bregctl test` and `package` refuse a receipt that still carries
  the member with `migration.review.receipt_proofs_retired`; remove it and
  regenerate the receipt. Like every package v0.38.0 built, one built with
  such a receipt no longer loads in the v0.39.0 runtime; the v0.39.0 tooling
  still reads it as the predecessor of the upgrade apply and ignores its
  `proofs` values.
- BREAKING: the WebAssembly executor builds Wasmtime without its default
  features. A WASM action or hook handler module that uses GC types, exception
  handling, or `externref` is refused at compile time with
  `action.handler.module_invalid` or `hook.handler.module_invalid`; rebuild
  such a guest without the proposal. A build without the `wasm` feature
  refuses a WASM hook handler with `hook.handler.wasm_build_unsupported`, as
  it already refused a WASM action handler. Default builds carry the feature.
- BREAKING: `bregctl dev` takes PostgreSQL loopback port 15432 on a first
  start, where it took 55432. A session that already started keeps its port.
  Anything that connects to a new session's database by the old default needs
  the new port, or `--database-port 55432` on the first start.
- BREAKING: `bregctl dev` pins a session on the compiled registry revision,
  the package `sourceRevision`, and the canonical JSON form of
  `tests/journeys.yaml` and the clients file. A `.breg/dev` session an earlier
  release started reads as changed inputs: run `bregctl dev stop --remove` on
  it before starting it with this release. No command carries its records
  across.
- BREAKING: the paths that served only releases before v0.38.0 are removed.
  `bregctl project migrate`, `bregctl apply
  --acknowledge-retired-audit-discard`, `bregctl field-encryption keygen
  --out`, `bregctl dev start --clients`, `--mint-port`, and `--mint-bin`, and
  `breg --config` are gone; use `--output`, `--clients-file`, and
  `--runtime-config`. A database that holds registry tables but no activation
  ledger is refused as `*.database.unrecognized` and no longer adopted. A
  `package/v1` package, the removed project and runtime configuration keys,
  dev state version 1, and a `bregctl-data/v1` import sidecar are refused as
  ordinary unreadable input, without a message naming a replacement. Schema
  install no longer upgrades tables created before v0.38.0.
- A predecessor package whose query temporal bindings lack `valueKind`, or
  whose compiled model or query inventory carries a temporal `scopeFields`, is
  refused with a derivation error. No release since v0.36.0 writes one.
  Rebuild and activate such a package with v0.38.0 before you upgrade.
- Immediate actions advance the shared history commit head in the same
  transaction as their effects, so latest snapshots and coverage rebaselines
  observe action writes. Action revisions an earlier release wrote are not
  backfilled and still cause coverage rebaselining to refuse: rebuild an
  affected pre-1.0 development database before using history snapshots or
  coverage rebaselining.
- Revision-history reads of a record an immediate action wrote answer again.
  A revision an earlier release journaled under the action's effect
  identifier is not rewritten: once a later package removes or renames that
  action or effect, or changes the effect's operation, that revision's detail
  read and any list page that includes it answer `503 source.unavailable`.

### Upgrade Registry Casework from v0.38.0

- Every BReg project compiles to a new `registryRevision` in this release,
  so a Casework BReg source pins a revision the upgraded BReg no longer
  serves, and Casework startup refuses it. After the BReg apply above, repin
  with
  `caseworkctl source add BREG_PROJECT --project PROJECT --source-id ID --apply`,
  then package, plan, and apply the Casework project once, and only then
  start `casework`, as step 5 of
  [Upgrade in this order](https://docs.registrystack.org/operate/advanced/upgrade-and-retire/#upgrade-in-this-order)
  orders. No Casework schema migration is pending.
- A page that waits only for source discovery no longer issues a cursor that
  repeats the same position. Retry such a `budget_exhausted` page without a
  cursor after reconciliation. The retried walk starts from the first position
  and can return items earlier pages returned: deduplicate work items by
  `itemId`, and replace holdings totals instead of adding to them.
- BREAKING: `caseworkctl dev` takes PostgreSQL loopback port 15433 on a first
  start, where it took 55433. A session that already started keeps its port.
  Use the new port, or `--database-port 55433` or
  `CASEWORKCTL_DEV_DATABASE_PORT` on the first start.
- `caseworkctl dev start` and `dev stop` report a local session failure under
  `caseworkctl.dev.*` codes, still exiting 3. A script that matched
  `caseworkctl.io-failure` or `caseworkctl.operational-failure` for these
  failures sees the new codes.
- BREAKING: the paths that served only releases before v0.38.0 are removed.
  `caseworkctl dev start --clients` is gone; use `--clients-file`. Retained
  dev state from a Mint-era session, or dev state that lacks `binaries`,
  `sources`, or `borrowedScopes`, is refused as invalid and left untouched:
  stop that session with the release that wrote it, or move `.casework/dev`
  aside. Recovery of a prepared BReg source action refuses saved attempt
  evidence that carries no `version`; every release has written one, so no
  retained attempt is affected.
- `caseworkctl source add` no longer refuses a BReg `registry.yaml` by name
  for carrying the bare `casework-lifecycle-v1` hook that releases before
  v0.34.0 wrote. v0.38.0 refused that hook, so no project it paired carries
  one. A project that still does keeps it as an authored hook: remove it from
  `registry.yaml` by hand.

- BREAKING: `evidencectl dev --mint-port` and `--mint-bin` are unknown

### Upgrade Registry Scheduling, Messaging, Render, and Registry Manifest from v0.38.0

### Upgrade Registry Discovery from v0.38.0

- BREAKING: Discovery accepts only Evidence service descriptions and
  selections. `discoveryctl` refuses to build an index from a Relay
  description, the `discovery` runtime refuses to start on a package index
  that contains a Relay service, and the Discovery clients refuse a Relay
  selection. Before upgrading, remove Relay origins from a mixed index, then
  rebuild the whole index with `discoveryctl package`. A persisted Evidence
  selection keeps its wire bytes and its binding identity.
- BREAKING: service search accepts `serviceKind=evidence` only, and no longer
  takes the `semanticClass` and `operationFamily` filters, which matched only
  Relay services. A search that sends `serviceKind=relay` or either filter
  answers `400` with the invalid-request problem. Remove them from callers.

## Base Registry Engine

- A root project may declare count datasets under `statisticalDatasets`: a
  unit entity, a population filter, a flow or stock period, boolean or
  closed-vocabulary dimensions, and explicit disclosure parameters. A live
  profile reads exact counts its own list grant could already count. One
  publisher publishes immutable, versioned releases under minimum-count
  suppression and rounding, and a released-data reader needs no record
  permission. Seven operations under `/v1/statistics/` serve JSON or CSV;
  publication and withdrawal are idempotent, and a withdrawn version keeps
  its header and reason without `contentDigest`. `bregctl statistics publish`
  and `withdraw` drive the lifecycle over HTTP, and the Rust, Node.js, and
  Python clients carry the operations. BReg has no release scheduler: run the
  publish command from your own.
  [Publish a statistical series](https://docs.registrystack.org/configure/breg-statistics/)
  gives the steps.
- The statistical disclosure method accepts stated inference risks: interval
  arithmetic over suppressed cells and rounded totals can pin suppressed
  values, exact zeros disclose absence, deterministic rounding permits
  differencing between releases, and the compiler checks only that each
  disclosure parameter is at least two. There is no privacy budget and no
  differential privacy. Read the
  [statistical dataset explanation](https://docs.registrystack.org/explanation/breg-statistical-datasets/)
  before granting readers access.
- Text search finds a record whatever the case of the typed term: `contains`
  and `prefix` match case-insensitively under PostgreSQL's locale rules, treat
  `%`, `_`, and backslash literally, and do not fold accents or rank results.
  An empty term matches every non-null value the caller's read profile
  permits. Matching stays restricted to compiled filter capabilities and rows
  the caller is already authorized to read.
- `bregctl check` names each unresolved field with its entity and its profile
  or constraint, and reports
  `access.profile.create_required_field_not_writable` when a direct create or
  import grant omits a required writable stored field. The finding fails a
  check only under `--deny-findings`.
- Derived SQL passes a closed grammar allowlist, and expressions inside
  accepted SQL/JSON functions receive the same relation, function, and
  encrypted-column checks as other derived SQL. Cast targets are limited to
  reviewed built-in scalar types, and column names resolve against the
  compiler-known output of the exact source, CTE, or subquery range in each
  `SELECT` scope.
- Generated views enforce string minimum and maximum length, text maximum
  length, decimal scale, precision, and range, integer integrality and range,
  and vocabulary membership on derived values before casting.
- An immediate action whose effects write fields that a locale collation
  orders differently from byte order, such as `award-number` and `awarded-by`
  under `en_US.utf8`, no longer answers `503 service.unavailable`. A hook
  proposal whose action commits effects at different revisions records the
  same resulting revision on every database collation.
- A missing or malformed `Idempotency-Key` on an immediate action answers
  `request.invalid` naming the header in `fieldPath`.
- `manifestProjection.vocabularies[].concepts` may label every code that any
  visible field of the vocabulary admits.
- A read abandoned at the request deadline (`504 request.timeout`) cancels its
  in-flight PostgreSQL statement and keeps its pool slot until PostgreSQL has
  stopped it, so the runtime session count stays within the pool's `maxSize`
  under overload.
- The metrics listener publishes `breg_worker_last_success_age_seconds` by
  `worker`, `breg_queue_oldest_pending_age_seconds` by `queue` for webhook
  deliveries, review submissions, and application jobs, and
  `breg_active_package_info` with the `package_digest` this process verified
  at startup. Anyone who reaches the metrics listener can read the package
  digest.
- A failed review worker iteration writes a warning with the closed code
  `review.worker.iteration_failed`. The review worker backs off an unavailable
  review authority's result feed from 1 second up to 60 seconds, warning once
  when it becomes unavailable and once when it recovers. The attachment
  verification worker claims the next due job as soon as it finishes one.
- A review-completion callback that fails authentication answers the
  registered `401 authentication.refused` problem instead of the undocumented
  `review_completion.authentication_refused` code.
- `bregctl apply` and `bregctl plan` take `--expected-digest`, the `sha256:`
  package digest `plan` and `package` print, and refuse a package with another
  digest as `apply.package.digest_mismatch` before any database contact.
  A configured package that `package.expectedDigest` does not pin is refused
  with a message naming the pinned and the found digests.
- A migration lock another session holds is reported as an activation in
  progress, never as an unreachable database, with the suggested action
  `retry_after_migration_lock_releases`. `bregctl migration reconcile` reads
  the active identity without the lock and reports `in_progress`.
- A package whose project declares a change-request `planner` is accepted as
  a predecessor. Earlier releases refused it, with
  `package.baseline.integrity_refused` under `--baseline-package` and
  `apply.package.refused` from `bregctl plan` and `bregctl apply`, so no
  successor of such a package could be built or applied. The package format
  is unchanged: a package v0.38.0 built needs no rebuild to serve as the
  predecessor.
- `bregctl test` rehearses a reviewed migration's assertions and steps under
  the lock and statement timeouts its descriptor declares, as activation does.
  `bregctl test --fingerprint-only --runtime-config <file>` measures the
  schema fingerprint a fresh install of the candidate produces without running
  fixtures or writing a receipt, and the
  `migration.review.fingerprint_mismatch` refusal names both fingerprints.
- `bregctl dev` no longer treats a comment, blank line, or key-order edit to
  a YAML file as a changed input. Any edit to a Rhai script or WASM module
  still counts.
- The WebAssembly executor runs Wasmtime 48.0.5, which carries the fixes for
  RUSTSEC-2026-0325, RUSTSEC-2026-0326, and RUSTSEC-2026-0327. Handler
  capabilities and fuel and memory limits are unchanged.
- Correction to the v0.36.0 notes: `bregctl dev` does keep a package sequence,
  in that release and since. Its state starts the sequence at 1 and advances
  it each time `bregctl dev prepare-source` prepares a successor, and its
  reports carry it as `packageSequence`.

## BReg citizen MCP gateway and review page

- `breg-mcp` refuses the retired `resourceServer.jwks` and
  `audit.maximumFileBytes` runtime keys with the generic unknown-field error
  and no longer names their replacements, `resourceServer.jwksSource` and
  `audit.rotateBytes`. `breg-review` has no user-visible change.

## Registry Casework

- An empty source-backed inbox view over a source reconciled within the
  larger of twice its `reconciliationIntervalMilliseconds` and 2 minutes
  returns `complete` without requeueing subjects or clearing source
  completeness. A caller serving no queue receives `complete` regardless of
  discovery state.
- `caseworkctl source add --casework-endpoint URL` sets the Casework endpoint
  of the local BReg review authority it writes, for a Casework session on a
  port other than the default 8092. It accepts only an exact loopback HTTP
  URL.
- `caseworkctl dev start` and `dev stop` name the cause of a local session
  failure: an occupied port (`caseworkctl.dev.port-occupied`), authored inputs
  that differ from a session retaining records
  (`caseworkctl.dev.inputs-changed`), a retained audit stream an earlier
  release wrote (`caseworkctl.dev.audit-format-unsupported`), an audit
  directory the runtime cannot open (`caseworkctl.dev.audit-unavailable`), and
  a supervised start that failed (`caseworkctl.dev.start-failed`). Each
  message is fixed text with a port number or a project-relative path.
- `caseworkctl dev stop --remove` also empties the project's retained
  `.casework/dev/audit` directory. A plain `dev stop` keeps it.

## Evidence, Discovery, and Registry Manifest

- Evidence has no runtime, bundle, or wire change in this release.
- Registry Discovery serves and builds Evidence-only indexes, as the upgrade
  section describes. `discoveryctl package` refuses an approved origin that
  publishes a Relay service with a message that says to remove Relay origins
  and package again.
- `registry-manifest --version` prints the build version. Registry Manifest
  has no other user-visible change.

## Shared platform and clients

- The Rust, Node.js, and Python BReg clients expose the validated `fieldPath`
  an accepted BReg problem names (`field_path` in Rust and Python), so a
  caller can identify the field or header that needs attention. The Rust
  client keeps the location out of error and debug text.
- The BReg client refuses served metadata whose operation omits
  `readableRequestFields`, where it treated that as an empty grant, and
  `BRegPreparedLifecycle::from_slice` refuses version 1 prepared lifecycle
  evidence.
- The unified Rust, Node.js, and Python clients no longer carry a `relay`
  namespace, and the `registry-relay-client` crate is removed.
- `registry-platform-hooks` lets a product's `DeliverySeams` note each worker
  iteration that completed without failure through the defaulted
  `iteration_succeeded` method.
- BREAKING: `registry-platform-hooks` `delivery_schema::install` no longer
  upgrades delivery tables created by builds older than v0.38.0. It still
  adds the dead-letter reason column and its constraint to a delivery-state
  table created without them.

## Editors

- The VS Code and Zed integrations no longer author Relay projects, and the
  hosted language server ships in `evidencectl` alone. They remain
  source-installed beta integrations; build the hosted CLI from the same
  checkout.
- The language server keeps watching a file a document references whatever
  its extension, so a diagnostic about a referenced file clears when that file
  changes. It still reads only `.yaml`, `.yml`, and `.json` product documents.

## Release process

- A nightly channel publishes evaluation builds from protected `main` after
  the exact source commit passes protected-main CI: an immutable GitHub
  prerelease tagged `v<base>-nightly.<YYYYMMDD>.<source SHA>` with binaries,
  installers, checksums, image scan and software bill of materials evidence,
  and build provenance, and the same tag on the public container packages. It
  publishes no npm package, PyPI package, or documentation site. The source
  installers for BReg, Casework, Evidence, and Scheduling accept
  `--channel nightly` or `--build <tag>`; an installer downloaded from a
  numbered release stays pinned to that release and refuses both. Use a
  numbered release for a production deployment. See
  [the nightly channel](https://github.com/registrystack/registry-stack/blob/v0.39.0/release/NIGHTLY.md).
- The release roster omits Relay from v0.39.0. Historical release manifests,
  notes, and documentation archives keep their Relay inventory unchanged.
- The BReg, Casework, and Scheduling release images fail to build when the
  product's adopter tool is not staged beside the runtime.
- The upgrade rehearsal starts only from v0.38.0. A release-tooling check
  holds that starting release to the newest published release below the first
  release of the workspace version's minor line, so a patch release keeps the
  starting release of its minor line.
- The runtime Dockerfiles pin the Distroless base image by digest. The macOS
  jobs of the release candidate, canary, benchmark, and contributor workflows
  run on `macos-26` arm64 runners, with the macOS 11 deployment target
  unchanged. The nightly's macOS job still runs on `macos-14`.
- The identifier publication job watches the exact deployment run its own
  dispatch created, so a rerun no longer follows an earlier failed run.

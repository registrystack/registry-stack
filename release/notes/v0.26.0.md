# Registry Stack v0.26.0

Registry Stack v0.26.0 is the beta-37 minor release. It introduces Base
Registry Engine as a shipped, configuration-compiled PostgreSQL system of
record, adds the shared Registry Record v1 response profile, and brings that
profile to Relay V2. The release carries two breaking adopter migrations:
Relay JSON and JSON-LD responses adopt the Registry Record envelope, and every
Registry Manifest data service must identify at least one existing dataset.
It does not retire an existing product.

## Base Registry Engine

- Base Registry Engine is a domain-neutral system of record for institutional
  registries that need governed writes, history, access control, and reviewed
  schema evolution. Its entities, relationships, routes, fields, access
  profiles, events, and datasets come from an active Registry package rather
  than built-in domain models.
- `breg` verifies one package and serves its compiled REST API against
  PostgreSQL. `bregctl` provides deterministic project checks, fixture tests,
  artifact generation, package inspection, detached-signature workflows,
  reviewed activation, verification, audit inspection, and data lifecycle
  commands. Production signing and migration authority remain separate from
  authoring.
- The first release closure contains `breg` and `bregctl` binaries for Linux
  amd64, Linux arm64, and macOS arm64, a checksum-verifying installer that
  installs the pair together, and the `ghcr.io/registrystack/breg` runtime
  image. The image contains the runtime and license only; deployment
  configuration, packages, trust anchors, secrets, and database credentials
  remain operator inputs.
- The maintained first-hour quickstart can use the released `breg`, `bregctl`,
  and `mint` binaries through `--installed`. It is a disposable loopback path,
  not a substitute for production package signing, database roles, TLS,
  migration review, or secret custody.
- The source workspace also adds the bounded `registry-breg-client`, the
  product-neutral `registry-record` DTO and validation crate, and the
  `registry-stack-client` Rust facade. These workspace crates remain
  unpublished, so source consumers must pin the exact Registry Stack source
  ref.

## Breaking change: Relay V2 adopts Registry Record v1

- Relay JSON and JSON-LD consultation responses now conform to
  `https://id.registrystack.org/profiles/registry-record/v1`. Each resource
  must declare governed `datasetIdentifier` and `entityTypeIdentifier` values
  beside its existing identifier.
- Registry, dataset, and entity-type identity moves to response `meta`; each
  Record under `data` or `items` no longer repeats `registryIdentifier`.
  JSON-LD responses carry the shared Registry Record context followed by the
  generated Relay operation context.
- Before upgrading, add the two identifiers to every authored resource, rename
  domain properties that collide with reserved envelope, context, identifier,
  or pagination members, then regenerate and reseal packages. Existing
  packages fail strict compilation because the new identifiers participate in
  the package digest.
- Restart pagination and cache revalidation after deployment because old
  cursors and ETags are invalid. Discovery descriptions for upgraded Relay
  deployments must replace Relay profile v2 with profile v3 and also declare
  the Registry Record v1 profile. GeoJSON keeps its separate OGC media profile
  and shape.

## Breaking change: Registry Manifest data-service membership

- Every authored `data_services[]` entry must now list at least one existing
  dataset in `serves_datasets`. Add the datasets exposed by each service before
  validating or republishing an older manifest that omitted this relationship.
- Datasets may now declare a canonical IRI and deliberate release version.
  First-class distributions bind to exactly one dataset and may identify a
  serving data service, an access or download URL, media type, format, title,
  description, and canonical IRI.
- DCAT rendering emits declared distributions, access-service relationships,
  access and download URLs, media types, formats, and dataset versions. A
  distribution that names an access service must bind to a dataset that service
  serves.
- Manifests that omit the additive dataset and distribution fields keep their
  exact typed canonical bytes and `source_manifest_digest`. An absent or empty
  top-level `distributions` collection is canonically equivalent. This
  compatibility does not make an empty `serves_datasets` list valid.

## Registry Discovery client handoff

- The Rust, Node.js, and Python Discovery clients distinguish structural
  selection validation from adopter trust. Structural validation checks the
  closed shape and capability binding only; it does not establish origin
  authenticity, catalog or mapping currentness, authorization, or trust.
- New acceptance helpers create an ephemeral handoff only after an
  application-owned policy accepts the advertised service. Credentials and
  native Evidence or Relay clients are constructed after that decision.
- Online renewal re-resolves and reselects the same service, permits only
  fetch-provenance and catalog-revision changes, and refuses any trust-relevant
  semantic change. It never silently selects a replacement service or Evidence
  alternative.
- Node.js and Python keep their previous validation names as compatibility
  aliases for the more explicit structural-validation names. The unpublished
  Rust crate renames `validate_service_selection` to
  `validate_service_selection_structure` without an alias.

## Published identifiers

- The active identifier catalog grows from 51 to 58 entries. It adds the
  Registry Record v1 profile, JSON Schema, JSON-LD context, and vocabulary,
  plus the Base Registry Engine project, module, and runtime configuration
  schemas. Each published profile, context, and schema is bound to its reviewed
  source and exact artifact digest.

## Release maintenance

- Daily candidate-image cleanup now records and skips the exact GitHub refusal
  for a publicly visible package version with more than 5,000 downloads, then
  continues cleaning the remaining packages. Any other delete failure still
  aborts the cleanup run.

## Release boundaries

- Beta publication promotes one verified candidate from protected `main`
  without rebuilding binaries, client packages, documentation, or runtime image
  manifests.
- The `breg` GHCR package must exist, be public, and grant this repository's
  Actions workflow write access before the first v0.26.0 candidate is
  requested. Its candidate-package cleanup enrollment follows the first
  published candidate.
- Candidate image scanning must complete successfully and applicable advisory
  decisions must carry the required exposure evidence.
- Exact already-completed image and client-registry operations may be
  reconciled during a retry. A mismatched immutable image or package version
  requires a new release version.
- Hosted deployments, external conformance, and adopter-specific rollout
  exercises remain outside this release's critical path.

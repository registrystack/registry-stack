# Registry Stack v0.42.0

Registry Stack v0.42.0 is the beta-54 release. It starts a fresh state
baseline for every product that keeps state: no product reads v0.41.0 state in
place. Base Registry Engine (BReg) projects now declare `recordTypes` and
Actions, and durable Proposals replace the entity-backed change-request model.
Registry Casework replaces source-owned WorkItems with one review-only
ReviewPolicy, ReviewRequest, ReviewTask, and ReviewResult model, and every
decided result names the policy outcome it settled on, with an optional public
reason BReg can show the subject. Evidence authoring moves to one normalized
`evidence.yaml` project with a separate target and target authority.
Configuration names converge across products: a shared `retention` block,
`receiptRetentionDays`, `statusResource`, and the `scope` claim default. Token
verifiers share one issuer network policy, and webhook envelopes are bounded at
the 1 MiB signable size. Registry Coordinator source joins the repository; it is
not a release artifact of v0.42.0.

## Compatibility and upgrade

Use matching v0.42.0 runtimes, tools, and clients. **v0.42.0 does not read
state v0.41.0 wrote.** An upgrade from v0.41.0 is a fresh installation beside
the deployment it replaces:

- BReg carries no state migration from v0.41.0. Rewrite the project as
  `recordTypes` and Actions, package it with the v0.42.0 tooling, and apply it
  to a fresh database. BReg has no dedicated refusal that names a v0.41.0
  database, so point it only at a fresh one. Export the Records you carry
  forward with `bregctl data export` while v0.41.0 still serves, naming with
  `--field` every field the reload needs: the export holds only the fields
  you name. Records reloaded with `bregctl data import` receive new record
  IDs, and the import reports counts only: remap relationship values by a
  stable business key, and treat record URLs and IDs held by clients or other
  products as invalid.
- Casework, Scheduling, and Messaging each install their complete schema as one
  baseline numbered version 100. Each refuses a database whose ledger holds any
  version below 100 at `plan`, `apply`, and startup, naming the fresh-install
  recovery; Casework reports `casework.activation.beta-schema`. A v0.41.0
  binary pointed at a v0.42.0 database refuses it as newer than it knows.
- Evidence requires a newly authored normalized project, target, and complete
  target authority. Retired split question and source projects and bundled
  authority are refused; there is no conversion.

Work still held by a v0.41.0 database is not carried forward: BReg records,
revision history, open change requests, and pending webhook deliveries;
Casework reviews in progress; Scheduling holds and appointments; and messages
still queued in Messaging. Before you stop each v0.41.0 runtime, finish, drain,
or record that work, and pause every caller, readers included, until the
cutover completes. Back up databases, configuration, packages, keys, and audit
streams, keep each v0.41.0 database unchanged with its binaries for
reconciliation and rollback, and apply the v0.42.0 packages to fresh databases
in the order
[upgrade and retire](https://docs.registrystack.org/operate/advanced/upgrade-and-retire/)
gives. Rollback means running v0.41.0 again against the retained database. No
migration tooling for v0.41.0 or earlier state is provided.

BReg now requires PostgreSQL 17 or later and a UTF8 database for runtime,
spatial provisioning, migration receipts, and schema-test receipts. Generated
text columns and indexes use the built-in `pg_catalog.pg_c_utf8` collation, so
the managed catalog fingerprint is the same on PostgreSQL 17 and 18. A non-UTF8
database, an unvalidated PostgreSQL 18 `NOT NULL` constraint, or a differing
managed text collation is refused with recovery guidance. The Node.js 24.11.0,
Python 3.11, and standalone Linux glibc 2.34 floors are unchanged from v0.41.0.

The forward state path, and the upgrade rehearsal, now start at v0.42.0. The
next release reads state v0.42.0 writes, subject to an explicitly documented
product replacement. See
[upgrades and state](https://docs.registrystack.org/reference/api-stability/#upgrades-and-state).

The entries below cover every BREAKING item since v0.41.0 in the
[product changelogs](https://github.com/registrystack/registry-stack/tree/v0.42.0/products).
Several are also covered by the fresh-database boundary above, but each still
needs its configuration, client, or automation change.

### BReg Records, Actions, and Proposals

- BREAKING: projects declare `recordTypes` and Actions. Immediate Actions
  commit their plan in one transaction; durable Proposals freeze the same plan
  for inspection, optional Review, and independently authorized application.
  The entity-backed change-request model and its routes are removed, with no
  compatibility layer or state migration. Rebuild packages from the current
  project format and apply them to a fresh database.
- BREAKING: the Rust, Node.js, and Python clients use standalone Proposal
  methods. In Node.js, `immediateActions` and `selectImmediateAction` become
  `actions` (with a declared mode) and `selectAction`; Action
  `contractFingerprint` becomes `revision`; BReg-owned `Entity` identifiers
  become `RecordType` identifiers. Replace lifecycle methods with
  `startProposal`, `prepareProposal`, `executeProposal`, and `recoverProposal`,
  and request attachments with `uploadProposalAttachment`,
  `downloadProposalAttachment`, and `deleteProposalAttachment`. Replace request
  history with `getProposal` and `listProposals`. Rust and Python expose the
  snake-case equivalents, and recovery requires a fresh authorized Proposal
  read. BReg metadata is now version 2 and the clients refuse older versions,
  so regenerate packages and update clients together. See the
  [Node.js client](https://github.com/registrystack/registry-stack/blob/v0.42.0/crates/registry-breg-client-node/README.md#standalone-proposals)
  and [Python client](https://github.com/registrystack/registry-stack/blob/v0.42.0/crates/registry-breg-client-py/README.md#standalone-proposals).
- BREAKING: the Proposal list takes `limit` (1 to 100, default 50) and refuses
  `top` with `query.invalid` naming `limit`. An ingestion run listing takes
  `cursor`, answers `nextCursor`, and refuses `after` with `query.invalid`
  naming `cursor`. Both refusals follow the authority check, so an unauthorized
  caller still sees concealment. Record, metadata, statistics, and GIS lists
  keep `$top` and `$skiptoken`. In Rust, `BRegProposalQuery.top` becomes
  `limit`, `BRegIngestionRunListQuery::after` becomes `cursor`, and
  `BRegIngestionRunPage::next_after` becomes `next_cursor`; Node.js and Python
  take `cursor` and return `nextCursor`.
- BREAKING: a Review that rejects a Proposal's current submission ends it. The
  Proposal moves to the terminal state `rejected` with a `rejected` lifecycle
  event whose `authorityKind` is `review`. Submit, Edit, Revise, Rebase, Apply,
  Retry, Cancel, and attachment uploads or removals answer `409
  proposal.rejected`, and each command link reads `review-rejected` with
  recovery `receipt-only`. `applicationStatus.state` reads `rejected`. A
  changes-requested result keeps the Proposal `submitted` and revisable and
  records a `review-returned` event. Start a new Proposal where a client waited
  to Revise after a rejection, and add the new `state`, `transition`, and
  `authorityKind` values to receivers.
- BREAKING: under required Review, `applicationStatus.state` reads
  `awaiting-review` until an approved result exists, in both application
  modes. `application-refused` now means only that an executor refused the
  frozen effects. A changes-requested or provider-ended Review is reported by
  the `apply` link's availability as `review-changes-requested` or
  `review-ended`, with the recovery `revise`. Update clients and generated
  project SDKs with the server.
- BREAKING: `applicationStatus.recovery` is `retry` or `correct-input`. The
  never-emitted `refresh`, `receipt-only`, and `terminal` values are removed
  from that schema, from the Rust `BRegApplicationRecoveryHint`, and from the
  Node.js types, and a document carrying them is refused as malformed. Apply,
  Retry, and Revise link availability keeps `refresh` and `receipt-only`.
- BREAKING: Apply, Retry, and Revise link availability no longer lists the
  never-emitted recovery `terminal`. It is removed from the schema, the Rust
  `BRegRecoveryHint`, and the Node.js and Python types, and a document carrying
  it is refused as malformed. Drop any `terminal` branch; a rejected Proposal
  reads `receipt-only`.
- BREAKING: every Proposal document and lifecycle event carries a required
  `turn` of `party`, `official`, or `nobody`, derived on read and never stored.
  `GET /v1/proposals?turn=party` (or `official`, `nobody`) filters by turn, and
  `state=rejected` lists rejected Proposals. A page may hold fewer than `limit`
  items, so keep paging while `nextCursor` is present. The Rust
  `BRegProposalQuery` gains `turn`. Refresh any pinned copy of the Proposal
  event schema.
- BREAKING: a Proposal lifecycle event's `subject.recordReference` is the
  Proposal's resource path, `/v1/proposals/{id}`, instead of a hashed
  reference. Record events keep their hashed reference. Match Proposal events
  by the path.
- BREAKING: `bregctl explain lifecycle` answers
  `breg/lifecycle-explanation/v1alpha6`, adding the `rejected` state, the
  `reject` transition, and its `review-authority-result` enforcement.
  `bregctl explain events` answers `breg/events-explanation/v1alpha6`, whose
  Proposal transitions add `rejected` and `review-returned`. Select the
  `v1alpha6` schema for both.
- BREAKING: an immediate Action whose declared field guard fails at commit
  answers `412 action.guard_failed` instead of `412 precondition.failed` when
  the current-target admission checks pass and the selected profile can read
  the failed guard's target fields. The code confirms that blocker; it does not
  promise the Action would otherwise succeed. An earlier refusal keeps its
  normal response, and a stale condition or a guard that cannot be disclosed
  remains `412 precondition.failed`. Clients that match `precondition.failed`,
  for example to offer reload and retry, must accept the new code; v0.41.0 Rust
  clients report it as an unrecognized problem.
- BREAKING: `bregctl explain routes` answers
  `breg/routes-explanation/v1alpha6`, which adds the `availability` Action
  route kind. Select the `v1alpha6` schema.

### Review outcomes and public reasons

Upgrade Casework and every review producer, including BReg, together. A
v0.41.0 producer refuses an approved result that names an outcome, and a
v0.42.0 producer refuses a v0.41.0 approved result that names none; either way
an approved BReg Proposal stays `submitted` until both sides are upgraded.

- BREAKING: every decided Casework ReviewResult names the policy outcome it
  settled on. `outcome` is required on approved, rejected, changes-requested,
  and answered results and absent on cancelled and superseded ones.
- BREAKING: a BReg Review result from Casework names its outcome, and BReg
  reads it.
- BREAKING: every Casework `ReviewDecisionReceipt` names the selected `outcome`.
  The field is required in the OpenAPI document and in the Rust, Node.js, and
  Python clients, which refuse a receipt without it. `outcomeLabel` stays
  optional.
- BREAKING: an approve without an outcome (`{"type":"approve"}`) is refused
  with `400 request.invalid`, path `$.outcome`, reason `outcome-not-declared`,
  and the `Registry-Casework-Validation-Allowed` header listing the policy's
  approval outcomes. Send one of them, for example
  `{"type":"approve","outcome":"approved"}`. A policy with `purpose: approval`
  must declare its approval outcomes (`settlement: approved`), and
  `caseworkctl check` refuses one that declares none.
- BREAKING: every review policy outcome declares `publicReason: required`,
  `optional`, or `none`, with no default. A decision may carry a `publicReason`
  of at most 2000 UTF-8 bytes, which the producer receives on the ReviewResult
  for the subject's owner; the private `reason` stays in the accountability
  record and the audit journal records only `publicReasonGiven`. Refusals are
  `public-reason-required`, `public-reason-not-declared`,
  `maximum-bytes-exceeded`, and `text-invalid` at `$.publicReason`. Add the
  declaration to every outcome.
- BREAKING: every approval in one stage names the same outcome. A differing
  approval is refused with `400 request.invalid`, path `$.outcome`, reason
  `approval-outcome-differs`, and the header naming the outcome already chosen.
  The final stage settles with that outcome and the public reason of the
  approval that meets its threshold; other public reasons are kept for
  accountability and not released.
- BREAKING: a private `reason` over its 2000-byte bound is refused with
  `maximum-bytes-exceeded` at `$.reason` instead of `text-invalid`. A blank or
  control-character reason still answers `text-invalid`. Update automation
  that matches the old reason.

### Casework review model and project format

- BREAKING: source-owned WorkItems, prepared attempts, and source actions are
  replaced by one ReviewPolicy, ReviewRequest, ReviewTask, Decision, and
  ReviewResult model. Requests select a policy by ID, with an optional exact
  version and digest, and context uses `mode` `submitted` or `current-source`.
  Casework has no source mutation authority and no retired HTTP or CLI
  compatibility surface. Use a fresh database; retained legacy schemas are
  refused before mutation, not converted or erased.
- BREAKING: the Casework project format aligns with the cross-product
  configuration conventions. `caseworkctl check` and the runtime refuse every
  old spelling at its path and name its replacement; there is no migration
  command. Pinned policy closures stored in the old shape are not converted.

  | Row | Before | After |
  | --- | --- | --- |
  | F1 | subject clock `after: {elapsed: PT48H}` | `after: {hours: 48}`; exactly one of `minutes`, `hours`, or `days` |
  | F2 | review policy `retention: {terminalDays, accountabilityDays}` | `retention: {terminalRetentionDays, accountabilityRetentionDays}` |
  | F3 | trusted producer `recoveryDays: N` | `retention: {receiptRetentionDays: N}`, at most 365 |
  | F4 | `accessProfiles`, `queues`, `teams`, `trustedProducers`, `calendars`, `clocks`, `reviewPolicies`, `contextProviders`, `taskTemplates`, a policy's `outcomes`, and a clock's `reminders` as lists of `{id: ..., ...}` | mappings from each ID to the rest of its entry |
  | F5 | `type: activity` | `type: stage` |
  | F6 | `anchor: request-accepted-at`, `anchor: stage-entered-at` | `anchor: {type: request-accepted}`, `anchor: {type: stage-entered}` |
  | F7 | subject clock `completeOn: result-terminal` | removed; a subject clock completes when the result is terminal |
  | F8 | `atRisk: {workingDaysBefore: N}`, reminder `workingDaysBefore: N` | `atRisk: {before: {workingDays: N}}`, `reminders: {REMINDER_ID: {before: {workingDays: N}}}` |
  | F9 | routing `when: {activity: review}` | removed; a rule naming a `stage` matches only that stage's tasks |

  Rows F1 to F3 and F5 to F9 also change the served policy in the OpenAPI
  document and the Node.js and Python client types. Served policies keep
  arrays, listed in identifier order.
- BREAKING: trusted producer findings read
  `casework.review-producer.no-policies`, `too-many-policies`,
  `invalid-policy`, and `duplicate-policy` instead of `no-kinds`,
  `too-many-kinds`, `invalid-kind`, and `duplicate-kind`. Receipt retention
  findings read `receipt-retention-out-of-range` and
  `receipt-retention-exceeds-result-retention` instead of
  `recovery-days-out-of-range` and `recovery-exceeds-retention`. Update
  scripts that match the old codes.
- BREAKING: task list, next-task, and holdings reads complete their bounded
  scan before sorting and paging, including unfiltered queues, and refuse an
  exhausted candidate or source-read budget with `review.query-too-broad`
  instead of returning a partial page. Defaults are 100 candidates, 25 source
  reads, and 2000 ms; page size and reference filtering do not reduce the scan.
  Size the policy for the expected query or narrow the queue or subject.
  Supervision and own-decision reads keep their partial-page contract.

### Token issuer network policy

- BREAKING: every token-verifying runtime uses one issuer network policy. The
  issuer and an operator-declared JWKS URI may resolve to private or loopback
  addresses on any origin. A discovered `jwks_uri` inherits that allowance only
  on the issuer's own origin; a discovered cross-origin key endpoint must use
  HTTPS and is refused on a private or loopback address. Cloud metadata and
  link-local addresses are always refused. Plain HTTP beyond loopback requires
  `allowInsecureHttp: true` and logs a startup warning. Declare a private key
  endpoint as `jwksSource: {type: uri, uri: ...}` or serve it from the issuer's
  origin. Evidence admits `allowInsecureHttp` only under the `local` assurance
  profile, and `breg-review` has no such setting: it signs people in only with
  an HTTPS issuer or a loopback one under `development-loopback`.
- BREAKING: Coordinator applies the same rule under
  `deployment.authentication`, including under `development-loopback`. This
  affects source-built Coordinator deployments only.

## Base Registry Engine

`GET /v1/proposals/{id}/submissions/{version}` reads one submitted version of
a Proposal under Proposal Get authority: its frozen effect digest, review
result, and application status, with `current` marking the latest version. Once
neither the review result nor the application receipt is retained, it answers
`410 proposal.submission_expired`. Proposal Get, each listed Proposal, and this
read carry `decision` once a reviewer decides, including any `publicReason`,
the only reviewer text BReg serves. The clients read it with
`read_proposal_submission` (`readProposalSubmission` in Node.js). A profile
holding the supplemental `get-application-actor` operation receives the keyed
`appliedBy` pseudonym and `appliedAt`; no response carries the raw issuer or
subject.

The `apply` link reports Reviews that cannot approve the current submission as
`review-ended` with recovery `revise`, and dependency failures as
`dependency-outage` with recovery `retry`. A rejected or applied Proposal keeps
its `reviewStatus` link, and a Proposal prepared without an optional input now
serves its review context with `null` for the omitted value. Cancel, Revise, or
Rebase closes the Proposal's queued automatic application job in the same
transaction. The clients name a refused transition's `reason` and `recovery` in
the message, and the runtime logs one warning naming the authority, HTTP status,
and Problem code when a review handoff is refused for good.

BREAKING: when package activation blocks submitted work, BReg withdraws that
work's Review and closes its application jobs in the same transaction. Before
activating an incompatible package, check the affected submitted Proposals and
arrange recovery with their requesters: a restoring package cannot revive
those rounds or jobs, so the requester must Cancel, or Rebase and Submit for
fresh Review. Late results remain evidence, authorized Get and List stay
available, and recovery names the package-change block. An explicit Review
producer-ID mismatch is now reported as such, with bounded diagnostics naming
both configured IDs, instead of as an uncertain transport outcome.

A `409 mutation.conflict` from a direct record create, patch, or batch that
violates a compare, int-range, or vocabulary constraint carries `recordType`,
`constraintId`, and `constraintKind`, plus `left` and `right` for a compare
constraint or `field` otherwise. BReg omits them when the caller cannot read
every field the constraint references; unique and temporal non-overlap
conflicts stay generic. Clients that hold this problem to a closed member set
must accept these members. The maintained clients expose them as the conflict's
constraint.

An immediate Action with at least one reference input advertises
`routes.availability`, a per-target check of its field-based `commitGuards`
under the selected Action profile and that profile's ordinary Get disclosure.
It grants no mutation authority. The answer is available, guard-not-satisfied,
input-required with the missing declared input names, or not-disclosed when
the guard depends on a field the caller cannot read; it never names a guard ID
or a Record value. It is a current hint: invocation remains the authoritative
check. The clients call it with `action_availability` (`actionAvailability` in
Node.js). See `products/breg/immediate-actions.md`. The generated OpenAPI
document now advertises Proposal Start as the `201` Proposal response with
`ETag` and `Location` that the runtime returns, and lists for each Action route
only the guard, handler, and Evidence failures its execution can return.

Filtered, sorted lists use declared `recordTypes[].indexes`, with the record ID
appended to each index, so an index accepts at most 31 authored fields.
Immediate Action row policies grow linearly with the number of effects, and each
target row is locked once. `bregctl init --from publicschema` derives a bounded
`structured` list for a multivalued property whose range class declares
`inline_only: true`, such as `ProfessionalLicense.profession_code`. Native
adopter tests can capture several Action results from one `bregctl examples`
run and assert an exact unordered set of collection members in journeys.

The supervised runtime erases expired Action and Proposal Evidence uses after
their 24-hour window in bounded, audited batches, and prunes terminal webhook
metadata once receipt and payload retention allow it. Read audit records
include a closed `refusalReason` where one is defined. Webhook deliveries expire
with their shared payload, settled URL proposal decisions finish delivery after
activation, and `webhook list` exposes `proposalCode` and a bounded
`proposalSummary` for the superseded-activation refusal. The Rust client's
`verify_webhook` and the Python client's `verify_webhook_delivery` use the
shared hooks receiver, with distinct codes for each delivery failure.

## Registry Casework

`authentication.oidc.revokedKeyIds` lists up to 128 key identifiers Casework
refuses locally even while the issuer still publishes them, and
`maximumTokenLifetimeSeconds` bounds a token's lifetime to 1 through 7200
seconds. Omitting either keeps the existing rule.

A decided review task stays in own-decision and supervision reads after its
source stops reporting the subject as reviewable, as a decided BReg Proposal
does. Claim, decide, `next`, and reads of open work still require a reviewable
subject. A task template with `subjects` bound to a BReg-backed review policy
is refused by name, as `casework.task-template.unserved-capability`, because
BReg does not serve task-grant context yet. A repeated stage or routing rule ID
is now refused as `config.duplicate-id`, replacing
`casework.review-policy.duplicate-stage-id` and
`casework.routing.duplicate-rule-id`.

Caseload preview and apply move one officer's complete claimed set, up to 100
tasks, and a preview must be applied within 15 minutes. Task reads expose an
optional `staffingDiagnostic: no-cover-available`, and the unused
`AssignmentContext` client export is removed. Stage clocks that fall in a
daylight-saving gap or fold now evaluate on every date. `caseworkctl provider
pair` pairs native BReg Proposal context and keeps a contract, capability, or
release mismatch as its own refusal with the configuration path, and the
Node.js and Python clients export the shared review submission digest helper.
Review creation and recovery return the admitted producer ID as bounded
acceptance metadata; the accepted JSON envelope is unchanged.

## Scheduling and Messaging

Scheduling now publishes an installer, as BReg and Casework do:

```bash
curl -fsSL https://github.com/registrystack/registry-stack/releases/download/v0.42.0/scheduling-install.sh | bash
```

It verifies the binaries against the release `SHA256SUMS` before writing them
to `$HOME/.local/bin` or `SCHEDULING_INSTALL_DIR`. It installs `schedulingctl`
on Linux amd64, Linux arm64, and macOS arm64, and the `scheduling` runtime on
Linux amd64, the one platform the runtime is published for. Messaging still has
no installer; its Linux amd64 binaries and image are on the release page.

Scheduling prunes delivered outbox intents and terminal observer delivery
metadata in bounded batches under `retention.receiptRetentionDays`, preserving
active and uncertain work, dead letters through payload expiry, audit evidence,
and spent idempotency keys. Raw claim owners expire after
`retention.claimOwnerRetentionDays` (default 7, range 1 through 365) following
an appointment's end or cancellation or a hold's end; the former owner can then
no longer read, act on, or replay a receipt containing the claim. The default
is a placeholder; choose a value for your deployment.

`messagingctl dev PROJECT --issuer-project BREG_OWNER --resource URI` borrows a
ready BReg development issuer for the clients the Messaging package names,
through public `bregctl dev export-client`. Scheduling and Messaging log the
expected claim and scope when a token lacks a required scope, never the token.

## Registry Coordinator

Registry Coordinator source is in the repository: a runtime that executes
finite, acyclic workflows across durable waits, outages, and restarts, calling
BReg, Casework, Scheduling, and Messaging through their public clients without
gaining their authority. It is not a release artifact of v0.42.0. The release
publishes no `coordinator` or `coordinatorctl` binary, no Coordinator image,
and no Coordinator namespace in the unified Node.js and Python client packages.
Pilots build it from the tagged source; see the
[Coordinator product directory](https://github.com/registrystack/registry-stack/tree/v0.42.0/products/coordinator).

## Development and release operation

BReg, Casework, and Messaging local development pull their pinned PostgreSQL
image from Docker Hub instead of ECR Public, with the same tag and digest.
Existing owned containers at the earlier ECR reference remain valid. Messaging
still pulls Mailpit from `ghcr.io`. Update development egress allowlists for
Docker Hub. `bregctl dev` requests each local client token for the resource
`issuer.clientResources` assigns, and accepts a development issuer's RS256 key
only when it declares `use: sig`. `registry-render init` prints a first-render
command that runs as printed from any directory, and `discoveryctl` help names
the `discovery --runtime-config` invocation it checks against.

The predecessor-state rehearsal refuses to start from a release before v0.42.0.
Until v0.42.0 is published, it runs the Evidence and Messaging legs with the
build under test on both sides, which exercises the scenarios but does not
demonstrate compatibility between releases. BReg, Casework, and Scheduling
state are not rehearsed; BReg and Casework keep their current-schema operator
checks.

Solmara Lab adaptation to the breaking changes is deferred. The approved 1.0
stability promise is unchanged and does not take effect in this pre-1.0 release.

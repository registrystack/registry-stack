# Registry Stack v0.27.0

Registry Stack v0.27.0 is the beta-39 release. It adds explicit Base Registry
Engine access configuration, BReg-to-Evidence authoring workflows, and clearer
local development and deployment diagnostics. It includes breaking BReg
configuration and problem-response changes described below.

## Upgrade Base Registry Engine projects and clients together

- Every row-bearing grant must declare `rowBoundaries`. Preserve the intended
  restrictions; use `rowBoundaries: []` only when no claim-bound row restriction
  is intended. `requestVisibility: owner` still limits request reads to the
  owner. An omitted declaration no longer compiles. Rebuild and review governed
  artifacts from the updated project before deploying them.
- For a route served by several profiles, set `default: true` on one intended
  profile or pass `accessProfile` on every request. Without either, the request
  refuses. Profile selection never searches for a grant the caller happens to
  satisfy.
- BReg problem `type` changes from `urn:breg:problem:<code>` to
  `https://id.registrystack.org/problems/registry-breg/<code path>`. The other
  problem members retain their existing meaning. Upgrade the service and
  maintained client package together. A mixed-version pair can report a
  generic protocol/problem error instead of the specific BReg error code.

## Check OIDC permission claims

For BReg, Evidence, Relay, and Evidence OID4VCI deployments using OIDC, the
selected permission claim must be a string or an array of strings when present.
Malformed values now refuse authentication instead of being ignored. A missing
claim remains allowed and supplies no permissions. Check your identity
provider's claim mapping before upgrading.

## Access and composition

- BReg supports explicit principal mapping from `sub`, bounded JWT audience
  arrays, and a review-stage rule excluding actors who decided an earlier
  stage. Access explanation includes action and workflow claim requirements.
- `bregctl dev` manages a local development registry. Supported governed
  lookups can be exported as Evidence sources; `evidencectl source` imports,
  compares, and updates source artifacts while preserving authored changes.
  Named source connections and selector profiles support these workflows.
  Evidence retains its own authorization and assertion rules.
- Evidence target commands prepare and check deployment targets. CLI output
  paths consistently use `--output`, `--output-dir`, and `--public-output`;
  previous spellings remain aliases. Prefer `evidencectl verify` over the
  deprecated `evidencectl request verify` spelling.

## Installation and maintenance

- Standalone Linux binaries, including CLI tools, require glibc 2.35 or later.
  Installers reject detected musl and older-glibc hosts before downloading.
  Published `linux/amd64` service images provide an alternative on supported
  container hosts.
- The unified Node.js client can be imported by package name, and BReg clients
  distinguish missing resources. Continue using `@registrystack/client` and
  `registry-stack-client` with their product namespaces.
- Runtime dependency checks can verify an explicitly required audit root.
  Local-development errors, export recovery diagnostics, key-file
  validation, and tutorial guidance are clearer and more consistent.
- Registry Manifest documents the ordering of field concepts without changing
  its generated output or asserting equivalence between the named vocabularies.

This remains a pre-1.0 Beta release for self-hosted institutional pilots.

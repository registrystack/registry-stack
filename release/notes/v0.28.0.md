# Registry Stack v0.28.0

Registry Stack v0.28.0 is the beta-40 release. It adds governed Base Registry
Engine actions with optional verified Evidence calls, native field integrity
and membership reads, and guided registry starter and Evidence source workflows.
It includes the compatibility changes below.

## Upgrade projects and scripts

- BREAKING: `bregctl dev` and `bregctl dev stop` now take the project directory
  as a positional argument. Replace `--project <dir>` with `<dir>` in scripts;
  omitting it still selects the current directory.
- Registry Manifest rejects repeated concept terms on a field, including
  equivalent expanded CURIEs and IRIs and differences only in scheme or host
  case. Remove duplicate entries before validation or publication. Manifests
  that still validate retain their authored spelling, canonical bytes, and
  `source_manifest_digest`.
- BReg reserves `bregState`, `proposalVersion`, and `effectDigest` as API field
  names for request-state queries. Rename ordinary field API names that collide
  before recompiling. Structured fields now also accept an array schema root
  with an explicit `items` schema; nested object schemas must remain closed.
- Native persisted-field `pattern` rules use PostgreSQL regular-expression
  syntax. Test them against PostgreSQL before packaging. Adding a rule validates
  existing rows under a table lock; changing or removing one requires a reviewed
  migration. A changed target pattern can require pending proposals to be
  rebased and reviewed again. Rebuild, test, sign, and activate governed packages
  when adopting the new declarations.
- Projects copied from the unreleased `professional-licences` starter must be
  initialized again. Its correction request now uses `licensedActivities` and
  `authorizationConditions` instead of `practiceScope`; that starter revision
  has no migration path.

## Governed registry operations

- Immediate actions can use a bounded Rhai handler to compute effects within
  declared write slots or return a declared refusal. Effects commit together.
  Fixed actions can require a linked reference target to have a declared value
  when the action is accepted. `bregctl project planner-test` checks exact
  handler effects and refusals with synthetic inputs.
- The trial `registry.action-handler/v2` ABI adds `evidence::resolve` for
  explicitly declared, verified Evidence assertions. Operators bind providers
  and credentials separately from the signed action contract. Successful receipt
  replay does not repeat Evidence calls. Version 1 input-only handlers remain
  available, and Evidence retains its own authorization.
- Accepted Evidence material has a separate 24-hour retention period. Operators
  use `bregctl evidence-retention erase-expired` to erase expired assertion bytes
  and verification context while preserving replayable receipts; ordinary
  history erasure does not cover this material.
- Membership read boundaries use current active membership records in the same
  registry for current and historical reads. They support read operations and
  cannot be combined with writes, actions, reviewed changes, or spatial bbox
  grants in the same profile.
- `submitterTargets` lets a manually applied change-request grant require
  current, same-profile GET authority over its declared native-reference
  targets. Authority is rechecked through intake, submission, revision, and
  exact replay. Request lists expose authorized filtering and sorting on
  request state, proposal version, and effect digest.

## Authoring and clients

- `bregctl init --from publicschema` derives a project from an embedded reference
  model through a terminal wizard, a selection file, or a named starter. Four
  registry starters include local scenarios that `bregctl examples` can run,
  resume, or restart. Starting the development registry alone does not load
  their sample records.
- `evidencectl source add` previews a connection from a stopped local BReg
  session and applies it with `--apply`, preserving records, history, and
  existing client identities. It requires a matching-version `bregctl` on
  `PATH`. Source-first targets and shared editor workspaces support the same
  authoring flow.
- The unified Node.js client's BReg namespace adds exact-JSON metadata, record,
  and lifecycle methods such as `getRecordJson` and `executeLifecycleActionJson`.
  These carry serialized JSON across the JavaScript number boundary and refuse
  unsupported numeric values instead of rounding them. Keep exact values as
  JSON text or use a lossless decoder; ordinary `JSON.parse` can lose precision.
- BReg export, import, migration, and development-session failures report more
  precise recovery information. Evidence authoring aligns source-origin and
  runtime-setting validation with deployment checks and bounds child-process
  output and version handshakes.

## Release verification and documentation

The signed release checksum inventory now also has a SLSA build provenance
bundle for `SHA256SUMS`. It identifies the publication workflow that assembled
the checksum file; candidate evidence retains the payload-build binding. Use
the verification procedure shipped with this release. Published documentation
generates CLI references from the reviewed source during its build.

This remains a pre-1.0 Beta release for self-hosted institutional pilots.

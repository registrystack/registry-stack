# Registry Stack v0.24.0

Registry Stack v0.24.0 is the beta-35 minor release. It publishes Registry
Discovery as a released runtime artifact for the first time: a `discovery`
container image and a `discovery` Linux binary now travel through the same
candidate, scan, and publication path as the other products. The minor version
reflects that additive inventory. It does not retire a product, change a
public API, or require a Registry Manifest format migration.

## Registry Discovery runtime artifact

- Registry Discovery ships as `ghcr.io/registrystack/discovery` and as the
  `discovery-v0.24.0-linux-amd64` binary attached to the GitHub Release. Before
  this release Discovery had no released artifact and could only be built from
  source. The Discovery client packages, published since v0.23.0, are
  unchanged in kind.
- Discovery serves one immutable index and writes nothing, so unlike the other
  runtime images it pre-owns no managed state and no audit directory. It reads
  no environment variable: the runtime file is bound by the image command
  rather than by `ENV`, so a second undeclared configuration source cannot
  appear later without failing the image contract check.
- `discovery --version` reports the release version. It previously exited with
  an "unexpected argument" error, because the binary declared no version at
  all. Discovery now takes its version from the same shared build-info source
  as every other Registry Stack executable, so a build without
  `REGISTRY_RELEASE_TAG` reports `<version>-dev` and only a release build
  reports the bare version.
- The Discovery artifact enters the inventory exactly at v0.24.0. Every
  released and staged earlier version keeps its exact recorded inventory, and a
  candidate rebuilt for an earlier version still produces byte-identical
  `SHA256SUMS`.

## Client packages

- The three Node client lockfiles carry resolved platform binding entries
  again, each with its version, resolved URL, and integrity hash. They
  previously held bare `optional` stubs, which npm tolerated only while the
  declared version was unpublished; `npm ci` began failing the moment v0.23.0
  published those packages.
- A Node client root manifest no longer pins its platform packages in the
  checked-in tree. The release binds the exact platform versions into the
  manifest it packs, and distribution validation reads the packed tarball back
  to prove the binding landed. This removes the contradiction that required a
  manual repair on protected `main` after every release.

## Release boundaries

- Beta publication promotes one verified candidate from protected `main`
  without rebuilding binaries, client packages, documentation, or runtime image
  manifests.
- The `discovery` GHCR package must exist, be public, and grant this
  repository's Actions workflow write access before the first v0.24.0
  candidate is requested. Its `discovery-candidate` cleanup enrolment follows
  the first published candidate.
- Candidate image scanning must complete successfully and applicable advisory
  decisions must carry the required exposure evidence.
- Exact already-completed image and client-registry operations may be
  reconciled during a retry. A mismatched immutable image or package version
  requires a new release version.
- Hosted deployments, external conformance, and adopter-specific rollout
  exercises remain outside this release's critical path.

# Registry Stack v0.23.0

Registry Stack v0.23.0 is the beta-34 minor release. It adds Registry
Discovery as a curated read-only index of public service descriptions, adds a
progressive Evidence client API, makes `relayctl` readable for adopters by
default, and distributes the Registry Discovery client packages through npm and
PyPI for the first time. The minor version reflects these additive surfaces. It
does not retire a product or require a Registry Manifest format migration.

## Registry Discovery

- Registry Discovery is a curated, read-only index of public Evidence and Relay
  service descriptions. It helps an application find advertisements. It does
  not establish provider trust, authorize a caller, proxy a native request,
  issue a credential, or carry credentials.
- The first provider representation is the closed
  `registry-discovery-v1alpha1` JSON-LD profile. It uses a deliberately
  selected DCAT 3, DCAT-AP 3.0.1, and BRegDCAT-AP alignment subset, and claims
  conformance to neither DCAT-AP nor BRegDCAT-AP in full. The pinned versions
  and terms are in `products/discovery/contracts/standards-profile.yaml`.
- The relying-party SDK performs a bounded, product-specific search and an
  ambiguity-safe selection. An Evidence selection retains the complete resolved
  AND-list and mapping provenance; a Relay selection retains the correlated
  semantic-class and operation-family match. A persisted selection can be
  revalidated before local trust accepts it and its advertised base URL is
  handed to the native Evidence or Relay client. A selection remains inert
  public metadata, not a trust decision and not a native request.
- The operator flow is owned by `discoveryctl`: offline `check`, one explicit
  `build`, deployment of an immutable index, then restart.
- Provider and adopter flows are gated in continuous integration.

## Registry Discovery client packages

- The Discovery relying-party SDK ships as `@registrystack/discovery-client` on
  npm and `registry-discovery-client` on PyPI, alongside the existing Evidence
  and Relay clients. These are the first published versions.
- Install a client package only at the exact Registry Stack version used by the
  corresponding deployment. Do not treat an npm `0.0.0` package-identity
  bootstrap as a usable client release.

## Evidence progressive client API

- The Evidence client SDKs gain a progressive API, so a relying party can make
  a first assertion request without assembling the full request contract, then
  move to the complete contract as its needs grow.
- Evidence adopter tooling binds the same progressive contracts, so the command
  line and the SDKs agree on what a request looks like.
- The client tutorial paths are synchronized across the Node and Python
  bindings, and the first assertion request is simplified.

## Relay V2 adopter tooling

- `relayctl` project workflow commands print a human-readable summary by
  default, carrying the report status, counts, and every diagnostic in severity
  order. `--json` selects the report document and its bytes are unchanged.
  Previously both branches wrote the same JSON document and differed only by a
  header line. This is specified in REQ-PR-RELAYCTL-026.
- Column-accounting diagnostics report an inherited failure at the resource's
  `classificationDefaults`, which the contract requires and which therefore
  always resolves in an editor. The column-specific path is used only where an
  override was actually authored, and the affected source column is named in
  the message. Previously these diagnostics could name a YAML node the adopter
  never wrote, which sent an editor to the start of the file.
- Diagnostics name the column and order key they are about.
- Every line of a human-readable report is escaped at the rendering boundary.
  SQLite places no restriction on what an identifier may contain, and a
  diagnostic carries an authored key path and often an authored column name, so
  adopter-supplied text could otherwise forge a report line, emit terminal
  escape sequences, or reorder the text drawn around it. The `--json` document
  is unaffected.
- The SDMX series branch decodes without a trailing refusal arm.

## Documentation

- The adopter documentation was reviewed and rewritten to read for a human
  rather than for a runner, across tutorials, configuration references, and the
  sidebar organization.
- Tutorials no longer print values a reader cannot reproduce, such as compiled
  contract revisions and installation-dependent counts.
- Pagefind gzip archives are canonicalized so the built documentation is
  byte-repeatable.

## Security and maintenance

- `h2` is upgraded to 0.4.17, past RUSTSEC-2026-0258 and GHSA-q83h-524g-xf6h.
  Version 0.4.15 accepted and queued empty DATA frames without limit, risking
  unbounded memory growth or a length-overflow panic when a malicious peer
  sends them and bodies are not actively drained.
- Release tooling recovers more smoothly from an interrupted run, and promotion
  verifies an existing draft.

## Release boundaries

- Beta publication promotes one verified candidate from protected `main`
  without rebuilding binaries, client packages, documentation, or runtime image
  manifests.
- The Discovery client packages require their npm and PyPI publishing identity
  to be provisioned before the first v0.23.0 candidate is requested.
- Candidate image scanning must complete successfully and applicable advisory
  decisions must carry the required exposure evidence.
- Exact already-completed image and client-registry operations may be
  reconciled during a retry. A mismatched immutable image or package version
  requires a new release version.
- Hosted deployments, external conformance, and adopter-specific rollout
  exercises remain outside this release's critical path.

# Registry Stack v0.41.0

Registry Stack v0.41.0 is the beta-53 release. It adds deferred Casework task
grants, fresh task-grant status checks in Scheduling, and original-receipt
reads in Scheduling and Messaging. Base Registry Engine clients accept
additive metadata and unknown Problem codes without granting unsupported
authority, and local BReg and Casework tooling agrees on principal claims.
The release also carries a native citizen self-registration and enrollment
acceptance project, lowers the standalone Linux glibc floor to 2.34, and moves
the client runtime floors to Node.js 24.11.0 and Python 3.11.

## Compatibility and upgrade

Use matching v0.41.0 runtimes, tools, and clients. This release reads state
v0.40.0 wrote; it does not restore an in-place path from an earlier release.
Back up databases, configuration, packages, keys, and audit streams before
upgrading, and preserve the same audit files. Follow
[upgrade and retire](https://docs.registrystack.org/operate/advanced/upgrade-and-retire/).
No migration tooling for older releases is provided.

The entries below cover every BREAKING item since v0.40.0 in the
[product changelogs](https://github.com/registrystack/registry-stack/tree/v0.41.0/products).
The shared client floors apply to the BReg, Casework, Discovery, Evidence,
Messaging, and Scheduling namespaces of the unified packages.

### Client runtime floors and Rust matches

- BREAKING: `registry-stack-client` requires Python 3.11 or later, replacing
  Python 3.10. `Requires-Python` is `>=3.11`, and the wheels use the Python
  3.11 stable ABI, `cp311-abi3`, replacing `cp310-abi3`. Upgrade the application
  interpreter before installing the client and update any wheel filename
  pinned in installation automation. Evidence development wheels have the
  same floor; `editors/configure.py` also requires Python 3.11 or later.
- BREAKING: `@registrystack/client` and its three platform packages require
  Node.js 24.11.0 or later, replacing Node.js 22.12.0. Move applications to
  Node.js 24 LTS before upgrading the client. `editors/install.sh vscode`
  likewise requires Node.js 24 or later to package the extension.
- BREAKING (Rust API): Scheduling and Messaging each add
  `ProblemCode::ReceiptUnresolved` to an enum that is not `#[non_exhaustive]`.
  Add a `ReceiptUnresolved` arm or a wildcard arm to exhaustive matches on
  `registry_scheduling_core::ProblemCode` and
  `registry_messaging_core::ProblemCode`, including their client re-exports
  and the codes carried by client errors.

### Task grants and current authority

- BREAKING: Scheduling refuses a runtime file without top-level
  `taskGrantStatus` as `scheduling.runtime.missing-task-grant-status`.
  Every v0.40.0 runtime file needs this addition. Configure a list of one to
  32 task authorities, matched by the exact `sourceIssuer` in their grants,
  for fresh status before every capacity commitment and idempotent replay.
  There is no fallback: inactive, mismatched, unlisted, or incompletely bound
  grants answer `403 operation.not-authorized`; an authority or credential
  outage answers `503 service.unavailable`. Alternatively, explicitly set
  `taskGrantStatus: unchecked-final-fifteen-minutes`. That choice performs no
  revocation check and accepts only a grant with at most 900 seconds remaining
  when the request enters. It checks remaining time, not the original grant
  mode, so it also admits the final 900 seconds of an originally deferred grant
  without checking revocation. Select this option only if that stale-authority
  window is acceptable; configure authorities when current status is required.
  An empty list is refused. See the complete
  [Scheduling runtime configuration](https://github.com/registrystack/registry-stack/blob/v0.41.0/products/scheduling/RUNTIME-CONFIG.md).
- BREAKING: BReg treats a 401 or 403 from a task-grant status endpoint as an
  outage, answering `503 service.unavailable` instead of
  `412 precondition.failed`. A 404 still refuses the grant with
  `precondition.failed`. Update alerts for a misconfigured or revoked status
  credential and recognize the shared `registry-task-status` user agent in
  Casework access logs, replacing `registry-breg-task-status`. The shared
  transport bounds an attempt at ten seconds; BReg's five-second outer bound
  still ends its check first.
- BREAKING: BReg validates each `taskGrantStatus` entry when reading the
  runtime file. Invalid entries report `breg.runtime.invalid-task-grant-status`
  at `/taskGrantStatus`, replacing activation-time
  `breg.runtime.invalid-binding`. No already activated valid entry needs
  editing. Update scripts that match the old diagnostic. `tokenEndpoint` is
  typed as a URL; `clientId`, `clientAssertionAudience`, and `caseworkResource`
  are external identifiers of 1 to 512 characters without control characters,
  and `caseworkResource` is an absolute resource URI. `sourceIssuer` accepts
  an absolute URN as well as a URL because the issuer is compared, not fetched.
- BREAKING: the Rust `CaseworkTaskAssertionSource`, also re-exported by the
  unified client, classifies a Casework 4xx assertion response other than 408
  and 429 as `TokenError::Invalid`, kind `invalid-credential`, instead of
  `unavailable`. This includes expired, revoked, or absent grants even if the
  Problem body is malformed. Request a new approval and stop retrying that
  credential. Responses 408, 429, and 5xx remain `unavailable`; transport
  failures retain their transport kind. Assertion requests are still sent once.

Casework task templates can opt into `authorizationMode: deferred`, with a
maximum `lifetimeSeconds` of 604800, or seven days. Omitted mode remains
`immediate`, with its 900-second ceiling. Deferred review grants pin the
assignment generation: release, reassignment, queue movement, absence-cover
change, decision, or completion ends the grant; reclaiming the task does not
revive it. Draft changes alone do not end it. Deferred templates cannot carry
Evidence bounds and are refused as `casework.task-template.deferred-evidence`.
Approval still names the template id and version; the preview, grant view, and
clients carry the mode and omit it for immediate grants.

Apply Casework migration 0022 through `caseworkctl plan` and `caseworkctl apply`.
It replaces the two task-grant expiry constraints, adds the review task's
`assignment_generation` column and its update trigger, and validates three
tables under an exclusive lock without rewriting them. Allow for that lock
when choosing the upgrade window.

BReg and Scheduling use the shared `TaskGrantStatusConfig` block in
`registry-platform-config` and status transport in `registry-platform-oidc`.
The optional `statusScope` and `statusPath` default to
`casework:grants:status` and `/v1/task-grants/{grantId}/status`. Set them only
for an authority with another scope or route. `statusScope` is one scope token;
`statusPath` starts with `/` and contains exactly one whole `{grantId}` segment.
Direct Rust consumers can map the shared block to `TaskGrantStatusEndpoint`
with `From` and validate its configuration without reading secrets or making
network requests. Product authorization and capacity ownership remain separate.

### Base Registry Engine historical state

- BREAKING: revision detail reads and list pages no longer read a revision
  journaled under an immediate action's effect identifier. They answer
  `503 source.unavailable`, even if the active package still declares that
  effect. Only v0.38.0 and earlier wrote this provenance; subsequent releases
  journal the entity's canonical operation identifier, such as
  `records.person.create`. A database a v0.40.0 apply created needs no action.
  Earlier revision rows are not read in place: apply to a new database, as
  v0.40.0 already required.
- BREAKING: startup no longer verifies or serves a database without subject
  access-log storage. Every apply from v0.38.0 onward installs that storage
  whether or not the package declares `accessLog`, so a database v0.40.0
  created needs no action. Refusal occurs before listener binding and writes
  nothing. Separate-role deployments report missing runtime-role grants;
  single-role deployments report that the database is not ready for the
  package. A database last applied before v0.38.0 requires a new database,
  as v0.40.0 already required.

### Retired command and compatibility paths

- BREAKING: `evidencectl build` is now an unknown command, reported as
  `evidencectl.usage` with exit 2 rather than `evidence.build.retired` with
  exit 1. Replace it with `evidencectl package PROJECT --target TARGET
  --output OUTPUT`. `evidencectl init` and `evidencectl new` also refuse
  `--generate-keys` as a usage error. Remove the flag; it previously did
  nothing, and local projects still generate their disposable keys.
- BREAKING: `casework migrate` and `caseworkctl db` are unknown subcommands
  with exit 2 and no dedicated replacement sentence. JSON automation sees
  `usage.invalid` instead of `usage.removed-command`. Use
  `caseworkctl plan --runtime-config FILE` followed by
  `caseworkctl apply --runtime-config FILE`.
- BREAKING: Casework removes `casework.package.retired-manifest`. A package
  containing `casework.package.json` reports `casework.package.invalid`
  when that file is unlisted, or `casework.package.unexpected-contents` when
  `SHA256SUMS` lists it. An incorrect `package.expectedDigest` is reported
  first as `casework.package.digest-mismatch`. Rebuild affected packages with
  `caseworkctl package`. v0.40.0 already refused these retired packages.
- BREAKING: `caseworkctl dev` refuses to remove an unlabeled database volume,
  even when the session's own container mounts it. Every v0.40.0 session labels
  its volume, so those sessions need no change. If retaining an older unlabeled
  `casework-dev-<identifier>` volume, inspect and back up its contents before
  removing it yourself with `docker volume rm`; removal destroys its data.
- BREAKING: the Casework BReg source adapter refuses a stored discovery cursor
  that is a bare continuation without its request entity. Every cursor
  v0.40.0 stored names that entity, so a v0.40.0 database needs no action.
- BREAKING: Scheduling removes three dedicated historical refusals. No input
  v0.40.0 wrote or accepted is affected, and those older inputs remain refused:
  - `scheduling migrate` is an unknown subcommand with exit 2. Activate with
    `schedulingctl plan --runtime-config FILE` and
    `schedulingctl apply --runtime-config FILE`; start with `scheduling serve`.
  - A retired `scheduling.package.json` reports `scheduling.package.invalid`
    at `/package/root` when unlisted, or
    `scheduling.package.unexpected-contents` when listed in `SHA256SUMS`,
    replacing `scheduling.package.retired-manifest`. Digest mismatch is still
    checked first. Rebuild with `schedulingctl package`.
  - A retained pre-v0.40 policy whose identity is under `scheduling` instead
    of `project` reports `schedulingctl.store-unavailable`, exit 3, replacing
    `schedulingctl.activation.earlier-release`. Start with a new database,
    run `schedulingctl apply --runtime-config FILE`, then
    `schedulingctl records apply --runtime-config FILE RECORDS`.
  Direct Rust consumers must remove uses of `RuntimeError::RemovedCommand`,
  `RuntimeError::exit_code`, `runtime::removed_command_refusal`,
  `RuntimeConfigError::RetiredPackageManifest`,
  `config::RETIRED_PACKAGE_MANIFEST_FILE`, and `StoreError::EarlierRelease`.
  `schedulingctl plan` performs its read-only publication check only when no
  schema version is pending; a v0.40.0-activated database has none pending.

### Local BReg and Casework workflows

- BREAKING: five `caseworkctl dev` configuration refusals now exit 1 instead
  of 3 and report their own codes instead of `caseworkctl.operational-failure`:
  `caseworkctl.dev.integrations-invalid`,
  `caseworkctl.dev.shared-client-mismatch`,
  `caseworkctl.dev.shared-task-authority-mismatch`,
  `caseworkctl.dev.source-binding-invalid`, and
  `caseworkctl.dev.borrowed-principal-invalid`. Update automation to inspect
  exit 1 and the specific code. These configurations already failed before.
- BREAKING: a Casework development session borrowing another project's issuer
  refuses a Casework access profile with `principalClaim: sub` as
  `caseworkctl.dev.borrowed-principal-invalid`. In that session, `sub` is the
  issuer owner's subject rather than the Casework principal. Use a stable
  claim such as `registry_principal` in every Casework access profile and
  register it for each client in both projects' `dev-clients.yaml`.

`caseworkctl source add` now derives the generated `casework-reader` profile's
principal claim through same-version `bregctl explain access`, preserves exact
`testBindings` variants, and infers only a default service client as executor.
For a BReg project using `sub`, its generated reader relies on the issuer's
verified subject. Align an earlier generated `casework-reader` profile and every
entity profile and action grant, including module contributions, to one
`principalClaim`, then repeat `source add`. Mixed principal claims are refused
before files are written. The local human reviewer bridge still uses
`registry_principal`. Equivalent review endpoint spellings, including trailing
slashes, retain their authored form when they resolve to the same API.

`bregctl dev` writes the compiled project's one principal claim into
`authentication.authorityClaims.principal` and includes
`authentication.authorityClaims.purpose: registry_purpose` only if a profile
requires purpose. Projects with no authenticated grant retain
`registry_principal`. It refuses incompatible claim mappings before retaining
first-start state. Use one principal claim that is neither `scope` nor the
purpose claim. Operated runtimes continue to configure these claims explicitly.
Local fixtures under a `sub` profile may use
`claims: {principal: "$localClientSubject"}` in their captured journey.
Local client files can also declare up to eight `taskGrantStatus` services and
machine-client grants for up to seven other audiences without expanding BReg
admission.

## Original receipts and client compatibility

Scheduling's `POST /v1/appointments/receipt` and Messaging's
`POST /v1/messages/receipt` recover the retained original success receipt using
the original `Idempotency-Key`, request body, and verified caller identity under
current ordinary read authority. They never repeat the mutation or claim
capacity. Scheduling can observe the outcome after the task grant ends;
Messaging neither spends nor requires the submission rate budget and never
answers 429 on this route. A missing, expired, changed, or refused receipt
answers `409 receipt.unresolved`, which does not prove that no effect occurred.
Rust, Node.js, and Python clients expose `appointment_receipt`,
`appointmentReceipt`, `message_receipt`, and `messageReceipt` in their language's
convention. Continue recovery before attempting a distinct write.

BReg Rust, Node.js, and Python clients ignore unknown object members after
duplicate checks, retain strict checks for known fields, and disable only
bindings whose required capabilities they do not understand. Unsupported
statistical datasets, descriptive change-request capabilities, selectors, and
spatial capabilities are omitted individually; an unknown temporal mode keeps
its served descriptor because null already means non-temporal. Tombstone,
batch, and lifecycle selection can report `required-capability` instead of
`contract-mismatch`. Valid unknown Problem codes retain HTTP status and trace
ID without inferred code or extension semantics; malformed envelopes remain
protocol errors. Fixed actions also accept omitted optional reference inputs
on create and patch while still checking supplied references and required
inputs.

## Linux installation and build tooling

Standalone Linux binaries now require glibc 2.34 or later, lowered from 2.35,
for the RHEL 9 family and Amazon Linux 2023. Both Linux architectures use the
same Zig floor selection and independent ELF-symbol check. Native Node.js and
Python client artifacts keep their separate glibc 2.17 contract; the standalone
floor does not change that contract.

The BReg, Casework, Scheduling, and Evidence installers start every staged Linux
binary with `--version` before selecting the new toolset. If any binary cannot
start, installation refuses that release and keeps the earlier toolset selected.
This also catches an installer asked to install an older release whose binaries
require a newer glibc than the host supplies.

Workflow `actions/setup-go` steps install Go 1.27.2, replacing 1.24.4, for
AWS-LC-FIPS source builds. Go is a build tool, not a shipped runtime or adopter
prerequisite. The canonical
Linux builder still installs its snapshot-pinned Debian Go package; this release
does not change that recipe. Linux arm64 builds now select the same hash-pinned
Zig toolchain and glibc floor on Ubuntu 24.04 as the canonical amd64 build.

BReg, Casework, and Messaging local development pull digest-identical PostgreSQL images
from `public.ecr.aws/docker/library/postgres`. Messaging also pulls Mailpit
from `ghcr.io/axllent/mailpit`. Update development egress allowlists for
`public.ecr.aws` and, for Messaging, `ghcr.io`. Retained BReg and Casework
containers using the earlier Docker Hub reference at the same digest remain
accepted; PostGIS sessions still use `postgis/postgis` on Docker Hub.

## Acceptance projects and release operation

The citizen self-registration acceptance project combines native ThunderID SMS
signup, account-owned applications, Casework review, and transactional Person
creation, account linking, and program enrollment through configured BReg
actions. It is an adopter proof using the products' existing boundaries, not a
built-in business model or a new runtime product.

Publication now refuses to create the numbered tag until `registrystack-id`
main pins the exact release source and identifier catalog SHA-256. The release
still rebuilds its own candidate; nightly builds do not substitute for it.
The predecessor-state rehearsal covers BReg, Casework, Evidence, and Messaging
from v0.40.0. Scheduling state remains outside that rehearsal.

Solmara Lab adaptation to the breaking changes is deferred. The approved 1.0
stability promise is unchanged and does not take effect in this pre-1.0 release.

## Support

Security fixes ship in the latest v0.x release. Earlier minor releases receive
no backports, and v0.41.0 has no fixed-duration support window. Release
preparation requires more than six months of remaining upstream support for
pinned LTS dependencies, including compatibility smoke platforms.

[Changes since v0.40.0](https://github.com/registrystack/registry-stack/compare/v0.40.0...v0.41.0).

# Registry Stack v0.47.0

Registry Stack v0.47.0 is the beta-59 release. `rstack dev` runs BReg,
Casework, Evidence, and Messaging projects on your workstation, alone or
together, and replaces the per-product development sessions. Base Registry
Engine (BReg) adds read-only external views over records another registry
keeps, Polygon and MultiPolygon fields, and date helpers for Action plans. An
applicant can see where a submission is in review. Registry Coordinator adds
monthly calendar starts, a service deadline, and a failure route for reads,
and is now promised at Registry Stack 1.0. Every `private_key_jwt` client now
states its client assertion audience. The standalone `registry-language-server`
ships as a release asset for the first time.

Configuration formats are aligned before 1.0, so some keys are renamed and the
old names are refused. Lists of entries that each carry an `id` become mappings
keyed by that id in BReg, Messaging, Scheduling, and Discovery files, and the
shared project block accepts a `label` and `description`. Read the upgrade
section before you start the new binaries. BReg and Scheduling start on a fresh
database, and the Coordinator starts on a fresh namespace. A metrics listener
can now bind to every interface of a container whose network is private to the
deployment, and more products report their background work.

BReg statistics gain sum, mean, distinct-count, ratio, and percentile
measures, exact reads for a named consumer, and exact public releases.

BReg access profiles can require a filter on every list, withhold a record or
its fields from profiles that are not exempt, and require a stated reason for
each request. The repository gains a K3s and Helm reference deployment for
v0.46.0 images, outside the release.

## Compatibility and upgrade

Use matching v0.47.0 runtimes, tools, and clients. Back up each deployment and
follow [upgrade and retire](https://docs.registrystack.org/operate/advanced/upgrade-and-retire/).

BReg and Scheduling start on a fresh database, and the Coordinator on a fresh namespace:

- BReg starts on a fresh database. `bregctl plan` and `bregctl apply` refuse a
  database whose active package was built before this release.
  `bregctl test --baseline-package` and `bregctl diff --runtime-config` refuse
  a baseline package built before this release. The refusal names the way
  forward: recreate the database, build a package with this release, then run
  `bregctl apply --package DIR --initial`. This release no longer reads the
  `entityId` member that packages compiled by v0.38.0 to v0.41.0 wrote in
  place of `recordType`, so a database whose active package was compiled by
  v0.41.0 or earlier cannot be upgraded in place. The refusal names `entityId`
  and the fresh-database path.
- Scheduling starts on a new database. This release does not read Scheduling
  state stored by an earlier release. A stored policy that holds one of the
  id-keyed collections in the list form is refused with a message that names
  the member, for example `services[*].id`.
- The Coordinator starts on a fresh namespace, as described below.
- Evidence and Messaging keep the database state v0.46.0 stored. Their project
  files need the edits listed below, and Messaging needs its package rebuilt.
- Casework keeps its database. No changelog asks it to start fresh, but its
  upgrade is not rehearsed, so back up its database first.

The release upgrade rehearsal starts from the v0.46.0 state and covers Evidence
and Messaging only. For Evidence, it moves the retained project's `id` into a
`project` block with a `version` and turns its `functions` list into a map. For
Messaging, it renames the database CA bundle key, rewrites `providers`,
`senderProfiles`, and `accessProfiles` in map form, rebuilds and checks the
package, and applies it over the previous activation. It then fails unless the
state is still served unchanged. It does not exercise BReg, Casework,
Scheduling, or the Coordinator.

BREAKING for BReg statistical datasets. See
[BReg statistics](https://docs.registrystack.org/configure/breg-statistics/).

- Add `type: minimum-count-and-rounding` to every dataset's `disclosure`
  block. `minimumCount` and `roundingBase` behave as before. A block without
  `type` is refused.
- Every statistical cell now names its measure. In JSON, `dataset.measure` is
  replaced by the `dataset.measures` array, and each cell carries `measure`.
  CSV gains a `measure` column before `value`. Update readers of both
  formats.
- A sum or mean cell's `value` can be a decimal string, and a mean over no
  values has a null `value` with status `not-applicable`. Treat an unknown
  status as no usable value. Datasets that declare only counts serve the same
  values.
- A dataset declares at most 12 dimensions.
- The definition digest now covers the disclosure method and the measures, so
  every dataset's digest changes once on upgrade. Releases published before
  the upgrade stay stored but are no longer served. Republish the periods you
  still need.

BREAKING: every `private_key_jwt` client states its client assertion audience,
with no default. The assertion carries that audience as its only value, with
the header `typ: client-authentication+jwt` (RFC 10070 section 4). A
configuration without the member fails to load and names it. Set each member
to the authorization server's issuer identifier, exactly as its metadata
publishes it:

- BReg: `evidenceProviders.<id>.privateKeyJwt.assertionAudience` in the
  runtime configuration.
- The BReg MCP gateway (`breg-mcp`): `assertionAudience` on its token
  exchange.
- Casework: `clientAssertionAudience` on each `contextProviders` binding and
  on its `delegatedDisplayExchange`. Casework refuses a file without it with
  `config.missing-key`.
- Coordinator: `clientAssertionAudience` on every connection `authorization`
  and `observationAuthorization` in `runtime.yaml`. An
  `observationAuthorization` states the same audience as its primary
  `authorization`. See the Coordinator entry below before you upgrade.
- Evidence: `clientAssertionAudience` on an `oauth2-private-key-jwt` source
  credential in the runtime configuration and the bundle, and on an
  `oauth2-private-key-jwt` connection in the authored target. Also
  `oauth.clientAssertionAudience` in an Evidence client profile, and
  `tokenClient.clientAssertionAudience` in the `evidence-oid4vci`
  configuration. `evidencectl client profile create` requires
  `--client-assertion-audience`.
- Adapter: `clientAssertionAudience` on an `oauth2-private-key-jwt` runtime
  credential, and on an ingestion job's `direct-breg` destination.
- Saved CLI connections: `assertionAudience`. The tools refuse
  `--private-key-jwt` without `--assertion-audience`.
- Node.js and Python clients: `audience` in `privateKeyJwt`
  (`private_key_jwt`), in the exchange `client`, and in the remote
  `bootstrap`. A client without it is refused at construction with kind
  `configuration`. A progressive Evidence client also requires the
  discovered issuer to equal this audience.
- Rust platform crate users: `registry-platform-httputil`'s
  `PrivateKeyJwt::new` refuses a `PrivateKeyJwtConfig` without
  `with_audience`, and `PrivateKeyJwtConfig::check_identity` takes the
  audience as `&str`.

BREAKING: the Coordinator starts on a fresh namespace. Protected state schema
version 6 adds a durable calendar cursor and an optional service deadline on
each Run. It refuses version 5 namespaces. The connection audience above is
also part of each connection's binding, so a Run admitted without it no longer
matches. Settle open Runs with the v0.46.0 binaries. Then apply v0.47.0 to a
fresh namespace and database identity. While a live Run remains,
`coordinatorctl deployment-status` with the upgraded configuration reports
`live-binding-conflict`. `coordinator --recovery-only` inspects it with
admissions and dispatch disabled.

BREAKING: configuration keys are renamed before 1.0 so that the products
agree. Each old key is refused as an unknown key, so the product fails to start
until you change it. Values do not change. Edit these files before you start
the v0.47.0 binaries:

- The TLS trust anchor of the shared `database` block:
  `database.trustedRootCertificateRef` is now `database.caBundleRef`. It is
  still a secret reference to the PEM CA bundle the connection trusts. This
  applies to the runtime configuration of BReg, Casework, Coordinator,
  Scheduling, Messaging, the Document Store, and the Adapter facade. In the
  Adapter job runtime configuration, `store.trustedRootCertificateRef` is now
  `store.caBundleRef`. A Messaging `smtp` provider's
  `providers.*.trustedRootCertificateRef` is now
  `providers.*.caBundleRef`. `rstack dev` writes the new key in the runtime
  files it generates.
- Discovery `origins.yaml` (`DiscoveryOrigins`): `origins[].originId` is now
  `origins[].id`. See the Discovery entry below for the new id rules and the
  record-id effect of renaming an origin.
- Evidence `EvidenceProject`: the top-level `id` is now `project.id`, and the
  new `project.version` (a human release label) is required. The top-level
  `label` and `description` are now `project.label` and `project.description`.
  A top-level `label` or `description` is refused with `config.removed-key`.
  `functions` is a map keyed by the Function id, so
  `functions: [{id: X, ...}]` becomes `functions: {X: {...}}`. The Evidence
  starter fragment `evidence/starter/definitions.yaml.fragment` now writes that
  shape.
- Coordinator `CoordinatorProject`: the top-level `label` and `description` are
  now `project.label` and `project.description`. A top-level `label` or
  `description` is refused with `config.removed-key`. The compiled presentation
  and the workflow's identity do not change.
- Render: the deprecated bare hex digest members and headers are removed. See
  the Render entry below for the names and the upgrade order.

Run each product's `check` command on the edited files before you restart.

BREAKING: collections that were lists of entries with an `id` member are
mappings from each id to the rest of the entry. This is a pre-1.0 cleanup, so
an item has one name and a duplicate cannot be written. In every file below, the
old list shape is refused, and so is an `id` member inside an entry, with a
message that names the mapping. A repeated key is refused at the repeating key.
Items are held sorted by id. Check findings and the source pointers in
`bregctl explain` name the id in place of the position, for example
`/senderProfiles/reminders-sms/onUncertain`. An entry with nothing else to say
is written `registry: {}`.

- BReg project and modules: `datasets`, `vocabularies`, `statisticalDatasets`,
  `reviewAuthorities`, `evidenceProviders`, `externalRecordTypes`,
  `externalProjections`, `externalViews`, `actions`, `functions`,
  `accessProfiles`, and `recordTypes`. Write
  `datasets: {registry: {display: ...}}` in place of
  `datasets: [{id: registry, display: ...}]`, and the same for each of the
  others. A module's `accessProfiles` on its Record types and on its
  `extendRecordTypes` entries are mappings too.
- BReg `extendRecordTypes` is a mapping from the extended Record type to the
  extension, with no inner `recordType`, so a module extends a type once. Write
  `extendRecordTypes: {entry: {fields: ...}}` in place of
  `extendRecordTypes: [{recordType: entry, fields: ...}]`.
- BReg `modules` lock: write
  `modules: {core: {version: 0.1.0, digest: sha256:...}}` in place of
  `modules: [{id: core, version: 0.1.0, digest: sha256:...}]`.
- After converting a BReg module, run `bregctl project lock`. Every module
  digest changes, even a module that declares no action or function, because an
  empty list is now an empty mapping. Registry revisions change with them.
  Compiled output, explanations, and the manifest metadata keep their shapes.
  Commands that listed `datasets`, `reviewAuthorities`, or a module's actions
  in the order the project wrote them now list them in id order.
- Two default access profiles may no longer share an operation on one Proposal
  action. BReg refuses them with `breg.proposal.default-multiple`.
- `bregctl module add consent` refuses a project that already declares an access
  profile the module would generate, with `module.consent.profile-clash`
  naming the profile.
- Messaging `messaging.yaml`: `providers`, `senderProfiles`, and
  `accessProfiles`. Write `providers: {mail-relay: {type: smtp}}` in place of
  `providers: [{id: mail-relay, type: smtp}]`, and likewise for the other two.
  `templates` stays a list, because a template is named by its id and version.
  The authoring schema states each mapping's size as `minProperties` and
  `maxProperties`. Rebuild packages with `messagingctl package`, because the
  package digest changes.
- Scheduling `scheduling.yaml`: `services`, `offerings`, `holidaySets`,
  `openings`, and `hooks`. Write
  `services: {registry-update: {label: Registry record update}}` in place of
  `services: [{id: registry-update, label: Registry record update}]`, and
  likewise for the other four. The `locations`, `pools`, `windows`, and
  `exceptions` lists in `records.yaml` and the fixture files are unchanged.
  Findings read like `/offerings/registry-update-30/exactTime/durationMinutes`,
  and the `schedulingctl check` report lists ids in sorted order. Rebuild
  packages with `schedulingctl package`, because the policy digest changes.
  Scheduling then starts on a new database, as the upgrade section says.
- Discovery `origins.yaml`: `origins` is a mapping from each origin id to the
  rest of its entry, held in id order, with the `id` member gone. Write
  `origins: {evidence-one: {catalogUrl: ...}}`. A repeated key is a
  `yaml.duplicate-key` finding at the repeat, which replaces
  `discovery.origins.duplicate-origin-id`. Findings read like
  `/origins/evidence-one/catalogUrl`. The schema bounds the mapping at 128
  entries. The published provider-publication profile does not change.
- `caseworkctl provider add` prints the BReg project fragments it proposes in
  the keyed form: `accessProfiles`, `reviewAuthorities`, and `actions` entries
  are keyed by id, with no inner `id`. Change paths and failure locations in
  the BReg project name the id as a path segment, for example
  `actions/correct-address/execution/proposal/reviewContext` in place of
  `actions[id=correct-address].execution.proposal.reviewContext`. A location in
  `bregctl explain` output, which keeps its list shape, keeps the selector form.

The shared project block of Adapter, Casework, Coordinator, Evidence, Messaging
and Scheduling also accepts an optional `label` and `description`, as display
text for people. They change no behaviour or compiled output. A Messaging or
Scheduling package digest covers the authored files, so adding or changing one
changes it. BReg is the exception: its display text stays under
`project.display`, which is part of the registry revision, and a BReg project
that sets `project.label` or `project.description` fails to parse.

BREAKING for Render callers: upgrade every product and binding that calls
Render with or before the Render server. A v0.46 client still requires
`pdfSha256` and `dataSha256`, and fails every render with a `protocol` error
when the server no longer sends them. Read `pdfDigest` and `dataDigest`

BREAKING for Discovery consumers: an origin keeps its record ids when its id
already fits the new local identifier pattern. An origin you rename to fit the
pattern publishes its new id as `originId`, so its record ids change. Tell
every consumer that pins that `originId` to pin it again.

BREAKING for Coordinator clients: upgrade the Rust, Python, and Node clients
with the server, once. Clients from before this release refuse response
members they do not recognise. They refuse every run status that carries the
new `stepLabel`, even when it is `null`. From this release the clients ignore
unrecognised members, so a later minor release can add members without
another client upgrade. Rust code that builds the client `RunStatus` as a
struct literal must set `step_label`.

BREAKING for Evidence, OID4VCI, and OID4VP metrics: the metrics listeners
refuse link-local and IPv4-mapped IPv6 addresses. If you bound metrics to an
address such as `169.254.1.1:9090`, move it to a loopback or private address.
You can also set `metricsListener.networkExposure: container-private`, as
described under operator metrics below.

BREAKING: BReg holds task grants to their stated limits. See
[BReg task grants](https://docs.registrystack.org/reference/breg-task-grants/).

- A bearer token that carries a Casework task grant (`registry_grant_*`
  claims) must carry `iat` and `exp`. Its lifetime, `exp - iat`, must be at
  most 900 seconds. Its `iat` must not be later than BReg's clock plus
  `authentication.oidc.leewayMilliseconds`. BReg refuses any other such token
  with `401 authentication.refused`, whatever time it has left.
- Confirm that your exchange issuer issues task-grant tokens for at most 900
  seconds, and that its clock agrees with BReg's within the leeway. Casework's
  documented exchange step uses 300 seconds. Tokens without a task grant keep
  the `authentication.oidc.maximumTokenLifetimeSeconds` ceiling.
- Record reads, read paths, statistics, and the Proposal review-record read
  admit a task grant only before its deadline. The grant must also name the
  request's principal and purpose, read from
  `authentication.authorityClaims.principal` and
  `authentication.authorityClaims.purpose`. A mismatch answers the ordinary
  `404` read refusal. Immediate Actions and Proposals already required this.
- Nothing changes if your principal claim is `sub` and your purpose claim is
  the contextual purpose claim. Otherwise, issue the exchanged token with the
  profile's principal and purpose claims.

BREAKING: the BReg subject access log keeps the access reason and the access
kind in their own columns, and the managed schema fingerprint changes with
them. Install this release on a fresh database. See
[BReg access log](https://docs.registrystack.org/operate/breg-access-log/).

BREAKING: Scheduling appointment detail (`GET /v1/appointments/{id}`) depends
on how the caller was admitted. A token that holds the reads scope reads the
appointments it owns, as before. A token admitted only through an
`appointment.read` task grant is held to that grant's service, location, and
current status. This holds even for an appointment its own subject booked. A client that
reads its own bookings with a grant-only token must also carry the reads
scope. See [Scheduling task grants](https://docs.registrystack.org/reference/scheduling-task-grants/).

BREAKING for Evidence:

- `acquisitionDeadlineMilliseconds` has a maximum of 300000 (300 seconds). The
  limit applies in the authored target
  (`sourceAcquisition.acquisitionDeadlineMilliseconds`) and in the runtime
  configuration. A longer deadline fails to load with a range error that
  names the field. Nothing is clamped, so write a value of at most 300000.
- Evidence does not release an acquisition result after the caller's task
  grant has expired, even inside the acquisition deadline. The caller
  receives `403 evidence.denied`, and the audit records the safe error
  category `grant-expired`. Issue grants that outlast the source round trip
  and signing.
- `evidence-oid4vci` refuses `offers.allowedClients: unrestricted` and
  `offers.requiredScopes: unrestricted` with
  `evidence.oid4vci.offer-gate-unrestricted`, unless `validationMode` is
  `supervised-local-development`. This replaces the v0.46.0 advice to write
  `requiredScopes: unrestricted` where the member was absent. List the clients
  that may request an offer and the scopes they must hold.

BREAKING: Casework refuses a `casework.yaml` whose access profiles for people
name different `principalClaim` values. People's profiles are staff,
supervisor, administrator, an initiator profile, and any other requester
profile. The refusal is `casework.access-profile.mixed-principal-claims`.
Profiles that a trusted producer uses are compared only with each other. Set
the same `principalClaim` on every person's profile, and issue that claim in
every person's token.

BREAKING: the Adapter facade polls an asynchronous write only at the source
origin it was sent to. Before the send, the write's store row pins the
configured `baseUrl` of every endpoint its write, status, and uncertainty
routes reach. Rotating a credential changes nothing. After a `baseUrl` change,
an unfinished write is held and never polled. Its status link answers the
stored 202, and a retry answers 409 without `Retry-After`. This lasts until
you restore the original `baseUrl` or the write expires. Let asynchronous
writes settle before upgrading. Rows written by an earlier version are
quarantined and expire.

BREAKING for Adapter ingestion jobs (`adapter-job`), which you build from the
tagged source:

- An item counts as possibly admitted when its BReg or Coordinator answer was
  lost and the retry was then refused. A later source edit or `rescan` of the
  item goes to the job's revised trigger. Without one, it is held as
  `adapter.job.revised-item`. An item whose first attempt never arrived is
  held the same way. No Adapter command releases a held item.
- Store schema 104 applies this rule to every refused revised event with a
  frozen receiver, and to a refused first registration with a recorded retry.
  Some legacy refused items have earlier attempts the store did not record.
  Before you run `init-store` and resume ingestion, check BReg or the
  Coordinator for admissions of those items. See [operate the Adapter](https://docs.registrystack.org/operate/adapter/).
- The direct BReg receiver identity now includes `clientAssertionAudience`. A
  direct BReg item left pending by an earlier binary stops the pass as
  `adapter.job.breg-receiver-changed`, and no configuration releases it.
  Before upgrading, take a database backup. Then run passes with the previous
  binary until `adapter-job status` lists no pending items.
- `init-store` moves the store to schema 104, which the previous binary
  refuses. If pending items remain, restore the backup, settle them with the
  previous binary, then upgrade and run `init-store` again.

## Local development with rstack dev

`rstack dev` is an alpha developer tool and may change. See
[Run a project with rstack dev](https://docs.registrystack.org/configure/run-a-project-with-rstack-dev/).

- `rstack dev check`, `start`, `status`, `token`, and `stop` run a checkout's
  BReg, Casework, Evidence, and Messaging projects, alone or together. The
  plan is an `rstack/dev` document in `dev.yaml`. `rstack` hands the plan to
  the CLI of the first product it lists, so install only the products the
  plan names.
- Each run starts its own PostgreSQL in Docker, on loopback with TLS. To use
  a server you already run, pass `--database-url` or set
  `RSTACK_DEV_DATABASE_URL`. The PostGIS image that spatial BReg projects need
  is linux/amd64 only, so it runs emulated on Apple Silicon.
- A plan defines up to 256 synthetic people.
  `rstack dev token RUN --as PERSON` writes a bearer header file for one of
  them.
- An optional loopback browser issuer signs a synthetic person in to a
  declared, already-built Node application. Start it with
  `rstack dev start --application-root DIRECTORY`. Your project's access
  profiles must admit the browser client explicitly.
- A Messaging run sends `smtp` mail to a Mailpit container and `http` SMS to
  a mock gateway. The run report lists them under `sinks`, and each product's
  runtime configuration under `runtimeConfigs`. `messagingctl init` now points
  at `rstack dev start`.
- An Evidence project with its own `local-target.yaml` runs on that target.
  The run generates the development secrets the target references.
- A BReg project with encrypted fields runs without extra setup. Each run
  draws its own development data key into its run directory, readable only by
  you, and removes the key with the run.
- In a paired BReg and Casework run, a reviewer can send a separate source
  credential for BReg beside the Casework token.
- `scenarioFile` in `dev.yaml` names an `RStackScenarios` v1alpha1 file inside
  the project. It holds 1 to 16 named scenarios, each of 1 to 32 steps, with
  at most 64 steps in total. The run report lists each result under
  `scenarios` with the file's hash.
- A plan with an inline `journey` key is refused with the fix to move its
  steps into a scenario file. A tool that wrote an inline `journey`, or read
  `journey` from the run report, must write a scenario file and read
  `scenarios` instead.
- A failed step keeps the product's public problem code and trace ID. An
  exact JSON `null` assertion is accepted.
- With `--format json`, refusals and startup failures print a
  `registry.rstack.error.v1` object. Its `error.class` is `domain` (exit 1),
  `usage` (exit 2), or `operational` (exit 3). When the run still holds
  resources, the object names its `run_id` and any known `recovery` details.
- A failed journey exits 1 with the regular run report and leaves the run
  available for you to inspect.
- `rstack dev stop RUN_ID --recover` releases a run whose supervisor is gone.
  It waits for the process guards, drops the run's databases and roles, and
  removes its containers and run directory. You can retry it after a partial
  failure. It retries a database drop that another backend still holds, until
  the cleanup deadline.
- The plan and scenario schemas are published under
  `products/platform/generated/dev/`, and the error object under
  `products/platform/schemas/rstack-dev-error.v1.schema.json`.

## BReg

- Statistical datasets declare `measures`: `count`, `distinct-count` over a
  `reference` field, `sum` and `mean` over integer or decimal fields, `ratio`
  of two additive measures, and `percentile`. Live reads serve every measure
  type.
- A new `read-exact` operation serves exact statistics of ended periods to one
  named machine consumer, through
  `GET /v1/statistics/{dataset}:exact?from=<period>&to=<period>`. The dataset
  names the visibility it computes under with `exactReads`. An exact read is
  as sensitive as the records, so grant it only to a named service under a
  data-sharing agreement.
- A new disclosure method, `exact-public-values`, releases exact values when
  the unit record type and every field the dataset reads are classified
  `public`.
- A `minimum-count-and-rounding` release can carry distinct counts. Sum
  releases under that method have contributor and dominance rules, but stay
  refused with `breg.statistical-dataset.sum-release-held` until a
  statistician has reviewed them. Serve sums through live reads, exact reads,
  or an exact public release until then.
- A publisher can dry-run a publication with
  `POST /v1/statistics/{dataset}/releases/{period}/versions:dry-run`. It
  returns the document a publication would store and the suppressed cells,
  and stores nothing. The clients gain `statistics_release_dry_run`,
  `statisticsReleaseDryRun`, `statistics_exact`, and `statisticsExact`.
- The BReg security model adds BREG-SEC-211 and BREG-SEC-212 and residuals
  BREG-RES-24 to BREG-RES-26 for exact reads and releases.

Read-only external views let a registry show a person or business held in
another registry beside its own Record. BReg does not copy the other
registry's data into the Record. See
[external projections](https://docs.registrystack.org/configure/breg-external-projections/).

- Declare `externalRecordTypes`, `externalProjections` (`mode: live` or
  `indexed`), and `externalViews` in the project. Grant `externalViews` and
  `refreshExternalProjections` in an access profile.
- Only a service profile with explicit clients, scopes, and purposes may hold
  `refreshExternalProjections`.
- In the runtime file, bind each source under `externalSources`. Its
  `allowedFields` is your approval of the outside fields BReg may copy. Give
  each indexed link a refresh plan under `externalRefresh`.
- Readers use `GET /v1/external-views/{view}/{link}/records` and
  `.../records/{root}`. A staff application's service client can ask for one
  root to be refreshed with `POST .../records/{root}/refresh`.
- A source notifier posts to
  `/v1/external-refresh-plans/{plan}/source-changes`. An Adapter projection
  operation serves the outside values.
- BReg runs refresh plans in process, each as its configured worker identity.
  `bregctl check` refuses a plan whose worker its access profile would refuse,
  with `breg.external-refresh.worker-not-admitted`.
- A plain indexed list marks a record whose outside copy is missing as
  `unavailable` and keeps serving the rest. A filtered, sorted, or counted
  list returns `registry-breg/external_view/incomplete` until every record it
  reads has a current copy.
- `bregctl external-projection inspect` and `purge` operate the cached
  values. `bregctl generate external-source-facts` writes the source facts.
- An indexed projection keeps its cache in four store tables and two refresh
  queue tables in `registry_internal`. It needs separate migration and
  runtime database roles.
- Exclude the cached data from logical backups with
  `--exclude-table-data='registry_internal.registry_external_*'`. Physical
  backups, WAL archives, and replicas still carry the cached values. See
  [back up and restore](https://docs.registrystack.org/operate/advanced/back-up-and-restore/).

Access profiles gain three controls. See
[BReg access](https://docs.registrystack.org/configure/breg-access/).

- A record permission can set `requiredFilters`, a list of alternative `fields`
  sets that a `list` must pin with top-level `eq` predicates carrying a
  non-null value. A list or `$count` that does not is refused with
  `400 query.filter_required` before any query runs. The problem carries a
  `requiredFilters` member that names the acceptable sets as API field names,
  and a fixed `detail`. A continuation page cannot drop the criteria, because
  the signed cursor binds the first page's filter.
- `bregctl check` refuses a `requiredFilters` that has an empty alternative,
  repeats an alternative, has more than eight alternatives or an alternative of
  more than 32 fields, names a field outside the same grant's
  `filterableFields` or one that cannot take `eq`, or sits on a grant without
  `list` or with `allowDataExport`, whose pages carry no filter
  (`breg.access-profile.required-filters-export-unsupported`). An empty `requiredFilters` is refused when the file is read, with
  `config.invalid-value`, so omit the key to put no criteria on lists. A field
  repeated within one alternative is refused with `config.duplicate-item`.
- Runtime metadata lists the alternatives beside `filterableFields`. The Rust
  client exposes `BRegQueryDescriptor::required_filters` and
  `BRegProblemCode::QueryFilterRequired`. The OpenAPI problem enum gains
  `query.filter_required`, and the Problem schema gains a bounded
  `requiredFilters` member, so a package's revision changes on rebuild. The
  OpenAPI declares that `400` on a list operation only where an admitted
  profile requires a filter. The ODRL export omits a list grant under
  `requiredFilters`, with the reason `required-filters`, and still exports its
  get. The key governs `list` only. Lookups, get, read paths, and `snapshot` are
  unchanged.
- A Record type can declare `disclosureConditions`, a mapping from each
  condition id to the condition. Each is a conjunction of one to four literal
  tests on the record's current values. It withholds the whole record
  (`withhold: record`), its revisions and snapshots (`history`), or named
  optional fields (`fields`) from every access profile that does not list it
  under `exemptProfiles`. A profile that writes the type only through an Action
  or Proposal permission can be listed. The record timer is never withheld
  from.
- A withheld record answers as an absent one. A withheld member is `null` on
  reads and revisions and absent from write responses. A JSON Patch `test` on a
  withheld field is refused. A direct write, immediate Action, or Proposal
  applied by hand is refused with `write.outside-boundary` when a `record`
  condition would hide its result from the writer. It is also refused when a
  condition that binds the applying profile matches the record and the write
  names a field it withholds, changes a field a constraint checks together with
  one, or would lift the mark. A bound profile cannot tombstone a record that a
  `fields` or `history` condition binding it matches. An import item the write
  rule refuses answers the generic `412 precondition.failed`.
- A Proposal applied automatically is checked against the profile that
  submitted the version being applied. An exempt submitter's Proposal can make
  that change, and one whose submitting profile was removed or lost its
  exemption is refused. An automatic Proposal still reads and writes under
  `system-proposal-apply`, which no condition can exempt. So even for an exempt
  submitter it cannot change a record a `record` condition matches or set a
  `record` mark. It ends `blocked` with no retry scheduled and the record
  unchanged. Use an immediate Action, or apply the Proposal by hand under an
  exempt profile.
- PostgreSQL enforces a `record` condition as a restrictive row policy.
  `bregctl check` refuses a bound profile whose filters, sorts, lookups,
  export, hook projections, read paths, row, membership, or consent boundaries,
  derived fields, spatial queries, Evidence facts, external view links, or
  statistical datasets reach a withheld value (`breg.disclosure.*`). A read path
  grant whose `filterableFields` or `sortableFields` names a field withheld on
  the path's `to` Record type is refused
  (`breg.disclosure.read-path-withheld-field`), because the filter and sort run
  before the field is withheld. It refuses a read path grant that reads,
  filters or sorts a derived field when the derived SQL reads a withheld field
  (`breg.disclosure.derived-reads-withheld-field`). It refuses a `record`
  condition on a consent Record type that a `requireConsent` names
  (`breg.disclosure.consent-record-condition`), because the consent check reads
  that type under the gated profile and a hidden revocation would let an earlier
  consent stand. A `fields` or `history` condition there stays allowed. It also
  refuses a Record timer that reads a withheld field, and a Record timer on a
  hidden record that creates a record a bound profile reads.
- `bregctl check` warns when a field a `fields` condition withholds is in a
  uniqueness constraint or a partial one's `when`, a unique encrypted lookup, or
  a temporal non-overlap. A Create, or a Patch of another record, that repeats
  the value answers `409` and confirms that it exists on a hidden record
  (`breg.disclosure.withheld-field-probe`). It also warns when a `record`
  condition on a view's root binds a profile that may refresh the view, because
  the refresh then skips the records the condition matches and still succeeds
  (`breg.disclosure.external-refresh-withheld-root`).
- Runtime metadata flags `mayBeWithheld` and lists the bound conditions without
  their literals. `bregctl explain access` lists them in full, the access
  preview names the ids that bind a profile, and the ODRL export omits a grant a
  condition binds (`disclosure-condition`). Proposal inputs stay visible to
  reviewers, and a uniqueness or reference conflict on a Create or Patch can
  reveal that a withheld record exists. The
  [BReg security model](https://docs.registrystack.org/security/breg/) gains
  obligation 22 and BREG-RES-27 for these limits. Packages that use the new key
  change revision, and the metadata, OpenAPI, and Explain documents gain members that
  earlier clients ignore.
- An access profile can set `requireAccessReason: true`. A request under it
  without a valid `Registry-Access-Reason` header (unpadded base64url UTF-8, at
  most 512 bytes) is refused with `400 request.access_reason_required`. The
  reason is stored on the subject access log entry and returned as
  `accessReason`.
- On a Record type with `accessLog`, each record a direct Create, Patch, Batch
  item, or Tombstone changes gets an entry with the reason and
  `accessKind: write`, written in the same transaction and raising no read
  alert. Action and Proposal writes record none. A read entry carries
  `accessKind: read`.
- A hook with `trigger: read` and `profiles` raises a value-free event for each
  logged read by those profiles, carrying an `access` object. The event is
  written with the access log entry, so `bregctl check` refuses a read hook on
  a Record type without `accessLog`
  (`breg.disclosure.read-hook-access-log-required`).
- `bregctl check` refuses `requireAccessReason` on a profile that grants import,
  invoke, start, `allowDataExport`, or an action, proposal, dataset, external
  view, or projection-refresh permission, which do not check the reason
  (`breg.access-profile.access-reason-operation-unsupported`). The ODRL export
  omits each grant of such a profile (`access-reason`).

Other BReg changes:

- A `crs84-polygon` field stores a bounded `Polygon` or `MultiPolygon` in WGS
  84 longitude and latitude. It takes `precision`, `maximumPositions`, and an
  optional `bbox`. The compiler validates it with PostGIS and generates a
  stored geometry column with a GiST index. A bbox grant filters Polygon and
  MultiPolygon fields by bounding-box intersection, as it does for a Point.
- A Rhai Action plan can call `today()`, `add_days(date, days)`, and
  `add_months(date, months)`. A registry that calls `today()` must set
  `project.timezone`. A Proposal plan evaluates `today()` when the Proposal
  starts, and its guards compare again at Apply.
- A date guard in `commitGuards` accepts `currentDateOffsetDays`, a signed
  whole-day offset. `bregctl project action-test` takes
  `--evaluation-date YYYY-MM-DD`, which a handler that calls `today()`
  requires. See [Actions](https://docs.registrystack.org/configure/breg-actions/).
- An applicant can see where a submission is in review. Set
  `readableReviewProgress: true` on the caller-owned Proposal grant that
  includes `get-review-status`. Then read the Proposal's `reviewStatus` link
  with `include=progress`.
- The progress response can add a `progressCode` from the review provider,
  and omits the Proposal ETag. The clients expose
  `read_proposal_review_status_with_progress` and
  `readProposalReviewStatusWithProgress`. See
  [Proposals](https://docs.registrystack.org/configure/breg-proposals/).
- Fix reading back an encrypted field on PostgreSQL. A read failed with
  `503 source.unavailable` once a stored value's encrypted envelope exceeded
  57 bytes. A reviewed migration whose history capture read such a value
  failed its apply.
- The encrypted-field fault was in every release from v0.33.0 through v0.46.0.
  No stored data changes, and nothing needs migrating.
- Runtime Action metadata (`GET /v1/registry`, `metadata/registry.json`, and
  the OpenAPI `x-registry-action` extension) carries `execution.review`
  (`none` or `required`) and `execution.application` (`manual` or
  `automatic`) for each Proposal Action. A host can use them to explain what
  follows Submit. Immediate Actions carry neither. The review authority,
  source, policy, and attempt limit stay in the build-time Action contracts.
  The members are additive within `metadataVersion: "2"`, and earlier clients
  ignore them.
- The Rust client exposes `BRegActionDescriptor::review()` and
  `application()`. They return `BRegActionReview` and `BRegActionApplication`,
  each with an `Unknown` variant for a value the client does not recognise. The
  `registry-stack-client` facade re-exports both. The Node.js and Python
  clients expose `review` and `application` on each Action as the served
  string. They are `null` (`None` in Python) when an older server sends none.
- Request audit records include a keyed `clientReference` when the bearer
  verifier matches an allowed OAuth client. It uses the same pseudonym as
  `authorization.clientPseudonym`. Client identifiers and tokens stay out of
  the journal.
- The Node.js client's record, list, continuation, metadata, contract,
  schema, revision, and lookup reads accept a final `{ signal: AbortSignal }`
  argument. Aborting rejects with a `BaseRegistryClientError` of kind
  `cancelled`, and no read is retried.
- The Node.js and Python clients expose the ETag observed on each Proposal
  response, as `responseEtag` and `response_etag`.

## Casework

- A review stage can offer a subset of the policy's outcomes with
  `stages[].outcomes`. A stage that omits the list offers every outcome.
  `caseworkctl check` refuses a stage that offers no advancing outcome.
- A stage can show the applicant a coarse progress code with
  `publicProgressCode`. The code is part of the frozen policy digest. The
  admitted producer reads it with
  `GET /v1/review-requests/{requestId}?include=progress`.
- Before you activate a policy that sets a progress code, upgrade clients that
  decode the full policy. An older client may reject the added stage field. A
  policy that omits the field keeps its earlier digest.
- A human reviewer's request can carry a separate credential for the source
  registry. Set `humanSourceAuthentication: {audience: ...}` on a
  `contextProviders` binding, with an audience that differs from Casework's
  own.
- The request then sends one `Registry-Source-Authorization: Bearer ...`
  header. Both tokens must be human, with a scalar audience and the same
  issuer and `sub`. The source registry still enforces its own client,
  profile, and disclosure. See
  [Casework configuration](https://docs.registrystack.org/reference/casework-configuration/).
- The Rust, Node.js, and Python clients take a `HumanSourceCredential` per
  call and report `humanSourceCredentialContract()`
  (`human_source_credential_contract` in Python).
- `caseworkctl explain` adds a top-level `accessProfiles` list with each
  profile's `id` and `principalClaim`.
- `caseworkctl check --runtime-config` refuses a `contextProviders` binding
  that startup would refuse, without resolving a secret. The diagnostic is
  `casework.runtime.invalid-context-provider`.
- `rstack dev` runs Casework projects through the installed `caseworkctl`, so
  a plan with only Casework projects needs no `bregctl`.

## Coordinator

- A workflow can start on a reviewed monthly calendar. Write `MIN HOUR 1 * *`
  or `MIN HOUR L * *` with a named IANA timezone. Admission supplies only
  `scheduledAt` and catches up with the latest due occurrence. It records how
  many occurrences it skipped.
- A new Workflow revision keeps an occurrence already due, unless the
  trigger's cron or timezone changed. A changed schedule runs nothing the
  previous one left due, and audits the skipped count as
  `calendar-reschedule`.
- `workflow.serviceDeadlineSeconds` sets an optional service deadline with a
  separate `onDeadline` path. It counts from Run admission and caps wait
  wake-ups. A still-pending wait takes `onDeadline` once, including after a
  restart.
- Read and evaluation call steps take an optional `onFailure` route. A
  definite availability failure takes it once the retry limit is exhausted. It
  is also taken when the next retry would not fit before the run deadline.
- The `onFailure` edge carries no call output. Mutations, refusals, invalid
  answers, and uncertain outcomes remain operational failures.
- Every run status carries `stepLabel`. It appears in start, status, list, and
  cancel answers and in the `run` member of an inspection. It is the authored
  label of the current step, read from the workflow definition the run was
  admitted on, so a later package that only relabels the step does not change
  it. It is `null` when the step has no label and after retention erases the
  run's stored payload. The protected state schema does not change.
- The Coordinator is now promised at Registry Stack 1.0, as the sixth promised
  product, instead of an experimental surface. The promise covers the
  `workflow.yaml`, `runtime.yaml`, and `scenarios.yaml` formats, the HTTP API,
  and the `coordinator` client namespace. Operations that call Registry
  Scheduling or Registry Messaging stay experimental with those products. The
  state baseline and the `v1alpha1` version strings do not change.

## Registry Adapter

- A reviewed projection operation serves BReg's read-only external views. A
  projection pack whose `fieldsSchema` constrains which fields are present is
  refused when the projection compiles. Describe each field only.
- An ingestion job can receive a governed offline QField submission. The
  `qfield-postgis` example reads a site point, its boundary polygon, and
  repeated contact rows from the collection database QFieldSync returns to.
  It starts a BReg Action or Proposal from them.
- PostgreSQL job sources can project bounded JSONB values, such as that
  geometry and its related rows. Item keys and query parameters stay scalar.
- The `adapter-job` host is still not released. Build it from the tagged
  source to use these job features.

## Evidence

- A `requestNonce` that is not 32 random bytes in unpadded base64url (43
  characters), or that repeats within a batch, is refused as
  `request.nonce-invalid` (400) instead of `evidence.invalid-request`. The
  problem detail states the expected format and never carries the value sent.
  A client that branches on `evidence.invalid-request` for this case must also
  accept the new code. The Evidence clients already classify it as
  `invalid-request`.
- The check, explain, and inspect reports show the project's version under
  `projectPresentation`. The compiled `EvidenceBundle` still carries only the
  project id, so bundle bytes and definition revisions do not change.
- A reader refuses a duplicate Function id as a duplicate key, so the
  `evidence.project.function-unique` finding is gone. Diagnostic paths name the
  Function by id, for example `/functions/derive-status/source` instead of
  `/functions/0/source`.
- A relying party can test its own verification of an Evidence answer. The
  synthetic vector in `fixtures/conformance/consumer-verification/` gives a
  signed response, the key to pin, the expectations, and the cases to accept or
  refuse. See
  [Verify an Evidence answer](https://docs.registrystack.org/configure/verify-an-evidence-answer/).

## Render

- The render route and `compile --format json` send only the labelled digests.
  The bare hex members and headers are removed: `pdfSha256` is now
  `pdfDigest`, `dataSha256` is now `dataDigest`, `X-Registry-Pdf-Sha256` is now
  `X-Registry-Pdf-Digest`, and `X-Registry-Data-Sha256` is now
  `X-Registry-Data-Digest`. The OpenAPI document no longer declares the old
  names.
- Audit entries rename `pdfSha256` to `pdfDigest` and `dataSha256` to
  `dataDigest`. Their values are labelled `sha256:<hex>`, like the seal digests
  beside them. Update any reader of the audit journal.
- In `registry-render-client`, `RenderedDocument` drops `pdf_sha256` and
  `data_sha256`. The Node and Python bindings drop `pdfSha256` and `dataSha256`.
  The client checks `pdf_digest` against the bytes and checks that
  `data_digest` is labelled.
- The OpenFn example `integrations/openfn/receipt-job.js` posts `pdfDigest`
  (labelled `sha256:<hex>`) to the delivery endpoint in place of `pdfSha256`.
  It returns `receipt.pdfDigest` in place of `receipt.sha256`.

## Discovery

- The id of an origin is a local identifier: a lowercase letter, then up to 63
  lowercase letters, digits, `_`, or `-`. Uppercase letters, `.`, a leading
  digit, and ids longer than 64 characters were accepted before. They are now
  refused at `/origins/N/id`. The `discovery.origins.invalid-origin-id` finding
  is gone, and the shared local identifier check reports instead.
- `origins[].enabled` is optional and defaults to `true`. `enabled: false`
  still leaves an origin out of `discoveryctl package`.
- For an origin whose id already fits, the index, the resolve API, and record
  ids do not change. The published member stays `originId`, and a record id
  hashes the same inputs as before.

## Operator metrics

- Registry Scheduling, the Document Store, Render, and the Adapter facade and
  job can serve Prometheus metrics on an optional operator-private listener.
  Set `metricsListener.bind` to a loopback or private address, distinct from
  the serving listener. It is off by default, and the serving listener never
  answers `/metrics`. Render refuses a link-local address, and the Adapter
  refuses an address equal to its serving or hook listener when it reads the
  document. A metrics listener closes within 10 seconds of a stop signal, even
  with a stalled client.
- Scheduling reports outbox and observer-hook work by state, including
  `dead-lettered`, how far the oldest pending item is past its due time, the
  last success of the hold-expiry and retention workers, and requests by route
  and status class.
- The Document Store reports content verification, erasure, and hook delivery
  jobs by state, the age of the oldest overdue item of each, the last success
  of the cleanup pass, and requests by route and status class.
- Render reports documents by operation and result, audit write failures, and
  the seconds until each configured seal certificate expires.
- The Adapter facade reports requests by route template and status class,
  upstream failures by class, journal write failures, and retention sweep
  failures. The job reports items by state, including `held` and `refused`, the
  age of its last settled pass, pass failures, hook refusals, and failed item
  samples. Held items stay read-only, and the owning product resolves them.
- BReg adds `breg_hook_deliveries` by state, including `dead-lettered`, and
  `breg_ingestion_runs` by state, including `blocked`. Its monitor page now
  lists all seven background workers, including `record-timer`.
- Casework adds `casework_completion_deliveries` by state, including
  `dead-lettered`, and `casework_completion_oldest_undelivered_age_seconds`.
  Review counts and the backlog are sampled separately, so one failing read
  does not hide the other or set `casework_database_up` to 0.
- Coordinator adds `coordinator_runs_attention` by reason,
  `coordinator_runs_restore_review_required`, `coordinator_hold_active` for the
  restore and admissions holds, and `coordinator_oldest_due_age_seconds` for
  the oldest pending step a worker can claim. The counts cover every run, not
  the capped list in `coordinatorctl doctor`.
- Every metrics listener accepts `metricsListener.networkExposure`. The default,
  `private-address`, keeps the loopback-or-private rule. Set
  `metricsListener.networkExposure: container-private` to also allow the
  unspecified address (for example `0.0.0.0`), for a container whose network is
  private to the deployment. This covers BReg, Casework, Coordinator,
  Scheduling, Messaging, the Document Store, Render, Evidence, the OID4VCI and
  OID4VP services, and the Adapter facade and job.
- Database-backed gauges in BReg, Casework, Coordinator, Scheduling,
  Messaging, and the Adapter job are read under one 5 second scrape deadline.
  The server cancels a slow read with a statement timeout set to the time left.
  The product logs a failed read by error class.
- A failed sample does not stop the other samples. BReg, Coordinator,
  Messaging, Scheduling, Casework, and the Document Store count failures in
  `breg_metrics_sample_failures_total`,
  `coordinator_metrics_sample_failures_total`,
  `messaging_metrics_sample_failures_total`,
  `scheduling_metrics_sample_failures_total`,
  `casework_metrics_sample_failures_total`, and
  `documents_metrics_sample_failures_total`. A failed gauge is left out and is
  never reported as zero.

  to RUSTSEC-2026-0565: STARTTLS reply injection, missing dot-stuffing after a

  CVE-2026-19499.

- Every image advisory baseline records eight High findings in the
  `libssl3t64` 3.5.7-1~deb13u3 overlay as accepted risk: CVE-2026-124709,

  Debian publishes a fix.

`adapter-job` host and `evidence-oid4vp`. The Coordinator image stays held,
while its binaries, installer, and clients ship as before.

# Registry Stack v0.40.0

Registry Stack v0.40.0 is the beta-52 release. It establishes one configuration
convention across the maintained products, with explicit document envelopes,
shared identifiers and scalar rules, typed URLs and secret references,
kebab-case protocol words, positioned diagnostics, and common offline checks.
It also makes keyed mutations safer to recover, adds Casework reviewer and
Supervisor discovery, includes Scheduling in the unified Node.js and Python
clients, and publishes the compatibility promise that takes effect at 1.0.

BREAKING: v0.40.0 does not upgrade v0.39.0 configuration, packages, or databases
in place. Rewrite retained configuration, rebuild packages, and apply stateful
products to new databases. No automatic migration is provided. The forward
state path starts at v0.40.0; later releases again read the state their immediate
predecessor wrote.

## Compatibility and migration

Use matching v0.40.0 runtimes, tools, and clients. Before changing a development
or pilot deployment, take the backups described in
[upgrade and retire](https://docs.registrystack.org/operate/advanced/upgrade-and-retire/),
finish recovery of outstanding writes against the earlier runtime, and stop
that runtime before directing callers to the fresh deployment. A fresh database
does not remember earlier spent idempotency keys: replaying an earlier committed
write against it can execute that write again.

The complete configuration migration notes below are part of this release's
notes. They preserve every breaking item, its replacement form, migration step,
and diagnostic mapping. Read the complete fragment for each product you use,
including its "Protocol words" and "Stable move" sections. There are 269
numbered or headed breaking migration items across the nine product fragments;
related changes shared by several products appear in each affected fragment.
The product changelogs additionally record Rust API removals and changes outside
the configuration program.

### Rewrite configuration and rebuild packages

- BREAKING: authored, operator, fixture, development-state, and report formats
  move to explicit product-owned envelopes and shared reader rules. Use the
  exact `apiVersion`, `kind`, keys, values, identifiers, and bounds in the
  linked migration notes. Retired forms have no compatibility aliases. Registry
  Manifest's exchange envelopes and Evidence's frozen deployment grammars keep
  their documented exceptions; do not apply another product's envelope to them.
- BREAKING: variant blocks use `type` where documented, including issuer
  `jwksSource` and action or hook handlers. Multi-word protocol values, tooling
  statuses, and client error classifications use kebab-case where the product
  notes specify it. Update configuration and comparisons in scripts, clients,
  audit queries, and alerts using the complete old-to-new tables. Standard-owned
  words, including registered OAuth error codes, keep their standard spelling.
- BREAKING: offline checks use positioned, value-free diagnostics and the shared
  exit contract: 0 accepted, 1 refused or denied warning, 2 usage error, and 3
  unreadable input. Update automation that matched old sentences, dotted field
  paths, diagnostic codes, report members, or product-specific exit values.
  The product notes name commands whose report changes are additive.
- BREAKING: closed inputs refuse unknown or duplicate keys, explicit nulls,
  forbidden substitution, invalid or duplicate identifiers, and out-of-range
  values. Runtime substitution is allowed only at declared scalar positions.
  Replace secret paths with the documented secret references and enable only
  the required providers. Delete optional members written as null; do not
  replace them with empty values unless the format permits that form.
- BREAKING: shared URLs refuse raw backslashes, whitespace, control characters,
  and hosts the URL parser rewrites. Write internationalized hosts in punycode,
  canonical IPv4 addresses, and `%20` or `%5C` for a space or backslash in a path
  or query. Issuer equality remains textual. Rust callers constructing the
  checked issuer or JWKS URI fields must use `registry_platform_yaml::Url::new`.
- BREAKING: OIDC `allowedClients` is required and repeated clients are refused.
  List the clients the deployment admits. Use `unrestricted` only where the
  product explicitly allows it; Scheduling and Messaging allow it in no mode.
  A client listed in `assertionIssuers` must name at least one issuer. Remove
  an empty entry to grant it no exchange authority, or supply its issuers.
- BREAKING: existing compiled packages and retained development-session files
  cannot be treated as current inputs. Re-lock modules when the product notes
  require it, build new packages with v0.40.0 tools, repin expected digests, and
  start fresh local sessions and databases. A v0.39.0 package is not a supported
  predecessor for an in-place activation. Render's maintained PDF and data
  hashes are unchanged, but its packages and expected digests must be rebuilt.

### Recover outstanding writes before the state reset

- BREAKING: BReg spends an idempotency key once per configured issuer and
  verified caller across ordinary write routes. A changed write under that key
  answers `409 idempotency.conflict`; an exact retry after the receipt horizon
  answers `410 idempotency.expired` and never executes again in that database.
  Use a fresh key for every distinct write. The receipt horizon is
  `idempotency.receiptRetentionDays`, default 7 and at most 365 days. Use
  `bregctl idempotency-retention erase-expired --runtime-config PATH --before RFC3339`
  to erase held responses past it. That operator command also clears the raw
  caller fields after the horizon while keeping the key spent. BReg schedules
  no automatic sweep.
- BREAKING: BReg's caller-scoped idempotency store is an engine capability.
  Rebuild the package and apply it to a new database with `bregctl apply
  --initial`. No earlier spent key or response is carried over. Resolve lost
  responses against the earlier deployment before the change, since a replay
  to the new database can execute again.
- BREAKING: no BReg ingestion run, chunk, or receipt crosses the state reset.
  Ingestion runs now belong to the verified caller rather than an audit-keyed
  pseudonym. An earlier `bregctl data import` checkpoint cannot resume against
  the new registry. Import again using a fresh checkpoint path.
- BREAKING: Messaging scopes spent submission keys to the verified issuer and
  subject. Rotating the audit hash key no longer frees them. A changed request
  after `retention.submissionReceiptRetentionDays` answers
  `409 idempotency.key-reused`. Before directing callers to v0.40.0, stop new
  submissions, let in-flight senders finish same-key recovery against the
  earlier runtime, and stop every earlier runtime. The fresh database remembers
  no spent keys, so retrying a previously committed submission can send twice.
- Scheduling owns claims by the verified issuer and subject, so audit-key
  rotation no longer detaches the caller from its holds and appointments.
  Expired receipt retention clears raw caller fields while keeping spent keys.
  Observe an uncertain outcome by its external reference before attempting a
  distinct booking. Do not treat `idempotency.expired` as proof that no earlier
  commitment exists.

### Base Registry Engine authorization and action handlers

- BREAKING: governed record, history, statistics, attachment, GIS,
  ingestion-run, and discovery reads refuse `HEAD` with the concealed 404 used
  for an unsupported method. Send `GET`. `/health`, `/healthz`, and `/ready`
  continue to accept `HEAD`.
- BREAKING: a standing agent profile, `actorKind: agent` without `taskGrant`,
  cannot hold statistical `publish`. This applies both to the publisher's
  project profile and to the unit entity profile a module contributes under
  the same id. Publishing and withdrawing commit immediately and have no
  human-confirmed draft. Move `publish` to a profile a person or service uses
  directly, re-lock affected modules, and rebuild the package. Startup refuses
  an earlier package that grants a standing agent publication authority.
  Standing agents may retain `read-live` and `read-releases`.
- BREAKING: every governed action handler declares
  `abi: registry.action-handler/v1`. Replace `registry.action-handler/v2`, keep
  the action's `evidence` declaration, re-lock affected modules, and rebuild
  the package. An `evidence` declaration alone selects Rhai Evidence access,
  provider activation, evaluation outside PostgreSQL, the Evidence deadline,
  and the generated `503 action.evidence_failed` response. WASM handlers still
  cannot declare Evidence. A retained v2 declaration is refused; after changing
  it to v1, a handler without an `evidence` block is an ordinary input-only
  action. Match `breg.action.handler-abi-invalid`
  instead of the removed `breg.action.handler-wasm-abi-unsupported` code.
  Evidence consumption by an action remains a trial.

### Rust platform API removals

- BREAKING: `RuntimeConfigError` exposes diagnostics in place of
  `RuntimeConfigErrorKind`, `kind()`, `code()`, `field()`, and `message()`.
  Match a diagnostic's code and JSON Pointer path; use
  `deciding_diagnostic()` for the refusal and `diagnostics()` for the whole
  list. Unreadable input uses `UNAVAILABLE_CODE`,
  `platform.runtime-config.unavailable`.
- BREAKING: `registry-platform-dispatch` writes `dead-lettered`,
  `retry-pending`, `replay-pending`, and `lease-lapsed`. Update direct consumers
  and create tables using the current `JobTable::create_statements`; earlier
  underscore words have no reader or conversion.
- BREAKING: `registry-platform-hooks` writes kebab-case delivery states,
  dispositions, and reasons, with `hmac-sha256-v1` and `after-commit`.
  Update `DeliveryCapture` values and use current table creation. Existing
  rows are not respelled.
- BREAKING: audit query redaction reports `invalid-query-encoding`; update
  direct crate consumers of the old `invalid_query_encoding` value.
- BREAKING: CLI reference constraints use `required-exactly-one`,
  `required-one-or-more`, `requires-all`, and `mutually-exclusive`. Update
  consumers of the committed command catalog. The maintained docs renderer
  already reads these words.
- BREAKING: Registry Manifest removes `render_entity_shacl`. Render the whole
  manifest through `render_shacl` instead.
- BREAKING: unused public helpers and shared APIs that only retired Registry
  Relay consumed are removed. Direct Rust consumers must remove those calls or
  supply their own behavior. The
  [Platform changelog](https://github.com/registrystack/registry-stack/blob/v0.40.0/products/platform/CHANGELOG.md)
  retains the complete removed-item inventory without abbreviating it.

## Casework reviewer discovery and retained decisions

- Active review-task lists accept `ownership=assigned-to-me` and
  `ownership=unclaimed`, applied before pagination. The caller's current
  membership, queue service, pinned deciding profile, and source visibility
  remain required.
- A decided single-task read includes `decidedByCaller`. The exact
  issuer-qualified decision author can recover a minimal `decisionReceipt`
  containing the pinned policy, decision type, selected outcome and its
  decision-time label where required, and decision time. It excludes the
  private reason and structured producer result.
- `GET /v1/review-tasks/own-decisions` discovers the caller's retained decisions
  after sign-in, optionally by queue. Own receipts and discovery end at
  terminal result expiry or erasure. Prior holding or assignment alone does
  not make a caller the decision author.
- `GET /v1/review-tasks/supervision` discovers active and retained terminal tasks
  in the Supervisor's current queues. Exact `requestId` lookup is available.
  Rows reveal no holder, deciding eligibility, submitted context, private
  reason, or producer result. Reading an accountability event still requires
  that endpoint's independent audited Supervisor authority.
- Accountability retains the exact selected outcome and pinned decision-time
  label through its own retention window, independently of terminal result
  erasure.
- Continuations bind the caller, selected profiles, exact view, and filters.
  Opaque checkpoints preserve scan progress for at most 15 minutes past a
  candidate the caller cannot see, without granting visibility. Current
  authority is rechecked. An expired, erased, mismatched, or unauthorized
  anchor answers `410 review.result-expired`; restart without a cursor.
- Execution leases use PostgreSQL time, avoiding a lease decision based on
  a worker's local clock.

## Clients and recovery

- BReg, Casework, Scheduling, and Messaging clients classify an uncertain
  mutation outcome explicitly and resend keyed mutations under the same key,
  with the same request, at most twice. Configure the shared retry ceiling
  through the product's documented client settings. A connect timeout before
  a request is sent is a connection failure. A 4xx response or unusable
  `Retry-After` stops automatic resending.
- BReg immediate-action preparation and recovery are available in Node.js and
  Python, and the Rust facade re-exports the action types. Scheduling joins
  the unified Node.js and Python package namespaces. Messaging's native
  binding remains included in the unified Python package.
- BReg's Rust, Node.js, and Python clients accept the caller-filtered
  `statisticalDatasets` descriptors the runtime already publishes. Rust
  exposes `BRegMetadata::statistical_datasets()`, Node.js exposes
  `BRegMetadata.statisticalDatasets`, and Python exposes
  `BRegMetadata.statistical_datasets`. The clients validate the closed
  dataset, dimension, period, digest, and operation vocabulary while
  retaining the descriptions as inert metadata. A release-only reader may
  receive them without entity or entity-operation authority. The accepted
  operations are `read-live`, `list-releases`, `read-released-series`,
  `read-latest-release`, `read-release-version`, `publish-release`, and
  `withdraw-release`.
- BReg runtime and clients accept the complete authenticated continuation
  envelope, up to 10,978 bytes, for record and GeoJSON continuations. The
  generated OpenAPI request and response bounds use the same ceiling.
  Snapshot tokens keep their separate 4,096-byte limit; authenticated
  encryption, expiry, query binding, caller binding, and the 10,979-byte
  refusal remain. Because the OpenAPI bound contributes to compiled package
  revisions, rebuild v0.40.0 packages and repin their final revisions and
  digests. DDL hashes and action and change-request fingerprints are unchanged.
- Node.js and Python settings reject unknown fields, booleans or out-of-range
  numeric limits, and wrapped 32-bit conversions as documented by each
  binding. Unconvertible mutation responses and protocol failures preserve
  unknown-outcome information. Node argument errors again retain their useful
  messages; rejected client settings are configuration errors.
- Evidence clients accept complete enveloped verification policies through
  the portable verifier. Offline `check-policy` and single-file authoring
  checks do not require contacting a source or resolving deployment secrets.
- Use the complete per-product error-word tables above when updating callers.
  A client classification changing to kebab-case does not rename a standard
  OAuth error or a runtime HTTP Problem code that the notes leave unchanged.

## Authoring, documentation, and release process

- Generated schemas, editor mappings, and shared diagnostics cover authored
  and operator formats. Offline checks report all findings at their source
  positions. `init` output includes schema mappings where documented.
- `evidencectl dev start PROJECT --target TARGET --issuer-project OWNER
  --preserve-target-authenticated-context` explicitly preserves a selected
  local target's reviewed human `authenticated-context` bindings for a
  borrowed BReg issuer. It accepts only a compiled local target whose
  authority otherwise matches the generated local access policies, whose
  selector claims exactly cover the selector fields, and whose admitted
  clients have exact active first-party owner pairings. Human selectors use
  request-origin by default. Institutional-grant exchange is not accepted as
  a human substitute, and a retained session must use the same mode. Stop and
  clean a retained local session before starting it in the other mode.
- The
  [API stability and versioning promise](https://docs.registrystack.org/reference/api-stability/)
  states the covered behavior, trial surfaces, security exceptions, and
  deprecation process that take effect at 1.0. v0.40.0 remains pre-1.0, and
  this release does not activate the 1.0 promise or change its approved terms.
- CLI reference review uses the committed command catalog. Documentation
  preparation renders that catalog without installing Rust. The candidate
  still reproduces the canonical documentation archive from its exact source.
- Nightly builds can reuse reviewed release advisory exceptions under their
  separate evaluation policy. They remain evaluation artifacts: a changed
  nightly can reach code an exception judged unreachable in its reviewed
  reference image. Numbered-release candidates retain the strict exact-image
  fingerprint checks.
- The upgrade rehearsal starts at v0.40.0. Until a release at that floor is
  public, it exercises its BReg, Casework, Evidence, and Messaging legs with
  current binaries on both sides. This does not prove an in-place v0.39.0
  upgrade. Scheduling state is not part of that rehearsal.
- The adopter demo in `registrystack/solmara-lab` needs adaptation to these
  breaking configuration changes. That work is deferred from this release.

## Support

Security fixes are shipped in the latest v0.x release. Earlier minor releases
do not receive backports, and v0.40.0 has no fixed-duration support window.
Operators should move to the latest v0.x release to receive fixes.

Release preparation requires more than six months of upstream support
remaining for each pinned LTS dependency, including compatibility-only smoke
platforms. A next-LTS migration blocks the cut when a pin fails that rule.

## Security review notes

The release changes configuration admission, authorization, replay ownership,
receipt retention, and caller-data minimization. Product-owned review notes
and the Evidence adopter-tooling review below record the enforcement points,
negative tests, and accepted limits:

- [BReg review notes](https://github.com/registrystack/registry-stack/blob/v0.40.0/products/breg/SECURITY-REVIEW-NOTES.md)
  cover caller-scoped idempotency, verified ingestion ownership, runtime and
  URL decoding, OIDC admission, database TLS refusal, standing-agent statistical
  publication, and Evidence access selected by the action declaration.
- Evidence adopter-tooling review covers the optional preservation of a
  local target's reviewed human `authenticated-context` bindings. The
  option requires a compiled local-assurance target, exact generated local
  access-policy equivalence apart from the reviewed profile name and
  authenticated-context claims, exact selector-field claim coverage, and
  exact active first-party client-to-owner-issuer pairings. A changed
  retained mode, an extra or different issuer, institutional-grant
  substitution, a task-grant profile, or other authority drift is refused.
  The sealed authority determines the retained mode, and production runtime
  configuration is unchanged.
- [Casework review notes](https://github.com/registrystack/registry-stack/blob/v0.40.0/products/casework/SECURITY-REVIEW-NOTES.md)
  cover source-bound discovery, retained decision disclosure, authority-bound
  continuations, fresh storage, and database-clock leases.
- [Messaging review notes](https://github.com/registrystack/registry-stack/blob/v0.40.0/products/messaging/SECURITY-REVIEW-NOTES.md)
  cover caller-scoped replay storage, client error vocabulary, and shipped
  database TLS refusal.
- [Scheduling review notes](https://github.com/registrystack/registry-stack/blob/v0.40.0/products/scheduling/SECURITY-REVIEW-NOTES.md)
  cover verified claim ownership, spent-key minimization, fresh storage, and
  the accepted grant-status deferral. Scheduling does not query grant status:
  revocation is bounded by the grant deadline, normally Casework's 900-second
  ceiling. Scheduling does not independently cap grants from another authority.

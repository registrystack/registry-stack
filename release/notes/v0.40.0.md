# Registry Stack v0.40.0

Registry Stack v0.40.0 is the beta-52 release. Base Registry Engine,
Registry Messaging, and Registry Scheduling bind retained idempotency state or
owned work to the verified caller, so an audit-key rotation does not change
the caller's identity. Their unified clients retry a bounded set of keyed
mutations when the outcome is unknown. Registry Casework adds reviewer
ownership filters, a supervisory review-task view, request-scoped supervisory
lookup, discovery of a caller's own retained decisions, and pinned outcome
labels on decision receipts. Scheduling joins the unified Node.js and Python
clients in this release.

Upgrade to v0.40.0 from v0.39.0, and from no earlier release: finish the
v0.39.0 upgrade first. This upgrade replaces BReg's idempotency storage and
stored ingestion runs, Messaging's idempotency records, and Scheduling's
stored claim ownership. Follow the product-specific preparation below before
starting an upgraded runtime.

## Compatibility and migration

Run the same release on every runtime, tool, and client, and upgrade in the
order [upgrade and retire](https://docs.registrystack.org/operate/advanced/upgrade-and-retire/#upgrade-in-this-order)
describes. Take the backups it names first; no product migrates backwards.

BREAKING: before 1.0, a release reads only the state its immediate predecessor
wrote. v0.40.0 reads state written by v0.39.0 and nothing older. If you run an
older release, upgrade one release at a time and finish each release's upgrade
steps before starting the next.

### Upgrade Base Registry Engine from v0.39.0

- Finish or cancel every ingestion run before upgrading. The upgrade discards
  all stored ingestion runs, chunks, and receipts. A run cannot resume after
  the upgrade.
- BREAKING: caller-keyed idempotency storage is a new engine capability.
  Rebuild every deployed project with the v0.40.0 `bregctl test` and
  `bregctl package`, naming its deployed package with `--baseline-package`,
  then use `bregctl plan` and `bregctl apply` before starting the upgraded
  `breg`. A v0.39.0 package no longer loads in the v0.40.0 runtime.
- Existing idempotency records become unreachable tombstones and lose their
  receipts during the upgrade. Retrying a v0.39.0 request after the upgrade
  can execute it again. Keep clients stopped across the apply and reconcile
  any request whose outcome was not known before the upgrade.
- A spent key is now scoped to the verified issuer and principal in one shared
  write scope. The receipt-retention default is seven days and accepts at most
  365 days. After receipt expiry an exact retry answers
  `410 idempotency.expired`; `bregctl idempotency-retention erase-expired`
  removes expired records while keeping the key digest spent.
- BREAKING: governed BReg read routes refuse `HEAD`. Health and readiness
  routes continue to answer it. Replace a governed `HEAD` probe with the
  corresponding authorized `GET`, or move the probe to a health route.

### Upgrade Registry Casework from v0.39.0

- Apply Casework schema migrations 20 and 21 with the v0.40.0
  `caseworkctl plan` and `caseworkctl apply` before starting the upgraded
  runtime. Migration 20 adds the reviewer and supervisor discovery indexes.
  Migration 21 adds retained accountability outcomes and the author-position
  index used by own-decision discovery.
- Migration 21 backfills an accountability outcome only while the original
  result remains available. A legacy non-approval selection erased or expired
  before the upgrade has no decision receipt after migration. Treat absence as
  unavailable evidence, never as approval.
- Reviewer task lists accept `ownership=assigned_to_me` and
  `ownership=unclaimed`. A decided task read carries `decisionReceipt` only
  when its retained decision was recorded by the current caller; it does not
  disclose the decision reason or result.
- Supervisors can read `GET /v1/review-tasks/supervision` across queues they
  currently supervise and can select an exact `requestId` before pagination.
  The route preserves source visibility and current Casework authority. A
  request that is absent or inaccessible produces the same empty result.
- Review-task cursors bind the caller, profiles, view, and filters. Opaque
  checkpoints that represent hidden scan positions expire after 15 minutes;
  invalid, expired, or mismatched checkpoints answer `410`.

### Upgrade Registry Scheduling from v0.39.0

- Apply Scheduling migrations 11 and 12 with the v0.40.0
  `schedulingctl plan` and `schedulingctl apply` before starting the upgraded
  runtime. Migration 11 moves idempotency attempts to retained caller and key
  references. Migration 12 records claim ownership by verified issuer and
  subject.
- Existing holds and appointments keep their capacity and history but have no
  caller owner after migration. Their earlier booker can no longer list, read,
  confirm, reschedule, cancel, release, or count them toward its hold ceiling.
  Reconcile any active v0.39.0 claims before the upgrade.
- Scheduling is available in the unified Node.js and Python clients beginning
  with v0.40.0. Keep runtime, tools, and clients on the same release.

### Upgrade Registry Messaging from v0.39.0

- Stop new submissions, let senders finish in-flight retries, and stop every
  v0.39.0 Messaging runtime before applying migration 3 with the v0.40.0
  `messagingctl plan` and `messagingctl apply`. Start only v0.40.0 runtimes
  after the apply.
- BREAKING: migration 3 replaces the idempotency table. Every key spent before
  the upgrade becomes reusable, so retrying a v0.39.0 submission afterward can
  send it twice. Reconcile any submission whose outcome was not known before
  the upgrade.
- A Messaging idempotency key is now scoped to the verified issuer and
  subject. Receipt erasure clears the retained issuer, subject, and key while
  its digest keeps the key spent for that caller.

### Upgrade Evidence, Discovery, Render, and Registry Manifest from v0.39.0

- Replace the binaries or images and restart them with the rest of this
  release. Their runtime state, packages, and configuration need no migration
  for the v0.40.0 changes.

### Upgrade unified clients from v0.39.0

- The BReg, Casework, Messaging, and Scheduling clients retry eligible keyed
  mutations up to two times by default, reusing the same key, headers, and
  body. Set the retry limit to zero to disable resends.
- Retries are limited to failures whose outcome can be unknown. Reads,
  unkeyed mutations, ordinary 4xx refusals, and connect failures are not
  resent. Messaging also does not retry `429`. Casework review-request create
  and cancel remain single-attempt operations.
- Node.js constructor and runtime configuration failures use their specific
  configuration error kind. Code that matched the earlier generic kind must
  match the new one.
- A connect timeout is reported as a connection failure because no request was
  sent. The BReg, Casework, Messaging, and Scheduling clients therefore treat
  it as a known outcome and do not resend it. Review, Discovery, Evidence, and
  token-exchange callers that matched the earlier `timeout` transport kind
  must match `connect` instead.

## Base Registry Engine

- Idempotency keys and ingestion runs use verified caller identity rather than
  audit pseudonyms, so rotating the audit hash key does not change ownership or
  exact-retry lookup.
- The client reports whether a returned failure may still have taken effect
  and applies the bounded retry policy described above.
- Node.js and Python callers can persist a prepared immediate action before
  sending it, then restore and revalidate it against fresh metadata with the
  original inputs, target conditions, and idempotency key after a lost
  response. The unified Rust facade exports the types needed to name the same
  action and recovery flow.

## Registry Casework

- Reviewer and supervisor applications can discover the tasks they own or
  oversee without reconstructing those views from the request history.
- The Rust, Node.js, and Python clients expose ownership filters,
  `supervisoryReviewTasks`, `SupervisoryReviewTaskQuery`, and the current
  caller's `decisionReceipt` on a decided reviewer task.
- The Node.js facade exposes `ownReviewDecisions` with
  `OwnReviewDecisionQuery`; the Rust and Python clients expose the same
  bounded operation in their native naming conventions.
- Supervisory task lookup accepts an exact request reference and preserves the
  same neutral response for missing and inaccessible work.
- Human Staff and Supervisor reviewers can list only their own retained
  decisions after a fresh sign-in. The bounded page is ordered newest first
  and contains the task and request identifiers, current queue, retained
  producer reference, and the caller's decision receipt. Current deciding
  profile, membership, queue service, source visibility, and result retention
  still apply; prior holding or assignment is not authorship.
- Decision receipts carry the decision-time outcome label from the request's
  pinned policy snapshot. Approval has no outcome or label. The separately
  authorized Supervisor accountability record retains the same receipt through
  the accountability window, including after result erasure, without exposing
  submitted context or the structured producer result.

## Registry Scheduling

- Holds and appointments use stable verified caller ownership. Retention
  removes raw attempt identifiers while preserving a digest that prevents
  reuse by the same caller.
- Scheduling operations are exported by the unified Rust, Node.js, and Python
  clients.
- An expired appointment command directs the caller to read by external
  reference or identifier before choosing a new key. An expired hold directs
  the caller to start a new request because holds cannot be read and expire on
  their own.
- The runtime configuration schema now publishes the existing startup bounds
  for hook destinations, hook attempts, attempt-receipt retention, and hook
  payload retention. Configuration accepted by v0.39.0 remains accepted.

## Registry Messaging

- Idempotency survives audit-key rotation because retained submissions use
  verified caller identity. Receipt expiry preserves a digest that keeps a key
  spent for its caller.
- The unified clients expose bounded unknown-outcome retries for message
  submission.

## Registry Manifest

- Registry Manifest has no user-visible format or rendering changes in this
  release.

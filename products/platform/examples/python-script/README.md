# Python script with generated workload credentials

This prepared script reads the synthetic licensing application from BReg and
submits one Registry Messaging request under a stable caller-owned key. It then
reads the original Messaging receipt with the same key and request. The script
uses `registry_client.connect()` and the private connection generated by
`rstack dev`; it never reads or passes a bearer token.

The example targets the candidate Python APIs in this checkout. Treat it as a
released workflow only after the assembled `registry-stack-client` wheel and
matching Registry Stack release have passed their distribution and live
acceptance checks.

## Start the prepared project

Use Python 3.11 or later, `uv`, matching BReg, Casework, and Messaging
components, and the dedicated PostgreSQL server described in
[PROJECT-DEV](../../PROJECT-DEV.md). The licensing project's Messaging provider
is deliberately unconfigured. Its receipt proves authenticated local
acceptance and retained command identity, not external email delivery.

Run these commands from this directory. Supply the database URL and CA through
your normal secret provider before starting the run.

```sh
uv sync --locked
sdk='registry-stack-client==<matching-release-version>'
# For prepared source, sdk may instead name the absolute assembled wheel.
RUN_REPORT="$(mktemp "${TMPDIR:-/tmp}/rstack-python-script.XXXXXX")"
rstack dev check ../licensing --json
rstack dev start ../licensing --ttl 10m --json > "$RUN_REPORT"
RUN_ID="$(jq -er .run_id "$RUN_REPORT")"
export REGISTRY_STACK_CONNECTION="$(jq -er .connection_file "$RUN_REPORT")"
uv run --locked --with "$sdk" python script.py
rstack dev stop "$RUN_ID"
```

The command prints a small JSON summary containing the visible application
count and the message receipt's identifier and status. It does not print the
connection document, token state, bearer, or trace identifiers. The fixed
synthetic request and `python-script-application-received` key make a rerun ask
Messaging for the same command rather than choose a new key.

If a native submission error says its outcome is unknown, the script reads the
original receipt once. It does not resubmit automatically. A known refusal, an
unresolved receipt, or a stopped or expired development run fails visibly.
Always stop the run by its reported ID after a script failure as well.

## Exercise one live rotation

Use the optional mode to retain one `Connection` and Python process across the
runner's one-minute credential rotation. It repeats the BReg read after 65
seconds before making the Messaging calls:

```sh
uv run --locked --with "$sdk" python script.py --wait-for-rotation
```

Passing this command against a live runner demonstrates the runtime behavior.
The source test below proves only that the same connection is retained and the
second protected call is made; it cannot prove that a token file rotated.

## Recover after local expiry

Runner rotation keeps a live run usable, but it never extends the run's TTL.
When the run expires or is stopped, its connection and token-state files are
removed.
Do not retry with the old `Connection`, copy its generated files, or lengthen a
token lifetime.
Start a new run with the commands in
[Start the prepared project](#start-the-prepared-project), export the new
`connection_file`, and rerun the script.

If the supervisor was lost before cleanup completed, inspect the recorded run
and recover only that run against the PostgreSQL cluster used to start it:

```sh
rstack dev status "$RUN_ID" --json
rstack dev stop "$RUN_ID" --recover
```

Use plain `rstack dev stop "$RUN_ID"` while the supervisor is still running.
Recovery refuses a different PostgreSQL cluster or maintenance database and
reports any resources that still need attention.
After recovery reports the run stopped, start a new run rather than reusing the
expired connection.

## Verify the source example

```sh
uv run --locked python -m unittest discover -s tests -v
uv run --with 'ruff==0.14.3' ruff format --check .
uv run --with 'ruff==0.14.3' ruff check .
```

These tests use protocol doubles. They cover exact BReg options, identical
Messaging key/body reuse, unknown-outcome receipt recovery, known-refusal
propagation, one-process rotation control flow, and bounded secret-free output.
They do not establish a built-wheel import, a live runner, PostgreSQL, product
authorization, token rotation, stop/expiry behavior, or external delivery.

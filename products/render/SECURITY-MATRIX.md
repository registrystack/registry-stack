# Security-invariant matrix

Each security requirement of Registry Render, named as a threat, with its
enforcement point and the executable negative test that proves it. Rows 24-30
cover optional document sealing. Residuals that are accepted, with their
conditions, follow the table.

| # | Threat | Enforcement point | Negative test |
|---|---|---|---|
| 1 | Untrusted data reaches a path-taking template function and reads files outside the bundle | `RenderWorld::snapshot_path` (world.rs): lexical rejection of `..`/absolute components followed by exact lookup in the immutable bundle snapshot; Typst additionally virtualizes absolute paths as root-relative before the world sees them | `golden::data_paths_cannot_escape_the_bundle`; `world::tests::virtual_paths_reject_escape_attempts` |

## Documented residuals (accepted, with conditions)

- **A render worker is not a sandbox.** It runs as the serving process's
  user, with the same filesystem and network. A worker that gained code
  execution through a Typst or decoder defect could read files that user can
  read, including key files under `secretProviders.file.root`, and connect to
  any socket that user can reach. On Linux, row 23 keeps the parent's
  environment and memory out of its reach. On macOS it does not: a same-user
  process reads another's arguments and environment through
  `KERN_PROCARGS2`, so such a worker can read every `${VAR}` and
  `secret:env` value the serving process holds; seal on Linux. The rest is
  not enforced. The worker needs only its
  pipes, so refusing socket creation and restricting its filesystem view
  (seccomp, Landlock) are the next steps, not yet taken because they need
  per-architecture filters proven on the release image.
- **The audit log is not tamper-evident on the host.** It carries no hash
  chain or signature, so a host user able to write the audit file can
  remove, rewrite, or reorder lines undetected. A render worker that gained
  code execution is such a user: it runs as the serving user, who owns the
  `file` destination. Deployments that need tamper evidence ship the `file`
  or `stdout` stream to append-only storage they control; deployments that
  seal use `audit.destination: stdout`, shipped to storage the serving user
  cannot write.
- **macOS workers have no address-space cap** (`RLIMIT_AS` is not exposed
  by rustix there): the timeout kill is the sole wall. Serve deployments
  for pilots should run on Linux, where the rlimit applies.
- **The output-size check runs after PDF export** in memory; Linux workers
  bound the spike by `RLIMIT_AS`, macOS only by the kill.
- **A chunked body that trips the tower stream limit mid-body** breaks the
  request stream, so the connection closes with no response and no audit
  event. Refusing chunked transfer before the first body byte is what keeps
  that path unreachable for ordinary callers; the backstop remains for a
  client that frames a Content-Length and then sends more.
- **Asset caps are code-level constants** (per-asset 2 MiB, request total
  8 MiB, JPEG/PNG only), not per-document manifest declarations.
  Per-document asset policy is a v2 option if a journey needs it.
- **A compromised worker can still get arbitrary content sealed.** The worker
  renders the content, so one that gained code execution can return any
  single-revision document, and the parent signs it. That content sits in
  the first revision, under `documentDigest`, because the parent writes
  every byte after it (row 27): comparing the digest with the record, or
  re-rendering from the record and comparing, exposes it. The parent bounds
  what it signs (rows 26 and 27), not what the document says. The mitigations are governed templates, which are verified at startup
  and by each worker (rows 3 and 4), the key staying outside the worker (row
  26), and the value-free audit (row 28) that lets an institution reconcile
  every sealed hash with its own records. The same worker can rewrite a
  `file` audit destination (previous residual), so that reconciliation
  holds only for an audit sent to `stdout` and on to storage the serving
  user cannot write.
- **The timestamp authority's identity is not pinned.** Render reaches the
  authority over TLS with the host's root certificates, or with only the CA
  bundle `timestampAuthority.caBundleRef` names, and accepts a token
  that matches the signature, nonce and key usage; it does not pin the
  authority's certificate or decide whether it is trusted. Validators decide
  trust in the seal certificate and the timestamp authority.
- **Local seal key files are for development and pilots.**
  `signer.privateKeyRef` resolves a JWK through the file secret provider, so the key is readable by the
  serving user and, with the worker not a sandbox (first residual), by a
  worker that gained code execution. Production custody (an HSM or a managed
  key service) is not yet supported.
- **No revocation data, no qualification.** A seal is PAdES baseline B-B or
  B-T. It embeds no revocation information (no B-LT or B-LTA) and makes no
  eIDAS qualification claim.
- **PDF/A conformance rests on the template.** veraPDF passed a fixture
  template at every accepted PDF/A level and at PDF/UA-1, rendered and
  sealed (`EVIDENCE.md`), so the seal keeps a level the rendered file meets;
  `check` refuses a reserved space the level's string limit cannot hold. A
  deployer's own template is not checked against its level, and veraPDF
  checks machine-checkable rules only.

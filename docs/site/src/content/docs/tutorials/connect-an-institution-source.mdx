OpenAPI can remove much of the mechanical work when you connect Evidence to an institution API.
It can describe operations and response shapes. It cannot decide which subjects a caller may name,
which facts a requirement needs, how zero or several matches are represented, or what the minimum
answer should be.

This page gets you to a reviewable source draft. It does not generate a complete deployment or
invent fixtures unrelated to your project.

## Before you start

You need an OpenAPI 3.0 or 3.1 document for the API Evidence will read. Use a sanitized copy during
authoring. Keep credentials, real responses, and personal data outside the project.

Choose an operation that can answer one bounded lookup:

- The request selects one subject from explicit fields.
- The response lets you distinguish no match, one match, and several matches.
- Response strings and collections have defensible bounds.
- The deployment can call it with a service credential, not an end-user session.

If an operation lists broad records and expects Evidence to filter them locally, choose a narrower
operation or improve the API first.

## Explore the document interactively

Run the source assistant without a project:

```sh
evidencectl source suggest --openapi <institution.openapi.yaml>
```

The assistant lists supported HTTP operations, then the candidate response leaves. Choose only the
fields required to resolve cardinality and derive the answer. With no `--project`, it prints a
draft and writes nothing.

`--openapi` also accepts an `https` URL. Evidencectl fetches the document, not the source endpoint
named inside it. Remote `$ref` documents are not fetched.

## Make the draft reproducible

Repeat the accepted choices as flags so another reviewer can reproduce them:

```sh
evidencectl source suggest \
  --openapi <institution.openapi.yaml> \
  --operation 'GET /people/{person_id}' \
  --source-id people \
  --select /date_of_birth
```

Use one `--select` per required JSON pointer. Array members use `*`, for example
`/results/*/status`. Add `--sample <sanitized-response.json>` only when the API document omits a
bound and you need a starting suggestion. A sample can suggest a bound but cannot prove it, so the
report marks that provenance for review.

## Write into a complete project

After reviewing the print-only draft, write its source artifacts into a complete deployment
project:

```sh
evidencectl source suggest \
  --openapi <institution.openapi.yaml> \
  --operation 'GET /people/{person_id}' \
  --source-id people \
  --project <evidence-project> \
  --select /date_of_birth
```

The command writes only new draft artifacts and refuses collisions. It does not silently edit the
governed `bundle/evidence.yaml`. Its report gives you the source block to review and place under
`sources`, followed by every unresolved `TODO(evidencectl)` decision.

The generated files are a starting point:

- The response schema closes and bounds the source shape.
- The prepare script materializes one bounded HTTP request.
- The extract script must map the source's own cardinality semantics to `match`, `no_match`, or
  `ambiguous`.
- The facts schema contains only the facts the derivation may receive.

## Review the decisions OpenAPI cannot make

Resolve every generated TODO before checking the project:

1. Confirm the exact base URL, path, method, redirect policy, timeout, response ceiling, and
   concurrency limit.
2. Bind only authorized subject selectors into the request. Do not forward arbitrary caller query
   parameters.
3. Choose the deployment credential reference. Never put credential values in the bundle, sample,
   script, command line, or fixture.
4. Confirm the projection excludes fields the derivation does not need.
5. Implement explicit zero, one, and several-match behavior from the API contract.
6. Define the requirement, purpose, allowed audience, derivation, and disclosed concept. These are
   governance decisions, not OpenAPI facts.

Run the real bundle loader when the project is complete:

```sh
evidence check --runtime <evidence-project>/runtime.yaml
```

A draft that is not yet referenced by `bundle/evidence.yaml` fails artifact closure. Treat that as
an unfinished project, not as permission to weaken closure checks.

## Local and deployable assurance differ

`assuranceProfile: local` may omit fixtures while you are learning and iterating. Production and
evidence-grade projects must carry complete, project-specific fixtures. Do not copy a fictional
fixture suite whose selectors, source shape, or answer has nothing to do with your integration.

Continue with [Prove and promote an Evidence project](../prove-an-evidence-project/) once the
source and requirement describe your actual project.

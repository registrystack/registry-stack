If you are evaluating Base Registry Engine (BReg) event delivery, add a committed
contact event to a local directory, run its create/read scenario, and inspect the
supervised receiver's value-redacted receipt.

<QuickstartMeta
  outcome="A signed contact-created delivery accepted by the local receiver."
  time="About 15 minutes, plus image downloads"
  level="Local evaluation only"
  prerequisites={['Matching breg and bregctl binaries', 'Running Docker', 'A shell and an editor']}
/>

## Create a directory with an event

```sh
mkdir -p tutorial-work
bregctl init tutorial-work/webhooks
```

Open `tutorial-work/webhooks/registry.yaml` and add this `hooks` member to the
`contact` Record type, beside `fields`:

```diff lang="yaml" title="tutorial-work/webhooks/registry.yaml" test-edit
     mutationMode: mutable
+    hooks:
+      - id: contact-created-v1
+        phase: after
+        trigger: created
+        projection: [name]
+        handler:
+          type: url
+          destinationId: contact-events
```

The projection authorizes only `name` to leave the registry. The destination is a
logical ID; development binds it to its supervised HMAC-verifying receiver.

```sh
bregctl check tutorial-work/webhooks
bregctl --format json explain events tutorial-work/webhooks
```

Inspect the event ID, projection, derived classification, and destination before
starting. Repair a named diagnostic before proceeding.

## Start and cause a delivery

:::caution[Use synthetic records]
The local receiver retains projected values in the owner-only `.breg/dev/` state.
Keep that directory out of version control and support messages.
:::

```sh
bregctl dev start tutorial-work/webhooks
bregctl examples run contact tutorial-work/webhooks
```

The scenario creates and reads its synthetic contact. Delivery happens after
commit. Give the worker time to attempt delivery before inspecting the receiver.
A repeated scenario resumes retained work; it does not create a fresh event each time.

## Inspect acceptance

```sh
bregctl --format json dev events tutorial-work/webhooks
```

The report identifies the event, destination, generation, attempt, and accepted
receipt. Projected values are omitted unless you explicitly add `--include-payload`.
An empty report can mean delivery is still pending; inspect the runtime diagnostics
and the queue with `bregctl webhook list --help` before creating another record.

Acceptance means the receiver accepted that attempt. An adopting service owns
durable inbox storage, processing, retention, and reconciliation. Its retry and
operator-replay handling must deduplicate the event before an external effect.
[Operate BReg webhooks](../../operate/breg-webhooks/) covers the separate outbox.

## Stop the session

```sh
bregctl dev stop tutorial-work/webhooks
```

This retains records and receiver receipts for inspection. To discard this
synthetic session, use `dev stop --remove`; that removes its owned database and
receipt journal. Keep any required evidence before removing it.

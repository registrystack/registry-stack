In about fifteen minutes your registry will tell another system each time a contact is created:
the event declared, the signed request it produces printed, and the receiver that accepts it explained.

## Declare the event

In the project directory, ask which events the registry sends today:

```sh test-cwd="tutorial-work/project"
rstack breg explain events .
```

```text test-excerpt
Event deliveries:
  No event deliveries declared.
```

None: a registry sends nothing until a Record type declares it. Open `registry.yaml` and add a
`hooks` list to the `contact` Record type, right after its `mutationMode` line:

```diff lang="yaml" title="registry.yaml" test-edit
     mutationMode: mutable
+    hooks:
+      - id: contact-created-v1
+        phase: after
+        trigger: created
+        projection: [name]
+        handler:
+          type: url
+          destinationId: contact-events
```

The hook fires once a new contact is committed. Its projection lets only `name` leave the
registry. `contact-events` is a destination name, not an address: an operator binds it to a URL
in the runtime file.

Check the project and ask again:

```sh
rstack breg check .
rstack breg explain events .
```

```text test-excerpt
Event deliveries:
  events.contact.contact-created-v1.webhook
    phase         after
    handler type  url
    destination   contact-events
    projected fields  name
```

## Print the signed request

A registry sends the event after the write that caused it commits. A development run started with
`rstack dev` binds no event destinations, so it refuses a project that declares one. You build the
receiver against a sample instead. This command prints the request one event produces. It needs no
running registry and no database:

```sh
rstack breg hook sample . --event contact-created-v1
```

```text test-excerpt
Built the sample delivery. The canonical request follows.
  event  contact-created-v1
```

The output is a complete `POST` request: the headers `Idempotency-Key`, `X-Registry-Signature` and
the `ce-` CloudEvents headers, then a body whose `values` hold a synthetic `name`. The signature
is a placeholder. A real delivery signs the exact bytes with a key you share with the receiver.

## Receive it

`products/breg/examples/webhook-receiver/` in the source repository holds a receiver that accepts
deliveries durably. It verifies the signature, checks that the registry, instance, Record type
and event match what you configured, and writes the event to its own SQLite inbox before it
answers `204`. It answers `503` when it cannot store the event, so the registry retries. Install
the `registry-stack-client` package, create an owner-only key file, and start it with the values
of your event:

```sh test-skip="needs the registry-stack-client package and a signing key of your own"
python3 products/breg/examples/webhook-receiver/receiver.py \
  --registry-id local-directory --instance-id local --record-type contact \
  --event-id contact-created-v1 --field name --key /path/to/key \
  --inbox /path/to/private-state/inbox.sqlite3 --port 8090
```

The receiver listens on `127.0.0.1` at `/events`. Bind the `contact-events` destination to it in
the runtime file of a registry you serve with `breg serve`, as
[Bind webhook receivers](../../operate/breg-webhooks/) describes. That page also shows how to
provision the shared key and list the deliveries still waiting or failed.

The receiver proves only that an attempt arrived. A real receiving service stores each event
before acting on it. A retry resends an event with the same `idempotencyKey`. An operator replay
resends it with the same `eventId` and a new key. Check both before acting.

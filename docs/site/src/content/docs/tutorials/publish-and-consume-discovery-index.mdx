You will package an index from one provider's public description, serve it, and then, as an
application, ask it which Registry Evidence service can answer a question.

## Install Registry Stack

Download one exact `rstack-vX.Y.Z-install.sh` and the verification material from the same Registry
Stack release. Follow the
[release verification procedure](https://github.com/registrystack/registry-stack/blob/main/release/VERIFY.md)
before running the installer. From the verified release directory, install the `discovery`
component:

```sh test-skip="uses a downloaded, independently verified release installer"
tag="vX.Y.Z"
bash "rstack-${tag}-install.sh" discovery
rstack discovery --version
```

The managed installation exposes `rstack` on your `PATH`. The `discovery` component supplies the
Discovery runtime and its command-line tools from the same release.

{/* Evidence: crates/registry-rstack/README.md; crates/registry-rstack/install.sh;
    release/VERIFY.md. */}

Clone the same release for the example project and synthetic provider description:

```sh test-skip="the runner starts in a copy of this checkout"
git clone --branch "$tag" --depth 1 --quiet https://github.com/registrystack/registry-stack.git
cd registry-stack
```

## Check the project

Copy the example project out of the checkout:

```sh
cp -R products/discovery/tutorial/project discovery-project
```

As the operator, you approve each provider by the URL of its public description, in
`discovery-project/origins.yaml`:

```yaml test-excerpt="discovery-project/origins.yaml"
apiVersion: id.registrystack.org/formats/discovery/origins/v1alpha1
kind: DiscoveryOrigins
origins:
  - originId: tutorial-evidence
    catalogUrl: http://127.0.0.1:38090/evidence.jsonld
    profile: registry-discovery-v1alpha1
    enabled: true
```

You also say which Evidence types meet a requirement an application may have.
`discovery-project/mappings/adult-status.yaml` maps the adult-status requirement to one type:

```yaml test-excerpt="discovery-project/mappings/adult-status.yaml"
apiVersion: id.registrystack.org/formats/discovery/evidence-mapping/v1alpha1
kind: DiscoveryEvidenceMapping
mappingId: urn:example:mapping:adult-status
mappingAuthorityId: urn:example:mapping-authority
requirementId: urn:example:requirement:adult-status
jurisdiction: urn:example:jurisdiction
alternatives:
  - evidenceTypeListId: urn:example:evidence-type-list:adult-status
    evidenceTypeIds:
      - urn:example:evidence-type:adult-status
```

Check the project. `--allow-loopback` accepts the local `http://127.0.0.1` URL; without it, only
HTTPS origins pass.

```sh
rstack discovery check --project discovery-project --allow-loopback
```

```text test-expect
valid origins=1 mappings=1
0 errors, 0 warnings in 3 files
```

The third file is `runtime.yaml`, which you use to serve the index. The check never contacts the
provider URL; a refused file gets one finding per problem, with its line, column, and fix.

{/* Evidence: crates/registry-discoveryctl/src/project.rs,
    check_is_offline_and_accepts_an_unreachable_https_origin. */}

## Package the index

Play the provider: open a second shell at the checkout root and serve its description at the
approved URL.

```sh test-background="http://127.0.0.1:38090/evidence.jsonld"
python3 products/discovery/tutorial/publication_server.py \
  --descriptions products/discovery/fixtures/descriptions
```

Back in the first shell, package the index:

```sh
rstack discovery package \
  --project discovery-project \
  --output discovery-project/package \
  --allow-loopback
```

```text test-expect
packaged packageDigest=sha256:<package-digest> catalogRevision=sha256:7e0799f2c5fd24957e4d1372f757c40abef694110eb70fc260a0abdc312ca963 mappingRevision=sha256:332004ca3920c498539180946e8f2637e9998ba7e49cd98f31e19d6f818857ac
```

Packaging fetched the description once. The catalog revision digests what the descriptions mean
and the mapping revision digests your mappings, so they match on any machine; the package digest
also covers when this run fetched, so yours differs.

Stop the publication server with `Ctrl+C`. Discovery never contacts a provider while it serves.

{/* Evidence: crates/registry-discoveryctl/tests/build.rs,
    package_fetches_each_origin_once_and_preserves_semantic_revisions. */}

## Serve the index

`discovery-project/runtime.yaml` names the listener, the limits, and a package root read from
`DISCOVERY_PACKAGE_ROOT`. Both paths must be absolute. In the first shell, start Discovery:

```sh test-background="http://127.0.0.1:38080/ready"
DISCOVERY_PACKAGE_ROOT="$PWD/discovery-project/package" \
  rstack discovery serve --runtime-config "$PWD/discovery-project/runtime.yaml"
```

It checks the package against its `SHA256SUMS` file before it listens. In the second shell:

```sh
curl -s http://127.0.0.1:38080/ready
```

```json test-expect
{"status":"ready"}
```

## Resolve a requirement

Now play the application. It knows it must establish that a person is an adult, but not which
provider can say so. Ask Discovery which Evidence types satisfy that requirement:

```sh
rstack discovery api /v1/evidence-types/resolve \
  --url http://127.0.0.1:38080 \
  --input - <<'JSON'
{"requirementId":"urn:example:requirement:adult-status","jurisdiction":"urn:example:jurisdiction"}
JSON
```

```json test-expect
{
  "requirementId": "urn:example:requirement:adult-status",
  "jurisdiction": "urn:example:jurisdiction",
  "mappingRevision": "sha256:332004ca3920c498539180946e8f2637e9998ba7e49cd98f31e19d6f818857ac",
  "alternatives": [
    {
      "evidenceTypeListId": "urn:example:evidence-type-list:adult-status",
      "evidenceTypeIds": ["urn:example:evidence-type:adult-status"],
      "mappingId": "urn:example:mapping:adult-status",
      "mappingAuthorityId": "urn:example:mapping-authority"
    }
  ]
}
```

Each alternative lists types that are required together; here there is one alternative with one
type.

## Find the provider

Search for Registry Evidence services that assert that type:

```sh
rstack discovery api \
  '/v1/services?serviceKind=evidence&evidenceType=urn%3Aexample%3Aevidence-type%3Aadult-status' \
  --url http://127.0.0.1:38080
```

The response carries the `catalogRevision` from the package step and one item. Its key fields:

```json test-excerpt
{
  "recordId": "urn:registrystack:discovery:record:sha256:676659c10ce5cc9d353f4fd2816673c7947e612151efbbe1cc4d42372d9be9d5",
  "bindingId": "urn:registrystack:discovery:binding:sha256:2f9ccc4629c7ea2409d986a9c0ee6e3afe6e63326ca7b1be7d9eb8c69082d96c",
  "serviceKind": "evidence",
  "endpointUrl": "https://evidence.example.org",
  "originUrl": "http://127.0.0.1:38090/evidence.jsonld",
  "originContentDigest": "sha256:fc96f3a8cb0d82239425ea5712dceca975a5899e5528616648174da661fae905"
}
```

`originContentDigest` is the SHA-256 of the exact bytes the provider published.

The application saves a selection: the `recordId` and `bindingId` it chose, and the two revisions
it chose under. A selection is public metadata, not a credential. Whether to trust
`endpointUrl` is decided by the application's own Evidence configuration, and the call to it never
passes through Discovery. The Discovery namespace of the
[Registry Stack client](../../reference/client-api/#registry-discovery) runs these searches and
saves selections from Rust, Node.js, or Python.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| A service stops at startup | Port `38090` or `38080` is in use | Stop the process using the port, then start the service again |
| `rstack discovery package` cannot fetch an origin | The publication server is not running | Start it, then package again; a failed run writes no package |
| `rstack discovery package` refuses the output directory | `discovery-project/package` exists from an earlier run | Remove it, then package again |

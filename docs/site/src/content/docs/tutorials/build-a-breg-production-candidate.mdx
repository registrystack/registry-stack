If you are preparing a Base Registry Engine (BReg) deployment, test one exact
project against an isolated schema-test database, package the successful
candidate, and verify its deployment binding before promotion.

<QuickstartMeta
  outcome="A tested package with its receipt and digest, ready for independent review and activation."
  time="About 30 minutes after database and issuer provisioning"
  level="Deployment preparation"
  prerequisites={['Matching breg and bregctl binaries', 'An isolated TLS PostgreSQL schema-test database', 'Separate migration and runtime roles', 'An operated issuer and short-lived test credentials', 'A shell and an editor']}
/>

## Prepare the project and deployment inputs

```sh
mkdir -p tutorial-work
bregctl init tutorial-work/candidate-project
bregctl check tutorial-work/candidate-project --production
```

The default project is the complete `minimal-directory`. Read its README and
replace its project identity, canonical base IRI, dataset, jurisdiction grants,
and local synthetic values with your reviewed model. Keep the project and its
journeys together. Repeat the production check after edits.

Copy its runtime example to a separate deployment directory. Follow
[Deploy a registry](../../operate/breg/#write-the-runtime-configuration) to bind
TLS PostgreSQL, migration/runtime roles, issuer, accepted clients, audit, cursor
secret, package location, and environment identity. Store secrets in owner-only
files and keep references in configuration. Local `dev` credentials and its
unsigned loopback setup are evaluation inputs.

Prepare a schema-test credentials document binding each protected journey step
to a short-lived real token. The two canonical clients have distinct jurisdiction
claims; preserve both permitted and concealed behavior in your replacement
credentials. Use `bregctl test --help` and
[Test with journeys](../../configure/breg-journeys/) for its credential contract.
Keep this document outside the authored package and version control.

## Run the exact journeys

The paths in these commands are absolute. Supply your trusted PostgreSQL CA,
runtime configuration, and credential binding:

```sh test-skip="requires operator-provisioned TLS PostgreSQL, issuer, and exact journey credentials"
SSL_CERT_FILE=/path/to/postgres-ca.pem bregctl test tutorial-work/candidate-project \
  --runtime-config /path/to/runtime-test.yaml \
  --credentials /path/to/credentials.yaml \
  --output /path/to/test-receipt.json
```

A successful result writes the canonical receipt for the exact sources, journey,
migration plan, and measured schema fingerprint. If a step fails, repair the
named input or authority and rerun into a fresh receipt path. Compilation alone
cannot substitute for this database and HTTP proof. The schema-test database is
isolated from the serving registry.

## Package the successful candidate

```sh test-skip="consumes the operator-provisioned rehearsal receipt"
bregctl package tutorial-work/candidate-project \
  --test-receipt /path/to/test-receipt.json \
  --output /path/to/build-1
```

The command reproduces the tested candidate and publishes `package/` and its
checksums in a new build directory. Record its package digest and source identity
for review. A changed source or mismatched receipt requires a new test; an existing
output directory is refused. Preserve the whole package instead of editing its
compiled contents.

## Verify the deployment binding

Set the deployment runtime file's `package.root` to that package directory and
pin the reviewed digest where your deployment uses `package.expectedDigest`.
Verify it before applying:

```sh test-skip="requires the completed deployment runtime binding"
bregctl verify --runtime-config /path/to/runtime.yaml
```

Review the package, checksums, external signing policy, runtime identity, issuer,
secrets, and separate database roles. The same tested package is promoted across
environments; environment-specific connection and identity values stay in each
runtime file. An operator with migration authority performs Plan and Apply.
Authoring and testing do not confer that credential.

For a successor, both Test and Package take `--baseline-package` naming the active
package and the same `--reviewed-migrations` when required. Resolve incompatible
open Proposals deliberately; activation cannot silently reinterpret frozen work.

## Retain evidence and clean up

Keep the exact source, receipt, package digest, and review with your private
operational evidence. Expire test tokens and remove only the disposable
schema-test resources you provisioned. This procedure starts no serving process.
Do not delete a serving registry to repeat a failed test.

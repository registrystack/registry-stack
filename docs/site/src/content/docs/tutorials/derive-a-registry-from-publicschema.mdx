If you are a data publisher who finished [Create and query your first registry](../first-breg/), you
already have `bregctl` installed. This tutorial derives a registry project from PublicSchema, an
external reference model embedded in the tooling, instead of writing the domain-neutral example
project. You pick a starter selection of concepts and properties, read what `init` wrote, check and
start the project, then edit the selection and derive it again. A closing section describes the
interactive wizard that asks the same questions at a terminal.

## Before you start

Open a terminal where you want to create the project, and confirm the binaries are on your `PATH`:

```sh
bregctl --version
```

The version printed is the one [Create and query your first registry](../first-breg/#install-base-registry-engine)
installed. Nothing here needs the `tutorial-work` directory from that tutorial; this tutorial derives
a project of its own. Docker is needed only later, to start the registry.

## Derive a project from PublicSchema

`bregctl init` writes the domain-neutral example project by default. With `--from publicschema`, it
derives a project from the PublicSchema 0.3.0 snapshot embedded in the binary instead, guided by a
selection of concepts and properties. `--starter household` supplies a selection shipped with the
model: the concepts `Person`, `Household`, and `GroupMembership`, with a subset of their properties.

Derive a project from the household starter:

```sh
bregctl init household-registry --from publicschema --starter household
```

```text
init succeeded
revision: sha256:<digest>
finding access.profile.higher_classification at entities[id=group-membership].accessProfiles[id=operator].readableFields[field=person]: this field is more sensitive than its entity's classification; verify the profile's scope and purpose before disclosing it
finding access.profile.higher_classification at entities[id=person].accessProfiles[id=operator].readableFields[field=marital-status]: this field is more sensitive than its entity's classification; verify the profile's scope and purpose before disclosing it
finding access.profile.unrestricted_collection at entities[id=group-membership].accessProfiles[id=operator].rowBoundaries: this profile can list all rows, subject only to query bounds; caller filters are not authorization. Add a claim-bound row restriction or review this registry-wide access
finding access.profile.unrestricted_collection at entities[id=group-membership].accessProfiles[id=reader].rowBoundaries: this profile can list all rows, subject only to query bounds; caller filters are not authorization. Add a claim-bound row restriction or review this registry-wide access
finding access.profile.unrestricted_collection at entities[id=household].accessProfiles[id=operator].rowBoundaries: this profile can list all rows, subject only to query bounds; caller filters are not authorization. Add a claim-bound row restriction or review this registry-wide access
finding access.profile.unrestricted_collection at entities[id=household].accessProfiles[id=reader].rowBoundaries: this profile can list all rows, subject only to query bounds; caller filters are not authorization. Add a claim-bound row restriction or review this registry-wide access
finding access.profile.unrestricted_collection at entities[id=person].accessProfiles[id=operator].rowBoundaries: this profile can list all rows, subject only to query bounds; caller filters are not authorization. Add a claim-bound row restriction or review this registry-wide access
finding access.profile.unrestricted_collection at entities[id=person].accessProfiles[id=reader].rowBoundaries: this profile can list all rows, subject only to query bounds; caller filters are not authorization. Add a claim-bound row restriction or review this registry-wide access
artifacts: 6
next: read household-registry/README.md, then run 'bregctl check household-registry'
next: leave the findings above as they are; the `operator` and `reader` profiles list whole collections on purpose, and the `operator` profile reads 2 fields the model marks sensitive, and household-registry/README.md says where to narrow them
next: run 'bregctl dev household-registry' to start the registry locally and replay household-registry/tests/journeys.yaml
next: replace canonicalBaseIri in household-registry/registry.yaml before you build a production package; the derived value is a reserved .invalid name that never resolves
next: keep household-registry/model/selection.yaml beside the project: edit it and pass it back with --selection to derive a fresh project
```

`init` compiled the project before printing its `revision`, the digest of the compiled model; `check`
and `dev` repeat this revision and every finding until you change something. The six artifacts are
`registry.yaml`, `README.md`, `dev-clients.yaml`, `runtime.example.yaml`, `tests/journeys.yaml`, and
`model/selection.yaml`. Unlike the domain-neutral example, a derived project has no `modules/`
directory: every entity lives in `registry.yaml`.

Both finding codes are expected, and the `next:` lines above say so. The rest of this tutorial
follows those lines in order.

## Read what init wrote

Open `household-registry/README.md`. It carries the attribution PublicSchema's license requires:

:::note[Keep the attribution notice]
"The concepts, properties, and code lists in this project are derived from PublicSchema 0.3.0
([https://github.com/PublicSchema/publicschema.org](https://github.com/PublicSchema/publicschema.org)),
licensed under CC-BY-4.0 ([https://creativecommons.org/licenses/by/4.0/](https://creativecommons.org/licenses/by/4.0/)).
The derivation selects, renames, and retypes definitions, so this project is a modified form of
the model. Keep this notice with the project and with any package built from it."

Carry the same notice into any package you build from this project; CC-BY-4.0 requires it.
:::

The README lists one section per entity, each naming the PublicSchema concept it came from and a
field table. The `person` entity, from PublicSchema's `Person`:

| Field | Property | Type | Classification |
|---|---|---|---|
| `person-code` | `identifier` | string, 1 to 64 characters | `internal` |
| `given-name` | `given_name` | string, up to 255 characters | `internal` |
| `family-name` | `family_name` | string, up to 255 characters | `internal` |
| `date-of-birth` | `date_of_birth` | date | `internal` |
| `sex` | `sex` | vocabulary-code from `sex` | `internal` |
| `preferred-language` | `preferred_language` | string, up to 64 characters | `internal` |
| `phone-number` | `phone_number` | string, up to 255 characters | `internal` |
| `marital-status` | `marital_status` | vocabulary-code from `marital-status` | `restricted` |

`household` and `group-membership` get the same shape lower in the file. The README also explains the
derivation rules that produced these fields: each selected concept becomes an entity, named in kebab
case from the concept and routed under its plural, with an identifier field the derivation adds; each
selected property becomes a field of the same name; an enumeration of at most 300 values becomes a
closed vocabulary-code field, a larger one a bounded string; a property whose value is another
selected concept becomes a `reference` to that entity, the way `group-membership.person` and
`group-membership.group` do here; a property whose value is a concept the model treats as a value,
such as `household.address`, becomes a `structured` field carrying it inline; and a property
PublicSchema marks sensitive or restricted becomes a `restricted` field, as does a `structured`
field whose inline value carries such a property, with everything else `internal`.

One rule never shows in a README, because it refuses a property before anything is written: a
property that could hold several records of another concept at once is not derived, and the
refusal says to model the relationship as its own entity, the way `group-membership` models the link
between a person and a household here.

Open `household-registry/model/selection.yaml`. It is the input `init` derived the project from, and
`init` also wrote a copy of it back into the project:

```yaml
apiVersion: registry.registrystack.org/breg-model-selection/v1alpha1
kind: ModelSelection
model: publicschema
modelVersion: 0.3.0
registry:
  id: household-registry
  title: Household Registry
entities:
- concept: Person
  properties:
  - name: given_name
  - name: family_name
  - name: date_of_birth
  - name: sex
  - name: preferred_language
  - name: phone_number
  - name: marital_status
- concept: Household
  properties:
  - name: name
  - name: group_type
  - name: member_count
  - name: address
  - name: food_security_level
- concept: GroupMembership
  properties:
  - name: person
  - name: group
  - name: role
  - name: start_date
  - name: end_date
```

Keep this file beside the project. Edit it and pass it back with `--selection` to derive a fresh
project, the way [Edit the selection and derive again](#edit-the-selection-and-derive-again) does
below.

## Check the project

Run `bregctl check` the way the first `next:` line says:

```sh
bregctl check household-registry
```

The report repeats the same revision and the same eight findings shown above, without the
`artifacts` count or the `next:` lines that only `init` writes.

Two finding codes appear, one per entity-and-profile pair they apply to:

`access.profile.unrestricted_collection` fires for every entity's `operator` and `reader` profile: a
profile that may list a whole collection, and a caller-supplied filter is not by itself
authorization. It is expected here: the household starter has no tenancy field to bind a row
restriction to. Add a claim-bound row restriction, or accept the registry-wide access, before a
production package.

`access.profile.higher_classification` fires twice, for `person.marital-status` and for
`group-membership.person`. PublicSchema marks both properties sensitive, so the derivation classified
the fields `restricted` inside entities that are themselves only `internal`, and the `operator`
profile reads them anyway. The finding asks you to confirm that profile's scope and purpose before
you rely on it; the `reader` profile does not see either field, since `reader` excludes everything
classified `restricted`.

Leave both findings while you explore the project. The README's own "Access profiles" section
explains them the same way, and names the exact fields.

## Start the registry

Start the project as a registry the same way as
[Create and query your first registry](../first-breg/#start-the-registry):

```sh
bregctl dev household-registry
```

The first start downloads the pinned PostgreSQL image. Once the registry answers, the report shows
its address, a token endpoint, and one credential per client in `dev-clients.yaml`: an `operator` and
a `reader`, matching this project's two access profiles.

Before the report printed, `dev` replayed `household-registry/tests/journeys.yaml` against a
throwaway database, the way [Create and query your first registry](../first-breg/#start-the-registry)
describes, then activated the package on an empty one. The registry starts with no records; the
journey file shows what a valid request looks like. Its first step is `create-person`:

```yaml
      - id: create-person
        entity: person
        accessProfile: operator
        claims: &operator_claims
          principal: household-registry-operator
          scopes: [registry:household-registry:operate]
          purpose: registry-operations
        request:
          operation: create
          data:
            person-code: person-1
            given-name: example
            family-name: example
            date-of-birth: "2024-01-01"
            sex: not_known
            preferred-language: example
            phone-number: example
            marital-status: never_married
        expect:
          outcome: success
          status: 201
          fields: {person-code: person-1}
        capture: example-person
```

The rest of the file creates a household and the group membership that links them, then reads each
one back as both profiles. To make the same create by hand, get a token the way
[Create and query your first registry](../first-breg/#get-a-token) does, then send the step's `data`
object as the body of the [create request](../first-breg/#create-a-record) shown there, against
this project's `persons` route instead of `records`:

```text
$registry_url/v1/records/persons?accessProfile=operator
```

The other routes are `households` and `group-memberships`.

Stop the registry the same way, with `bregctl dev stop household-registry`, or add `--remove` to
discard the session and any records you created.

## Edit the selection and derive again

`model/selection.yaml` is ordinary input, not a generated file: edit it and derive again to get a
fresh project from the change. Open `household-registry/model/selection.yaml` and remove
`marital_status` from `Person`'s properties:

```yaml
- concept: Person
  properties:
  - name: given_name
  - name: family_name
  - name: date_of_birth
  - name: sex
  - name: preferred_language
  - name: phone_number
```

Derive a second project from the edited file, into a new directory:

```sh
bregctl init household-registry-2 --from publicschema --selection household-registry/model/selection.yaml
```

The report has a new revision, the same six `access.profile.unrestricted_collection` findings, and
only one `access.profile.higher_classification` finding left, for `group-membership.person`; removing
`marital_status` removed the other one. The `next:` line about sensitive fields now reads in the
singular: the `operator` profile reads a field the model marks sensitive, not two.

`household-registry-2/README.md` explains what is left the same way: it reports
`access.profile.higher_classification` for `group-membership.person`, because PublicSchema marks that
property sensitive, so the derivation classified the field `restricted` inside an entity that is not,
and `operator` reads it anyway. Keep the finding as a reminder of what that profile discloses, or
raise the entity's classification in `model/selection.yaml` and derive again.

The `person` field table in `household-registry-2/README.md` no longer lists `marital-status`. Any
other edit, adding a property or removing one, follows the same cycle: change
`model/selection.yaml`, derive into a new directory, and read the new README.

## Use the interactive wizard

Without `--starter` or `--selection`, `init --from publicschema` asks its questions at a terminal
instead of reading a file. Every prompt, and the review at the end, go to standard error; standard
output carries only the final report, so a script that captures standard output still gets a clean
result even if the command happens to run at a terminal.

The wizard asks, in order:

1. "Registry identifier", with the help text "lowercase letters, digits, and hyphens; it names the
   registry in its IRIs, scopes, and the catalogue".
2. "Registry title", defaulting to a title derived from the identifier.
3. "Which concepts become entities?", a multi-select listed by schema file then name (space to
   toggle, type to filter, enter to confirm). Abstract concepts, and concepts with no property the
   project could carry, are left off the list.
4. "Which concepts connect what you chose?", a multi-select of the concepts you did not choose
   that refer to at least two of the ones you did, each shown by what its references point at:
   "Group Membership (publicschema-misc): group is a Household, person is a Person". Choosing one
   adds it to the entities; enter alone adds none. PublicSchema links its concepts through such
   concepts rather than through direct properties, so a registry of a household and a person has
   no field between them until a membership is added. When a chosen concept has nothing in the
   model to connect it, a line above the prompt says so, and the prompt is skipped when there is
   nothing to offer.
5. For each chosen concept, "Which properties of `<Title>` become fields?", a multi-select. A
   property the project cannot carry is named first, with the reason, but not offered as an option. Each
   offered option names its shape, its classification when the property is sensitive or restricted,
   and how many of the systems the model tracks already record it; a required property, one at
   least 60% of those systems record, or a reference to another chosen concept starts ticked.
6. "Which entity does `<Concept>.<property>` point at?", a single select, asked only when more than
   one chosen concept fits a reference.
7. "Keep the default identifiers and routes?", after one line per entity showing its route and its
   identifier field. Answering no asks, for each entity in turn: "Entity identifier for
   `<Concept>`", "Collection route for `<Concept>`", and "Identifier field for `<Concept>`", each
   with its default shown.
8. "Which code lists should the project list in full?", a multi-select, ticked for any list of at
   most 300 values; an unticked list is carried as a bounded code instead. This prompt is skipped
   when no chosen property draws on a code list.
9. The selection is printed as YAML, followed by a line naming any entity no field connects to
   another, then "Derive the project from this selection?".

An entity nothing links is not an error: a registry of unrelated collections is a legitimate
choice. The written README carries a "What is not linked" section naming those entities and the
concepts of the model that would connect them, and the report's next steps point to it. Add the
concept under `entities` in `model/selection.yaml` and derive again to link them.

Answering no at the last prompt, or cancelling any of them with Esc or Ctrl-C, writes nothing and
reports `init.selection.cancelled`: cancelled at a prompt; nothing was written.

Without a terminal at all, for example in a script or in CI, the wizard cannot run, and
`init --from publicschema` alone refuses immediately:

```text
error init.selection.missing at arguments: `init --from publicschema` asks its questions at a terminal; without one, pass `--selection <FILE>` or `--starter <NAME>` (one of `household`)
```

Pass `--starter household` or `--selection <FILE>` instead, the way the rest of this tutorial does.

## Troubleshooting

| Symptom | Next move |
| --- | --- |
| `bregctl` is not found | Add the installer's directory, `~/.local/bin` unless you changed it, to `PATH` in this terminal. |
| `init --from publicschema` refuses with `init.selection.missing` | No terminal is attached, so the wizard cannot ask its questions. Pass `--starter household` or `--selection <FILE>` instead. |
| `init --from publicschema --selection <FILE>` refuses over the file | `<FILE>` is a symbolic link, or larger than 256 KiB. Point `--selection` at an ordinary file under that size. |
| `bregctl init` cannot parse the edited `model/selection.yaml` | Compare the indentation of the lines you changed with the rest of the file; a selection is a plain YAML list of entities, each with a `properties` list under it. |
| `bregctl dev household-registry` fails before it reports `ready` | Check that Docker is running. The private logs are under `household-registry/.breg/dev/logs/`; do not share the credential or secret files beside them. |

If you provide assertions from Base Registry Engine (BReg), import one narrow
lookup into a complete Evidence project, author the assertions it supports, and
check their disclosure and refusal behavior with synthetic fixtures. This
exercise runs offline and packages a candidate without starting either service.

## Unpack the reviewed inputs

Download the [BReg and Evidence teaching files](../../examples/breg-evidence-starter.tar.gz)
into a fresh working directory as `breg-evidence-starter.tar.gz`, then unpack:

```sh
mkdir teaching-inputs
tar -xzf breg-evidence-starter.tar.gz -C teaching-inputs
cp -R teaching-inputs/registry ./registry
bregctl check ./registry
```

The explicit registry declares two unique selectors and a lookup-only source
profile. Its `label` field is unavailable to that profile. The default `bregctl
init` contact directory supplies no Evidence lookup grant or business key, so
this exercise uses the integration's authored model.

The archive also contains a complete `offline-starter` and an optional BReg
assertion fragment under `starter`. Keep their boundaries: the fragment cannot
initialize an Evidence project by itself.

## Initialize the independent Evidence project

```sh
evidencectl init ./evidence --starter ./teaching-inputs/offline-starter --profile local
evidencectl check ./evidence
evidencectl test ./evidence --target ./evidence/local-target.yaml
```

Read `evidence/evidence.yaml`. Sources, selector profiles, named Functions, and
AssertionDefinitions are declared in that one normalized project. The local
target and its separate authority file supply complete disposable caller grants.
Initialization creates owner-only local keys; keep `.generated/` out of version
control and support messages.

The 13 SQLite cases cover active and retired values, missing or ambiguous matches,
stale extracts, bounded statements/results, and hostile selectors remaining bound
parameters. A successful fixture run reports the evaluated cases. This proves
recorded-source behavior, not access to a running registry or live signing.

## Export and import one BReg Source

```sh
bregctl generate evidence-source ./registry \
  --access-profile evidence-source --record-type record \
  --selector by-code --selector by-registration-number \
  --fields status --source-id registry-status --connection registry \
  --output ./registry-status-export
evidencectl source import ./registry-status-export --project ./evidence
```

The export selects the existing profile, exact selector alternatives, and status
fact. It creates no BReg authority. Import verifies the export inventory and
merges its normalized Source, selector profiles, and named preparation/extraction
Functions into the existing EvidenceProject. It adds no AssertionDefinition or
caller grant. Keep the independent SQLite definition.

An unreadable field is refused during export. A changed export artifact fails
checksum verification before import changes authored files. Generate a fresh
output directory when revising the contract.

## Add the reviewed assertion definitions

Copy the fragment's programs and fixtures into the project:

```sh
cp teaching-inputs/starter/functions/*.rhai evidence/functions/
cp teaching-inputs/starter/fixtures/*.yaml evidence/fixtures/
```

Open `teaching-inputs/starter/definitions.yaml.fragment` beside
`evidence/evidence.yaml`. Append its two `functions` entries to the existing list,
and merge its `assertionDefinitions` entries into the existing map. Preserve the
current Sources, selector profiles, Functions, and `extract-record-active`
definition. The fragment is ordinary authoring, not a second import format.

`record-active` derives one boolean. `record-status-pair` derives the reviewed
active/retired pair. Both reuse the imported Source and exact selector contracts.
Their 22 cases cover identity/type mismatches, absent facts, source failures,
minimum disclosure, and refusal boundaries. An absent or null status is
unavailable evidence and cannot become an authoritative `false`.

## Bind a separate complete local target

```sh
evidencectl target new ./configured-target --local --project ./evidence
```

Review the generated authority for all three definitions. In
`configured-target/target.yaml`, replace the empty `connections` map with this
synthetic fixture binding:

```yaml
connections:
  registry:
    origin: http://127.0.0.1:8090
    authentication:
      type: oauth2-private-key-jwt
      tokenEndpoint: http://127.0.0.1:8091/oauth2/token
      clientIdRef: secret:file/registry-client-id
      clientAssertionKeyRef: secret:file/registry-client-key
      clientAssertionAudience: http://127.0.0.1:8091
      scope: registry:evidence:lookup
      maximumCacheSeconds: 60
```

These are fixed local contract specimens. Fixtures supply recorded responses and
resolve no source credential or network endpoint. Before live use, bind the
actual registry origin, issuer, exact audience/resource/scopes, and approved
source-client secrets. Source credentials never authorize an Evidence caller.

```sh
evidencectl check ./evidence --target ./configured-target
evidencectl test ./evidence --target ./configured-target
evidencectl package ./evidence --target ./configured-target --output ./candidate
```

A complete run evaluates 35 cases across three definitions. Inspect a failing
case and its named Source, Function, or grant rather than weakening its expected
refusal. Packaging writes `candidate/bundle/` and a separate target handoff.
Neither product is deployed. Use a fresh candidate directory for the next build.

## Maintain meaning and authority separately

Record-value changes need no new export. A consumed selector, fact, authority,
or derived behavior change does. Export to a fresh directory, review
`evidencectl source diff`, then apply the reviewed `source update` against the
same project and target. Recheck fixtures and package before coordinating the
provider and Evidence deployment. A renamed fact must be reconciled with every
Function that reads it; an unused registry field must not alter assertion meaning.

No service was started in this exercise. Retain or remove the synthetic project,
local keys, exports, and candidate under your own development retention policy.
Keep local authority and credentials separate from the production deployment.

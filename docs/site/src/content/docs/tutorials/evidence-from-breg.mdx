If your institution answers questions from a Base Registry Engine (BReg) registry, Evidence can
look up one record and sign a narrow answer about it. You will export one lookup from a teaching
registry, build an Evidence project around it, and test it offline with synthetic fixtures. The
last step shows how to check, on a deployed registry, that the lookup credential reaches nothing
else.

## Unpack the teaching files

Download the [BReg and Evidence teaching files](../../examples/breg-evidence-starter.tar.gz)
into a fresh working directory as `breg-evidence-starter.tar.gz`, then unpack them:

```sh
mkdir teaching-inputs
tar -xzf breg-evidence-starter.tar.gz -C teaching-inputs
cp -R teaching-inputs/registry ./registry
bregctl check ./registry
```

The registry has one Record type, `record`, with two unique selectors: `by-code` and
`by-registration-number`. Its `evidence-source` access profile may only look records up, and it
cannot read `label`.

The check passes with two warnings, one for each access profile:

```text
Authoring check passed; registry revision sha256:<revision>.
warning[breg.access.profile-unrestricted-rows] <dir>/registry/registry.yaml:124:22 /accessProfiles/1/permissions/records/0/rowBoundaries
  this profile has no claim-bound row restriction for its granted operations; Review this registry-wide access
  next: Review the finding, and change the source if the behavior it describes is not intended.
warning[breg.access.profile-unrestricted-rows] <dir>/registry/registry.yaml:103:22 /accessProfiles/0/permissions/records/0/rowBoundaries
  this profile has no claim-bound row restriction for its granted operations; Review this registry-wide access
  next: Review the finding, and change the source if the behavior it describes is not intended.
0 errors, 2 warnings in 2 files
```

Both are expected. Each profile sets `rowBoundaries: unrestricted`: Evidence may look up any
record by its code, and the operator manages every record. [Grant fields and
rows](../../configure/breg-access/#grant-fields-and-rows) explains row boundaries.

The archive also holds `offline-starter`, a complete Evidence project, and `starter`, a fragment
of assertion definitions over the registry lookup. The fragment is not a project on its own.

## Start the Evidence project

```sh
evidencectl init ./evidence --starter ./teaching-inputs/offline-starter --profile local
evidencectl check ./evidence
evidencectl test ./evidence --target ./evidence/local-target.yaml
```

Read `evidence/evidence.yaml`. Sources, selector profiles, named Functions, and
AssertionDefinitions live in that one project. The local target and its separate authority file
grant a disposable local caller. Initialization creates owner-only local keys under
`.generated/`; keep that directory out of version control and support messages.

The 13 fixture cases read a recorded SQLite extract. They cover active and retired values,
missing or ambiguous matches, stale extracts, bounded results, and hostile selectors that stay
bound parameters. A pass proves recorded-source behavior, not access to a running registry.

## Export and import one lookup

```sh
bregctl generate evidence-source ./registry \
  --access-profile evidence-source --record-type record \
  --selector by-code --selector by-registration-number \
  --fields status --source-id registry-status --connection registry \
  --output ./registry-status-export
evidencectl source import ./registry-status-export --project ./evidence
```

The export reports `Generated 9 artifacts.` and repeats the two warnings. It names the existing
profile, both selectors, and the `status` fact, and it grants no registry authority. Asking for
`label` instead is refused with `breg.evidence-source.refused`, because the profile cannot read
it.

Import checks every artifact's checksum before it changes a file. It adds a Source named
`registry-status`, its selector profiles, and its preparation and extraction Functions. It adds
no AssertionDefinition and no caller grant. To revise the contract, export to a fresh directory.

## Add the assertion definitions

Copy the fragment's programs and fixtures into the project, then merge its definitions into
`evidence/evidence.yaml` with [yq](https://github.com/mikefarah/yq) version 4:

```sh
cp teaching-inputs/starter/functions/*.rhai evidence/functions/
cp teaching-inputs/starter/fixtures/*.yaml evidence/fixtures/
yq --inplace '
  .functions += load("teaching-inputs/starter/definitions.yaml.fragment").functions
  | .assertionDefinitions += load("teaching-inputs/starter/definitions.yaml.fragment").assertionDefinitions
' evidence/evidence.yaml
```

The command appends the fragment's two Functions and adds its two definitions. It keeps the
Sources, selector profiles, existing Functions, and `extract-record-active` as they were. The
fragment is ordinary authoring, not a second import format.

`record-active` derives one boolean. `record-status-pair` derives the active and retired pair.
Both read the imported Source through its exact selectors. Their 22 cases cover identity and
type mismatches, absent facts, source failures, minimum disclosure, and refusals. An absent or
null status is unavailable evidence; it never becomes an authoritative `false`.

## Bind a local target and package

```sh
evidencectl target new ./configured-target --local --project ./evidence
```

Review the generated authority for all three definitions. In `configured-target/target.yaml`,
replace the empty `connections` map with this synthetic binding:

```yaml
connections:
  registry:
    origin: http://127.0.0.1:8090
    authentication:
      type: oauth2-private-key-jwt
      tokenEndpoint: http://127.0.0.1:8091/oauth2/token
      clientIdRef: secret:file/registry-client-id
      clientAssertionKeyRef: secret:file/registry-client-key
      clientAssertionAudience: http://127.0.0.1:8091
      scope: registry:evidence:lookup
      maximumCacheSeconds: 60
```

Fixtures supply recorded responses, so nothing here contacts a network endpoint or resolves a
credential. Before live use, bind the real registry origin, issuer, audience, scope, and source
client secrets. A source credential never authorizes an Evidence caller.

```sh
evidencectl check ./evidence --target ./configured-target
evidencectl test ./evidence --target ./configured-target
evidencectl package ./evidence --target ./configured-target --output ./candidate
```

The test run evaluates 35 cases across three definitions. If a case fails, inspect its named
Source, Function, or grant; do not weaken its expected refusal. Packaging writes
`candidate/bundle/` and a separate target handoff. Use a fresh candidate directory for each
build.

## Check the source credential on a deployed registry

Fixtures cannot show what a live credential reaches. Once your registry serves this project, and
before Evidence takes traffic, call it the way Evidence will: as a plain HTTP caller holding the
source client's token. [Deploy and serve](../../operate/breg/) covers running the registry.

Ask your identity operator for an owner-only `source-authorization.curl` file. It holds a
short-lived authorization header for the source client; keep it outside the candidate. Put the
synthetic selector in `source-lookup.json`:

```json
{"selector":"by-code","values":{"code":"SYNTHETIC-ACTIVE"}}
```

Look the record up through the route the export names, on your registry's own origin:

```sh
curl --silent --show-error --fail-with-body \
  --config ./source-authorization.curl \
  --header 'Content-Type: application/json' \
  --data-binary @source-lookup.json \
  'https://registry.example.invalid/v1/records/records:lookup?accessProfile=evidence-source&$select=code,status' \
  --output source-lookup-response.json --write-out 'HTTP %{http_code}\n'
```

A match answers HTTP 200 with one record, limited to `code` and `status`. A code that matches no
record, or more than one, answers 404 `lookup.unresolved`. Read the record's UUID from
`data.recordIdentifier`.

Next, the registry operator confirms that the record is readable through a profile the source
client does not hold. They run this in their own workspace; their credential never enters
Evidence:

```sh
curl --silent --show-error --fail-with-body \
  --config ./operator-authorization.curl \
  'https://registry.example.invalid/v1/records/records/<recordIdentifier>?accessProfile=operator' \
  --output operator-read-response.json --write-out 'HTTP %{http_code}\n'
```

Replace `<recordIdentifier>` with the UUID in this command and the next. Once the operator sees
HTTP 200, request the same record and profile with the source credential:

```sh
curl --silent --show-error --fail-with-body \
  --config ./source-authorization.curl \
  'https://registry.example.invalid/v1/records/records/<recordIdentifier>?accessProfile=operator' \
  --output source-refusal.json --write-out 'HTTP %{http_code}\n'
```

This one must fail: curl exits nonzero with HTTP 404 and the problem `resource.not_found`. The
registry answers a profile the token does not satisfy exactly as it answers a missing record,
so the caller learns nothing. [Read refusals](../../reference/breg-api/#read-refusals) lists
these answers. If the request succeeds, keep traffic off and correct the source client or the
profile before you retry.

A collection request proves nothing here: the teaching operator profile grants no `list`, so it
is refused whoever asks. A fixture pass, a complete target, or a working token exchange does not
replace these checks either. Keep the synthetic responses in each party's private workspace.

## Maintain meaning and authority separately

A change to record values needs no new export. A change to a consumed selector, fact, profile, or
derived behavior does. Export to a fresh directory, review `evidencectl source diff`, then apply
the reviewed `evidencectl source update` against the same project and target. Recheck the
fixtures and package again. A renamed fact must be reconciled with every Function that reads it.

No update switches the registry, Evidence, and their consumers at once. For a breaking change,
pause the affected Evidence traffic and [activate](../../operate/breg/#activate-and-serve) the
new registry package. Repeat the source lookup check, start the new Evidence candidate, and
resume consumers only after a fresh synthetic assertion verifies.

No service ran in this exercise. Remove the synthetic project, local keys, exports, and candidate
under your own retention policy, and keep local credentials away from production.

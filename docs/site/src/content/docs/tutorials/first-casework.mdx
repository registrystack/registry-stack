You will submit one ReviewRequest as a producer, decide it as staff, and read the answer as the
producer. The request carries its own snapshot, so no source registry is needed.

## Install Registry Stack

Download one exact `rstack-vX.Y.Z-install.sh` and the verification material from the same Registry
Stack release. Follow the
[release verification procedure](https://github.com/registrystack/registry-stack/blob/main/release/VERIFY.md)
before running the installer. From the verified release directory, install the `casework`
component:

```sh test-skip="uses a downloaded, independently verified release installer"
tag="vX.Y.Z"
bash "rstack-${tag}-install.sh" casework
rstack casework --version
```

The managed installation exposes `rstack` on your `PATH`. The `casework` component supplies the
Casework runtime and its command-line tools from the same release.

{/* Evidence: crates/registry-rstack/README.md; crates/registry-rstack/install.sh; release/VERIFY.md. */}

## Create the project

Create a project from the standalone template and work inside it:

```sh
mkdir -p tutorial-work
rstack casework init tutorial-work/casework --template standalone-decision
cd tutorial-work/casework
```

```json test-excerpt
  "command": "init",
  "status": "complete",
  "created": "tutorial-work/casework",
  "next": "Run caseworkctl check, test and types. Write a dev.yaml plan beside casework.yaml and run rstack dev start.",
  "template": "standalone-decision"
}
```

## Check what the policy allows

The project declares one [ReviewPolicy](../../reference/glossary/#review-policy), `decision`: who
may ask, which team answers, and the outcomes allowed. Check it offline and run its fixture:

```sh
rstack casework check .
rstack casework test .
```

```json test-excerpt
{
  "policyBindings": [
    {"digest": "sha256:<digest>", "id": "decision", "version": "1"}
  ]
}
```

The digest pins the policy's behavior. To read what that behavior is, explain it:

```sh
rstack casework explain .
```

```json test-excerpt
{
  "contextCustody": "admitted bounded snapshot",
  "refusals": [
    "untrusted producer",
    "policy binding mismatch",
    "concealed source",
    "changed subject or contract",
    "stale task revision",
    "ineligible reviewer"
  ]
}
```

Casework keeps the snapshot the producer sends and refuses each listed case.

## Describe the local run

`rstack dev` runs the project on your machine from a plan file. First tell Casework which issuer
and subject the producer's tokens carry. The template trusts a fixed local address, and a run signs
its test tokens under an HTTPS issuer name of your choosing:

```diff test-edit title="casework.yaml"
 trustedProducers:
   requester:
     profile: requester
-    issuer: http://127.0.0.1:8093
-    subject: b75315b2-5854-70f3-8867-511dd771a6da
+    issuer: https://identity.standalone.example.test
+    subject: requester
```

The plan lists the product, the test people and what each may do. It names a scenario file, which
runs when the run starts:

```yaml title="dev.yaml" test-file
apiVersion: id.registrystack.org/formats/rstack/dev/v1alpha1
kind: RStackDev
issuer: https://identity.standalone.example.test
products:
  - {product: casework, project: ., audience: "urn:example:standalone-decision"}
people:
  administrator:
    subject: administrator
    client: standalone-workbench
    grants:
      casework:
        profile: administrator
        scopes: ["casework:admin"]
        claims: {registry_actor_kind: human}
  staff:
    subject: staff
    client: standalone-workbench
    grants:
      casework:
        profile: staff
        scopes: ["casework:staff"]
        claims: {registry_actor_kind: human}
  requester:
    subject: requester
    client: standalone-requester
    grants:
      casework:
        profile: requester
        scopes: ["casework:request"]
scenarioFile: tests/scenarios.yaml
```

A new Casework directory has no staff. The scenario has the administrator seat one team on the
`decisions` queue and put the person `staff` in it:

```sh
mkdir tests
```

```yaml title="tests/scenarios.yaml" test-file
apiVersion: id.registrystack.org/formats/rstack/scenarios/v1alpha1
kind: RStackScenarios
scenarios:
  - id: staff-the-queue
    steps:
      - id: staff-the-queue
        product: casework
        as: administrator
        method: POST
        path: /v1/directory/bootstrap
        headers: {If-Match: '"0"', Idempotency-Key: staff-the-queue}
        body:
          teamId: decisions-team
          staff: [{issuer: https://identity.standalone.example.test, subject: staff}]
          supervisors: []
          queueId: decisions
        expect: {status: 200}
```

## Start the run

Check the plan, then start the run. [Run a project with rstack dev](../../configure/run-a-project-with-rstack-dev/)
explains the options and how to recover a failed run:

```sh
rstack dev check .
rstack --format json dev start . --ttl 2h > run.json
run_id="$(jq -r .run_id run.json)"
casework_url="$(jq -r .products.casework run.json)"
```

PostgreSQL runs in Docker, and the run has seated one staff team. Its state, keys and logs live in
the run's own owner-only directory, outside your project. Each call below needs a short-lived token
for one of the plan's people. This function asks for one and prints the header file to pass to curl:

```sh
headers_for() {
  rstack dev token "$run_id" --as "$1" | awk '$1 == "casework" && $2 == "headers" {print $3}'
}
```

## Submit a ReviewRequest

Save the request. It names the policy, the subject under review, and the snapshot a reviewer will
read:

```json title="request.json" test-file
{
  "policy": {"id": "decision"},
  "subject": {
    "source": "standalone",
    "type": "batch",
    "id": "LIC-2026-0041",
    "version": "1",
    "digest": "sha256:6a3167d79ae3308448b24f2c9c0b9ac1cf116a7ad8be0c167c7e8660e43662bb"
  },
  "requesterReference": "LIC-2026-0041",
  "context": {
    "mode": "submitted",
    "snapshot": {"reference": "LIC-2026-0041", "summary": "Review licence batch LIC-2026-0041"}
  }
}
```

The subject digest is the producer's own fingerprint of the version it asks about, here the
SHA-256 of the snapshot's compact JSON; Casework binds the request and its result to it. Send it:

```sh
curl -sS --fail-with-body --header @"$(headers_for requester)" \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: tutorial-review-1' \
  --data @request.json \
  --output accepted.json "$casework_url/v1/review-requests"
jq . accepted.json
request_id="$(jq -r .requestId accepted.json)"
```

```json test-excerpt
{
  "requestId": "<id>",
  "policy": {"id": "decision", "version": "1", "digest": "sha256:<digest>"},
  "submissionDigest": "<digest>"
}
```

The request named only the policy ID, so Casework bound it to the active version and the digest
`check` printed. The same body under the same key returns this request, not a second one.

## Read the ReviewTask

The request opened a [ReviewTask](../../reference/glossary/#review-task). List it as staff:

```sh
curl -sS --fail-with-body --header @"$(headers_for staff)" \
  --output tasks.json "$casework_url/v1/review-tasks?limit=25"
task_id="$(jq -r '.items[0].taskId' tasks.json)"
task_revision="$(jq -r '.items[0].revision' tasks.json)"
```

Try to read it as the producer:

```sh
curl -sS --header @"$(headers_for requester)" \
  --output refused.json --write-out '%{http_code}\n' "$casework_url/v1/review-tasks/$task_id"
jq . refused.json
```

```json test-excerpt
{"code": "operation.not-authorized", "status": 403, "title": "Operation not authorized"}
```

A producer may read its result, never the human task.

{/* Evidence: crates/registry-casework/src/http.rs, review_tasks, get_review_task. */}

## Claim and decide

[Claim](../../reference/glossary/#claim) the task at the revision you read, so no one else decides
it while you work:

```sh
curl -sS --fail-with-body --header @"$(headers_for staff)" --request POST \
  --header "If-Match: \"$task_revision\"" \
  --header 'Idempotency-Key: tutorial-claim-1' \
  --output claimed.json "$casework_url/v1/review-tasks/$task_id/claim"
jq . claimed.json
claimed_revision="$(jq -r .revision claimed.json)"
```

```json test-excerpt
{
  "revision": 2,
  "state": {"held": {"holder": {"issuer": "https://identity.standalone.example.test", "subject": "staff"}}}
}
```

You hold the task at revision 2. Save one of the policy's outcomes as `decision.json`:

```json title="decision.json" test-file
{"decision":{"type":"answer","outcome":"confirmed"}}
```

Send the decision:

```sh
curl -sS --fail-with-body --header @"$(headers_for staff)" \
  --header 'Content-Type: application/json' \
  --header "If-Match: \"$claimed_revision\"" \
  --header 'Idempotency-Key: tutorial-answer-1' \
  --data @decision.json \
  --output /dev/null --write-out '%{http_code}\n' "$casework_url/v1/review-tasks/$task_id/decisions"
```

Casework records the decision and answers `204`.

{/* Evidence: crates/registry-casework/src/http.rs, claim_review_task, decide_review_task;

## Read the ReviewResult

Back as the producer, fetch the answer:

```sh
curl -sS --fail-with-body --header @"$(headers_for requester)" \
  --output result.json "$casework_url/v1/review-requests/$request_id/result"
jq . result.json
```

```json test-excerpt
{"status": "answered", "outcome": "confirmed", "availableUntil": "<instant>"}
```

The [ReviewResult](../../reference/glossary/#review-result) repeats the request's policy, subject
and submission digest. It names no reviewer and is kept until `availableUntil`.

remove the run's containers, database and credentials.

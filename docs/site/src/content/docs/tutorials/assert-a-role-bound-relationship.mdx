Answer, "Is this candidate in the complete legal-parent set for this child?" This tutorial reuses
the reviewed standalone project from [your first Evidence Gateway assertion](../first-evidence-assertion/).
Its definition binds two subjects in distinct roles and releases one Boolean.

## Review the complete relationship path

Enter the copied standalone project left by the first tutorial:

```sh test-cwd="first-evidence-assertion"
cd adult-status
```

The `legal-parent-relationship` definition in `evidence.yaml` declares both `child` and
`candidate-parent`, the `relationship-check` purpose, and the Boolean Output `is-parent` with
concept `urn:example:concept:legal-parent-relationship:v1`.

The `parent-record` Source uses only the `child` selector to fetch one complete parent set. Its
named `extract-parents` Function refuses no match, multiple matches, an incomplete set, or a record
for another child. The named `derive-parent-relationship` Function receives the minimized
`candidate-parent` selector and tests membership. The Output gate permits only `is-parent`, so the
parent list cannot enter the assertion.

`dev-authority.yaml` grants one complete request shape to the existing `standalone-service`
profile: the exact definition, purpose, signed-JWS representation, audience-scoped binding, and
both request-origin roles. Partial grants cannot be combined into authority.

Prove the project closure, then run the relationship fixture alone:

```sh
evidencectl check . --target local-target.yaml
evidencectl test . \
  --target local-target.yaml \
  --fixture fixtures/legal-parent-relationship.yaml
```

The nine synthetic cases cover true and false membership, no match, ambiguity, source failure, an
incomplete set, a missing required fact, an empty complete set, and an attempted relationship-graph
reconstruction. Fixture evaluation is offline; it does not prove the source is reachable.

## Start the authenticated source and Evidence Gateway

In another terminal, start the bounded source with the token already generated by the first
tutorial:

```sh test-cwd="first-evidence-assertion/adult-status" test-background="http://127.0.0.1:8081/healthz"
python3 serve-source.py \
  --port 8081 \
  --token-file .generated/secrets/synthetic-source-token
```

The health route exposes no record data. Every record route requires the bearer token from the
target, and the source suppresses selector values from its logs.

Start a fresh local generation. The first tutorial retained the `tutorial-client` registration
when it cleaned its earlier generation.

```sh
evidencectl dev start . \
  --target local-target.yaml \
  --evidence-port 18080 \
  --issuer-port 8082
```

## Request and verify the relationship

Prepare one request with both role-qualified subjects:

```sh
evidencectl request prepare legal-parent-relationship \
  --client tutorial-client \
  --purpose relationship-check \
  --subject child:record-id=child \
  --subject candidate-parent:record-id=parent \
  --name legal-parent-relationship
```

Send the prepared request, retain the exact response, and verify it before reading the value:

```sh
curl --silent --show-error --fail-with-body \
  --config .evidence/requests/legal-parent-relationship/authorization.curl \
  --request POST \
  --url http://127.0.0.1:18080/v1/evidence \
  --header 'Content-Type: application/json' \
  --header 'Accept: application/jose+json' \
  --data-binary @.evidence/requests/legal-parent-relationship/request.json \
  --output .evidence/requests/legal-parent-relationship/response.json
evidencectl verify .evidence/requests/legal-parent-relationship/response.json \
  --context .evidence/requests/legal-parent-relationship/verification.json \
  --output .evidence/requests/legal-parent-relationship/verified.json
```

Check only the governed facts the application needs:

```sh
python3 - <<'PY'
import json

path = ".evidence/requests/legal-parent-relationship/verified.json"
evidence = json.load(open(path))
assert {subject["role"] for subject in evidence["subjects"]} == {
    "child",
    "candidate-parent",
}
assert evidence["supportedValues"] == [{
    "providesValueFor": "urn:example:concept:legal-parent-relationship:v1",
    "value": True,
}]
PY
```

The verified assertion contains two distinct opaque subject bindings and one Boolean. It excludes
the child selector, candidate selector, source token, and complete parent set.

## Prove the role boundary

A missing role is not the granted request shape. Preparation refuses it before creating request
artifacts:

```sh test-exit="1"
evidencectl request prepare legal-parent-relationship \
  --client tutorial-client \
  --purpose relationship-check \
  --subject child:record-id=child \
  --name missing-candidate-parent
```

Repeating the `child` role is also malformed, even when both values are valid selector values:

```sh test-exit="1"
evidencectl request prepare legal-parent-relationship \
  --client tutorial-client \
  --purpose relationship-check \
  --subject child:record-id=child \
  --subject child:record-id=parent \
  --subject candidate-parent:record-id=parent \
  --name duplicate-child
```

Role names and values have different jobs. Swapping the two valid values still creates a complete
request shape, but it asks whether `child` is a parent of the record selected as `parent`. The
source has no complete parent record for that child selector, so Evidence Gateway returns the
same public no-match refusal used for any unresolved subject and produces no assertion.

```sh
evidencectl request prepare legal-parent-relationship \
  --client tutorial-client \
  --purpose relationship-check \
  --subject child:record-id=parent \
  --subject candidate-parent:record-id=child \
  --name swapped-relationship
curl --silent --show-error \
  --config .evidence/requests/swapped-relationship/authorization.curl \
  --request POST \
  --url http://127.0.0.1:18080/v1/evidence \
  --header 'Content-Type: application/json' \
  --header 'Accept: application/jose+json' \
  --data-binary @.evidence/requests/swapped-relationship/request.json \
  --output .evidence/requests/swapped-relationship/refusal.json \
  --write-out '%{http_code}\n' \
  > .evidence/requests/swapped-relationship/status.txt
python3 - <<'PY'
import json
from pathlib import Path

request = Path(".evidence/requests/swapped-relationship")
assert (request / "status.txt").read_text().strip() == "422"
assert json.loads((request / "refusal.json").read_text())["code"] == "evidence.unavailable"
assert not (request / "verified.json").exists()
PY
```

Do not treat every `false` relationship as a lookup failure. When `child` resolves to a complete
set and `candidate-parent` is absent from that set, the governed answer is a signed `false`. When
the child record is unresolved or incomplete, the service releases no relationship answer.

## Inspect the audit and clean up

Stop the retained generation before reading its last operation:

```sh
evidencectl dev stop .
evidencectl audit show --last-operation
evidencectl dev clean .
```

The audit records the definition, purpose, requester pseudonym, and release or refusal class. It
does not record either selector value, the parent set, or the returned Boolean. The tutorial runner
stops the synthetic source. If you started it by hand, press `Ctrl+C` in its terminal.

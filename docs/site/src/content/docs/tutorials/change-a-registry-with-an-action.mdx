In about ten minutes you will change the registry from
[Create your first registry](../first-breg/) in the two ways it allows: one change takes effect
the moment it is asked for, the other is prepared first and then applied by the registry. You will
check the registry's answer to each, and finish with three contacts in the registry.

## Return to your project

Open a terminal in the directory that holds `tutorial-work` and go to the project. The run from
the first tutorial holds one contact. This tutorial adds two scenarios to the project's scenario
file, so you stop and restart the run to send them. Stopping a run keeps its development data, so
the next start skips the first scenario and runs the two new ones:

```sh test-cwd="tutorial-work/project"
RUN="$(awk '$1 == "Run" {print $2}' dev-run.txt)"
rstack dev stop "$RUN"
```

```text test-expect
Run <run-id> stopped
```

## Read the two Actions

Besides creating and editing Records field by field, a project can declare an
[Action](../../reference/glossary/#action): a named change with typed inputs and a fixed list of
effects. Open `registry.yaml` and find `actions`:

```yaml title="registry.yaml" test-excerpt="registry.yaml"
actions:
  update-contact-email:
    display: {label: Update contact email, description: Replace one contact's email address as soon as the Action is invoked.}
    execution: {mode: immediate}
    inputs:
      - {id: contact, apiName: contactId, type: reference, target: contact, required: true, classification: internal}
      - {id: email, type: string, required: true, minimumLength: 1, maximumLength: 254, classification: internal}
    plan:
      type: fixed
      effects:
        - id: contact-email
          target: {fromInput: contact}
          operation: patch
          set:
            email: {fromInput: email}
```

`update-contact-email` takes a contact and an email address. Its `plan` is its
[Plan](../../reference/glossary/#planner): the one effect it has, a patch of that contact's
`email`. `execution: {mode: immediate}` means the registry makes the change in the same request
that invokes the Action.

```yaml title="registry.yaml" test-excerpt="registry.yaml"
  register-contact:
    display: {label: Register contact, description: Create one contact through a Proposal that applies on submit without external review.}
    execution:
      mode: proposal
      proposal:
        review: {type: none}
        retention: {mode: retain}
```

`register-contact` creates a contact, but in `proposal` mode. Starting it creates a
[Proposal](../../reference/glossary/#proposal): a draft the caller can edit, submit, or cancel,
which the registry keeps. `review: {type: none}` means nobody has to approve it, so the registry
applies it once it is submitted.

The access profile grants each Action separately. A caller may invoke `update-contact-email` only on
contacts in its own jurisdiction:

```yaml title="registry.yaml" test-excerpt="registry.yaml"
      actions:
        - action: update-contact-email
          operations: [invoke]
          targets:
            - recordType: contact
              rowBoundaries:
                - {field: jurisdiction, claim: jurisdiction, operator: equals}
          results: [contact-email]
```

## Change a contact's email

An immediate Action asks the registry which state of the contact the change is based on, then
sends the change with that condition. A scenario does both. Add the `update-contact-email` scenario
to the end of `dev/scenarios.yaml`. It creates a contact with the email `old@example.test`, and
changes it with the Action:

```yaml title="dev/scenarios.yaml" test-append
  - id: update-contact-email
    steps:
      - id: create-contact
        product: breg
        as: editor
        method: POST
        path: /v1/records/contacts
        headers: {Idempotency-Key: create-moving-contact}
        body: {data: {name: Moving contact, email: old@example.test, jurisdiction: zone-a}}
        expect: {status: 201}
        capture: {contact: {type: pointer, pointer: /data/recordIdentifier}}
      - id: read-conditions
        product: breg
        as: editor
        method: POST
        path: /v1/actions/update-contact-email/target-conditions
        body: {input: {contactId: "{{contact}}"}}
        expect: {status: 200}
        capture: {contactCondition: {type: pointer, pointer: /preconditions/contactId/ifMatch}}
      - id: invoke
        product: breg
        as: editor
        method: POST
        path: /v1/actions/update-contact-email
        headers: {Idempotency-Key: update-contact-email}
        body:
          input: {contactId: "{{contact}}", email: new@example.test}
          preconditions: {contactId: {ifMatch: "{{contactCondition}}"}}
        expect:
          status: 200
          json: {/action: update-contact-email, /results/contact-email/revision: 2}
```

The `invoke` step expects the registry's answer to the Action: an
[ActionReceipt](../../reference/glossary/#action). An ActionReceipt names the Action, gives this
change an `applicationId`, and lists, for each effect in the Plan, the Record it changed and that
Record's new revision. Revision `2` is the contact after the change.

## Register a contact through a Proposal

Add the `register-contact` scenario to the end of the file. It takes the Proposal through three
steps as `editor`: start it, submit it, and read it until the registry has applied it.

```yaml title="dev/scenarios.yaml" test-append
  - id: register-contact
    steps:
      - id: start
        product: breg
        as: editor
        method: POST
        path: /v1/actions/register-contact/proposals
        headers: {Idempotency-Key: start-registration}
        body: {input: {name: Registered contact, email: registered@example.test, jurisdiction: zone-a}}
        expect: {status: 201, json: {/state: draft}}
        capture:
          proposal: {type: pointer, pointer: /id}
          draftEtag: {type: header, header: etag}
      - id: submit
        product: breg
        as: editor
        method: POST
        path: "/v1/proposals/{{proposal}}/submit"
        headers: {If-Match: "{{draftEtag}}", Idempotency-Key: submit-registration}
        body: {}
        expect: {status: 200, json: {/state: submitted}}
      - id: inspect
        product: breg
        as: editor
        method: GET
        path: "/v1/proposals/{{proposal}}"
        expect: {status: 200, json: {/state: applied}}
        poll: {maximumWaitMilliseconds: 10000, pollIntervalMilliseconds: 500}
```

Starting the Proposal creates a draft that is the caller's turn to work on, and the scenario
expects `state: draft`. Submitting it freezes the inputs. Because no review is required, the
registry schedules the application itself, after its answer to the submit. The last step reads the
Proposal until its state is `applied`.

## Run the scenarios

Check the plan and start a new run:

```sh
rstack dev check .
rstack dev start . --ttl 4h | tee dev-run.txt
```

```text test-expect
Development plan is valid
0 errors, 0 warnings in 1 file
Run <run-id> ready
  Development data is kept after stop in <data-directory>; start this project with --clean to clear it.
  breg http://127.0.0.1:<port>
  Runtime config breg <runtime-config>
  Scenario directory-contact skipped
  Scenario update-contact-email passed
  Scenario register-contact passed
  Logs <logs-directory>
  rstack dev token <run-id> --as editor
  rstack dev token <run-id> --as foreign-editor
```

The first scenario was skipped because the kept database already holds its contact, and both new
scenarios passed. Their steps expected the registry's own answers, so the Action's receipt
and the applied Proposal were checked as the scenario ran.

## Read the new contact

List the contacts as `editor`, with a fresh token for the new run:

```sh
RUN="$(awk '$1 == "Run" {print $2}' dev-run.txt)"
BREG_URL="$(awk '$1 == "breg" {print $2}' dev-run.txt)"
EDITOR_HEADERS="$(rstack dev token "$RUN" --as editor | awk '$2 == "headers" {print $3}')"
rstack breg api /v1/records/contacts --url "$BREG_URL" --header @"$EDITOR_HEADERS"
```

The list holds three contacts: the one from the first tutorial, the one the Action changed, and the
one the Proposal created. The registry's record of the Proposal's result looks like this:

```json test-excerpt
{
  "domainData": {
    "email": "registered@example.test",
    "jurisdiction": "zone-a",
    "name": "Registered contact"
  },
  "recordIdentifier": "<record-id>",
  "revisionIdentifier": "1"
}
```

The registry is still running with three contacts. The next tutorial reads and changes these
contacts from Python and Node.

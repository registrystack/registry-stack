If you are evaluating Base Registry Engine, start with a small business directory.
You will create a business record, change its label, try requests the server refuses, and extend
an editable project with a configuration module. The records use two required fields, `code` and
`label`, plus an optional group reference and status;
business registration is the example you supply, not a built-in server type.
An optional final exercise sends a signed webhook to a local receiver.

## Install Base Registry Engine

Install `breg` and `bregctl`, then the Evidence Gateway toolset, because Registry Mint ships in it and
the launcher runs Mint to issue the local access tokens:

```sh
curl -fsSL https://github.com/registrystack/registry-stack/releases/latest/download/breg-install.sh | bash
curl -fsSL https://github.com/registrystack/registry-stack/releases/latest/download/evidencectl-install.sh | bash
bregctl --version
mint --version
```

Each installer checks its binaries against the release `SHA256SUMS` before anything reaches
`~/.local/bin`, and installs them together or not at all. Keep that directory on your `PATH` in both
terminals, because the launcher finds all three binaries there.

The commands pipe a script from GitHub straight into `bash`, so replace `| bash` with `| less` first if you
would rather read it before it runs. On a tutorial machine that is your own call, but before these binaries
reach a host that serves anyone else, check them against the signed `SHA256SUMS` chain described in
[OpenSSF and release trust](../../security/openssf-evidence/), or follow
[release verification](https://github.com/registrystack/registry-stack/blob/v0.26.1/release/VERIFY.md)
and rerun the installer with `BREG_ASSET_DIR` pointing at the verified directory.

## Read the first record

In the second terminal, save the address and prepare an authorization header file:

```sh
registry_run="$PWD/products/breg/quickstart/.run"
registry_url=$(cat "$registry_run/breg-origin")
umask 077
mkdir tutorial-work
sed 's/^/Authorization: Bearer /' "$registry_run/secrets/operator-token" \
  > tutorial-work/authorization.header
```

The header file contains a token and is readable only by your user.
Keep it out of version control and support messages.
If a request returns `401` after a pause, [renew the token](#renew-an-expired-token) and retry.

Read the records using the `operator` access profile:

```sh
curl --silent --show-error --fail-with-body \
  --header @tutorial-work/authorization.header \
  "$registry_url/v1/records/records?accessProfile=operator" | python3 -m json.tool
```

The `items` array contains one record. Its `data.domainData` object holds the configured fields:

```json
{
  "code": "QS-001",
  "group": null,
  "label": "Quickstart example record",
  "status": null
}
```

The launcher set only `code` and `label`. `group` and `status` are optional fields of the same
entity, so they read as `null` until a record supplies them.

Beside it, `data.recordIdentifier` and `data.revisionIdentifier` identify the record and its
version, and the response's `meta` object names the registry, dataset, and entity type.

`/v1/records/` is the API prefix; the second `records` comes from the project's `route: records`.
The `operator` profile permits these reads when the token has the required scope and purpose.

Try the same request without the header:

```sh
curl --silent --show-error \
  --output tutorial-work/problem.json --write-out 'HTTP %{http_code}\n' \
  "$registry_url/v1/records/records?accessProfile=operator"
```

```text
HTTP 404
```

Open `tutorial-work/problem.json`: its code is `resource.not_found`.
BReg conceals this protected route from an unauthenticated caller.
Naming the profile did not grant access.
The refused requests in this tutorial omit `--fail-with-body` so you can inspect their HTTP status.

## Create a record

Create the business record and save the response:

```sh
curl --silent --show-error --fail-with-body \
  --header @tutorial-work/authorization.header \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: tutorial-create-1' \
  --data '{"data":{"code":"DEMO-002","label":"North Quay Engineering"}}' \
  --output tutorial-work/created.json --write-out 'HTTP %{http_code}\n' \
  "$registry_url/v1/records/records?accessProfile=operator"
```

```text
HTTP 201
```

Read the response:

```sh
python3 -m json.tool tutorial-work/created.json
```

The server generates the identifier, shown as `<record-id>`:

```json
{
  "data": {
    "recordIdentifier": "<record-id>",
    "revisionIdentifier": "1",
    "snapshot": "<snapshot-token>",
    "domainData": {
      "code": "DEMO-002",
      "group": null,
      "label": "North Quay Engineering",
      "status": null
    }
  },
  "meta": {
    "registryIdentifier": "generic-registry",
    "datasetIdentifier": "generic-registry",
    "entityTypeIdentifier": "record"
  }
}
```

`data.snapshot` only appears on create, patch, and tombstone responses. It is an opaque
token for a later `:snapshot` read, described in the
[Base Registry Engine API](../../reference/breg-api/) reference.

Run the create command again unchanged, then read the response again.
You get `201` with the same identifier and revision, not a second record.
`Idempotency-Key` identifies a single write so a client can retry after losing a response.
Use a different key for a different write.

## Choose which fields to read

Ask for labels only:

```sh
curl --silent --show-error --fail-with-body \
  --header @tutorial-work/authorization.header --get \
  --data-urlencode 'accessProfile=operator' \
  --data-urlencode '$select=label' \
  --data-urlencode '$top=10' \
  "$registry_url/v1/records/records" | python3 -m json.tool
```

Each item's `domainData` now contains only `label`. The identifiers stay in the envelope:
`$select` names configured fields only and refuses `recordIdentifier`.
Change `$select=label` to `$select=code,label` and repeat the request to restore both fields.
Single quotes prevent the shell from expanding `$select` and `$top`.

Reading a field does not necessarily permit filtering by it. Try a filter on `label`:

```sh
curl --silent --show-error \
  --header @tutorial-work/authorization.header --get \
  --data-urlencode 'accessProfile=operator' \
  --data-urlencode "\$filter=label eq 'North Quay Engineering'" \
  --output tutorial-work/problem.json --write-out 'HTTP %{http_code}\n' \
  "$registry_url/v1/records/records"
```

```text
HTTP 400
```

The problem code is `query.invalid`.
Open `products/breg/quickstart/.run/project/registry.yaml` in your editor.
The operator grant lists `label` under `readableFields` and `writableFields`, but its
`filterableFields` names only `code` and `status`. Each list is a separate permission.
Repeat the request with `code` in place of `label` and it returns the record you created.

## Update the record

Read the created record and save its HTTP headers:

```sh
record_id=$(python3 -c 'import json; print(json.load(open("tutorial-work/created.json"))["data"]["recordIdentifier"])')
curl --silent --show-error --fail-with-body \
  --header @tutorial-work/authorization.header \
  --dump-header tutorial-work/record.headers \
  "$registry_url/v1/records/records/$record_id?accessProfile=operator" | python3 -m json.tool
```

The response still shows `"revisionIdentifier": "1"`.
Its `ETag` header identifies the version you read. Save the exact value, including its quotes:

```sh
record_etag=$(awk 'tolower($1) == "etag:" {print $2}' tutorial-work/record.headers | tr -d '\r')
```

Change the label with JSON Patch. `If-Match` prevents the update if the record has changed since your read:

```sh
curl --silent --show-error --fail-with-body \
  --header @tutorial-work/authorization.header \
  --header 'Content-Type: application/json-patch+json' \
  --header 'Idempotency-Key: tutorial-patch-1' \
  --header "If-Match: $record_etag" \
  --request PATCH \
  --data '[{"op":"replace","path":"/data/label","value":"North Quay Engineering Ltd"}]' \
  "$registry_url/v1/records/records/$record_id?accessProfile=operator" | python3 -m json.tool
```

The response has the same identifier, `"revisionIdentifier": "2"`, and label `North Quay Engineering Ltd`.
Patch paths address the object you send at creation, so `/data/label` names the label; the
response nests stored fields under `data.domainData`, which is not a patch target.
Try a different update while still using the old ETag:

```sh
curl --silent --show-error \
  --header @tutorial-work/authorization.header \
  --header 'Content-Type: application/json-patch+json' \
  --header 'Idempotency-Key: tutorial-patch-2' \
  --header "If-Match: $record_etag" \
  --request PATCH \
  --data '[{"op":"replace","path":"/data/label","value":"North Quay Engineering Group Ltd"}]' \
  --output tutorial-work/problem.json --write-out 'HTTP %{http_code}\n' \
  "$registry_url/v1/records/records/$record_id?accessProfile=operator"
```

```text
HTTP 412
```

The problem code is `precondition.failed`; the label remains `North Quay Engineering Ltd`.
In an application, fetch the current record and let the user reconcile the change before retrying.
A new idempotency key does not bypass the version check.

## Try an invalid record

Omit the required `code` field:

```sh
curl --silent --show-error \
  --header @tutorial-work/authorization.header \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: tutorial-missing-code' \
  --data '{"data":{"label":"South Harbour Logistics"}}' \
  --output tutorial-work/problem.json --write-out 'HTTP %{http_code}\n' \
  "$registry_url/v1/records/records?accessProfile=operator"
```

```text
HTTP 400
```

The problem code is `request.invalid`; no record was created.
In the project's `registry.yaml`, find `required: true` on the `code` field.
The same definition supplies the validation rule and generated request schema.

## Change a field in a module

Create an editable project outside the launcher's disposable directory:

```sh
bregctl init tutorial-work/project
```

The command prints `init succeeded` and writes a working project: `registry.yaml`, one module
under `modules/`, `tests/journeys.yaml`, a `runtime.example.yaml`, and a `README.md` listing them.
It reports one finding, which does not block authoring:

- `access.profile.unrestricted_collection`: the operator profile can list every row. That is
  intended for a registry-wide operator; the project's second profile, `record-reader`, shows the
  claim-bound row restriction that closes it.

Open `tutorial-work/project/modules/record-notes/module.yaml`. The module extends the `record`
entity the project owns:

```yaml
extendEntities:
  - entity: record
    fields:
      - {id: internal-note, type: string, maxLength: 500, classification: internal}
```

A field without `required: true` is optional. Its classification matches the entity's default,
`internal`. A more sensitive value such as `restricted` adds a second finding,
`access.profile.higher_classification`, once a grant exposes the field; it asks you to confirm
the profile's scope and purpose first.

Adding a field to the model does not grant access to it, and no profile lists this one yet.
In `tutorial-work/project/registry.yaml`, add it to the operator grant for `record`, keeping the
indentation:

```yaml
readableFields: [code, label, group, status, internal-note]
writableFields: [code, label, group, status, internal-note]
filterableFields: [code, status]
```

Now change the module itself: raise its `maxLength` to `1000` and its `version` to `0.2.0`.
Re-pin it and check the combined project:

```sh
bregctl project lock tutorial-work/project
bregctl check tutorial-work/project
```

Look for `project lock succeeded`, a `modules` list showing the module as `updated`, and
`check succeeded`. Both commands repeat the one finding.
The `modules` entry in `registry.yaml` records the module's version and content digest, and
`project lock` rewrote both. A stale digest is an error, so rerun `project lock` after every
module edit and review the changed digest with its source.

Inspect the query permissions:

```sh
bregctl explain queries tutorial-work/project
```

The operator's list operation over `record` has `filterable` entries for `code` and `status`,
each with examples such as `$filter=code eq 'example'`, and `internalNote` among its `apiFields`.
This describes your edited project; the running quickstart still uses its original package.

## Generate the API schema

Generate JSON Schema and OpenAPI from the edited project:

```sh
bregctl generate schemas tutorial-work/project --output tutorial-work/schemas
bregctl generate openapi tutorial-work/project --output tutorial-work/api
```

Both commands print `generate succeeded`.
Read the record schema:

```sh
python3 -m json.tool tutorial-work/schemas/generated/schemas/record.schema.json
```

Find `internalNote` under `properties`. An optional field accepts `null`, so the generator wraps
its type in `anyOf`:

```json
{
  "internalNote": {
    "anyOf": [
      {
        "maxLength": 1000,
        "minLength": 0,
        "type": "string"
      },
      {
        "type": "null"
      }
    ]
  }
}
```

The authored `internal-note` becomes `internalNote` in JSON, and the length you raised in the
module reached the schema.
The `required` list still contains only `code` and `label`.
Open `tutorial-work/api/generated/openapi.json` to see the create and PATCH request shapes.
Generated files are outputs: edit YAML and regenerate into a fresh directory to change them.

You have compiled an extension, not installed it into the running database.
Testing and activating a changed package is covered in [deploy and operate a registry](../../operate/breg/).

## Try a webhook (optional)

The demo replaces `products/breg/demo/.run/` on each launch.
Stopping it removes its database. Use synthetic records and keep your own project outside `.run/`.

```sh
products/breg/demo/run.sh --installed --webhook
```

Wait for these lines; other setup output is omitted:

```text
Webhook delivery, retry, dead-letter inspection, and replay passed.
Base Registry Engine business demo is ready.
```

### Inspect the event

In the second terminal, inspect the compiled event:

```sh
webhook_run="$PWD/products/breg/demo/.run"
bregctl explain events "$webhook_run/project"
```

Find `operating-created-v1`. Open
`products/breg/demo/.run/project/modules/business-establishment-summary/module.yaml`
and compare its `events` entry with the report. The list sits under the entity extension:

```yaml
extendEntities:
  - entity: business
    events:
      - id: operating-created-v1
        trigger: created
        projection: [establishment-code, operating-status]
        when:
          kind: fields
          afterEquals:
            operating-status: operating
        webhook:
          destinationId: business-event-receiver
```

The condition selects new operating establishments. The projection sends two fields, not the establishment's name
or opening date. Open `products/breg/demo/.run/runtime.yaml` to find the matching
`eventDestinations.business-event-receiver`: that is where the URL, key reference, and retry limits live.
Do not edit these running deployment files; changes need a checked package and restart.

Preview the request without sending it:

```sh
bregctl --format json webhook sample "$webhook_run/project" \
  --event operating-created-v1
```

The report shows CloudEvents headers and a JSON body. The `values` keys use the authored
`establishment-code` and `operating-status` spellings. Its signature is a placeholder; the running
worker signs actual deliveries with the shared key.

### Cause a delivery

Obtain a fresh token from this demo's Mint client and keep it in an owner-only header file:

```sh
webhook_url=$(cat "$webhook_run/breg-origin")
umask 077
mint token \
  --url "$(cat "$webhook_run/mint-origin")/token" \
  --client-id business-demo \
  --key "$webhook_run/keys/operator/signing-p256-private-jwk" \
  > "$webhook_run/secrets/operator-token" &&
sed 's/^/Authorization: Bearer /' "$webhook_run/secrets/operator-token" \
  > tutorial-work/webhook-authorization.header
```

Success prints nothing. This token lasts five minutes; repeat this command if a later request
returns `401`. Keep the first terminal running so Mint can issue the replacement.
Create another synthetic establishment:

```sh
curl --silent --show-error --fail-with-body \
  --header @tutorial-work/webhook-authorization.header \
  --header 'Content-Type: application/json' \
  --header 'Idempotency-Key: tutorial-establishment-9' \
  --data '{"data":{"establishmentCode":"ESTABLISHMENT-TUTORIAL-009","siteName":"North Quay Annex","establishmentKind":"warehouse","operatingStatus":"operating"}}' \
  --output tutorial-work/establishment.json --write-out 'HTTP %{http_code}\n' \
  "$webhook_url/v1/records/establishments?accessProfile=business-operator"
```

```text
HTTP 201
```

Count the events received:

```sh
python3 -c 'import json,sys; print(len(json.load(open(sys.argv[1]))["events"]))' \
  "$webhook_run/webhook-receiver-state.json"
```

The count reaches `8`. Delivery is asynchronous; if you still see `7`, repeat the count command.
Repeat the same create request with its original idempotency key. It returns the same record;
the event count stays `8`.

### Read delivery history

Open the receiver's metadata report:

```sh
python3 -m json.tool "$webhook_run/webhook-receiver-state.json"
```

`verificationFailures` is `0`. Each event has attempts with a `generation`, `attempt`, and
`accepted` result. Find an automatic retry: the attempt increases within generation `1`.
Then find the replay: its generation increases to `2`, with a different idempotency key.
The report records no establishment values.

Inspect the dead-letter snapshot saved before the launcher's replay:

```sh
python3 -m json.tool "$webhook_run/webhook-list.json"
```

Compare that saved report with the current queue. This CLI command connects to PostgreSQL
directly, so give it the demo's certificate authority (CA) file:

```sh
SSL_CERT_FILE="$webhook_run/tls/ca.pem" bregctl --format json webhook list \
  --runtime-config "$webhook_run/runtime.yaml"
```

Once delivery finishes, the current `deliveries` list is empty.
Successful payloads have been erased; this command lists outstanding or expired work, not
a history of successful deliveries. The receiver's report lets you inspect what happened.

## Troubleshooting

### Renew an expired token

The local token lasts five minutes. While Mint is still running, renew it and replace the header file:

```sh
umask 077
mint token \
  --url "$(cat "$registry_run/mint-origin")/token" \
  --client-id generic-quickstart \
  --key "$registry_run/keys/operator/signing-p256-private-jwk" \
  > "$registry_run/secrets/operator-token" &&
sed 's/^/Authorization: Bearer /' "$registry_run/secrets/operator-token" \
  > tutorial-work/authorization.header
```

Success produces no terminal output. Retry the failed request.
If renewal fails, check that the first terminal is still running and inspect its Mint log.

    crates/registry-mint/src/main.rs. */}

### Other problems

| Symptom | Next move |
| --- | --- |
| A prerequisite is missing or Docker cannot start a container | Install the named tool or start Docker, then rerun the launcher. A rerun replaces the previous disposable run. |
| The launcher stops because `breg`, `bregctl`, or `mint` is not on `PATH` | Add the installers' directory, `~/.local/bin` unless you changed it, to `PATH` in that terminal, or rerun the installer that provides the missing binary. |
| The first run pauses before the ready message | Docker is downloading the PostgreSQL image. Wait for the ready message. |
| A service does not become ready | Inspect `.run/logs/` under the quickstart directory. Do not share tokens, keys, or database URL files. |
| A create request returns `409` with code `idempotency.conflict` | The key was already used with a different body. Reuse the exact body to retry, or choose a new key for a new write. |

If you are evaluating Base Registry Engine (BReg), create a small contact directory,
start it locally, and run a scenario that creates and reads one synthetic contact.
Your project includes explicit clients and jurisdiction boundaries.

## Install Base Registry Engine

Install matching `breg` and `bregctl` binaries. The release installer verifies the
release checksums before installing both binaries into `~/.local/bin`:

```sh test-skip="downloads a release; use matching candidate binaries for a reader run"
curl -fsSL https://github.com/registrystack/registry-stack/releases/latest/download/breg-install.sh | bash
bregctl --version
```

Keep that directory on `PATH`. Review the installer before running it on an
operated host, and pin a reviewed release for deployment.

## Create and inspect your project

```sh
mkdir -p tutorial-work
bregctl init tutorial-work/project
bregctl check tutorial-work/project
bregctl examples list tutorial-work/project
```

Open the generated README and `registry.yaml`. The default `minimal-directory`
project declares the `contact` Record type, its `name`, `email`, and `jurisdiction`
fields, and the `directory-editor` profile. `dev-clients.yaml` declares `editor`
and `foreign-editor` with different jurisdiction claims. The project also includes
journeys, the `contact` scenario and its synthetic input, and a runtime example.
An existing destination is refused; choose a fresh directory to preserve your work.

## Start the registry

:::caution[Keep local data synthetic]
The session retains records in a Docker volume and keys in the owner-only
`.breg/dev/` directory. Keep these values out of version control and support messages.
:::

```sh
bregctl dev start tutorial-work/project
```

The command starts PostgreSQL and the local issuer, tests and packages the project,
activates it, and waits for BReg readiness. Its report identifies service addresses
and private credential paths. A first image download can take longer than a restart.
A failed start retains private diagnostics under `.breg/dev/`; read those before
changing your model. A binary-version mismatch requires matching installations.

## Create and read a contact

```sh
bregctl examples run contact tutorial-work/project
```

The scenario uses the authored `editor` client to create its contact and read that
same record. A repeated run resumes from retained scenario state rather than
blindly creating another contact. The journey fixtures also exercise concealment
from the foreign jurisdiction. Inspect `tests/journeys.yaml` to see the permitted
and refused operations your project tests before activation.

For application integration, obtain caller-filtered metadata and use a matching
[Registry Stack client](../../tutorials/query-breg-client/). The API's stable record
identifiers and revision conditions are separate from the contact's domain fields.

## Stop or remove your local session

```sh
bregctl dev stop tutorial-work/project
```

Stopping retains records, credentials, package, and scenario checkpoints. Restart
with `dev start` to resume. If you edit a retained project incompatibly, the start
refuses rather than silently replacing its data.

:::danger[Remove only disposable data]
Adding `--remove` discards the owned database volume, records, receipts, and
scenario checkpoints. Keep any data you need before running it. Audit files remain.
:::

```sh
bregctl dev stop tutorial-work/project --remove
```

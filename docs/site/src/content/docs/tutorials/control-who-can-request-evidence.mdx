In about fifteen minutes you will register two applications under access profiles of their own,
send the same region request as each, and see one answered and the other refused. You continue in
the project from [Return a governed value](../return-a-governed-value/), with the source and
Evidence Gateway still running.

## See who may ask today

In `first-evidence-assertion/adult-status`, list the clients the project knows:

```sh test-cwd="first-evidence-assertion/adult-status"
evidencectl access client list --format json | jq -c '.entries[]'
```

```text test-expect
{"accessProfiles":["standalone-service"],"id":"example-caller","status":"active"}
{"accessProfiles":["standalone-service"],"id":"tutorial-client","status":"active"}
```

A client is one application's identity. Both hold `standalone-service`, so both may ask every
question that access profile grants. `example-caller`
comes with the project; you added `tutorial-client` in Your first assertion.

## Add two access profiles

Give each new application a profile with one grant. Add these profiles to the end of
`dev-authority.yaml`, at the same indentation as `standalone-service`:

```yaml title="dev-authority.yaml" test-append
  age-checker-service:
    authority: organizational
    actorKind: service
    requesterTags:
    - age-checker-service
    grants:
    - definition: adult-status
      purpose: age-check
      audienceFrom: authenticated-requester
      representations:
      - signed-jws
      subjectBinding: audience-scoped
      subjects:
      - role: subject
        selectorProfile: record-by-id
        valueOrigin: request
  region-router-service:
    authority: organizational
    actorKind: service
    requesterTags:
    - region-router-service
    grants:
    - definition: residence-region
      purpose: residence-check
      audienceFrom: authenticated-requester
      representations:
      - signed-jws
      subjectBinding: audience-scoped
      subjects:
      - role: subject
        selectorProfile: record-by-id
        valueOrigin: request
```

`requesterTags` lists the tags a caller's token must carry to act under the profile. Check that
each grant stays inside its definition's grant ceiling:

```sh
evidencectl check . --target local-target.yaml
```

```text test-excerpt
0 errors, 0 warnings
```

## Register a client for each profile

Evidence Gateway reads profiles and clients only as it starts, and `evidencectl` refuses a client
change while it runs, so stop it first:

```sh
evidencectl dev stop .
```

```text test-expect
Local Evidence stopped
```

Register one client per profile; the local issuer puts each profile's tags in its client's tokens:

```sh
evidencectl access client add age-checker \
  --access-profile age-checker-service \
  --generate-local-key
evidencectl access client add region-router \
  --access-profile region-router-service \
  --generate-local-key
```

```text test-expect
Added client age-checker with access profile age-checker-service.
Added client region-router with access profile region-router-service.
```

Start Evidence Gateway again with the same ports, so it loads the profiles and clients:

```sh
evidencectl dev start . \
  --target local-target.yaml \
  --evidence-port 18080 \
  --issuer-port 8082
```

```text test-excerpt
Evidence ready at http://127.0.0.1:18080
```

The source kept running throughout.

{/* Evidence: crates/registry-evidencectl/src/access.rs, require_stopped_or_absent_session, requester_tags;
    crates/registry-evidencectl/src/dev.rs, retain_completed_dev_root. */}

## Ask for a purpose the definition does not declare

`adult-status` declares only the purpose `age-check`. Ask under another:

```sh test-exit="1"
evidencectl request prepare adult-status \
  --client age-checker \
  --purpose residence-check \
  --subject subject:record-id=adult \
  --name adult-wrong-purpose
```

```text test-expect
evidencectl: purpose does not match the active local tutorial definition
```

Preparation refuses it, so nothing reaches Evidence Gateway.

## Send the region request as each client

Preparation checks the request against the project, not the grants, so both succeed:

```sh
evidencectl request prepare residence-region \
  --client region-router \
  --purpose residence-check \
  --subject subject:record-id=adult \
  --name region-by-router
evidencectl request prepare residence-region \
  --client age-checker \
  --purpose residence-check \
  --subject subject:record-id=adult \
  --name region-by-checker
```

Send both; Evidence Gateway applies the grants:

```sh
for name in region-by-router region-by-checker; do
  curl --silent --show-error \
    --config ".evidence/requests/$name/authorization.curl" \
    --request POST \
    --url http://127.0.0.1:18080/v1/evidence \
    --header 'Content-Type: application/json' \
    --header 'Accept: application/jose+json' \
    --data-binary "@.evidence/requests/$name/request.json" \
    --output "$name.response" \
    --write-out "$name HTTP %{http_code}\n"
done
```

```text test-expect
region-by-router HTTP 200
region-by-checker HTTP 403
```

Read the refusal `age-checker` received:

```sh
jq . region-by-checker.response
```

```json test-expect
{
  "type": "https://id.registrystack.org/problems/registry-evidence/evidence/denied",
  "title": "Evidence request is not permitted",
  "status": 403,
  "detail": "the Evidence request is not permitted",
  "code": "evidence.denied",
  "traceId": "<trace-id>"
}
```

`evidence.denied` does not name the missing grant.
[Evidence problems](../../reference/evidence-problems/) lists every code.

Leave the source and Evidence Gateway running; the next tutorial continues with them.

This tutorial joins an application record, a human review, and an email without accepting a
caller-supplied recipient. Coordinator reads registry-owned contact details from Base Registry
Engine (BReg), stores its bounded run state encrypted, sends useful review facts to Casework, waits
durably, then reads BReg again before it asks Messaging to send anything.

## Build the local tools

From the source checkout, build the eight product commands and the trusted input helper. The
repository's pinned Rust toolchain and locked dependency graph select their exact versions. This
uses the ordinary runtime features; the tutorial does not require test-only PostgreSQL support.

```sh
cargo build --locked \
  -p registry-coordinator --example reviewed-notice-input \
  -p registry-breg --features registry-breg/runtime \
  -p registry-bregctl \
  -p registry-casework \
  -p registry-caseworkctl \
  -p registry-messaging \
  -p registry-messagingctl \
  --bins
```

The helper finds these commands under `target/debug`. It uses OpenSSL to create short-lived local
database certificates and Docker to run disposable PostgreSQL and Mailpit containers.

## Start the four products

From a Registry Stack source checkout, start the example-owned session. It uses `bregctl dev` for
the shared local issuer and application registry, packages and applies Casework, Messaging, and
Coordinator through their normal commands, and sends email to the version-pinned Mailpit SMTP
sink. The helper creates only resources recorded under its session directory.

```sh
mkdir -p tutorial-work
python3 products/coordinator/examples/reviewed-notice/session.py start \
  --session-dir tutorial-work/reviewed-notice
```

The helper seeds one application, computes its reviewed projection digest with the maintained Rust
review protocol, discovers the permitted `reviewed-notice` contract, starts with that exact `workflowRevision`, and
waits until Casework owns the decision. It keeps
credentials in owner-only files. Its status contains the Workflow revision, endpoint references,
and file references without secret values.

Standalone Casework review carries an exact expected PolicyBinding. Acceptance and the eventual
result must match its ID, version, and digest, as well as the subject and submission digest.
This workflow creates no BReg Proposal and grants no registry mutation authority.

The producer is trusted to prepare the review subject with the supplied helper. Coordinator checks
the submitted BReg revision before it requests review, but it does not recompute the producer's
projection digest.

```sh
python3 products/coordinator/examples/reviewed-notice/session.py status \
  --session-dir tutorial-work/reviewed-notice \
  > tutorial-work/session-status.json
python3 - <<'PY'
import json
s = json.load(open('tutorial-work/session-status.json'))
print('Session:', s['status'])
print('Application:', s['applicationId'])
print('Run:', s['runId'])
PY
```

Local access tokens expire. If a later request returns `401`, refresh the relevant header file
with `cargo run --locked -p registry-bregctl --bin bregctl -- dev token CLIENT PROJECT`.
Use `staff` for Casework or `coordinator-producer` for Coordinator as `CLIENT`, and the
`ownerProject` path in `tutorial-work/session-status.json` as `PROJECT`. Then repeat the request.

## Inspect the parked run

Read the run through Coordinator's authenticated inspection API. Confirm state `running`, step
`await-review`, and the original `workflowRevision`. This completion wait has not sent a message.
Inspection also exposes its next observation and durable budget without the review correlation data.

```sh
python3 - <<'PY'
import json, urllib.request
s = json.load(open('tutorial-work/session-status.json'))
token = next(line.split(': ', 1)[1].strip() for line in open(s['coordinatorHeaderFile'])
             if line.startswith('Authorization: '))
request = urllib.request.Request(
    f"{s['coordinatorApi']}/v1/runs/{s['runId']}/inspect",
    headers={'Authorization': token},
)
with urllib.request.urlopen(request) as response:
    run = json.load(response)['run']
print('State:', run['state'])
print('Step:', run['step'])
assert run['workflow'] == s['workflow']
assert run['workflowRevision'] == s['workflowRevision']
PY
```

## Read and claim the Casework task

List the open task with the Casework profile and credential the session exported from the shared
issuer. Then read its context. The snapshot contains facts a reviewer can act on, while the
applicant's email stays in BReg.

```sh
python3 - <<'PY'
import json, urllib.request
s = json.load(open('tutorial-work/session-status.json'))
token = next(line.split(': ', 1)[1].strip() for line in open(s['staffHeaderFile'])
             if line.startswith('Authorization: '))
headers = {'Authorization': token, 'Registry-Casework-Profile': s['caseworkProfile']}
request = urllib.request.Request(f"{s['caseworkApi']}/v1/review-tasks?queue=applications&limit=25", headers=headers)
with urllib.request.urlopen(request) as response:
    task = next(item for item in json.load(response)['items'] if item['state'] == 'open')
json.dump(task, open('tutorial-work/review-task.json', 'w'), indent=2)
context_request = urllib.request.Request(f"{s['caseworkApi']}/v1/review-tasks/{task['taskId']}/context", headers=headers)
with urllib.request.urlopen(context_request) as response:
    facts = json.load(response)['context']['snapshot']
print('Applicant:', facts['applicantName'])
print('Program:', facts['benefitProgram'])
print('Requested amount:', facts['requestedAmount'])
PY
```

The printed facts must match the synthetic application. Claim that exact task revision:

```sh
python3 - <<'PY'
import json, urllib.request, uuid
s = json.load(open('tutorial-work/session-status.json'))
t = json.load(open('tutorial-work/review-task.json'))
token = next(line.split(': ', 1)[1].strip() for line in open(s['staffHeaderFile'])
             if line.startswith('Authorization: '))
headers = {
    'Authorization': token,
    'Registry-Casework-Profile': s['caseworkProfile'],
    'If-Match': f'"{t["revision"]}"',
    'Idempotency-Key': str(uuid.uuid4()),
}
request = urllib.request.Request(f"{s['caseworkApi']}/v1/review-tasks/{t['taskId']}/claim", data=b'', method='POST', headers=headers)
with urllib.request.urlopen(request) as response:
    assert response.status == 200
print('Claimed')
PY
```

## Restart Coordinator while it waits

Restart only Coordinator. BReg, Casework, Messaging, PostgreSQL, and Mailpit continue running. The
parked run remains at the same wait after the new worker loads durable state:

```sh
python3 products/coordinator/examples/reviewed-notice/session.py restart-coordinator \
  --session-dir tutorial-work/reviewed-notice \
  > tutorial-work/session-status.json
```

## Approve the application

Read the claimed task again to obtain its current revision, then record the decision:

```sh
python3 - <<'PY'
import json, urllib.request, uuid
s = json.load(open('tutorial-work/session-status.json'))
t = json.load(open('tutorial-work/review-task.json'))
base = f"{s['caseworkApi']}/v1/review-tasks/{t['taskId']}"
token = next(line.split(': ', 1)[1].strip() for line in open(s['staffHeaderFile'])
             if line.startswith('Authorization: '))
common = {'Authorization': token,
          'Registry-Casework-Profile': s['caseworkProfile']}
with urllib.request.urlopen(urllib.request.Request(base, headers=common)) as response:
    current = json.load(response)
body = json.dumps({'decision': {'type': 'approve'}}).encode()
headers = {**common, 'Content-Type': 'application/json',
           'If-Match': f'"{current["revision"]}"', 'Idempotency-Key': str(uuid.uuid4())}
request = urllib.request.Request(base + '/decisions', data=body, method='POST', headers=headers)
with urllib.request.urlopen(request) as response:
    assert response.status == 204
print('Approved')
PY
```

A successful decision prints `Approved`. If the task revision changed, read it again before deciding.

The Casework completion event advances an eligible read on the restarted worker while preserving
the durable observation floor. Coordinator reads the authoritative
result, reads BReg again, verifies the reviewed revision still matches, checks that
`noticeAllowed` is still true, and obtains the recipient from that current record.

## Verify the run and local email

Wait for the run's explicit success outcome:

```sh
python3 - <<'PY'
import json, time, urllib.request
s = json.load(open('tutorial-work/session-status.json'))
token = next(line.split(': ', 1)[1].strip() for line in open(s['coordinatorHeaderFile'])
             if line.startswith('Authorization: '))
headers = {'Authorization': token}
url = f"{s['coordinatorApi']}/v1/runs/{s['runId']}/inspect"
deadline = time.monotonic() + 60
while True:
    with urllib.request.urlopen(urllib.request.Request(url, headers=headers)) as response:
        run = json.load(response)['run']
    if run['state'] != 'running': break
    if time.monotonic() >= deadline: raise SystemExit('run did not settle')
    time.sleep(.2)
print('State:', run['state'])
print('Outcome:', run['outcome'])
assert run['output']['messageId']
PY
```

Confirm `finished` with outcome `notice-accepted` and a message identifier. If the run remains
held, inspect its failure code and wait budget before any retry. Keep the original start identity,
key, revision, and input; a fresh key creates fresh work.

Finally, inspect what the local SMTP server received. SMTP acceptance is the available receipt in
this setup; SMTP does not report later recipient delivery back to Messaging.

```sh
python3 - <<'PY'
import json, time, urllib.request
s = json.load(open('tutorial-work/session-status.json'))
deadline = time.monotonic() + 30
while True:
    with urllib.request.urlopen(s['mailpit'] + '/api/v1/messages') as response:
        messages = json.load(response)['messages']
    if messages: break
    if time.monotonic() >= deadline: raise SystemExit('Mailpit received no message')
    time.sleep(.2)
assert len(messages) == 1
message = messages[0]
print('Messages:', len(messages))
print('To:', message['To'][0]['Address'])
print('Subject:', message['Subject'])
PY
```

Confirm exactly one message addressed to `amina@example.invalid` with subject `Application approved`.
No message or a held run requires inspection of the private session logs; do not infer delivery
from Coordinator acceptance alone.

Changing the application revision after submission routes to `application-changed`. Removing
`noticeAllowed` routes to `notice-permission-gone`. A rejection routes to `review-rejected`. None
of those outcomes calls Messaging.

Start with a three-row public works workbook. By the end of this tutorial, you
will have a protected records API in Registry Relay and a separate evidence API
in Registry Notary. You will make one denied records request, read one authorized
record, and verify two facts without receiving that record.

<QuickstartMeta
  outcome="A protected local API over a spreadsheet, plus minimized evidence answers from Relay and Notary."
  time="About 20 minutes after Registryctl and Docker are installed"
  level="Local development with a contained spreadsheet"
  prerequisites={['A released Registryctl 1.0 installation', 'Docker Engine', 'Docker Compose 2.35.0 or later', 'curl', 'A spreadsheet application', 'A shell and a text editor'] }
/>

The workbook and credentials in this tutorial are synthetic and disposable.
Do not replace them with personal data or production credentials during the
first run.

## Before you start

Choose an exact published 1.x tag from the
[Registry Stack releases](https://github.com/registrystack/registry-stack/releases), then
download its installer:

```sh
tag="v<major>.<minor>.<patch>"
installer="registryctl-${tag}-install.sh"
curl --proto '=https' --tlsv1.2 --fail --location \
  --output "$installer" \
  "https://github.com/registrystack/registry-stack/releases/download/${tag}/${installer}"
```

This quick installation path trusts GitHub and TLS. The installer verifies the
Registryctl binary and its matching signed release lock against the release
checksums. When your acceptance process requires publisher authentication,
follow `release/VERIFY.md` from the same tag before running the installer.

```sh
bash "$installer"
```

A successful 1.0 installer ends with the installed binary and signed release
lock paths, followed by the spreadsheet `Try it` commands. If your shell cannot
find `registryctl`, add the printed binary directory to `PATH` before
continuing.

Confirm that Registryctl and Docker Compose are available:

```sh
registryctl --version
docker compose version
```

The first line has the shape `registryctl 1.x.y`. Compose reports
`Docker Compose version v<version>` and must report 2.35.0 or later. Start in a
directory that is not inside another Registry Stack project.

## Create the spreadsheet registry

Initialize the released spreadsheet starter and enter the project:

```sh
registryctl init my-first-registry --template spreadsheet
cd my-first-registry
```

Registryctl copies the project and workbook from the installed release. It does
not fetch a remote template.

```text
Created Registry Stack project fictional-public-works-registry in my-first-registry.
Next: cd my-first-registry && registryctl test
```

Open `data/public_works_projects.xlsx` and select the `Projects` worksheet. It
contains three synthetic records:

| `project_id` | `district_code` | `sector` | `status` |
| --- | --- | --- | --- |
| `pw_001` | `north-01` | `water` | `active` |
| `PW-002` | `central-02` | `health` | `planned` |
| `PW-003` | `coastal-03` | `transport` | `active` |

Keep the identifiers' case and punctuation. The first live request reads
`pw_001`. The follow-on evidence tutorial uses `PW-002`.

## Test the starter

Run the maintained offline fixtures before starting containers:

```sh
registryctl test
```

```text
Registry Stack test: passed for fictional-public-works-registry.
Fixtures: 8.
Next: registryctl dev
```

This checks active, planned, and missing-record behavior, the derived
authorization-before-source cases, and the exact one-field snapshot output
contract. It does not start Docker, resolve a secret, or contact a source.

## Start the local registry

Start the disposable Registry Relay and Registry Notary runtime:

```sh
registryctl dev --detach
```

Registryctl validates the project, mounts the contained workbook read-only,
creates development-only trust and isolated credentials, and starts released
digest-locked images on loopback HTTP. Its
output identifies both APIs and prints ready-to-run commands with owner-only
curl configuration files:

```text
Relay API: http://127.0.0.1:4242
Evidence API: http://127.0.0.1:4243
Records denied request: curl --config '/<absolute-project-path>/.registry-stack/dev/local/<runtime-id>/credentials/records-denied.curl'
Records request: curl --config '/<absolute-project-path>/.registry-stack/dev/local/<runtime-id>/credentials/records-request.curl'
Evidence request: curl --config '/<absolute-project-path>/.registry-stack/dev/local/<runtime-id>/credentials/request.curl'
```

Your absolute path and runtime identifier will differ. Copy commands from your
own output rather than the example above. The curl configurations keep
disposable credentials out of the command line and your shell environment.
The generated runtime publishes only the two application ports on host
loopback. Put an operator-owned reverse proxy or ingress in front when adapting
the products to a shared environment that requires TLS.

### Make one denied records request

Copy the complete command after `Records denied request:` and run it unchanged.
It sends no credential. Relay responds with `401 Unauthorized` and a
`problem+json` body whose stable code is `auth.missing_credential`.

```json
{
  "status": 401,
  "code": "auth.missing_credential"
}
```

The displayed body is abridged because the actual response also contains a
generated request identifier. The result proves that the registry is running
and the records route is protected.

### Read one protected spreadsheet record

Copy the complete command after `Records request:` and run it unchanged. The
generated caller is bound to `pw_001`, has only the starter's records scopes,
and supplies the declared case-management purpose.

Relay returns the four fields in the authored projection:

```json
{
  "project_id": "pw_001",
  "district_code": "north-01",
  "sector": "water",
  "status": "active"
}
```

This is the protected records API. The caller can read its authorized record,
but it cannot choose a different `project_id` by changing the record identifier
in the URL.
Relay derives the required filter from the authenticated principal.

### Request minimized evidence

Copy the complete command after `Evidence request:` and run it unchanged. This
request goes to Registry Notary. Notary authorizes the evidence request, then
asks the private consultation Relay for only the source value needed to decide
the two claims.

The response contains generated identifiers, timestamps, and provenance. These
are the relevant fields:

```json
{
  "results": [
    {
      "claim_id": "project-record-exists",
      "value": true,
      "satisfied": true,
      "disclosure": "predicate"
    },
    {
      "claim_id": "project-status-accepted",
      "value": true,
      "satisfied": true,
      "disclosure": "predicate"
    }
  ]
}
```

This is an abridged response. Both predicates are true because `pw_001` exists
and its status is `active`. The evidence response does not contain `north-01`,
`water`, `active`, or the workbook row. Relay owns the bounded source read;
Notary owns claim evaluation and disclosure.

## Run the maintained smoke check

Run the development checks:

```sh
registryctl dev smoke
```

```text
Development smoke: passed.
  unauthorized: status=denied; passed=true; token_counter_delta=unobserved; source_counter_delta=unobserved; minimized_claim_ids=none
  authorized: status=authorized; passed=true; token_counter_delta=unobserved; source_counter_delta=unobserved; minimized_claim_ids=project-record-exists,project-status-accepted
```

The first scenario proves that the live evidence route denies the unauthenticated
request. The second performs the authorized lookup and reports only the two
configured claim identifiers. A local workbook has no request counter, so the
runtime honestly reports those effects as `unobserved`. The derived offline
authorization-before-source fixture still verifies the zero-source-effect
denial invariant in Relay. The direct records requests above and this evidence
smoke check exercise different public surfaces.

## Inspect the contract you own

Now inspect the authored files behind the behavior you observed. Do not
edit files under `.registry-stack/`; Registryctl regenerates that disposable
state from the authored project.

### Follow the workbook into Relay

Open `environments/local.yaml`. The binding names the workbook, sheet, header,
and exact column mapping:

```yaml
entities:
  projects:
    provider:
      type: xlsx
      project_file: data/public_works_projects.xlsx
      path: /var/lib/registry/public_works_projects.xlsx
      sheet: Projects
      header_row: 1
    columns:
      project_id: project_id
      district_code: district_code
      sector: sector
      status: status
```

`project_file` is what Registryctl validates. `path` is the read-only container
location generated for Relay. `entities/projects.yaml` separately defines the
record schema, primary key, and materialization limits.

### Find the records policy

Open `registry-stack.yaml` and find `projects-records`:

```yaml
api:
  scopes:
    metadata: projects:metadata
    rows: projects:rows
    aggregate: projects:aggregate
    evidence_verification: projects:evidence_verification
  purposes: [public-works-case-management]
  projection: [project_id, district_code, sector, status]
  pagination: { default_limit: 50, max_limit: 100 }
  filters: { project_id: [eq] }
  required_principal_filters: [project_id]
```

These are the four fields returned by your records request. Scope, purpose, and
principal-bound filtering are independent gates. The generated development
caller is convenient, but it does not weaken or bypass the authored policy.

### Find the evidence policy

In the same file, find `public-works-verification`:

```yaml
purpose: public-works-case-management
access: { scopes: ["evidence:projects:read"] }
consultations:
  project:
    integration: project-record-snapshot
    input: { project_id: request.target.identifiers.project_id }
claims:
  project-record-exists:
    cel: project.matched
    disclosure: predicate
  project-status-accepted:
    cel: 'project.matched && project.status == "active"'
    disclosure: predicate
```

`integrations/project-record-snapshot/integration.yaml` allows the consultation
Relay to expose only `status` to Notary. Both claims use predicate disclosure,
so the evidence caller receives boolean decisions instead of that status or the
record.

Inspect the focused offline trace when you want to see those boundaries without
running the stack:

```sh
registryctl test \
  --integration project-record-snapshot \
  --fixture match \
  --trace
```

```text
Registry Stack test: passed for fictional-public-works-registry.
Fixtures: 3.
  PASS project-record-snapshot.match
    inputs: project_id
    calls: call=1 operation=snapshot method=GET path=/snapshot query=[] headers=[] body=none
    outputs: status
    claims: project-record-exists, project-status-accepted
    outcome: match
  PASS project-record-snapshot.match::derived/request_to_consultation_binding
    inputs: project_id
    calls: notary-relay-consultation
    claims: project-record-exists, project-status-accepted
    source access: true
  PASS project-record-snapshot.match::derived/authorization_before_source
    inputs: project_id
    expected error: authorization.denied
    source access: false
Next: registryctl dev
```

## Stop the disposable runtime

Stop the bound runtime and remove its generated development trust, credentials,
and state:

```sh
registryctl dev down
```

```text
Stopped and removed the bound disposable development runtime.
```

The authored project and workbook remain.

## Build the review inputs

Review directly authored non-secret values, then build deterministic unsigned
inputs for the three product lanes:

```sh
registryctl check --explain --show-authored-values
registryctl build
```

Confirm the four-field records projection, the case-management purpose, the
principal-bound `project_id`, the single `status` consultation output, and the
two predicate claims. The build ends with:

```text
Built unsigned signing inputs for relay-public, relay-consultation, notary.
Build output: .registry-stack/build/local
Next: bind an operator-managed source in a separate governed environment and rerun registryctl test; do not sign this file-backed build
```

The public Relay, private consultation Relay, and Notary remain separate review
and ownership lanes. Building does not approve, sign, or deploy them. Registry
Stack 1.0 runs a project-local workbook only in the disposable development
runtime. It does not package that workbook for a governed deployment.

## What you built

You turned a spreadsheet into two deliberately different APIs:

- The public Relay refused an anonymous call and returned one principal-bound,
  four-field record to an authorized caller.
- The consultation Relay exposed only `status` to Notary after authorization.
- Notary returned two predicate decisions without returning `status` or the
  spreadsheet row.
- Disposable credentials remained isolated in owner-only files instead of
  your shell environment or generated review inputs.

## Troubleshooting

| Symptom | Cause | Resolution |
| --- | --- | --- |
| `registryctl init` reports a non-empty destination | Registryctl never merges a starter into an existing directory. | Choose an absent or empty directory. |
| `registryctl test` reports workbook or fixture diagnostics | An authored file no longer matches the maintained starter. | Restore the starter for the first run, or complete the spreadsheet adaptation before testing again. |
| `registryctl dev` reports that Docker is unavailable | Docker Engine is not running or Compose is older than 2.35.0. | Start Docker and confirm `docker compose version`. |
| A development port is already in use | Another process owns a required loopback port. | Stop that process, then run `registryctl dev` again. |
| A printed request reports that its config file is missing | The disposable runtime was stopped or replaced after Registryctl printed the command. | Start the runtime again and copy the newly printed command. |
| A generated artifact integrity check fails | A file under `.registry-stack/` was edited or replaced. | Stop the disposable runtime and rebuild from the authored project. |

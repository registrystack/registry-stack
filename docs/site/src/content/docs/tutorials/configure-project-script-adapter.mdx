Use this guide to adapt a project created with the HTTP template when its source requires OAuth
2.0 client credentials and a reviewed Rhai script must normalize the response.

## When to use this

Use Rhai when a fixed HTTP request plus JSON-pointer output mapping cannot express the source
contract.
Examples include explicit match and no-match branches, identifier checks, bounded pagination,
and construction of a smaller output object.

Keep the ordinary HTTP capability when fixed mapping is sufficient.
Rhai does not grant another destination, credential, request, or output authority.

OAuth-backed Rhai is an adaptation of the `http` starter, not another template.

## Before you start

Create the HTTP starter and confirm its three fixtures pass:

```sh
registryctl init my-registry --template http
cd my-registry
registryctl test
```

Keep the passing result as the comparison point for the adaptation.
You also need a reviewed non-production source contract and wholly synthetic observations for
each accepted and rejected result.
Review [Configure OAuth client credentials](../../configure/oauth-client-credentials/) for the
token request, response profile, private binding, and rotation contract before adding Rhai.

## Declare the OAuth and script boundary

Replace `integrations/person-record/integration.yaml` with this bounded contract:

```yaml
version: 1
id: person-record
revision: 1

source:
  product: fictional-civic-registry
  versions:
    unverified: [events-api-v1]
  auth:
    type: oauth2_client_credentials
    request: form
    response_profile: oauth2_bearer
    scope: records.read
    audience: https://registry.invalid
    refresh_skew: 20s
  allow:
    - method: GET
      path: /v1/people/*
  response:
    format: json
    max_bytes: 256KiB

input:
  person_id:
    role: selector
    type: string
    maxLength: 64

capability:
  script:
    file: adapter.rhai

outputs:
  active: { type: boolean }

limits:
  calls: 1
  source_bytes: 256KiB
  request_bytes: 4KiB
  deadline: 15s
```

`oauth2_bearer` accepts a bounded `access_token`, exact `token_type: Bearer`, and integer
`expires_in`.
Relay bounds token caching by that expiry.

Use `oauth2_bearer_no_expiry` only when the reviewed source response omits expiry.
That profile rejects `expires_in` and refresh controls, disables caching, and performs a fresh
bounded token exchange for every authorized execution.

Neither profile exposes the client secret, token, or token response to Rhai.
Project authoring's hard ceilings are 1 MiB per request, 16 MiB from the source, and 20 seconds.
Keep the integration's actual limits smaller when the reviewed source contract permits it.

## Bind endpoint and secret references

Replace the `person-record` source binding in `environments/local.yaml`:

```yaml
integrations:
  person-record:
    source:
      origin: https://registry.invalid
      credential:
        client_id: { secret: REGISTRY_CLIENT_ID }
        client_secret: { secret: REGISTRY_CLIENT_SECRET }
        generation: 1
      oauth:
        origin: https://identity.invalid
        path: /oauth/token
        generation: 1
```

Keep the remaining environment fields created by the HTTP template.
The environment contains secret references, not secret values.
An operator supplies the referenced values to the consultation Relay for governed deployment.

Relay owns token acquisition, strict token-response decoding, cache policy, the authorization
header, redirects, Transport Layer Security, and the source call.

## Write the adapter

Create `integrations/person-record/adapter.rhai`:

```rhai
fn consult(ctx) {
    let target = source.path(
        "/v1/people/{person_id}",
        #{ person_id: ctx.input.person_id }
    );
    let response = source.get(target, #{ query: #{} });

    if response.status == 404 {
        return result.no_match();
    }
    if response.status != 200 {
        return result.fail(failure.source_rejected);
    }
    if response.body.person_id != ctx.input.person_id {
        return result.fail(failure.subject_mismatch);
    }

    result.match(#{ active: response.body.active })
}
```

The script receives typed consultation input and a bounded source response.
It can return only a match, no match, ambiguity, or a closed failure.
For a match, it must return the complete declared output map.

Rhai has no ambient network, filesystem, environment, subprocess, clock, random, credential, or
production logging access.
Each `source.*` call returns to Relay for authorization against the authored method, path, and
remaining budgets.

## Update the synthetic match fixture

Replace the interactions in
`integrations/person-record/fixtures/active.yaml` with an OAuth exchange and one source call:

```yaml
interactions:
  - expect:
      method: POST
      path: /oauth/token
      body: { grant_type: client_credentials }
    respond:
      status: 200
      headers: { Content-Type: application/json }
      body:
        access_token: SYNTHETIC_FIXTURE_TOKEN
        token_type: Bearer
        expires_in: 300
  - expect:
      method: GET
      path: /v1/people/AB-123456
    respond:
      status: 200
      body:
        person_id: AB-123456
        active: true
expect:
  outcome: match
  outputs: { active: true }
  claims: { person-record-exists: true, person-active: true }
```

Keep the request, input, name, and classification fields from the starter fixture.
Adapt the no-match and ambiguity fixtures to include the same valid token exchange before their
source result.

Add wholly synthetic fixtures for source rejection, subject mismatch, malformed OAuth response,
malformed source response, timeout, and oversize response.
The complete fixture set must also prove that authorization denial causes neither a token call
nor a source call.

## Verify offline

Run the focused trace, then the complete fixture set:

```sh
registryctl test \
  --integration person-record \
  --fixture active-person \
  --trace
registryctl test
```

The focused trace may show the synthetic token request and source observation.
The complete test passes only when every declared and derived security case agrees with the
authored contract.
Fixture success remains synthetic evidence, not live-source interoperability evidence.

## Verify the development path

Start the same generic development runtime used by the HTTP starter:

```sh
registryctl dev --detach
registryctl dev smoke
registryctl dev down
```

For this OAuth scenario, the denial report has zero token and source calls.
The authorized report has one token exchange, one source call, and the minimized claim
identifiers `person-active` and `person-record-exists`.
Retained output contains no token, credential, or source-returned value.

## Review and rebuild

Review the redacted plan and regenerate the unsigned lane inputs:

```sh
registryctl check --explain
registryctl build
```

Confirm that the evidence service still has exactly one Relay consultation.
The consultation Relay owns the OAuth destination, credential consumers, Rhai script, source
authority, and minimized `active` output.
Notary owns claims and disclosure, and receives no OAuth credential or source origin.

For the exact maintained execution of the no-expiry branch, use the
[synthetic OpenCRVS Events API-shaped search](../verify-opencrvs-claims/).
Its public overlay is the project that the documentation gate executes.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| The OAuth fixture rejects a success body | The response has an unknown field, wrong token type, missing required expiry, or invalid expiry. | Match the selected closed response profile. |
| A source call fails before dispatch | The method, path, target, query, or budget is outside authored authority. | Correct the script or narrowly update the reviewed allow policy. |
| A match result is rejected | The script omitted an output or returned the wrong type. | Return the complete declared output map. |
| A token or secret appears in Rhai | The credential boundary has been crossed. | Stop testing and report the failure through the repository security process. |
| The live source differs from fixtures | Synthetic contract evidence does not establish live interoperability. | Record a separate source-owner compatibility review before changing a version from `unverified` to `tested`. |

Use a reviewed non-personal workbook after the
[spreadsheet first run](../publish-spreadsheet-secured-registry-api/) works.
Registryctl validates the workbook against explicit authored schema, access,
and consultation decisions.

## When to use this

Use this path when the institution starts from an XLSX workbook or a reviewed
XLSX derivative of another source.
The 1.0 path deliberately supports a regular table with one header row.
It does not infer relationships, formulas, access policy, or the meaning of a
record.

Start with the maintained four-column shape to get a working result:

| Required header | Purpose |
| --- | --- |
| `project_id` | Stable, unique record key |
| `district_code` | Example protected registry field |
| `sector` | Example protected registry field |
| `status` | Bounded input to the sample consultation output |

For a different schema, edit the entity definition, workbook mapping, records
projection, snapshot output, and fixtures together.
The [project configuration reference](../../reference/project-configuration/)
lists those fields.

## Before you start

Prepare a reviewed derivative with:

- One worksheet named `Projects`
- One header row containing exactly the four required headers
- A non-empty, unique `project_id` for every row
- Static values with no formulas or external workbook links
- No personal data for local development

Review the
[XLSX readiness contract](../../products/registry-relay/xlsx-readiness-contract/)
before adapting a larger or less regular workbook.

## Create a clean spreadsheet project

Create a new project rather than modifying generated files:

```sh
registryctl init institution-registry --template spreadsheet
cd institution-registry
```

Registryctl reports the created project and the next `registryctl test`
action.

Copy the reviewed workbook over the sample:

```sh
cp /path/to/reviewed-registry.xlsx data/public_works_projects.xlsx
```

The command prints nothing when it succeeds.
Registryctl reads the workbook but never writes its cells.

## Record the source revision

Open `environments/local.yaml`.
The starter contains:

```yaml
    source_revision: synthetic-public-works-v1
    generation: "1"
```

Replace it with the reviewed source revision and generation:

```yaml
    source_revision: reviewed-registry-2026-07-31
    generation: "1"
```

Use an institution-owned immutable revision identifier.
Increment `generation` only when the operator accepts a replacement source
generation.

The same file binds:

```yaml
    provider:
      type: xlsx
      project_file: data/public_works_projects.xlsx
      path: /var/lib/registry/public_works_projects.xlsx
      sheet: Projects
      header_row: 1
    columns:
      project_id: project_id
      district_code: district_code
      sector: sector
      status: status
```

`project_file` stays inside the project and names the human-owned workbook.
`path` is the read-only location generated for Registry Relay.
Do not point either field outside the project or through a symbolic link.

## Review what Relay can return

Open `registry-stack.yaml` and review the `projects-records` service.
The sample projection is:

```yaml
      projection: [project_id, district_code, sector, status]
      filters: { project_id: [eq] }
      required_principal_filters: [project_id]
```

Remove every field that callers do not need.
A workbook field is not exposed merely because it exists in the entity schema.
It must also appear in this projection.

The required `project_id` filter is bound to authenticated caller identity.
A caller-supplied query value does not replace that binding.

## Review the consultation meaning

The same project declares one consultation service over the same snapshot:

```yaml
  public-works-verification:
    kind: consultation_api
    version: 1
    purpose: public-works-case-management
    legal_basis: public-service-delivery
    consent: not_required
    consultations:
      project:
        integration: project-record-snapshot
        input: { project_id: request.target.identifiers.project_id }
```

Keep `public-works-verification` only when this bounded registry lookup has the
meaning your institution intends.
Rename the service and its `purpose` when `public-works-case-management` does
not express the reviewed policy.
The consultation returns the integration's declared minimized outputs. It is
not a legal eligibility decision.

Update the synthetic fixtures under
`integrations/project-record-snapshot/fixtures/` whenever the consultation
meaning changes.
Fixtures contain invented observations and expected results.
Do not copy whole workbook rows into them. The selected smoke fixture below
uses only one reviewed identifier and the `status` value the consultation
returns.

## Select one reviewed smoke row

The local runtime needs one non-sensitive row that you are allowed to exercise.
For a concrete checkpoint, suppose the reviewed workbook contains this row:

| `project_id` | `district_code` | `sector` | `status` |
| --- | --- | --- | --- |
| `institution_001` | `north-01` | `water` | `active` |

Use the actual identifier and evidence-relevant values from your reviewed test
row in place of `institution_001` and `active`. Do not select a personal or
production record merely to make the smoke check pass.

In `environments/local.yaml`, replace the starter's local caller selection:

```yaml
  local_api_keys:
    match_principal: pw_001
    no_match_principal: registryctl_local_no_match
    scopes: [projects:metadata, projects:rows]
```

with the reviewed row identifier:

```yaml
  local_api_keys:
    match_principal: institution_001
    no_match_principal: registryctl_local_no_match
    scopes: [projects:metadata, projects:rows]
```

Then replace
`integrations/project-record-snapshot/fixtures/match.yaml`:

```yaml
name: match
classification: synthetic
input: { project_id: pw_001 }
interactions:
  - expect: { method: GET, path: /snapshot }
    respond: { status: 200, body: { status: active } }
expect:
  outcome: match
  outputs: { status: active }
```

with a synthetic observation matching only the selector and the outcome you
intend to exercise:

```yaml
name: match
classification: synthetic
input: { project_id: institution_001 }
interactions:
  - expect: { method: GET, path: /snapshot }
    respond: { status: 200, body: { status: active } }
expect:
  outcome: match
  outputs: { status: active }
```

Keep `development.default_fixture: match`. The fixture remains synthetic; the
local snapshot smoke check separately confirms that the selected reviewed row
is reachable through Relay and that the consultation returns only the declared
`status` output.

## Validate the workbook and authored policy

Run the offline fixture suite:

```sh
registryctl test
```

A passing unchanged fixture set reports:

```text
Registry Stack test: passed for fictional-public-works-registry.
Fixtures: 3.
Next: registryctl dev
```

This proves the authored consultation semantics against synthetic
observations. It does not prove facts about the workbook.

Validate the actual workbook mapping, every selected row, the records policy,
and the consultation configuration:

```sh
registryctl check --explain
```

A valid project begins with:

```text
Registry Stack check: valid for fictional-public-works-registry.
Fixtures: 3.
Explanation: registry.project.explanation.v1
```

The explanation redacts workbook-sensitive and internal authored values.
Use the named diagnostic path to correct a header, type, duplicate key, row
limit, projection, or consultation error.

## Run the local product boundaries

Run the disposable local products against the copied workbook:

```sh
registryctl dev --detach
registryctl dev smoke
registryctl dev down
```

Registryctl mounts only the validated, project-contained workbook into the
Relay workloads that consume it. The mount is read-only and digest-bound to the
development plan. Registryctl does not start the synthetic HTTP source or
generate source credentials for this mode.

The smoke result reports one live authorization denial and one authorized
result with `minimized_claim_ids=none`, because this project releases no
attributes. It exercises both Relay lanes against the copied workbook using
the reviewed request and expected output shape. A local workbook has no
request counter, so smoke reports source effects as `unobserved`; the derived
offline security fixture verifies the authorization-before-source contract. If
smoke fails, recheck the selected row, `match_principal`, and `match.yaml`
together.

## Build reviewable inputs

Build deterministic unsigned inputs:

```sh
registryctl build
```

Registryctl reports:

```text
Built unsigned signing inputs for relay-public, relay-consultation.
Build output: .registry-stack/build/local
Next: bind an operator-managed source in a separate governed environment and rerun registryctl test; do not sign this file-backed build
```

The build contains the generated product inputs and a digest-bound
materialization.
It does not copy the human-owned workbook into portable review reports, approve
the data, or activate a deployment. The 1.0 managed deployment generator does
not package project-local workbook sources. Bind an operator-managed HTTP
source before starting governed approval.

## Verify

Before handoff, confirm:

- `registryctl test` passes with synthetic fixtures that express the reviewed
  consultation meaning.
- `registryctl check --explain` validates the copied workbook and names no
  diagnostic violations.
- `registryctl dev smoke` records a live denial and minimized authorized
  output against the selected reviewed case; the derived fixture supplies the
  authorization-before-source evidence that a local file cannot count.
- `registryctl build` emits both unsigned product lanes.
- If the project is under version control, its status does not include
  `.registry-stack/` or an unapproved workbook.

## Troubleshooting

| Symptom | Cause | Resolution |
| --- | --- | --- |
| Worksheet or header diagnostic | The workbook does not match `sheet`, `header_row`, or `columns`. | Correct the reviewed derivative or the exact authored mapping. |
| Duplicate primary key | Two rows share `project_id`. | Resolve the source identity problem. Registry Stack does not choose a duplicate. |
| Formula or external reference diagnostic | The selected worksheet contains computed or linked cells. | Replace them with reviewed static values. |
| Unexpected field appears in Relay output | The field remains in `api.projection`. | Remove it and obtain review before rebuilding. |
| Fixture passes but workbook check fails | Fixtures test authored consultation semantics, while `check` also validates the workbook mapping and rows. | Correct the workbook or authored mapping without copying sensitive workbook values into fixtures. |
| Workbook check passes but smoke fails | The selected smoke request or expected outputs no longer match the reviewed workbook case. | Update the development request fixture and expected output shape to describe one non-sensitive reviewed example without copying unrelated rows. |

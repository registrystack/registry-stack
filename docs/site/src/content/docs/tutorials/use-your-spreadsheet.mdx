Adapt the maintained spreadsheet template from one workbook you control, then verify the
resulting records policy and consultation-backed claims with synthetic fixtures.

## When to use this

Use this procedure for one reviewed XLSX worksheet with an explicit header row and a stable unique
key.
Use a synthetic, public, or otherwise approved non-personal derivative during development.

Manual source analysis remains necessary when the workbook has formulas, external links, merged
tables, several related sheets, ambiguous keys, or values that need policy interpretation.
Registryctl does not infer those decisions.

## Before you start

Complete [Run your first spreadsheet-backed registry project](../publish-spreadsheet-secured-registry-api/)
once with the unmodified starter.

Prepare a reviewed derivative with:

- One selected worksheet and one header row
- One stable, non-empty, unique text key
- Explicit fields approved for the protected records projection
- The smallest field set required by one consultation-backed claim
- No formulas or external workbook links in selected cells
- At least one synthetic matching row and one synthetic absent identifier

Write down these decisions:

| Placeholder | Derive it from |
| --- | --- |
| `<entity-id>` | Stable lower-snake-case name for the selected worksheet |
| `<key-field>` | Logical name for the stable unique key |
| `<released-field>` | Logical name for the field required by the claim |
| `<key-header>` and `<released-header>` | Exact workbook header cells |
| `<worksheet-name>` | Exact worksheet tab name |
| `<matching-key-value>` | Synthetic key value present in the workbook |
| `<purpose>` | Reviewed reason callers may use the service |
| `<registry-id>` and `<service-id>` | Stable project and records-policy identifiers |

Replace every angle-bracket placeholder before running Registryctl.

## Create a separate project

Create a fresh adaptation so the maintained sample remains available for comparison:

```sh
registryctl init reviewed-registry --template spreadsheet
cd reviewed-registry
cp /path/to/reviewed-source.xlsx data/reviewed-source.xlsx
```

Registryctl never writes workbook cells.
Do not edit `.registry-stack/`; Registryctl owns that generated directory.

## Describe the selected fields

Rename `entities/projects.yaml` to match the entity id, then replace its content:

```sh
mv entities/projects.yaml entities/<entity-id>.yaml
```

```yaml
version: 1
id: <entity-id>
revision: 1
primary_key: <key-field>
schema:
  type: object
  additionalProperties: false
  required: [<key-field>, <released-field>]
  properties:
    <key-field>: { type: string, minLength: 1, maxLength: 128 }
    <released-field>: { type: string, minLength: 1, maxLength: 256 }
materialization:
  max_records: 10000
  max_bytes: 16MiB
  refresh: manual
  retain_generations: 2
```

`primary_key` identifies the source record.
`additionalProperties: false` turns an unexpected selected column into a review event.
Change types, nullability, lengths, and limits deliberately when the reviewed workbook requires
another contract.

## Bind the workbook

In `environments/local.yaml`, replace the `entities` block:

```yaml
entities:
  <entity-id>:
    provider:
      type: xlsx
      project_file: data/reviewed-source.xlsx
      path: /var/lib/registry/reviewed-source.xlsx
      sheet: "<worksheet-name>"
      header_row: 1
    columns:
      <key-field>: "<key-header>"
      <released-field>: "<released-header>"
    source_revision: reviewed-source-v1
    generation: "1"
```

The column keys are logical names from the entity schema.
The quoted values are exact workbook headers.

Keep the local development scenario, caller, Relay, Notary-to-Relay, and deployment blocks from
the template.
Update `relay.local_api_keys.match_principal` to `<matching-key-value>` and keep the no-match
principal absent from the selected key column.
Local credentials remain disposable; they are not production identities.

## Author the records policy

In `registry-stack.yaml`, replace the `entities` declaration and records service:

```yaml
entities:
  <entity-id>:
    file: entities/<entity-id>.yaml

services:
  <service-id>:
    kind: records_api
    entity: <entity-id>
    title: Reviewed local records
    description: Protected view of the approved workbook derivative.
    owner: Local evaluation team
    sensitivity: confidential
    access_rights: restricted
    update_frequency: as_needed
    api:
      scopes:
        metadata: <entity-id>:metadata
        rows: <entity-id>:rows
        aggregate: <entity-id>:aggregate
        evidence_verification: <entity-id>:evidence_verification
      purposes: [<purpose>]
      projection: [<key-field>, <released-field>]
      pagination: { default_limit: 50, max_limit: 100 }
      filters: { <key-field>: [eq] }
      required_principal_filters: [<key-field>]
      standards: { ogc_features: false, sp_dci: false }
```

Keep the evidence service as a separate entry under `services`.
The records projection controls externally readable fields.
The required key filter comes from trusted caller identity, not a caller-supplied query value.

## Adapt the snapshot consultation

Rename the integration directory and update its declaration:

```sh
mv integrations/project-record-snapshot integrations/reviewed-record-snapshot
```

Replace `integrations/reviewed-record-snapshot/integration.yaml`:

```yaml
version: 1
id: reviewed-record-snapshot
revision: 1

input:
  record_id:
    role: selector
    type: string
    maxLength: 128

capability:
  snapshot:
    entity: <entity-id>
    exact:
      <key-field>: { input: record_id }
    freshness: 24h

outputs: [<released-field>]

not_applicable:
  ambiguity:
    rationale: The exact selector is the entity primary key and can identify at most one materialized record.
    request_fixture: match
```

Update the project integration entry:

```yaml
integrations:
  reviewed-record-snapshot:
    file: integrations/reviewed-record-snapshot/integration.yaml
```

Update the evidence service to retain exactly one Relay consultation:

```yaml
consultations:
  record:
    integration: reviewed-record-snapshot
    input:
      record_id: request.target.identifiers.<key-field>
claims:
  record-exists:
    cel: record.matched
    disclosure: predicate
  released-field-present:
    cel: 'record.matched && record.<released-field> != null'
    disclosure: predicate
```

Use domain-accurate claim ids and expressions for the reviewed field.
Do not add self-attested, source-free, or caller-defined fallback claims.

## Replace the synthetic fixtures

Update the template's three fixtures under
`integrations/reviewed-record-snapshot/fixtures/`:

- `match.yaml` selects `<matching-key-value>`, returns one synthetic
  `<released-field>` value, and expects both claims to be true.
- `planned.yaml` becomes a second synthetic matched record with the policy result you intend to
  distinguish.
- `no-match.yaml` selects a synthetic absent key and expects `record-exists: false`.

Keep `classification: synthetic`.
Update `development.default_integration` to `reviewed-record-snapshot` and keep its
`default_fixture` aligned with the match fixture.

## Validate the adaptation

Run the offline fixtures and redacted plan review:

```sh
registryctl test
registryctl check --explain
```

Review the workbook path, sheet, exact headers, unique key, records projection,
principal-bound filter, snapshot selector, minimized output, claims, and disclosure.
Fix the authored workbook or YAML named by a diagnostic.

## Run the local path

Start the disposable runtime and execute its default scenarios:

```sh
registryctl dev --detach
registryctl dev smoke
registryctl dev down
```

The denial scenario must report zero source work.
The authorized scenario must report one snapshot lookup and only the two declared claim ids.
The smoke report does not retain workbook rows or raw credentials.

## Build the reviewed inputs

Build the unsigned three-lane closure:

```sh
registryctl build
```

Keep the complete generated closure together.
The workbook, entity, environment, records policy, integration, fixtures, and claims remain
author-owned.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| The worksheet or header is missing | The authored binding does not match exact workbook text. | Correct the sheet, header row, or quoted column mapping. |
| A key is missing or duplicated | The selected field is not a stable unique key. | Resolve the source identity problem; Registry Stack does not choose a duplicate. |
| A value has the wrong type | The workbook and entity contract disagree. | Correct the derivative or deliberately change the schema. |
| A formula or external link is rejected | The selected workbook contains unevaluated behavior. | Replace it with reviewed static values in the derivative. |
| Smoke reports unexpected claims | The default fixture, consultation output, and claim expressions disagree. | Align the authored fixture and claim policy without widening the source projection. |

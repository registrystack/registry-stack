If your institution publishes a read-only SQLite extract rather than an API, Evidence Gateway can
answer from that file. You will build an Evidence project over a synthetic extract, prove it
with fixtures, and bind an extract file. Evidence never connects to your database.

/>

## Create the SQLite starter

```sh
evidencectl init registry-status \
  --transport sqlite-extract \
  --profile local
```

```text test-expect
Created an editable SQLite-extract authoring project in registry-status
  README: registry-status/README.md (what each file holds, and what comes next)
  project: registry-status/evidence.yaml
  functions: registry-status/functions
  queries: registry-status/queries
  target: registry-status/local-target.yaml
  authority: registry-status/dev-authority.yaml
  fixtures: registry-status/fixtures
  keys: registry-status/.generated/secrets (owner-only, disposable, and unbound)
Next: run `evidencectl check registry-status` and `evidencectl test registry-status` to prove the synthetic starter, then edit its source, statement, schemas, derivation, and fixtures together.
A normalized synthetic Source, AssertionDefinition, and local target were generated. No production extract or deployment bundle was generated.
```

Keep the disposable keys in `.generated/` out of version control.
The `Next` line mentions schemas, but this starter has none to edit.

## Read the extract binding

```sh
cd registry-status
```

The `record-status` Source has `type: sqlite-extract`. Its head names the Function that reads
rows and the extract profile a target binds to a file:

```yaml title="evidence.yaml" test-excerpt="evidence.yaml"
sources:
  record-status:
    acquisitionPosture: record-transformed
    extract:
      function: extract-record-status
    extractProfile: record-status
```

The project holds the logical name `record-status`, never a filesystem path. The Source's
`request.statement` names one fixed statement:

```sql title="queries/record-status.sql" test-excerpt="queries/record-status.sql"
SELECT qualifying_record_count
FROM records
WHERE reference = :record_reference
ORDER BY record_id;
```

`request.parameterBindings` binds the subject's `record-reference` selector to `:record_reference`,
so a caller's value never becomes statement text.

{/* Evidence: crates/registry-evidencectl/templates/sqlite-extract/queries/record-status.sql;
    crates/registry-evidence/src/source_sqlite.rs, bind_values. */}

## Read what the answer means

The `record-status` assertion definition carries the identifiers a relying party reads:

```yaml title="evidence.yaml" test-excerpt="evidence.yaml"
outputs:
  satisfied:
    concept: urn:example:concept:record-status:v1
    type: boolean
purpose: record-status-check
question: Does the selected synthetic record satisfy the reviewed condition?
representations:
  - signed-jws
semantics:
  evidenceType: urn:example:evidence-type:record-status:v1
  kind: criterion
  referenceFrameworks:
    - urn:example:framework:record-status:v1
  requirement: urn:example:requirement:record-status:v1
```

Replace every `urn:example:` identifier, the `purpose`, and the `question` with your institution's
reviewed ones. Keep the shape: one boolean output read from one Source. [How Evidence
works](../../explanation/how-evidence-works/#what-do-i-define) explains each part.

## Prove the starter

```sh
evidencectl check . --target local-target.yaml --deny-warnings
evidencectl test . --target local-target.yaml --deny-warnings
```

```text test-expect
Evidence project check: complete
Project: .
Target: local-target.yaml
0 errors, 0 warnings
PASS: check
PASS: fixtures/record-status.yaml (13 cases)
2 passed, 0 failed (13 cases evaluated)
Proof: offline synthetic fixture evaluation; no live dependency readiness was checked
```

Each case writes a read-only synthetic extract and runs the fixed statement against it.
`evidencectl dev start` refuses a SQLite Source, so fixtures are how you run one locally. A
warning or error names the file and key to correct.

## Adapt it to your extract

Change these together, then rerun both commands:

1. In `queries/record-status.sql`, select only the facts the assertion needs from your table,
   keeping every caller value in a named parameter.
2. In `evidence.yaml`, make the Source's `request.columns`, `parameterBindings`, `response`, and
   `facts` match the statement, keeping every bound, `maximumExtractAgeSeconds` included.
3. In `functions/`, update the fact keys the two Functions read and write.
4. In `dev-authority.yaml`, update the grant for any identifier you renamed.
5. In `fixtures/record-status.yaml`, replace the rows with invented ones and keep the refusal
   cases that still apply.

## Bind an extract file

The target, not the project, says which file an extract profile reads. Add a binding to
`local-target.yaml`:

```yaml title="local-target.yaml" test-append
extracts:
  record-status:
    path: /var/lib/registry-evidence/extracts/record-status-2026-10-14.sqlite
```

```sh
evidencectl check . --target local-target.yaml --deny-warnings
```

```text test-expect
Evidence project check: complete
Project: .
Target: local-target.yaml
0 errors, 0 warnings
```

The check does not open the file or match the key to an `extractProfile`, so match it yourself.
Your export tooling writes the file with one `evidence_extract` row holding `published_at`,
`publisher`, and `extract_id`. Evidence refuses an extract older than `maximumExtractAgeSeconds`.

:::caution
Evidence opens the extract in SQLite's immutable mode, so never change a file a running service
reads. Publish each refresh as one checkpointed, unwritable file at a new path, with no `-wal` or
`-journal` beside it, and restart Evidence.
:::

[Build a production candidate](../build-and-deploy-evidence-project/) checks the file on the
target host.

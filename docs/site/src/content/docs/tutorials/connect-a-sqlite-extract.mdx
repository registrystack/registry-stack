Use a SQLite extract when an authority can publish an immutable snapshot but cannot offer a
bounded live API. Evidence Gateway runs one reviewed statement against the file an operator binds.
Evidence does not connect to the authority's database, hold an export credential, or create the
extract.

This how-to starts with synthetic data. You will prove the Source, statement, Functions, output,
complete grant, and privacy boundary before binding a real extract.

## Create the normalized starter

Create the local authoring project:

```sh
evidencectl init registry-status \
  --transport sqlite-extract \
  --profile local
```

The starter contains one normalized `evidence.yaml`, its query and named Functions, a fixture,
`local-target.yaml`, `dev-authority.yaml`, and disposable owner-only keys. Prove the complete local
model and run the SQLite statement against the synthetic extract:

```sh
evidencectl check registry-status \
  --target registry-status/local-target.yaml \
  --deny-warnings
evidencectl test registry-status \
  --target registry-status/local-target.yaml \
  --deny-warnings \
  --explain
```

The fixture run reports `13 cases evaluated`. Those cases include positive and false results,
no match, ambiguity, the row and extract-age bounds, source and parameter failures, statement
refusal, hostile selector text kept as a bound value, the output gate, and anti-reconstruction.
The trace reports stages and shapes without printing selector or source values.

If either command reports a warning or error, correct the named project, target, authority, or
fixture field before adapting the starter. Do not turn off `--deny-warnings` to make a candidate
pass.

## Edit the Source and Functions together

The authored model has these owned inputs:

```text
registry-status/
  evidence.yaml
  queries/record-status.sql
  functions/extract-record-status.rhai
  functions/derive-record-status.rhai
  fixtures/record-status.yaml
  local-target.yaml
  dev-authority.yaml
```

In `evidence.yaml`, `sources.record-status` names the fixed statement, authorized selector binding,
expected columns, closed response shape, private facts, and execution bounds. The named extraction
Function reduces the bounded result to `match`, `no_match`, or `ambiguous`. The named derivation
Function maps private facts to the definition's declared Outputs.

Adapt these inputs as one reviewed change:

1. Change the table and column names in `queries/record-status.sql`. Select only the facts needed
   for the assertion and keep every caller-derived value in a named parameter.
2. Make `sources.record-status.request.columns`, `parameterBindings`, `response`, and `facts` in
   `evidence.yaml` match the statement exactly. Retain explicit row, cell, response, statement-step,
   timeout, concurrency, and extract-age bounds.
3. Update the extraction and derivation Functions without adding I/O or another Source path.
4. Replace the starter's selector profile, requirement, framework, Evidence Type, purpose, output
   concept, and audience identifiers in `evidence.yaml`.
5. Update the matching complete grant in `dev-authority.yaml`. A grant names one definition,
   purpose, audience rule, representation, subject binding, and every subject's role, selector
   profile, and value origin. Partial grants are never combined.
6. Replace the synthetic schema and rows in `fixtures/record-status.yaml`. Keep all values invented,
   retain a privacy canary, and preserve the negative cases that still express the Source contract.

Rerun `check` and `test` after each coherent change. A project is not ready to package while the
starter's example identifiers, statement contract, or complete grant remains.

`evidencectl dev start` refuses a SQLite Source because local serving does not bind extracts. Use
the fixture path for local execution. It materializes the declared synthetic extract, makes the file
read-only, and runs the reviewed statement for real.

## Publish an immutable extract

Create the SQLite file with the authority's export tooling. The file must contain exactly one
metadata row:

```sql
CREATE TABLE evidence_extract (
  published_at TEXT NOT NULL,
  publisher    TEXT NOT NULL,
  extract_id   TEXT NOT NULL
);
```

Write `published_at` as the snapshot instant. If the statement compares text timestamps with
`:evidence_now`, normalize those columns to whole-second UTC in `YYYY-MM-DDTHH:MM:SSZ` form before
publication.

Checkpoint the database into one file with no `-wal` or `-journal` beside it. Transfer the file to
a new versioned path, make the file non-writable to every identity, and never replace its bytes.
Evidence opens the file with SQLite's immutable mode, so a changed file behind a running connection
would violate the database engine's assumptions. Publish a new path and restart for every refresh.

## Bind the deployment target

Add the logical `extractProfile` from `sources.record-status` to the deployment target. The starter
uses `record-status`:

```yaml
extracts:
  record-status:
    path: /var/lib/registry-evidence/extracts/record-status-2026-10-14.sqlite
```

The target owns the host path. Packaging compiles this binding to `sourceExtracts` in the emitted
`runtime.yaml`; neither the project nor its governed bundle contains a filesystem location.

Create the production or evidence-grade target by following [Build and deploy an Evidence Gateway
project](../build-and-deploy-evidence-project/). Then check the edited model and build a new candidate
outside the authoring project:

```sh test-skip="requires the reader's completed deployment target and installed extract"
evidencectl check registry-status \
  --target "<deployment-target>" \
  --deny-warnings
evidencectl test registry-status \
  --target "<deployment-target>" \
  --deny-warnings
evidencectl package registry-status \
  --target "<deployment-target>" \
  --output candidate-staging
```

Install `candidate-staging/bundle` at the exact `package.root` in
`candidate-staging/runtime.yaml`, provision the referenced secrets, and activate
`candidate-staging/compiled-authority.yaml`. The offline check then validates the installed package,
runtime, authority binding, and logical extract binding without reading secrets or contacting a
service:

```sh test-skip="requires an installed candidate and activated target authority"
evidence check \
  --runtime-config candidate-staging/runtime.yaml \
  --deny-warnings
```

On the target host, prove the operational dependencies before starting the service:

```sh test-skip="requires the target host, signer, issuer, audit destination, secrets, and mounted extract"
evidence check \
  --runtime-config candidate-staging/runtime.yaml \
  --require-runtime-dependencies \
  --deny-warnings
```

The target-host check opens the read-only extract, validates its metadata and fixed statement,
checks its age, initializes the signer and audit destination, resolves configured secrets, and
checks the token issuer. A stale extract, missing binding, statement shape or extract metadata mismatch, writable input,
or unavailable dependency refuses the deployment.

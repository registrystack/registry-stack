If your application verifies Evidence responses, its verifier must trust keys your organization
approved, never keys the service or the response supplies while it is being verified. This page
pins the provider's public keys, keeps a revoked key out, and takes a signing-key rotation without
a gap.

## Pin the provider's keys in the client profile

`evidencectl client profile create` takes the trust mode. Pass `--pinned-jwks <PATH>`, which its
help describes as a "Reviewed pinned JWKS file, relative to the profile file":

```sh
evidencectl client profile create \
  --base-url https://evidence.example.com \
  --client-id age-check-app \
  --private-key-file app-key/client-assertion-p384-private-jwk \
  --pinned-jwks trusted-jwks.json \
  --output age-check-client.json
```

```text test-expect
Created client profile
```

Without that flag the profile uses `https-discovery`, and `--local-loopback-discovery` is its
loopback form: in both, the client fetches the service's key set itself. A profile client carries
no revoked-key list in any trust mode, so with a profile you revoke a key by removing it from the
pinned set.

## Build the pinned key set

Obtain each public JWK from the provider through your onboarding channel, not from its JWKS
endpoint alone, then assemble the pinned key set:

```sh
evidencectl jwks \
  --output trusted-jwks.next.json \
  provider-current.public.jwk.json \
  provider-next.public.jwk.json
```

```text test-expect
wrote trusted-jwks.next.json
```

The command refuses a private key and an existing output file; pass `--force` to overwrite. Write
a new file and activate it through your configuration change process, so the previous set stays
available for rollback.

## Keep a denylist with an explicit client

When you need revoked key ids beside the pinned set, construct the client yourself:

```python
client = EvidenceClient(
    "https://evidence.example.com",
    trusted_jwks=json.loads(Path("trusted-jwks.json").read_text()),
    revoked_key_ids=["<revoked kid>"],
    token=token_config,
)
```

A revoked key id is refused even while the key is still in the pinned set.

### Node

```js
const client = new evidence.EvidenceClient({
  baseUrl: 'https://evidence.example.com',
  trustedJwks: JSON.parse(readFileSync('trusted-jwks.json', 'utf8')),
  revokedKeyIds: ['<revoked kid>'],
  token: tokenConfig,
})
```

## Take a rotation

1. When the provider announces a new key, add it to the pinned set and activate the set before the
   provider signs with it.
2. Once the provider's maximum assertion lifetime plus clock skew has passed since the old key last
   signed, remove the old key from the set; with an explicit client, also add its key id to
   `revoked_key_ids` if it was compromised.
3. Keep each retired set with the decisions it governed, because a replay needs the keys trusted
   at the time.

A response signed by a key outside the set fails with code `key`. Treat that as a trust change to
approve, never as a key to fetch. The provider's side is
[Rotate Evidence Gateway signing keys](../rotate-evidence-signing-keys/); the threat model is in
[Evidence Gateway security model](../../security/evidence/).

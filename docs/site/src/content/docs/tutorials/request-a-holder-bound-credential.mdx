Complete [Explore SD-JWT VC locally](../request-evidence-as-sd-jwt-vc/) before starting. That
tutorial issues the default audience-scoped credential, whose subject binding is scoped to the
requesting relying party. This page covers the other subject binding mode, `holder-bound`, where the
binding is scoped to the holder's own key instead, so one credential can be presented to a relying
party that was not named when it was issued.

The holder-bound profile is a frozen contract, but the local authoring workspace does not yet
declare a binding mode on an authored question. This tutorial therefore works against a deployment
bundle rather than a local `questions/` project. Read
[Known limitations](../../explanation/known-limitations/) before you plan a production rollout with
this mode.

## Decide whether the mode fits

The two modes trade different things away, and neither is a default that suits every requirement.

| Property | `audience-scoped` (the default) | `holder-bound` |
| --- | --- | --- |
| Binding scope | The authenticated relying party | The presented holder key |
| Reuse | One relying party only | Any relying party the holder presents to |
| Response formats | Signed JWS, SD-JWT VC, or the unsigned envelope | The SD-JWT VC serialization or its batch envelope |
| Correlation | Two relying parties cannot join their subjects | Two relying parties see the same subject for the same key |
| Possession | Not proven, and not asked for | Proven by a key-binding JWT the holder signs |

Nothing about the request selects the mode. The requirement declares it in the immutable bundle,
and a requirement that declares nothing serves `audience-scoped` whatever the caller supplies.

## Permit the mode in the bundle

Three declarations must agree before a holder-bound release is reachable. Add the SD-JWT VC
serializations to the bundle-wide formats, and declare a batch ceiling only if this deployment will
serve batches:

```yaml
responseFormats: [signed-jws, sd-jwt-vc, sd-jwt-vc-batch]
holderBoundBatchMaxSize: 4
```

Declare the mode on the requirement itself:

```yaml
requirements:
  - id: urn:example:requirement:age-bracket:v1
    subjectBinding: holder-bound
```

Name the mode on every authority grant that may reach that requirement:

```yaml
authorityProfiles:
  approved-caller:
    kind: explicit-request
    requesterTags: [approved-caller]
    grants:
      - requirement: urn:example:requirement:age-bracket:v1
        purpose: service-path-selection
        audienceFrom: authenticated-requester
        responseFormats: [signed-jws, sd-jwt-vc, sd-jwt-vc-batch]
        subjectBindingModes: [holder-bound]
        subjects:
          - role: person
            selectorProfile: person-reference-v1
            valueOrigin: request
```

`signed-jws` stays in the list because every scope must keep signed JWS enabled, grants included,
and naming it here releases nothing: the binding mode is what restricts issuance, so a holder-bound
requirement is never served as signed JWS. Permitting a serialization is never permitting a binding
mode: a grant states each separately, and a grant that omits `subjectBindingModes` permits
`audience-scoped` alone. A holder-bound requirement whose concepts use an entity-reference value
form is rejected at startup, because that pointer is only resolvable by the audience it was scoped
to and a holder-bound assertion names no audience.

Check the candidate before deploying it:

```sh
evidence check --runtime <evidence-project>/runtime.yaml
```

A holder-bound requirement that the bundle or every grant leaves unreachable fails here, at
startup, rather than at request time.

## Generate a holder key

The holder key is the subject's key, not the deployment's. Generate a disposable P-256 pair for
this walkthrough:

```sh
evidencectl keygen holder --output-dir keys
```

```text
keys/holder-p256-private-jwk
keys/holder-p256-public.jwk.json
```

Only `holder-p256-public.jwk.json` is ever sent. A request carrying a key with any private member
is refused before source access, as is a non-P-256 key, a key whose algorithm is not `ES256`, and a
second key repeating an earlier RFC 7638 thumbprint.

## Request one credential

Start from `request.json`, the request body you already send for this requirement, and add the
public key to its `holderKeys` array. A single-credential request is an array of one:

```sh
python3 - <<'PY'
import json
from pathlib import Path

request = json.loads(Path("request.json").read_text())
request["holderKeys"] = [json.loads(Path("keys/holder-p256-public.jwk.json").read_text())]
Path("holder-request.json").write_text(json.dumps(request, indent=2) + "\n")
PY
```

Send it with the exact SD-JWT VC media type:

```sh
curl --silent --show-error --fail-with-body \
  --config authorization.curl \
  --request POST \
  --url https://<evidence-host>/v1/evidence \
  --header 'Content-Type: application/json' \
  --header 'Accept: application/dc+sd-jwt' \
  --data-binary @holder-request.json \
  --output credential.sd-jwt \
  --write-out 'HTTP %{http_code}\n'
```

```text
HTTP 200
```

The stored credential confirms the presented key in `cnf` and ends in a trailing tilde. It carries
neither `audience` nor `requestNonce`: there is no relying party at issuance to name, so the two
payload members are absent together. The request still carries its own request nonce under the
unchanged transport rules; it is simply not projected into a holder-bound payload.

An unusable `holderKeys` entry returns `evidence.invalid_request`. A missing one under a holder-bound
requirement returns the same problem, and it is answered only after authorization and the format
gate, so an unauthorized caller learns nothing about the requirement's binding mode. See the
[errors and problems reference](../../reference/evidence-problems/).

## Ask for a batch

Build `holder-batch-request.json` the same way, with one public JWK per holder key in
`holderKeys`, keeping every key distinct by RFC 7638 thumbprint and staying within the
deployment's declared `holderBoundBatchMaxSize`. Select the batch envelope to receive one
credential per key:

```sh
curl --silent --show-error --fail-with-body \
  --config authorization.curl \
  --request POST \
  --url https://<evidence-host>/v1/evidence \
  --header 'Content-Type: application/json' \
  --header 'Accept: application/vnd.registrystack.evidence.batch+json' \
  --data-binary @holder-batch-request.json \
  --output batch.json \
  --write-out 'HTTP %{http_code}\n'
```

The envelope carries the credentials in the order the keys were presented:

```json
{
  "schema": "registry.sd-jwt-vc-batch-envelope/v1",
  "type": "SdJwtVcBatchEnvelope",
  "credentials": ["<credential>", "<credential>", "<credential>"]
}
```

One authorization decision, one source acquisition, and one derivation produce the whole set, and a
failure on any member releases nothing. There is no partial batch.

A batch reduces deterministic key-based linkability, and it does not make its members unlinkable.
Every member shares an issuance timestamp, purpose, requirement, Evidence Type, configuration
revision, and disclosed values, and the issuer knows the whole set was released together. Verify
each member individually as an ordinary holder-bound credential; nothing consumes the envelope at
verification.

## Present the credential

Evidence Gateway appends no key-binding JWT. The stored credential is not a presentation, and the
`evidence verify-presentation` command refuses a file that ends in a trailing tilde rather than
verifying it without a proof of possession.

The holder builds the presentation, following RFC 9901 Section 4.3: keep the issuer-signed
credential and the disclosures being presented, then append a key-binding JWT after the last tilde,
signed by the private half of the key in `cnf`. Its protected header carries exactly `alg` and
`typ` (`kb+jwt`), optionally `kid`, and its payload carries exactly `nonce`, `aud`, `iat`, and
`sd_hash`. The `nonce` and `aud` values come from the relying party the holder is presenting to,
not from the issuer.

## Verify a presentation offline

The relying party retains its expectations independently of the credential. Write them as a
holder-bound policy document:

```yaml
subjectBinding: holder-bound
expectedAssuranceProfile: evidence-grade
issuedBy: urn:example:issuer:authority
providedBy: https://<evidence-host>
requirement: urn:example:requirement:age-bracket:v1
evidenceType: urn:example:evidence-type:age-bracket
expectedIssuancePurpose: service-path-selection
configurationRevision: sha256:<64-hex-digest>
expectedSubjects:
  - role: person
    binding: <pinned-subject-binding>
expectedOutputs:
  - concept: urn:example:concept:age-bracket:v1
    form: string
revokedKeyIds: []
maximumAssertionLifetimeSeconds: 300
keyBindingAudience: <this-relying-party>
keyBindingNonce: <challenge-this-relying-party-issued>
maximumKeyBindingAgeSeconds: 60
```

`expectedSubjects` is pinned from the relying party's own trusted state and is never recomputed
from the credential. The binding is an HMAC under a deployment secret the relying party does not
hold, so it cannot derive the value; it learns it from an enrolment or account record it already
trusts. `expectedHolderKeyThumbprint` is available for a relying party that already knows which
holder it is talking to, and it is optional: possession is proven by the key-binding signature over
the credential's own confirmation key, not by recognizing the thumbprint.

`expectedIssuancePurpose` is the purpose the credential was issued under, compared as signed
issuance provenance. It is not a downstream use limit, a licence, or an authorization.

Verify the presentation against a pinned trusted key set:

```sh
evidence verify-presentation \
  --sd-jwt-vc-presentation presentation.sd-jwt \
  --jwks trusted-issuer-keys.json \
  --policy holder-bound-policy.yaml
```

```text
verified-at: 2026-08-08T09:30:00Z
authentic: yes
possession: proven when the key-binding JWT was signed; not proof that the presentation is fresh, single-use, or unreplayed
currently-valid: yes
```

The command opens no network connection, and `trusted-issuer-keys.json` is the complete approved
trust set for the run. Pass `--at <rfc3339-utc>` to re-verify at a historical decision instant.

Three exit codes separate the outcomes that need different handling:

| Exit code | Meaning |
| --- | --- |
| 0 | Authentic, possession proven, and currently valid |
| 3 | Authentic and possession proven, but not currently valid at the verification instant |
| 1 | Everything else, including every verification failure class |

Verification fails closed and reports only a closed failure class, never a diagnostic detail that
would describe the presented material. The key-binding JWT is checked before any policy comparison,
so a presentation that proves no possession never reaches the expectations.

## Know what a verified presentation proves

A successful run proves that a trusted issuer key signed this exact payload, that the disclosed
values match the digests the issuer signed, that the presenter held the private half of the
credential's confirmation key when the key-binding JWT was signed, and that every pinned
expectation held.

It proves none of the following:

- that the presentation is fresh, single-use, or unreplayed. The expected challenge is compared,
  never consumed, and the command retains no state between runs, so the same file verifies again
  under the same policy. Retiring a challenge belongs to the relying party's own challenge
  lifecycle, which RFC 9901 places in the surrounding protocol;
- that the presenter is the subject of the credential, or is authorized to act for that subject;
- that the credential has not been revoked. There is no status list, no revocation, and no expiry
  beyond `validUntil`;
- that the holder presented it to only one relying party. A reused holder key is a correlator the
  service cannot prevent.

A valid issuer signature alone proves no possession. Possession is proven only by the key-binding
JWT signature over the credential's own `cnf`.

## Know the boundary

This is still one stateless assertion in a second serialization, not a credential lifecycle. There
is no OID4VCI offer, issuance session, or token exchange: the `evidence` binary speaks no OID4VCI
at all. There is no wallet onboarding, presentation exchange protocol, status service, refresh, or
reissuance. Full SD-JWT VC and OID4VCI conformance stay unclaimed.

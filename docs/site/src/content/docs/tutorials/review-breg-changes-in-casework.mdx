If you already own a Base Registry Engine (BReg) registry and want people to review its Proposals in Casework, pair the
producer's exact context export with a Casework policy. You will produce a checked Casework package;
BReg keeps responsibility for submission, cancellation, result correlation, and later application.

## Prepare the matching inputs

Use the BReg package produced by your registry's normal schema-test and packaging procedure.
Pairing consumes its sealed native export; it does not infer a contract from a running source or
modify BReg's access grants.

In your Casework project, declare a current-source ReviewPolicy with the native export's exact
contract ID, revision, and schema digest, and vendor its bounded display schema.
The provider's source namespace and purpose-specific service profile must match the producer.
The maintained canonical example uses provider `facility-proposal-context`, namespace
`facility-registry`, and action `correct-address`.
For another action, use your own matching declarations rather than renaming an unrelated export.

Set the paths to your prepared project and sealed package, plus the provider and action IDs
from those matching declarations:

```sh test-skip="the reader supplies the exact project and tested producer package"
casework_project=/absolute/path/to/casework-project
breg_package=/absolute/path/to/breg-build/package
provider_id=facility-proposal-context
action_id=correct-address
```

[Author a Casework policy](../../configure/casework/#choose-context-custody) describes those inputs.
A BReg build package and an editable registry source directory are different artifacts.
Use the package directory containing its manifest and checksums, not the editable source directory.

## Preview and apply pairing

Preview the matching pairing without writing:

```sh
caseworkctl provider pair "$casework_project" \
  --provider-id "$provider_id" \
  --breg-package "$breg_package" --action-id "$action_id"
```

Inspect the reported native contract and registry revision, then write that verified export:

```sh
caseworkctl provider pair "$casework_project" \
  --provider-id "$provider_id" \
  --breg-package "$breg_package" --action-id "$action_id" --apply
```

Pairing verifies the already-vendored schema and contract against the sealed BReg package, writes
the exact provider export and its description reference, and records the producer revision. It provisions no credential and activates neither service.
If it refuses a contract mismatch, regenerate the producer export, vendor its exact schema, and update
the policy's contract pin before retrying. Preserve the previous package until you have checked the
candidate; replacing a contract does not reinterpret accepted reviews.

## Check and package the paired project

Compare the complete imported contract with the same BReg package, inspect the compiled policy,
and build a fresh Casework package:

```sh
caseworkctl check "$casework_project" --against-breg-package "$breg_package"
caseworkctl explain "$casework_project"
caseworkctl package "$casework_project" --output ./paired-casework-package
```

A successful check confirms the exported contract, registry revision, and exact schema bytes.
The package contains the reviewed policy and its local dependency closure.
This offline result establishes authoring consistency; it does not establish source reachability or
human disclosure in a deployment.

Before enabling the BReg producer, select the Casework policy ID in BReg's required
review declaration. Casework freezes the concrete version and digest on acceptance.
If you require an exact pin, add the actual compiled version and digest together.
Rebuild the tested BReg package and recheck pairing when that package changes.

## Bind transport and authority

Configure the provider deployment reference in Casework's runtime file with the BReg endpoint,
`statusProfile`, token endpoint, exact audience/resource/scopes, and secret references.
The status profile needs only native `get-review-status` authority.
A human caller separately selects an authorized `Registry-Source-Profile`; the provider forwards that
human's current bearer for `get-review-context`. A status credential cannot supply displayed fields.

Deploy and activate each product through its own operator procedure.
The BReg producer submits a frozen Proposal using the compiled review binding, Casework records the
human outcome as an immutable Decision, and BReg authenticates and correlates the result before its separately authorized
application step. Casework performs no source action.
A missing, changed, concealed, or non-reviewable subject cannot become a disclosed human task.

## Apply and observe the exact BReg submission

BReg Proposal application defaults to the restricted built-in executor. It needs
no executor OAuth client or self-HTTP endpoint. Author
`execution.proposal.application.mode: manual` only when a separately authorized
caller must apply. External recovery of automatic work requires a verified human
and an explicit BReg operation grant. A Casework Decision grants no source
application authority.

The BReg `reviewAuthorities` binding names the exact endpoint, producer identity,
requester profile, and renewable credential. An absent optional authority disables
only operations requiring it. Generated CRUD, immediate Actions, and no-review
Proposals remain available; an outage never implies approval. Every uncommitted
review-required application obtains fresh authenticated and unexpired approval
for the exact frozen binding.

Observe the Proposal through an authorized Get and preserve `actionRevision`,
`submissionVersion`, and `effectDigest`. Applied work includes retained local
application evidence; blocked work includes a safe reason, recovery hint, and
currently authorized promoted links. Revise or Rebase makes the earlier binding
stale and requires resubmission and new review when applicable. Do not silently
follow its successor.

A Casework rejection ends the Proposal in `rejected`; a changes-requested
decision keeps it `submitted` with Revise promoted. Either way the Proposal Get
carries `decision`, with the public reason the reviewer wrote for the subject
and none of the reviewer's notes.

Recover an uncertain Start, Submit, or Apply with its original prepared command
and idempotency key. A later observation is not proof that the uncertain command
executed. Repair a named binding or use the currently authorized recovery
transition; never force either product's work tables to a result.

Your registry can hold a Proposal until a person approves it. Here you pair one Action's review
context with a Casework policy, then bind Casework as your Base Registry Engine (BReg) review
authority. The registry keeps submission, correlation, and application; Casework records the
decision and writes nothing to your registry.

## Start from the maintained pair

The facility template and Casework's canonical-review example are built to pair. The template's
`correct-address` Action creates a Proposal that requires review by the `casework` authority. The
Casework project declares the matching provider, `facility-proposal-context`, for the source
namespace `facility-registry`.

Install copies that match your binaries with `bregctl init --template facility-registry facility`
and `caseworkctl init review --template canonical-review`. You can also read the
[facility template](https://github.com/registrystack/registry-stack/tree/main/products/breg/examples/facility)
and the
[canonical-review example](https://github.com/registrystack/registry-stack/tree/main/products/casework/examples/canonical-review)
in the repository. For your own Action, declare the same pieces with your own identifiers, as
[Author a Casework policy](../../configure/casework/#choose-context-custody) describes.

Set the paths and identifiers. The package is the built directory with its manifest and checksums,
not your editable source:

```sh test-skip="the reader supplies the exact project and tested producer package"
casework_project=/absolute/path/to/casework-project
breg_package=/absolute/path/to/breg-build/package
provider_id=facility-proposal-context
action_id=correct-address
```

## Pair the review context

Preview the pairing; it writes nothing:

```sh
caseworkctl provider pair "$casework_project" \
  --provider-id "$provider_id" \
  --breg-package "$breg_package" --action-id "$action_id"
```

A pairing that works reports `"ok": true`, the context `contract` it verified, and the package's
`registryRevision`. Its `readerAuthority` names the operation `get-review-status` with
`"sourceWrites": false`: Casework reads review status from your registry and never writes to it.
Write the pairing:

```sh
caseworkctl provider pair "$casework_project" \
  --provider-id "$provider_id" \
  --breg-package "$breg_package" --action-id "$action_id" --apply
```

The report now says `"applied": true`, and the provider description sits under
`context-providers/`. If the policy's contract pin does not match the package's export, the command
exits 1 with `caseworkctl.refused` and "The authored input was refused." Regenerate the export,
vendor its schema, and update the pin before you retry.

## Check and package

Compare the paired project with the package, inspect the policy, and build the Casework package:

```sh
caseworkctl check "$casework_project" --against-breg-package "$breg_package"
caseworkctl explain "$casework_project"
caseworkctl package "$casework_project" --output ./paired-casework-package
```

A passing check confirms the context contract and the exact schema bytes, and reports the package's
registry revision. It runs offline: it proves the projects agree, not that either service is
reachable. Rebuild and recheck whenever the BReg package changes.

## Bind the review authority

A review authority is the service your registry asks for a decision. The project names it, and the
runtime configuration binds it to an endpoint and a credential;
[Review authorities, declared twice](../../configure/breg-actions/#review-authorities-declared-twice)
shows both halves. Three things in that binding must agree with the Casework producer:

```yaml title="casework.yaml"
trustedProducers:
  facility-registry:
    profile: requester
    issuer: https://identity.example.test
    subject: facility-registry-review-producer
    trustedInitiatorIssuer: https://identity.example.test
    sourceNamespaces: [facility-registry]
    reviewPolicies: [facility-address-review]
    retention: {receiptRetentionDays: 30}
```

- `producerId` equals the producer's key, `facility-registry` here. Both products fold it into
  each submission's digest.
- The binding's `profile`, and its credential's issuer and subject, match the producer's `profile`,
  `issuer`, and `subject`.
- `recoveryDays` is required and must not exceed `receiptRetentionDays`, which is at most 365. The
  registry retries an uncertain submission against a receipt Casework keeps only that long. No tool
  compares the two values.

Each submission carries a subject binding: the source namespace, the Proposal, its version, and its
`effectDigest`. Casework decides on that exact binding, and the registry accepts only a result that
matches it.

By default the registry polls Casework for results. For a completion signal instead, add
`completionTokenRef` and `completionRecipient` to the binding together. Then give the Casework
producer a completion destination that presents the same token.

A reviewer reads the Proposal under their own registry access profile. The provider's status
credential checks review status only and never supplies displayed fields.

## Read the signals

Submit a Proposal for the paired Action, then read it with a profile that holds the `apply` grant.
While Casework reviews it, the Proposal's `apply` link is unavailable with reason `pending-review`
and recovery `refresh`.

Two binding faults read differently:

- Casework answers a credential that matches no producer, or a policy or source namespace the
  producer does not list, with 403 `operation.not-authorized`. The registry records `remote-refused`
  and logs a warning with the authority, status, and problem code. The Proposal reads `review-ended`
  with recovery `revise`.
- A `producerId` that differs from the producer's key fails the registry's own acceptance check.
  The Proposal reads `dependency-outage` with recovery `retry` until `recoveryDays` pass, then
  `review-ended`. When a review never settles, check `producerId` first.

After the decision, the Proposal follows its usual states: `applied`, `rejected`, or `submitted`
with Revise offered when changes are requested. [Proposals](../../configure/breg-actions/#proposals)
covers those states and application; a Casework decision never grants authority to apply.

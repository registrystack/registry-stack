If you are connecting Base Registry Engine (BReg) to Registry Casework or another
conforming review authority, bind one exact policy and authenticated producer
connection. BReg retains the Proposal and applies its frozen effects; the
authority owns policy and decisions.

## Prepare both contracts

Start with a checked Proposal Action such as the generated `facility-registry`
project. Prepare the authority independently with its admitted source namespace,
producer identity, policy, and producer context schema. Obtain the immutable
policy ID, version, and digest from that authority. Replace the example's synthetic
pin in `execution.proposal.review.policy`; set the logical `authority` and
`source` to the configured connection.

Keep both products' databases, credentials, and grants separate. A review result
does not grant BReg target authority, and a BReg profile does not grant a Casework
decision. Human context reads remain subject to current Proposal and record
permissions. The authority receives the bound context, never raw attachment bytes.

## Bind the deployment

In BReg runtime configuration, map `reviewAuthorities.<authority>` to the exact
endpoint, producer ID, requester profile, recovery window, and maintained
credential. Use secret references. For local evaluation, the project's
`dev-clients.yaml` accepts the same logical authority with a dedicated issuer
client whose scopes and identity the authority admits. The client needs no BReg
record profile.

Automatic application is the default. BReg's built-in executor uses its compiled
system grant for the exact frozen submission, so you configure no executor OAuth
client or self-HTTP endpoint. For explicit manual application, author
`execution.proposal.application.mode: manual` and grant the intended caller
Proposal Apply separately.

A missing review binding disables dependent operations while generated CRUD,
immediate Actions, and no-review Proposals remain usable. Restore the exact
binding to resume retained work. An outage never downgrades review to approval.

## Check before submitting

```sh
bregctl check ./facility-registry
bregctl --format json explain proposals ./facility-registry
```

Check the policy pin, source namespace, producer admission, current endpoint,
and selected authority profile on both sides. Compilation proves the BReg
configuration; it does not authenticate the external service or evaluate policy.
Use your authority's maintained deployment and policy checks before admitting work.

## Submit and observe

Select the Action from BReg metadata, Start a draft, and use its promoted Submit
link. The submission binds the exact plan, targets, Action revision, context,
attachments, and policy. BReg correlates the authenticated result to that frozen
binding and obtains fresh unexpired approval before an uncommitted application.

Observe the Proposal through its authorized Get. Preserve `actionRevision`,
`submissionVersion`, and `effectDigest`. Applied work includes retained local
application evidence. Blocked work exposes safe recovery information and permitted
transitions. Revise or Rebase requires a new submission; an earlier approval
cannot authorize changed contents. Recover an uncertain command with its original
prepared request rather than inferring execution from later state.

If review cannot progress, inspect the exact Proposal and authority work under
their separate grants. Repair the binding or use an authorized Cancel, Rebase,
or recovery operation that the Proposal currently promotes. Never edit either
product's work tables to force a result.

Use fixtures after the Source, AssertionDefinition, Functions, Outputs, and complete target grants
are ready for review. This how-to continues the writable `adult-status` project from [Get your first
Evidence Gateway assertion](../first-evidence-assertion/).

Fixtures are executable, synthetic claims about that project. Evaluation loads the production
bundle, runs the fixed Source boundary, executes the named extraction and derivation Functions,
applies the output gate, signs, verifies, and checks privacy expectations. It does not start HTTP,
authenticate a token, contact a provider, resolve source credentials, or write the production audit
log.

## Connect each definition to its fixture

The normalized model keeps each fixture reference with its definition in `evidence.yaml`:

```yaml
assertionDefinitions:
  adult-status:
    fixtures: fixtures/adult-status.yaml
```

The same definition declares its semantics, purpose, grant ceiling, subjects, acquisition Source,
derive Function, Outputs, validity, subject binding, and response representations. Do not recreate
those decisions inside the fixture.

`local-target.yaml` selects `dev-authority.yaml`. That authority contains complete grants for the
target: one grant supplies the definition, purpose, audience rule, representation, subject binding,
and all subject selector value origins. A client assigned an access profile gains no authority that
the matching complete grant and definition ceiling do not already permit.

Run the project check before changing fixtures:

```sh
evidencectl check . \
  --target local-target.yaml \
  --deny-warnings
```

A complete result with zero warnings proves that the project, target, authority, references, and
authored limits agree. It does not contact the Source or prove target-host dependencies.

## Write synthetic cases

Keep every fixture under `fixtures/`, set `synthetic_only: true`, and use the current
`EvidenceFixture` envelope. Put shared observation time, selectors, and transport expectations in
`common`; each case then states one input variation and its expected outcome.

Keep the cases that reviewers need to approve:

- an ordinary positive result and a legitimate negative value;
- important time, number, and codelist boundaries in the derivation;
- no match and ambiguity when the Source exposes those distinct outcomes;
- missing or mistyped facts and unavailable or malformed Source responses;
- output outside the declared Output contract;
- statement, parameter, and row-bound refusals for a SQLite Source;
- privacy canaries that must stay out of evidence and diagnostics;
- anti-reconstruction cases for outputs that must not be released together.

For an HTTP Source, a case supplies a synthetic provider response. For a SQLite Source, the fixture
supplies SQL that creates one synthetic extract, and cases supply selectors. The evaluator executes
the reviewed statement against a temporary read-only SQLite file, so a recorded result cannot hide a
broken statement.

The fixture grammar is closed. An unknown key, unknown mutation, unsupported expectation, missing
case, or real-data marker refuses evaluation. Use the [fixture
contract](https://github.com/registrystack/registry-stack/blob/main/products/evidence/reference/request-adapter/deployment-projects/FIXTURES.md)
when adding a case form.

## Run the complete suite

From the `adult-status` project directory, run:

```sh
evidencectl test . \
  --target local-target.yaml \
  --deny-warnings
```

The maintained standalone project reports:

```text
PASS: check
PASS: fixtures/adult-status.yaml (10 cases)
PASS: fixtures/legal-parent-relationship.yaml (9 cases)
PASS: fixtures/professional-licence-status.yaml (10 cases)
PASS: fixtures/residence-region.yaml (9 cases)
5 passed, 0 failed (38 cases evaluated)
Proof: offline synthetic fixture evaluation; no live dependency readiness was checked
```

`evidencectl` first resolves a matching `evidence` binary. It then compiles the project and selected
target into private staging, checks the bundle, and delegates every fixture decision to the Evidence
runtime. A version mismatch refuses before fixture evaluation; install matching binaries or put the
matching `evidence` first on `PATH`.

Use machine output in CI and keep the report with the build evidence rather than in the authored
project:

```sh
evidencectl --format json test . \
  --target local-target.yaml \
  --deny-warnings \
  > "<private-build-evidence>/fixture-report.json"
```

Treat a failed case, missing reference, warning, unknown field, or unsupported expectation as a
failed build input. Do not turn a real failure into an ignored case.

## Explain one case

Select one fixture and case when a result needs diagnosis:

```sh
evidencectl test . \
  --target local-target.yaml \
  --fixture fixtures/adult-status.yaml \
  --case boundary-at-bangkok-midnight \
  --explain \
  --deny-warnings
```

The trace names the case's expected and observed result classes, reason code, and every stage it
reached. Read the final stage first. `prepare`, `acquire`, `extract`, `derive`, `validate`, `expect`,
and `sign` entries report identifiers, counts, and shapes. A failed case adds a failure and finding
codes and stops at the stage that ended it.

The trace never prints a response, fact, derived value, or selector value. Evaluation also refuses
a trace containing a value listed in `privacy_expectation.diagnostics_exclude`. `--explain` changes
no outcome or exit code.

## Package the proved revision

Package only the exact project and target revision that passed. Choose a new output directory outside
the authoring project:

```sh
evidencectl package . \
  --target local-target.yaml \
  --output ../evidence-candidate
```

The candidate contains `bundle/`, `runtime.yaml`, and `compiled-authority.yaml`. Packaging repeats
the runtime bundle checks, but it does not install the bundle, activate authority, resolve secrets,
open a production extract, contact a token issuer, or initialize the signer and audit destination.

For a deployment handoff, record the passing fixture report, reviewed source revision, candidate
digest, target and authority review, and the later target-host proof together. Follow [Build and
deploy an Evidence Gateway project](../build-and-deploy-evidence-project/) to install the candidate,
activate its complete authority, and run `evidence check --require-runtime-dependencies` on the
target host.

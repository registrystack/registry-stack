Complete [Add OAuth-backed Rhai adaptation](../configure-project-script-adapter/) before starting
this case study. You will apply that workflow to an OpenCRVS Events API-shaped event search.
The example is synthetic and does not establish compatibility with an OpenCRVS deployment.

## When to use this

Use this shape when an integration team wants to review the Registry Stack source boundary before
testing a named OpenCRVS release and country configuration.

Registryctl 1.0 does not ship an OpenCRVS template or privileged OpenCRVS connector.
Start with the `http` template and adapt it.

## Case-study scope

This page exercises exactly this synthetic example:

- OAuth client credentials with JSON request encoding
- `oauth2_bearer_no_expiry` with only `access_token` and `token_type: Bearer`
- One read-only `POST /api/events/events/search`
- An exact `and` query on birth-event type and one synthetic tracking id
- A response limited to two results with `id`, `type`, `status`, and `trackingId`
- One Rhai mapping that checks cardinality, event type, and the returned tracking id
- Minimized outputs `event_type` and `registered`
- One consultation service, `birth-event-verification`, holding exactly one Relay consultation
- Match, no match, ambiguity, source rejection, subject mismatch, malformed source response,
  timeout, OAuth redirect, OAuth media type, token type, extra-member, expiry, oversize response,
  and authorization denial cases

The request and response are example test files.
They are not asserted to be a native OpenCRVS contract or release-specific API shape.
An OpenCRVS deployment owner must replace them from the exact deployment's reviewed API
documentation before any interoperability test.

## Before you start

Create the HTTP project, then use `curl` and Python 3 to download and verify the public example
from the installed Registryctl release:

```sh
registryctl init opencrvs-events-api --template http
cd opencrvs-events-api
(
  set -eu
  REGISTRYCTL_VERSION=$(registryctl --version)
  REGISTRYCTL_VERSION=${REGISTRYCTL_VERSION#registryctl }
  case "$REGISTRYCTL_VERSION" in
    ''|*[!0-9A-Za-z.-]*|[!0-9]*)
      printf '%s\n' "unexpected Registryctl version: $REGISTRYCTL_VERSION" >&2
      exit 1
      ;;
  esac
  OVERLAY=opencrvs-events-api-overlay-v1.sh
  OVERLAY_URL="https://docs.registrystack.org/v/$REGISTRYCTL_VERSION/examples/registryctl/$OVERLAY"
  curl -fsS "$OVERLAY_URL" -o "$OVERLAY"
  curl -fsS "$OVERLAY_URL.sha256" -o "$OVERLAY.sha256"
  python3 - "$OVERLAY" "$OVERLAY.sha256" <<'PY'
import hashlib
import hmac
import sys
from pathlib import Path

overlay = Path(sys.argv[1])
lines = Path(sys.argv[2]).read_text(encoding="ascii").splitlines()
if len(lines) != 1:
    raise SystemExit("overlay checksum file must contain exactly one line")
expected, separator, filename = lines[0].partition("  ")
if separator != "  " or filename != overlay.name:
    raise SystemExit("overlay checksum file names the wrong asset")
actual = hashlib.sha256(overlay.read_bytes()).hexdigest()
if not hmac.compare_digest(actual, expected):
    raise SystemExit("overlay checksum mismatch")
PY
  sh "$OVERLAY"
  rm "$OVERLAY" "$OVERLAY.sha256"
)
```

The overlay first verifies that the complete authored closure still matches the pristine HTTP
starter embedded in that Registryctl release.
It stops before replacing any file when the starter is missing, changed, or contains another
authored file.
The overlay reports:

```text
Applied the synthetic OpenCRVS Events API-shaped OAuth and Rhai overlay.
```

The overlay is a released documentation asset, not a third Registryctl template.
It contains every authored file and fixture used by this page.
The documentation gate applies the same overlay to a fresh `http` starter without reading or
copying a source-tree fixture.

Keep every identifier, credential, token, and source response synthetic.
The maintained executable example uses registry id `synthetic-opencrvs-events-api`, integration
alias `birth-event-search`, and consultation service `birth-event-verification`.
These names identify the synthetic project only.

## Declare the synthetic event lookup

The overlay creates `integrations/birth-event-search/integration.yaml` with this exact contract:

```yaml
version: 1
id: synthetic-opencrvs-events-search
revision: 1

source:
  product: opencrvs-events-api
  versions:
    unverified: [develop-synthetic-shape-2026-07-30]
  auth:
    type: oauth2_client_credentials
    request: json
    response_profile: oauth2_bearer_no_expiry
  allow:
    - method: POST
      path: /api/events/events/search
      semantics: read_only
  response:
    format: json
    max_bytes: 64KiB

input:
  tracking_id:
    role: selector
    type: string
    maxLength: 32
    pattern: "^TRK-SYNTH[0-9]{6}$"

capability:
  script:
    file: adapter.rhai

outputs:
  event_type:
    type: string
    maxLength: 32
  registered:
    type: boolean

limits:
  calls: 1
  source_bytes: 128KiB
  request_bytes: 16KiB
  deadline: 10s
```

The product and version fields record review context.
They do not select an executor or grant source access.
The allow policy and environment binding own that authority.

The overlay replaces the integration entry in `registry-stack.yaml` with:

```yaml
integrations:
  birth-event-search:
    file: integrations/birth-event-search/integration.yaml
```

## Bind OAuth and source origins

The overlay binds the integration in `environments/local.yaml`:

```yaml
integrations:
  birth-event-search:
    source:
      origin: https://events.opencrvs.invalid
      credential:
        client_id: { secret: OPENCRVS_EVENTS_CLIENT_ID }
        client_secret: { secret: OPENCRVS_EVENTS_CLIENT_SECRET }
        generation: 1
      oauth:
        origin: https://identity.opencrvs.invalid
        path: /oauth/token
        generation: 1
```

The same file selects the maintained synthetic scenario:

```yaml
development:
  source_mode: synthetic
  default_integration: birth-event-search
  default_fixture: birth-event-match
```

The `.invalid` origins prevent accidental contact with a real deployment.
The environment stores secret references, not values.
Relay owns token acquisition, the authorization header, and the source call.
Rhai scripts and consultation callers receive no client secret, token, or token response.

## Map the minimized outputs

The overlay creates `integrations/birth-event-search/adapter.rhai`:

```rhai
fn consult(ctx) {
    let exact_tracking_id = #{
        type: "exact",
        term: ctx.input.tracking_id
    };
    let birth_event_clause = #{
        eventType: "birth",
        trackingId: exact_tracking_id
    };
    let response = source.post_json("/api/events/events/search", #{
        query: #{
            type: "and",
            clauses: [birth_event_clause]
        },
        limit: 2,
        offset: 0
    });
    if response.status != 200 {
        return result.fail(failure.source_rejected);
    }

    let events = response.body.results;
    if response.body.total == 0 && events.len == 0 {
        return result.no_match();
    }
    if response.body.total > 1 || events.len > 1 {
        return result.ambiguous();
    }
    if response.body.total != 1 || events.len != 1 {
        return result.fail(failure.source_rejected);
    }

    let event = events[0];
    if event.trackingId != ctx.input.tracking_id {
        return result.fail(failure.subject_mismatch);
    }
    if event.type != "birth" {
        return result.fail(failure.source_rejected);
    }

    result.match(#{
        event_type: event.type,
        registered: event.status == "REGISTERED"
    })
}
```

The adapter constructs the closed output object field by field.
It does not return the response, event id, tracking id, declaration, OAuth material, or
source-only metadata.

## Keep one consultation-backed service

The overlay replaces the starter service in `registry-stack.yaml` with:

```yaml
services:
  birth-event-verification:
    kind: consultation_api
    version: 1
    purpose: birth-event-registration-verification
    legal_basis: public-service-delivery
    consent: not_required
    consultations:
      event:
        integration: birth-event-search
        input:
          tracking_id: request.target.identifiers.opencrvs_tracking_id
```

The service declares exactly one consultation, and that consultation derives from exactly one
declared integration.
There is no self-attested, source-free, or caller-defined fallback: the only way to reach an
answer is the authorized source read.

## Author the synthetic match fixture

The exact `integrations/birth-event-search/fixtures/match.yaml` file is:

```yaml
name: birth-event-match
classification: synthetic
input: { tracking_id: TRK-SYNTH000001 }
interactions:
  - expect:
      method: POST
      path: /oauth/token
      headers: { Accept: application/json, Content-Type: application/json }
      body: { grant_type: client_credentials }
    respond:
      status: 200
      headers: { Content-Type: application/json }
      body:
        access_token: SYNTHETIC_FIXTURE_TOKEN
        token_type: Bearer
  - expect:
      method: POST
      path: /api/events/events/search
      body:
        query:
          type: and
          clauses:
            - eventType: birth
              trackingId: { type: exact, term: TRK-SYNTH000001 }
        limit: 2
        offset: 0
    respond:
      status: 200
      body:
        total: 1
        results:
          - id: 00000000-0000-4000-8000-000000000001
            type: birth
            status: REGISTERED
            trackingId: TRK-SYNTH000001
            declaration:
              child:
                name: Synthetic Source-Only Name
            ignored_source_metadata: synthetic-source-only
expect:
  outcome: match
  outputs:
    event_type: birth
    registered: true
```

The public overlay also contains the exact synthetic fixtures for no match, ambiguity, source
rejection, subject mismatch, malformed source response, timeout, OAuth redirect, OAuth media type,
token type, extra-member, and expiry rejection.
The complete test also derives authorization-before-source and output-minimization cases.

## Prove the offline cases

Run the focused synthetic trace, then every fixture:

```sh
registryctl test \
  --integration birth-event-search \
  --fixture birth-event-match \
  --trace
registryctl test
```

The trace may contain fixture-authored synthetic values.
It must not contain a client secret, access token, or token response.

## Prove the local product path

Run the generic development path:

```sh
registryctl dev --detach
registryctl dev smoke
registryctl dev down
```

The denial scenario reports zero token and source calls.
The authorized scenario reports one token call, one source call, and
`minimized_claim_ids=none`, because this project releases no attributes and returns only the
declared consultation outputs.

## Record the evidence limits

State all of these limits with the case-study result:

- The request and response are synthetic.
- The OAuth profile is the exact closed profile declared in the project.
- The Rhai mapping is the reviewed script digest.
- The outputs are the exact ids declared in the project.
- Only the executed negative cases have evidence.

Do not claim live OpenCRVS compatibility, maintainer endorsement, country-configuration
conformance, native deployment support, or correctness for another API shape.
Real interoperability evidence requires a separately authorized test against a named release and
country configuration.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| The real OpenCRVS contract differs | This page uses a synthetic shape. | Replace the path, OAuth profile, mapping, and fixtures from source-owner review before testing. |
| The token fixture accepts extra fields | The selected OAuth profile is not enforced strictly. | Use the closed profile and rejection fixtures for unaccepted members. |
| The adapter returns the source event | The output contract is wider than the claim requires. | Construct the smallest typed output object. |
| A denied request increments a source counter | Authorization did not precede token acquisition or source access. | Stop the runtime and report the failure through the repository security process. |

## Obtain the export for the operated registry

Ask the BReg operator for the exact reviewed package identity, its generated
OpenAPI, and a source export made from the authored project matching that package.
Keep the stable source and connection IDs agreed in the local tutorial. Matching
OpenAPI shapes alone do not establish matching read authorization or derived
lookup behavior.

For an already activated registry, record the activated package identity. For a
planned successor, record its candidate identity and defer activation to
[Coordinate a breaking update](#coordinate-a-breaking-update). BReg package
signing, migration and activation remain
separate privileged operations. Follow
[Build a BReg production candidate](../build-a-breg-production-candidate/).

Place the reviewed export at `exports/registry-status-operated`. Compare and
accept its ordinary source files before binding the new environment:

```sh
evidencectl source diff ./exports/registry-status-operated --project ./evidence
evidencectl source update ./exports/registry-status-operated --project ./evidence
```

Without a target these commands validate the authored source graph and report
structural impact. Resolve changes to facts, selectors or extraction explicitly.
Update the question meaning and fixtures when necessary. If local and upstream
files both changed, use the resolutions described in the
[source export contract](../../products/registry-evidence/source-exports/).
Do not overwrite a customization to make a build pass.

## Author the operated target settings

Keep the reviewed Evidence project and complete environment targets in your
deployment repository. Copy the local settings to a separate file for editing:

```sh
evidencectl target new ./production-settings \
  --settings ./evidence/targets/local/target.yaml
```

The copied `target.yaml` is an `EvidenceTarget`; its `authority` field names the separate
`EvidenceTargetAuthority`. Set the target ID and the authority's `target` to `production`, and keep
both `project` fields equal to the EvidenceProject ID. Review the service identity, authentication,
complete grants, source connections, signer and process bindings before packaging.

The identity administrator supplies the HTTPS issuer, JWKS endpoint, resource audiences and claim
mapping. The authority owner approves complete grants within the definition ceilings. The registry
administrator supplies the protected source origin and dedicated credential references. The signing
operator supplies the public JWK and exact Transit version; the deployment operator owns the
installed bundle, secret and audit paths, private listener and any private CA files.

Use a compatible OpenID Connect issuer for an operated deployment. Its source registration and Evidence caller
registration have different audiences and grants. A source credential must not
carry BReg operator privileges.

Set the source connection in `production-settings/target.yaml` using the approved values. This
example includes optional fields for an issuer that requires both audience
parameters; omit those fields when its registration does not require them:

```yaml
connections:
  registry:
    origin: https://registry.example.invalid
    authentication:
      type: oauth2-private-key-jwt
      tokenEndpoint: https://registry-identity.example.invalid/token
      clientIdRef: secret:file/registry-client-id
      clientAssertionKeyRef: secret:file/registry-client-key
      clientAssertionAudience: https://registry-identity.example.invalid/client-auth
      audience: urn:example:resource:registry
      scope: registry:evidence:lookup
      maximumCacheSeconds: 60
    maximumConcurrency: 4
    admissionTimeoutMilliseconds: 5000
    tokenTimeoutMilliseconds: 5000
```

`clientAssertionAudience` identifies the authorization server for the signed
client assertion. `audience` is the resource-audience form parameter requested
for the access token. Neither is the Evidence caller's audience.

If the source or token endpoint uses a private CA, name `tlsTrustProfile` on the
connection and bind that name to `outboundTls.trustProfiles` with an
absolute `caBundleFile`. Keep system roots enabled. There is no certificate
verification bypass. The [configuration reference](../../reference/evidence-configuration/)
defines the complete authentication union and runtime bindings.

## Bind the production signer

Complete [Configure Transit signing](../move-evidence-to-production-signing/)
before creating the target. Save its independently obtained public JWK at
`evidence-signing-public.jwk.json`.

:::danger[The private signing key never leaves the provider]
Never export the private Transit key, and never reuse the local tutorial's
private key for this deployment. A private key that has left provider custody
cannot be returned to it: the only recovery is a new key, a new public JWK, and a
fresh distribution to every verifier that pinned the old one.
:::

Set `assuranceProfile` to `production`. Place the public JWK under
`production-settings/public-keys/<thumbprint>.jwk.json`, then replace the local signer in
`production-settings/target.yaml` with the matching public-key reference and proxy binding:

```yaml
signer:
  type: transit
  algorithm: ES256
  publicJwkFile: public-keys/<thumbprint>.jwk.json
  unixSocketPath: /run/registry-evidence/transit-proxy.sock
  mount: transit
  keyName: evidence-signing
  keyVersion: 1
  attemptTimeoutMilliseconds: 2000
```

Use the operator's exact selected version, which may differ from this example.
Set `package.root` to the final deployment location, such as
`/srv/evidence/packages/operated-001/bundle`. The local package output may live
elsewhere before transport. Bind production secret and audit paths separately.

```sh
evidencectl target new ./evidence/targets/production \
  --settings ./production-settings/target.yaml
evidencectl target explain ./evidence/targets/production ./evidence --json
evidencectl test ./evidence --target ./evidence/targets/production
```

The explanation reads the project and target authority, compiles its complete grants and reports
the target's connection names. Review the target documents themselves for exact
origins, authority and signing configuration. It does not resolve or print secret
values. Creation is refused when the target directory already exists; edit its
ordinary files or choose another directory.

## Build and hand over exact bytes

```sh
evidencectl package ./evidence --target ./evidence/targets/production \
  --output ./candidate-operated-001
evidence check --runtime-config ./candidate-operated-001/runtime.yaml
```

Package uses the matching Evidence runtime to validate the generated package and required
fixtures before publishing. A refused package publishes nothing at `--output`; rerun the exact
`evidencectl test` command for the complete fixture diagnosis. The check then verifies and compiles
the installed package offline, reading no secret material, and reports the package digest and the
number of requirements it compiled. Run it in a context where the target runtime file's absolute
`package.root` already resolves: a packaging host that does not carry that path cannot run the
check until the package is installed. The target-host proof below adds
`--require-runtime-dependencies`, which validates mounted secret material exactly as startup does.
Neither command
contacts the source, caller issuer or Transit service.

Hand over the authored revision, operated source-export baseline, complete target,
exact bundle digest and candidate, the emitted runtime and compiled authority, required secret references, and
the approved synthetic verification case. The candidate contains immutable `bundle/` with `SHA256SUMS` and governed Evidence artifacts, plus
separate `runtime.yaml` and `compiled-authority.yaml`. Install `bundle/` at the emitted runtime's
`package.root`; retain the handoff documents separately.
Development services, credentials, tokens and live responses stay outside it.

Named connections share an HTTP client, eligible OAuth token cache and bounded
source capacity inside one Evidence process. They do not cache source facts or
share authority across callers. Size the connection capacity for the registry's
budget and multiply by your Evidence replica count when planning total load.

For future source changes, add the production target to `source diff` before
updating to compare actual affected requirement revisions. A data-only record
update needs no source export. A credential rotation that preserves the governed
identity uses the [source credential rotation procedure](../../products/registry-evidence/source-credential-rotation/).

## Provision and check the target host

The operator places the exact package at the configured `package.root` and makes the
package and separately supplied runtime non-writable to the service identity. Provision owner-only
source client files, independent audit and subject-binding HMAC secrets, durable
audit storage, private CA files when needed, and the workload-local Transit
proxy.

:::caution[Development material stays off the operated host]
Do not copy `.evidence/dev` or `.breg/dev` to the host. They hold the local
exercise's session key pairs, generated database roles, local TLS material and
credentials. Anything from them that reaches an operated host has to be treated
as disclosed and replaced through the operator's own provisioning.
:::

Under the intended service identity, after those dependencies exist:

```sh
evidence authority activate --runtime-config '<candidate>/runtime.yaml' \
  --document '<candidate>/compiled-authority.yaml'
evidencectl doctor --runtime-config '<candidate>/runtime.yaml'
evidence check --runtime-config '<candidate>/runtime.yaml' --require-runtime-dependencies
evidence serve --runtime-config '<candidate>/runtime.yaml'
```

Use your configured deployment target. `evidencectl doctor` reports every artifact
the runtime would otherwise refuse at startup for wrong permissions, ownership
or secret exposure, all in one pass instead of one restart at a time; fix each
named artifact and rerun it until it exits zero. If `check
--require-runtime-dependencies` still refuses, it exits nonzero with `a
required runtime dependency is unavailable`; inspect the named dependency
(secrets, audit storage, the Transit proxy) before retrying `serve`. The
runtime also checks signer custody and exact public-key agreement. Wait for
`GET /ready` before routing an approved synthetic request through the HTTPS
boundary. Readiness alone does not prove the intended BReg lookup grant.

Follow [Request Evidence from an application](../request-evidence-from-an-application/)
using an independently provisioned caller, approved pinned Evidence signing
keys, the reviewed operated contract catalog, and a synthetic record. Verify the
signature, expected identities, purpose, audience, nonce, contract revision,
assurance and answer. Do not adopt a fetched catalog or key as trusted merely
because the endpoint returned it. Exercise a separately ungranted caller and
confirm that no assertion is accepted.

Before enabling application traffic, check the source identity directly. Have
the identity operator provision an owner-only `source-authorization.curl` file
containing a short-lived authorization header for the dedicated source client.
Keep it outside the candidate. Create `source-lookup.json` with the approved
synthetic selector, such as this example for the tutorial registry:

```json
{"selector":"by-code","values":{"code":"SYNTHETIC-ACTIVE"}}
```

Use the operated HTTPS origin and exact route from its reviewed export:

```sh
curl --silent --show-error --fail-with-body \
  --config ./source-authorization.curl \
  --header 'Content-Type: application/json' \
  --data-binary @source-lookup.json \
  'https://registry.example.invalid/v1/records/records:lookup?accessProfile=evidence-source&$select=code,status' \
  --output source-lookup-response.json --write-out 'HTTP %{http_code}\n'
```

Read the synthetic record's UUID from `data.recordIdentifier` in the successful
lookup response. Have the BReg operator first confirm that their own credential
can read that exact record through the `operator` profile. They run this positive
control in their own private workspace; their credential never enters Evidence:

```sh
curl --silent --show-error --fail-with-body \
  --config './operator-authorization.curl' \
  'https://registry.example.invalid/v1/records/records/<recordIdentifier>?accessProfile=operator' \
  --output operator-read-response.json --write-out 'HTTP %{http_code}\n'
```

Replace `<recordIdentifier>` with the returned UUID in both GET commands. After
the operator confirms HTTP 200, request the same record and profile using only
the source credential:

```sh
curl --silent --show-error --fail-with-body \
  --config ./source-authorization.curl \
  'https://registry.example.invalid/v1/records/records/<recordIdentifier>?accessProfile=operator' \
  --output source-refusal.json --write-out 'HTTP %{http_code}\n'
```

For this model, the source GET exits
nonzero with HTTP 404, concealing the ungranted operator resource. It performs no
write. If this GET succeeds with the source credential, keep traffic disabled
and correct the source registration or profile before retrying. A collection
request cannot replace this check: the teaching operator has no list grant, so
it would also be refused. Keep these synthetic responses in the private verifier
workspaces.

An offline fixture pass, complete target or successful token exchange is not a
substitute for these deployed authorization checks.

## Coordinate a breaking update

A source import updates authored files. It cannot atomically change a registry
package, running Evidence bundle and consumer expectation. For a change to
consumed lookup meaning or question semantics:

1. Prepare the BReg and Evidence candidates and review the actual affected
   requirement revisions with consumers. Test the new pair against disposable
   provider data before touching the operated pair.
2. Pause and drain affected Evidence traffic. Pause the whole instance when
   per-question draining is unavailable. Retain the approved previous candidates
   and the BReg operator's recovery plan.
3. Activate and verify the new BReg package through its maintained procedure.
   Check the intended synthetic lookup with the source workload identity.
4. Start the exact new Evidence candidate, wait for readiness and verify a fresh
   synthetic assertion using the new approved consumer expectations.
5. Resume the coordinated consumers only after those checks pass.

If a check fails, keep traffic paused. Follow the BReg recovery plan and restore
a mutually compatible provider, Evidence candidate and consumer contract before
resuming. Preserve the audit streams from both runtimes and the BReg operator
commands. For file destinations, collect the final active files after their writers
stop, along with the sealed segments. Confirm receipt of every collected file in
your append-only archive before local retention deletes it; the runtimes provide
no local chain-verification command. Follow the
[audit shipping procedure](../../operate/retention-and-persistent-state/#ship-registry-evidence-audit-records-off-host).

:::caution[A migration may not reverse]
Database migrations may constrain reversal, so activating the new BReg package is
the step in this cutover that reinstating the previous binary does not always
undo. Choose the migration's reviewed recovery path rather than assuming a
rollback restores the earlier state.
:::

Keeping an old consumer catalog alone does not keep old behavior available. A
provider change can alter a lookup even when the HTTP schema stays the same, so
compare the operated source export and consumed behavior revision as part of
every coordinated change.

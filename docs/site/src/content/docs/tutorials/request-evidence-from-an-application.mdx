## Give the application its own identity

Enter the normalized project:

```sh test-cwd="first-evidence-assertion"
cd adult-status
```

Register `age-check-app` under the existing `standalone-service` target profile:

```sh
evidencectl access client add age-check-app \
  --access-profile standalone-service \
  --generate-local-key
```

The reviewable registration contains the client's public key and access-profile assignment. Its
private key stays owner-only at `.evidence/clients/age-check-app/private.jwk`. Registration selects
authority that the target already defines; it cannot create or widen a grant.

Create an owner-only client profile. It holds references to the private key and deployment
metadata, never the private key itself:

```sh
evidencectl client profile create \
  --base-url http://127.0.0.1:18080 \
  --client-id age-check-app \
  --private-key-file .evidence/clients/age-check-app/private.jwk \
  --local-loopback-discovery \
  --client-assertion-audience http://127.0.0.1:8082 \
  --resource urn:registrystack:evidence:local:gateway \
  --scope evidence:request \
  --expected-audience urn:example:audience:standalone-app \
  --expected-issuer urn:registrystack:evidence:local:issuer \
  --expected-provider urn:registrystack:evidence:local:provider \
  --output age-check-client.json
```

Local development publishes a local token resource, assertion issuer, and provider identity while
preserving the project's governed assertion audience and target-required scope. A deployed client
pins the corresponding reviewed deployment values.

For a deployed service, store the private key in a secret manager and pin reviewed trust material
or use authenticated HTTPS discovery. Loopback discovery is an explicit local-development mode.

## Start the local services

In another terminal, start the synthetic source:

```sh test-cwd="first-evidence-assertion/adult-status" test-background="http://127.0.0.1:8081/healthz"
python3 serve-source.py \
  --port 8081 \
  --token-file .generated/secrets/synthetic-source-token
```

Back in the project terminal, start Registry Evidence and its local issuer:

```sh
evidencectl dev start . \
  --target local-target.yaml \
  --evidence-port 18080 \
  --issuer-port 8082
```

```text test-excerpt
Evidence ready at http://127.0.0.1:18080
Issuer ready at http://127.0.0.1:8082
```

## Request and verify in application code

The maintained client package is `registry-stack-client` and imports as `registry_client`. Install
the package at the exact version of the running service. The tutorial gate supplies a wheel built
from this checkout.

```sh test-skip="the gate installs the matching client wheel before replaying this page"
version="$(evidencectl --version | awk '{print $2}')"
python3 -m venv .venv
. .venv/bin/activate
python -m pip install "registry-stack-client==${version}"
```

Create a small application:

```python title="request_adult_status.py" test-file
from registry_client.evidence import EvidenceClient

client = EvidenceClient.from_profile("age-check-client.json")
verified = client.request("adult-status", **{"record-id": "adult"})

is_adult = verified.values["adult"]
if is_adult is not True:
    raise RuntimeError("the synthetic adult record did not produce adult status")
print("VERIFIED adult=true")
```

Run it:

```sh
python3 request_adult_status.py
```

```text test-expect
VERIFIED adult=true
```

`request` reads the published contract, obtains a short-lived token, closes a fresh nonce and
verification expectations, sends one request, and verifies the response. Application decisions
must use `verified.values`, never an undecoded response body.

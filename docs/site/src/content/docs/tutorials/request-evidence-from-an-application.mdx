If you build an application that asks Registry Evidence for an assertion, you give it its own
identity, send one request from a small program, verify the response before you read it, decide
from the verified value, and keep what you need to stand behind that decision later.

## Give the application an identity

Under `rstack dev`, an application is a person: a subject, a client name, and the token claims its
calls carry. Add `age-check-app` to `dev.yaml` with the same grant `caller` holds:

```diff lang="yaml" title="dev.yaml" test-edit
         claims: {evidence_audience: "urn:example:audience:standalone-app"}
+  age-check-app:
+    subject: "urn:registrystack:evidence:local:client:age-check-app"
+    client: age-check-app
+    grants:
+      evidence:
+        profile: standalone-service
+        scopes: ["evidence:request"]
+        claims: {evidence_audience: "urn:example:audience:standalone-app"}
 scenarioFile: tests/scenarios.yaml
```

In a new terminal, read the run back from `run.json` and redefine the helper that fetches a token
header file:

```sh test-cwd="first-evidence-assertion/adult-status"
run_id="$(jq -r .run_id run.json)"
evidence_url="$(jq -r .products.evidence run.json)"
runtime_config="$(jq -r .runtimeConfigs.evidence run.json)"
headers_for() {
  rstack dev token "$run_id" --as "$1" | awk '$1 == "evidence" && $2 == "headers" {print $3}'
}
```

```sh test-cwd="first-evidence-assertion/adult-status"
rstack dev stop "$run_id"
rstack dev check .
rstack --format json dev start . --ttl 2h > run.json
run_id="$(jq -r .run_id run.json)"
```

## Prepare the request

Preparation writes the request body and the verification context: the provider keys and
expectations the application will hold the response to, fixed before anything is sent. It takes the
run's Evidence address, the application's token and the run's runtime configuration, which names the
trusted keys:

```sh
rstack evidence request prepare adult-status \
  --evidence-url "$evidence_url" \
  --header @"$(headers_for age-check-app)" \
  --runtime-config "$runtime_config" \
  --purpose age-check \
  --subject subject:record-id=adult \
  --name age-check-app
```

```text test-expect
Prepared verification context: .evidence/requests/age-check-app/verification.json
Prepared authorization: .evidence/requests/age-check-app/authorization.curl
```

## Request and decide in Python

Install `registry-stack-client` at the version `rstack evidence --version` prints:

```sh test-skip="the gate installs the matching client wheel before replaying this page"
python3 -m venv .venv
. .venv/bin/activate
python -m pip install "registry-stack-client==<version>"
```

Save this program as `request_adult_status.py`. It sends the prepared request with the
application's token, verifies the signed response against the prepared context before it returns
a value, and keeps three files:

```python title="request_adult_status.py" test-file
import sys
import time
import urllib.request
from pathlib import Path

from registry_client.evidence import verify_retained

url, headers_file, prepared = sys.argv[1], sys.argv[2], Path(sys.argv[3])
header_name, header_value = Path(headers_file).read_text().strip().split(": ", 1)

request = urllib.request.Request(
    f"{url}/v1/evidence",
    data=(prepared / "request.json").read_bytes(),
    headers={
        "Content-Type": "application/json",
        "Accept": "application/jose+json",
        header_name: header_value,
    },
)
with urllib.request.urlopen(request) as reply:
    response = reply.read()
decided_at = int(time.time())

context = (prepared / "verification.json").read_bytes()
verified = verify_retained(context, response)

Path("adult-status.response.jws").write_bytes(response)
Path("adult-status.retained.json").write_bytes(context)
Path("adult-status.verified-at.txt").write_text(f"{decided_at}\n")

if verified.evidence["supportedValues"][0]["value"] is not True:
    raise RuntimeError("not an adult")
print("VERIFIED adult=true")
```

`verify_retained` checks the response against the prepared context and raises `VerificationError`
when it does not hold, so `verified.evidence` is the only thing to decide from. The program keeps
three files:

- `adult-status.response.jws`, the signed assertion exactly as received.
- `adult-status.retained.json`, the retained verification: the keys and expectations fixed before
  the request was sent, without selector values.
- `adult-status.verified-at.txt`, the decision instant in Unix seconds.

Tokens last at most five minutes, so ask for the header file as you run it:

```sh
python3 request_adult_status.py "$evidence_url" "$(headers_for age-check-app)" .evidence/requests/age-check-app
```

```text test-expect
VERIFIED adult=true
```

## Create the client profile

Against a deployed service, the maintained client requests and verifies in one call from a client
profile. The profile holds everything your code would otherwise hard-code about the deployment. A
run issues tokens only through `rstack dev token`, so this page sends the request itself; create the
profile when the operator has registered your application and given you these values:

```sh test-skip="needs a deployed service and the client registration its operator issues"
rstack evidence client profile create \
  --base-url https://evidence.example.com \
  --client-id age-check-app \
  --private-key-file app-key/client-assertion-p384-private-jwk \
  --expected-audience urn:example:audience:standalone-app \
  --expected-issuer <issuer> \
  --expected-provider <provider> \
  --resource <resource> \
  --scope evidence:request \
  --output age-check-client.json
```

It pins the base URL, issuer, provider, and audience the client insists on, and the token request
it makes ([Request an access token](../../configure/request-an-access-token/) explains those
values). It refers to the private key without containing it. Then
`EvidenceClient.from_profile("age-check-client.json").request("adult-status", **{"record-id": "adult"})`
returns the verified values and the retained verification this page builds from the prepared
context.

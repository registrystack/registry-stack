## Preserve four independent inputs

Enter the project left by the first tutorial. Evidence Gateway, its issuer, and the source can all
remain stopped.

```sh test-cwd="first-evidence-assertion"
cd adult-status
```

The first tutorial left these files:

- `adult-status.jws.json`, the exact untrusted response bytes;
- `adult-status.verified.json`, the payload published by the first successful verification;
- `.evidence/requests/adult-status/verification.json`, the owner-only context fixed before the
  response existed;
- `.evidence/requests/adult-status/verified-at.txt`, the recorded start of that successful
  verification.

Create an owner-only consumer record. Copy the response exactly, and split the local context into
the two inputs a production relying party governs separately.

```sh
umask 077
install -d -m 700 consumer-record
python3 - <<'PY'
import json
import shutil
from pathlib import Path

request_dir = Path(".evidence/requests/adult-status")
record_dir = Path("consumer-record")
context = json.loads((request_dir / "verification.json").read_text())

shutil.copyfile("adult-status.jws.json", record_dir / "response.jws.json")
shutil.copyfile(request_dir / "verified-at.txt", record_dir / "verified-at.txt")
(record_dir / "trusted-jwks.json").write_text(
    json.dumps(context["trustedJwks"], indent=2) + "\n"
)
(record_dir / "verification-policy.json").write_text(
    json.dumps(context["verificationPolicy"], indent=2) + "\n"
)
PY
```

The tutorial derives the JWKS and policy from a private context that `evidencectl request prepare`
created before it received a response. A production consumer obtains these from its own reviewed
trust configuration and transaction state. Do not take keys, expected claims, or a policy from the
response or from live discovery during verification.

## Replay the accepted response

Check the retained policy, then verify at the instant recorded immediately before the first
successful verification. The first tutorial published that owner-only time only after verification
succeeded.

```sh
evidence check-policy \
  --verification-policy consumer-record/verification-policy.json
evidence verify \
  --jws consumer-record/response.jws.json \
  --jwks consumer-record/trusted-jwks.json \
  --policy consumer-record/verification-policy.json \
  --at "$(cat consumer-record/verified-at.txt)" \
  > consumer-record/verification.txt
```

`evidence verify` opens no listener, contacts no issuer, fetches no discovery document, and calls
no source. It prints the payload only after the pinned key signed the exact bytes, every retained
expectation matched, and the assertion was current at the named instant. `evidencectl verify`
internally used its current clock and does not expose that exact instant, so the retained time is
precisely the recorded start of the successful operation. It is not the assertion's signed
`issuedAt`. Application code should pass and retain its own explicit decision instant when its
verifier supports that contract.

Application code can now publish verified data from `consumer-record/verification.txt` to decision
logic.

## Replay the same decision

Later, re-run the verifier with the retained time. The answer is about that historical decision,
even if the assertion is no longer current today.

```sh
evidence verify \
  --jws consumer-record/response.jws.json \
  --jwks consumer-record/trusted-jwks.json \
  --policy consumer-record/verification-policy.json \
  --at "$(cat consumer-record/verified-at.txt)"
```

`authentic` and `currently-valid` answer different questions. A stored response can remain
authentic after its validity window, but it cannot support a new current decision. Replaying the
retained instant accounts for the earlier decision; verifying at the current time answers whether
the same response is usable now.

## Prove the response remains untrusted input

Change one encoded payload byte in a copy. The pinned key, policy, and historical instant stay the
same.

```sh
python3 - <<'PY'
import json
from pathlib import Path

source = Path("consumer-record/response.jws.json")
document = json.loads(source.read_text())
payload = document["payload"]
document["payload"] = ("A" if payload[0] != "A" else "B") + payload[1:]
Path("consumer-record/tampered.jws.json").write_text(json.dumps(document) + "\n")
PY
```

Verification refuses the changed bytes and never prints a verified payload.

```sh test-exit="1"
evidence verify \
  --jws consumer-record/tampered.jws.json \
  --jwks consumer-record/trusted-jwks.json \
  --policy consumer-record/verification-policy.json \
  --at "$(cat consumer-record/verified-at.txt)"
```

## Put the boundary in application code

Preserve this order in a consuming application:

1. Generate and retain the request nonce and every policy expectation before sending the request.
2. Select the trusted provider identity and pinned key set through reviewed configuration.
3. Store the returned bytes as untrusted input.
4. Record a verification instant, verify the exact response format against the retained policy and
   keys, and publish the instant only after success.
5. Publish only the verified payload to decision logic.
6. Retain the instant, result, response digest, and policy and JWKS revisions under your retention
   rules.

Use distinct types, files, or process boundaries for unverified bytes and verified values. An
application object that looks usable before verification makes accidental trust more likely.

Retain enough to repeat the decision without asking the provider to recreate it: the signed bytes
and format, the original application transaction, the expected request and subject bindings, the
pinned key revision, the verification policy and instant, and the verified result or its governed
digest. The source record does not belong in this verifier record.

The opaque subject binding is meaningful only for the audience and purpose that produced it. Keep
the application's mapping from its person or case to the transaction in its own protected records;
the assertion does not disclose that local identifier.

## If a retained input is missing

Missing input is a failed verification record, not a reason to fetch replacement trust. Rerun the
request and verification steps in [Get your first Evidence Gateway assertion](../first-evidence-assertion/)
when `adult-status.jws.json`, `adult-status.verified.json`,
`.evidence/requests/adult-status/verification.json`, or
`.evidence/requests/adult-status/verified-at.txt` is absent. A production retention policy must
decide whether to reject the operation, recover an authoritative archived revision, or make a new
request.

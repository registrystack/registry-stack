Continue from the spreadsheet project in `my-first-registry`.
You will inspect one Relay-backed claim, change its authored policy, and verify the result without
adding another product, runtime, or trust path.

<QuickstartMeta
  outcome="A reviewed change to one consultation-backed predicate claim, verified offline and through the disposable local runtime."
  time="About 15 minutes after completing the spreadsheet tutorial"
  level="Local development with synthetic records"
  prerequisites={['The unmodified my-first-registry project', 'A released Registryctl 1.0 installation', 'Docker Engine', 'Docker Compose 2.35.0 or later'] }
/>

The workbook, identifiers, and credentials remain synthetic.

## Enter the project

Run every command from the project created in the preceding tutorial:

```sh
cd my-first-registry
```

The spreadsheet template already contains public Relay, consultation Relay, and Notary inputs.
There is no separate `add notary` step in Registryctl 1.0.

## Inspect the consultation boundary

Open `registry-stack.yaml`.
The `public-works-verification` service has exactly one consultation:

```yaml
consultations:
  project:
    integration: project-record-snapshot
    input:
      project_id: request.target.identifiers.project_id
claims:
  project-record-exists:
    cel: project.matched
    disclosure: predicate
  project-status-accepted:
    cel: 'project.matched && project.status == "active"'
    disclosure: predicate
```

Relay performs the exact snapshot lookup and releases only `status` to Notary.
Notary evaluates the two predicate claims.
The caller never supplies a fallback claim value or alternate Common Expression Language (CEL)
root.

`project-status-accepted` is project policy.
It does not establish programme eligibility, fraud, or another legal conclusion.

## Observe the initial planned result

Run the planned fixture with its synthetic trace:

```sh
registryctl test \
  --integration project-record-snapshot \
  --fixture planned \
  --trace
```

The trace reports a matched synthetic record with `status: planned`.
The initial expectation is:

```yaml
claims:
  project-record-exists: true
  project-status-accepted: false
```

This is a policy non-match.
It is distinct from the `no-match` fixture, which means the bounded snapshot lookup found no
record for that synthetic key.

## Change the authored policy

In `registry-stack.yaml`, replace the active-only expression:

```yaml
project-status-accepted:
  cel: 'project.matched && project.status == "active"'
  disclosure: predicate
```

with:

```yaml
project-status-accepted:
  cel: 'project.matched && (project.status == "active" || project.status == "planned")'
  disclosure: predicate
```

The expression remains rooted in the single `project` consultation.
Do not replace it with a caller-supplied value or source-free assertion.

In `integrations/project-record-snapshot/fixtures/planned.yaml`, update the expected claim:

```yaml
claims:
  project-record-exists: true
  project-status-accepted: true
```

Keep the source observation `status: planned`.
Only the authored policy and its expectation changed.

## Verify the policy change offline

Run the focused trace:

```sh
registryctl test \
  --integration project-record-snapshot \
  --fixture planned \
  --trace
```

The planned fixture now reports both claims as true.

Run the complete fixture set:

```sh
registryctl test
```

The match and no-match fixtures plus their derived security cases must still pass.

Fixture evidence is bounded to the synthetic workbook and declared lookup.
A false existence predicate means no match in that source snapshot, not global nonexistence,
fraud, ineligibility, or a legal negative.

## Select the changed scenario for development

In `environments/local.yaml`, select the planned fixture as the default development scenario:

```yaml
development:
  source_mode: synthetic
  default_integration: project-record-snapshot
  default_fixture: planned
```

Each environment declares one default scenario.
Registryctl does not use a command-line fixture selector for `dev`.

## Run the changed product path

Start the disposable environment:

```sh
registryctl dev --detach
```

Registryctl prints an owner-only `curl --config` request after startup.
That standard HTTP request uses a generated credential file without placing the credential in
the shell command or Registryctl report.

Run the maintained denial and authorized scenarios:

```sh
registryctl dev smoke
```

The denial scenario must report zero source work.
The authorized scenario must report one snapshot lookup and only
`project-record-exists,project-status-accepted` as minimized claim identifiers.

It is a local development request, not a deployed-system compatibility runner.

## Review the effective change

Review the redacted plan:

```sh
registryctl check --explain
```

Confirm that:

- The exact snapshot selector remains in consultation Relay
- The consultation output remains only `status`
- The service still has exactly one consultation
- Both claims remain predicate disclosures
- The policy change does not alter the workbook or source authority

Build the changed unsigned inputs:

```sh
registryctl build
```

The change affects the product lanes reported by Registryctl.
`build` does not sign or activate them.

## Stop the local environment

Stop the workloads and remove disposable state:

```sh
registryctl dev down
```

The authored policy and fixture edit remain in the project.

## What you built

You changed one predicate policy while preserving the exact Relay consultation that supplies its
evidence.
The offline fixtures proved the planned and no-match meanings.
The local runtime proved authorization before one bounded snapshot lookup and value-free
reporting.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| The planned fixture remains false | The claim expression or fixture expectation was not updated. | Keep the source observation unchanged and update both authored policy surfaces. |
| Another fixture fails | The policy change altered a broader contract. | Review every reported fixture before building. |
| `dev` still selects `match` | The local default scenario was not changed to `planned`. | Update `development.default_fixture` and rerun `dev`. |
| Smoke performs source work on denial | Authorization did not stop the snapshot lookup. | Stop the runtime and report the failure through the repository security process. |
| A generated artifact differs | A file under `.registry-stack/` was edited or replaced. | Remove the disposable generated closure and rerun Registryctl from authored files. |

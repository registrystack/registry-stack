Use Registry Notary when a caller needs a bounded claim result instead of a
registry row. This tutorial evaluates one synthetic claim entirely offline,
proves its match and no-match meanings, and builds the validated Relay and
Notary inputs that an operator would review next.

<QuickstartMeta
  outcome="A canonical project whose synthetic fixtures prove a bounded population-record-exists claim and whose unsigned Relay and Notary inputs pass product validation."
  time="About 10 minutes"
  level="Local offline authoring"
  prerequisites={['registryctl 0.14.0 and its matching image lock', 'A shell and a text editor'] }
/>

This task does not contact a registry, start a service, issue a credential, or
prove wallet interoperability. Its fixtures are synthetic and have no network,
credential, or filesystem authority.

## Create the canonical claim project

Initialize the exact snapshot starter:

```sh
registryctl init --from snapshot --project-dir my-first-claim
cd my-first-claim
```

Registryctl copies one canonical `registry-stack.yaml` project, its
`person-snapshot` integration, two synthetic fixtures, a logical entity, and a
local environment. You edit authored project files, never generated Relay or
Notary YAML.

## Evaluate the matching fixture

Run the matching fixture with its safe trace:

```sh
registryctl test \
  --project-dir . \
  --integration person-snapshot \
  --fixture snapshot-match \
  --trace
```

The report begins with a pass for `person-snapshot.snapshot-match`. Its bounded
result is:

```text
outcome: match
claims:
  population-record-exists: true
  population-registration-status: active
  residency-confirmed: true
```

The trace shows the typed selector name, the fixed snapshot operation,
minimized output names, claim identifiers, outcome class, and derived negative
cases. It does not grant the fixture access to a real source or retain a
subject record.

`population-record-exists: true` means this exact project fixture produced one
validated match for the selected snapshot key. It does not prove that the
record exists in every registry, that the caller is the person, or that the
person is eligible for a service.

## Evaluate the no-match fixture

Run the maintained no-match case:

```sh
registryctl test \
  --project-dir . \
  --integration person-snapshot \
  --fixture snapshot-no-match \
  --trace
```

The result is:

```text
outcome: no_match
claims:
  population-record-exists: false
  population-registration-status: null
  residency-confirmed: null
```

`false` means this bounded source observation produced no match. It does not
prove global nonexistence, identity fraud, ineligibility, or any legal
negative. Value claims remain `null` because no source row was selected.

The exact snapshot selector is the entity primary key. A duplicate key is
rejected when the snapshot is materialized, so an ambiguous multiple-row result
is not applicable to this one-key journey.

## Inspect the governed claim

Read the small authored service and integration:

```sh
sed -n '1,180p' registry-stack.yaml
sed -n '1,180p' integrations/person-snapshot/integration.yaml
```

The important service boundary is:

```yaml
services:
  benefits-eligibility:
    kind: evidence
    version: 1
    purpose: benefits-eligibility
    legal_basis: public-service-delivery
    consent: not_required
    access: { scopes: ["evidence:population:read"] }
    consultations:
      person:
        integration: person-snapshot
        input:
          person_id: request.target.identifiers.population_person_id
    claims:
      population-record-exists:
        cel: person.matched
        disclosure: predicate
      population-registration-status:
        output: person.registration_status
        disclosure: value
      residency-confirmed:
        output: person.residency_confirmed
        disclosure: predicate
```

The caller supplies the typed identifier. Relay owns the exact source lookup
and returns only the reviewed `registration_status` and
`residency_confirmed` outputs to the generated consultation boundary. Notary
owns claim evaluation and disclosure. A claim identifier and boolean are not
raw registry fields.

The project separately binds purpose, legal basis, caller scope, consultation
input, claim expression, value source, and disclosure mode. None is inferred
from the fixture response.

## Run the complete fixture set

Run every synthetic fixture:

```sh
registryctl test --project-dir .
```

The command reports:

```text
PASS: 5/5 fixtures passed
```

This gate validates the project's maintained authorization,
malformed-source, subject-binding, status, match, and no-match fixtures.
It does not contact a registry or check local runtime files and secrets.

## Inspect runtime prerequisites

Ask Registryctl which local runtime prerequisites are available:

```sh
registryctl preflight --project-dir . --environment local
```

A fresh snapshot starter reports:

```text
Registry Stack project "fictional-population-registry" is not locally ready for environment "local".
```

The command exits nonzero because the offline starter does not include an
operator's signing key, caller key fingerprints, materialized source file, or
Relay token file. This expected result inventories runtime prerequisites. It
does not run fixtures, contact a source, or block the remaining offline
authoring steps.

## Validate the authored claim configuration

Validate the project and inspect its value-free effective plan:

```sh
registryctl check --project-dir . --environment local --explain
```

The report begins:

```text
Registry Stack project: fictional-population-registry (valid)
Fixtures: 5/5 passed (offline synthetic)
```

This gate validates the authored project, integration, entity, fixture, and
environment relationships. It also compiles and validates the proposed Relay
and Notary configuration without writing build output or resolving runtime
secrets.

## Compare the disclosure intent

Compare the current authored state with the snapshot starter:

```sh
registryctl compare --project-dir . --environment local --from-starter snapshot
```

Before you change the claim, the result is:

```text
semantic comparison: equivalent; assurance: embedded_exact_release; changes: 0; review plan: generated_no_changes
```

This gate compares claim, scope, purpose, and disclosure intent. It does not
approve a change or observe runtime behavior.

## Build reviewable product inputs

Generate the unsigned Relay and Notary inputs:

```sh
registryctl build --project-dir . --environment local
```

The report begins:

```text
Built Registry Stack project "fictional-population-registry".
  Output: .registry-stack/build/local
  Fixtures: 5/5 passed
```

This gate reruns the fixtures and product validation, then generates separate
reviewable Relay and Notary inputs plus an artifact manifest. It does not
resolve runtime secrets, contact a source, sign the inputs, or activate either
product.

## Review generated product inputs

Review the inventory and generated paths:

```sh
sed -n '1,260p' .registry-stack/build/local/artifact-manifest.json
```

The manifest binds authored inputs and generated outputs by digest. Generated
product files are review output, not a second authoring surface. Do not edit
them.

This local build is unsigned. It does not activate Notary, contact a source,
or grant production approval. An operator must supply reviewed environment
bindings, secrets, network controls, signing, activation, audit, and recovery
before a deployed claim can be trusted.

## Change one disclosure boundary

To stop releasing the registration status as a value, change this authored
claim in `registry-stack.yaml`:

```yaml
population-registration-status:
  output: person.registration_status
  disclosure: value
```

to:

```yaml
population-registration-status:
  output: person.registration_status
  disclosure: redacted
```

The matching fixture still expects the old visible value, so the next test
fails. Update only its reviewed claim expectation in
`integrations/person-snapshot/fixtures/match.yaml`:

```yaml
population-registration-status: redacted
```

Rerun the fixture gate:

```sh
registryctl test --project-dir .
```

The command reports `PASS: 5/5 fixtures passed`. The updated fixture now proves
the reviewed redacted result.

Validate the changed authored configuration:

```sh
registryctl check --project-dir . --environment local --explain
```

The report still begins with
`Registry Stack project: fictional-population-registry (valid)`. The
explanation shows the changed disclosure in the compiled configuration.

Compare the change with the starter:

```sh
registryctl compare --project-dir . --environment local --from-starter snapshot
```

The report now starts with `semantic comparison: different` and lists a
disclosure change.

Generate the changed product inputs:

```sh
registryctl build --project-dir . --environment local
```

The report begins with
`Built Registry Stack project "fictional-population-registry".` The build
reruns validation and writes new generated product inputs and an artifact
manifest. This is an authored policy change with an explicit test, not a
generated-file edit.

## Troubleshooting

| Symptom | Cause | Resolution |
| --- | --- | --- |
| A fixture fails after a claim edit | The maintained expected claim result still represents the old policy. | Review the intended meaning, update the authored fixture expectation, and rerun the full project. Do not make the expectation pass mechanically. |
| `preflight` reports a missing binding | The local environment does not provide one required entity, integration, service, caller, or secret reference. | Correct the human-owned environment file using the stable diagnostic. |
| `check` reports a claim or consultation error | The claim references an unavailable output, purpose, input, integration, or service boundary. | Correct the authored project. Do not bypass the product validator. |
| A generated artifact fails integrity validation | Generated output was changed after compilation. | Discard the generated closure and rebuild from reviewed authored files. |
| The documented recovery does not solve the problem | The offline starter does not cover every claim design. | Open a [public Registry Stack issue](https://github.com/registrystack/registry-stack/issues/new/choose) with the command, stable code, Registryctl version, and safe field names. Do not include identifiers, fixture observations, credentials, or private endpoints. |

Use the released HTTP starter to model one bounded lookup against a registry API.
First test and run the contract with synthetic observations. Then bind the reviewed source in the
authored project files, without changing the Registry Relay boundary.

A project has two product lanes, `relay-public` and `relay-consultation`, and the starter authors
a consultation service over one bounded HTTP source.

<QuickstartMeta
  outcome="A tested bounded HTTP integration, a disposable local runtime, and unsigned inputs for two independently approved product lanes."
  time="About 15 minutes after Registryctl and Docker are installed"
  level="Local development with synthetic records"
  prerequisites={['A released Registryctl 1.0 installation', 'Docker Engine', 'Docker Compose 2.35.0 or later', 'A shell with curl and a text editor'] }
/>

The project and source observations in this tutorial are synthetic.
Do not add production endpoints, source credentials, or personal data.

## Before you start

Install the latest released Registryctl:

```sh
curl -fsSL https://docs.registrystack.org/install.sh | bash
```

This quick installation path trusts Registry Docs hosting, GitHub, and TLS.
The installer then verifies the downloaded Registryctl binary and matching signed release lock
against the release checksums.
When your acceptance process requires publisher authentication, use the tag-frozen
`release/VERIFY.md` linked by the installer instead of this quick path.

A successful 1.0 installer ends with the installed binary and signed release lock paths, then
prints the spreadsheet and HTTP `Try it` commands. If your shell cannot find `registryctl`, add
the printed binary directory to `PATH` before continuing.

Confirm that Registryctl and Docker Compose are available:

```sh
registryctl --version
docker compose version
```

Registryctl reports its installed version without contacting the network.
The output has the shape `registryctl 1.x.y`. Compose reports
`Docker Compose version v<version>` and must report 2.35.0 or later.

Start in a directory that is not inside another Registry Stack project.
Registryctl otherwise discovers the nearest parent containing `registry-stack.yaml`.

## Create the bounded HTTP integration

Initialize the tested HTTP template and enter the project:

```sh
registryctl init my-registry --template http
cd my-registry
```

Initialization reports the created path and next action:

```text
Created Registry Stack project fictional-citizen-registry in my-registry.
Next: cd my-registry && registryctl test
```

Registryctl copies the template from its installed release and does not fetch a remote template.

The authored files have separate responsibilities:

| Path | Decision you own |
| --- | --- |
| `registry-stack.yaml` | The consultation service, its purpose, legal basis, consent basis, and the input each consultation maps from the request |
| `integrations/person-record/integration.yaml` | Typed input, fixed request, source outcomes, and minimized output |
| `integrations/person-record/fixtures/` | Synthetic requests, responses, and expected results |
| `environments/local.yaml` | Default development scenario, source destination, and secret references |

Files under `.registry-stack/` are generated.
Review them when handing work to another owner, but make changes in the authored files.

## Test the authored contract

Run every fixture offline:

```sh
registryctl test
```

A passing starter reports:

```text
Registry Stack test: passed for fictional-citizen-registry.
Fixtures: 21.
Next: registryctl dev
```

This command exercises the three authored outcomes (match, ambiguous, and no match) and their
derived security cases without starting Docker, resolving a secret, or contacting a source.
Fixture evidence proves the authored contract against synthetic observations, not compatibility
with an institution's live registry.

Inspect the synthetic match interaction:

```sh
registryctl test \
  --integration person-record \
  --fixture active-person \
  --trace
```

The focused result is:

```text

Fixtures: 7.
  PASS person-record.active-person
    inputs: person_id
    calls: call=1 operation=request method=GET path=/people/* query=[fields] headers=[] body=none
```

The derived cases assert that the fixed request cannot be widened, that each source failure mode
is rejected rather than coerced into an answer, and that only the declared output leaves the
integration.

The trace may show the synthetic identifier and `active` value authored in that fixture.
Do not use `--trace` with observations copied from a production source.

## Run the local product path

Start the disposable development runtime in the background:

```sh
registryctl dev --detach
```

Registryctl validates the project, rebuilds stale product inputs, checks the installed release
lock, and starts digest-locked images.
The command prints the loopback Relay API endpoint, the source mode, and the `Smoke`, `Logs`, and
`Down` actions. A project that also serves a records API prints two records request commands; this
starter authors a consultation only, so it prints none.
The authored local environment selects the synthetic `active-person` scenario, so there is no
scenario-selection flag.

The development trust anchors, credentials, bundles, and state are local disposable material.
They use the `development` trust domain and are not inputs to a governed deployment.

Run the maintained runtime check:

```sh
registryctl dev smoke
```

A passing report for this starter is one line:

```text
Development smoke: passed.
```

The scenario lines are reported only for a project that serves a records API. The smoke run drives
the `unauthorized` and `authorized` records scenarios, proves that authorization stopped the source
call on denial, and reports only the minimized attribute identifiers the authorized call released.
This starter authors a consultation and no records API, so it has no records scenario to drive and
the report carries no scenario line. Follow
[Publish a spreadsheet-backed registry API](../publish-spreadsheet-secured-registry-api/) for the
starter that exercises the denial and authorized path end to end.
The smoke report contains no credential or source-returned value.

Inspect value-free log availability if a scenario fails:

```sh
registryctl dev logs
```

The report keeps the public Relay, consultation Relay, and synthetic source identities separate
without copying their log values into Registryctl output.

## Stop the disposable runtime

Stop the bound runtime and remove its disposable state:

```sh
registryctl dev down
```

Registryctl reports that it stopped and removed the bound development runtime.
The authored project remains and can recreate the runtime.

## Review and build the project

Validate the authored project and inspect its redacted effective plan:

```sh
registryctl check --explain
```

Review the fixed request, authorization policy, source bounds, and minimized output.
`check` is offline and does not resolve a secret.

Build deterministic unsigned inputs:

```sh
registryctl build
```

The human result identifies the build path and governed handoff:

```text
Built unsigned signing inputs for relay-public, relay-consultation.
Build output: .registry-stack/build/local
Next: registryctl trust anchor create --help
```

That directory contains signing inputs for `relay-public` and `relay-consultation`.
`build` does not create production keys, sign a bundle, assemble an approved baseline set, or
activate a product.
The public Relay and the consultation Relay remain independently approved.

The selected environment controls the two Relay inputs independently.
A nonempty `relay.allowed_clients` list admits the intended public OpenID Connect clients.
Registryctl rejects an empty list rather than generating a public Relay that accepts every client
from the trusted issuer.
The `relay.consultation` binding enables the separate consultation Relay input and admits only its
configured workload client and principal; do not copy that client into `relay.allowed_clients`.

## Bind the reviewed registry

Keep the passing starter as a known-good baseline, then adapt only the authored files:

1. In `integrations/person-record/integration.yaml`, replace the placeholder product and version,
   choose the source authentication profile, and author the exact method, path, query, accepted
   statuses, output pointers, and limits from the reviewed source contract.
2. In `environments/local.yaml`, set `development.source_mode` to `operator_bound`, replace the
   source origin, and bind secret references when authentication is required. Never put a secret
   value in the project.
3. Change `registry-stack.yaml` only when the consultation input, purpose, legal basis, or consent
   basis differs from the starter.
4. Replace the fixtures with wholly synthetic observations for every accepted and rejected source
   outcome. Do not copy production responses or personal records into fixtures.

Use the ordinary fixed HTTP capability when it can express the integration. Follow the
[OAuth client-credentials guide](../../configure/oauth-client-credentials/) when the source needs
a token, the [API-key guide](../configure-project-api-key-authentication/) for a reviewed key
contract, or the [OAuth-backed Rhai guide](../configure-project-script-adapter/) only when fixed
mapping cannot normalize the response.

Run the adapted project through the same commands:

```sh
registryctl test
registryctl check --explain
registryctl dev --detach
registryctl dev smoke
registryctl dev down
registryctl build
```

`test` remains offline. `dev` is the first command that contacts the operator-bound source, so use
an approved non-production endpoint and test identity. The maintained public continuation below
provides an executable no-credential example of this binding pattern.

## Optional: exercise a public no-credential source

This continuation is an explicit network test, not part of the authoritative offline fixture
gate.
It creates a separate project and maps one tiny public JSON API through the bounded HTTP path.
It requires curl and Python 3.
The `public-demo` and `public-demo-missing` environments are adopter-owned source bindings with
`source_mode: operator_bound`.
The integration declares `auth: { type: none }`, so there is no source credential or secret
binding.

From the parent of `my-registry`, create the separate demonstration project:

```sh
registryctl init public-json-live-demo --template http
cd public-json-live-demo
(
  set -eu
  REGISTRYCTL_VERSION=$(registryctl --version)
  REGISTRYCTL_VERSION=${REGISTRYCTL_VERSION#registryctl }
  case "$REGISTRYCTL_VERSION" in
    ''|*[!0-9A-Za-z.-]*|[!0-9]*)
      printf '%s\n' "unexpected Registryctl version: $REGISTRYCTL_VERSION" >&2
      exit 1
      ;;
  esac
  OVERLAY=jsonplaceholder-todo-live-overlay-v1.sh
  OVERLAY_URL="https://docs.registrystack.org/v/$REGISTRYCTL_VERSION/examples/registryctl/$OVERLAY"
  curl -fsS "$OVERLAY_URL" -o "$OVERLAY"
  curl -fsS "$OVERLAY_URL.sha256" -o "$OVERLAY.sha256"
  python3 - "$OVERLAY" "$OVERLAY.sha256" <<'PY'
import hashlib
import hmac
import sys
from pathlib import Path

overlay = Path(sys.argv[1])
lines = Path(sys.argv[2]).read_text(encoding="ascii").splitlines()
if len(lines) != 1:
    raise SystemExit("overlay checksum file must contain exactly one line")
expected, separator, filename = lines[0].partition("  ")
if separator != "  " or filename != overlay.name:
    raise SystemExit("overlay checksum file names the wrong asset")
actual = hashlib.sha256(overlay.read_bytes()).hexdigest()
if not hmac.compare_digest(actual, expected):
    raise SystemExit("overlay checksum mismatch")
PY
  sh "$OVERLAY"
  rm "$OVERLAY" "$OVERLAY.sha256"
)
registryctl test --environment local
registryctl check --environment public-demo --explain
registryctl check --environment public-demo-missing --explain
```

The overlay first verifies that the complete authored closure still matches the pristine HTTP
starter embedded in that Registryctl release.
It stops before replacing any file when the starter is missing, changed, or contains another
authored file.
`registryctl test --environment local` remains offline.
Its completed, missing, and ambiguous cases are wholly synthetic and remain
the authoritative project-contract evidence.
The two `check` commands verify the explicit environment bindings without contacting the public
API.

Run the success path against public todo `4`:

```sh
registryctl dev --environment public-demo --detach
registryctl dev --environment public-demo smoke
registryctl dev --environment public-demo down
```

Then run the negative control against absent todo `999999`:

```sh
registryctl dev --environment public-demo-missing --detach
registryctl dev --environment public-demo-missing smoke
registryctl dev --environment public-demo-missing down
```

Both smoke reports must pass.
Operator-bound source counters are `unobserved` because Registryctl has no authority to inspect
the external service.
The negative environment selects the synthetic `no-todo` expectation and makes the bounded live
request to `/todos/999999`, which the public service currently returns as `404`.

The public service is [JSONPlaceholder](https://jsonplaceholder.typicode.com/).
Its availability, response stability, retention, and operation are outside Registry Stack's
trust boundary.
This demonstration is not an institutional registry, interoperability result, source-owner
approval, or production evidence.
Keep the source version `unverified`, and do not infer compatibility from a passing run.

Remove the demonstration project after the two controls:

```sh
cd ..
rm -r public-json-live-demo
cd my-registry
```

Maintainers can execute the exact network-dependent sequence with
`scripts/check-registryctl-public-source-live.sh`.
The gate is skipped unless `REGISTRYCTL_PUBLIC_SOURCE_LIVE=1`, and can retain its value-free
Registryctl reports plus the two public responses when
`REGISTRYCTL_PUBLIC_SOURCE_EVIDENCE_DIR` names an evidence directory.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| `init` refuses the destination | The directory exists, is unsafe, or conflicts with another project. | Choose an absent directory outside another Registry Stack project. |
| `test` reports a request mismatch | The integration and fixture no longer describe the same request. | Update the authored integration and its wholly synthetic fixture together. |
| `dev` reports an unavailable image | A digest-locked release image is absent. | Load the exact image archive from the verified release payload. |
| `dev` reports a port collision | Another process owns a required loopback port. | Stop that process or author distinct local development ports. |
| `dev smoke` reports source work on denial | An authorization-before-source invariant failed. | Stop the runtime and report the failure through the repository security process. |
| A generated file differs after editing | A file under `.registry-stack/` was changed directly. | Remove the disposable generated closure and rerun the producing command. |

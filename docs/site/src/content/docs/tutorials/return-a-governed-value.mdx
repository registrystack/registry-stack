In about ten minutes you will ask the project from [Your first assertion](../first-evidence-assertion/)
which region a synthetic person lives in, and read `north` from a verified response. Then you will
see why no other answer could have come back: the project lists every value the answer may take.

## Request the region

Work in `first-evidence-assertion/adult-status`, where the source and Evidence Gateway from
Your first assertion are still running. Prepare a request for the `residence-region` assertion
definition:

```sh test-cwd="first-evidence-assertion/adult-status"
evidencectl request prepare residence-region \
  --client tutorial-client \
  --purpose residence-check \
  --subject subject:record-id=adult \
  --name residence-region
```

```text test-expect
Prepared request: .evidence/requests/residence-region/request.json
Prepared verification context: .evidence/requests/residence-region/verification.json
Prepared authorization: .evidence/requests/residence-region/authorization.curl
```

Send the request, then verify the response before reading it:

```sh
curl --silent --show-error --fail-with-body \
  --config .evidence/requests/residence-region/authorization.curl \
  --request POST \
  --url http://127.0.0.1:18080/v1/evidence \
  --header 'Content-Type: application/json' \
  --header 'Accept: application/jose+json' \
  --data-binary @.evidence/requests/residence-region/request.json \
  --output residence-region.jws.json
evidencectl verify residence-region.jws.json \
  --context .evidence/requests/residence-region/verification.json \
  --output residence-region.verified.json
```

```text test-expect
VERIFIED
```

```sh
jq '.supportedValues' residence-region.verified.json
```

```json test-expect
[
  {
    "providesValueFor": "urn:example:concept:residence-region:v1",
    "value": "north"
  }
]
```

The source holds a birth date and a private address beside the region; the assertion carries
only `north`.

## See which values the answer may take

In `evidence.yaml`, the `residence-region` definition's `region` output is a
`controlled-category`: `values` lists every value it may carry.

```yaml title="evidence.yaml" test-excerpt="evidence.yaml"
outputs:
  region:
    concept: urn:example:concept:residence-region:v1
    type: controlled-category
    values:
    - north
    - south
```

A [Function](../../reference/glossary/#function) that computed any other value would not get it
past Evidence Gateway. One fixture case proves that by returning a value outside the list; run the
region fixtures with their trace:

```sh
evidencectl test . --target local-target.yaml --fixture fixtures/residence-region.yaml --explain
```

```text test-excerpt
"id": "negative-outside-controlled-values",
"observedResult": {
  "class": "service-unavailable"
},
"reasonCode": "output-refused",
```

Evidence Gateway refused the output, so the caller would have received a refusal, not the value.

## See who may ask

The same definition sets a `grantCeiling`, the [grant ceiling](../../reference/glossary/#grant-ceiling): the widest authority any grant may give for it:

```yaml title="evidence.yaml" test-excerpt="evidence.yaml"
purpose: residence-check
grantCeiling:
  authorities:
  - organizational
  actorKinds:
  - service
  valueOrigins:
  - request
  audiences:
  - urn:example:audience:standalone-app
```

`dev-authority.yaml` grants one exact request shape within it, to the `standalone-service`
access profile that `tutorial-client` holds:

```yaml title="dev-authority.yaml" test-excerpt="dev-authority.yaml"
- definition: residence-region
  purpose: residence-check
  audienceFrom: authenticated-requester
  representations:
  - signed-jws
  subjectBinding: audience-scoped
  subjects:
  - role: subject
    selectorProfile: record-by-id
    valueOrigin: request
```

Leave the source and Evidence Gateway running; the next tutorial continues with them.

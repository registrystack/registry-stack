If you are deploying a citizen chat assistant beside Base Registry Engine (BReg),
prepare the registry's native Proposal Action, the gateway, and the separate human
review page. Keep draft preparation and submission under independent credentials.

## Prepare the source and issuer

Start with your own checked registry project. Declare a steward-controlled link
from the citizen's verified principal to one permitted Record, a proposal-mode
Action whose target input refers to that Record, a standing-agent profile for
Start/Get/Edit, and a human profile for review and Submit.

The issuer must support the chat host's protected-resource access, token exchange
for the gateway, and the review page's sign-in. Bind exact clients, resource
indicators, scopes, actor identity, and short token lifetimes. Use synthetic records
for the first evaluation. [Configure the citizen chat assistant](../../configure/breg-mcp/)
provides the maintained configuration and trust contract.

## Configure the supporting services

Set `service.details.recordType`, `service.application.action`, and
`service.application.targetInput` in the gateway. Set the same Action and target
input with the separate human profile in the review page's `registry` block.
Keep secrets in owner-only deployment storage and reference them from each
runtime file. The gateway needs no submit credential, and the review page needs
no agent credential.

Validate both runtime documents offline:

```sh test-skip="requires the operator's completed service configuration files"
breg-mcp --runtime-config /etc/breg-mcp/runtime.yaml check
breg-review --runtime-config /etc/breg-review/runtime.yaml check
```

A named diagnostic identifies a document member to repair. These checks open no
socket, read no secret, and prove no issuer or registry exchange. Follow
[Operate the citizen chat assistant](../../operate/breg-mcp/) to start the separate
processes behind your configured proxies and verify readiness.

## Verify the authority split

With your synthetic citizen signed in, inspect its own permitted record, Start
a draft, and edit an allowed input. The gateway must reject a tool argument that
tries to replace its controlled target. Its delegated caller cannot submit the
draft or mutate a target directly.

Open the returned review link, sign in independently, compare the canonical draft
with the target record, and confirm submission. Review and application follow the
Action's frozen configuration. Observe the exact Proposal binding and local
application status; an older submission cannot inherit approval after a revision.
Record permitted and refused outcomes privately before admitting real users.

If a call fails, inspect the same operation correlation in the service and BReg
audit streams, check issuer/audience/profile bindings, and repair the named
configuration. Recover uncertain keyed commands with their original binding and
key. Do not create a fresh draft to hide an uncertain result.

Stop the processes through your supervisor after evaluation. Keep or remove the
synthetic registry and private credentials according to your deployment's explicit
retention decision; stopping a supporting service does not erase BReg records.

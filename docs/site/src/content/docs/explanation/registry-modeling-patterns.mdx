Base Registry Engine (BReg) has no built-in facility, business, or permit model. Every pattern
here is ordinary configuration you can read in a starter and adapt.

## Start from the facility template

```sh
bregctl init --template facility-registry facility
bregctl check facility
```

The excerpts below come from the template's `registry.yaml`.

## Separate an object from its registration

A facility can change operator without becoming a different facility, and a permit's expiry need
not end the business that held it. The template keeps the link in its own
[Record type](../../reference/glossary/#record-type), written once and never patched:

```yaml test-excerpt="facility/registry.yaml"
  - id: facility-assignment
    route: facility-assignments
    primaryDataset: facility-registry
    mutationMode: create-only
```

## Choose a field kind

A `string` carries a bounded line such as a name or code, and `text` carries long prose. A closed
list of states is a `vocabulary-code`. A `date` is a full calendar day and a `timestamp` an
instant. `decimal` takes a declared precision. When several fields share one shape, declare it once
as a value type and refer to it with `typeRef`:

```yaml test-excerpt="facility/registry.yaml"
      - {id: postal-code, apiName: postalCode, typeRef: postal-code, required: true, classification: internal}
      - {id: status, type: vocabulary-code, vocabulary: facility-status, required: true, classification: internal}
```

A `string` or `text` field can also declare `pattern`, a PostgreSQL regular expression the
database enforces on every write path. It is not anchored for you: `[0-9]{13}` matches any value
containing thirteen digits, so write `^[0-9]{13}$` when you mean the whole value. A pattern checks
one row, so a rule that depends on another record belongs in an Action's `commitGuards`. Adding a
pattern to a running registry checks every existing row first, and changing or removing one is a
reviewed destructive change. Mark a restricted value `encrypted` when a database reader must not
see it. [Field encryption](../../configure/breg-field-encryption/) explains what that seals.

The limits on each kind are in the
[configuration reference](../../reference/breg-configuration/).

## Identifiers and uniqueness

For a number that BReg issues, put `generate` on a stored `string` field. Choose `type: sequence` with `minimumDigits` for a padded number, or `type: random` with `length`
for a code. Both accept a literal `prefix`. For example, `generate: {type: sequence, prefix:
"APP-", minimumDigits: 4, scope: [jurisdiction]}` issues `APP-0001` separately within each
jurisdiction. Only a sequence takes `scope`; leave it out for one namespace across the Record
type. A random code uses a fixed alphabet without easily misread characters. BReg adds the database
uniqueness constraint, and the caller omits the generated field from writes. The Record's UUID
still identifies it in routes and references.

A scope field must be a `public` or `internal` value that is not a reference, because BReg keeps
issued values with their scopes after erasure. It must be supplied on create and cannot change
after issuance. BReg reserves values transactionally and never reuses an issued value. Proposal
Submit allocates and freezes the value for review, and Apply and Retry use that frozen value, so a
rejected or cancelled Proposal still consumes its number. A register that needs gapless numbers
cannot issue them with a sequence through a Proposal Action. If you enable generation on a field
that already exists, a reviewed migration must backfill any missing
values before BReg seeds its allocation state and checks retained values for uniqueness. The
repository's `products/breg/acceptance/generated-identifiers/registry.yaml` shows both strategies
and a Proposal Action.

A `unique` constraint can span several fields, such as issuer and number, and can apply only when
a condition holds.

## References between Record types

A `reference` field holds the ID of a record of the named Record type, and the database refuses a
value that names no such record. `inverseName` names the reverse direction, so a facility exposes
its assignments without a field of its own:

```yaml test-excerpt="facility/registry.yaml"
      - {id: facility, type: reference, target: facility, required: true, classification: internal, relationship: {inverseName: assignments}}
      - {id: operator, type: reference, target: operator, required: true, classification: internal, relationship: {inverseName: facilityAssignments}}
```

A read path follows the link in one request. The reader's
[access profile](../../reference/glossary/#access-profile) still decides what it returns:

```yaml test-excerpt="facility/registry.yaml"
    readPaths:
      - {id: operators, through: facility-assignment, to: operator, route: operators}
```

## Dates and validity

A Record type's `temporal` declaration names its start and end fields. Exclusivity needs a separate
`temporal-non-overlap` constraint with the right `scopeFields`. A date or role field alone imposes
nothing.

To name the last day in force, use `temporal.lastDayField` instead of `endField`, so a period
ending on 31 December includes that day. The
[API reference](../../reference/breg-api/) describes how the temporal routes read it.

## Choose how changes reach records

Generated record routes suit directory maintenance where authorised callers patch each record
directly. An immediate Action commits several effects atomically, such as a facility and its
first assignment, and a Proposal Action keeps a durable draft for review and later application.
[Actions and Proposals](../../configure/breg-actions/) explains how to choose.

## Change several records through one Action

An Action changes several Record types in one transaction. For example, a licensing authority can
model an officer's decision as an [Action](../../reference/glossary/#action),
`decide-licence-application`, whose inputs carry the outcome and the officer's reference and whose
plan writes a decision record either way. As a proposal-mode Action, a reviewer approves or rejects
that exact submission (a [Proposal](../../reference/glossary/#proposal)), and only applying it
writes the record. The recorded decision is then an ordinary record that other offices can read
under their own access profiles.

## Attachments

A document submitted with a Proposal uses a bounded attachment slot, not a string field:

```yaml test-excerpt="facility/registry.yaml"
        attachments:
          - {id: supporting-document, required: false, maximumBytes: 1048576, contentTypes: [application/pdf], classification: restricted}
```

## Incomplete dates

A `date` is a full calendar day, so a known year is not a known January 1. Less precise
information needs a different representation.

## Modules and access

Modules share definitions across projects. An extension adds fields and constraints. It cannot
remove an inherited constraint or replace a field, so change the owning definition when its policy
does not fit. Record reads, Action invocation, and Proposal transitions have separate grants, and a
classification label is not an authorisation boundary.

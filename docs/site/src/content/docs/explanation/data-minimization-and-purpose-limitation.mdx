## How the requirement model limits collection at the source

The first place minimisation appears is in the unit of data Registry Evidence is built around.
A requirement describes one reviewed question and the exact values its answer may carry, not a
whole record, so returning a full record would over-collect relative to the question actually
asked.
The design treats the narrow question, not the record, as the thing to be answered.

The project author still decides which source fields the answer needs. Minimisation therefore
depends on a reviewed contract and its fixtures, not on a runtime deriving a source projection
from the question it was asked.

## Purpose limitation as an enforced gate, not a label

The closed Registry Evidence request schema carries the same idea further. A caller supplies a
nonce, a requirement, a purpose, and one selector per declared role. It may also pin a
configuration revision and supply up to sixteen holder public keys, one per credential. A holder
key reaches only the credential response formats, and under the holder-bound mode its thumbprint
also scopes the subject binding. There are no thresholds,
expressions, paths, headers, source fields, or response projections a caller can set.
The effect a reviewer should take away is that purpose, when configured, acts as a precondition
for access rather than an after-the-fact annotation.

Several of these protections apply only when configured; the operator-responsibilities section
lists them.

## Minimisation at the output: closed value forms

Minimisation also applies to what leaves the boundary. Registry Evidence has no caller-selectable
disclosure at all, so there is no request-time negotiation to review.

Instead, a requirement declares one to sixteen *concepts*, and each concept fixes the exact *value
form* its fact takes: a boolean, a code from a reviewed codelist, a bounded identifier or number, a date or time
bucket, an audience-scoped opaque reference, or a reviewed closed structure. The set of forms is
closed at twelve, and a requirement issuing under the holder-bound subject binding mode may use
ten of them: the two entity-reference forms take the audience as a derivation input, so a
holder-bound requirement declaring either is refused at startup rather than served with a
degenerate reference. The answer carries a value for each declared concept and nothing else, and the
assertion schema rejects additional properties.
For a reviewer, this moves the disclosure decision from request time, where a caller could argue
for more, to authoring and review time, where an operator justifies it once and can be held to it.
(The forms themselves are catalogued in [How Evidence
works](../how-evidence-works/) and are out of scope here.)

There is no equivalent of the retired redacted mode, and this is structural rather than an
omission: an assertion must carry at least one supported value, so an assertion with nothing in it
cannot be produced. A request that cannot be answered returns a problem document and no assertion.

Minimisation can continue past the response boundary when the operator enables the SD-JWT VC
format. That format is a second encoding of the same assertion, never a credential lifecycle: the
signed body carries a SHA-256 digest of each selectively disclosable value, so a holder can later
present a subset. A value uses one disclosure by default. A governed structured value can instead
place each direct field in a separate disclosure while keeping nested field values atomic. Two
points matter to a reviewer. The issuer appends every disclosure, so the response the caller
receives reveals the same set as the signed JWS. Holder-side omission works on whole outputs
only: a holder may withhold an output, a signed digest with no presented disclosure, and the
verifier accepts the result when the relying party's policy does not require that output. An
output the policy marks required must be disclosed, a disclosed output must match its declared
concept and form, and a structured value is disclosed whole or not at all, so a presentation that
shows some fields of one and withholds the others is refused. The verifier never accepts a
shortened value. Registry Evidence runs no wallet protocol of its own. The experimental
`evidence-oid4vci` service beside it delivers the credential to a wallet (see [OID4VCI
issuance](../../configure/evidence-oid4vci/)), and the holder's wallet decides what to present.
Under the default audience-scoped binding mode a caller may supply a holder public key that
Registry Evidence echoes into the `cnf` claim for a relying party to check itself, and nothing
verifies it.

A requirement may instead declare the holder-bound subject binding mode, which changes what the
credential is bound to and moves the audience check from issuance to presentation. The service
still issues no key-binding JWT and holds no presentation state. A relying party verifies a
presentation with the portable verifier or the `evidence verify-presentation` operator command.
Registry Evidence itself verifies a credential a holder presents from a wallet before it answers
with a `holder-presented` assertion.
For minimisation the mode is a trade rather than a gain: the same holder key, trust domain,
purpose, subject role, selector profile, and selector values yield the same binding for every
verifier, so a holder who reuses one key is correlatable across the verifiers it presents to.
Holder-bound issuance also refuses the two entity-reference value forms, and a holder-bound
assertion carries neither an audience nor the request nonce, because it names no relying party to
echo them to.

Purpose behaves the same way on both sides of the boundary. A relying party compares the issuance
purpose as signed provenance: it records why the assertion was produced and licenses, limits, or
authorises nothing about what the relying party may now do with it. Under the holder-bound mode
that record is also disclosed to every verifier the credential reaches, and it is a
low-cardinality attribute, so treat it as visible rather than internal.

A further minimisation detail guards against a subtler leak.
No match, ambiguity, a missing required fact, and an unresolved derivation input all collapse into
one problem response with the same title and body shape, so the refusal itself does not tell a
caller whether a record exists. Registry Evidence does not pad responses to a constant time. A
source that answers a no-match faster than a match can still reveal membership through latency
(see the [Registry Evidence security model](../../security/evidence/)). The outcomes stay distinct
in the audit record. Collapsing is a property of what the caller sees, not of what the operator can
review.

## Ask for the weakest answer that does the job

When you decide what crosses to or from another institution, start at the weakest answer and climb
only when it cannot do the job. In plain words, from weakest to strongest:

1. Nothing: refuse when the purpose, authority, or scope is missing.
2. A description of what exists, with no person-level data.
3. Counts, rates, or other totals.
4. A match, mismatch, or "cannot tell" on facts the caller already holds.
5. A computed fact, such as "is registered" or "is eligible", without the record behind it.
6. A fact the person states, labelled as self-stated.
7. A rendered document filtered to what is allowed.
8. A signed credential or receipt for a named purpose and validity period.
9. Selected fields of the record, only when the law allows a record-level look and the access is
   scoped, filtered, and audited.

Registry Manifest publishes descriptions, Base Registry Engine (BReg) statistical datasets serve
totals, Registry Evidence serves matches and other computed signed assertions, Registry Render
produces PDF documents, and a BReg access profile serves the last rung. Record the purpose or legal
basis for each access grant and partner relationship. Where the source is silent, write "not
stated"; that is allowed, and it is a finding to raise with whoever owns the question, not a reason
to stop.

## Data stays at source: distributed custody

Underneath all of this is an architectural choice that matters for minimisation at the system
level: data stays at source.
The design premise is distributed custody. Registry Evidence answers from each authority's own
register without copying records into a shared store. BReg holds records only where an
institution runs it as its system of record.
Registry Evidence reads a source only through the reviewed Adapter pack route its project selects.
It refuses a route that can reach a write, and it exposes no route that writes to a source registry.
Base Registry Engine (BReg) is different: it is a writable register. Its write routes create
records, patch or tombstone records of a mutable Record type, and run the Actions and Proposals the
institution configures.

For a reviewer this has a direct consequence.
Registry Evidence cannot alter or delete the records it reads, so it has no erasure flow at the
source. Erasure there is an operation on the source registry.
Erasure of retained detail is a per-product operation, listed in the
[What the architecture does not provide](#what-the-architecture-does-not-provide) section.

One related boundary is positive rather than cautionary.
The portable metadata the stack publishes must not carry person-level data or runtime secrets and
bindings, which is precisely why those artifacts are safe to share: they hold no personal data.
But publishing metadata only describes; it does not authorise access, enforce a policy, or assert
that any record exists, so a published manifest carries no data-protection guarantee about live
data.

## Audit as an accountability primitive

Accountability is supported through audit, which is treated as a security control rather than an
optional log.
Registry Evidence is fail-closed by construction rather than by configuration. It
writes an access record before it contacts any source and a release record after signing and
before release. An audit failure fails the request. Selector, source, and disclosed values
never appear in those records or in logs, and raw source responses are never persisted.
BReg is also fail-closed by construction. It writes a request entry before protected I/O and a
response entry with the outcome. When the request entry is refused, BReg performs no protected
I/O and releases nothing. A mutation appends its response entry after the commit, so a refused
response entry leaves the change committed and the response withheld. Its entries carry keyed
references and closed terms, never a raw principal, record id, or selector.

{/* Evidence: crates/registry-breg/src/audit.rs, module doc and RegistryAudit::append;

Fail-closed audit is not a deployment setting in either product. It is also not a guarantee that
every route in any given build has been individually audited against it.
Whether a particular deployment meets it is something a reviewer verifies in that deployment, not
something the design asserts on its behalf.

## What the architecture does not provide

Some of the most important things for a DPO to know are the absences.
[Known limitations](../known-limitations/) lists the cross-product limits and links each product's own.

- No data-subject request workflow: No product ships a workflow for a data subject's request for
  erasure, rectification, or access. The institution decides each request and runs the product
  operation that carries it out.
- Erasure is per product and covers retained detail only: Registry Evidence erases nothing at the
  source it reads. BReg erases retained record history with `bregctl history erase` and Proposal
  detail with `bregctl proposal-retention erase`. It erases expired Evidence responses it retained
  for a record with `bregctl evidence-retention erase-expired`. None of these commands erases the
  current record or the audit journal (see [Retain, erase, and audit](../../operate/breg-retention/)). Registry Casework erases
  expired review data. Registry Messaging erases message payloads and records when their retention
  periods end. The Registry Document Store erases a removed document's bytes after the policy's
  grace period.
- Rectification is an ordinary change: BReg corrects a record through a patch on a mutable Record
  type, or a configured Action or Proposal. For an event record, a later record declares that it
  `corrects` or `supersedes` the earlier one. No product ships a data-subject rectification
  workflow.
- Subject access log: a BReg Record type can opt in to a subject-facing log of reads. The log
  records who read one subject's Record, when, and for which declared purpose (see
  [Give subjects a log of reads of their Record](../../operate/breg-access-log/)).

A Registry Evidence assertion has no revocation, suspension, status list, or credential-status
endpoint. It carries a validity window and is otherwise final once released. Cross-authority
federation, aggregate-analytics privacy budgeting, and the general compliance disclaimer are
likewise stack-wide absences rather than specifics of data minimisation or purpose limitation, but
a data-protection assessment should weigh them too.
[Known limitations](../known-limitations/) links each product's own limits.

## Operator responsibilities: what the design leaves to you

The minimisation and purpose-limitation posture this page describes is the design default, but the
operator owns the configuration.
Several of the protections are conditional, and a reviewer should test the deployment, not the
design, for each one.

The main conditional control is the authored projection. A runtime can stop a caller from reaching
past the reviewed contract, but it cannot decide which values an institution has a lawful reason to
expose. Project reviewers must confirm the source authority, selector inputs, output projection,
purpose, requirements, and declared value forms together, and Registry Evidence expects the complete
simultaneously enabled configuration to be reviewed as one disclosure surface, since two answers
that are each defensible alone can reconstruct a protected value between them. Operators must then
bind only the reviewed source and workload credentials to the generated product inputs.

More broadly, the architecture defines primitives and leaves a large set of
data-protection-relevant controls to the operator.
Secret and key provisioning, audit retention and storage, tenant isolation, transport security,
edge rate limiting, deployment configuration, and incident response are not defined by the design;
they are responsibilities you provision and verify in a deployment.
For the concrete stores and product expiry points, see
[Retention and persistent state](../../operate/retention-and-persistent-state/).
Registry Stack offers minimisation, purpose limitation, and
accountability as enforceable design primitives, but whether a given deployment realises them (and
whether it meets any legal obligation) depends on how the operator configures and runs it.

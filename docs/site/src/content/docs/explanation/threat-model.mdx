This page summarises the cross-product threat model. Product specifications and source-owned
security tests remain authoritative for exact behaviour. Base Registry Engine (BReg) owns the
governed record boundary described below.

## Assets

- Authoritative registry records and history.
- Person-level source data. Evidence reads source data in place and releases only a computed,
  disclosure-shaped answer; no source row crosses the assertion boundary.
- Private signing keys. Only public verification material leaves the service, so offline
  verification requires no protected access.
- Caller and source credentials, subject selectors, and source responses.
- Governed packages and runtime configuration.
- Audit integrity and availability of required service and recovery paths.

Registry Evidence is a minimum-disclosure assertion service. Registry Platform supplies shared
security primitives so authentication, HTTP policy, audit, cryptography, and secret handling remain
reviewable in one place instead of diverging between services. Demo integrations sit outside this
production boundary and do not establish a production freshness or replay-protection profile.

## Trust boundaries

| Boundary | Main control |
| --- | --- |
| Caller to product | OIDC authentication, explicit authorisation, bounded request parsing |
| BReg to PostgreSQL | Compiled schema and operations, least-privilege database identity |
| Evidence to source | Fixed destination and request, credential isolation, transport and response bounds |
| Evidence to verifier | Signed assertion, published verification material, audience and expiry checks |
| Public checker to Evidence through the operator proxy | Operator proxy limits the path and the request rate and keeps no client address; holder-held 120-bit check code; identical not-found answer; fixed answer fields; request headers ignored except `Content-Type` |
| Product to audit storage | Value-free records, durable append path, fail-closed behaviour where required |
| Operator to package | Closed schemas, digest verification, reviewed activation and rollback |

## Evidence authentication and source boundaries

Registry Evidence authenticates callers with one reviewed OIDC bearer profile. It then makes one
authorisation decision before credential resolution or source access. That decision binds the
requester, requirement, purpose, subject roles, selector profiles, authority, origin tuple, and
audience. Operational and discovery routes are unauthenticated, and none reveals enabled definitions or
requester permissions. The [Registry Evidence security model](../../security/evidence/) states
these rules in full, along with the unauthenticated public check route and the proxy it depends on.

Evidence reaches data only through the digest-pinned Adapter pack route that each source names.
Every operation the route can reach must be read-only. That means an HTTP `GET`, a `POST` the pack
declares safe, a GraphQL query, or a reviewed statement over a local read-only SQLite extract.
The engine holds the route to these limits:

- Governed connection policy fixes each endpoint's origin, authentication, and TLS.
- The engine owns headers and credentials.
- It follows no redirect and ignores proxy settings.
- It caps data operations, time, and response bytes for each acquisition.
- Caller values reach the route only as authorised selector inputs checked against its input
  schema. They cannot select an undeclared endpoint.

The route must return match, no match, ambiguous, or declared unresolved, and matched facts must
satisfy the reviewed facts schema. Evidence never exposes or chooses candidates. Raw source
responses are neither persisted nor logged.

## Threats the design mitigates

- Secret material in deployment configuration: an HTTP source credential is named by a logical
  secret reference instead of stored in the bundle. A SQLite extract is bound by file path and
  needs no credential. Plain HTTP is admitted only under the local assurance profile at a canonical
  numeric loopback origin. Anywhere else, a source endpoint with no authentication needs a client
  certificate (`mtlsIdentity`).
- Token forgery: signatures, issuer, audience, token type, and algorithm are checked before token
  claims are trusted. Route scopes and grants remain governed even when a token is valid.
- Sender-constrained token replay as bearer: Evidence denies an access token with a
  proof-of-possession confirmation claim because it validates no sender proof.
- Other request-path threats: the [Registry Evidence security model](../../security/evidence/)
  states the control for privilege escalation, membership and authorisation oracles, and payload
  substitution. It also covers release without accountability, hot policy mutation, tenant
  confusion, and leakage through errors, logs, or telemetry. A response-timing difference can still
  reveal membership.
- Cross-purpose tracking: subject bindings use a keyed, domain-separated derivation over audience
  (or the holder's key for a holder-bound answer), purpose, role, selector profile, key version, and
  the complete canonical selector bundle.
- Over-collection: callers cannot supply thresholds, expressions, scripts, source fields, paths,
  headers, relationship types, or response projections. Undeclared concepts and values outside
  governed type, codelist, cardinality, precision, or size bounds are rejected.
- SSRF and uncontrolled egress: governed connection policy fixes each endpoint's origin,
  authentication, and TLS. The engine owns headers, follows no redirect, ignores proxy settings,
  and caps data operations. A SQLite extract source opens one bound local file and has no network
  destination an attacker can steer.
- Hostile or defective reviewed scripts: the script engine has no filesystem, environment, network,
  process, module, ambient clock, or randomness. Operation ceilings stop runaway execution. A route
  that reads a SQLite extract receives only rows and publication metadata, never the extract path,
  a file handle, or a database connection.

**Audit as a control.** Evidence writes a mandatory access-attempt entry before each source
acquisition, before any source credential or call. One entry covers every call the route makes.
It writes a disclosure-release entry after signing but before returning the response. A failure
blocks the corresponding action. The audit log is not chained or signed, so the writing host can
rewrite or delete local entries.

[Operate the Registry Evidence audit log](../../operate/evidence-audit/) covers what each entry
holds and the keyed pseudonyms. It also covers shipping the log to append-only storage, the
single-writer lock, and the pseudonym master an investigation depends on.

## The automated adversary

The model assumes every reachable deployment is probed continuously at machine speed. Refusal
shapes therefore avoid distinguishing signals, and source calls remain fixed by governed
configuration. Request schemas expose no caller-supplied expression, script, path, header, or
projection. Parsers and scripts apply size, count, and operation ceilings so one request cannot buy
unbounded work.

Nightly fuzz smoke covers platform token and API-key parsing, SD-JWT issuance and
holder-proof input, reviewed SQLite statement parsing, Evidence verification, authoring readers,
and Manifest YAML and rendered-artifact JSON. The merge queue runs the platform and Evidence
targets when matching paths change. It does not cover every request path or every
presentation path behind an otherwise valid signature.

Human review remains load-bearing under sustained probing. It must cover the whole enabled
disclosure surface, project semantics, dependency update cadence, and edge rate controls.

## Field encryption draws a boundary inside the database

BReg can store a restricted field as an AES-256-GCM envelope under a data-encryption key wrapped by
Vault or OpenBao Transit. This protects values from database administrators, replicas, dumps,
backups, and SQL injection that reaches only ciphertext. It does not protect values from the running
process or a holder of the Transit credential because both can obtain plaintext.

Equality lookups use an HMAC-SHA-256 blind index, which deliberately exposes equality, presence,
and cardinality to a database reader. [Encrypt a field](../../configure/breg-field-encryption/)
covers what a reader sees when a value cannot be opened and the plaintext backups taken before
encryption.

The implementation uses the FIPS build of AWS-LC with no non-FIPS runtime fallback. Registry Stack
does not claim certification of itself.

## Residual risks and operator duties

- Health, readiness, and offline checks do not certify Transit policy or key custody.
  [Known limitations](../known-limitations/) says the same of key custody for every product.
- Combined disclosure remains a human review. Differently named disclosure families can overlap,
  and rate limits do not make an unsafe bundle safe.
- Startup does not detect overlapping authority paths. Ambiguity denies at request time but appears
  as an unexplained refusal.
- Rate limits are per process and in memory. Replicas multiply budgets and restart resets them,
  including the failed-selector enumeration defence.
- Released assertions have no recall, revocation, status list, or presentation-time check. Validity
  windows and key publication determine how long they verify.
- A wallet presentation passes through the OpenID4VP verifier, which holds it in memory until
  Evidence reads it or its result lifetime ends, and never verifies it. A compromised verifier can withhold or misroute a
  presentation or read the claims a holder disclosed; it cannot make Evidence accept a forged
  credential, because Evidence checks the issuer, the disclosures, and the holder binding itself.
  A restart discards open sessions. Which relying parties accept a `holder-presented` assertion is
  set out in the [Registry Evidence security model](../../security/evidence/).
  {/* Evidence: products/evidence/contracts/oid4vp-profile.yaml, service_boundary, sessions;
       crates/registry-evidence/src/wallet_presentation.rs, WalletPresentationVerifier;
       crates/registry-evidence-client/src/prepare.rs, default_accepted_channels;
       crates/registry-breg/src/problem.rs, ActionEvidenceFailed. */}
- A cross-device wallet flow lets a holder present into a session someone else started, by relay
  or by cooperation. Holder binding proves the presenter controls the wallet key, not that the
  presenter is the applicant. `possession` proves a credential from a trusted issuer was presented
  into the session; with `attribute-match`, the requirement's derivation compares the disclosed
  claims with the one expected record, so another person's credential yields a mismatch. Evidence
  also refuses a read whose stated receipt time falls outside the verifier's largest result window
  plus clock skew, so a verifier that kept a presentation cannot replay it beyond that window.
  {/* Evidence: crates/registry-evidence/src/wallet_presentation.rs, received_within_window,
       SubjectLinkMode. */}
- The calling relying party states the presenting principal and the session reference for a
  wallet read. Evidence refuses a principal that did not create the session, but it cannot tell
  which relying party a session was meant for. Run one relying party per Evidence deployment that
  serves wallet channels.
  {/* Evidence: crates/registry-evidence/src/wallet_presentation.rs, ReadRequest,
       WalletPresentationVerifier::verified (created_by);
       products/evidence/examples/wallet-presentation/evidence.yaml, wallet-session selector
       profile. */}
- The request nonce is echoed correlation data, not replay prevention. Evidence does not enforce
  uniqueness or consume it.
- Secret provisioning, key custody and rotation, audit retention, backups, database access,
  network isolation, TLS, edge quotas, monitoring, dependency response, incident response, source
  correctness, and legal authority remain operator duties.
- Project approval remains semantic. Validators cannot decide whether an institution chose the
  lawful purpose, correct source fields, derivation, or disclosure default.

## BReg statistical publication boundary

A BReg publisher can turn record-derived counts into a release readable by profiles without record access. The compiler confines the population and dimension domains and requires caller-independent source visibility across the entire derived dependency closure. Live reads reuse ordinary list predicates. The runtime verifies package activation and freshness before committing an immutable version; current definition digests fence released reads.

The runtime cannot update or delete release tables. A migration-owned PostgreSQL function records a withdrawal and deletes its content atomically. Audit gates cover request attempts and returned bytes and contain references and lifecycle metadata, never cell values or unit counts.

Suppression and deterministic rounding accept inference through totals, interval arithmetic, zeros, differencing, and auxiliary information. They supply no cumulative privacy budget. See [publish statistics](../../configure/breg-statistics/#review-what-a-release-discloses) before deciding which populations may be released.

## What is explicitly out of scope

These are non-goals for this version. None of them should be read into a Registry Stack
conformance claim:

- A credential lifecycle: Registry Evidence's SD-JWT VC output is a second serialisation of the same
  stateless assertion. There is no status list, revocation, reissuance, or persisted credential
  state, in either subject binding mode. Registry Evidence itself speaks no wallet protocol. The
  experimental `evidence-oid4vci` service beside it delivers holder-bound credentials to a wallet.
  It uses a credential offer and a nonce-checked proof of possession. It holds that exchange state
  in memory for minutes and never signs (see [OID4VCI issuance](../../configure/evidence-oid4vci/)).
  Under the default audience-scoped mode there is no holder binding ceremony, and an optional
  caller-supplied holder key is echoed unverified into a confirmation claim rather than proved. A
  requirement that declares the holder-bound mode adds a proof of possession the relying party
  checks at presentation: Registry Evidence appends no key-binding JWT, issues no presentation
  challenge, and retains no presentation or replay state.
  {/* Evidence: crates/registry-evidence-oid4vci/src/lib.rs, module doc (never signs, in-memory
       state); crates/registry-evidence-oid4vci/src/service.rs, OFFERS_PATH, NONCE_PATH,
       CREDENTIAL_PATH, and ProofRefusal; crates/registry-platform-sdjwt/src/lib.rs,
       validate_oid4vci_proof_jwt; products/evidence/contracts/oid4vci-profile.yaml, excluded
       credential status and lifecycle operations. */}
- Delegated or federated evaluation between peers: no service in this model evaluates a
  question on another deployment's behalf, and there is no trust-chain discovery, peer
  registry, or cross-institution evaluation route.
- Identity resolution: lookup is match, no-match, ambiguous, or declared unresolved. Registry
  Evidence is not an identity-resolution or record-linkage engine and returns no candidate
  material.
- Cross-verifier credential use under the default binding mode: an audience-scoped subject binding
  makes an assertion meaningful to one relying party and correlatable across none. A requirement
  that declares the holder-bound mode opts out of this non-goal deliberately, and accepts the
  correlation that follows: holder key reuse links a holder across every verifier that sees it,
  and the service can neither prevent nor detect that. Batch issuance under distinct keys reduces
  the deterministic key-based link; it does not make credentials unlinkable, because members still
  share an issuance timestamp, purpose, requirement, Evidence Type, configuration revision, and
  disclosed values.
- Replay prevention at presentation: a relying party verifying a key-binding JWT compares the
  nonce from the challenge it issued, and comparing a nonce is not consuming it. The same
  presentation bytes verify again under the same stateless policy. RFC 9901 section 7.3 places the
  challenge lifecycle in the surrounding protocol, so issuing a nonce, retaining it, and retiring
  it are the relying party's own duties.
- External policy enforcement of any kind: no runtime service in this stack evaluates an
  external policy. There is no policy decision point, no ODRL term enforcement, and no policy
  discovery. Registry Manifest can publish a policy reference, and that reference describes
  intent rather than naming a control the stack applies.
- Certified standards compliance: Aligning with a standard is not conforming to it. Speaking
  the shape of OIDC, OAuth 2.0, SD-JWT VC, CCCEV, or the rest does not certify conformance to
  any of them, and CCCEV-shaped output is not conformant to CCCEV 2.2.0.
- A hostile local account on the machine that runs adopter tooling: `bregctl`, `evidencectl`,
  `caseworkctl`, `schedulingctl`, and the other authoring and scaffolding commands
  assume a single-user machine the adopter trusts, and resisting another account on that machine
  is not a tooling guarantee. Some `bregctl` lifecycle writes walk directories by descriptor:
  they refuse a symbolic link they encounter, and an ancestor replaced after the walk cannot
  redirect them, because they keep writing into the directory they already hold. Other tooling
  writes use ordinary path-based file operations, and another account that can write to a parent
  directory can race their directory creation or redirect them through a symbolic link. Generate
  production key material on a machine where no other account can write anywhere along the output
  path. The owner, mode, and no-follow checks described for the runtimes are runtime startup
  checks.
  {/* Evidence: descriptor-held SafeDir walk with openat and O_NOFOLLOW,
       crates/registry-bregctl/src/safe_path.rs; path-based directory creation in
       ensure_private_dir_impl and ensure_parent_dir, crates/registry-evidencectl/src/keygen.rs,
       and ensure_private_parents, crates/registry-bregctl/src/field_encryption.rs. */}
- Non-Unix targets: Registry Evidence is Unix-only. Its secret and audit invariants depend on
  owner, mode, no-follow, link-count, and open-file identity checks, so the runtime does not
  compile for a non-Unix target rather than degrading those checks.
  {/* Evidence: compile_error under #[cfg(not(unix))], crates/registry-evidence/src/lib.rs;
       platform.supported and platform.reason, products/evidence/contracts/runtime.schema.yaml. */}

denial behaviour, audit failure, dependency failure, backup, and recovery.

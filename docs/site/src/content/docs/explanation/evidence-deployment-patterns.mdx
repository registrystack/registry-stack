Registry Evidence derives, protects and releases a minimised assertion from one authoritative record.
Other systems around it publish APIs, move messages or run workflows.
This page explains how Evidence combines with them, and which choices a production deployment makes
without changing Evidence's public schemas or runtime behaviour.

## Deployment patterns

In every pattern Evidence keeps the same responsibilities: it validates the identity context it is
configured to accept, and it enforces requirement, purpose, subject-authority and disclosure rules.
A neighbouring system never replaces those checks.

{/* Evidence: crates/registry-evidence/src/authority.rs AuthoritySnapshot;
    crates/registry-evidence/src/auth.rs principal;
    crates/registry-evidence/src/selector.rs authority_selected_by_principal. */}

### Standalone

Evidence exposes HTTPS directly, using one supported authentication profile and a configured durable
audit sink.
Production exposure includes per-principal rate controls.

{/* Evidence: crates/registry-evidence/src/config.rs OidcAuthenticationConfig, RateLimitConfig, AuditConfig. */}

### API gateway

A gateway such as WSO2 manages API publication, authentication protocol integration, rate controls
and routing.
Evidence still validates the configured identity context on every request and applies its own
requirement, purpose, subject-authority and disclosure rules.

{/* Evidence: crates/registry-evidence/src/config.rs OidcAuthenticationConfig;
    crates/registry-evidence/src/authority.rs AuthoritySnapshot. */}

### X-Road

Evidence sits behind a provider Security Server, or calls a source through X-Road.
X-Road provides trusted exchange and transaction protections.
Evidence remains responsible for deriving, protecting and releasing the minimised assertion.

### OpenFn

An OpenFn workflow calls Evidence as one atomic step and routes the minimised result.
Evidence does not take over workflow branching, business retries or destination writes.

## Production decisions

The product boundary is closed.
Each production deployment supplies or confirms twelve governed choices without changing public
schemas or runtime semantics:

1. The OIDC profile: issuer, audience, token type, algorithm allowlist and principal claim.
2. How subject authority is conveyed and governed.
3. Selector profiles, their exact field sets, value origins and public cardinality-disclosure rules.
4. The exact source contract and acquisition posture.
5. The enabled source-authentication profiles.
6. The enabled Version 1 Evidence Types and the fixed CCCEV-aligned concepts.
7. The durable audit sink.
8. The legal timezone and observation-time rules for each time-dependent requirement.
9. The Vault or OpenBao Transit deployment, local proxy, pinned key version and operator policy for
   the non-exportable P-256 signing key.
10. How relying parties obtain and pin the provider's verification trust.
11. The existence-disclosure behaviour permitted for each enabled requirement under the closed public
    problem contract.
12. For each extract source: who publishes it, on what cadence and to which mounted path, so that
    publication stays inside the requirement's maximum age.

{/* Evidence: crates/registry-evidence/src/config.rs OidcAuthenticationConfig, principal_claim,
    observation_timezone, SigningConfig, AuditConfig, RateLimitConfig;
    crates/registry-evidence/src/runtime.rs TransitConfiguration. */}

### Audit integrity is the sink's property

Choice 7 selects where a deployment ships audit entries, not which writer to build.
Evidence writes through the shared platform audit writer to a durable local file or to standard
output.
Entries are not chained.
Tamper evidence is the property of the append-only store the operator ships entries to, so the choice
of that store, and of who may change its retention, is the deployment's audit integrity decision.

{/* Evidence: crates/registry-evidence/src/config.rs AuditConfig;
    crates/registry-evidence/src/audit.rs AuthorityKind. */}

This stack has two publication paths, and they are no longer two views of the same input.

Registry Manifest publishes a **portable description**: standards-facing files that any
downstream system can fetch from a file host, produced from one `metadata.yaml` with no
running service.
Registry Relay publishes a **governed service**: a reviewed registry contract, compiled by
`relayctl` into a sealed package, served read-only over HTTP.

Earlier releases coupled the two, with Relay rendering Manifest artifacts at runtime under
`/metadata/*` and filtering them by the caller's scope.
That coupling is gone.
Relay V2 reads no manifest, and the artifacts it seals into a package are generated by its
own compiler from its own contract.
Choose the path by what you need to publish, not by which product you already run.

## Path one: portable description, no service

You write one `metadata.yaml` and run the `registry-manifest` binary.
Nothing else is required: no database, no credentials, no network, no listener.

```bash
registry-manifest validate metadata.yaml
registry-manifest render metadata.yaml --format catalog
registry-manifest publish metadata.yaml --out target/metadata/public
```

`publish` writes each rendered artifact to a named file in the target directory, plus an
`index.json` discovery entry point carrying `schema_version: registry-manifest-index/v1`.
The result is a directory of static files that can be served from an object store, a CDN,
or a government open-data portal.

From the catalog, dataset, and entity blocks of that one file, Registry Manifest derives a
DCAT catalog document, a BRegDCAT-AP profile, a CPSV-AP service catalogue for declared
public services, SHACL shapes, a JSON Schema per entity, an OGC API Records item
collection, ODRL policy documents, and CCCEV evidence metadata.
Embedded codelist nodes are SKOS-shaped inside the linked-data outputs, and the
linked-data formats are JSON-LD.
No renderer makes a network call or reads a file the manifest did not name.

A generated example lives at
`products/breg/generated/business-establishments/generated/manifest/registry-manifest.json`.
Its catalog uses the same Manifest schema. A shortened YAML equivalent looks like this:

```yaml
schema_version: registry-manifest/v1
catalog:
  id: business-establishments
  base_url: https://business-establishments.example.gov
  title:
    en: Business Establishments Registry Catalog
  publisher:
    name: Business Registration Authority
    iri: https://business-establishments.example.gov/authority
  conforms_to:
    - https://www.w3.org/TR/vocab-dcat-3/
  standards:
    dcat: "3.0"
    json_schema: "2020-12"
```

The manifest holds no source path, table name, database scope, or credential.
That boundary is what makes the output publishable: a manifest is safe to hand to a
standards body or commit to a public repository.

`registry-manifest validate` and `registry-manifest validate-profiles` are the CI-time

## Path two: governed service, compiled and sealed

Registry Relay publishes differently.
There is no descriptive file that a downstream system fetches and interprets.
There is a **registry contract** that a reviewer approves, a compiler that turns it into a
complete checked model, and a sealed package that one Relay process serves.
`relayctl` owns every step before the process starts, and `relay` owns nothing before it.

The full pipeline, from an existing SQLite database to a running service:

| Step | Command | What it produces |
| --- | --- | --- |
| Start a project | `relayctl init <PROJECT>` | A complete authoring project whose starters are visibly marked unreviewed. |
| Learn the source | `relayctl inspect <DATABASE> --starters <DIR>` | Structural facts about the database, read without reading any row value. |
| Author the contract | edit `registry.yaml` | The reviewed agreement: registry identity, sources, resources, operations, access profiles, disclosure. |
| Check it | `relayctl check <PROJECT>` | Compilation and validation, or a refusal naming what is wrong. |
| Check it for release | `relayctl check <PROJECT> --production` | The same, plus a requirement that every generated suggestion has actually been reviewed. |
| Prove behavior offline | `relayctl test <PROJECT>` | The project's fixture cases run through the same kernel the server uses. |
| Inspect the artifacts | `relayctl generate <PROJECT> --output <DIR>` | The deterministic generated inventory: OpenAPI, JSON Schema, SHACL, JSON-LD context and vocabulary. |
| Classify the change | `relayctl diff <PREVIOUS> <CURRENT>` | Every difference, each carrying a change class and an impact. |
| Seal it | `relayctl package <PROJECT> --output <DIR>` | A sealed package directory with a revision digest over its own contents. |
| Serve it | `relay serve --runtime <PATH>` | One process serving one package, with deployment-local settings supplied separately. |

Two properties of this pipeline matter more than the command list.

**`inspect` never reads a value.**
It reports the structure of the database so a publisher can author against what is
actually there, and it can write starter fragments into a directory you name.
Those starters are suggestions, not decisions: `check --production` refuses a project whose
suggestions were never reviewed, so the release gate is human review, not compiler output.

**`diff` classifies, it does not approve.**
It compares two projects and reports each difference with a class such as
`disclosure-expanded`, `scope-changed`, `purpose-expanded`, `row-binding-removed`, or
`unfiltered-enabled`, and an impact of `informational`, `narrowing`, `widening`, or
`breaking`.
A publisher can therefore see that a proposed edit widens a disclosure before it is
deployed, rather than discovering it in an audit log afterwards.

`relayctl` defines no product-specific environment-variable configuration.
Every governed input is a path, flag, project file, the documented current-directory default for
`tooling editor`, or a language-server document, so host configuration cannot select another
Registry or deployment environment.
A global `--json` flag emits the shared report for local automation.

## What a sealed package is, and what it is not

`relayctl package` writes a directory containing the authored `registry.yaml`, the
governed input files it referenced under `governed/`, the compiled model at
`compiled/registry.json`, the generated artifacts under `generated/`, and a
`relay-package.json` manifest that lists every file with its digest.
The manifest's `packageRevision` is a digest over the canonical form of that list.
The command refuses to write into a directory that already exists, and it leaves a
partially written directory in place rather than deleting evidence of a failed attempt.

At startup, Relay re-derives that digest from the files on disk and compares it byte for
byte before it serves anything.

This is an integrity check, not an authenticity check.
`packageRevision` proves that the package you are serving is the package that was built.
It does not prove who built it.
Relay packages are not signed, and Relay signs no response.
If you need an authenticity proof, it has to come from the channel you distributed the
package over, or from your own signing step around it.

{/* Evidence: crates/registry-relay-v2/src/package.rs:25-26 declares

The deployment-local half stays outside the package entirely.
Listener address, source file paths, issuer, audit sink, secrets, limits, and quotas live
in a separate `runtime.yaml` that cannot add or weaken anything the contract decided.
See [Configure Relay](../../configure/relay/) for that file's shape.

## Choosing a path

Publish with Registry Manifest when:

- You need static standards artifacts for an open-data portal or a discovery index.
- You want the description to survive without a service, or to be validated in CI before
  any deployment exists.
- Your environment cannot run a persistent process.

Publish with Registry Relay when:

- Callers need authorized read access to actual records, not a description of them.
- The data is sensitive enough that you want the readable columns, the operations, and the
  shape of every response fixed by review rather than by a query the caller writes.
- You need a durable audit record of each released response.

The two are not alternatives, and they are also not two ends of one pipeline any more.
A deployment can run both: a static manifest publication that tells the world the registry
exists and what it contains, and a governed Relay deployment that answers authorized
questions about it.
They are maintained as separate inputs, and a change to one does not propagate to the
other.

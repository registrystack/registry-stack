If you are designing an institutional registry with Base Registry Engine (BReg),
one governed project supplies its storage, API, permissions, and write behavior.
The runtime stays domain-neutral while the project declares your Record types,
Actions, and durable Proposals.

## What you write

`registry.yaml` declares identity, datasets, Record types and fields, references,
access profiles, Actions, and events. Modules reuse governed assets. Project-local
value types and named Functions share types and plan code without introducing a
second configuration format. Stable IDs identify definitions; labels,
descriptions, and safe titles present them to readers.

Journey fixtures declare permitted and refused API behavior. Local clients and
resumable scenarios support evaluation. Deployment configuration separately binds
PostgreSQL, issuer, secrets, listeners, review authorities, and destinations.
Operator credentials stay outside the authored package.

## What the server compiles

Record types become typed PostgreSQL storage with reference, uniqueness, revision,
and optional temporal constraints. Generated routes expose only configured
operations. Schemas, OpenAPI, metadata, and typed project clients derive from the
same contract. An Action input's compiler-emitted JSON Schema is required and is
copied exactly into MCP tools.

The shared Registry Record envelope keeps record identity and revision separate
from domain fields. Its independently versioned `entityTypeIdentifier` names the
Record type. Action receipts and Proposals use distinct response shapes.

## How access works

The issuer owns identity and tokens. BReg verifies a token, selects one access
profile, and checks its operation, field, and row grants before record I/O.
Profiles grant records, Actions, and Proposals separately. A local client, a
reference, a filter, a metadata descriptor, or a review result creates no grant.

Concealment hides inaccessible records and work. Proposal List requires its own
authority and conceals work before filtering or counting. Human review context
also obeys current record disclosure. A service review-status grant is limited
to the named authority's frozen work and carries no display values.

### Local clients and their tokens

The development command provisions a local issuer and registers explicitly
authored clients. The default directory uses two clients with distinct
jurisdictions against the same editor profile. Their scopes and claims satisfy
that project's grants; registering another client adds no registry authority.
Operated deployments supply their own issuer and credentials.

## Three ways to write

Generated CRUD maintains individual records under explicit permissions and
concurrency conditions. An immediate Action accepts typed inputs and applies an
ordered plan atomically, including multi-record effects. A Proposal Action starts
a durable draft and later freezes a plan for application.

Action execution mode is governed configuration. Fixed plans declare effects;
named Functions calculate effects inside an explicit write ceiling. Guards check
required current facts at commit. A Record type can require Proposals for an
operation independently of profile grants, so an immediate Action cannot bypass
that boundary.

Submission freezes inputs, targets and revisions, effects and digest, Action
revision, attachments, and the external policy binding. An external authority owns
review decisions. BReg owns applying the exact frozen plan and never reruns changed
code to reinterpret it. Review-required application needs fresh authenticated,
unexpired approval.

Automatic application is the default under the built-in executor's restricted
system grant. Explicit manual mode uses independent caller Apply authority.
External recovery of automatic work needs a verified human and an explicit grant.
No executor OAuth client or self-HTTP endpoint is needed.

An authorized Proposal Get reports the exact frozen binding and local application
status. Applied work carries retained evidence; blocked work carries safe recovery
information and authorized links. Revise or Rebase makes an earlier binding stale.
Observation does not reconcile an uncertain command: retain its original prepared
request and key for exact recovery.

## History, time, and erasure

Writes preserve revisions and audit, and optional validity intervals describe when
facts apply. Snapshot reads reproduce a retained committed state under current
authority. History, Proposal detail, attachments, Evidence uses, and idempotency
responses have distinct retention scopes. Erasure cannot be undone; expired or
erased receipts keep their keys spent and cannot execute again.

## From project to production

Offline compilation precedes real-PostgreSQL journey testing. A successful exact
receipt permits packaging. The operator reviews and activates that same package
with separate migration authority. Deployment identity and database values remain
environment-specific. Incompatible open work cannot be silently reinterpreted
by activation; preserve inspection and recovery or resolve the work first.

## Events

Committed record and Proposal transitions produce governed outbox work. Delivery
is authenticated, bounded, retried, and inspected independently of the source
transaction. A receiver owns durable acceptance, deduplication, and any external
effect. Delivery grants no authority to read or mutate BReg.

## Where the product stops

BReg owns its PostgreSQL source of record. It carries no built-in institutional
domain, issues no identity tokens, and evaluates no external review policy.
Optional review or Evidence dependencies disable only operations requiring them;
they never widen authority or block unrelated configured operations.

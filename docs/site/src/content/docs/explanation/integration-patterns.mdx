Choose the smallest product boundary that answers the integration need.

## Governed system of record

Use Base Registry Engine (BReg) when the institution needs to create, update, review, and audit
records in a PostgreSQL-backed registry. Applications call BReg's own record API. Casework can coordinate
review while BReg retains mutation authority.

## Bounded evidence

Use Evidence Gateway when a relying service needs a signed answer to a predefined question. Configure
one fixed source request, bounded derivation, entitlement, and output contract. The relying service
verifies the assertion and makes its own decision.

## Static metadata publication

Use Registry Manifest when an integrator needs portable catalog, schema, service, policy, or
evidence-offering metadata. Render and host the artifacts as static files. Metadata describes the
service but does not grant access.

## Provider discovery

Use Registry Discovery to publish a curated index of Evidence Gateway descriptions. The application
searches, explicitly selects, validates, and locally accepts a provider before constructing the
native Evidence client.

## Workflow orchestration

Any orchestrator can call maintained product APIs: an outbox service beside your application, a
workflow engine, or a scheduled job. Keep credentials and product policy in the owning boundary. A
workflow may coordinate calls, but it does not become the authorization source or system of record.

Take one journey: register an establishment in BReg, then book its inspection in Registry
Scheduling<DocsetProduct product="registry-messaging"> and notify its contact through Registry
Messaging</DocsetProduct>. Each step calls a different product, any answer can be lost, and the
journey can wait between steps for a person or a free slot. The same rules let you resume any step
safely:

1. Derive each step's `Idempotency-Key` from the source event and the step, for example
   `<event-id>:register` and `<event-id>:book`, and persist it before the first send. A random key
   makes a resumed step a second request, and a key built from personal data copies that data into
   the product's idempotency records. Keep each key to the form every product in this journey
   accepts: 1 to 128 visible ASCII characters, with no comma or semicolon. BReg accepts up to 256
   bytes but refuses those two characters; the others accept them but stop at 128.
2. Retry under the persisted key, within the receipt horizon. The maintained clients for these
   products already resend a mutation whose outcome is unknown under the same key, at most twice by
   default, as
   [unknown outcomes](../../reference/client-api/#unknown-outcomes-and-the-same-key-retry)
   describes. When the error still reports an unknown outcome, your later retries reuse that key;
   a new key can apply the step twice. Each product holds a key's first answer only for its receipt
   horizon, 7 days by default in BReg (`idempotency.receiptRetentionDays`). Past it, BReg answers
   an exact retry with `410 idempotency.expired` and runs nothing: the write committed, so read the
   record instead.
3. When a step acts on a human approval, obtain a task grant for that step close to when it runs,
   instead of holding one grant across a wait. A Registry Casework grant lasts at most 900 seconds,
   and each assertion minted from it at most 60 seconds. Persist only the grant ID, never an
   assertion or an access token. A grant that expires before its step completes needs a new
   approval and a new grant.
4. Observe each outcome with an ordinary read token for the same principal, not with the step's
   grant, which may have expired by the time you look.
5. Keep references in the orchestrator's state: the event ID, each step's key and grant ID, record
   IDs and revisions, appointment IDs<DocsetProduct product="registry-messaging">, message
   IDs</DocsetProduct>, and external references. Never keep a token or personal data there; read a
   contact from the source of record when the step that needs it runs.

The products differ in where a grant is needed and how you find an outcome you never received.

From BReg, keep the record identifier and revision identifier a write returns.
[Idempotency](../../reference/breg-api/#idempotency) gives how long BReg replays a key and what an
exact retry answers after that.

{/* Evidence: crates/registry-record/src/lib.rs, record_identifier and revision_identifier. */}

Scheduling commits capacity only under a live grant that covers the offering's service, location,
and action. Send `externalReferences` naming the BReg record with the booking. Once the grant has
expired, call `GET /v1/appointments` filtered by that reference with a read token for the same
issuer and subject; the listing returns only the caller's own appointments, so book and observe
under one principal.
[Recover an unknown outcome](../../reference/apis/registry-scheduling/#recover-an-unknown-outcome)
gives the receipt horizon and its refusals.

<DocsetProduct product="registry-messaging">

Messaging takes no task grant: the sender's access profile decides. Keep the message `id` from the
`202` receipt and call `GET /v1/messages/{message_id}` as the principal that submitted it.
[The Messaging contract boundary](../../reference/apis/registry-messaging/#contract-boundary) gives
the key horizon, its refusals, and the recovery when a `403` or `422` answers an exact retry.

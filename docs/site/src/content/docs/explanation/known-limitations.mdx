Registry Stack ships versioned `v0.x` releases, each with published release notes. The
open-source project does not operate deployments and offers no service-level agreement: your
institution, or the provider it contracts, runs each deployment and agrees hosting, support, and
response times in that contract. This page lists the limits that apply across products, and where
each product states its own.

## Product maturity

- Interfaces may change before 1.0. Keep clients and deployments on compatible releases.
- Operators must supply production identity, networking, transport termination, secret storage,
  key custody and rotation, edge rate limiting, tenant isolation, monitoring, audit storage,
  backup, and incident response.
- Generated checks establish contract consistency. They do not certify legal compliance,
  accessibility, source correctness, or institutional authority.

## Platform support

Open the [release](https://github.com/registrystack/registry-stack/releases) for the version you
deploy. Its assets list the installers, native binaries, and client packages available for each
platform. The release manifest records the published container images and their digests.

- The release publishes no Windows, Intel macOS, or musl Linux artifact. Installers refuse
  unsupported operating systems and architectures before downloading.
- Standalone Linux binaries, including CLI tools, link the GNU C library dynamically and require
  glibc 2.34 or newer. Installers reject detected musl hosts, including Alpine, and glibc versions
  below 2.34. That floor is the one of the release an installer was published with. A release's
  Linux binaries need the glibc that release was built for, so each installer also starts every
  Linux binary it verified before it selects the release. A release whose binary does not start on
  the host is refused, and the installed toolset stays selected. Python client wheels are
  `manylinux_2_17`; no `musllinux` wheel is published.
- Each container image is `linux/amd64`; no multi-architecture image index is published. An arm64
  container host therefore needs amd64 emulation.
- Published macOS executables target arm64. Registry Manifest ships as a standalone executable.
  An archive includes the executable, notices, and any shared AWS-LC-FIPS libraries it uses.
  The release publishes no Homebrew formula, `cargo binstall` target, apt, apk, yum, Nix,
  winget, or Scoop package.
- A release publishes no Helm chart, Compose deployment, Kubernetes operator, or hosted offering.
  The source tree carries an unsupported reference Helm chart for a single-server K3s installation.
  It is not part of any release.
  The Base Registry Engine (BReg) quickstart publishes its container ports on loopback only.
  On Linux, its short-lived development key listener binds every interface while it runs and
  serves only a public key.

## Stack-wide boundaries at a glance

- No source mutation: Registry Evidence reads its fixed sources read-only, and persists nothing it
  read.
- A published manifest grants nothing: Publishing a dataset, policy, or evidence offering in a
  discovery artifact grants no access, enforces nothing, and asserts no fact about a live record.
  Discovery metadata is not a trust anchor: a published manifest does not bind a consumer to trust
  a JWKS endpoint or a service host.
  Trust bootstrap stays in the consumer's local policy.

## Security-model operator boundary

A healthy, reachable, internally consistent deployment is not the same as a production-secure one.
Read the full security boundary in the [security overview](../../security/).

- Health checks do not certify key custody: Readiness, liveness, and protocol-conformance checks
  do not certify production-grade private-key custody.
  A deployment using software keys, local JWK files, or demo-generated keys can be reachable and
  internally consistent yet not production-secure.
- Audit retention is not audit completeness: Base Registry Engine, Registry Evidence, Registry
  Casework, Registry Coordinator, Registry Document Store, Registry Messaging, Registry Render,
  and Registry Scheduling write their local audit logs through one shared writer.
  It neither chains nor signs entries, so the log gives no cryptographic tamper evidence.
  A running writer detects an external change to its active file and fails closed.
  With the `file` destination it deletes sealed files after `retentionDays`.
  Registry Adapter keeps its audit journal in an append-only PostgreSQL table and deletes rows
  older than its retention period.
  No product ships sealed history for you.
  Tamper evidence and completeness come only from the append-only storage the operator ships audit
  entries to.
- Demo and template code is not a production profile: Demo helper code and generated workflow
  snippets are integration examples, not a production freshness or replay-protection profile, and
  must not be relied on for freshness, expiry, or replay protection.

## Supply-chain and release limits

- Partial release signing: One keyless cosign bundle authenticates the public
  `SHA256SUMS` inventory, and GitHub artifact attestations authenticate the
  candidate manifest and bundle.
  OCI image signatures are not yet published, and Git version tags are not yet
  cryptographically signed (GPG, SSH, or Sigstore).
  The `v0.8.0` prerelease predates release-asset signing and remains unsigned.

For how to verify what *is* signed, see the release verification guidance in `release/VERIFY.md`
in the repository.

## Product removal

Registry Relay ended with version 0.38.0 and is absent from 0.39.0. No maintained component replaces
its generic SQLite publication, SDMX, or JSON-FG surfaces. See the
[retirement decision](../../decisions/registry-relay-retirement-2026-10-03/).

If your Base Registry Engine (BReg) registry needs changes beyond field-by-field edits, declare
them as Actions. Here you see what an Action declares, when it applies at once and when it becomes
a reviewed Proposal, and how a Plan computes its effects.
[Change a registry with an Action](../../tutorials/change-a-registry-with-an-action/) runs both.

## Start from the facility template

```sh
bregctl init --template facility-registry facility
bregctl check facility
```

The template declares three Actions: `register-facility`, `correct-address`, and
`deactivate-facility`; `bregctl explain actions facility` shows each one compiled.
The authored `operator-editor` access profile supplies setup authority; tooling never injects a seeding grant.

## What an Action declares

An [Action](../../reference/glossary/#action) has typed `inputs`, an `execution` mode, a `plan`
of effects, and optional `commitGuards`. `deactivate-facility` holds all four:

```yaml title="registry.yaml" test-excerpt="facility/registry.yaml"
  deactivate-facility:
    display:
      label: Deactivate facility
      description: Submit a durable deactivation that requires no external review.
    execution:
      mode: proposal
      proposal:
        review: {type: none}
        application: {mode: manual}
        retention: {mode: retain}
    commitGuards:
      targets:
        - {input: facility, revision: unchanged}
        - {input: facility, field: status, equals: active}
    inputs:
      - {id: facility, apiName: facilityId, type: reference, target: facility, required: true, classification: internal}
    plan:
      type: fixed
      effects:
        - id: facility-status
          target: {fromInput: facility}
          operation: patch
          set:
            status: {value: inactive}
```

Commit guards are checked when the change commits: here, the facility must be unchanged since
the Proposal froze it, and still active. The caller never chooses the execution mode.

Who may run an Action is an access-profile grant, `invoke` for an immediate Action and `start`
for a Proposal:

```yaml title="registry.yaml" test-excerpt="facility/registry.yaml"
      actions:
        - action: correct-address
          operations: [start]
```

Other Proposal operations, such as `submit`, `cancel`, or `apply`, are granted separately under
`permissions.proposals`, so whoever drafts a change need not apply it.

The Action grant also declares `targets`. Every input that references an existing Record needs
current target authority, including a reference used only as a link in a newly created Record.
When two inputs reference the same Record type, BReg checks the target row boundaries against each
referenced Record independently. An `in` boundary therefore succeeds only when the array claim
covers both Records; authority over one does not authorise the other.
From a matching source checkout, run
`rstack dev start products/breg/fixtures/multi-reference-array-claim`
to exercise the permitted and refused cases with the fixture's test callers.

## Immediate Actions return an ActionReceipt

`register-facility` declares `execution: {mode: immediate}`. One request checks the guards,
writes every effect, and commits the new revisions, the receipt, the audit entry, and any outbox
events together, or none of them. The answer is an
[ActionReceipt](../../reference/glossary/#action-receipt) naming each changed Record and its new revision.

Before invocation, use the caller-filtered Action descriptor to identify concurrency conditions.
`requiredConditionKeys` contains the API names of existing write targets and inputs with an
`unchanged` revision guard. When that list is nonempty, `routes.targetConditions` advertises the
endpoint that reads their current condition tokens. Send its returned `preconditions` unchanged
with the invocation. A reference used only as a link still needs target authority, but it is not a
condition input. When `requiredConditionKeys` is empty, omit `preconditions`.
The [immediate Action API contract](../../reference/breg-api/#immediate-actions) gives the request
rules.

A Record type can require a Proposal for an operation:

```yaml title="registry.yaml" test-excerpt="facility/registry.yaml"
    mutationPolicy:
      patch: proposal-required
```

With this on `facility`, neither a direct patch nor an immediate Action may patch a facility; only
a Proposal can. `register-facility` still creates facilities at once.

## Proposals

An Action in `proposal` mode creates a [Proposal](../../reference/glossary/#proposal) instead.
`correct-address` requires review:

```yaml title="registry.yaml" test-excerpt="facility/registry.yaml"
    execution:
      mode: proposal
      proposal:
        review:
          type: required
          authority: casework
          source: facility-registry
```

A Proposal starts as a `draft` its author can edit. Submitting it freezes the inputs, the
computed effects and their digest, the target revisions, and the Action revision; review and
application work on that frozen submission, so a later change to the Plan or policy cannot
reinterpret it. Revise or Rebase returns it to a new draft, which must be submitted, and
reviewed, again.
[Configure Proposals](../breg-proposals/) covers review declaration, grants, turns, and recovery in full.

A Proposal ends in one of three states:

- `applied`: the registry wrote the frozen effects, under the commit guards as they stand at that
  moment. With no review it follows submission; with required review it needs current approval of
  that exact submission.
- `rejected`: the review authority rejected the submission. This is final. A reviewer who wants
  another attempt returns it with changes requested instead, which keeps it `submitted` and offers
  Revise.
- `cancelled`: a caller with the `cancel` grant withdrew it before it applied.

Application is automatic, under a restricted system grant for that one submission, unless the
Action declares `application: {mode: manual}`, as `deactivate-facility` does; then a caller with
the `apply` grant applies it. The Proposal's `applicationStatus` reports progress: `awaiting-review`, `pending`,
`applying` while a worker is writing it, then `applied`, or `blocked` with a reason and a
recovery hint.

## Review authorities, declared twice

The project names each review authority it relies on:

```yaml title="registry.yaml" test-excerpt="facility/registry.yaml"
reviewAuthorities:
  - id: casework
    protocol: id.registrystack.org/protocols/review/v1
    display:
      label: Casework review authority
      description: Logical authenticated review authority resolved by deployment configuration.
```

The deployment binds that `id` to a running service. The template's README shows the binding to
write in the runtime configuration:

```yaml title="README.md" test-excerpt="facility/README.md"
reviewAuthorities:
  casework:
    endpoint: http://127.0.0.1:8100/
    profile: requester
    producerId: facility-registry
    recoveryDays: 30
    client: requester
```

In production the same map sits in the runtime configuration (`runtime.yaml`), with a `tokenRef`
or `privateKeyJwt` credential instead of `client`. A `privateKeyJwt` credential's required
`assertionAudience` is the authorization server's issuer identifier, exactly as its metadata
publishes it, which the client assertion carries as its only audience (RFC 10070 section 4). A
missing binding disables only the operations that need it. An unreachable authority never counts as approval.

Registry Casework is one such authority. The registry sends it the frozen submission and applies
only the correlated result;
[Review a Proposal in Casework](../../tutorials/review-breg-changes-in-casework/) pairs the two.

## Plans and Evidence

A [Plan](../../reference/glossary/#planner) is fixed, like `deactivate-facility`'s, or computed
by a Rhai Function. `correct-address` names its Function and bounds what it may write:

```yaml title="registry.yaml" test-excerpt="facility/registry.yaml"
    plan:
      type: function
      function: correct-address-plan
      inputs: [facility, address-line, city, postal-code]
      writes:
        - id: facility-address
          target: {fromInput: facility}
          operation: patch
          fields: [address-line, city, postal-code]
      refusals:
        - {code: invalid-postal-code, label: Postal code is invalid}
```

The project's `functions` entry names its script:

```rhai title="plans/correct-address.rhai" test-excerpt="facility/plans/correct-address.rhai"
fn plan(ctx) {
    let postal_code = ctx.inputs["postal-code"];
    postal_code.trim();
    if postal_code == "" {
        return #{
            refusal: #{
                code: "invalid-postal-code",
                field: "postal-code"
            }
        };
    }
```

The planner receives `ctx.inputs`, holding only the inputs the Plan lists. It returns either a
`refusal`, whose `code` the Action declares, or `effects`: a list of maps, each with the `id` of a
declared write and its `set` or `clear` fields. The declaration fixes each write's target and
operation, so the script cannot redirect one. Omitting a write skips it; the caller still needs
authority over its target.

Effects apply in authored order. A value `fromEffect` must name an earlier `create`, as
`register-facility`'s assignment names its new facility. Two effects that land on the same Record
are written together as one revision; two effects that write the same field fail `bregctl check`.

An Action with a Rhai Plan may also declare `evidence`: at most two capabilities, each naming an
Evidence provider the project declares, a requirement, its subjects, and the outputs it may read.
The script calls `evidence::resolve("<capability id>", subjects)` once per capability and
receives only those outputs; a failed call refuses the operation. `commitGuards.evidence`
instead checks a requirement at commit and never changes the effects. The provider's endpoint and
credentials belong to the runtime configuration; BReg inherits no Evidence authorisation.

## Plan syntax and Rhai limits

A plan fragment looks like this; use the complete facility project for required fields, references, guards, datasets, and grants:

```yaml
actions:
  register-facility:
    execution:
      mode: immediate
    inputs:
      - id: name
        type: string
        required: true
        minimumLength: 1
        maximumLength: 200
        classification: internal
    plan:
      type: fixed
      effects:
        - id: facility
          target:
            recordType: facility
          operation: create
          set:
            name:
              fromInput: name
```

HTTP input names come from `apiName`, and plans address the authored input IDs.
A literal uses `value`; a reference to an earlier created Record uses `fromEffect`.
Effect order is authored order, with explicit dependencies.
A forward reference refuses compilation.
Aliased writes to one target fold into one revision; conflicting writes or cycles refuse atomically.

For computed effects, declare a named Function and select `plan.type: function` with its `function`, `inputs`, `writes`, and declared `refusals`.
The write ceiling remains governed configuration.
A Function's `writes` are a ceiling, not CRUD permission: a profile allowed to invoke the Action gains no ordinary create or patch on the Record types those writes name.
Rhai uses `registry.action-plan/v1` and `ctx.inputs`, and returns exactly one of two map shapes: `#{effects: [...]}` or `#{refusal: #{code: "...", field: "..."}}`, where `field` is optional.
[WASM handlers](../breg-wasm-action-handlers/) have their own admitted backend contract.

A Rhai plan has no database, filesystem, network, clock or stored-Record API.
The host owns the target, operation, IDs, authority, validation and transaction.
The only exceptions are `today()`, the registry-local date captured once for the evaluation, and `evidence::resolve` where the Action declares Evidence.
The [person registration example project](https://github.com/registrystack/registry-stack/blob/main/products/breg/acceptance/person-registration-rhai/README.md) shows normalisation, coordinated creates and omitted effect slots.

{/* Evidence: crates/registry-breg/src/tests/rhai_planner_sandbox_tests.rs (a_plan_cannot_read_the_clock);
    crates/registry-breg/src/action_handler.rs today evidence::resolve;
    products/breg/acceptance/person-registration-rhai/README.md */}

A Function accepts only declared scalar inputs, including Record reference IDs.
A `decimal` input arrives as its canonical JSON string.
Compilation refuses a `crs84-point`, `crs84-polygon`, or `structured` input with `breg.action.handler-input-type-unsupported`; use fixed effects for those values.
A `string` or `text` input must declare a `maximumLength` of at most 4,096 Unicode scalar values, so every value fits the 16,384-byte UTF-8 string budget; a larger bound fails with `breg.action.handler-input-string-bound`.
Every Function input string, timestamps included, also has a 16,384-byte admission limit.
An HTTP request exceeding a declared bound or that byte limit returns `400 request.invalid` before the Function runs.

An omitted optional input has no key in `ctx.inputs`; an explicit JSON `null` has a key whose value is the unit value `()`.
Test membership with `in` when absence matters, and guard both cases before calling a string method:

```rhai
let family = if "family-name" in ctx.inputs && ctx.inputs["family-name"] != () {
    ctx.inputs["family-name"]
} else { "" };
family.trim();
```

Calling a string method on an unguarded missing or null value fails the handler.
Required inputs refuse omission and null before the Function runs, and fixed-effect Actions refuse an explicit null input.
When an optional input is absent or null, omit the corresponding field from an effect's `set` map.
Copying `()` or `null` into a required, non-null field is a handler result failure; it does not clear the field.

The Rhai Action ABI provides three bounded date-string helpers:

- `today()` returns the registry-local `YYYY-MM-DD` date captured once for the evaluation.
- `add_days(date, days)` adds from -365,000 through 365,000 whole days.
- `add_months(date, months)` adds from -12,000 through 12,000 months, clamping to the target month's last day.

Invalid dates, an out-of-range result, or an offset outside those bounds fails the handler without exposing the supplied value.
A Function that calls `today()` requires `project.timezone`.
A caller-selected business date remains a typed input such as `asOfDate` and is caller data.
Plan logic runs only when that Action is invoked and is not a Record field-validation boundary.
If a rule must not be bypassed, withhold the ordinary Create profile that could write the same state without the Action.

`bregctl check` performs one narrow source check for literal catalogue mistakes.
It validates the string literal in a returned root map whose only key has the shape `#{refusal: #{code: "..."}}`.
It also validates each string-literal `id` in a returned root map whose only key has the shape `#{effects: [#{id: "...", ...}]}` with a literal effects array.
The walker checks explicit `return` statements anywhere inside the one-argument entrypoint and its final root-level map expression.
It does not inspect an implicit map result inside a nested `if` branch.
Helper-returned, computed, or dynamically assembled outcomes remain runtime behaviour and need executable branch tests.

A Record timer may invoke a deliberately non-public immediate Action from governed Record fields.
That timer-only Action remains in compiled inspection but has no caller route, access-profile selection, public metadata entry, portable Action contract, or generated client method.
See [Schedule Actions with Record timers](../breg-record-timers/).

## Authorise and guard an immediate Action

An Action grant uses `permissions.actions`, the Action ID, `operations: [invoke]`, explicit target row boundaries, and permitted result effects.
It grants no ordinary CRUD.
Its target row boundaries are runtime-enforced Action authority in addition to any ordinary Record grant held by the same profile.
Every existing reference target needs current target authority, including link-only references and targets chosen by a function.
`commitGuards` checks required current facts inside the mutation transaction.
A Record type's `mutationPolicy` still prevents immediate writes to Proposal-required targets.

`bregctl explain access` reports this authority, whether any direct Record grant also exists, and the compiled write or existing-target role of each Action target use.
The direct-grant flag does not compare that grant's operations or row boundaries, and Action target authority does not grant ordinary CRUD.
For a Proposal Action, a `write` use under the Start grant describes an effect the Proposal may apply after approval; it does not grant the Start caller a direct Record write.

An invocation commits Record effects, revisions, history, audit, the idempotency receipt, and outbox together.
A refused effect leaves no partial Record or event.
The response discloses only granted result effects.
Events describe committed work; an external webhook failure cannot roll back the registry transaction.
The webhook receiver example shows durable acceptance and deduplication for an adopting service.

### Shift a date guard by an offset

A date guard may shift the registry-local date by a signed whole-day offset:

```yaml
commitGuards:
  targets:
    - input: licence
      field: valid-through
      currentDate: on-or-after
      currentDateOffsetDays: 30
```

An absent or zero `currentDateOffsetDays` compares with today.
The bounded offset applies to the same local date for advisory availability and for commit or Proposal Apply re-evaluation.

A Proposal Plan evaluates `today()` once, when the Proposal starts.
Its commit guards check `currentDate` again when the Proposal is applied.
If approval crosses midnight or takes days, the date the Plan used and the date the guard compares against are different days.
Write the guard offset with that gap in mind.

### Compare a stored field with an input

A field guard on a reference input compares the target's stored field with a literal (`equals`, or an integer `atLeast` or `atMost`) or with a declared Action input, so the caller never echoes the stored value back:

```yaml
commitGuards:
  targets:
    - input: case
      field: opened-at
      atMostFromInput: assigned-at
    - input: case
      field: expires-on
      atLeastFromInput: assigned-on
inputs:
  - id: assigned-at
    type: timestamp
    required: true
    classification: internal
  - id: assigned-on
    type: date
    required: true
    classification: internal
```

`equalsFromInput`, `atLeastFromInput`, and `atMostFromInput` each name one declared input; a guard carries exactly one comparison.
The stored field is the subject, and both bounds are inclusive: `atMostFromInput` passes when the stored value is less than or equal to the input, and `atLeastFromInput` when it is greater than or equal to it.
The two ordered keys accept `int64`, `date`, and `timestamp` fields only, and the input must be a `required` input of the same type.

`bregctl check` refuses a pairing of different types, a field with no order (such as `string` or `decimal`), an undeclared input, and an optional input (`breg.action.commit_guards.targets-value-invalid`).
A missing input therefore never reaches a guard at commit, and an availability check that lacks it answers `input-required` with `missingInputs`, as for `equalsFromInput`.
The comparisons use no new operators or expressions.
A guard cannot express "one of several values". For a rule such as "revoke a licence that is active or suspended", `equals` takes one scalar and `bregctl check` refuses an array literal.
Declare one Action per allowed state, each guarded on one value and producing the same effect.

Dates compare as calendar dates and timestamps compare as instants, not as text, so `2026-10-30T10:00:00Z`, `2026-10-30T10:00:00+00:00`, and `2026-10-30T12:00:00+02:00` are the same instant.
A stored `timestamp` is an instant that the registry reads back in UTC with a `+00:00` offset (see [Model event records](../breg-event-records/)); a client never needs to match that text.
A stored value that is absent fails the guard, so an unset optional field is never at least or at most any input.
A failed guard answers like any other field guard: `412 action.guard_failed` when the guard facts are readable, else `412 precondition.failed`, with no Record changed.

### Check one target's advisory availability

An immediate Action with at least one reference input advertises one `routes.availability` endpoint.
`targetInput` selects one reference input for that request.
Send that reference and any other declared input values already available to the application:

```json
{
  "targetInput": "itemId",
  "input": {
    "itemId": "00000000-0000-0000-0000-000000000001"
  }
}
```

The check evaluates field-based `commitGuards` for that one target under the selected Action profile and its ordinary Get disclosure.
It returns the observed target revision with `available: true`, or with `available: false` and the reason `guard-not-satisfied`.
A guard may declare an optional, stable LocalId `reason` of at most 64 characters.
The response exposes it as `guardReason` only when every guard fact and every row-boundary fact for the selected target is readable.
The generic `reason` remains `guard-not-satisfied`.

If a declared input needed by a guard is absent, `available` is `null`, the reason is `input-required`, and `missingInputs` names only declared API input names.
If a guard or row boundary depends on a fact the caller cannot read, or the profile lacks Get authority for the target Record type, the answer is `available: null` with `observedRevision: null`, `not-disclosed`, and no `guardReason` or `missingInputs`:

```json
{
  "availability": {
    "available": null,
    "observedRevision": null,
    "reason": "not-disclosed",
    "recovery": "none"
  }
}
```

A target denied by the ordinary Get boundary and a missing target both use the concealed 404.
Query reference inputs separately when an Action has several targets.
A known failed guard takes precedence over missing guard input; correcting that guard may expose an `input-required` result on the next check.
No availability response names a guard ID or a Record value.

Availability is an observation.
It does not run a Function, test SQL uniqueness or Evidence, mint a condition token, grant mutation authority, or reserve the observed revision.
Invoke remains responsible for current authority, concurrency, form completeness, every guard, Functions, and Evidence; all required checks must succeed before effects commit.
`available: true` means only that this target's field guards are currently satisfied, including the case where it has no field guards.

A safely disclosed field guard that fails at commit answers `412 action.guard_failed` after current-target admission checks pass.
The code confirms that blocker; effect application, proposed-value authorisation, and database constraints run only after guards pass.
An earlier refusal retains its normal response.
Stale conditions and guard failures that cannot be disclosed remain `412 precondition.failed`.
Invoke rechecks the guard during commit.
If it fails, BReg rolls back and re-observes disclosure before returning `guardReason`; advisory `guardReason` is neither authority nor a reservation.

## Invoke and recover

Select the Action from caller-filtered metadata.
Its fixed execution mode and advertised routes distinguish immediate Invoke from Proposal Start.
Obtain any required target conditions through the selected binding, and use advisory availability to guide the form when the Action advertises it.
Retain the user's input and conditions, and prepare one invocation with a caller-owned idempotency key.
The server rechecks package identity, current authority, guards, and concurrency.

An omitted `accessProfile` when the Action route has no default, an unknown profile, and a profile the caller cannot use all return the same concealed 404.
The response does not list usable profiles.
Select the profile and Action from caller-filtered metadata, then prepare the invocation from that client binding instead of probing Action URLs.

Recover a lost response using the same prepared request and key.
A replay returns the retained receipt without replanning or reacquiring Evidence.
A changed input or binding conflicts; an expired or erased receipt refuses without executing again.
Refresh stale conditions only after reviewing current input and targets.

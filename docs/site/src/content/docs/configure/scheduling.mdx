If you are writing the policy a Registry Scheduling deployment will serve, you edit one project
directory and prove it offline. You continue in `./scheduling`, the project from
[Prove your first booking policy](../../tutorials/first-scheduling/), where the fixture already
closes `station-2`.

## Read the opening hours

An offering is bookable only inside an [opening](../../reference/glossary/#opening): the weekly
hours one location publishes. `check` listed two under `effective.openings`. This is the one that
serves `registry-update-30`:

```yaml title="scheduling/scheduling.yaml" test-excerpt="scheduling/scheduling.yaml"
openings:
  bangkok-counter-hours:
    location: bangkok-counter
    holidaySet: office-holidays
    weekdays: [mon, tue, wed, thu, fri]
    startTime: "09:00"
    endTime: "12:30"
    effectiveFrom: "2026-10-01"
    effectiveUntil: "2026-12-31"
```

Times are wall-clock times at the location, read in the time zone its location record names, so
the counter opens at 09:00 Bangkok time on weekdays. The opening ends on `effectiveUntil`; from
2027 this offering publishes no starts until you extend that date and deploy the change.

## Close a public holiday

Every opening names a [holiday set](../../reference/glossary/#holiday-set), and a date in that set
closes the opening for the whole day. The starter's set closes nothing yet. Close Tuesday 13
October 2026:

```diff test-edit title="scheduling/scheduling.yaml"
   office-holidays:
     revision: 1
+    dates:
+      - "2026-10-13"
     label: Public holidays observed by the registry offices.
```

Prove it with a case at the end of the counter fixture. A booking at 09:00 that day must be
refused:

```yaml title="scheduling/fixtures/counter-stations.yaml" test-append
  - name: the-holiday-is-not-served
    request:
      offering: registry-update-30
      start: 2026-10-13T02:00:00Z
      party:
        recipients: 1
        attendees: 1
      duplicateKey: subject:four
      policyRevision: 1
    expect:
      type: refused
      code: schedule.unpublished
```

```sh
schedulingctl test ./scheduling --format json
```

```json test-excerpt
{
  "detail": "refused schedule.unpublished (detailed: schedule.unpublished)",
  "name": "the-holiday-is-not-served",
  "status": "pass"
}
```

A passing report carries `proofBoundary: offline-synthetic` and `productionClosure: false`, so it
does not establish source reachability or deployment readiness.

## Read the hold and reminder rules

A caller first takes a [hold](../../reference/glossary/#hold) on a start, then confirms it as an
appointment. The hold policy applies to every offering:

```yaml title="scheduling/scheduling.yaml" test-excerpt="scheduling/scheduling.yaml"
holdPolicy:
  ttlMinutes: 5
  maximumPerCaller: 3
  because: Holds are short because counter capacity is scarce.
```

An unconfirmed hold returns its station to the pool after five minutes, and one caller holds at
most three at a time. The offering adds its own rules:

```yaml title="scheduling/scheduling.yaml" test-excerpt="scheduling/scheduling.yaml"
cancellationCutoffMinutes: 240
reminders:
  - offsetMinutes: 1440
    because: One reminder the day before a counter update.
  - offsetMinutes: 120
    because: A second reminder two hours before, when stations are scarce.
duplicateActiveKey: subject
```

A caller may not cancel within four hours of the start. Each confirmed appointment records two
reminder intents, due one day and two hours before it; the runtime delivers them to the reminder
destination the operator configures, or keeps them readable in its outbox when there is none.
`duplicateActiveKey: subject` is the rule the fixture's second case proved: one active booking per
subject.

Every entry carries `because`, a sentence for the next person who reads the policy. It is part of
the policy, so a changed reason changes the digest too.

## Tell another system when an appointment is confirmed

An observer [hook](../../reference/glossary/#scheduling-hook) sends a signed event after an
appointment is confirmed, rescheduled, or cancelled. The policy names the trigger and the fields it
sends; it holds no address and no secret. Add one at the end of `scheduling.yaml`:

```yaml title="scheduling/scheduling.yaml" test-append
hooks:
  appointment-confirmed:
    phase: after
    trigger: appointment.confirmed
    projection:
      - appointmentId
      - start
    handler:
      type: url
      destinationId: case-system
```

```sh test-exit="1"
schedulingctl check ./scheduling
```

```text test-excerpt
error[scheduling.runtime.unbound-hook-destination] ./scheduling/runtime.example.yaml:<position> /destinations/hooks
  destinations.hooks must bind every destination scheduling.yaml hooks.*.handler.destinationId names
```

`check` reads `runtime.example.yaml` as the runtime reads its own file, and refuses a hook with
nowhere to deliver. The address and signing key belong to the deployment. Bind them there:

```diff test-edit title="scheduling/runtime.example.yaml"
-destinations: {}
+destinations:
+  hooks:
+    case-system:
+      url: https://cases.example.test/scheduling-events
+      hmacSha256KeyRef: secret:file/case-system-hmac
```

```sh
schedulingctl check ./scheduling
```

```text test-excerpt
Authoring check passed.
```

The projection is closed per trigger. A confirmed or rescheduled appointment may send
`appointmentId`, `revision`, `offering`, `start`, `end`, `state`, and `policyRevision`; a
cancellation sends only `appointmentId`, `revision`, and `state`. `check` refuses any other field
with `scheduling.project.unsupported-hook-projection`, so a hook never sends the station, the
caller, or the cancellation reason. A cancellation intent sent to the reminder destination does
carry the reason. Delivery happens after the appointment commits,
at least once, signed with Standard Webhooks, and the receiver's answer never changes a booking.

## When callers arrive in a window

The `standalone-arrival-window` template sells arrival windows instead of exact times: a caller
books a place in a two-hour block, and the block's capacity is counted in units. Create it beside
your project and explain it:

```sh
schedulingctl init ./arrival --template standalone-arrival-window
schedulingctl explain ./arrival --format json
```

```json test-excerpt
{
  "arrival": {
    "horizonDays": 45,
    "leadTimeMinutes": 60,
    "window": "household-morning-window"
  },
  "id": "household-morning",
  "mode": "arrival-window"
}
```

The window itself is a record in `./arrival/records.yaml`, with its start, end, and `units`. A
`subquotas` entry caps how many of those units one channel, `public` or `assisted`, may take. A
subquota is a ceiling, not a reservation: the other channel may still use units the first leaves
free.
A channel the policy declares but gives no subquota draws from the window's total alone, and a request naming an undeclared channel is refused.
Nothing in the grammar reserves capacity for a channel.

A records window may also list `resources`.
Each names an exact-time requirement offering at the window's location with `partyCounts: optional` that sells the window's whole span, an optional resource, and physical units.
The window reserves them once for its whole span through a parent claim in the allocation ledger, so the reservation conflicts with exact-time bookings and other windows that need the same resource.
`records apply` refuses a window whose resource is unavailable, busy, or not freshly covered by a configured busy source.
`records apply` and a policy publication both refuse a requirement the deployed policy cannot reserve that way with `mismatched-reference`.
A window whose record is unchanged keeps what it holds across later records applies and policy publications, and a later absence of its resource shows in `resourceImpacts` instead.
Bookings in the window consume only the window's units.

## Send reminders and appointment events

The runtime has two outbound integration seams.
Both carry the same envelope, and neither lets a receiver change a booking.

A commitment mints the reminder intents its offering declares, each due a fixed number of minutes before the appointment.
A worker renders every due intent as one shared hook envelope in canonical JSON and POSTs it to the configured reminder destination with `content-type: application/json`.
An appointment observer receives the same envelope.

Every event carries these members:

| Field | Value |
| --- | --- |
| `id` | The outbox intent's identifier |
| `type` | `org.registrystack.scheduling.` plus the intent's purpose |
| `source` | `urn:registrystack:scheduling:` plus the deployment's `scheduling.id` from the policy |
| `time` | When the intent fell due, RFC 3339 in UTC at millisecond precision |
| `subject` | `recordReference` `/v1/appointments/<id>` and `recordRevision`, the appointment revision the intent was minted for |
| `dataschema` | `urn:registrystack:scheduling:reminder-data:` plus the intent's purpose |
| `data` | The payload the runtime committed |
| `causation` | A root chain: `root` is the event's own `id` and `hop` is `0` |

There are four purposes, so four types:

- `confirmation` and `change` carry the committed appointment's identifier, revision, offering, start, end, and the policy revision it was committed under.
- `cancellation` carries the identifier, revision, and reason.
- `reminder` carries the identifier, revision, offering, start, and how many minutes before the start it was minted for.

Delivery runs on the shared dispatch core.
Each attempt is bounded at five seconds, and a transport failure retries after thirty seconds, doubling to about thirty-two minutes.
A refusal the retry classes do not cover sets the intent aside for the operator, and the eighth failed attempt sets it aside.
A worker that stops mid-attempt leaves its lease to lapse, and the attempt counts as a failure.
If the destination accepts an event but the runtime cannot record that outcome, recovery applies the retry schedule and may send the event again.
Retries are bounded, so successful delivery is not guaranteed.
The destination deduplicates on the envelope `id`, which is the same on every attempt.

A cancellation or reschedule cancels the appointment's reminders no attempt has started on, in the same transaction.
Immediately before each send, the runtime reads under the attempt's lease whether the intent still describes the appointment.
A reminder whose appointment was cancelled or moved to a newer revision is set aside as superseded and never sent, and a lapsed lease starts no send.
With no reminder destination configured, each intent stays readable in the outbox and is set aside as local when it falls due, never pretended delivered.
Adopting the product does not require wiring a notification bus first.

Reminders use Standard Webhooks with the required `destinations.reminders.hmacSha256KeyRef`.
The runtime signs the canonical envelope bytes, the outbox id carried in `webhook-id`, and the
lease time in Unix seconds carried in `webhook-timestamp`. The receiver reads the signature from
`webhook-signature` and deduplicates by `webhook-id`, which stays fixed across retries.

`destinations.reminders.url` is the fallback for every purpose. The optional `purposes` block
configures separate destinations for `confirmation`, `change`, `cancellation`, or `reminder`.
Each must share the fallback URL's origin and use its own signing key. Configure the matching
trusted source and key at the receiver for each URL. During rotation, set
`previousHmacSha256KeyRef` to send a second signature after the current one. Use distinct keys
across all reminder and hook destinations.

### Appointment observers

An observer is a governed hook.
A policy may declare `phase: after` with a URL handler for exactly four triggers:

| Trigger | Allowed projected fields |
| --- | --- |
| `appointment.confirmed` | `appointmentId`, `revision`, `offering`, `start`, `end`, `state`, `policyRevision` |
| `appointment.rescheduled` | `appointmentId`, `revision`, `offering`, `start`, `end`, `state`, `policyRevision` |
| `appointment.cancelled` | `appointmentId`, `revision`, `state` |
| `appointment.attendance-observed` | `appointmentId`, `appointmentRevision`, `attendanceRevision`, `attendanceState`, `observedAt`, `recordedAt`, `policyRevision` |

The runtime refuses conditions, principals, Rhai or Wasm handlers, unknown triggers, and fields outside that table.
It captures one canonical event and its delivery row in the same transaction as the appointment change.
An after-commit worker then POSTs it to the deployment-bound destination.
Delivery is at least once, signed with Standard Webhooks, retried within fixed product ceilings, and audited without payload values.
Each attempt's audit entry is accepted before the request leaves, or the delivery stays pending and nothing is sent.
A receiver response is observation only: Registry Scheduling deterministically refuses every proposal and never turns it into a booking, reschedule, or cancellation.

The hook id becomes the event `type`.
The source is `urn:registrystack:scheduling:<scheduling-id>`, the subject record reference is `/v1/appointments/<appointment-id>`, and `data` contains only the requested fields.
`state` is the public value `confirmed` or `cancelled`.
Actor identity, task grants, resource and channel identifiers, duplicate keys, and cancellation reasons cannot be projected.
Operator replay is not exposed.

Retained payloads expire after `retention.hookPayloadRetentionDays`, and terminal delivery metadata ages out under `retention.receiptRetentionDays`.
[Registry Scheduling configuration reference](../../reference/scheduling-configuration/#retention) states the exact cleanup rules.

## Record attendance

Registry Scheduling can retain one current attendance observation for a logical appointment.
The observation is separate from the capacity lifecycle.
Recording `arrived`, `completed`, or `no-show` does not confirm, cancel, move, release, or consume a hold or appointment, and changing the booking later does not rewrite the attendance history.

An observation describes the appointment as a whole.
It does not identify an individual participant and is never expanded to one row per party member.
Optional party counts do not decide whether an authorised observation may be recorded.
A resource-only reservation can therefore carry an explicit appointment-level observation.
Registry Scheduling does not infer a person, a headcount, equipment return, condition, damage, or any source-system outcome from it.

### Write authority

Every write requires a current task grant whose exact service and location permission contains `attendance.record`.
Catalogue access, ordinary owner reads, source-manager appointment detail, operational appointment profiles, and other commitment actions do not imply this action.
The task grant is checked before the transaction opens, and its deadline is checked again at commit.
The source that approved the grant remains independent of the booking record and any institutional decision that follows from attendance.
[Registry Scheduling task grants](../../reference/scheduling-task-grants/) describes the grant.

The write is:

```http
PUT /v1/appointments/{appointment_id}/attendance
Authorization: Bearer TASK_TOKEN
Idempotency-Key: caller-chosen-key
Content-Type: application/json

{
  "observedAppointmentRevision": 3,
  "observedRevision": 0,
  "state": "arrived",
  "observedAt": "2026-10-23T08:15:00Z"
}
```

`observedAt` is when staff say the attendance fact became effective.
`recordedAt` is when Registry Scheduling made the recording decision after acquiring the appointment lock.
The observation row, history detail, receipt, and after-event use that same time, and it does not claim the exact database commit instant.
An effective time after the decision time is refused.
A late or backfilled observation is permitted, including for a past or cancelled appointment, because the observation is a corrigible fact rather than a capacity transition.

`observedAppointmentRevision` must equal the booking revision under the transaction lock.
That stops a staff client that read an earlier visit from attaching a no-show or arrival after another caller rescheduled it.
`observedRevision: 0` records the first fact for the current visit.
A correction supplies that visit's exact current attendance revision, and each accepted correction appends a new revision.
A stale concurrent correction is refused with `revision.mismatch`.
A no-show can therefore be corrected to arrived or completed without changing the appointment revision or state.
The caller supplies an idempotency key: an exact retry returns its original answer, and reusing the key for changed bytes is refused.

The visit binding is the revision of the latest `confirmed` or `rescheduled` appointment history event.
Cancellation advances the appointment revision but does not mint a new visit, so it does not hide an observation.
A reschedule does mint a new visit, and its exact detail initially has no current attendance.
Rescheduling away and later back still produces a new visit revision, which avoids reviving the older visit's observation even when its displayed times match.

The current response keeps the two revision streams explicit:

```json
{
  "appointmentId": "25b91ea4-75ca-48de-b9ef-4326fec81f28",
  "appointmentRevision": 3,
  "revision": 2,
  "state": "completed",
  "observedAt": "2026-10-23T08:45:00Z",
  "recordedAt": "2026-10-23T09:00:00Z"
}
```

The exact appointment detail may include this minimised current document for the current owner, the retained source manager, or the exact appointment-detail task grant.
Attendance corrections also appear in the authorised exact appointment history, using its existing pseudonymised actor envelope.
The current detail does not expose the attendance writer, and neither surface exposes the grant or task subjects.
Operational reads omit attendance unless their selected profile explicitly projects `attendance`, which returns only the permitted current observation and never the correction history.

### After event

The write appends its correction, idempotency receipt, history entry, and `appointment.attendance-observed` after-event in the same database transaction.
Hook delivery signs the event and delivers it after commit.
The event carries appointment identity, booking and attendance revisions, state, effective time, and recorded time through a closed projection.
It carries no writer, grant, party identity, participant list, resource condition, or institutional decision.

A Registry Coordinator workflow can follow the event only through its own configured, authorised trigger.
Event admission grants no authority for the workflow's later product calls, and a receiver response cannot change the appointment or attendance observation.

## Link bookings to records in other systems

An admission may carry `externalReferences`, each a typed opaque tuple of `product`, `recordType`, and `identifier`.
Registry Scheduling stores only that tuple.
It never calls the referenced product, resolves the identifier, or grants any authority through the link.
Identifiers name records only, so never put personal data in a reference.
Existing admissions may omit the field, and existing appointments return an empty set.

A hold returns the references it was created with.
Confirming that hold copies the same immutable references to the appointment, and a direct booking takes them from its admission.
A reschedule must omit `externalReferences`, and rescheduling and cancellation retain the original set.
Exact retries may reorder the set, but changing a reference under the same idempotency key is `idempotency.key-reused`.

`GET /v1/appointments` requires `externalReferenceProduct`, `externalReferenceRecordType`, and `externalReferenceIdentifier`, and accepts the ordinary `cursor` and `limit` parameters.
It returns only appointments owned by the authenticated caller that carry the exact tuple.
Its cursor is bound to both that caller and the tuple, and ownership is rechecked on every page.
The link lets another product find appointments created by its stable service principal without giving Registry Scheduling access to that product.

An orchestrator that books for another product's record needs `externalReferences` on every create it makes.
The reference is how it learns an outcome it never received.
The listing needs only the read scope, so a token for the same issuer and subject that carries no task grant finds the appointment after the grant that booked it has expired.
The token that carried the expired grant cannot do this, because an expired grant refuses the whole token, read scope included.
A hold is not listed; a hold that is never confirmed expires and returns its capacity.

Ordinary listing is per principal by design.
By default a hold or appointment is owned by the verified token issuer and subject that booked it, so another principal sees an empty page even when it serves the same product.
An orchestrator that must observe its own outcomes books and reads under one principal.
An appointment an orchestrator books for a party is therefore the orchestrator's, not the party's: an external party reference alone permits no read or change.
The official books for the party, and changes go through the process that booked it.

History and audit carry the keyed pseudonym of that pair, derived with the audit hash key (`audit.hashKeyRef`).
The key decides no ownership, and rotating it leaves every live claim with its owner.
After an appointment ends or is cancelled, or a hold expires, is released, or is consumed, the `retention.claimOwnerRetentionDays` window bounds the raw pair.
It defaults to seven days and accepts 1 through 365 days.
The sweep replaces the pair with an inert digest, and the former owner can no longer list, read, act on, or recover a receipt for that claim.
The claim, its history, and audit stay.
[Registry Scheduling API](../../reference/apis/registry-scheduling/) gives the full recovery rules for an unknown outcome.

## Record booking parties and management

An exact-time offering may opt into `partyCounts: optional`.
Room and equipment bookings can then omit `party` without inventing a recipient or attendee.
Omitted policy configuration keeps required counts, as do arrival windows.
Supplied counts are validated and retained independently from capacity units, and a booking that omits `party` under `partyCounts: optional` records no counts.

`partyReferences` can record up to sixteen typed `beneficiary` or `organization` references to source-owned records.
Use opaque identifiers without names or contact details; these references grant no authority.
They are retained through confirmation and rescheduling and follow identity retention.
Changing the booking's time does not change its recorded parties or manager.

Assisted booking can explicitly select `manager: schedulingManager`, using a fixed value from the source grant's signed identity rather than a caller-supplied person identifier.
The actor and manager are then separate.
Additional exact actions, fresh online grant status, and the retained source-manager binding authorise creation, management, and current-detail reads.
This path grants no list or history access.
[Registry Scheduling task grants](../../reference/scheduling-task-grants/#source-managed-assisted-bookings) describes the complete authority and recovery contract.

Operational staff can use a separate bounded appointment work list when runtime configuration grants an explicit role scope and a service, location, and resource profile.
Its projection contains only permitted scheduling data, not booking identity or contact data.
[Registry Scheduling configuration reference](../../reference/scheduling-configuration/#operational-appointment-read-profiles) describes the profiles.

## Observe an original receipt

`POST /v1/appointments/receipt` accepts the original request body and `Idempotency-Key` under current ordinary read authority.
It returns `200` with the retained original success receipt for the same verified issuer and subject.
It never repeats the business operation.
A same-principal read credential can observe work after task authority ends, and another service identity cannot impersonate that principal.
`409 receipt.unresolved` covers unavailable evidence such as a missing, expired, or changed receipt, or a claim whose owner has been erased.
It does not prove that no effect occurred.

The receipt route authenticates before checking the JSON media type and decoding its bounded body.
The router still rejects a declared body larger than one MiB before entering the handler.
Authenticated callers keep the usual malformed JSON, unsupported media type, request-shape, and body-size refusals.

## Book a finite weekly series

The finite series recipe lets a source application reserve a bounded weekly series through the public Python client.
The source owns the recurrence rule, series revisions, occurrence identities, and recovery journal.
Registry Scheduling remains the only capacity authority, and every create, reschedule, and cancellation goes through its ordinary public API and capacity transaction.

The recipe implements explicit partial results.
It can confirm some occurrences and refuse others, and its durable result always names every occurrence.
It never presents the series as wholly booked when a subset was committed.
The SQLite journal is a compact reference for an adopter that needs a complete single-node implementation or a concrete schema to port.
An institution's existing durable source application is the preferred owner when it already has transactions, locking, and recovery operations.

### Bounds and civil time

A definition contains:

- A UUID `seriesId`.
- An IANA `timezone` and an offset-free `localStart`.
- `intervalWeeks`, from 1 through 52.
- Exactly one end rule: `count`, or an inclusive local `throughDate`.
- `ambiguousTime`, set to `reject`, `earlier`, or `later`.
- Zero or more `exclusionDates`, each of which must name a generated local candidate date.

`count` counts weekly candidates before exclusions, and an excluded date does not extend the term.
Each candidate receives `UUIDv5(seriesId, "occurrence:<ordinal>")`, so its identity survives retries, exclusion, and later time changes.
A nonexistent wall time is always refused.
An ambiguous wall time is refused unless the definition selects the earlier or later actual instant.

The default maximum is 64 candidates over at most 366 days.
Aggregate capacity work is limited to 256 allocation lines.
The recipe calculates that value from the actual admission template as one primary allocation plus the length of `additionalAllocations`, multiplied by non-excluded occurrences, and the caller cannot supply a smaller count.
An adopter can choose lower `Limits`.

The full admission template is copied for each occurrence, and only `start` and the recipe's correlation references are added or replaced.
`durationMinutes`, `resource`, party data, and `additionalAllocations` bundle constraints pass through without being reconstructed or dropped.
Registry Scheduling still validates the complete admission under the active offering, task grant, and capacity ledger.
On reschedule, the recipe preserves the complete interval, resource, party counts, and bundle request, and omits `externalReferences`, `partyReferences`, and `manager`, as the public contract requires.
Registry Scheduling retains the appointment's immutable create-time references, party references, and manager.

### Durable partial results and recovery

`SeriesJournal` uses a source-owned SQLite database with WAL, foreign keys, full synchronous commits, and `BEGIN IMMEDIATE` revision changes.
Each command stores its exact credential-profile label, idempotency key, canonical request, request hash, method kind, attempts, and outcome before a summary is returned.
Bearer tokens are never stored.

Before network I/O, a prepared command is committed as `dispatched`.
A process-wide and operating-system file lock prevents another process from reconciling an in-flight HTTP call, and the SQLite lease generation fences stale completions after a crash.
A restart handles a dispatched create through `appointment_receipt` with the exact original key and body.
A missing or expired receipt remains `unresolved` and never licenses a new key.
Reschedule and cancel have no separate receipt observer, so recovery sends only the identical stored mutation under its original key and current authority.
An expired key or unusable response remains unresolved, and the recipe does not infer mutation success from a current appointment read.

The credential-profile label identifies the operator-configured credential source that may resume the journal.
It is not a verified token identity, because Registry Scheduling verifies the bearer token and exact actor on every call.
A different local profile cannot take over prepared work, and a mismatch while recovering an already dispatched command leaves that outcome unresolved with its original profile, key, and request intact.
Before dispatch or receipt recovery, the processor checks the stored request against its prepared hash, and a mismatch raises an explicit integrity error without making a client call.
That detects inconsistent local journal data; it does not authenticate a database against someone who can rewrite both the command and its hash.

SQLite gives complete durability and concurrency for one mounted journal, but it is not an active-active database.
An application with a durable source store can port the same invariants: compare-and-swap series revisions, immutable prepared commands, commit-before-dispatch, fenced leases, exact-key recovery, and per-occurrence outcomes.

### Correlation and disclosure

Each admission retains two opaque references:

```text
source-application / reservation-series / <series UUID>
source-application / reservation-occurrence / <occurrence UUID>
```

They contain no personal data and grant no authority.
Supported owner and operational appointment reads can select or return these references under their own authorisation.
An explicitly configured observer projection may include allowed references under the hook disclosure policy.
The default iCalendar export strips external references, so the recipe makes no default calendar-correlation claim.

Show `result["occurrences"]` rather than deriving a single success flag.

`prepare_edit` requires the current `expected_revision`.
It accepts scope `one`, `this-and-future`, or `all`, and the caller must provide one explicit change for every non-past occurrence the scope selects.
A reschedule names its new local wall time, and a cancellation may carry a reason.
The journal records the complete diff before preparing commands.
An occurrence with a prepared, dispatched, or unresolved command cannot accept another edit, so resolve that command first.
Every mutation uses the occurrence's current appointment identifier and observed Scheduling revision.
A stale series revision fails before command preparation, and a Scheduling revision or capacity conflict is retained as that occurrence's refusal.
A failed reschedule leaves the old confirmed appointment and its history intact, and past occurrences are never edited or erased.

## Export appointments as iCalendar

The calendar export example writes a bounded snapshot of current appointments as an iCalendar file.
It is an adapter over the Rust Scheduling client, not a calendar service.
It has no calendar write credential, feed URL, subscription token, webhook receiver, recurrence model, or background synchronisation authority.

Each appointment is one `VEVENT` under RFC 5545.
`UID` is stable from the runtime-minted appointment UUID, and `SEQUENCE` is the Scheduling revision.
`DTSTAMP` is the explicit export clock, and `DTSTART` and `DTEND` are the current displayed interval in UTC.
A cancelled appointment has `STATUS:CANCELLED`.
Output uses CRLF and folds UTF-8 content lines at 75 octets.
A revision outside RFC 5545's signed 32-bit `INTEGER` range, a non-positive interval, or interval precision the format cannot preserve is a hard error.

By default, an event contains only its stable identifier, revision, displayed interval, state, a generic `Appointment` summary, and opaque busy-time status.
It contains no person name, contact, organiser, attendee, location, offering, resource, channel, party count, party reference, external record reference, manager selection, cancellation reason, description, or URL.

Supply the bearer token through `REGISTRY_SCHEDULING_TOKEN` using the deployment's normal secret injection.
The command accepts no token argument and never puts a token in a URL or diagnostic.
A personal export rereads each explicitly named appointment through the owner-authorized detail route:

```sh test-skip="needs a running Registry Scheduling deployment and a bearer token"
cargo run --locked -p registry-scheduling-client --example calendar-export -- \
  personal \
  --base-url https://scheduling.example.gov/ \
  --appointment 03f4f87d-82c1-4e89-9554-620118a560d0 \
  > appointments.ics
```

A staff export uses the separately authorised operational query.
It requires the current configured projection profile and a service, location, and time interval:

```sh test-skip="needs a running Registry Scheduling deployment and a bearer token"
cargo run --locked -p registry-scheduling-client --example calendar-export -- \
  staff \
  --base-url https://scheduling.example.gov/ \
  --service registry-update \
  --location north-counter \
  --start 2026-11-01T00:00:00Z \
  --end 2026-12-01T00:00:00Z \
  --profile calendar-export \
  > appointments.ics
```

The staff path requests at most 50 rows per page, follows at most 10 pages, and accepts at most 500 source rows.
Personal export accepts at most 500 appointment identifiers, and repeated rows count toward the limit.
Repeated appointment rows converge to the highest revision, while inconsistent rows at the same revision are refused.
Page, row, interval, and empty-result bounds are errors, never silent truncation.
The adapter buffers the complete export before writing standard output, so a failed read or continuation cannot produce a partial calendar file.

Every invocation fetches current state and accepts no lifecycle signals.
A delayed or duplicate create, reschedule, or cancellation signal therefore cannot overwrite a newer appointment during export, and the three project to the same `UID` with a higher `SEQUENCE` and current state.
Registry Scheduling supplies authoritative instants, and the adapter writes them in UTC.
It does not infer a civil time zone, emit `VTIMEZONE`, or recalculate daylight-saving transitions, and an interval spanning a daylight-saving change keeps its actual elapsed duration.

The saved `.ics` file is a snapshot.
Browser, proxy, filesystem, and calendar-application caches can retain an older copy, and importing a later snapshot is an action owned by the person or institution operating that calendar.
Calendar applications vary in whether an import updates, duplicates, or ignores an existing event, so the adapter makes no claim of automatic importer convergence and infers no recurrence from similar appointments.

If you are deciding who may read and change what in a Base Registry Engine (BReg) registry, this
page shows you how, using the facility template. You will see how a token reaches one
[access profile](../../reference/glossary/#access-profile), how a profile limits fields and rows,
how related Records are disclosed, and which stricter read checks and grants a project can add.

## Start from the facility template

Create the facility project in an empty directory and check it:

```sh
bregctl init --template facility-registry facility
```

```sh
bregctl check facility
```

```text test-excerpt
Authoring check passed; registry revision sha256:<digest>.
```

The starter check passes without warnings. It keeps operator access on direct, jurisdiction-bound
routes. [Disclose related Records](#disclose-related-records) shows the warning you get when you
add its optional related read.

## How a token reaches a profile

The runtime verifies every bearer token against the one issuer its runtime configuration names,
and admits only the clients listed in `allowedClients`. A request without a verified token is
refused before any profile is considered. The same configuration names the token claims that
carry the caller's principal and [purpose](../../reference/glossary/#purpose); [What a token must
carry](../../operate/breg/#what-a-token-must-carry) covers that side.

Each request then uses exactly one profile. The caller names it with the `accessProfile` query
option; without one, the route's default applies: the only profile granting that route, or the
one marked `default: true`. Profiles are never merged, and naming a profile grants nothing. The
profile admits the request only when the token carries its `principalClaim`, every scope in
`requiredScopes`, and one of its `requiredPurposes`, and matches `actorKind` and
`requesterClients` when the profile sets them. Here is the profile that maintains operators:

```yaml title="registry.yaml" test-excerpt="facility/registry.yaml"
accessProfiles:
  operator-editor:
    principalClaim: registry_principal
    requiredScopes: ["registry:operator:write"]
    requiredPurposes: [facility-administration]
    permissions:
      records:
        - recordType: operator
          operations: [create, get, list, patch]
          readableFields: [operator-code, status, jurisdiction]
          writableFields: [operator-code, status, jurisdiction]
          rowBoundaries:
            - {field: jurisdiction, claim: jurisdiction, operator: equals}
```

When the token fails any of these checks, or the profile does not grant the operation, BReg
answers exactly as it does for a Record that does not exist, and records the refusal in the audit
journal. A caller cannot tell a forbidden Record from a missing one.

BReg has no built-in notion of jurisdiction, region, or office. In the template, `jurisdiction`
is an ordinary token claim, and the row boundary compares it with the Record's `jurisdiction`
field. The local test clients show two readers that differ only in that claim:

```yaml title="dev-clients.yaml" test-excerpt="facility/dev-clients.yaml"
  - id: reader
    accessProfiles: [facility-reader]
    scopes: [registry:facility:read]
    claims: {registry_principal: synthetic-reader, registry_purpose: facility-administration, jurisdiction: zone-a}
  - id: foreign-reader
    accessProfiles: [facility-reader]
    scopes: [registry:facility:read]
    claims: {registry_principal: synthetic-foreign-reader, registry_purpose: facility-administration, jurisdiction: zone-b}
```

`dev-clients.yaml` only mints local tokens that ask for these profiles; it adds no authority. In
production the claim comes from your issuer, so the issuer must be one you trust to assert it.

## Grant fields and rows

A record permission names a Record type and its operations. `readableFields` limits what a
response discloses and `writableFields` what a create or patch may set; `filterableFields`,
`sortableFields`, and `allowCount` each enable one query feature. Field lists use the field `id`,
not its `apiName`. A write never reveals a field the profile cannot read.

A [row boundary](../../reference/glossary/#row-boundary) compares a Record field with a token claim.
`equals` compares with one scalar claim value. `in` requires a claim whose value is a JSON array;
in `dev-clients.yaml`, write the array as a YAML sequence:

```yaml title="dev-clients.yaml"
claims:
  registry_principal: synthetic-transfer-clerk
  registry_purpose: permit-administration
  allowed_jurisdictions: [north-district, south-district]
```

A missing `in` claim or a scalar in its place fails closed. When journeys need another claim
variant for a refusal, bind that client to the exact step with
[`testBindings`](../../reference/bregctl-dev/#explicit-teaching-clients).

Every boundary on a permission must hold. Reads leave other rows out, and writes check both the
stored row and the row as it would be after the change. A permission that creates must keep its
boundary field writable, otherwise every create is refused, and `bregctl check` says so. A patch
under an `in` boundary can move a row between the caller's allowed values, which `bregctl check`
points out. Write
`rowBoundaries: unrestricted` only for deliberately registry-wide authority.

An agent is held to a narrower rule. A token from an agent, or one acting for another principal,
cannot create, patch, or delete Records directly, with or without a task grant; it reaches them
through [Actions and Proposals](../breg-actions/) instead.

For a task-grant token, row-boundary claims other than `sub` resolve only from the grant's signed
`identity` object, never from other token claims. To pin a grant to its subject, author a row
boundary on that subject key. Without one, the profile's ceiling applies to every row, as for
standing agents, and `bregctl check` reports `breg.access-profile.task-grant-rows-unbound`.

## Disclose related Records

A Record type can declare a read path to related Records. The facility reaches its operators
through the assignment that links them:

```yaml title="registry.yaml" test-excerpt="facility/registry.yaml"
    readPaths:
      - {id: operators, through: facility-assignment, to: operator, route: operators}
```

The starter leaves that path ungranted. Its `facility-reader` profile grants operators directly,
and the facility grant has no `readPaths` entry:

```yaml title="registry.yaml" test-excerpt="facility/registry.yaml"
        - recordType: facility
          operations: [get, list]
          readableFields: [facility-code, name, address-line, city, postal-code, status, jurisdiction]
          rowBoundaries:
            - {field: jurisdiction, claim: jurisdiction, operator: equals}
```

Direct operator reads apply the operator permission's jurisdiction boundary. A related read uses
the facility permission's authority instead. Add the optional path grant to see that distinction:

```diff lang="yaml" title="facility/registry.yaml" test-edit
           operations: [get, list]
           readableFields: [facility-code, name, address-line, city, postal-code, status, jurisdiction]
+          readPaths:
+            - {path: operators, readableFields: [operator-code, status, jurisdiction]}
           rowBoundaries:
             - {field: jurisdiction, claim: jurisdiction, operator: equals}
```

Check the edited project:

```sh
bregctl check facility
```

```text test-excerpt
warning[breg.access.profile-related-disclosure] <project-dir>/registry.yaml:237:15 /accessProfiles/facility-reader/permissions/records/1/readPaths/0
  profile `facility-reader` can read `operator` records linked to `facility` through `facility-assignment` on read path `operators`; it sees fields jurisdiction, operator-code, status under its own `facility` row boundaries, and access profiles declared for `operator` do not apply
  next: Remove fields that these readers should not see from this read path's readableFields, or remove the read path; use a direct permission on the related record type when its own row boundaries should apply.
0 errors, 1 warning in 3 files
```

Listing a facility's operators is authorised by `facility-reader`'s grant
on the facility, the root of the path. The row boundaries of `facility-reader`'s own grant on
`operator` do not apply to the operators that come back. A reader who may see a facility sees
every operator assigned to it, with the path's readable fields, whatever that operator's
jurisdiction.

The warning remains even though the direct operator grant names the same three fields, because its
row boundary does not govern the related read. Ask the same two questions of your own paths: can a
related Record sit outside the reader's rows, and do the path's fields disclose more than a direct
grant would? If either answer exposes more than you intend, narrow the path's `readableFields`, or
remove the path grant and use the direct target grant. The shipped starter takes that latter,
narrower route. When a target, or the Record type a path passes through, must never be disclosed
without its own row check, give that Record type `accessRequirements` with row boundaries: the
compiler then refuses any read path grant that reaches it.

### Require access conditions on a Record type

`accessRequirements` on a Record type are mandatory compiler checks, not grants.
The key gives no profile any access.
`bregctl check` refuses every access profile that reaches the Record type, including a profile a module contributes, when the profile:

- lacks a required scope (`breg.access.requirements-scope-missing`);
- widens the allowed purposes, which includes an empty purpose list (`breg.access.requirements-purpose-widened`);
- omits a required row boundary, with the exact field, claim, and operator binding (`breg.access.requirements-row-boundary-missing`).

## Require search criteria for lists

A grant that lets a profile `list` a Record type lets it browse every row the boundaries admit.
When the caller should find a Record, not enumerate them, add `requiredFilters` to the grant. Each
entry is an alternative set of fields, and a list must pin every field of at least one set with an
`eq` filter:

```diff lang="yaml" title="facility/registry.yaml" test-edit
           readPaths:
             - {path: operators, readableFields: [operator-code, status, jurisdiction]}
+          filterableFields: [facility-code, city, status]
+          requiredFilters:
+            - fields: [facility-code]
+            - fields: [city, status]
           rowBoundaries:
             - {field: jurisdiction, claim: jurisdiction, operator: equals}
```

With this grant, `GET /v1/records/facilities?$filter=facilityCode eq 'F-001'` runs, and so does
a filter that pins both `city` and `status`. A list with no filter, or with only `city`, is refused
with `400 query.filter_required` before any query runs. The response carries `requiredFilters`, the
acceptable sets as API field names, and its `detail` names them.

An alternative counts as met only when the filter is a top-level `and` of predicates, brackets
included, and every field of the alternative has an `eq` predicate with a non-null value. A predicate
under `or` or `not` does not count, and neither do `ne`, comparisons, `in`, `startswith`, or a test for
null. Other predicates may sit beside the required ones. `$count` is held to the same rule. A
`$skiptoken` cursor carries the first page's filter under its signature, so a continuation page
cannot drop or change it.

`bregctl check` refuses a `requiredFilters` that:

- names a field missing from the same grant's `filterableFields`
  (`breg.access-profile.required-filters-field-not-filterable`);
- names a field that cannot take an `eq` filter
  (`breg.access-profile.required-filters-field-not-equality-filterable`);
- sits on a grant without `list`
  (`breg.access-profile.required-filters-list-required`);
- is empty, has an empty alternative, repeats an alternative, or has more than eight alternatives
  (`breg.access-profile.required-filters-empty`, `breg.access-profile.required-filters-duplicate`,
  `breg.access-profile.required-filters-too-many`).

A field repeated within one alternative is refused when the file is read, with
`config.duplicate-item` at the repeat.

Check the edited project:

```sh
bregctl check facility
```

```text test-excerpt
0 errors, 4 warnings in 3 files
```

`requiredFilters` governs `list` only. That includes the paged collection reads that share its
grant, such as a temporal `current` or `as-of` list and a GIS collection with `bbox`. It does not
change lookups, a get, a read path, a bulk export, or a `snapshot` read. A profile that holds those
grants can still enumerate through them, so grant them only where the caller may enumerate. The same
metadata that lists `filterableFields` for a surface also lists its `requiredFilters`, so a client
can ask for the right criteria before it searches. The ODRL export omits the grant's `list`
permission, with the reason `required-filters`, and still exports its `get`.

## Require a current membership

A row boundary works when the Record carries the claim value it is compared with. Sometimes the
right to read follows an affiliation that changes over time: a facility belongs to an
organisation, and whoever is currently a member of that organisation may read it. Copying members
into tokens would leave access in place until each token expired.

`membershipBoundaries` on a record permission puts that rule into the registry. Each entry names
the Record's reference `field`, a `membershipRecordType`, and that type's `membershipKeyField`,
`principalField`, and `activeField`. A row is readable only while a membership Record exists with
the same key, the caller's verified principal, and `active: true`. Memberships are ordinary
Records that a separate steward profile creates and deactivates. A request that starts after a
deactivation commits no longer sees the Records; a read already running may finish. Historical
reads compare against current memberships too, so a past membership cannot restore access.

A facility stores `organization`, a reference to an `organization` Record type.
A separate `membership` Record type stores an `organization` reference, a string `principal`, and a Boolean `active`.
Its optional descriptive fields can remain private.
Add the boundary to the facility's read grant:

```yaml
accessProfiles:
  member:
    principalClaim: principal
    requiredScopes:
      - records:read
      - membership:use
    permissions:
      records:
        - recordType: facility
          rowBoundaries: unrestricted
          operations:
            - get
            - list
            - lookup
            - snapshot
            - revisions
          readableFields:
            - label
          filterableFields:
            - label
          sortableFields:
            - label
          allowCount: true
          revisionAccess: true
          lookups:
            - selector: label
              valueOrigin: request
          membershipBoundaries:
            - field: organization
              membershipRecordType: membership
              membershipKeyField: organization
              principalField: principal
              activeField: active
```

The `label` lookup selector must already be declared on the facility Record type.
The two organisation fields must be stored references to the same Record type.
`principalField` must be a stored string or text field and `activeField` a stored Boolean.
Only active-lifecycle membership rows with `active: true` and an exact match to the profile's verified principal grant access.
A missing membership, null value, inactive membership, or other principal does not.
Configure a stable identity claim from a trusted issuer, and do not accept caller-submitted principal values as authority.

Every listed membership boundary and ordinary `rowBoundaries` predicate must hold.
Declare `rowBoundaries` explicitly even when membership is the only row restriction; `rowBoundaries: unrestricted` adds no direct claim predicate and leaves the membership checks in force.
Up to eight membership boundaries are supported.
The declared fields are authorisation inputs, not an additional readable-field grant.
The root profile must satisfy the membership Record type's mandatory scopes and purposes.
The current boundary does not carry additional direct row requirements from that source, so the compiler rejects a membership Record type with mandatory `rowBoundaries`.

The organisation membership access example project in the repository (at your release tag) holds the complete authored model, including separate steward grants and an index on principal, organisation, and active status.
Run `bregctl check` against that directory to compile it.
The same boundary compiles for facility and document registries without new server code.

Membership boundaries apply to reads only: get, lookup, list, count, snapshot, and revisions.
A record grant with a membership boundary cannot also grant writes.
Action and Proposal grants do not accept `membershipBoundaries` and do not inherit membership checks from read grants.
Give record mutations and membership administration to a separate, explicitly authorised steward profile.
Cursor replay on a read re-evaluates live membership, and a read grant never authorises a mutation or its replay.
Spatial bbox permissions use a separate authority role and cannot currently be combined with membership boundaries; ordinary reads of facilities remain available under the membership profile.

Membership profiles can protect the root of a relationship read path.
A related Record type's membership rules cannot silently be bypassed by targeting it through a separate root grant, so the compiler rejects such target permissions.
Membership sources must remain leaf Record types without their own membership boundaries or incoming relationship read paths, which prevents recursive row-security policies.

### Revocation and history

Authorisation queries read current membership Records in PostgreSQL.
A new request issued after a membership deactivation commits is denied or returns an empty authorised collection, including counts, lookups, and cursor continuations.
An already running read can finish from the statement snapshot that preceded revocation.
There is no token membership cache, external authorisation service, or registry-wide authorisation lock.

Snapshots and revisions compare the retained Record's organisation with current memberships.
The historical membership state cannot restore access, and deactivation removes access to those historical Records as well.
Moving a facility to another organisation does not by itself remove access to its older revisions from members of the previous organisation.
This preserves the ordinary historical row-boundary contract, and current-owner-only history is a different policy that this feature does not imply.
Erased history remains unavailable.

### How PostgreSQL enforces it

PostgreSQL enforces the predicate through generated `SECURITY INVOKER` functions and forced row-level security.
Each generated PL/pgSQL function saves the prior authorisation context, enables only its matching membership probe, and restores the context before returning.
Its exception block rolls back the local context on errors.
It does not grant direct membership endpoints or derived views access to private membership Records.
The logical source views keep `security_invoker`, so the caller's row-level security policies decide every read through them; they are not barrier views.
No additional database role or RLS bypass is required.
PostgreSQL 17 remains the minimum for this surface, and other enabled features can require a newer supported version.

Use `bregctl explain access` to inspect the expanded membership boundary alongside its scopes, purposes, and ordinary row boundaries.
Compiler diagnostics identify the unsupported field or grant and describe the supported alternative.

## Require the subject's consent

A membership boundary asks whom the caller works for. A consent check asks what the Record's
subject decided: that this recipient may read their Record, for this purpose, under this profile.

`requireConsent` on a record permission lists checks, each naming a consent `record` type and
`on`, the field that identifies the subject (`id` for the row itself). The project declares
`recipients`, the organisations that read and the clients each one reads through. BReg derives the
caller's recipient from the verified client, never from a token claim, so a gated profile must
list its `requesterClients`. A row is disclosed only while a current consent covers it; a
withdrawal takes effect for every request that starts after it commits, with no token change or
restart. Gated permissions
are read-only, cannot export, and need their own clients, because any profile without
`requireConsent` reads without the check.

The profile id is the scope the subject agreed to. Removing `requireConsent` or widening a gated
profile in place would read under a scope the subject never saw, so publish a new profile and list
the old id under `retiredConsentScopes`.

[Gate reads on consent](../breg-consent/) covers the consent Record type, recipients, and how an
Action issues a consent.

## Withhold a record while a condition holds

Some records need more protection while a flag is set: a person under witness protection, a case
that is sealed, a field that is hidden once a status changes. `disclosureConditions` on a Record type
withholds a record, its history or named fields from every access profile the condition does not
exempt, for as long as the record's current values match. Each condition is keyed by its id:

```yaml
recordTypes:
  case:
    disclosureConditions:
      sealed-case:
        when:
          - {type: field-equals, field: sealed, value: true}
        withhold: record
        exemptProfiles: [registrar]
      hide-notes:
        when:
          - {type: field-in, field: status, values: [closed, archived]}
        withhold: fields
        fields: [notes]
        exemptProfiles: [registrar, auditor]
```

`when` is one to four predicates, all of which must match. A predicate is `field-equals`,
`field-in` (one to 32 values), `field-is-null` or `field-is-not-null`, on a stored, unencrypted
field of type boolean, string, text, vocabulary code, `int64`, date or `uuid`. A literal is never
null. An unset member counts as null. A Record type holds at most eight conditions.

`withhold` picks what is hidden:

| `withhold` | A profile the condition binds sees |
| --- | --- |
| `record` | No record. A get answers `404 resource.not_found`, identical to an absent record. A list, a count, a snapshot and a lookup leave it out. Its revisions answer as not found. |
| `history` | The current record, but none of its revisions or snapshots, which answer as not found. |
| `fields` | The record, with each field named under `fields` returned as `null`, on reads and on revisions. The member is present and null whether or not it holds a value, so the response does not show whether it was set. |

A write response never carries a field a `fields` condition names for the profile, whatever the
record's state. A JSON Patch `test` on such a field is refused like a test on a field that does not
exist, so it cannot be used to guess the value.

`exemptProfiles` names the profiles the condition never applies to. List at least one, and only
profiles the project declares. A profile with no record grant on the Record type can be listed when
an Action or Proposal permission of that profile targets the type, so it can write a marked record
through the Action or the Proposal apply. The record timer, which runs under the reserved
`system-record-timer` profile, is never withheld from, so a timer keeps firing on a record that is
hidden from people. A timer may not read a field that a `fields` condition withholds from some
profile, because what the timer writes would reveal it. For the same reason, a timer on a Record
type with a `record` condition may not create a record that a profile the condition binds can read.

### How a condition is evaluated

The condition reads the record's current state at the moment of each request. Marking a record
withholds it from the next read, and clearing the mark discloses it again, with no migration. On
history surfaces the state is the latest retained revision, which equals the current row after every
writer. A snapshot reference taken before a record was marked does not read it. PostgreSQL enforces a
`record` condition as a restrictive row policy, so a query that forgets to apply it cannot read the
row.

A Create, Patch, immediate Action or Proposal applied by hand whose resulting record a `record`
condition would hide from the writing profile is refused with `403 write.outside-boundary`. Give the
profile that sets the mark an exemption. A Patch of a record the profile can no longer see answers
`412 precondition.failed`, as for an absent record.

### Who can lift a mark

Only an exempt profile lifts a `fields` or `history` condition, or writes a field a `fields`
condition withholds. When a condition that binds the writing profile matches a record, a write to
that record is refused with `403 write.outside-boundary` in three cases:

- The write names a field the condition lists under `fields`. Writing back the `null` a read showed
  counts, so the answer is the same whether or not the field holds a value.
- The write changes a field that a constraint checks together with a field the condition lists
  under `fields`. That is another field of a uniqueness constraint, a field a partial uniqueness
  constraint's `when` reads, the other side of a comparison, a scope field of a temporal
  non-overlap, or a valid-time field. The conflict or failed check would otherwise answer whether
  the withheld value matches a guess. Writing back the stored value is allowed.
- The record would no longer match the condition afterwards, which would lift the mark.

A bound profile can still set a mark and write any field a condition does not name. In the example
above, a caseworker bound by `hide-notes` can close a case but cannot reopen it. The rule covers a
Patch, each batch or import item, an immediate Action and a Proposal. It checks the profile that
applies the change. An import item it refuses answers the generic `412 precondition.failed` instead
of the 403, as import does for a row boundary. A Create has no earlier state, so this rule never
refuses it.

A bound profile also cannot tombstone a record that a condition binding it matches. A `fields` or
`history` condition refuses the tombstone with `403 write.outside-boundary`. A `record` condition
already hides the row, so the tombstone answers `412 precondition.failed`, as for an absent record.

A Proposal review shows a withheld field as `null`, and applying a change set to a record that
became withheld after submission is refused. A Proposal applied by hand is checked as a write by the
profile that applies it. A Proposal applied automatically is checked against the profile that
submitted the version being applied, which each submit records. An exempt submitter's automatic
Proposal can make a change this rule refuses to a bound profile. A bound submitter's is refused
wherever a write by that profile would be, and so is one whose submitting profile was removed or lost
its exemption after submission. A version that records no submitting profile is checked against the
reserved `system-proposal-apply` profile, which no condition exempts. A refused automatic Proposal
leaves the record unchanged and ends `blocked` at that attempt, with the recovery `correct-input`.
The reason is `attempts-exhausted` when that was its last attempt, and `application-refused`
otherwise.

An automatic application still reads and writes its targets under `system-proposal-apply`. A target
that a `record` condition hides from that profile is absent to it, so an automatic Proposal cannot
apply to such a record, whoever submitted it. Nor can an automatic Proposal set a `record` mark,
even when its submitter is exempt: the condition's row policy refuses the marked record under
`system-proposal-apply`, so the Proposal ends `blocked` and the record is unchanged. For either
case, use an immediate Action or apply the Proposal by hand, under an exempt profile.

### What `bregctl check` refuses

A condition that leaves a withheld value reachable through another surface fails the check, so the
guarantee does not rest on remembering every route. For a profile a condition binds, the check
refuses:

- a `fields` condition that names a required field or `id`, or a condition with `fields` and a mode
  other than `fields` (`breg.disclosure.fields-invalid`). A field named twice is refused with
  `config.duplicate-item` when the file is read.
- a withheld field in the profile's `filterableFields`, `sortableFields`, lookups, data export, hook
  projections or statistical dataset (`breg.disclosure.withheld-field-exposed`);
- a `when` field of an unsupported type, or a literal that does not fit it
  (`breg.disclosure.when-field-invalid`, `breg.disclosure.when-value-invalid`);
- more than eight conditions, or an empty or unknown `exemptProfiles` (`breg.disclosure.too-many`,
  `breg.disclosure.exempt-profiles-invalid`);
- spatial queries over a withheld geometry (`breg.disclosure.spatial-query-withheld-geometry`);
- a derived field, row boundary, membership boundary, consent requirement, read path, Evidence fact
  or external view link that reads a withheld field
  (`breg.disclosure.derived-reads-withheld-field`, `breg.disclosure.row-boundary-withheld-field`,
  `breg.disclosure.membership-boundary-withheld-field`,
  `breg.disclosure.consent-boundary-withheld-field`, `breg.disclosure.read-path-withheld-field`,
  `breg.disclosure.evidence-fact-withheld-field`,
  `breg.disclosure.external-view-withheld-field`);
- a Record timer whose `at`, `notAfter`, `rearmOn`, `when` or `fromField` input reads a withheld
  field (`breg.disclosure.timer-reads-withheld-field`). The timer runs without the condition, so
  its Action, or the moment it fires, would reveal the value;
- a Record timer on a Record type with a `record` condition whose Action creates a record the profile
  reads (`breg.disclosure.timer-creates-readable-record`). The created record would carry the id of
  a hidden record, and any value the timer maps from it;
- a statistical dataset that would count or read a withheld record or field
  (`breg.disclosure.statistics-withheld-field`, `breg.disclosure.statistics-live-bound`,
  `breg.disclosure.statistics-publisher-bound`). See
  [Disclosure conditions](../breg-statistics/#disclosure-conditions) for datasets;
- the reserved profile id `system-record-timer`.

These refusals hold whatever the profiles:

- A change hook (`created`, `patched` or `tombstoned`) on a Record type with a `record` or `history`
  condition (`breg.disclosure.withheld-field-exposed`). A change hook must project at least one
  field and its destinations hold no access profile, so such a Record type declares no change hook
  at all.
- A `trigger: read` hook on a Record type without `accessLog`
  (`breg.disclosure.read-hook-access-log-required`). The read alert is written with the subject
  access log entry, so it would never fire.

`bregctl explain access` lists each condition in full, `when` literals included, for the author. The
runtime metadata a caller reads flags `mayBeWithheld` on a field and names the bound conditions by
`id` and mode, and never carries the literals. The ODRL export omits a grant a condition binds, with
the reason `disclosure-condition`.

### What a condition does not hide

Four limits are inherent to what a write has to check, and a fifth follows from how history works.
Design around them.

- A Proposal's inputs stay visible to its reviewers. A reviewer sees what the author typed, even for
  a field the reviewer's own profile would not read on the record.
- A Create or Patch can confirm a hidden value. A Create, or a Patch of another record, that repeats
  a unique value of a record a `record` condition withholds answers `409 mutation.conflict`, which
  shows that the hidden record exists. For a field a `fields` condition withholds, a Create or a
  Patch of another record that repeats its value answers the same `409` when the field belongs to a
  uniqueness constraint, has a unique encrypted lookup, or is in a temporal non-overlap. That
  confirms the value exists on a hidden record. A field a partial uniqueness constraint's `when`
  reads answers in the same way: a repeated unique value conflicts only when the hidden record's
  field meets the predicate. `bregctl check` warns about the `fields` case with
  `breg.disclosure.withheld-field-probe`, ranked as widening access,
  so the check fails under `--deny-warnings` until you
  [accept the finding](../../reference/configuration-files/#accept-an-intentional-project-warning).
  Keep the field out of the constraint, or accept the finding if the profiles that can create or
  patch these records are trusted.
  A Patch of the marked record itself cannot probe its withheld value this way, because the rule in
  [Who can lift a mark](#who-can-lift-a-mark) refuses it.
- A refused write can reveal that a condition matches. The `403 write.outside-boundary` a bound
  profile meets tells it that a condition holds for this record. A `null` it read is then known to
  be withheld rather than unset.
- A write that sets a reference can reveal that a withheld record exists, because the database
  checks that the target is there.
- `withhold: history` on a record the caller can read answers its revisions as not found. A client
  that expects the current revision to appear in the history sees it missing.

## Require a reason for each read

Add `requireAccessReason: true` to an access profile when each use of it must state why. Every
request under the profile must then carry a `Registry-Access-Reason` header, the reason as UTF-8 text
encoded as unpadded base64url. The text is at most 512 bytes, not blank, and has no control
character. A request without a valid header is refused with `400 request.access_reason_required`
before any record is read. The reason is stored on the subject access log entry and carried by a
read alert, so a reviewer can ask why. See
[Record why a record was read or written](../../operate/breg-access-log/#record-why-a-record-was-read-or-written).

The reason is checked on record reads and direct writes only. A direct Create, Patch, Batch or
Tombstone under the profile must carry the header. On a Record type with `accessLog`, each record it
changes gets a subject access log entry with `accessKind: write` and the reason, written in the same
transaction. On a Record type without `accessLog` the header is still required, but nothing stores
the reason. `bregctl check` refuses the key on a profile that grants import, invoke or start
operations, bulk data export, or an action, proposal, dataset, external view or projection-refresh
permission, because those paths do not check it
(`breg.access-profile.access-reason-operation-unsupported`). Bulk export is refused even though it
would only fail at run time: its list calls send no reason, so every page would be refused. The ODRL
export omits every grant of such a profile, with the reason `access-reason`, because ODRL has no
term for the header.

## What a reader meets when a check fails

Membership and consent refusals look like every other access refusal. A get on a Record the
caller may not see answers `404`, exactly as for a Record that does not exist; a list or count
leaves the Record out. The caller learns nothing about why, or whether the Record exists. The
[problem documents](../../reference/breg-api/#problem-documents) in the API reference list the
codes, and the [configuration reference](../../reference/breg-configuration/) carries every key
named on this page.

## Grant statistical datasets

A project that publishes counts declares statistical datasets, and a profile reaches them through
`permissions.datasets`. Each entry names a `dataset` and its operations: `read-live` for current
counts, `publish` to publish or withdraw a release, `read-releases` to read published releases, `read-exact`
to read exact values for ended periods as a named consumer.
A standing agent profile, one with `actorKind: agent` and no `taskGrant`, cannot hold `publish` or `read-exact`:
a release takes effect at once, with no draft for a person to confirm, so the compiler refuses it.
[Publish a statistical series](../breg-statistics/) covers the datasets themselves.

If you are authoring Base Registry Engine (BReg) permissions, grant each caller
only the record, Action, and Proposal operations it needs. Verify fields and row
boundaries before testing with real tokens.

## One profile per request

A request selects one `accessProfile`. BReg verifies the token and checks scopes,
purpose, principal, actor/client restrictions, and the selected operation. Naming
a profile creates no authority. A missing or invalid token is refused before
selection; inaccessible records and work remain concealed.

Profiles decide authority before record I/O. Caller filters reduce an authorized
collection but never establish access. A local `dev-clients.yaml` registration
requests governed profiles and adds no grant.

## Declare a profile

The default directory supplies this complete record grant:

```yaml
accessProfiles:
  - id: directory-editor
    default: true
    principalClaim: registry_principal
    requiredScopes: [registry:directory:write]
    requiredPurposes: [directory-administration]
    permissions:
      records:
        - recordType: contact
          operations: [create, get, list, patch]
          readableFields: [name, email, jurisdiction]
          writableFields: [name, email, jurisdiction]
          rowBoundaries:
            - field: jurisdiction
              claim: jurisdiction
              operator: equals
```

Each required claim must come from your verified issuer. Configure the runtime's
principal and purpose claim names to match the project. Review `actorKind` and
`requesterClients` when restricting a profile to an agent, service, or exact client.
A task grant can only narrow its compiled ceiling; it cannot create a grant.

## Grant operations, fields, and rows

`permissions.records` names a Record type. `readableFields` limits disclosure,
`writableFields` limits Create and Patch, and `filterableFields`, `sortableFields`,
and `allowCount` independently enable query features. Field lists use logical IDs,
not public `apiName` values. A write does not reveal an unreadable field.

Declare row boundaries explicitly. `equals` compares a field with one claim value;
`in` compares it with an admitted list claim. All boundaries must hold. Reads
conceal other rows; writes check existing and proposed state. Create must be able
to supply the boundary field, so keep it writable and send the permitted value.
A missing writable create boundary is reported. Patch with an `in` boundary can
move a row between allowed values and produces a writable-boundary advisory.
An `equals` boundary remains pinned to its single claim value.

Use `rowBoundaries: unrestricted` only for deliberately registry-wide authority.
Explicit unrestricted authority is not a wildcard in a list. A caller's query
cannot narrow an overly broad grant into a safe grant.

`permissions.actions` names an Action and grants Invoke or Start, with explicit
target boundaries and permitted results. `permissions.proposals` independently
grants lifecycle operations, ownership, input/attachment disclosure, and target
boundaries. List is separate from Get. A Record type's Proposal-required mutation
policy still prevents direct writes even when a caller otherwise has authority.

## Access requirements

Record type `accessRequirements` are compiler constraints on the declared grants,
not additional permissions. Use them when an authored model requires a specific
minimum or restriction and inspect `check` diagnostics when profiles change.

## Require consent for a read

Consent-gated reads, current membership boundaries, relationship reads, history,
and Evidence lookups keep their own explicit permissions. A reference never
implies permission to see its target. Add only the mechanism your actual reader
journey requires, and check both permitted and concealed outcomes.

## Read the compiled access

```sh
bregctl check ./my-registry
bregctl --format json explain access ./my-registry
```

Inspect each operation, its fields, and row predicates. Diagnostics identify the
source member. `--deny-warnings` can make advisory findings blocking after you
have deliberately resolved them; the default canonical directory does not need
an unrestricted-profile exception.

## Preview synthetic claims

```sh
bregctl --format json explain access ./my-registry --scenario /path/to/scenario.json
```

Use `bregctl explain --help` for the bounded scenario contract. This preview
performs no token verification or record access. Run the declared database journeys
with real credentials to prove runtime authority and concealment.

## Start from a working example

```sh
bregctl init ./directory
bregctl init ./facility --template facility-registry
```

Use fresh paths. The facility project separates directory maintenance, operator
setup, immediate registration, correction authoring, manual application, human
review context, and service review status. Start with its narrow grants rather
than copying one broad operator role into every client.

## Troubleshooting

A concealed refusal requires checking verified claims, selected profile, operation,
field, and row boundaries together. A compile diagnostic naming a missing grant
requires an explicit model decision. Adding a scope to a local client alone
cannot repair the governed permission. For a stale condition, reread current
work and review the input before preparing a new command.

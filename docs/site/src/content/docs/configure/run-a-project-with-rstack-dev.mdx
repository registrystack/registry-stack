If you are writing a registry project and want to see Base Registry Engine (BReg) and Registry
Casework serve it together, `rstack dev` starts both from your project directory, runs short
scenarios against them, and removes everything when you stop. It does not start PostgreSQL and does
not use Docker: you supply a development PostgreSQL server over TLS. This page takes you from a
checkout to a running pair, using the licensing example that ships with Registry Stack.

## Before you start

You need:

- PostgreSQL 17 or newer command-line tools (`initdb`, `pg_ctl`, `psql`) and `openssl` on your
  `PATH`, to run the local server below. A server you already have works too if it serves TLS and
  has an administrator role with `LOGIN CREATEROLE CREATEDB`.
- `curl` and `jq`.
- A checkout of Registry Stack at the release you installed, for the example project.

## Install the components

Install `rstack` from one verified release, then add the two components the example uses. The
steps are in [Decide your first Base Registry Engine registry](../../tutorials/first-breg/#install-registry-stack);
install `casework` the same way.

```sh test-skip="uses a downloaded, independently verified release installer"
rstack install breg casework
```

Check the selected installation before you continue:

```sh test-skip="needs the installed release"
rstack components list
```

Success is a `breg` line and a `casework` line that each say `installed`. `available` means that the
selected release provides the component but it is not installed, so run the `rstack install`
command again. `unavailable` means that the selected release does not provide the component for
your platform. If your shell cannot find `rstack`, or the command says `No installation selected`,
repeat the verified `rstack` installation steps linked above.

## Start a local TLS PostgreSQL server

`rstack dev` always verifies the server certificate and host name, so the server needs a
certificate your machine trusts. This recipe makes a private certificate authority, starts the
server on `127.0.0.1`, and creates a least-privilege administrator. Keep the working directory
outside any repository. If port 5432 is taken, change `PORT`.

```sh test-skip="needs a PostgreSQL installation and starts a server"
export DEV="$HOME/rstack-dev-postgres"
PORT=5432
mkdir -p -m 700 "$DEV"
umask 077
openssl rand -hex 16 > "$DEV/postgres.pass"
openssl rand -hex 16 > "$DEV/devadmin.pass"
initdb -D "$DEV/data" -U postgres --auth=scram-sha-256 --pwfile="$DEV/postgres.pass" -E UTF8

openssl req -new -x509 -newkey rsa:2048 -nodes -days 30 -subj /CN=rstack-dev-ca \
  -addext basicConstraints=critical,CA:TRUE -keyout "$DEV/ca.key" -out "$DEV/ca.pem"
openssl req -new -newkey rsa:2048 -nodes -subj /CN=localhost \
  -keyout "$DEV/data/server.key" -out "$DEV/server.csr"
printf 'subjectAltName=DNS:localhost,IP:127.0.0.1\nextendedKeyUsage=serverAuth\n' \
  > "$DEV/server.ext"
openssl x509 -req -in "$DEV/server.csr" -CA "$DEV/ca.pem" -CAkey "$DEV/ca.key" \
  -CAcreateserial -days 30 -extfile "$DEV/server.ext" -out "$DEV/data/server.crt"

printf "listen_addresses = '127.0.0.1'\nport = %s\nssl = on\n" "$PORT" \
  >> "$DEV/data/postgresql.conf"
pg_ctl -D "$DEV/data" -l "$DEV/postgres.log" -w start
```

The passwords are random and stay in owner-only files, so nothing secret reaches your shell
history or a process list. Create the administrator with the password from its file:

```sh test-skip="needs the running development server"
CONNECTION="host=127.0.0.1 port=$PORT user=postgres dbname=postgres sslmode=verify-full sslrootcert=$DEV/ca.pem"
PGPASSWORD="$(cat "$DEV/postgres.pass")" psql "$CONNECTION" <<'SQL'
\set pw `cat "$DEV/devadmin.pass"`
CREATE ROLE devadmin LOGIN CREATEROLE CREATEDB PASSWORD :'pw';
SQL
```

Success is `CREATE ROLE`. The server must be running before you start a project. Point `rstack dev`
at it:

```sh test-skip="needs the running development server"
export RSTACK_DEV_DATABASE_CA="$DEV/ca.pem"
export RSTACK_DEV_DATABASE_URL="postgresql://devadmin:$(cat "$DEV/devadmin.pass")@127.0.0.1:$PORT/postgres?sslmode=verify-full"
```

Set the URL through an environment variable, not `--database-url`, because a flag is visible to
other local users in the process list. For a spatial project, install PostGIS for this server and
create the administrator as a superuser instead.

## Adapt the development plan

Copy the licensing example from your checkout, then work in the copy:

```sh test-skip="needs a Registry Stack checkout"
cp -R path/to/registry-stack/products/platform/examples/licensing ./licensing
```

The directory holds a BReg project (`registry/`), a Casework project (`casework/`) and the plan
`dev.yaml`. Open `dev.yaml`: `rstack dev` reads it and any authored scenario file it names. Product
files stay byte-for-byte unchanged, and generated settings, keys and packages live in the run's
owner-only scratch directory.

To adapt the plan to your own project, change these parts and leave the structure alone:

- `issuer` names the identity issuer the local test tokens claim. Use a name that is yours.
- `products` lists each product's project directory and token audience, in any order. The run
  starts BReg before Casework.
- `people` declares synthetic test people, each with a subject and one grant per product. A grant
  selects an access profile of that product's project, its scopes, and extra claims. A BReg grant
  must name a profile the BReg project declares.
- `scenarioFile` names the project-relative file (for example `tests/scenarios.yaml`) whose
  scenarios the run makes before it reports ready. The plan must set it; an inline `journey` key is
  refused, so move those steps into the file. Each step names a person, a product, a method, a path
  starting with `/v1/`, and what it expects back. The file path cannot contain `..` or backslashes.
  The start and status reports include `scenarioDigest` for the exact file bytes captured at start.
  When the BReg project is the development project root (`project: .`), keep the scenario file out
  of `tests/`: `bregctl check` reads every YAML file there as a BReg test.
  A scenario takes its BReg access profile from the test person's grant, so do not repeat it as
  `accessProfile` in a step path. A path that names a different profile than the grant's is
  refused at check time.

[Write the development plan](#write-the-development-plan) describes every key, capture type, and limit.

## Check, then start

`check` validates the plan and resolves its fixtures, grants and references with the installed
authoring tools. It works with the database offline.

```sh test-skip="needs the installed release and a running development server"
rstack dev check ./licensing
```

Success is `Development plan is valid` and exit status 0. Add `--deny-warnings` to refuse any
warning, and `--json` for a machine-readable report. Fix every error before you start: the report
names the plan field that caused it.

Start the run. The time to live (TTL) begins when the run is ready and defaults to 30 minutes:

```sh test-skip="needs the installed release and a running development server"
rstack dev start ./licensing --ttl 30m
```

The command creates separate databases and logins for the run, starts both products on loopback
ports, runs the scenarios, and returns while the services keep running:

```text test-excerpt
Run 2f17770cb47d4502ad0b809a529f4309 ready
  breg http://127.0.0.1:64930
  casework http://127.0.0.1:64931
  Journey licensing-approval passed
  Logs STATE_DIRECTORY/2f17770cb47d4502ad0b809a529f4309/logs
  rstack dev token 2f17770cb47d4502ad0b809a529f4309 --as administrator
  rstack dev token 2f17770cb47d4502ad0b809a529f4309 --as applicant
  rstack dev token 2f17770cb47d4502ad0b809a529f4309 --as intake
  rstack dev token 2f17770cb47d4502ad0b809a529f4309 --as reviewer
```

Your run ID and ports differ, and `STATE_DIRECTORY` stands for the state directory your run reports. Copy the run ID: every later command takes it. The
scenario has already created an application in BReg and had a reviewer approve it in Casework.
`rstack dev status RUN_ID` repeats this report at any time.

## Call the products with a token

`token` writes a short-lived bearer header file for a test person and reports where it is. Tokens
expire five minutes after issue, or with the run if that is sooner, so ask again when one lapses.
Pass the header file to curl with `--header @FILE`:

```sh test-skip="needs a running development run"
RUN=2f17770cb47d4502ad0b809a529f4309
HEADERS="$(rstack dev token "$RUN" --as applicant --json | jq -r '.credentials[0].header_file')"
curl -sS --header @"$HEADERS" \
  "http://127.0.0.1:64930/v1/records/applications?accessProfile=applicant"
```

Use the BReg URL from your own report. BReg needs the selected profile as the `accessProfile`
query parameter, and the response lists the application the scenario created:

```json test-excerpt
{"items":[{"domainData":{"profession":"Surveyor","reference":"application-001"},"recordIdentifier":"23257c7f-1acd-4fbf-8a3c-4b253238043c","revisionIdentifier":"1"}],"meta":{"datasetIdentifier":"licensing","recordTypeIdentifier":"application","registryIdentifier":"licensing"},"pageInfo":{"nextCursor":null}}
```

Casework needs no query parameter, because its header file carries the profile. This asks for the
reviewer's open tasks; the queue is empty because the scenario already decided the request:

```sh test-skip="needs a running development run"
HEADERS="$(rstack dev token "$RUN" --as reviewer --json | jq -r '.credentials[0].header_file')"
curl -sS --header @"$HEADERS" "http://127.0.0.1:64931/v1/review-tasks?queue=applications"
```

```json test-excerpt
{"items":[],"status":"complete"}
```

A BReg project with encrypted fields runs without extra setup: each run gets its own development
data key, removed when the run ends, so encrypted data does not outlive its run. A step in the
project's `tests/journeys.yaml` that touches an encrypted Record type fails the pre-activation
test, because that test has no key. Exercise those Record types in an authored Stack scenario
file instead.

## Stop the run

```sh test-skip="needs a running development run"
rstack dev stop "$RUN"
```

Success is `Run RUN_ID stopped`. Stop, and TTL expiry, terminate both services and remove the run's
databases, roles, keys and files. Stop the PostgreSQL server itself when you finish:

```sh test-skip="needs the running development server"
pg_ctl -D "$DEV/data" stop
```

## When a run fails

A failed scenario is different from a startup failure. `start` exits 1 but prints the normal run
report. With `--json`, its `schema_version` is `registry.rstack.dev.v1` and its `status` is `ready`.
The report has `scenarios[*].result`, with at least one `failed`, and `scenarioDigest` (`sha256:<hex>`) identifies the exact file bytes captured
at start. The failed step includes its reason. The services keep running, and
`rstack dev status RUN_ID` repeats the results and digest, so use the run ID to inspect the products
and logs before you stop the run.

Other refusals and failures produce an error report instead. With `--json`, the report is one
object on standard output with `schema_version` `registry.rstack.error.v1` and `status` `refused`.
Its process exit status and `error.class` identify the kind of failure:

| Exit | `error.class` | Meaning |
| --- | --- | --- |
| 1 | `domain` | The request, the project, the plan or the run's state was refused. Fix the plan or the command. |
| 2 | `usage` | The command line is wrong, such as a malformed run ID, `--ttl` or test person name. |
| 3 | `operational` | The environment failed: PostgreSQL is unreachable or refuses the administrator, a product binary cannot start, no loopback port is free, a product or the run does not start in time, or a run needs its resources released. |

For example, `rstack dev start ./licensing --json` with the PostgreSQL server stopped (the operating
system error number varies by platform):

```text test-excerpt
{"error":{"class":"operational","message":"cannot establish the PostgreSQL administrator session over verified TLS: the PostgreSQL connection handshake failed: error connecting to server: Connection refused (os error 61)"},"schema_version":"registry.rstack.error.v1","status":"refused"}
```

Start the server and run the command again. Without `--json`, the same message goes to standard
error as `rstack dev: MESSAGE` with the same exit status.

When a start fails before the run becomes available, the run directory is removed but its logs are
kept at `<state>/failed/<run_id>/logs`, and the error names the path. A live run's logs are in
`<run>/logs`: `supervisor.log` for the supervisor and one file per product stage, such as
`breg-check.log` or `casework-runtime.log`. `rstack dev status RUN_ID` names the logs directory.
Delete kept logs yourself.

When a run still holds databases, roles or processes, the error carries its `run_id` and a
`recovery` object listing them. This happens if PostgreSQL is unavailable during cleanup for
longer than the supervisor retries (up to 30 minutes), or if the supervisor was lost. Release the
run with:

```sh test-skip="needs a run that lost its supervisor"
rstack dev stop RUN_ID --recover
```

If the supervisor is still running, use plain `stop`. For a lost supervisor, its process guards
stop the products and any product tools still running. Use the original PostgreSQL cluster and
maintenance database for `--recover`. Recovery waits for the guards, drops the databases and
roles, and removes the run directory, including its development key file. If a check or cleanup
step fails, the report explains what to inspect before retrying.
[Recover a run](#recover-a-run) lists the manual steps and the recovery fields.

## PostgreSQL server requirements

The server must be PostgreSQL 17 or newer and must serve TLS.
The runner always verifies the server certificate and host name.
It trusts the platform's roots, or the CA bundle in PEM format named by `RSTACK_DEV_DATABASE_CA`.

The administrator role named in the URL needs `LOGIN CREATEROLE CREATEDB`.
Superuser is not needed for a non-spatial run.
The runner sets `createrole_self_grant` on its own sessions, so you do not configure it.
The administrator also installs `btree_gist`, which PostgreSQL treats as a trusted extension.
The runner reads `pg_catalog.pg_control_system()` to identify the cluster for recovery.
PostgreSQL allows this function by default.

The administrator URL always carries a password.
Set it through `RSTACK_DEV_DATABASE_URL`, because `--database-url` is visible to other local users in the process list.
The URL must be a `postgres://` or `postgresql://` URL with one TCP host, a user, a password, and one database name.
Percent-encode special characters in the password.
The URL accepts these query parameters and refuses all others:

- `sslmode`: `require`, `verify-ca`, or `verify-full`.
  The runner verifies the certificate and host name whichever you choose.
- `connect_timeout` and `application_name`.
- `sslrootcert` is refused.
  Set `RSTACK_DEV_DATABASE_CA` instead.

## Write the development plan

The plan file starts with the schema modeline that editors read, as the licensing example's `dev.yaml` does.
A versioned plan schema validates it.
List the project's issuer, product directories, and audiences in startup order, and the test people with synthetic subjects and exact product grants.
A grant selects the access profile, scopes, and additional claims.
Each selected profile gets the test person's subject in its principal claim.
The products enforce their ordinary permissions.
If several people match a step in the BReg project's `tests/journeys.yaml`, select its alias under `schemaTestPeople.<journey-id>.<step-id>`.
The run obtains the normal schema-test receipt before packaging.

Every BReg grant must name an access profile the BReg project declares, including a profile that carries only proposal permissions and so belongs to no entity.
`rstack dev check` refuses a grant that does not, and so does `start`, before it provisions anything.
The error names the plan pointer, for example `/people/NAME/grants/breg/profile`.
A Casework grant must name an access profile of the Casework project, reported at `/people/NAME/grants/casework/profile`.
The run does not compare scopes with the profile: a profile's required scopes are a per-entity rule, and a mismatch appears as a failed journey step.

### Native review handoff

For a native review handoff, `bindings.bregReviewAuthority` identifies the Casework producer, and `bindings.caseworkContextProvider` identifies the BReg context provider and action.
`rstack dev check` refuses a binding that names a review authority or action the BReg project does not declare, or a producer or context provider the Casework project does not declare.
`start` refuses it before it provisions anything.
`check` also writes each binding's product configuration exactly as `start` does.
BReg's review-authority reader and `caseworkctl check --runtime-config` on the Casework configuration refuse what each product would refuse at startup, and `check` reports the refusal, with the rule it broke, at the plan field that produced the value.
It refuses a BReg grant profile that is not the `service-status` profile the Casework context provider's policy names.

A binding requests tokens for the other product's audience as an OAuth resource, so that audience must be an absolute URI, such as `urn:example:review`.
It requests the scopes of its identity's grant for that product.
Those scopes must be OAuth scope-tokens (no quotes or backslashes) that fit in 4096 bytes when joined by spaces.
`check` reports a violation at the audience or the grant's `scopes`.
The run pairs the provider on a private copy before packaging.

A reviewer whose Casework context call forwards the bearer to BReg declares both grants, one shared client, and `caseworkContext: true`.
Both grants declare the same scopes and additional claims.
Casework reads the token subject or the BReg principal claim.
The token carries both audiences and the authority explicitly shared by both grants.

### Authored scenario file

Set `scenarioFile: tests/scenarios.yaml` in `dev.yaml` and omit `journey` to run an authored pack.
The path must stay inside the development project.
Absolute paths, parent components, backslashes, and symlinks escaping the project are refused.
The file follows the Stack scenarios schema:

```yaml
apiVersion: id.registrystack.org/formats/rstack/scenarios/v1alpha1
kind: RStackScenarios
scenarios:
  - id: read
    steps:
      - id: list
        product: breg
        as: operator
        method: GET
        path: /v1/records/records
        expect:
          status: 200
```

The file contains 1 to 16 uniquely named scenarios, each with 1 to 32 steps, and no more than 64 steps in total.
Each scenario uses the same journey, step, expectation, and capture rules as the inline form described next.
Captures are available only to later steps in the same scenario.
`{{run.issuer}}` is the one run value available in strings; it resolves to the effective issuer URL after the runner binds its loopback port.
Other references must name an earlier capture.
The runner reads and validates the file during `check` and `start`, then snapshots its content before execution, so edits after `start` do not alter that run.
Scenarios execute in file order and each gets fresh captures.

The BReg project's `tests/journeys.yaml` remains its separate native schema test input.
The Stack scenario file does not replace or change it.
Existing plans with one inline `journey` remain supported, but a plan cannot specify both forms or neither.

{/* Evidence: crates/registry-rstack-dev/src/plan.rs SCENARIOS_API_VERSION, SCENARIOS_KIND, scenarioFile;
    products/breg/generated/tools/scenarios.v1alpha1.schema.json RStackScenarios. */}

### Journey steps

A journey runs 1 to 32 steps in order.
Each step names the test person it runs as (`as`), the product, the method, and a relative path that starts with `/v1/`.
A step sends one of two request bodies:

- `body` is a JSON body.
- `raw` is a non-JSON body for methods other than GET: `contentType` and `base64`.

A step can also set the `If-Match`, `Idempotency-Key`, and `Registry-Source-Profile` headers.
Use URI-safe characters for values in a path.

Each step asserts the response with `expect`:

- `status` is one accepted HTTP status from 200 to 599, or a list of up to 16.
- `json` maps JSON pointers to exact expected values.
- `checks` lists up to 32 assertions.
  Each tests one JSON pointer with exactly one of `equals`, `length`, or `contains`.
- `code` is the problem code an error response must carry.

A step remembers values from its response under `capture`.
Refer to a capture as `{{capture-name}}` in a later step's path, request body, header, expected value, or `find` value.
A step cannot use its own captures.
Capture names are unique across the journey.
A capture has one `type`:

- `pointer` remembers the string or number at a JSON pointer in the body.
- `header` remembers a response header.
  `etag` is the supported header.
- `find` searches the array at a JSON pointer for the one item whose `where` pointer equals a value, and remembers the item's `pointer` value.
  The step fails if no item or more than one item matches.
- `value` remembers the value at a pointer.
  With `query`, the value must be a URL, and the capture is that query parameter's value.

Use a bounded GET `poll` for asynchronous delivery or result retrieval.
Set `maximumWaitMilliseconds` up to 60 seconds and choose a `pollIntervalMilliseconds` from 50 to 5000.
A journey can make at most 512 requests and transfer at most 8 MiB of request and response bodies in total.

{/* Evidence: crates/registry-rstack-dev/src/plan.rs maximumWaitMilliseconds, pollIntervalMilliseconds;
    crates/registry-rstack-dev/src/journey.rs JOURNEY_ATTEMPT_LIMIT, JOURNEY_TRANSFER_LIMIT. */}

### Token report

`token` writes a short-lived bearer header file for each grant.
Its JSON report gives the person's `alias`, the `expires_at` time when the tokens expire (five minutes after issue, or with the run if that is sooner), and a `credentials` list whose entries carry the `product`, the selected `profile`, and the `header_file` path.
Pass the file to curl with `--header @HEADER_FILE`.
With BReg, include the selected profile as the `accessProfile` query parameter.
With Casework, the header file carries the profile.

## Start a declared application

An optional `application` block starts one already-built local Node 24 host beside the products.
Set `issuer: run` for this mode and pass its built root at start with `--application-root DIRECTORY`; omit both for the product-only run.
`check` validates the declaration and deployment file without requiring the built root.
The application block names a browser `client`, an exact `callbackPath`, a local `healthPath`, a built `entry`, configuration `prepare` and `checker` files, and a `deployment` file relative to the development project.
It also names the configuration command's `configSchema` and exact `prepareVersion` line, and the `configEnvironment` variable through which the host reads its generated file.
The built files must stay inside the supplied root; the deployment file must stay inside the development project.
The entry is explicit, including when the application uses its own default entry.

Before provisioning, `start` checks Node 24, the built files, and the configuration command's `--version` output.
The runner picks a loopback issuer and application port.
After the product journey, it writes an owner-only run input with the declared schema name, real addresses, product audiences, and paths to a fresh browser-client secret and an optional Casework recovery key.
It requests separate resource grants when Casework is present, invokes the declared command with `--deployment`, `--run`, and `--out`, then invokes the checker with the generated configuration path.
The child receives only the declared configuration-file environment variable and runs in the built root.
The ready report adds `issuer` and `application` URLs.
`status` repeats them, and `stop`, expiry, or a crashed child stops the issuer and app alongside the products.
Configuration commands and built hosts are trusted local code supplied by the operator; the runner does not fetch or build them.
A later `start` creates a fresh disposable run and databases; it does not restore unfinished application work.

### Browser issuer

The browser issuer presents only the plan's synthetic test people.
It issues one resource-bound token per product after a confidential authorization-code exchange with S256 PKCE.
It grants the intersection of the requested scopes and the selected person's scopes for that product; a request with no overlap is refused.
Browser tokens carry the same grant in `scope` and `registry_scopes`.
In application mode, `name` is presentation-only and `registry_scopes` carries the selected person's narrowed host scopes.
Do not use either as a BReg or Casework principal claim or as an additional authored grant claim; `check` and `start` refuse those configurations.

One browser session can obtain a second product grant for the same person, and `prompt=login` opens the person picker again.
The authored BReg and Casework profiles still decide which client and person can use each operation.
Declare the browser client in the relevant BReg requester profiles; the runner adds it to the runtime's accepted-client list but does not change the authored package.
Browser tokens last at most 15 minutes and expire with the run; `rstack dev token` continues to issue five-minute CLI tokens.

### Bind an existing Casework producer to a run

A plan for a BReg and Casework pair may explicitly bind the existing review producer's issuer on a private source copy before normal packaging.
Use `issuer: run`; `application` is optional for this exact paired binding.
Add exact old-value guards to the existing binding:

```yaml
bindings:
  bregReviewAuthority:
    id: casework
    producer: registry
    identity: producer
    runIssuerBinding:
      producer:
        expectedIssuer: https://issuer.example.test
        expectedProfile: requester
        expectedSubject: producer
      initiator:
        expectedIssuer: https://issuer.example.test
        trust: run-test-people
```

The selected Casework producer must already have exactly that issuer, profile, and subject.
The existing `people.producer` subject and Casework grant profile must match it.
No producer, person, profile, client, scope, or grant is created.
`initiator` is separately optional: omission preserves `trustedInitiatorIssuer`, including its absence.
Opt-in requires an existing exact issuer pin and replaces it with this run's issuer.
`run-test-people` acknowledges issuer-level initiator trust under the admitted producer; it is not a subject allowlist.
Existing initiator profiles, exclusion, and requester-read rules still apply.

`check` calls `caseworkctl generate run-source` for structured validation without allocating an issuer or provisioning a database.
`start` captures the checked Casework source closure privately and refuses drift before activation.
The worker uses the real allocated issuer, writes a disposable source copy with only the selected issuer members changed, then follows normal provider pairing, check, new packaging, apply, and doctor.
The original project is never rewritten.
Private capture and transform receipts contain source and output file hashes, the binding digest, the actual issuer, and changed pointers; normal package and activation reports retain the new package identity.
Run cleanup removes these run-local receipts with the other private files.
Each start allocates a reservation and signing key and prepares and packages the source again instead of loading an old bound package.
The kernel may later recycle a port; that does not reuse an old key or run.
Fixed HTTPS product-only plans remain unchanged.

An authored exact Casework policy version or digest selection is never rewritten by source binding.
If the newly packaged policy no longer matches that selection, the ordinary product refusal remains authoritative.

Without `application`, the exact paired binding starts only product APIs.
It requires no application root, Node, or host build and admits no browser client.
The reserved loopback issuer URL is a logical issuer identifier in this mode, not a browser sign-in or discovery endpoint.
Products use the pinned static JWKS; CLI tokens and the separately served run-local machine token endpoint continue to use the same effective issuer.
The worker holds the reservation until cleanup.
`issuer: run` without application and without this exact paired binding is refused, including BReg-only plans; fixed HTTP remains refused.

### Explicit browser roles with separate human source credentials

A paired BReg and Casework built application may declare `application.caseworkSourceCredentialRoles` as 1 through 32 distinct existing role identifiers.

It does not pick roles, infer a staff profile, or modify the authored deployment.

## Run isolation

Each run listens on loopback, creates separate databases and migration and runtime logins, and pins its own public signing key in the runtime files.
The local issuer signs under the project's issuer name with a key unique to the run.
Use synthetic test people and keep the issuer's private directory under your user account.

Stop and TTL expiry terminate the services and remove the databases, roles, keys, and run files.
A spatial BReg run also creates a `NOLOGIN` role whose name starts with `breg_bbox_`; cleanup removes it with the others.

### Encrypted fields

A BReg project with encrypted fields runs without extra setup.
`start` draws a development data key for the run from the operating system's random source and writes it as `field-key` in the run directory, readable only by your user.
BReg reads it through its `local-file` key custody, which it accepts only for a local development database.
The key is never printed, never written to the checkout, and is removed with the run directory on stop, TTL expiry, and a failed start.
When a run needs recovery, the report names the key file under `recovery.field_encryption_key` until `stop --recover` removes it.
Every run gets a new key, so encrypted data does not outlive its run.

The schema test that `start` runs before activation has no field-encryption key.
A step in `tests/journeys.yaml` that touches a Record type with an encrypted field fails it, and `start` reports `breg test failed (test.step.failed)`.
Exercise those Record types in the plan's `journey` instead.

This key custody is for development only.
A deployment supplies its key as [Encrypt a field](../breg-field-encryption/) describes.

    crates/registry-rstack-dev/src/lib.rs field_encryption_key. */}

### State directory

The state directory holds one directory per run.
It defaults to `rstack-dev-UID` in the system temporary directory.
Set `RSTACK_DEV_STATE_DIR` to use another location.
A run directory is renamed to `.<run_id>.removing` before it is deleted, and `status` and `stop` ignore that name.
If the deletion is interrupted, delete that directory yourself; the run's field-encryption key is deleted before the rename, so it holds no key material.

## Recover a run

If PostgreSQL becomes unavailable during cleanup, the supervisor retries with backoff for up to 30 minutes.
It then writes `cleanup-pending.json` in the run directory.
If the supervisor is lost, the run's process guards stop the product runtimes and any product tool that was still running.
`stop` and `status` report the run directory, the recorded process groups, and the database and role names.

Release a run whose supervisor is gone with:

```sh test-skip="needs a run that lost its supervisor"
rstack dev stop RUN_ID --recover [--database-url URL]
```

Use plain `stop` while the supervisor is still running.
For recovery, use an administrator URL for the same PostgreSQL cluster and maintenance database used at startup, with the same administrator rights.
`--database-url` defaults to `RSTACK_DEV_DATABASE_URL`, as for `start`.
Recovery checks the recorded cluster identifier and maintenance database before dropping any resources.
It waits for the process guards to finish, then drops the databases and roles and removes the run directory.
If any step fails, the report gives the reason and the resources you can check before retrying.

An abrupt machine restart can stop a guard before it writes its completed cleanup receipt.
In that case `--recover` refuses to claim the guarded workload was reaped, even if the process no longer exists.
Verify ownership and finish cleanup with the manual steps that follow.
The same manual path applies to runs from an older development build without recovery metadata.
Recovery releases the disposable run; it does not resume its application or pending work.

A successful recovery reports `status` `stopped` and a `recovered` object with `stopped_process_groups` and `databases_and_roles`.

If you need to finish cleanup by hand, do it in this order:

1. Verify which product processes still belong to the run and stop those groups.
   Use the run's configuration paths and process details to establish ownership before signaling a group.
2. Connect to the original PostgreSQL cluster as the administrator.
   Run `DROP DATABASE IF EXISTS "NAME" WITH (FORCE)` for each listed database.
3. Run `DROP ROLE IF EXISTS "NAME"` for each listed role, including a `breg_bbox_*` role from a spatial run.
4. Remove the run directory.
   It holds the run's development field-encryption key when `field_encryption_key` is listed.

    crates/registry-rstack-dev/src/recovery.rs. */}

## Error report fields

With `--json`, a refusal or startup failure from `rstack dev` start, status, token, or stop prints one JSON object on standard output, validated by the `rstack-dev-error` v1 schema.
The launcher prints the same object for failures before the helper starts, such as a missing component.
An interrupted `start` is class `domain`.
Environment failures (class `operational`) also include a PostgreSQL server that cannot provision a run's databases and roles, a cleanup that stalled, and an internal failure of the run's supervisor.

- `schema_version` is `registry.rstack.error.v1` and `status` is `refused`.
- `error.class` and the exit status are described in [When a run fails](#when-a-run-fails).
  `error.message` is the human-readable reason.
- `run_id` is present when the failure concerns a run that still has resources to release.
  Try `stop --recover`; an incomplete guard receipt requires the verified manual cleanup in [Recover a run](#recover-a-run).
- `recovery` accompanies `run_id` when the resources are known.
  It has `kind` (`lost-supervisor` or `cleanup-pending`), `run_directory`, `processes`, `objects` or `databases_and_roles`, and `field_encryption_key` when the run directory still holds the run's key file (the path, never the key).
  It carries `reason` when `--recover` could not finish.

Without `--json`, the message goes to standard error as `rstack dev: MESSAGE` with the same exit code.
The reports of `rstack dev check` use `BRegCtlReport` instead.
A helper started without the launcher's request prints a plain message and exits 2.

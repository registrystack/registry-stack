If you are writing a registry project, `rstack dev` runs it on your machine. It starts the products
the project lists, runs short scenarios against them, and removes everything when you stop. One
product is enough: you do not need the others to try yours. This page starts with one product on its
own, then runs several together, and ends with the reference for the plan, applications, issuer
binding, isolation and recovery.

## Generate the application client

From the application, run `npm install @registrystack/client`, then run
`rstack client generate --help` for the register, product and output options.
The command looks for the installed `@registrystack/client` package starting at the output file's directory.
Like `rstack dev`, it sets `RSTACK_BREGCTL_BIN` to the selected release's `bregctl` when an installed release is selected.
See the [TypeScript client reference](../../reference/typescript-clients/).

## Before you start

You need:

- Docker. A run starts its own PostgreSQL server in a container, so the first run pulls the image
  and needs network access. If you cannot use Docker, run your own server and read
  [Use a PostgreSQL server you run](#use-a-postgresql-server-you-run).
- `curl`.
- A checkout of Registry Stack at the release you installed, for the example projects.

Evidence, Render, and Discovery can run on their own without a database or Docker.

## Install the components

Install `rstack` from one verified release, then add the component your project uses, such as Base
Registry Engine (BReg). The steps are in
[Decide your first Base Registry Engine registry](../../tutorials/first-breg/#install-registry-stack).

```sh test-skip="uses a downloaded, independently verified release installer"
rstack install breg
```

Check the selected installation before you continue:

```sh test-skip="needs the installed release"
rstack components list
```

Success is a `breg` line that says `installed`. `available` means that the selected release
provides the component but it is not installed, so run the `rstack install` command again.
`unavailable` means that the selected release does not provide the component for your platform. If
your shell cannot find `rstack`, or the command says `No installation selected`, repeat the verified
`rstack` installation steps linked above. `rstack dev` asks only for the components the plan lists,
so a BReg-only project needs no `casework`.

### Build from source

If you build the components yourself, build the command-line tool and the server of each product you
run in one command, then tell `rstack` where they are with the `RSTACK_*_BIN` variables:

```sh test-skip="needs a Registry Stack source checkout and a Rust toolchain"
cargo build --locked -p registry-bregctl -p registry-breg --features registry-breg/runtime --bins
export RSTACK_BREGCTL_BIN="$PWD/target/debug/bregctl"
export RSTACK_BREG_BIN="$PWD/target/debug/breg"
```

Set the tool and runtime paths for the products in your plan.

| Product | Tool override | Runtime override |
| --- | --- | --- |
| BReg | `RSTACK_BREGCTL_BIN` | `RSTACK_BREG_BIN` |
| Casework | `RSTACK_CASEWORKCTL_BIN` | `RSTACK_CASEWORK_BIN` |
| Evidence | `RSTACK_EVIDENCECTL_BIN` | `RSTACK_EVIDENCE_BIN` |
| Messaging | `RSTACK_MESSAGINGCTL_BIN` | `RSTACK_MESSAGING_BIN` |
| Scheduling | `RSTACK_SCHEDULINGCTL_BIN` | `RSTACK_SCHEDULING_BIN` |
| Documents | `RSTACK_DOCUMENTSCTL_BIN` | `RSTACK_DOCUMENTS_BIN` |
| Coordinator | `RSTACK_COORDINATORCTL_BIN` | `RSTACK_COORDINATOR_BIN` |
| Adapter | `RSTACK_ADAPTERCTL_BIN` | `RSTACK_ADAPTER_BIN` |
| Render | `RSTACK_RENDER_BIN` | `RSTACK_RENDER_BIN` |
| Discovery | `RSTACK_DISCOVERYCTL_BIN` | `RSTACK_DISCOVERY_BIN` |

On macOS, a source build of the products links a dynamic FIPS library that the loader cannot find,
so a binary started outside Cargo aborts with `Library not loaded`. Source the helper in your
current shell and build through it, as `CONTRIBUTING.md` in the checkout describes. Installed
releases do not need this.

The development runner is the `crates/registry-rstack-dev` crate. Each supported product CLI links
it behind a hidden subcommand, and `rstack dev` runs it through the CLI of the plan's first product
in the order BReg, Casework, Evidence, Messaging, Scheduling, Documents, Coordinator, Adapter, Render, and Discovery.

## Run one product on its own

The BReg minimal example is a small directory registry with a plan file, `dev.yaml`, and one
scenario. Copy it from your checkout and work in the copy:

```sh test-skip="needs a Registry Stack checkout"
cp -R path/to/registry-stack/products/breg/examples/minimal ./directory
```

`rstack dev` reads `dev.yaml` and the scenario file it names. Product files stay byte-for-byte
unchanged, and generated settings, keys and packages live in the run's owner-only scratch
directory. Check the plan, then start a shorter run with an explicit time limit:

```sh test-skip="needs the installed release and Docker"
rstack dev check ./directory
rstack dev start ./directory --ttl 30m
```

`check` validates the plan and resolves its fixtures, grants and references with the installed
authoring tools. It works with the database offline and needs no Docker. Success is
`Development plan is valid` and exit status 0. Add `--deny-warnings` to refuse any warning. With the
global `--format json` option, `check` writes a `BRegCtlReport` with `command` set to `dev-check`.
Fix every error before you start: the report names the plan field that caused it.

`start` pulls the PostgreSQL image on the first run, creates databases and logins for the run,
starts BReg on a loopback port, runs the scenario, and returns while BReg keeps running. The time to
live (TTL) begins when the run is ready and defaults to eight hours. `--ttl` takes one whole number
from `1s` to `24h` with an `s`, `m` or `h` suffix:

```text test-excerpt
Run 2f17770cb47d4502ad0b809a529f4309 ready
  breg http://127.0.0.1:64930
  Scenario directory-contact passed
  Logs STATE_DIRECTORY/2f17770cb47d4502ad0b809a529f4309/logs
  rstack dev token 2f17770cb47d4502ad0b809a529f4309 --as editor
  rstack dev token 2f17770cb47d4502ad0b809a529f4309 --as foreign-editor
```

Your run ID and port differ, and `STATE_DIRECTORY` stands for the state directory your run reports.
Copy the run ID: every later command takes it. The scenario has already created a contact and read
it back. `rstack dev status RUN_ID` repeats this report at any time.

### Call the product with a token

`token` writes a short-lived bearer header file for a test person and prints where it is. Tokens
expire one hour after issue, or with the run if that is sooner, so ask again when one lapses.
Pass the header file to curl with `--header @FILE`:

```sh test-skip="needs a running development run"
RUN=2f17770cb47d4502ad0b809a529f4309
HEADERS="$(rstack dev token "$RUN" --as editor | awk '$1 == "breg" && $2 == "headers" {print $3}')"
curl -sS --header @"$HEADERS" http://127.0.0.1:64930/v1/records/contacts
```

Use the BReg URL from your own report. The response lists the contact the scenario created:

```json test-excerpt
{"items":[{"domainData":{"email":"contact@example.test","jurisdiction":"zone-a","name":"Example contact"},"recordIdentifier":"1a34839c-66d8-44d2-a7aa-136de5615d07","revisionIdentifier":"1"}],"meta":{"datasetIdentifier":"directory","recordTypeIdentifier":"contact","registryIdentifier":"local-directory"},"pageInfo":{"nextCursor":null}}
```

### Stop the run

```sh test-skip="needs a running development run"
rstack dev stop "$RUN"
```

Success is `Run RUN_ID stopped`. Stop, and TTL expiry, terminate the services and remove the run's
databases, roles, keys, files and containers.

### Other products on their own

Casework runs on its own the same way. The `products/casework/examples/standalone-decision`
example lists only Casework, creates a request as one test person, and has another decide it, with
no BReg binary present.

Evidence runs on its own too, and it needs no database and no Docker. The
`products/evidence/examples/standalone` example lists only Evidence and asks it for an adult-status
assertion as one test person. Evidence reads a data source, so start the example's synthetic source
in its own terminal, in the copy of the example:

```sh test-skip="needs a Registry Stack source checkout and Evidence installed"
python3 serve-source.py --port 8081
```

Then run the plan from another terminal in the same directory:

```sh test-skip="needs a Registry Stack source checkout and Evidence installed"
rstack dev start .
```

Success is `Scenario ask-adult-status passed` and one `evidence` URL. The run is its own issuer, so
the plan sets `issuer: run` and the test token's requester tag is the grant's `profile`, which
must be a tag the `requesterTags` of an access profile in your `dev-authority.yaml` lists. The run
uses your `local-target.yaml` and the authority it names. The run packages the project, activates
its authority and starts `evidence serve` inside the run directory. It never writes to your project.
`rstack dev stop RUN_ID` removes everything. [Evidence on its own](#evidence-on-its-own) has the
details.

Messaging runs without contacting a real provider. For each provider in the project's
`messaging.yaml`, the run starts a sink on loopback: Mailpit in a labelled Docker container for an
`smtp` provider, and a mock gateway inside the supervisor for an `http` provider. The gateway
answers each send with `queued` and then posts a signed `delivered` callback to the run's Messaging
runtime. A plan with an `smtp` provider needs Docker for Mailpit even when you supply the database
by address. `stop`, TTL expiry and `--recover` remove Mailpit with the run. The
`products/messaging/examples/starter` example sends one SMS through the gateway as a scenario.
[Messaging and its sinks](#messaging-and-its-sinks) has the details.

### Read the run report

The start and status reports carry two maps for tools that work beside the run. With the global
`--format json` option they are `runtimeConfigs` and `sinks` in the `registry.rstack.dev.v1` report.
The human report prints the same facts.

- `runtimeConfigs` maps each product to the absolute path of the runtime configuration the run
  wrote for it. For Evidence it is `<run>/evidence-candidate/runtime.yaml`. Pass that path to
  `evidencectl request prepare --runtime-config` instead of guessing it. The human report prints
  one `Runtime config PRODUCT PATH` line per product. Only the address line starts with the
  product name, so `awk '$1 == "breg" {print $2}'` reads the address.
- `bregHookSink` gives the loopback origin and the URL where you can read received BReg hooks.
- `sinks` maps each Messaging provider to its sink, where you can read what the run sent:
  `{"type":"smtp","smtp":"HOST:PORT","url":"MAILPIT_URL"}` for Mailpit, or
  `{"type":"http","url":"GATEWAY_ORIGIN/sent"}` for the mock gateway. It is absent when the run has
  no sink.

## Run several products together

The licensing example that ships with Registry Stack runs BReg and Casework as a pair. Copy it and
work in the copy:

```sh test-skip="needs a Registry Stack checkout"
cp -R path/to/registry-stack/products/platform/examples/licensing ./licensing
```

The directory holds a BReg project (`registry/`), a Casework project (`casework/`) and the plan
`dev.yaml`. Install `casework` beside `breg` with `rstack install casework`, then check and start
the plan as before:

```sh test-skip="needs the installed release and Docker"
rstack dev check ./licensing
rstack dev start ./licensing
```

The report names a URL for each product and a scenario result, and lists every test person:

```text test-excerpt
Run 2f17770cb47d4502ad0b809a529f4309 ready
  breg http://127.0.0.1:64930
  casework http://127.0.0.1:64931
  Scenario licensing-approval passed
  Logs STATE_DIRECTORY/2f17770cb47d4502ad0b809a529f4309/logs
  rstack dev token 2f17770cb47d4502ad0b809a529f4309 --as administrator
  rstack dev token 2f17770cb47d4502ad0b809a529f4309 --as applicant
  rstack dev token 2f17770cb47d4502ad0b809a529f4309 --as intake
  rstack dev token 2f17770cb47d4502ad0b809a529f4309 --as reviewer
```

The scenario has already created an application in BReg and had a reviewer approve it in Casework.
A test person's header file covers each product the person has a grant for, so ask for the token of
the person you want and pass the header line that names the product you call:

```sh test-skip="needs a running development run"
RUN=2f17770cb47d4502ad0b809a529f4309
HEADERS="$(rstack dev token "$RUN" --as applicant | awk '$1 == "breg" && $2 == "headers" {print $3}')"
curl -sS --header @"$HEADERS" \
  "http://127.0.0.1:64930/v1/records/applications?accessProfile=applicant"
```

BReg needs the selected profile as the `accessProfile` query parameter when the project declares
more than one profile. The response lists the application the scenario created:

```json test-excerpt
{"items":[{"domainData":{"profession":"Surveyor","reference":"application-001"},"recordIdentifier":"23257c7f-1acd-4fbf-8a3c-4b253238043c","revisionIdentifier":"1"}],"meta":{"datasetIdentifier":"licensing","recordTypeIdentifier":"application","registryIdentifier":"licensing"},"pageInfo":{"nextCursor":null}}
```

Casework needs no query parameter, because its header file carries the profile. This asks for the
reviewer's open tasks. The queue is empty because the scenario already decided the request:

```sh test-skip="needs a running development run"
HEADERS="$(rstack dev token "$RUN" --as reviewer | awk '$1 == "casework" && $2 == "headers" {print $3}')"
curl -sS --header @"$HEADERS" "http://127.0.0.1:64931/v1/review-tasks?queue=applications"
```

```json test-excerpt
{"items":[],"status":"complete"}
```

Stop the run with `rstack dev stop "$RUN"`.

## Adapt the development plan

To adapt a plan to your own project, change these parts and leave the structure alone:

- `issuer` names the identity issuer the local test tokens claim. Use a name that is yours.
- `products` lists each product's project directory and token audience, in any order. Name any
  nonempty subset of `breg`, `casework`, `evidence`, `messaging`, `scheduling`,
  `documents`, `coordinator`, `adapter`, `render` and `discovery`. The run starts
  BReg before Casework. An application needs BReg.
- `people` declares synthetic test people, each with a subject and one grant per product. A grant
  selects an access profile of that product's project, its scopes, and extra claims. A BReg grant
  must name a profile the BReg project declares. When several people could fill a BReg schema-test
  step, `schemaTestPeople` names the one that does.
- `scenarioFile` names the project-relative file (for example `tests/scenarios.yaml`) whose
  scenarios the run makes before it reports ready. Move any inline `journey` steps into this file.
  Follow the [scenario step rules](#scenario-steps). Keep `..` and backslashes out of the file path.
  The start and status reports include `scenarioDigest` for the exact file bytes captured at start.
  When the BReg project is the development project root (`project: .`), keep the scenario file out
  of `tests/`, as the minimal example does with `dev/scenarios.yaml`: `bregctl check` reads every
  YAML file directly under `tests/` as a BReg test. A scenario takes its BReg access profile from
  the test person's grant, so do not repeat it as `accessProfile` in a step path. A path that names
  a different profile than the grant's is refused at check time.

[Write the development plan](#write-the-development-plan) describes every key, capture type, and limit.

A BReg project with encrypted fields runs without extra setup: each run gets its own development
data key, removed when the run ends, so encrypted data does not outlive its run. A step in the
project's `tests/journeys.yaml` that touches an encrypted Record type fails the pre-activation
test, because that test has no key. Exercise those Record types in an authored Stack scenario

## When a run fails

A failed scenario is different from a startup failure. `start` exits 1 but prints the normal run
report, with the failed step and its reason. With the global `--format json` option, its
`schema_version` is `registry.rstack.dev.v1` and its `status` is `ready`. The report has
`scenarios[*].result`, with at least one `failed`, and `scenarioDigest` (`sha256:<hex>`) identifies
the exact file bytes captured at start. The services keep running, and `rstack dev status RUN_ID`
repeats the results and digest, so use the run ID to inspect the products and logs before you stop
the run.

Other refusals and failures print `rstack dev: MESSAGE` on standard error. With `--format json`, the
report is one object on standard output with `schema_version` `registry.rstack.error.v1` and
`status` `refused`. The process exit status and `error.class` identify the kind of failure:

| Exit | `error.class` | Meaning |
| --- | --- | --- |
| 1 | `domain` | The request, the project, the plan or the run's state was refused. Fix the plan or the command. |
| 2 | `usage` | The command line is wrong, such as a malformed run ID, `--ttl` or test person name, or a run ID that is unknown or already cleaned up. |
| 3 | `operational` | The environment failed: PostgreSQL or Docker is unreachable or refuses the administrator, a product binary cannot start, no loopback port is free, a product or the run does not start in time, or a run needs its resources released. |

For example, `rstack dev start ./directory` with Docker stopped is an exit 3 failure whose message
names the Docker command that failed and both ways out: start Docker, or supply a server with
`RSTACK_DEV_DATABASE_URL`. Start Docker and run the command again.

When a start fails before the run becomes available, the run directory and its containers are
removed but its logs are kept at `<state>/failed/<run_id>/logs`, and the error names the path. A
live run's logs are in `<run>/logs`: `supervisor.log` for the supervisor and one file per product
stage, such as `breg-check.log` or `casework-runtime.log`. `rstack dev status RUN_ID` names the logs
directory. Delete kept logs yourself.

If the supervisor stops while a run is live, `rstack dev stop RUN_ID` retries cleanup for 60 seconds.
If it still cannot release the run, it says the supervisor was lost and prints the command that
recovers it:

```sh test-skip="needs a run that lost its supervisor"
rstack dev stop RUN_ID --recover
```

If the supervisor is still running, use plain `stop`. For a lost supervisor, its process guards
stop the products and any product tools still running. Recovery waits for the guards, drops the
databases and roles, removes the run's containers, and removes the run directory, including its
development key file. When you supplied the server by address, use the original PostgreSQL cluster
and maintenance database for `--recover`. If a cleanup step fails, the report explains what to
inspect before retrying. [Recover a run](#recover-a-run) lists the manual steps and the recovery
fields.

## The managed PostgreSQL server

The run starts PostgreSQL for BReg, Casework, Messaging, Scheduling, Documents, Coordinator and
Adapter unless you supply a database address. Evidence, Render and Discovery need no database.

- The server is a `postgres:18.7` container, pinned by digest.
  A BReg project that requires PostGIS gets `postgis/postgis:18-3.6` instead.
  That image is published for linux/amd64 only, so on Apple Silicon it runs emulated and a spatial run takes about a minute.
- The first run pulls the image, so it needs network access and takes longer.
- The container publishes its port on `127.0.0.1` only.
  The runner draws a CA for the run, and the server uses TLS with `verify-full`, as the products require.
- The container carries the label `org.registrystack.rstack.dev-run=RUN_ID`.
  `stop`, TTL expiry, a failed start and `stop --recover` remove it, and any Mailpit container of the run, by that label.
- The administrator is a superuser with a generated password.
  Anyone who can run `docker inspect` on the container can read that password.
  Docker access already grants root on the host, so the throwaway server adds no new exposure.
  The least-privilege administrator described below protects a shared or hosted server.
- If Docker is missing or its daemon does not answer, `start` fails with an operational error that names both ways out: install Docker, or supply a server by address.
- Recovering a managed run needs Docker, not an administrator URL.
- `RSTACK_DEV_DATABASE_CA` without a URL is refused.

## Use a PostgreSQL server you run

Use a server you run when you cannot use Docker, or for hosted Studio, CI, or a shared server.
Set `RSTACK_DEV_DATABASE_URL` to its administrator URL and, if its certificate is not publicly trusted, `RSTACK_DEV_DATABASE_CA` to the CA file.
Use a least-privilege administrator there.

The server must be PostgreSQL 17 or newer and must serve TLS.
The runner always verifies the server certificate and host name.
It trusts the platform's roots, or the CA bundle in PEM format named by `RSTACK_DEV_DATABASE_CA`.

The administrator role named in the URL needs `LOGIN CREATEROLE CREATEDB`.
Superuser is not needed for a non-spatial run.
The runner sets `createrole_self_grant` on its own sessions, so you do not configure it.
The administrator also installs `btree_gist`, which PostgreSQL treats as a trusted extension.
The runner reads `pg_catalog.pg_control_system()` to identify the cluster for recovery.
PostgreSQL allows this function by default.

The administrator URL always carries a password.
Set it through `RSTACK_DEV_DATABASE_URL`, because `--database-url` is visible to other local users in the process list.
The URL must be a `postgres://` or `postgresql://` URL with one TCP host, a user, a password, and one database name.
Percent-encode special characters in the password.
The URL accepts these query parameters and refuses all others:

- `sslmode`: `require`, `verify-ca`, or `verify-full`.
  The runner verifies the certificate and host name whichever you choose.
- `connect_timeout` and `application_name`.
- `sslrootcert` is refused.
  Set `RSTACK_DEV_DATABASE_CA` instead.

### A local server

This is the one recipe for a local server by address.
It needs PostgreSQL 17 or newer command-line tools (`initdb`, `pg_ctl`, `psql`) and `openssl` on your `PATH`.
It makes a private certificate authority, starts the server on `127.0.0.1`, and creates a least-privilege administrator.
Keep the working directory outside any repository.
If port 5432 is taken, change `PORT`.

```sh test-skip="needs a PostgreSQL installation and starts a server"
export DEV="$HOME/rstack-dev-postgres"
PORT=5432
mkdir -p -m 700 "$DEV"
umask 077
openssl rand -hex 16 > "$DEV/postgres.pass"
openssl rand -hex 16 > "$DEV/devadmin.pass"
initdb -D "$DEV/data" -U postgres --auth=scram-sha-256 --pwfile="$DEV/postgres.pass" -E UTF8

openssl req -new -x509 -newkey rsa:2048 -nodes -days 30 -subj /CN=rstack-dev-ca \
  -addext basicConstraints=critical,CA:TRUE -keyout "$DEV/ca.key" -out "$DEV/ca.pem"
openssl req -new -newkey rsa:2048 -nodes -subj /CN=localhost \
  -keyout "$DEV/data/server.key" -out "$DEV/server.csr"
printf 'subjectAltName=DNS:localhost,IP:127.0.0.1\nextendedKeyUsage=serverAuth\n' \
  > "$DEV/server.ext"
openssl x509 -req -in "$DEV/server.csr" -CA "$DEV/ca.pem" -CAkey "$DEV/ca.key" \
  -CAcreateserial -days 30 -extfile "$DEV/server.ext" -out "$DEV/data/server.crt"

printf "listen_addresses = '127.0.0.1'\nport = %s\nssl = on\n" "$PORT" \
  >> "$DEV/data/postgresql.conf"
pg_ctl -D "$DEV/data" -l "$DEV/postgres.log" -w start
```

The passwords are random and stay in owner-only files, so nothing secret reaches your shell history or a process list.
Create the administrator with the password from its file:

```sh test-skip="needs the running development server"
CONNECTION="host=127.0.0.1 port=$PORT user=postgres dbname=postgres sslmode=verify-full sslrootcert=$DEV/ca.pem"
PGPASSWORD="$(cat "$DEV/postgres.pass")" psql "$CONNECTION" <<'SQL'
\set pw `cat "$DEV/devadmin.pass"`
CREATE ROLE devadmin LOGIN CREATEROLE CREATEDB PASSWORD :'pw';
SQL
```

Success is `CREATE ROLE`.

## Write the development plan

The plan file starts with the schema modeline that editors read, as the licensing example's `dev.yaml` does.

### Native review handoff

For a native review handoff, `bindings.bregReviewAuthority` identifies the Casework producer, and `bindings.caseworkContextProvider` identifies the BReg context provider and action.
`rstack dev check` refuses a binding that names a review authority or action the BReg project does not declare, or a producer or context provider the Casework project does not declare.
`start` refuses it before it provisions anything.
`check` also writes each binding's product configuration exactly as `start` does.
`caseworkctl check --runtime-config` on the Casework configuration refuses what Casework would refuse at startup, and `check` reports the refusal, with the rule it broke, at the plan field that produced the value.
BReg checks its review-authority configuration when the run starts it.
`check` refuses a BReg grant profile that is not the `service-status` profile the Casework context provider's policy names.

A binding requests tokens for the other product's audience as an OAuth resource, so that audience must be an absolute URI, such as `urn:example:review`.
It requests the scopes of its identity's grant for that product.
Those scopes must be OAuth scope-tokens (no quotes or backslashes) that fit in 4096 bytes when joined by spaces.
`check` reports a violation at the audience or the grant's `scopes`.
The run pairs the provider on a private copy before packaging.

Both grants declare the same scopes and additional claims.
Casework reads the token subject or the BReg principal claim.

The native review example at `products/breg/acceptance/reviewed-evidence-journey/dev.yaml` declares one.

### Evidence on its own

An Evidence plan starts no database and needs no Docker.
The run is the issuer: Evidence's local target accepts only a loopback issuer, so the plan sets `issuer: run`, and the run signs each test token with a throwaway key it serves as a key set on its own loopback origin.
An Evidence plan may not declare an application, and it may not name another issuer.

To start Evidence, the run copies the project and creates a target with `evidencectl target new`, from the project's `local-target.yaml` when it has one, with development secrets for what that target references.
It points the target at the run's issuer, listener and package directory, packages the project, activates the compiled authority and runs `evidence serve`.
All of it lives in the run directory, and the project is never written.
The package directory is made read-only because Evidence refuses a package that is writable.
The run makes it writable again when it removes the run directory.

An Evidence grant's `profile` is the requester tag the token carries in `evidence_tags`.
Use a tag the project's access profile admits.
A project with a `local-target.yaml` runs with that target and the authority it names, for example `dev-authority.yaml`, so use a tag one of its profiles lists in `requesterTags`.
A project without one gets a target made from its definitions' ceilings, which admits `local-service`.
The grant's `claims` supply the rest, for example `evidence_audience`.
Each token also carries `registry_actor_kind: service` unless the grant's claims set another kind, and the person's `subject` is the token's `sub`.
The run does not start the project's data source.
Start it first, as the project's README says.
The example at `products/evidence/examples/standalone` needs `python3 serve-source.py --port 8081` running in its directory.

### Messaging and its sinks

A Messaging plan runs against a development PostgreSQL server like BReg and Casework.

### Authored scenario file

`dev.yaml` must set `scenarioFile`, for example `scenarioFile: tests/scenarios.yaml`.
A plan without it is refused, and so is a plan with an inline `journey` key: move its steps into the scenarios file and set `scenarioFile`.
The path must stay inside the development project.
Absolute paths, parent components, backslashes, and symlinks escaping the project are refused.
When the BReg project is the development project root (`project: .`), keep the scenario file out of `tests/`, as the BReg minimal example does with `dev/scenarios.yaml`.
`bregctl check` reads every YAML file directly under `tests/` as a BReg test and warns about a directory it does not read.
The file follows the Stack scenarios schema, `products/platform/generated/dev/scenarios.v1alpha1.schema.json`:

```yaml
apiVersion: id.registrystack.org/formats/rstack/scenarios/v1alpha1
kind: RStackScenarios
scenarios:
  - id: read
    steps:
      - id: list
        product: breg
        as: operator
        method: GET
        path: /v1/records/records
        expect:
          status: 200
```

The file contains 1 to 16 uniquely named scenarios, each with 1 to 32 steps, and no more than 64 steps in total.
Each scenario follows the step, expectation, and capture rules in [Scenario steps](#scenario-steps).
Captures are available only to later steps in the same scenario.
`{{run.issuer}}` is the one run value available in strings; it resolves to the effective issuer URL after the runner binds its loopback port.
Other references must name an earlier capture.
The runner reads and validates the file during `check` and `start`, then snapshots its content before execution, so edits after `start` do not alter that run.
Scenarios execute in file order and each gets fresh captures.

The BReg project's `tests/journeys.yaml` remains its separate native schema test input.
The Stack scenario file does not replace or change it.

A scenario step takes its BReg access profile from the grant of the test person it runs as.
A step path that names `accessProfile` itself is accepted only when it names that same profile, and the check refuses any other value with the step, both profiles and the fix.

### Scenario steps

A scenario runs 1 to 32 steps in order.
Each step names the product, HTTP method and relative path. Include `as` for products that verify
tokens. Omit it for Discovery. Use a path under `/v1/` or the Adapter contract path
`/.well-known/registry-adapter/effective-contract`.
A step sends one of two request bodies:

- `body` is a JSON body.
- `raw` is a non-JSON body for methods other than GET: `contentType` and `base64`.

A step can also set the `If-Match`, `Idempotency-Key`, and `Registry-Source-Profile` headers.
Use URI-safe characters for values in a path.

Each step asserts the response with `expect`:

- `status` is one accepted HTTP status from 200 to 599, or a list of up to 16.
- `json` maps JSON pointers to exact expected values.
- `checks` lists up to 32 assertions.
  Each tests one JSON pointer with exactly one of `equals`, `length`, or `contains`.
- `code` is the problem code an error response must carry.

A step remembers values from its response under `capture`.
Refer to a capture as `{{capture-name}}` in a later step's path, request body, header, expected value, or `find` value.
A step cannot use its own captures.
Capture names are unique across the scenario.
A capture has one `type`:

- `pointer` remembers the string or number at a JSON pointer in the body.
- `header` remembers a response header.
  `etag` is the supported header.
- `find` searches the array at a JSON pointer for the one item whose `where` pointer equals a value, and remembers the item's `pointer` value.
  The step fails if no item or more than one item matches.
- `value` remembers the value at a pointer.
  With `query`, the value must be a URL, and the capture is that query parameter's value.

Use a bounded GET `poll` for asynchronous delivery or result retrieval.
Set `maximumWaitMilliseconds` up to 60 seconds and choose a `pollIntervalMilliseconds` from 50 to 5000.
A scenario can make at most 512 requests and transfer at most 8 MiB of request and response bodies in total.

{/* Evidence: crates/registry-rstack-dev/src/plan.rs maximumWaitMilliseconds, pollIntervalMilliseconds;

## Start a declared application

An optional `application` block starts one already-built local Node 24 host beside the products.

`check` validates the declaration and deployment file without requiring the built root.
The application block names a browser `client`, an exact `callbackPath`, a local `healthPath`, a built `entry`, configuration `prepare` and `checker` files, and a `deployment` file relative to the development project.
It also names the configuration command's `configSchema` and exact `prepareVersion` line, and the `configEnvironment` variable through which the host reads its generated file.
The built files must stay inside the supplied root; the deployment file must stay inside the development project.
The entry is explicit, including when the application uses its own default entry.

### Encrypted fields

## Recover a run

If cleanup cannot finish, for example because PostgreSQL is unavailable, the supervisor retries for 60 seconds.
It then stops and reports a lost-supervisor recovery that names the `stop RUN_ID --recover` command.
If the supervisor is lost, the run's process guards stop the product runtimes and any product tool that was still running.
`stop` and `status` report the run directory, the recorded process groups, and the database and role names.

Release a run whose supervisor is gone with:

```sh test-skip="needs a run that lost its supervisor"
rstack dev stop RUN_ID --recover [--database-url URL]
```

Use plain `stop` while the supervisor is still running.
A managed run needs Docker for recovery and no URL: the command removes the run's container by its label.
For a run on a server by address, use an administrator URL for the same PostgreSQL cluster and maintenance database used at startup, with the same administrator rights.
`--database-url` defaults to `RSTACK_DEV_DATABASE_URL`, as for `start`.
Recovery checks the recorded cluster identifier and maintenance database before dropping any resources.
It waits for the process guards to finish, then drops the databases and roles and removes the run directory.
If any step fails, the report gives the reason and the resources you can check before retrying.

An abrupt machine restart can stop a guard before it writes its completed cleanup receipt.
In that case `--recover` refuses to claim the guarded workload was reaped, even if the process no longer exists.
Verify ownership and finish cleanup with the manual steps that follow.
The same manual path applies to runs from an older development build without recovery metadata.
Recovery releases the disposable run; it does not resume its application or pending work.

A successful recovery reports `status` `stopped` and a `recovered` object with `stopped_process_groups` and `databases_and_roles`.

If you need to finish cleanup by hand, do it in this order:

1. Verify which product processes still belong to the run and stop those groups.
   Use the run's configuration paths and process details to establish ownership before signalling a group.
2. Connect to the original PostgreSQL cluster as the administrator.
   Run `DROP DATABASE IF EXISTS "NAME" WITH (FORCE)` for each listed database.
3. Run `DROP ROLE IF EXISTS "NAME"` for each listed role, including a `breg_bbox_*` role from a spatial run.
4. Remove the run directory.
   It holds the run's development field-encryption key when `field_encryption_key` is listed.

{/* Evidence: crates/registry-rstack-dev/src/lib.rs CLEANUP_BUDGET, stopped_process_groups, lost-supervisor, org.registrystack.rstack.dev-run;
    crates/registry-rstack-dev/src/recovery.rs. */}

## Error report fields

With the global `--format json` option, a refusal or startup failure from `rstack dev` start, status, token, or stop prints one JSON object on standard output, validated by the `rstack-dev-error` v1 schema.
The launcher prints the same object for failures before the helper starts, such as a missing component.
An interrupted `start` is class `domain`.
Environment failures (class `operational`) also include a PostgreSQL server that cannot provision a run's databases and roles, a cleanup that stalled, and an internal failure of the run's supervisor.

- `schema_version` is `registry.rstack.error.v1` and `status` is `refused`.
- `error.class` and the exit status are described in [When a run fails](#when-a-run-fails).
  `error.message` is the human-readable reason.
- `run_id` is present when the failure concerns a run that still has resources to release.
  Try `stop --recover`; an incomplete guard receipt requires the verified manual cleanup in [Recover a run](#recover-a-run).
- `recovery` accompanies `run_id` when the resources are known.
  It has `kind` (`lost-supervisor`), `run_directory`, `processes`, `objects` (or, for a managed run, `container`), and `field_encryption_key` when the run directory still holds the run's key file (the path, never the key).
  It carries `reason` when `--recover` could not finish.

Without `--format json`, the message goes to standard error as `rstack dev: MESSAGE` with the same exit code.
The reports of `rstack dev check` use `BRegCtlReport` instead.
A helper started without the launcher's request prints a plain message and exits 2.

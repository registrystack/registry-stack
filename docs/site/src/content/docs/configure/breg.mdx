If you are describing your own registry to the Base Registry Engine (BReg), you write a
[project](../../reference/glossary/#registry-project): a directory of files that declares what the
registry stores, who may read and change it, and how it changes. You can start a project three
ways, then check it offline, with no database.

## Choose a starting point

- `bregctl init <directory>` writes the default `minimal-directory` starter: one `contact` Record
  type, the project the tutorials use.
- `bregctl init --template facility-registry <directory>` writes facilities, operators,
  assignments, and a directory, with immediate and Proposal Actions and a Rhai plan.
- `bregctl init --from publicschema <directory>` derives a project from the PublicSchema concepts
  you select. [Derive a registry from PublicSchema](../../tutorials/derive-a-registry-from-publicschema/)
  walks through it.

Each writes into a new directory and refuses one that exists.

## Start from the facility template

```sh
bregctl init --template facility-registry facility
```

  examples/inputs/facility.json

  plans/correct-address.rhai

`registry.yaml` is the registry itself. `dev-clients.yaml` names the local test callers and the
access profile each one requests. `tests/journeys.yaml` holds the permitted and refused requests
the project must keep passing. `examples/` holds ready-made requests for a local run, and
`plans/correct-address.rhai` is the plan code one Action calls.

```sh
bregctl check facility
```

```text test-excerpt

```

Check compiles all three YAML files together. It also prints one warning about a related-records
read, which [Control access and reads](../breg-access/) explains.

## Read the top of registry.yaml

```yaml title="facility/registry.yaml" test-excerpt="facility/registry.yaml"
apiVersion: id.registrystack.org/formats/breg/project/v1alpha1
kind: BRegProject
project:
  id: facility-registry
  canonicalBaseIri: https://facility-registry.example.gov
  version: 0.1.0
  defaultLanguage: en
  display:
    label: Facility Registry
    description: Facilities, operators, assignments, and an administrative directory.
```

`project` gives the registry its identity. The rest of the file follows in this order:
`package` (the source revision a production package records), `datasets`, `reviewAuthorities`,
`recordTypes`, `valueTypes`, `functions`, `actions`, `accessProfiles`, and `vocabularies`. A
project may also declare `modules`, `statisticalDatasets`, `recipients`, and
`evidenceProviders`. The [configuration reference](../../reference/breg-configuration/) lists
every key with its type and bounds.

## Declare Record types

```yaml title="facility/registry.yaml" test-excerpt="facility/registry.yaml"
  facility:
    route: facilities
    primaryDataset: facility-registry
    mutationMode: mutable
    readPaths:
      - {id: operators, through: facility-assignment, to: operator, route: operators}
    mutationPolicy:
      patch: proposal-required
```

Each [Record type](../../reference/glossary/#record-type) names its route, its dataset, and its
fields. Every field declares its type, bounds, requiredness, and classification; `typeRef` reuses
scalar constraints from `valueTypes`, and `apiName` sets the public property name. In both projects
and modules, declare reference, `crs84-point`, `crs84-polygon`, and structured types directly on
each field or Action input instead of through `valueTypes`. `mutationPolicy` here means
a facility changes only through a [Proposal](../../reference/glossary/#proposal), even for a
caller whose profile grants `patch`.

A Record type can declare multiple stored geometry fields. Its `geojson.geometryField` binding
selects one CRS84 Point or polygon field as the primary GeoJSON geometry. A polygon field accepts
GeoJSON Polygon and MultiPolygon values. A polygon field requires `precision` from 0 through 9 and
`maximumPositions` from 4 through 10,000. The position limit counts every ring and part, including
closing positions. Set `geojson.geometryField` to that field when you want GeoJSON and GIS reads.
The [configuration reference](../../reference/breg-configuration/) lists the optional coordinate
bounds and the other field members.

Polygon values use strict two-dimensional GeoJSON with only `type` and `coordinates`. BReg refuses
foreign members, invalid topology, positions beyond the field's precision or optional bounds, and
an edge whose longitude changes by more than 180 degrees. Split a shape at the antimeridian and
send the parts as a MultiPolygon. BReg preserves ring order and winding and derives no area field.

## Grant access

An [access profile](../../reference/glossary/#access-profile) binds required scopes, purposes, and
row boundaries to four separate kinds of grant: `permissions.records`, `permissions.actions`,
`permissions.proposals`, and `permissions.datasets` for statistical datasets. A local client in
`dev-clients.yaml` only requests a profile; declaring it grants nothing.

## Declare Actions and plan code

An [Action](../../reference/glossary/#action) is a named change with typed inputs. A
[Function](../../reference/glossary/#function) declares its runtime, source, entrypoint, ABI,
capabilities, and limits, and the Action that calls it fixes what it may write. Record hooks
announce committed changes; [Bind webhook receivers](../../operate/breg-webhooks/) covers
delivery.

## Keep a file with a Record

A Record type can keep a file, such as a signed form, beside its fields.
Declare each file slot under `attachments` on the Record type:

```yaml
  application:
    route: applications
    primaryDataset: directory
    mutationMode: mutable
    attachments:
      - id: evidence
        maximumBytes: 1048576
        contentTypes: [application/pdf]
        classification: restricted
        writeOnce: true
```

A slot declares its byte limit, its accepted media types and its classification.
A Record type declares at most eight slots, each up to 16 MiB with at most 16 media types.
A slot ID cannot reuse a field ID.
`writeOnce: true` is required, because nothing replaces a file once a slot holds one.

Two things fill a slot: the create effect of an immediate Action, or an applied Proposal that promotes one of its files.
[Keep a supporting document on the record](../breg-proposals/#keep-a-supporting-document-on-the-record) covers the Proposal path.
An immediate Action's effect names the slot and the request file that fills it:

```yaml
    plan:
      type: fixed
      effects:
        - id: application
          target: {recordType: application}
          operation: create
          set: {name: {fromInput: name}}
          attachments:
            evidence: {fromAttachment: evidence}
```

`bregctl check` refuses a request file on a patch effect, an Action with Evidence and a timer Action.
A file name cannot reuse an Action input ID.

The request carries every file the Action names in `attachments`, beside `input`.
Each file has its media type, its SHA-256 digest in lowercase hexadecimal and its base64 content:

```json
{
  "input": {"name": "Example applicant"},
  "attachments": {
    "evidence": {"contentType": "application/pdf", "sha256": "<digest>", "content": "<base64>"}
  }
}
```

BReg checks every file before it writes anything:

| Problem | Status | Cause |
| --- | --- | --- |
| `attachment.content-type` | 415 | The media type is not one the slot declares. |
| `attachment.too-large` | 413 | The file is larger than the slot's `maximumBytes`. |
| `attachment.digest-mismatch` | 422 | The digest does not match the bytes. |
| `action.guard_failed` | 412 | A commit guard failed, so nothing was written. |
| `attachment.slot-write-once` | 409 | The slot already holds a file. |

The record, its history, the file reference, the idempotency receipt and any hook event commit together, or none of them commits.
Hook events never carry file bytes.

Reading a file needs its own grant.
List the slot in `readableAttachments` on a record grant that includes `get`:

```yaml
records:
  - recordType: application
    operations: [get]
    readableFields: [name]
    readableAttachments: [evidence]
```

The caller downloads the file from `GET /v1/records/applications/{record_id}/attachments/evidence`.
The response has the stored media type and a `Repr-Digest` header with the stored SHA-256 digest.
A profile without the grant gets 404.
So do a record outside the profile's row boundaries, an empty slot and a file that verification has not approved.
When the Record type keeps an [access log](../../operate/breg-access-log/), each download is recorded in it.
History erasure removes the file reference, as [Erase retained history](../../operate/breg-retention/#erase-retained-history) explains.
That includes a file a Proposal promoted: erasing the revision the Proposal wrote also removes the Proposal's link to it.

## Generate business identifiers

The UUID in each Record envelope remains the stable Record identity.
Use a generated `string` field for an institution-facing number or code.
It reads like an ordinary field, but callers and Actions cannot set or patch it.
Do not grant it in `writableFields` or a Function write ceiling.

Add `generate` to a stored `string` field:

```yaml
- id: number
  type: string
  required: true
  minimumLength: 6
  maximumLength: 32
  classification: internal
  generate:
    type: sequence
    prefix: "APP-"
    minimumDigits: 4
    scope:
      - jurisdiction
- id: code
  type: string
  required: true
  minimumLength: 12
  maximumLength: 12
  classification: internal
  generate:
    type: random
    prefix: "REF-"
    length: 8
```

`sequence` allocates `APP-0001`, `APP-0002`, and onward within each distinct `jurisdiction`.
`minimumDigits` pads the number but does not cap the sequence, so the field's `maximumLength` must fit its full range.
`random` generates `length` characters after the prefix from the fixed alphabet `23456789ABCDEFGHJKLMNPQRSTUVWXYZ`, which leaves out characters people commonly misread.
Choose enough length for the expected number of Records.
BReg retries a collision within a bounded attempt count and refuses the create if the code space cannot supply a free value.

`scope` is accepted on `sequence` only.
It lists required stored scalar fields classified `public` or `internal`, and never a `reference`.
BReg keeps every issued value with its scope values after the Record is erased, so a scope must not hold restricted data or point at a person; use a jurisdiction or category code.
BReg includes the scope values in both the allocation namespace and a database uniqueness constraint.
Omit `scope` for one namespace across that Record type; a `random` code always has one namespace across its Record type.
Include the scope fields when you look up a scoped identifier, because the same code can exist in another scope.
The compiler limits the combined maximum size of the identifier field and its scope fields to a 1 KiB index budget.
For string and text fields it counts four bytes per character to cover UTF-8 values, including retained identifiers seeded during migration.
Use short keys for scope fields rather than descriptions.
A scope field cannot change after the Record is created, because moving a number to another namespace would invalidate its issued meaning.
Issued values are never recycled, including after a Record is tombstoned or erased.

Direct create, batch and import create, and Action create allocate in the write transaction.
A Proposal allocates on Submit and freezes the exact values in its reviewed effects.
A replay of Submit, Apply, or Retry reuses those values.

Sequences are monotonic, not gapless.
A create that rolls back releases its number, so a failed write leaves no gap.
Gaps come from three places:

- A Proposal that is rejected or cancelled after Submit keeps the values Submit allocated.
- Revise followed by a fresh Submit can allocate new values and leaves the earlier ones reserved.
- A sequence adopted on an existing field starts after the highest retained number and skips values already reserved.

A register that must issue gapless numbers therefore cannot use `sequence` with a Proposal Action.
A `sequence` value is guessable and shows how many values its scope has issued.
Use `random` for a code that people outside the registry see, such as one printed on a certificate and checked on a public verification page.

For a new registry, the compiler installs allocation state and the unique constraint with the initial schema.
Enabling generation on a field in an existing registry requires a reviewed migration.
Backfill any missing values first; the compiler then seeds reservations and sequence high-water marks from retained rows and checks uniqueness before activation.
Existing identifiers are preserved.
Changing or removing an active generation rule is unsupported, so plan the strategy, prefix, length, and scope as part of the issuing scheme.

## Register and transfer a facility

The facility-registry fixture combines immediate Actions with a related-Record acceptance condition, current ownership, and committed events.
Checking the source alone does not activate a registry; use the same package and apply boundary as any other project.

An administrator first creates an operator through `POST /v1/records/operators?accessProfile=operator-administrator`.
Registration then accepts this body through `POST /v1/actions/register-facility`:

```json
{
  "input": {
    "facilityCode": "FAC-001",
    "label": "Synthetic facility",
    "owner": "owner-a",
    "operatorId": "00000000-0000-4000-8000-000000000001"
  }
}
```

Use an existing authorised operator identifier in place of the synthetic UUID.
Send the registrar token and a stable `Idempotency-Key` for the submission.
Registration returns identifiers for `facility` and `initial-assignment`.
Recover a lost response by repeating the identical Action with the same key.
A corrected submission gets a new key.

Transfer first obtains an opaque edit condition from `POST /v1/actions/transfer-facility/target-conditions?accessProfile=facility-transfer` with `{"input":{"facilityId":"<returned facility identifier>"}}`.
Submit the returned `preconditions` unchanged with the facility identifier and destination `owner` to the transfer Action.
A stale condition requires a fresh user decision; do not silently refresh the edit baseline before submission.
The fixture journeys cover registration, replay, inactive-operator refusal, a refused destination, successful transfer, and former-owner refusal.
Its `directClaims` use the scalar `registry_principal` and a string array for the broker's `allowed_owners` boundary.
Fixture metadata repeats the principal value to bind the expected row boundary; the bearer token carries that claim only once.

The operator guard is an acceptance-time check on a linked input, not a permanent condition on later Records.
Inactivating an operator later does not undo an earlier registration, and the initial assignment is neither a membership grant nor a promise that the operator stays active.
The `facility-registrar` profile permits only the registration Action and limits the facility owner to the verified principal; it grants no direct facility or assignment create, patch, or delete.
After a transfer, the same former-owner token loses current GET and LIST access and the new owner gains it.
The fixture compares the claim with the stored owner directly, so access is not inferred from the initial assignment or from membership Records.
History access is granted separately, and the fixture grants none.

The fixture does not implement a general cross-Record invariant, arbitrary SQL or Rhai reads during a mutation, or a process engine.
Live relational membership authorisation is a separate policy capability that needs its own declared model and tests.
Use a Proposal when accepting a change requires review.

## Publish metadata with manifestProjection

Domain-semantic entries in `manifestProjection` are optional overlays on the configured data model.
One project declares one catalogue with its publisher, one or more identified `authorities`, one public service, one or more datasets, one or more data services, and optional distributions.
The public service names the authority legally competent for it with `competentAuthority`, an id from `authorities`.
The generated Manifest carries the authorities in `authorities[]` and the reference in the service's `competent_authority`, which CPSV-AP renders as `hasCompetentAuthority`.
Every Record type names exactly one `primaryDataset`, while each data service explicitly lists its nonempty `servesDatasets`.
Project-level `accessProfile` and `classificationCeiling` values are defaults that a dataset may narrow or replace.
The compiler resolves every membership and reference before generation, and refuses duplicates, missing memberships, and dangling authority, dataset, service, or distribution references.

Generated Manifest and DCAT bytes are one classified publication slice.
A dataset appears only when its effective access profile matches the governed project publication profile and its effective classification ceiling does not exceed the governed project ceiling.
Services, distributions, public-service references, Record types, fields, and relationship edges are pruned with that slice, so a public artifact cannot disclose a protected dataset by reference.

The projection can also declare localised catalogue and resource text, Record type concept URIs, identifiers, field concepts, relationship roles, and codelist schemes.
Registry Manifest remains the only portable metadata compiler and DCAT renderer.
BReg does not infer or hardcode a domain model.
Operational references may cross datasets, but Registry Manifest v1 accepts portable relationship targets only within the same dataset.
BReg therefore keeps the operational reference valid while omitting that edge from the portable projection until Registry Manifest defines cross-dataset relationship semantics.

When the source dataset, source Record type, reference field, target dataset, and target Record type are all visible in the publication slice, authoring commands report `breg.manifest-projection.cross-dataset-reference-omitted` at the reference field.
The warning does not invalidate the runtime reference.
Keep the dataset split and account for the missing metadata relationship in consumers, or place the Record types in the same projected dataset if that fits the intended model.
The warning is omitted when any of those members is concealed, so it does not reveal hidden relationships.
`bregctl check --deny-warnings` treats it as a failed check.

The business-establishments example project defines two datasets, one data service that serves both, one distribution attached to the registered-businesses dataset, and Record types with explicit primary-dataset membership.
Its local example concept URIs demonstrate semantic metadata without claiming conformance to an external domain model.
Generate the canonical Registry Manifest source and a DCAT JSON-LD catalogue from the project directory:

```sh test-skip="needs the reader's project directory"
bregctl generate manifest ./business-establishments --output ./business-metadata
```

Registry Manifest owns the standards rendering, so BReg carries no second DCAT implementation.

## Live derived fields

A derived relation is a reviewed SQL asset, compiled into a read-only `security_invoker` view over the caller's `registry_source` rows.
Its SQL must be one `SELECT` with the declared key and field aliases.
The compiler accepts an explicit set of raw PostgreSQL grammar nodes, the aggregate functions `count`, `bool_and`, and `every`, and `registry_context.evaluation_date()`.
`JSON_VALUE` and `JSON_EXISTS` may read scalars inside a structured field.
An explicit `RETURNING` type must be a supported built-in scalar type.
Ordinary casts are limited separately to reviewed built-in scalar targets; arrays, catalog reference types, XML, money, and timestamp-with-time-zone casts are refused.
Column references resolve against the columns exposed by each range in its own SELECT scope, so a range name cannot capture its whole row and attribute notation cannot invoke an unlisted function.
`JSON_QUERY`, table functions, SQL/JSON aggregates and constructors, and XML constructs are refused.
Additions to this grammar require a concrete use case and review; a parser upgrade does not automatically admit new syntax.
Joins use explicit `ON` conditions; source and join aliases cannot rename columns through alias lists.
`LIMIT` and `OFFSET` are refused on the rows the SQL returns, including through a table expression or `FROM` subquery.
Which rows get a value would then depend on which rows the reader can see.
A correlated subquery in an expression may still use them to pick among one row's linked rows.
A `FROM` subquery cannot use them, even when it is `LATERAL`.

Every emitted derived row must have a non-null canonical `id`, and one derived relation may emit at most one row for that `id`.
BReg refuses the query atomically when reviewed SQL violates either rule.

The generated view checks derived values before casting them to their declared types.
String length bounds, text maximum length, exact decimal scale and precision, integer integrality and range, and vocabulary membership are enforced without truncation or rounding.
Null values retain their existing nullable behaviour.
A violating value raises a stable database error identifying the field without including its value; an API read fails through the ordinary value-free source-unavailable response.
Only derived relations reached by a read are evaluated.

View definitions belong to the managed catalog fingerprint.
When a compiler release changes these wrappers, its release note carries the package upgrade instructions, and the [changelog](../../changelog/) links every release note: rebuild from the authored project with the deployed package as the baseline and apply the successor before switching the runtime.
Starting the runtime never rewrites the active catalog.

### Grant the Record types the SQL reads

The derived view runs under the caller's row security.
Its SQL sees only the rows that the caller's access profile can read, on every Record type it reads.
`readableFields` limits what a read returns, not what the computation reads.

A profile that reads a derived field must therefore see every row that the SQL links to on other Record types.
Otherwise the field is computed from part of the data, and the read returns a wrong value with no error.
The grant follows the derived relation, not the column, so reading one column needs access to every Record type that the relation's SQL reads.

`bregctl check` checks each profile that reads, filters or sorts a derived field.
For each other Record type the SQL reads, the profile's grant on that type must:

- include `get`, `lookup`, `list`, `batch`, `revisions` or `snapshot`, refused otherwise with `breg.disclosure.derived-reads-unreadable-source`
- have the same `rowBoundaries`, in the same order, as the profile's grant on the Record type that owns the derived field
- require no `requiredPurposes`, or every purpose that the owner's grant requires

A grant that breaks the boundary or purpose rule is refused with `breg.disclosure.derived-reads-source-boundary`.
The request matches the reader's boundaries as one ordered list.
A grant with fewer boundaries, or with none, sees no rows rather than more.
A request runs under one purpose, and a grant that requires purposes sees no rows under any other.
A profile's purposes cover each of its grants in the project, so a purpose mismatch comes from a module grant that requires other purposes.
A read path runs under the profile's grant on the path's root Record type, so that grant sets the boundaries and purposes.
A profile bounded by `id` cannot read a derived field over another Record type, because no row of another type shares that `id`.

A derived field whose SQL reads its own Record type once, row by row, needs no other grant.
SQL can read its own Record type more than once, in a join, a subquery or a table expression used twice.
It then reads other rows of that type, so the owner's Record type counts as a type the SQL reads.
So does SQL whose key is not each row's own `id`, read from the Record type itself rather than through a table expression or subquery.
So does SQL that combines or picks among its rows with an aggregate, `GROUP BY` or `DISTINCT ON`, unless any `GROUP BY` or `DISTINCT ON` includes that `id`.
A profile bounded by `id` cannot read such a field.
A read path reader needs its grant on the owner to match its grant on the path's root.
These refusals use `breg.disclosure.derived-reads-other-owner-rows`.
To serve a profile bounded by `id`, read the Record type once, in the top-level `FROM`, keyed on its own `id`.
Group or pick `DISTINCT ON` by nothing or by that `id`.

The smallest grant is `get`, with only the link fields readable and the same row boundaries.
Here a derived `member-count` field on `household` counts the linked `member` rows:

```yaml
accessProfiles:
  household-reader:
    principalClaim: registry_principal
    requiredScopes: ["registry:household:read"]
    permissions:
      records:
        - recordType: household
          operations: [get, list]
          readableFields: [household-code, member-count]
          rowBoundaries:
            - {field: district, claim: district, operator: equals}
        - recordType: member
          operations: [get]
          readableFields: [household]
          rowBoundaries:
            - {field: district, claim: district, operator: equals}
```

A row boundary names a field by its `id`, so the Record type the SQL reads needs a field with the same `id`, here `district`.
Matching boundaries assume that each linked row holds the same boundary value as the row it links to, and BReg cannot check that.
A `member` recorded in a different district from its household is left out of the household's count, with no error.
Keep boundary values consistent across linked records.

A subquery that refers to no column of the row reads more than the linked rows.
It computes one value over every row the reader sees.
Such a subquery may read a Record type on which the reader's grant has row boundaries.
`bregctl check` then reports the finding `breg.disclosure.derived-reads-withheld-source-rows`.
The value is exact only for readers whose grant on that Record type is unbounded.
BReg flags only a subquery inside an expression.
It does not detect a join to a table expression or `FROM` subquery over rows not linked to the row.
Keep such a derived field to readers whose grant on that Record type is unbounded.

Other protections on a Record type the SQL reads also leave rows out of the computation.
They are a `record` disclosure condition that binds the reader, and `membershipBoundaries` or `requireConsent` on the reader's grant on that type.
The same grant governs the profile's direct reads, where hiding those rows may be intended.
So `bregctl check` reports each one as the finding `breg.disclosure.derived-reads-withheld-source-rows` instead of refusing it.
The derived value leaves out the rows that the protection hides.

## Schedule a Record-controlled Action

Record type declares the timer, while the root project grants the exact Record type and timer
pair. [Schedule Actions with Record timers](../breg-record-timers/) covers the authoring contract and the inspection commands.

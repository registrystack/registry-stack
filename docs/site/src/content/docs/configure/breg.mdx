If you are describing your own registry to the Base Registry Engine (BReg), you write a
[project](../../reference/glossary/#registry-project): a directory of files that declares what the
registry stores, who may read and change it, and how it changes. You can start a project three
ways, then check it offline, with no database.

## Choose a starting point

- `bregctl init <directory>` writes the default `minimal-directory` starter: one `contact` Record
  type, the project the tutorials use.
- `bregctl init --template facility-registry <directory>` writes facilities, operators,
  assignments, and a directory, with immediate and Proposal Actions and a Rhai plan.
- `bregctl init --from publicschema <directory>` derives a project from the PublicSchema concepts
  you select. [Derive a registry from PublicSchema](../../tutorials/derive-a-registry-from-publicschema/)
  walks through it.

Each writes into a new directory and refuses one that exists.

## Start from the facility template

```sh
bregctl init --template facility-registry facility
```

```text test-excerpt
Initialized a registry project. 10 artifacts written.
  revision  sha256:<digest>

  README.md
  dev-clients.yaml
  examples/inputs/correction.json
  examples/inputs/deactivation.json
  examples/inputs/empty.json
  examples/inputs/facility.json
  examples/scenarios.json
  plans/correct-address.rhai
  registry.yaml
  tests/journeys.yaml
```

`registry.yaml` is the registry itself. `dev-clients.yaml` names the local test callers and the
access profile each one requests. `tests/journeys.yaml` holds the permitted and refused requests
the project must keep passing. `examples/` holds ready-made requests for a local run, and
`plans/correct-address.rhai` is the plan code one Action calls.

```sh
bregctl check facility
```

```text test-excerpt
Authoring check passed; registry revision sha256:<digest>.
```

Check compiles all three YAML files together. It also prints one warning about a related-records
read, which [Control access and reads](../breg-access/) explains.

## Read the top of registry.yaml

```yaml title="facility/registry.yaml" test-excerpt="facility/registry.yaml"
apiVersion: id.registrystack.org/formats/breg/project/v1alpha1
kind: BRegProject
project:
  id: facility-registry
  canonicalBaseIri: https://facility-registry.example.gov
  version: 0.1.0
  defaultLanguage: en
  display:
    label: Facility Registry
    description: Facilities, operators, assignments, and an administrative directory.
```

`project` gives the registry its identity. The rest of the file follows in this order:
`package` (the source revision a production package records), `datasets`, `reviewAuthorities`,
`recordTypes`, `valueTypes`, `functions`, `actions`, `accessProfiles`, and `vocabularies`. A
project may also declare `modules`, `statisticalDatasets`, `recipients`, and
`evidenceProviders`. The [configuration reference](../../reference/breg-configuration/) lists
every key with its type and bounds.

## Declare Record types

```yaml title="facility/registry.yaml" test-excerpt="facility/registry.yaml"
  - id: facility
    route: facilities
    primaryDataset: facility-registry
    mutationMode: mutable
    readPaths:
      - {id: operators, through: facility-assignment, to: operator, route: operators}
    mutationPolicy:
      patch: proposal-required
```

Each [Record type](../../reference/glossary/#record-type) names its route, its dataset, and its
fields. Every field declares its type, bounds, requiredness, and classification; `typeRef` reuses
scalar constraints from `valueTypes`, and `apiName` sets the public property name. In both projects
and modules, declare reference, `crs84-point`, and structured types directly on each field or
Action input instead of through `valueTypes`. `mutationPolicy` here means
a facility changes only through a [Proposal](../../reference/glossary/#proposal), even for a
caller whose profile grants `patch`.

## Grant access

An [access profile](../../reference/glossary/#access-profile) binds required scopes, purposes, and
row boundaries to four separate kinds of grant: `permissions.records`, `permissions.actions`,
`permissions.proposals`, and `permissions.datasets` for statistical datasets. A local client in
`dev-clients.yaml` only requests a profile; declaring it grants nothing.

## Declare Actions and plan code

An [Action](../../reference/glossary/#action) is a named change with typed inputs. A
[Function](../../reference/glossary/#function) declares its runtime, source, entrypoint, ABI,
capabilities, and limits, and the Action that calls it fixes what it may write. Record hooks
announce committed changes; [Bind webhook receivers](../../operate/breg-webhooks/) covers
delivery.

If you are authoring a Base Registry Engine (BReg) project, declare your Record
types, typed Actions, access profiles, and events in one governed model. Compile
that model offline before provisioning a database.

## Start from a complete project

```sh
bregctl init ./my-registry
bregctl check ./my-registry
```

The destination must be new. The default `minimal-directory` includes a `contact`
Record type, a jurisdiction-bound editor profile, explicit local clients, journey
fixtures, a resumable scenario, and a runtime example. Read its generated README
before changing identities or grants.

For atomic writes and durable work, use a separate destination:

```sh
bregctl init ./facility-registry --template facility-registry
bregctl check ./facility-registry
```

This project includes facilities, operators, assignments, directory entries,
reusable value types, a named Rhai Function, and immediate and Proposal Actions.
Its operator setup grant is authored in the project. Tooling adds no seed authority.

## Declare Record types and fields

`registry.yaml` starts with `apiVersion:
id.registrystack.org/formats/breg/project/v1alpha1` and `kind: BRegProject`.
`project` supplies identity, version, language, and canonical base IRI. `datasets`
supplies the datasets each Record type references through `primaryDataset`.

Use `recordTypes` for stored records:

```yaml
recordTypes:
  - id: contact
    route: contacts
    primaryDataset: directory
    mutationMode: mutable
    fields:
      - id: name
        type: string
        required: true
        minimumLength: 1
        maximumLength: 160
        classification: internal
```

Keep the complete generated project around this fragment. Every field declares
its type, bounds, requiredness, and classification. Reference fields name another
Record type. Use `apiName` for a deliberate public property name and `typeRef`
for a reusable project-local value type. Stable IDs carry identity; `display`
labels, descriptions, and safe titles carry presentation.

A Record type's `mutationPolicy` can require a Proposal for an operation. An
Action cannot bypass that requirement merely because a profile grants writes.
[Actions and Proposals](../breg-actions/) supplies the durable write model.

## Grant authority explicitly

`accessProfiles` binds verified scopes, purpose, principal, operations, fields,
and row boundaries. `permissions.records`, `permissions.actions`, and
`permissions.proposals` grant separate powers. A local client merely requests a
profile; declaring it in `dev-clients.yaml` creates no profile grant.

Start with the generated jurisdiction boundary. Keep a boundary field writable
for Create so a caller can supply the exact value its claim permits. Review any
Patch grant with an `in` boundary that can move a record between allowed values. Filters never replace row
authorization. [Control access per profile](../breg-access/) owns the grant model.

## Reuse and compose

Modules reuse governed project assets. Named `valueTypes` and `functions` keep
local types and plan code in one place. A Function's declared runtime, source,
entrypoint, ABI, capabilities, and limits remain part of the compiled contract.
Its write ceiling and refusals belong to the Action that calls it.

Record hooks describe committed events. Bind outbound destinations and secrets
in deployment configuration. [Bind webhook receivers](../../operate/breg-webhooks/) for outbound delivery.
External consumers receive no registry authority
from a delivery. Registry Manifest remains a one-way portable metadata projection;
its independently versioned entity vocabulary is separate from BReg authoring.

## Inspect the contract

```sh
bregctl --format json explain model ./my-registry
bregctl --format json explain access ./my-registry
bregctl --format json explain actions ./my-registry
bregctl --format json explain proposals ./my-registry
```

These commands need no database. Diagnostics identify the document and member
that needs repair. Use `bregctl check --help` for production and warning policy;
review warnings rather than treating them as extra grants. For a function, use
`project action-test --help` to test bounded synthetic inputs offline.

Database journeys prove current authorization, concurrency, and transactional
behavior beyond what compilation can establish. Test the exact candidate before
packaging it, and keep migration credentials with the operator.

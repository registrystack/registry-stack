If your code must present a bearer access token to Registry Evidence, Base Registry Engine (BReg),
or another Registry Stack service, you get it from the deployment's OAuth issuer with the
client-credentials grant, authenticating with a signed client assertion instead of a secret.

## Before you start

Get these values from the issuer administrator and the service's operator:

- The HTTPS token endpoint
- Your registered client identifier
- Your client's private JWK, with a `kid` and an `alg` the issuer accepts
- The issuer identifier, exactly as the issuer's metadata publishes it: it is the client-assertion
  audience
- The RFC 8707 resource identifier of the service you call
- The scopes that service's deployment requires

Keep the private key in a secret store, and never fall back to a client secret. Scopes are the
deployment's choice: one target may require a scope such as `evidence:request`, another may
require none. Request exactly the scopes your deployment names.

## With the Evidence client

A client built with `EvidenceClient.from_profile`, as in
[Request Evidence from your application](../../tutorials/request-evidence-from-an-application/),
needs no token code: the client profile drives the exchange. The explicit constructor takes it as
`token=`:

```python
client = EvidenceClient(
    base_url, trusted_jwks, revoked_key_ids,
    token={"private_key_jwt": private_key_jwt},
)
```

`private_key_jwt` holds `token_endpoint`, `client_id`, `client_key`, `audience` (the issuer
identifier, with no default), and optionally `resource` and `scopes`; the [client API reference](../../reference/client-api/#token-configurations)
has the rest. The client builds and signs each client assertion for you.

## Without the client

Any other caller, BReg callers included, signs a client assertion and posts this form to the token
endpoint:

```text
grant_type=client_credentials
client_id=<client-id>
client_assertion_type=urn:ietf:params:oauth:client-assertion-type:jwt-bearer
client_assertion=<signed-client-assertion>
resource=<resource-identifier>
scope=<scopes>
```

Omit `scope` when the deployment requires none. Keep `resource` and `scope` fixed for the client's
lifetime, so a cached token never serves another service. `resource` is a registered identifier,
not a URL to fetch.

The client assertion is a compact JWT signed with your private key. Its protected header carries:

- `alg`: the algorithm your key signs with, one of `EdDSA`, `ES256`, `RS256`, `ES384`, or `RS384`
- `kid`: your key's identifier, which the issuer uses to select your registered public key
- `typ`: `client-authentication+jwt`

Its claims carry:

- `iss` and `sub`: your client identifier
- `aud`: the issuer identifier, exactly as the issuer's metadata publishes it, as the only audience;
  an issuer that follows RFC 10070 section 4 refuses any other value, its token endpoint URL included
- `iat`: the current Unix time
- `exp`: `iat` plus a short lifetime, at most 300 seconds and no longer than your issuer accepts
  (the maintained clients default to 60)
- `jti`: a fresh identifier for every assertion, because a replay-checking issuer refuses a
  repeated one

An issuer checks `iat` and `exp` against its own clock, so keep yours synchronised.

## Request a separate token for each resource

You can register one OAuth client with your issuer and request a separate access token for each Registry Stack resource.
Each resource server independently checks its audience, admitted client, scopes, and actor profile.
Separate per-resource tokens are the recommended deployment pattern.
Existing bounded multi-audience tokens remain accepted where the owning profile supports them and includes its target audience; an additional audience alone is no refusal.
A token without the target audience grants no access to that resource.
Casework task-client profiles keep their narrower audience rules.

## Token profile each service accepts

Use RFC 9068 `typ: at+jwt` and RS256 or ES256 with public asymmetric signing keys.
`application/at+jwt` is the equivalent media-type spelling the shared verifier accepts.
Do not substitute an ID token or a UserInfo JWT.
Algorithms are resource policy: Casework, Scheduling, and Messaging admit RS256 and ES256.
BReg keeps its one explicitly configured algorithm, including its existing product-specific choices.
Configure RS256 or ES256 for the common profile, rather than widening every product to the union of all supported algorithms.

For each service, request the resource it names and make sure the token carries the audience configured for it:

- BReg: the selected access profile, the configured scope claim and separator, `registry_actor_kind`, and the contextual rules.
  The actor kind is profile-specific.
  It requires a configured maximum token lifetime of 1 to 7200 seconds and a `leewayMilliseconds` of whole seconds, 0 to 300000 ms.
  The resource server never refreshes; you obtain a replacement token.
- Casework: `requiredScopes` in the selected Requester, Staff, or Supervisor profile.
  The scope claim defaults to `registry_scopes`.
  Human routes require the configured `humanIdentity`, which defaults to `registry_actor_kind: human`.
  Task clients use their separate actor profile.
  `exp` and `nbf` are enforced, with an optional `maximumTokenLifetimeSeconds` and zero verifier skew.
  You obtain another per-resource token on expiry.
- Scheduling: `readsScope` (default `scheduling:read`) and a separate explain scope.
  Mutations require their task-grant authority.
  The scope claim defaults to `scope`, and actor and grant validation stay Scheduling-owned.
  `exp` and `nbf` are enforced, with no additional maximum lifetime or skew configured; task grants have separate deadlines.
  You obtain another per-resource token on expiry.
- Messaging: one declared access profile selects clients, scopes, and permitted actor kinds.
  The scope claim defaults to `scope`.
  `exp` and `nbf` are enforced, with no additional maximum lifetime or skew configured.
  You obtain another per-resource token on expiry.

## Provider behaviour

The canonical `PrivateKeyJwt` client provider caches only its own configured resource token and reacquires it before expiry.
Token exchange is uncached.
Use one provider instance per resource and scope set.
Python exposes it as `registry_client.auth.PrivateKeyJwt`; `registry_client.breg.PrivateKeyJwt` remains the same class for compatibility.
Rust exposes it in `registry_stack_client::auth`.

The provider's `resource` is the RFC 8707 resource indicator for the issued access token.
Its required `audience` instead names the client assertion's audience: the authorization server's issuer identifier, exactly as its metadata publishes it (RFC 10070 section 4).
It has no default, a provider built without it is refused, and it does not select an access-token audience.
Keep that distinction when you configure one shared OAuth registration.
A provider does not choose scopes, derive an audience, or grant downstream authority.

## Issuer networking

Plain HTTP on a literal IPv4 or IPv6 loopback address or `localhost` is accepted for local use.
Beyond loopback, set `allowInsecureHttp: true` explicitly, and only for a network where the operator approves unencrypted traffic.
The declared issuer and the declared JWKS endpoint may resolve to private networks.
A discovered endpoint inherits that allowance only on the exact issuer origin; a discovered cross-origin endpoint must use HTTPS and public addresses.
Cloud metadata and link-local addresses remain denied.
A hostname that resolves to loopback is not a literal-loopback exception.
[Connect an OIDC issuer](../../operate/advanced/connect-an-oidc-issuer/) covers the choices in detail.

## Safe diagnostics

Public invalid-credential responses remain a generic 401 `authentication.refused`.
Authenticated profile and route failures keep their documented 403 or concealment, and a verifier outage keeps its product's 503.
Internal verification stages are fixed labels: header, algorithm, token-type, key, signature, issuer, audience, time, client, scope, profile, and unavailable.
Each verifier emits at most one diagnostic per stage per minute.
These logs contain no credential, claim, issuer, audience, scope, key, or subject values.
Use the selected configuration and safe local validation to identify the mismatched field, and never add token contents to runtime logs.
Local fixture validation names the field or rule and the expected profile category without printing input values.

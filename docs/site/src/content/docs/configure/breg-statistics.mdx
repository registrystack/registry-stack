If your institution publishes counts from a Base Registry Engine (BReg) registry to a dashboard, statistics office, or republisher, declare a statistical dataset and publish its ended periods. Release readers see small counts suppressed and the rest rounded, without permission on the records behind them.

## What a statistical dataset fixes

A statistical dataset counts the records of one Record type, its unit, that match a fixed population, per calendar period, grouped by a closed set of dimensions. The registry project declares all of this and PostgreSQL computes the counts. A consumer chooses periods and JSON or CSV, never SQL, a grouping, or the population, so every reader counts the same thing.

## Declare a dataset

The facility template declares none; add one under the root `statisticalDatasets` key of `registry.yaml`, with these members:

- `id`, and `unit`, the Record type whose records are counted
- `population`, a filter in the same `$filter` grammar as a list query, over that Record type's fields
- `period`, either `type: flow` with a date `field` that places each record in one period, or `type: stock` with a `validity` (`temporal`, or `from` and an optional `until` date field) that counts the records valid on the period's reference date
- `granularity` (`day`, `month`, `quarter`, or `year`) and `firstPeriod`, both inside `period`
- `dimensions`, boolean or vocabulary-code fields of the unit Record type
- `disclosure`, with `minimumCount` and `roundingBase`, each at least 2

One period, with every dimension code and every total, must fit in 10,000 cells. The [configuration reference](../../reference/breg-configuration/#statistical-dataset-declarations) lists every member and the refusals `bregctl check` reports.

## Live counts and releases

A live count is computed on request from current data. It is exact, and filtered by the same rules as the profile's ordinary list query, so a live cell is a count the profile could already obtain by listing records.

A release is a stored, numbered version of one ended period, computed against one snapshot and transformed for disclosure. A final release can be corrected by a later final release, and a provisional release is refused once a final exists. Each release carries a definition digest of the population, sources, publisher visibility, dimensions, and disclosure parameters. Changing who may read a dataset keeps the series; changing what it counts starts another one.

## Decide who reads a dataset

Each [access profile](../../reference/glossary/#access-profile) that reaches it says so under `permissions.datasets`, beside its record permissions under `permissions.records`. A dataset permission holds `dataset` and `operations`, drawn from three operations:

- `read-live`, exact live counts
- `publish`, publishing and withdrawing releases
- `read-releases`, released documents

One profile at most holds `publish` on a dataset. Give it to a profile a person or a service uses directly: a standing agent profile, one with `actorKind: agent` and no `taskGrant`, cannot publish or withdraw a release, and `bregctl check` refuses the project with `breg.access-profile.standing-agent-publish-forbidden`. [Control access](../breg-access/) explains task grants.

A publisher and every `read-live` profile also need a count-capable list permission on the unit. A publisher's visibility must not depend on the caller, because the same dataset would otherwise count a different population for each caller. A profile that holds only `read-releases` needs no record permission. The configuration reference carries the full set of rules. Run `bregctl explain access` to see, for each dataset, which profiles hold each operation.

## Review what a release discloses

A release suppresses positive counts below `minimumCount` and rounds the rest to the nearest multiple of `roundingBase`, halves up. Exact zeros stay zero, and each total is transformed on its own, so totals need not equal the sum of visible cells.

Suppression does not keep a cell unknown. With minimum five and base five, two suppressed cells under a published total of ten must each be four. The minimum counts records, not people, so a cell can describe fewer subjects than the minimum. A suppressed cell at minimum two holds exactly one. A count below half the rounding base publishes as zero with status `rounded`. BReg applies no privacy budget across versions; dimensions, cadence, and readers remain your institution's disclosure decision.

## Publish an ended period

[Obtain publisher and reader tokens](../request-an-access-token/) into separate absolute,
owner-only files. The commands on this page use a dataset `monthly-discharge-reports`, published by
`statistics-publisher` and read by `statistics-reader`. BReg has no release scheduler; your own
scheduler or CI runs this command with a fresh token:

```sh test-skip="needs a live registry"
bregctl statistics publish \
  --breg-url "$BREG_URL" \
  --access-token-file "$PUBLISHER_TOKEN_FILE" \
  --dataset monthly-discharge-reports \
  --period 2025-01 \
  --status final \
  --profile statistics-publisher \
  --idempotency-key monthly-discharge-reports-2025-01-final-1
```

The response names the version, definition digest, content digest, and snapshot. Reuse the key to retry the same publication; choose a new key for a correction. A current or future period, or one before `firstPeriod`, is refused.

## Read a series

A reader names its profile with `accessProfile` and a period range. Ask for `text/csv` to receive `period`, `periodStart`, `periodEnd`, one column per dimension, `value`, and `status`:

```sh test-skip="needs a live registry"
bregctl api \
  '/v1/statistics/monthly-discharge-reports/releases:series?accessProfile=statistics-reader&from=2025-01&to=2025-03&status=final' \
  --url "$BREG_URL" \
  --token-file "$READER_TOKEN_FILE" \
  --accept text/csv
```

A suppressed value is blank, not zero; a period without a release has no cells.

## List and withdraw releases

`GET /v1/statistics/<dataset>/releases` lists version headers of the active definition, newest first, up to 100 a page (`$top`, `$skiptoken`), withdrawn versions included.

Withdrawal deletes a version's stored content but keeps its header and reason. It cannot recall a copy a reader already downloaded. The reason is `computation-error`, `source-data-error`, or `disclosure-risk`:

```sh test-skip="needs a live registry"
bregctl statistics withdraw \
  --breg-url "$BREG_URL" \
  --access-token-file "$PUBLISHER_TOKEN_FILE" \
  --dataset monthly-discharge-reports \
  --period 2025-01 \
  --version 1 \
  --reason computation-error \
  --profile statistics-publisher \
  --idempotency-key monthly-discharge-reports-2025-01-withdraw-1
```

A direct read of that version then returns 410 with the reason, and a latest read falls back to the previous eligible version. Every package installs the release store, and the runtime database role cannot update or delete it, so keep the separate migration credential.

If your institution publishes counts from a Base Registry Engine (BReg) registry to a dashboard, statistics office, or republisher, declare a statistical dataset and publish its ended periods. Release readers see small counts suppressed and the rest rounded, without permission on the records behind them.

## What a statistical dataset fixes

A statistical dataset counts the records of one Record type, its unit, that match a fixed population, per calendar period, grouped by a closed set of dimensions. The registry project declares all of this and PostgreSQL computes the counts. A consumer chooses periods and JSON or CSV, never SQL, a grouping, or the population, so every reader counts the same thing.

## Declare a dataset

The facility template declares none; add one under the root `statisticalDatasets` key of `registry.yaml`, with these members:

- `id`, and `unit`, the Record type whose records are counted
- `population`, a filter in the same `$filter` grammar as a list query, over that Record type's fields
- `period`, either `type: flow` with a date `field` that places each record in one period, or `type: stock` with a `validity` (`temporal`, or `from` and an optional `until` date field) that counts the records valid on the period's reference date
- `granularity` (`day`, `month`, `quarter`, or `year`) and `firstPeriod`, both inside `period`
- `dimensions`, boolean or vocabulary-code fields of the unit Record type
- `measures`, optional, a list tagged by `type`: `count`; `sum` with a `field`; `mean` with a `field` and a `scale` from 0 to 38; `distinct-count` with a `reference` `field`; `ratio` with a `numerator`, a `denominator`, and a `scale` from 0 to 38; `percentile` with a `field`, a `percentile` from 1 to 99, and a `scale` from 0 to 38. Omitting the list gives one count measure with the id `count`
- `disclosure`, tagged by a required `type`: `minimum-count-and-rounding` with `minimumCount` and `roundingBase`, each at least 2; or `exact-public-values` with no other member

One period, with every dimension code, every total, and every measure, must fit in 10,000 cells. A dataset declares at most 12 dimensions. A dimension cannot be named `measure`, which is a reserved column name. A sum, a mean, or a percentile needs an unencrypted `int64` or `decimal` field of the unit, and a distinct count an unencrypted `reference` field, each readable by every `read-live` profile. Every measure type is available on the exact paths: `read-live`, `read-exact`, and a release under `exact-public-values`. A release under `minimum-count-and-rounding` carries counts, distinct counts, and sums under the rules in [Release sums](#release-sums), which are held for review. A dataset with a mean, a ratio, or a percentile cannot be released under it (`breg.statistical-dataset.measure-release-unsupported`) and reads them live or exactly; a reader of a release who wants a mean divides a released sum by a released count:

```yaml
measures:
  - id: count
    type: count
  - id: amount_total
    type: sum
    field: amount
  - id: amount_mean
    type: mean
    field: amount
    scale: 2
```

A distinct count reports how many different values a `reference` field takes among a cell's records. On a parcel register, a count of parcels and the number of distinct owners:

```yaml
measures:
  - id: count
    type: count
  - id: owner_count
    type: distinct-count
    field: owner
```

Its `value` is a JSON integer, and an empty cell is 0. Records with no owner are left out. A field of any other type is refused with `breg.statistical-dataset.measure-field-type`, and two distinct counts over the same field with `breg.statistical-dataset.measure-distinct-count-duplicate`. A distinct count is not additive: one owner can hold parcels in two districts, so the distinct owners of two districts are not the sum of each district's distinct owners. A total is counted over the records, and a reader must not add distinct-count cells. Because totals are computed over the records, a dataset that declares a distinct count declares at most 4 dimensions (`breg.statistical-dataset.non-additive-dimensions`).

A ratio divides one measure by another: the share of irrigated area is a sum of irrigated hectares over a sum of total hectares, and hectares per owner is a sum over a distinct count. `numerator` and `denominator` name a `count`, `distinct-count`, or `sum` measure of the same dataset, and `scale` is required:

```yaml
measures:
  - id: area_total
    type: sum
    field: area
  - id: owner_count
    type: distinct-count
    field: owner
  - id: hectares_per_owner
    type: ratio
    numerator: area_total
    denominator: owner_count
    scale: 2
```

A ratio, a mean, a percentile, an unknown id, the ratio's own id, or the same measure on both sides is refused with `breg.statistical-dataset.ratio-operand`. The value is computed from the operands' exact values, never from their rounded text, and rounded half away from zero to `scale` digits. A denominator of zero gives no value and the status `not-applicable`. A total's ratio is the ratio of the totals, not the mean of the cells' ratios, because averaging ratios weights a small cell like a large one.

A percentile is the value below which the given share of a field's values fall. On the parcel register, the median parcel area is `percentile: 50`:

```yaml
measures:
  - id: area_median
    type: percentile
    field: area
    percentile: 50
    scale: 1
```

With the cell's n values sorted as x[1] to x[n] and q equal to `percentile` divided by 100, the value is (x[j] + x[j+1]) / 2 when n times q is a whole number j, and x[ceil(n q)] otherwise. This is the inverse of the empirical distribution function with averaging at discontinuities (Hyndman and Fan definition 2), so the median of 1, 2, 3, 4 is 2.5 and the median of 1, 2, 3 is 2. Records with no value for the field are left out, and the value is rounded half away from zero to `scale` digits. A cell with no values has no value and the status `not-applicable`. Spreadsheet and statistics-package defaults often use another definition (interpolation, Hyndman and Fan definition 7), so a value can differ from a spreadsheet's `PERCENTILE` on a small cell.

The field must be `int64` or `decimal` (`breg.statistical-dataset.measure-field-type`). It must be readable, not only filterable, by every `read-live` profile, by the publisher, and by the `exactReads` profile, and it must be classified `public` under `exact-public-values`, as for a sum or a mean. A percentile is not additive, since a total's percentile is computed over the records, so a dataset that declares one declares at most 4 dimensions (`breg.statistical-dataset.non-additive-dimensions`), as for a distinct count. Adding either measure changes the definition digest and starts a new release series.

A dataset's disclosure block names how its releases are protected:

```yaml
disclosure:
  type: minimum-count-and-rounding
  minimumCount: 5
  roundingBase: 5
```

The [configuration reference](../../reference/breg-configuration/#statistical-dataset-declarations) lists every member and the refusals `bregctl check` reports.

### Dimension codes

A dimension cell carries a code, not a label.
Boolean codes are `true` and `false`.
`_T` denotes a total, and `_U` denotes a null value when the field can be null; derived fields are
nullable for this purpose.
A vocabulary code beginning with `_` is reserved and refused.
A non-null value outside the declared vocabulary refuses the whole computation without disclosing
that value.

The names `period`, `periodStart`, `periodEnd`, `value`, and `status` are reserved for the document
and CSV representation, so a dimension cannot use one of them.

## Live counts and releases

A live value is computed on request from current data. It is exact, and filtered by the same rules as the profile's ordinary list query, so a live count is one the profile could already obtain by listing records. A live sum, mean, distinct count, ratio, or percentile is exact and can reveal one record's value in a small cell, so it is granted only to a profile that can read the records and the field, and it is not disclosure-controlled. Under `minimum-count-and-rounding`, releases carry counts, distinct counts, and sums.

A release is a stored, numbered version of one ended period, computed against one snapshot and transformed for disclosure. A final release can be corrected by a later final release, and a provisional release is refused once a final exists. Each release carries a definition digest of the population, sources, publisher visibility, dimensions, measures, and the disclosure method and its parameters. Changing who may read a dataset keeps the series; changing what it counts, adding a distinct count included, starts another one, and so does changing the disclosure method.

{/* Evidence: crates/registry-breg/src/postgres/statistics.rs;
    crates/registry-breg/src/compiler/statistics.rs, definition_digest. */}

Publication computes under one source snapshot and records the shared history head with that
computation.
The release's `snapshot` is an opaque bookmark when history coverage is available, or `null` after
erasure or another coverage invalidation.
Publication continues from current data without a history rebaseline, and a rebaseline can restore
bookmarks for later releases.
Persistence then verifies the same package activation, rechecks eligibility and freshness, and
allocates the next version.
BReg refuses a computation that a newer committed computation superseded.
Immediate Actions and ordinary mutations advance the same history head.

Versions increase monotonically per dataset and period, including across changed definitions.
Latest reads skip withdrawn versions, and `status=final` selects only final releases.
A version from another definition stays stored but is unavailable until that exact definition is
active again, because read eligibility uses the active definition digest.
The digest covers the unit, population, period, dimensions and codes, the definitions of referenced
fields and derived SQL inputs, publisher visibility on every source dependency, and the disclosure
parameters.
The `read-releases` and `read-live` grants and `firstPeriod` do not change it.

## Release sums

Released sums are held for review. The rules below are implemented and tested, but `bregctl check` refuses a `publish` or `read-releases` grant on a dataset that declares a sum under `minimum-count-and-rounding` (`breg.statistical-dataset.sum-release-held`) until a statistician has reviewed the rules and their implementation. Until then, serve sums through `read-live`, `read-exact`, or a release under `exact-public-values`.

A sum released under `minimum-count-and-rounding` needs a contributor, the party a value belongs to, and a dominance percentage:

```yaml
disclosure:
  type: minimum-count-and-rounding
  minimumCount: 5
  roundingBase: 5
  contributor:
    type: field
    field: owner
  dominancePercent: 15
```

`contributor` is `type: field` with a `reference` field of the unit, such as the owner of a parcel, or `type: each-record`, which states that every record is its own contributor. `dominancePercent` is an integer from 1 to 100. Both are required when a dataset that grants `publish` declares a sum, and refused otherwise; there are no defaults.

In brief, the rules apply in this order:

1. A cell with at least one and fewer than `minimumCount` contributors is suppressed. Five parcels owned by one farmer are a cell of one.
2. A sum is suppressed when the cell without its two largest contributors is smaller than `dominancePercent` percent of the largest (the p% rule). The second-largest contributor can estimate the largest by subtracting its own value from the total, and the rule bounds how close that estimate gets.
3. A suppressed sum suppresses the same measure in every total that contains it, so one small district can blank a national total. BReg does not choose extra cells to suppress.
4. A sum over an `int64` field is rounded to `roundingBase`; a sum over a `decimal` field is exact.
5. Values must not be negative: a summed `decimal` field declares a `minimum` of zero or more, and a publication is refused with `negative-value` when a value is negative.
6. Day periods are refused, a dataset declares at most 4 dimensions, and two datasets that release a sum of the same field over the same unit and population with nested dimensions are refused.

A suppressed cell has no value, and the document never says why. The release document states the `contributor`, `dominanceRule: p-percent`, and `sumTotals`, but never `dominancePercent`, which is also left out of the definition digest. Changing the contributor starts a new release series; changing the percentage does not. The [configuration reference](../../reference/breg-configuration/#statistical-dataset-declarations) lists every member and refusal code.

A release is immutable, so dry-run a publication to see which cells and totals will be blank before you publish. The publisher sends the publication's body to `POST /v1/statistics/<dataset>/releases/<period>/versions:dry-run`, with no `Idempotency-Key`. The response is the release document a publication made at that moment would store, with its next version number, and `suppressions`: for each suppressed cell, its index in `document.cells` and the reason (`minimum-count`, `minimum-contributors`, `dominance`, or `contains-suppressed-sum`; the list of reasons may grow). A dry run stores nothing, reserves no version, and writes one audit entry. The clients offer `statistics_release_dry_run` (Rust and Python) and `statisticsReleaseDryRun` (Node.js).

## Decide who reads a dataset

Each [access profile](../../reference/glossary/#access-profile) that reaches it says so under `permissions.datasets`, beside its record permissions under `permissions.records`. A dataset permission holds `dataset` and `operations`, drawn from four operations:

- `read-live`, exact live values
- `publish`, publishing and withdrawing releases
- `read-releases`, released documents
- `read-exact`, exact values for ended periods, for a named consumer

One profile at most holds `publish` on a dataset. Give it to a profile a person or a service uses directly: a standing agent profile, one with `actorKind: agent` and no `taskGrant`, cannot publish or withdraw a release, and `bregctl check` refuses the project with `breg.access-profile.standing-agent-publish-forbidden`. [Control access](../breg-access/) explains task grants.

A publisher and every `read-live` profile also need a count-capable list permission on the unit. A publisher's visibility must not depend on the caller, because the same dataset would otherwise count a different population for each caller. A profile that holds only `read-releases` needs no record permission. The configuration reference carries the full set of rules. Run `bregctl explain access` to see, for each dataset, which profiles hold each operation.

### Rules the compiler enforces

`bregctl check` refuses a project that breaks one of these rules:

- A dataset needs at least one grant (`breg.statistical-dataset.grants-empty`).
- A profile names a dataset in at most one permission, and a permission on a dataset the project does
  not declare is refused (`breg.access-profile.permission-dataset-unknown`).
- At most one profile holds `publish` on a dataset (`breg.statistical-dataset.publisher-multiple`).
- When a dataset has a publisher, the publisher and every `read-live` profile must also hold
  `read-releases` (`breg.statistical-dataset.read-releases-required`), because release reads
  authorise the publisher, every `read-live` profile, and every other `read-releases` profile.
- `read-releases` on a dataset nobody publishes is refused
  (`breg.statistical-dataset.publisher-missing`).

Every dataset profile is authenticated, and you choose one profile per request with
`accessProfile`.
BReg never combines profiles into a larger grant.
`/v1/registry` and `/openapi.json` filter dataset operations with the same authorisation checks, and
a release-only reader receives no Record type grant.

The statistical query uses the same list predicates, forced row security, visibility checks, and

A publisher's population must not depend on the caller.

## Periods and evaluation dates

Granularities are day, month, quarter, and year, using UTC calendar periods.
The period codes are `YYYY-MM-DD`, `YYYY-MM`, `YYYY-Qn`, and `YYYY`.
A range uses positive four-digit years, and each period's exclusive end must also fit that date
range: `9999-11` is valid and `9999-12` is refused.
A range includes both named periods and contains at most 366 periods.
A response contains at most 10,000 cells, including totals and zero-filled domain combinations.

A flow counts the unit's rows whose date field falls in `[start, end)`.
A stock counts the rows valid on the period's reference date.
A stock names its validity in one of two ways:

```yaml
period:
  type: stock
  granularity: month
  firstPeriod: 2025-01
  validity: temporal
```

`validity: temporal` uses the Record type's temporal declaration.
Alternatively, `validity` names the date fields with `from` and `until`.
The interval is `[from, until)`, and a null end means open-ended.
When `until` names the unit's `lastDayField`, the interval runs through that last day inclusive, as
it does under `validity: temporal`.
An ended period's reference date is its final day.
The current period uses today's date in the registry's time zone, which a project with a
statistical dataset must declare; [History reads](../../reference/breg-api/#history-reads)
describes `project.timezone`.
Publication requires an ended period at or after `firstPeriod`.

## Serve exact values to a named consumer

A policy-simulation or costing service sometimes needs exact statistics over records it cannot read. `read-exact` serves counts, sums, means, distinct counts, ratios, percentiles, and cells of one for ended periods to a profile that holds the grant, and the profile needs no record access. The dataset declares the visibility the read computes under with `exactReads`, and the consumer's profile holds only `read-exact`:

```yaml
statisticalDatasets:
  - id: monthly-discharge-reports
    unit: discharge-report
    population: "substanceCode ne null"
    period:
      type: flow
      field: period-start
      granularity: month
      firstPeriod: 2025-01
    dimensions:
      - administrative-boundary
    measures:
      - id: count
        type: count
      - id: amount_total
        type: sum
        field: amount
    disclosure:
      type: minimum-count-and-rounding
      minimumCount: 5
      roundingBase: 5
    exactReads:
      accessProfile: statistics-scope
accessProfiles:
  - id: costing-service
    permissions:
      datasets:
        - dataset: monthly-discharge-reports
          operations:
            - read-exact
```

The `statistics-scope` profile must see the same records whoever calls. `bregctl check` refuses it if its visibility depends on the caller (row or membership boundaries, required purposes or consent, or no read access to a record type the dataset depends on), if its `list` grant does not cover what the dataset filters and groups by, or if it cannot read a sum, mean, percentile, or distinct-count field. A `read-exact` grant without `exactReads` is refused with `breg.statistical-dataset.exact-reads-missing`, `exactReads` without a `read-exact` grant with `breg.statistical-dataset.exact-reads-unused`, and an unknown profile with `breg.statistical-dataset.exact-reads-profile-unknown`. A standing agent profile cannot hold `read-exact` or be the `exactReads` profile. The grant works under either disclosure method and needs no publisher, so the sum above, whose release under `minimum-count-and-rounding` is held for review, is still served exactly.

The consumer reads one range of ended periods. Both `from` and `to` are required, because the current period has not ended. A dataset that depends on the evaluation date accepts one period per request:

```sh test-skip="needs a live registry"
bregctl api \
  '/v1/statistics/monthly-discharge-reports:exact?accessProfile=costing-service&from=2025-01&to=2025-03' \
  --url "$BREG_URL" \
  --token-file "$CONSUMER_TOKEN_FILE"
```

The document carries `exact`, with `evaluatedAt` and the caller's `accessProfile`, in place of `live`; statuses are `exact` and `not-applicable`. Each read is audited with the caller's profile and the requested range.

The output is as sensitive as the records. It discloses cells of one and exact sums, and BReg cannot control what the consumer does with it. Grant `read-exact` to one named service under a data-sharing agreement that names the legal basis, the purpose, no onward disclosure, what the consumer may publish from its results, retention, and breach notice. Widening the `exactReads` profile's `list` grant widens every exact read, so review a change to that profile as a disclosure decision.

## Review what a release discloses

A release is disclosed under the method the dataset's `disclosure.type` names.

### Minimum count and rounding

A release under `minimum-count-and-rounding` suppresses positive counts below `minimumCount` and rounds the rest to the nearest multiple of `roundingBase`, halves up. Exact zeros stay zero, and each total is transformed on its own, so totals need not equal the sum of visible cells. A distinct-count cell is transformed on its own value, independently of the record count of the same cell, so a cell can show 10 parcels and a suppressed number of owners. A released sum follows the rules in [Release sums](#release-sums).

Suppression does not keep a cell unknown. With minimum five and base five, two suppressed cells under a published total of ten must each be four. The minimum counts records, not people, so a cell can describe fewer subjects than the minimum. A suppressed cell at minimum two holds exactly one. A count below half the rounding base publishes as zero with status `rounded`. BReg applies no privacy budget across versions; dimensions, cadence, and readers remain your institution's disclosure decision.

Live data contains exact values for the selected profile.
For every base cell and every margin, an exact zero stays zero with status `exact`, a positive count
below `minimumCount` becomes null with status `suppressed`, and every other count rounds to the
nearest multiple of `roundingBase` with status `rounded`, including a rounded zero.
True counts exist only during computation; release storage keeps the transformed document, its
digest, and lifecycle metadata.

The compiler checks only that each parameter is at least two.
Three limits stay with the dataset's author:

- `minimumCount` is a threshold on unit rows, not on distinct people or organisations.
  Where one subject can hold several unit rows, a published cell can describe fewer subjects than
  the threshold.
- A suppressed cell holds one through `minimumCount` minus one. At the floor of two, `suppressed`
  means exactly one.
- The two parameters are not checked against each other.
  A count from `minimumCount` up to, but not including, half of `roundingBase` publishes as zero
  with status `rounded`, which its status tells apart from an exact zero.
  With minimum two and base five, a rounded zero is exactly two.
  A `roundingBase` of at most twice `minimumCount` produces no rounded zero.

Seven positive suppressed cells under a rounded total of five pin every cell to one.
Deterministic rounding also permits differencing between releases or overlapping populations, and
exact zeros disclose absence and can disclose group attributes.
Review each dataset's population, dimensions, release cadence, and auxiliary information before you
grant readers access.

### Exact public values

A register of public facts, such as licensed facilities or registered cooperatives, has nothing to protect, and suppression only makes its figures wrong. Declare `type: exact-public-values` and a release carries the exact value of every measure (counts, sums, means, distinct counts, ratios, and percentiles), with no suppression and no rounding:

```yaml
disclosure:
  type: exact-public-values
```

The dataset compiles only when the unit Record type, every field the dataset reads (population, period, dimension, and measure fields), and every source Record type of a derived field it reads are classified `public`. Otherwise `bregctl check` refuses with `breg.statistical-dataset.exact-release-not-public`, one diagnostic per item to reclassify. The Record type's own classification counts because membership of a register is itself disclosed: an exact count of one says a record exists. A derived field's source Record types count because a derived field labelled `public` can read restricted inputs. Reclassifying is a visible, reviewable act; there is deliberately no switch that turns protection off without it.

The publisher rules do not change. Under `exact-public-values` the publisher must also be able to read each sum, mean, percentile, or distinct-count field.

BReg checks the classification labels, not whether the data is in fact public. A Record type or field wrongly classified `public` is released exactly, including cells of one, and readers can copy the immutable release; withdrawal erases only the engine's stored content. Review a classification change as a disclosure decision, and keep `minimum-count-and-rounding` for any register whose membership is not public.

## Publish an ended period

[Obtain publisher and reader tokens](../request-an-access-token/) into separate absolute,
owner-only files. The commands on this page use a dataset `monthly-discharge-reports`, published by
`statistics-publisher` and read by `statistics-reader`. BReg has no release scheduler; your own
scheduler or CI runs this command with a fresh token:

```sh test-skip="needs a live registry"
bregctl statistics publish \
  --breg-url "$BREG_URL" \
  --access-token-file "$PUBLISHER_TOKEN_FILE" \
  --dataset monthly-discharge-reports \
  --period 2025-01 \
  --status final \
  --profile statistics-publisher \
  --idempotency-key monthly-discharge-reports-2025-01-final-1
```

The response names the version, definition digest, content digest, and snapshot. Reuse the key to retry the same publication; choose a new key for a correction. A current or future period, or one before `firstPeriod`, is refused.

Publication and withdrawal require an `Idempotency-Key`, scoped to the caller like every BReg
mutation key.
An identical retry under the same current authority returns the retained status, headers, and body
without creating another version, for `retention.receiptRetentionDays` after the first commit.
After that the retry returns `410 idempotency.expired` and creates nothing.
Binding the key to a different request returns `409 idempotency.key-reused`.

## Read a series

A reader names its profile with `accessProfile` and a period range. Ask for `text/csv` to receive `period`, `periodStart`, `periodEnd`, one column per dimension, `measure`, `value`, and `status`:

```sh test-skip="needs a live registry"
bregctl api \
  '/v1/statistics/monthly-discharge-reports/releases:series?accessProfile=statistics-reader&from=2025-01&to=2025-03&status=final' \
  --url "$BREG_URL" \
  --token-file "$READER_TOKEN_FILE" \
  --accept text/csv
```

A suppressed value is blank, not zero; a period without a release has no cells. A JSON document lists the declared measures in `dataset.measures`, and each cell names its measure in `measure`, with one cell per period, dimension combination, and measure.

A mean, a ratio, or a percentile is read live or exactly, or in a release under `exact-public-values`; a sum is too, or in a release under `minimum-count-and-rounding` once its rules are reviewed. A sum's, a mean's, a ratio's, and a percentile's `value` is a decimal string such as `"1234.50"`, not a JSON number, with exactly the measure's `scale` digits after the point; a count stays an integer. A mean or a percentile over no values, and a ratio with a zero denominator, has a null `value` and the status `not-applicable`. A release under `minimum-count-and-rounding` uses `exact`, `suppressed`, and `rounded`, and a suppressed sum has no value; one under `exact-public-values` uses `exact` and `not-applicable` only. The status vocabulary can grow, so treat an unknown status as no usable value.

## List and withdraw releases

`GET /v1/statistics/<dataset>/releases` lists version headers of the active definition, newest first, up to 100 a page (`$top`, `$skiptoken`), withdrawn versions included.

Withdrawal deletes a version's stored content but keeps its header and reason. It cannot recall a copy a reader already downloaded. The reason is `computation-error`, `source-data-error`, or `disclosure-risk`:

```sh test-skip="needs a live registry"
bregctl statistics withdraw \
  --breg-url "$BREG_URL" \
  --access-token-file "$PUBLISHER_TOKEN_FILE" \
  --dataset monthly-discharge-reports \
  --period 2025-01 \
  --version 1 \
  --reason computation-error \
  --profile statistics-publisher \
  --idempotency-key monthly-discharge-reports-2025-01-withdraw-1
```

A direct read of that version then returns 410 with the reason, and a latest read falls back to the previous eligible version. Every package installs the release store, and the runtime database role cannot update or delete it, so keep the separate migration credential.

The database records the withdrawal and deletes the content in one fixed PostgreSQL function, and
the immutable version header remains.
A direct read of the withdrawn version returns `410 statistical_dataset.version_withdrawn` with the
reason code.
A second withdrawal is refused, and an identical idempotent retry returns its original response.

A withdrawn header omits `contentDigest` in the withdrawal response, in its audit entry, and in every
later listing.
The digest is an unsalted hash of a document whose members other than the cells can be derived from
the header and the dataset metadata, so serving it would let a reader confirm guessed cell values
offline after the content is gone.
The stored header row and the publication's own audit entry keep the digest for operators, and an
identical retry of the publication returns the response the publisher first received.

## Representations

Live and series reads use `from` and `to`, and a series requires both.
Latest and series reads accept `status=final`.
Header listing accepts `$top` from one through 100 and an opaque `$skiptoken`.
The cursor binds the activation, dataset definition, selected profile, principal, purpose, and page
size, so reauthorise before you open it.
Listings order periods newest first, then versions newest first, and a consumer should tolerate
concurrent publications while paging.

A document contains `dataset`, `periods`, `dimensions`, and `cells`, plus `live` or `release`
metadata, and a released document also describes `disclosure`.
A cell contains `period`, its dimension codes, `value`, and `status`.
A released series represents missing periods explicitly and does not invent cells for them.

An absent or unmatched `Accept` header selects JSON.
Use `Accept: application/json` or `Accept: text/csv` for live, latest, version, and series reads.
CSV follows RFC 4180 quoting with these columns:

```text
period,periodStart,periodEnd,<dimension field IDs...>,value,status
```

Suppressed values are blank in CSV.
Plot `periodStart` against `value`, filter dimension codes before plotting, and keep `status` so a
blank cell cannot be mistaken for zero.
Release listings and mutation responses are JSON.

Stored JSON is canonicalised with RFC 8785 and hashed with SHA-256.
`Repr-Digest` uses RFC 9530 syntax and hashes the exact response bytes, so a CSV digest differs from
its JSON digest.
Responses send `Cache-Control: no-store` and `Vary: authorization, accept`, without a strong `ETag`.
[Statistical dataset routes](../../reference/breg-api/#statistical-datasets) lists the routes.

## Operate statistical releases

Release tables are engine-owned and installed in every package.
The runtime can insert and select headers and content and select withdrawals, but it cannot update
or delete those tables.
Only the migration-owned withdrawal function can delete content, while it records the withdrawal.
Catalog verification covers that function's owner, body, language, volatility, privileges, and fixed
search path.

{/* Evidence: crates/registry-breg/tests/postgres_statistics.rs
    statistics_store_has_exact_runtime_acl_and_withdrawal_function_shape,
    statistics_catalog_refuses_extra_grants_and_withdrawal_function_tampering. */}

Every protected request has an audit attempt before database I/O and an accepted terminal entry
before bytes are returned.
A publication or withdrawal whose commit fails, or whose deadline passes while the commit is in
flight, has no proven outcome.
It returns `503 source.unavailable` and appends no terminal entry, so its attempt is answered
`unfinished`, never `refused`.
Retry with the same `Idempotency-Key`: a write that did commit returns its retained response.
Audit entries contain keyed references and lifecycle metadata, never cell values or unit counts.
Aggregate reads add no individual subject access-log hits.

A computation consumes the HTTP request deadline, including pool acquisition, locks, the grouped
statement, and persistence.
The statement budget is capped at 30 seconds.
BReg has no release cache and no background scheduler: schedule the publish command from your
institution's cron or CI with a token file.
A dashboard reader needs an OAuth client that can satisfy the deployed issuer and the selected
profile, so verify that authentication journey for your dashboard connector before you configure it.

It does not implement the full SDMX REST API or a JSON-stat representation.

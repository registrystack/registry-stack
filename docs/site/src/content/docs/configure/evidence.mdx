If you are preparing an Evidence Gateway deployment, validate the authored project, its environment
bindings and complete grants together before you create a candidate.
Use matching `evidence` and `evidencectl` binaries and start from the project you completed in
[your first assertion](../../tutorials/first-evidence-assertion/).

## Edit the owning document

Keep reusable meaning in `evidence.yaml`: AssertionDefinitions, named Sources and Functions,
selector profiles, Outputs and package grant ceilings.
Keep environment bindings in the selected target: service identity, authentication, Source
connections, signer, secret references, listener, audit destination and operational limits.
Keep complete access profiles and grants in the target's separate authority document.
A local client registration names existing access profiles; registration grants no authority by itself.

Use the [authoring reference](../../products/registry-evidence/authoring-form/) for how these fields
fit together and the [configuration reference](../../reference/evidence-configuration/) for exact
keys, variants and constraints.
Editor diagnostics and `evidencectl` use the same normalized model.
A schema-valid document still needs reference, interface, grant and runtime validation.

## Check the selected target

From your authored project, run:

```sh
evidencectl check . --target local-target.yaml --deny-warnings
evidencectl explain . --target local-target.yaml
```

A target argument may name a YAML file or a directory containing `target.yaml`.
Explain reports definition revisions, Function interfaces and call sites, resource ceilings and
effective complete grants without resolving secrets or reading Source values.
If check names a missing local deployment input, provision the reviewed public key before claiming
deployment closure.
For a production or evidence-grade target, require that closure explicitly:

```sh
evidencectl check . --target "<production-target>" --production --deny-warnings
```

Production check refuses a missing governed public signing key before runtime delegation.
Offline closure does not prove target-host secret paths or live dependency readiness.
Correct a refused file or field using its diagnostic, then rerun check.
Do not weaken an assurance profile or a grant to make validation succeed.

## Run authored fixtures

Add or update synthetic fixtures for each changed AssertionDefinition, then run:

```sh
evidencectl test . --target local-target.yaml --explain
```

This delegates evaluation to the actual Evidence fixture kernel.
A Source suggestion alone is not a complete definition or an authored fixture.
The SQLite starter supports offline fixture evaluation; local `dev start` refuses SQLite serving.
Use the same declared Source and complete grants when you bind a published extract for deployment.

## Create and preflight the candidate

Write a candidate outside the authored project, into a directory that does not exist:

```sh
evidencectl package . --target "<deployment-target>" --output ../evidence-candidate
```

The candidate contains the immutable `bundle/`, process-local `runtime.yaml` and
`compiled-authority.yaml`.
One captured project snapshot supplies all candidate artifacts, and the runtime validates compiled
authority even when no fixtures exist.
Install the bundle at the emitted runtime's package path, provision its referenced secrets, activate
the compiled authority and run `evidencectl doctor --runtime-config <absolute-file>` before serving.
The [Evidence product page](../../products/registry-evidence/) links to the runnable standalone
project with synthetic data and cleanup.

Authority activation has its own revision, digest and durable history.
Restart the intended process to adopt a successor authority snapshot; ongoing requests keep their
resolved snapshot and remain subject to live task-grant validity and release-audit checks.
An assertion proves only its declared claims and bindings, not downstream write or review authority.

If you are writing the policy a Registry Casework deployment will run, you edit a project
directory and check it offline, with no database and no network. You continue in
`tutorial-work/casework`, the project from
[Decide your first ReviewRequest](../../tutorials/first-casework/), with its development session
still running.

## Read the project files

`casework.yaml` is the policy. `dev-clients.yaml` names the local callers and teams for
`caseworkctl dev`, `fixtures/` holds the cases `test` proves, and `runtime.example.yaml` is a
starting runtime configuration for a deployment. `.casework/schemas/` holds the JSON Schemas your
editor reads through each file's first-line comment. Check the project as it stands:

```sh test-cwd="tutorial-work/casework"
caseworkctl check .
```

```json test-excerpt
{
  "filesChecked": 3,
  "policyBindings": [
    {"digest": "sha256:<digest>", "id": "decision", "version": "1"}
  ]
}
```

Check reads `casework.yaml`, `dev-clients.yaml`, the development session's state file while one
exists, and any `holiday-sets/`, and prints one binding for each
[ReviewPolicy](../../reference/glossary/#review-policy). When a file is wrong, it prints a refusal
with a code such as `casework.review-policy.unknown-queue`, the file, line, and JSON pointer, and
the next step to take.

## Name the queue for its reviewers

Each [access profile](../../reference/glossary/#access-profile) admits a token that carries its `requiredScopes`, takes the caller's identity
from `principalClaim`, and gives the caller one role: `staff`, `supervisor`, `administrator`, or
`requester`. The project declares one of each:

```yaml title="casework.yaml" test-excerpt="casework.yaml"
accessProfiles:
  staff:
    principalClaim: sub
    requiredScopes: [casework:staff]
    role: staff
```

A [queue](../../reference/glossary/#queue) is where a stage's ReviewTasks wait. Its label is what
reviewers see, so give it the name your team uses:

```diff test-edit title="casework.yaml"
 queues:
   decisions:
-    label: Decisions awaiting review
+    label: Licence decisions
```

Labels are excluded from the policy digest, so `check` still prints the same binding.

## Read the review policy and its producer

```yaml title="casework.yaml" test-excerpt="casework.yaml"
reviewPolicies:
  decision:
    version: "1"
    purpose: answer
    context: {mode: submitted}
    stages:
      - id: answer
        queue: decisions
        decidingProfiles: [staff]
        requiredApprovals: 1
```

A ReviewPolicy fixes the purpose, the stages in order, the profiles that decide each stage, the
`displaySchema` reviewers see, and the outcomes a decision may record. Each outcome sets its
`settlement`, whether a reason is required, and whether a public reason is `required`,
`optional`, or `none`. A larger policy adds `routing` rules that send a task to another queue by its
fields, and `teams` that state which profiles a queue's staff must hold.

For an approval policy, you can start with `caseworkctl init --template
single-reviewer-approval`, `two-peer-approval`, or
`technical-check-then-authorization`. The two-peer pattern supplies two local people on one
Staff profile. The technical pattern gives its first stage `negativeDecisions: advise`:
each completed decision counts toward its threshold, including a rejection or request for
changes, then a separate authorizer decides. The default, `settle`, retains the immediate
negative veto. An advisory stage must have a later stage; `check` refuses an advisory final
stage. `explain` reports the effective mode.

Earlier advisory reasons remain available to authorized reviewers in decision history.
The producer receives only the settling outcome and its public reason. All three patterns
exclude the initiator; the technical pattern also excludes earlier reviewers from authorization.

{/* Evidence: crates/registry-caseworkctl/src/templates.rs, approval_project;
    crates/registry-casework-core/src/review.rs, ReviewNegativeDecisionMode and record_review_decision;
    crates/registry-caseworkctl/src/report.rs, ExplainStage. */}

`context: {mode: submitted}` reviews the snapshot the producer sent. A policy whose reviewers
must see the source's current record sets `mode: current-source` and names a
[context provider](../../reference/glossary/#context-provider), as
[Review a Proposal in Casework](../../tutorials/review-breg-changes-in-casework/) does.
`trustedProducers` names each calling system: its access profile, issuer, subject, source
namespaces, and the policies it may request.

The digest covers the policy's behavior and everything it depends on: stages, context, outcomes,
access profiles, queues, teams, producers, and the clocks and calendars it uses. A producer that
names only the policy ID is bound to the active version and digest when Casework accepts its
request. A producer that pins `version` and `digest` is refused with `review.policy-mismatch` once
the active digest changes.

{/* Evidence: crates/registry-casework-core/src/review.rs, digest_with();

## Give the stage a deadline

A [clock](../../reference/glossary/#clock) measures a deadline, and a stage clock counts working
days on a [calendar](../../reference/glossary/#calendar). Add a calendar and a five-day review
deadline to the end of `casework.yaml`:

```yaml title="casework.yaml" test-append
calendars:
  office:
    timezone: Asia/Bangkok
    workingWeekdays: [monday, tuesday, wednesday, thursday, friday]
    holidaySet: office-holidays
clocks:
  review-deadline:
    type: stage
    anchor: {type: stage-entered}
    calendar: office
    after: {workingDays: 5}
    dueTime: "17:00"
    atRisk: {before: {workingDays: 1}}
    reminders: {due-soon: {before: {workingDays: 1}}}
```

The task is due at 17:00 Bangkok time on the fifth working day after it enters the stage, and is
at risk one working day before. A clock may also carry `steps` that move a due task to another
queue; it never decides an outcome. Attach the clock to the policy:

```diff test-edit title="casework.yaml"
         requiredApprovals: 1
+    clocks: [review-deadline]
     retention:
```

The calendar's working days exclude the dates of its holiday set. Write one revision of it, so
`check` validates it with the project:

```sh
mkdir -p holiday-sets
```

```yaml title="holiday-sets/office-holidays-7.yaml" test-file
apiVersion: id.registrystack.org/formats/casework/holiday-set/v1alpha1
kind: CaseworkHolidaySet
holidaySet: office-holidays
revision: 7
dates: [2026-09-07]
```

Check the project and prove its fixture again. The clock changed the policy's behavior, so its
digest changes:

```sh
caseworkctl check .
caseworkctl test .
```

```json test-excerpt
{
  "filesChecked": 4,
  "policyBindings": [
    {"digest": "sha256:<digest>", "id": "decision", "version": "1"}
  ]
}
```

```json test-excerpt
{"proofBoundary": "offline-synthetic", "productionClosure": false}
```

`offline-synthetic` means no PostgreSQL and no runtime decision took part.

## Generate types and plan the package

A producer's client code is written against typed bindings: the policy bindings and the
TypeScript and Python types for its requests, tasks, and results. Generate them outside the
project and hand them to the producer's developers:

```sh
caseworkctl types . --output ../casework-types
```

```json test-excerpt
{
  "files": ["casework.ts", "casework.py", "contexts.schema.json"],
  "output": "../casework-types"
}
```

Then plan the [policy package](../../reference/glossary/#policy-package) without writing it:

```sh
caseworkctl package . --dry-run
```

```json test-excerpt
{
  "dryRun": true,
  "files": ["casework.yaml"],
  "packageDigest": "sha256:<digest>"
}
```

The [package digest](../../reference/glossary/#package-digest) covers the bytes of every packaged
file, so any edit changes it. The holiday set is not packaged: an administrator publishes its
revisions to the running service, and until one is published the stage clock cannot compute a due
time. [Deploy Registry Casework](../../operate/casework/) activates the package.

{/* Evidence: crates/registry-caseworkctl/src/project_types.rs, generate();
    crates/registry-caseworkctl/src/project.rs, package_dry_run();

## Restart the session on the edited project

The running session serves the package it built when it started, and it refuses to restart on
edited files while it holds records, so discard it and start a fresh one. This deletes the
ReviewRequest you decided earlier and the session's credentials:

```sh
caseworkctl dev stop --remove
caseworkctl dev start
```

```json test-excerpt
{"status": "complete", "outcome": "stopped", "directory": {"revision": 0, "teams": 0}}
```

```json test-excerpt
{"status": "complete", "outcome": "ready", "directory": {"revision": 1, "teams": 1}}
```

The session keeps its ports. Its tokens are new, so run `caseworkctl dev token` again before your
next call. Leave it running.

{/* Evidence: crates/registry-caseworkctl/src/dev/mod.rs, start, stop, InputsChanged. */}

## Enable a delegated staff reader

A separately operated assistant can list its represented staff member's assigned
ReviewTasks and read context through the default-off delegated-reader routes.
Enable a named `authentication.delegatedStaffReaders` policy in the Casework
runtime, admitting the exact gateway, represented Staff profile, read scope,
assertion issuer and short token lifetime. The source-built `registry-mcp`
service selects that policy through `readerPolicy`.

Casework checks the current holder and assignment before release. These
credentials do not admit ordinary producer, decision or administration routes.
Submitted context uses the retained task material. Current-source context also
needs an admitted source profile and `delegatedDisplayExchange` on its provider;
Casework exchanges to the source resource rather than forwarding its own bearer.
The institution must approve the source agent profile's disclosure ceiling.
That service profile does not automatically inherit the staff member's human
Base Registry Engine (BReg) permissions.

Follow [the staff configuration example](https://github.com/registrystack/registry-stack/blob/main/products/platform/examples/mcp-runtime/README.md)
for settings that must match and issuer requirements. `registry-mcp` is currently
source-build-only. Its native drill uses a synthetic issuer, so check your IdP's
exchange support before enabling the policy.

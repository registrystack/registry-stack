If you are writing the policy a Registry Casework deployment will run, you edit a project
directory and check it offline, with no database and no network. You continue in
`tutorial-work/casework`, the project from
[Decide your first ReviewRequest](../../tutorials/first-casework/), with its `rstack dev` run
still going.

## Read the project files

`casework.yaml` is the policy. `dev.yaml` and `tests/scenarios.yaml`, which you wrote in the
tutorial, describe the local run for `rstack dev`. `fixtures/` holds the cases `test` proves, and
`runtime.example.yaml` is a starting runtime configuration for a deployment. `.casework/schemas/` holds the JSON Schemas your
editor reads through each file's first-line comment. Check the project as it stands:

```sh test-cwd="tutorial-work/casework"
caseworkctl check .
```

```json test-excerpt
{
  "filesChecked": 1,
  "policyBindings": [
    {"digest": "sha256:<digest>", "id": "decision", "version": "1"}
  ]
}
```

Check reads the project's configuration files and any `holiday-sets/`, and prints one binding for each
[ReviewPolicy](../../reference/glossary/#review-policy). When a file is wrong, it prints a refusal
with a code such as `casework.review-policy.unknown-queue`, the file, line, and JSON pointer, and
the next step to take.

## Name the queue for its reviewers

Each [access profile](../../reference/glossary/#access-profile) admits a token that carries its `requiredScopes`, takes the caller's identity
from `principalClaim`, and gives the caller one `actsAs` value: `staff`, `supervisor`, `administrator`, or
`requester`. You configure trusted issuers under `authentication.oidc.issuers.<id>`. Every profile
a person uses must name the same `principalClaim` across the issuer set. Otherwise one person
would appear as two principals and Casework refuses the project with `casework.access-profile.mixed-principal-claims`. Profiles a trusted producer uses are
services and share one claim among themselves, which may differ from the people's. The project
declares one of each:

```yaml title="casework.yaml" test-excerpt="casework.yaml"
accessProfiles:
  staff:
    principalClaim: sub
    requiredScopes: [casework:staff]
    actsAs: staff
```

A [queue](../../reference/glossary/#queue) is where a stage's ReviewTasks wait. Its label is what
reviewers see, so give it the name your team uses:

```diff test-edit title="casework.yaml"
 queues:
   decisions:
-    label: Decisions awaiting review
+    label: Licence decisions
```

Labels are excluded from the policy digest, so `check` still prints the same binding.

## Read the review policy and its producer

```yaml title="casework.yaml" test-excerpt="casework.yaml"
reviewPolicies:
  decision:
    version: "1"
    purpose: answer
    context: {mode: submitted}
    stages:
      - id: answer
        queue: decisions
        decidingProfiles: [staff]
        requiredApprovals: 1
```

A ReviewPolicy fixes the purpose, the stages in order, the profiles that decide each stage, the
`displaySchema` reviewers see, and the outcomes a decision may record. Each outcome sets its
`settlement`, whether a reason is required, and whether a public reason is `required`,
`optional`, or `none`. A larger policy adds `routing` rules that send a task to another queue by its
fields, and `teams` that state which profiles a queue's staff must hold.

For an approval policy, you can start with `caseworkctl init --template
single-reviewer-approval`, `two-peer-approval`, or
`technical-check-then-authorization`. The two-peer pattern supplies two local people on one
Staff profile. The technical pattern gives its first stage `negativeDecisions: advise`:
each completed decision counts toward its threshold, including a rejection or request for
changes, then a separate authoriser decides. The default, `settle`, retains the immediate
negative veto. An advisory stage must have a later stage; `check` refuses an advisory final
stage. `explain` reports the effective mode.

Earlier advisory reasons remain available to authorised reviewers in decision history.
The producer receives only the settling outcome and its public reason. All three patterns
exclude the initiator; the technical pattern also excludes earlier reviewers from authorisation.

{/* Evidence: crates/registry-caseworkctl/src/templates.rs, approval_project;
    crates/registry-casework-core/src/review.rs, ReviewNegativeDecisionMode and record_review_decision;
    crates/registry-caseworkctl/src/report.rs, ExplainStage. */}

`context: {mode: submitted}` reviews the snapshot the producer sent. A policy whose reviewers
must see the source's current record sets `mode: current-source` and names a
[context provider](../../reference/glossary/#context-provider), as
[Review a Proposal in Casework](../../tutorials/review-breg-changes-in-casework/) does.
`trustedProducers` names each calling system: its access profile, issuer, subject, source
namespaces, and the policies it may request.

The digest covers the policy's behaviour and everything it depends on: stages, context, outcomes,
access profiles, queues, teams, producers, and the clocks and calendars it uses. A producer that
names only the policy ID is bound to the active version and digest when Casework accepts its
request. A producer that pins `version` and `digest` is refused with `review.policy-mismatch` once
the active digest changes.

## Give the stage a deadline

A [clock](../../reference/glossary/#clock) measures a deadline. A stage clock counts working
days on a [calendar](../../reference/glossary/#calendar). A subject clock counts elapsed minutes,
hours or days. Add a calendar and a five-day review
deadline to the end of `casework.yaml`:

```yaml title="casework.yaml" test-append
calendars:
  office:
    timezone: Asia/Bangkok
    workingWeekdays: [monday, tuesday, wednesday, thursday, friday]
    holidaySet: office-holidays
clocks:
  review-deadline:
    type: stage
    anchor: {type: stage-entered}
    calendar: office
    after: {workingDays: 5}
    dueTime: "17:00"
    atRisk: {before: {workingDays: 1}}
    reminders: {due-soon: {before: {workingDays: 1}}}
```

The task is due at 17:00 Bangkok time on the fifth working day after it enters the stage, and is
at risk one working day before. A clock may also carry `steps` that move a due task to another
queue; it never decides an outcome. Attach the clock to the policy:

```diff test-edit title="casework.yaml"
         requiredApprovals: 1
+    clocks: [review-deadline]
     retention:
```

The calendar's working days exclude the dates of its holiday set. Write one revision of it, so
`check` validates it with the project:

```sh
mkdir -p holiday-sets
```

```yaml title="holiday-sets/office-holidays-7.yaml" test-file
apiVersion: id.registrystack.org/formats/casework/holiday-set/v1alpha1
kind: CaseworkHolidaySet
id: office-holidays
revision: 7
dates: [2026-09-07]
```

Check the project and prove its fixture again. The clock changed the policy's behaviour, so its
digest changes:

```sh
caseworkctl check .
caseworkctl test .
```

```json test-excerpt
{
  "filesChecked": 2,
  "policyBindings": [
    {"digest": "sha256:<digest>", "id": "decision", "version": "1"}
  ]
}
```

```json test-excerpt
{"proofBoundary": "offline-synthetic", "productionClosure": false}
```

`offline-synthetic` means no PostgreSQL and no runtime decision took part.

## Generate types and plan the package

A producer's client code is written against typed bindings: the policy bindings and the
TypeScript and Python types for its requests, tasks, and results. Generate them outside the
project and hand them to the producer's developers:

```sh
caseworkctl types . --output ../casework-types
```

```json test-excerpt
{
  "files": ["casework.ts", "casework.py", "contexts.schema.json"],
  "output": "../casework-types"
}
```

Then plan the [policy package](../../reference/glossary/#policy-package) without writing it:

```sh
caseworkctl package . --dry-run
```

```json test-excerpt
{
  "dryRun": true,
  "files": ["casework.yaml"],
  "packageDigest": "sha256:<digest>"
}
```

The [package digest](../../reference/glossary/#package-digest) covers the bytes of every packaged
file, so any edit changes it. The holiday set is not packaged: an administrator publishes its
revisions to the running service, and until one is published the stage clock cannot compute a due
time. [Deploy Registry Casework](../../operate/casework/) activates the package.

## Restart the run on the edited project

A run serves the package it built when it started, so stop it and start a fresh one on the edited
files. This deletes the ReviewRequest you decided earlier and the run's credentials. The scenario
seats the staff team again. Find the run first. The start report you saved in `run.json` names it:

```sh
run_id="$(jq -r .run_id run.json)"
casework_url="$(jq -r .products.casework run.json)"
headers_for() {
  rstack dev token "$run_id" --as "$1" | awk '$1 == "casework" && $2 == "headers" {print $3}'
}
```

```sh
rstack dev stop "$run_id"
rstack --format json dev start . --ttl 2h > run.json
run_id="$(jq -r .run_id run.json)"
casework_url="$(jq -r .products.casework run.json)"
```

The new run has a new ID, a new port and new tokens, so ask for tokens again with `headers_for`
before your next call. Leave it running.

## Enable a delegated staff reader

A separately operated assistant can list its represented staff member's assigned
ReviewTasks and read context through the default-off delegated-reader routes.
Enable a named `authentication.oidc.delegatedStaffReaders` policy in the Casework
runtime, admitting the exact gateway, represented Staff profile, read scope,
assertion issuer and short token lifetime. The source-built `registry-mcp`
service selects that policy through `readerPolicy`.

Casework checks the current holder and assignment before release. These
credentials do not admit ordinary producer, decision or administration routes.
Submitted context uses the retained task material. Current-source context also
needs an admitted source profile and `delegatedDisplayExchange` on its provider;
Casework exchanges to the source resource rather than forwarding its own bearer.
The institution must approve the source agent profile's disclosure ceiling.
That service profile does not automatically inherit the staff member's human
Base Registry Engine (BReg) permissions.

Follow [the staff configuration example](https://github.com/registrystack/registry-stack/blob/main/products/platform/examples/mcp-runtime/README.md)
for settings that must match and issuer requirements. `registry-mcp` is currently
source-build-only. Its native drill uses a synthetic issuer, so check your IdP's
exchange support before enabling the policy.

## Pin a policy and submit a request

Policy, stage, routing-rule, queue, team and outcome labels are presentation text for people.
They are single-line values: tabs, line feeds, carriage returns and other control characters are refused.
Stable references use ids, and labels do not change a policy's behavioural binding digest.

A policy binding closes over every access profile, queue, team and the project inbox, even when one policy does not currently name them.
It also closes over that policy's referenced clocks and calendars, context provider, task templates and trusted producers.
This whole-project staffing closure means adding an otherwise unused queue or team changes every policy binding.
`explain` keeps that closure in `dependencies` and reports narrower usage separately.
It also lists all project clocks, calendars and trusted producers at project level.
It reports the queues a policy uses, including clock reassignment queues, the union of its deciding profiles, and every Staff or Supervisor profile eligible to be selected.

Each protected API call authenticates with `Authorization: Bearer ...` and selects one declared profile.
Shared producer Review routes use `Registry-Review-Profile`; Casework policy inspection, human and administrative routes use `Registry-Casework-Profile`.
The development header file includes both, so the same registered caller can use its permitted routes.
The producer's Requester profile is separate from the human Staff or Supervisor profile.
Bootstrap a team serving the policy's queue through the authenticated Directory API before you expect reviewers to see work.

### Select the policy

The producer normally submits `policy: {"id":"decision"}`.
Casework selects and freezes its current compiled policy at first acceptance.
This delegates policy-version governance to the trusted Casework administrator.
A producer that must approve every policy change instead submits the exact `{id, version, digest}` binding; both pin fields are required together.

For strict mode, read `policyBindings[]` from the checked project's flat report:

```sh
caseworkctl --format json check .
```

For a deployed service, the authenticated `GET /v1/review-policies/decision` returns a policy closure whose `identity` is the exact binding for strict mode.
Use that identity, or the generated typed client, rather than inventing a digest.

{/* Evidence: crates/registry-review-protocol/src/lib.rs PolicySelection;

### Submit the request

A request to `POST /v1/review-requests` carries:

- `policy`.
- An immutable `subject` with `source`, `type`, `id`, `version` and a real content `digest`.
- An opaque `requesterReference`.
- `context: {"mode":"submitted","snapshot":{...}}` that validates against the pinned display schema.
- An optional qualified `initiator`, which supports reviewer exclusion.

Send `Idempotency-Key`.
A retry with the same key and original body recovers the accepted request before consulting current policy, even after policy updates.
Acceptance, polling and results retain the concrete accepted policy; never fill that binding into the original selector or change its submission digest.
New review work requires a new submission.

Current producer authority and context compatibility remain required.
The admitted producer identity, namespace, policy, subject binding and submission digest govern later cancellation and result access.
Creation and recovery responses include `Registry-Review-Producer`, naming the admitted producer explicitly, so a source can diagnose a producer-ID configuration mismatch without guessing from a digest.

### Show applicant progress

A stage can declare `publicProgressCode`, a lowercase local identifier such as `identity-check`.
The code is part of the frozen policy digest.
The admitted producer can request the current mapped code with `GET /v1/review-requests/{requestId}?include=progress`.
Casework includes `progressCode` only when a reviewing request's active stage declares one.
Producers map the code to applicant-facing language and verify the exact accepted request, subject, policy and submission digest before displaying it.

Upgrade clients that decode full policy or task-context closures before you activate a policy that sets progress codes.
Older Casework clients can reject the added stage field.
Policies that omit the field keep the earlier closure shape and digest.

### Cancel a request

The same admitted producer can cancel an open Review even when its current source conceals the item.
Cancellation uses the retained exact subject binding, settles its tasks and clocks, and retains the terminal evidence without reading source content.
This does not expand reviewer or supervisor visibility or cancellation authority.
A source package activation can use this operation to close a round that requires Rebase and fresh Review.

### Read the result

The same producer reads `GET /v1/review-requests/{requestId}/result` or its resumable result feed.
A `ReviewResult` repeats the subject, policy and submission digest, and carries a terminal status such as `approved`, `rejected`, `answered`, `cancelled` or `superseded`.
A decided result names its `outcome` and any `publicReason`; a cancelled or superseded one carries neither.

A completion destination, when configured, receives a Standard Webhooks-signed wake with event, request and result identifiers.
Delivery is at-least-once.
A wake carries no decision payload; the producer fetches the result and authorises any later mutation independently.
[Receive Casework completion wakes](../casework-completion-receivers/) defines the wake.

## Record decisions

Human reviewers read `GET /v1/review-tasks`, then claim, assign, delegate, release, draft privately, or decide a task under its current revision.
Send `If-Match` and `Idempotency-Key` on the documented mutations.
Decisions and task holdings are revision-fenced; an old response cannot authorise a later state.

The decision vocabulary belongs to the policy: `approve`, `reject`, `changes-requested` or `answer`, each naming one of the policy's declared outcomes.
A reason or structured result is required when the selected outcome requires one.
An approval names an outcome too; one without it is refused at `$.outcome`, and the `Registry-Casework-Validation-Allowed` header lists the current stage's approval outcomes.

{/* Evidence: crates/registry-casework/src/http.rs approval-outcome-differs;

### Public and private reasons

Each outcome declares `publicReason: required`, `optional` or `none`.
A public reason of at most 2000 UTF-8 bytes reaches the producer on the ReviewResult.
The private `reason` stays in the accountability record, and the audit journal records only that a public reason was given.

An approval carries no private `reason`: only `outcome` and `publicReason`.
A member the request type does not declare, such as `reason` on an approval, is refused with 422 `request.unprocessable`.
The `Registry-Casework-Validation-Path` header names it (`$.decision.reason`) with reason `schema-mismatch`; the submitted value is never echoed.

{/* Evidence: crates/registry-casework-core/src/review.rs PUBLIC_REASON_PATH;
    crates/registry-casework-core/src/http.rs registry-casework-validation-path */}

### Thresholds and settlement

Stage thresholds count independent eligible reviewers.
Every approval in one stage names the same outcome.
One naming another outcome than the stage already chose is refused at `$.outcome` with `approval-outcome-differs`, and the `Registry-Casework-Validation-Allowed` header names the chosen outcome.

The final stage settles the request with that outcome and the public reason of the approval that meets its threshold.
Earlier stages' outcomes and reasons, and other approvers' public reasons, are kept for accountability and not released.

{/* Evidence: crates/registry-casework/src/http.rs approval-outcome-differs */}

### Offer different outcomes per stage

Each stage can set `outcomes` to the non-empty subset of policy outcome ids it offers.
Omitting the field offers every policy outcome.
`caseworkctl check` refuses an unknown outcome id and a stage with no available path to advance or settle the review: every stage must offer an outcome whose settlement is `approved` (`answered` for an answer policy).
`caseworkctl explain` always reports the effective outcomes for each stage, including the all-policy default.

A `changes-requested` result ends that review version.
A resubmission creates a new request and starts at the first stage by default.
Set `resubmission: resume-at-returning-stage` on the review policy to start at the stage that requested changes.
Casework finds the same producer's latest earlier request, and resumes only if that request settled as `changes-requested`.
If the latest round was approved, rejected, cancelled, or is still open, the new request starts at the first stage.
The subject source, type, and ID must match.
Casework also requires the same policy ID.
Casework reads the stage of the decision that settled the earlier request.
Casework matches the returning stage by its ID in the new policy.
If that stage no longer exists, Casework starts at the first stage.
Casework resumes within the earlier request's result retention, and starts a resubmission at the first stage after that.
The `review-resumed-at-stage` history detail carries only `stageId`, without linking to the earlier request.
Earlier approvals are not carried over.
The subject clock starts with a fresh budget.
Omitting `resubmission` preserves the policy digest.

### Distinct approvals

Each approval in a stage must come from a different eligible person.
A development clients file can bind several clients to the same access profile.
Each client has its own identity and token, and two clients on a team's staff list that resolve to the same principal are refused.
Use two clients on one Staff profile to exercise `requiredApprovals: 2` locally; separate profile names are not a substitute for independent people.

A repeat claim after that person's decision returns `403 review.distinct-approver-required`.
The bounded `insufficient-distinct-approvers` task notice identifies a staffing shortfall without listing team members.
`caseworkctl doctor` warns when current serving-team membership cannot staff a configured stage; offline `check` cannot inspect live Directory membership.

### Ask the applicant

A reviewer who holds a task can ask the applicant for more before deciding.
Casework keeps the ask, and the producer shows it to the applicant and reports the answer.

A stage opts in with `asks: {}`.
Only an approval policy can declare it, and a stage without `asks` behaves as before, with the same policy bytes and digest.
The producer must say it reads asks, with `readsAsks: true` on its `trustedProducers` entry.
`caseworkctl check` reports a policy with `asks` that a listed producer does not read.

```yaml
reviewPolicies:
  licence-renewal:
    stages:
      - id: review
        queue: licensing
        decidingProfiles: [licensing-officer]
        requiredApprovals: 1
        asks: {}
trustedProducers:
  licensing-registry:
    readsAsks: true
```

The holder sends `POST /v1/review-tasks/{taskId}/asks` with `If-Match`, `Idempotency-Key` and a body of `text` and `wants`.
The text is plain, bounded like a public reason, and has no control characters.
`wants` lists what the applicant should give, from `answer` and `document`.
Casework refuses the ask when the caller does not hold the task, the request is no longer under review, the task is not at the active stage, the stage declares no `asks`, the producer does not read asks, or the request already has an open ask.
Each refusal has its own problem code: `review.ask-task-inactive`, `review.ask-not-offered`, `review.ask-producer-unsupported` and `review.ask-already-open`, besides `review.task-not-held` and the usual precondition failure.
The task stays claimed by the same holder.

The producer reads the ask on `GET /v1/review-asks`, a resumable feed of announcements, and then on `GET /v1/review-requests/{requestId}/asks/{askId}`.
It reports the answer with `POST /v1/review-requests/{requestId}/asks/{askId}/answer`, which carries the subject binding and the time the answer was committed.
It carries no text.
Only the producer that created the request can answer.
Casework returns an empty `404` for an unknown or foreign ask.
Casework returns `409 review.ask-not-open` for answered or closed asks and for answers given after `dueAt`.
The answer time must not precede the ask or lie more than five minutes ahead of Casework's clock, or Casework answers `review.ask-answer-time-invalid`.

A task with an open ask carries the marker `waiting`, and the marker becomes `answered` when the producer reports the answer.
The marker stays with the task if the holder releases it or a supervisor reassigns it, so the next holder sees it.
`GET /v1/review-tasks` and the holdings list accept `marker=waiting`, `marker=answered`, or `marker=expired`.
The task context lists the request's asks with their text, wants, times, state and the task that asked.

An ask closes when the task that holds it is decided, and every open ask closes when the request settles or is cancelled.
Asks and their feed announcements are erased with the request's history.

Set `answerWithin` under `asks` to give the applicant an elapsed-time budget:

```yaml
asks:
  answerWithin:
    hours: 48
  onDue: return-to-reviewer
  pauseClocks: true
```

`answerWithin` accepts one unit: `minutes`, `hours`, or `days`, as elapsed clocks do.
Casework calculates the absolute `dueAt` from its own `askedAt` time.
Without `answerWithin`, the ask has no due date.
`onDue` defaults to `return-to-reviewer`, its only supported value.
After `dueAt`, clock maintenance expires an open ask and records `closedAt`.
Casework sets the task marker to `expired` and leaves the task with its holder.
Casework writes an `ask-expired` history row, an audit record, and a producer feed announcement.

The producer learns of asks by polling, so delivery can lag.
Casework judges timeliness by `answeredAt`, the time the applicant answered, rather than when the report arrives.
Casework accepts an answer at or before `dueAt` even after maintenance marks the ask expired.
Delivery lag therefore never makes an on-time answer late.
The ask becomes `answered` and the task marker becomes `answered`, unless another ask on that task is open, when it remains `waiting`.
Closing a task or request preserves an already expired ask's state and expiry time.
An expired ask can receive an on-time answer only while its request is still under review.
The `ask-answered` history detail records `arrivedAfterDue` when the report arrives after the deadline.
An answer after `dueAt` receives `409 review.ask-not-open` and changes nothing.

`pauseClocks` defaults to `false`.
When `true`, Casework pauses the subject clock and current stage activity clocks while the ask is open.
Setting `pauseClocks: true` requires `answerWithin` on the same stage's asks.
Otherwise validation reports `casework.review-policy.ask-pause-requires-answer-within`.
Paused clocks produce no reminders, steps, or task deadlines.
`GET /v1/review-requests/{requestId}/clocks` shows their state as `paused`.

## Pair a current-source provider

A current-source review adds one read-only context provider.
The canonical review example project contains a submitted-context policy and a BReg Proposal policy.
Its vendored schema and `context.contract` pin the exact native `correct-address` review-context export.
The compiled policy checks the schema offline; an open review never silently adopts a later producer contract.
The `facility-address-review` policy has `purpose: approval` and `context.mode: current-source`, one provider and exact contract, and a vendored bounded display schema.
Casework keeps the request binding and derived task metadata, not the current-source business projection.

The provider exposes only the capabilities a compiled policy uses.
Human display, service status and task-grant context are separate purpose-bound reads; routing context remains a separate capability.
A BReg provider can expose task-grant context only when the paired package declares a distinct `get-task-grant-context` service profile with the exact source fields.
`caseworkctl check` and the runtime refuse a task template with `subjects` when the provider or runtime binding omits that capability.
There is no fallback to human display or service status.

### How a human read reaches the source

The reviewer sends the current human bearer and selects an authorised BReg source profile with `Registry-Source-Profile` for open Casework work, source context, lists, decisions and new notes.
BReg must trust that issuer and audience, authorise the selected profile and subject, and grant `get-review-context` with the intended field disclosure.
It applies that profile's disclosure and checks the exact Proposal binding.
Casework never substitutes its service credential for a human display read.

Casework selects the action and purpose from current caller-visible metadata, then checks the observed Proposal binding and exact context contract at visibility and decision boundaries.
Context meaning, field semantics and schema bytes stay pinned while profile and row disclosure remain current.
A concealed, changed or non-reviewable Proposal is refused or omitted from the visible task list.
Open work must still be reviewable at the source: claim, decide, `next` and reads of an open task refuse or omit it once it is not.

The service credential uses only its separate status and optional task-grant profiles.
A task-grant read sends Casework's request and task correlation plus the frozen Proposal identity, contract, accepted policy, purpose and exact requested fields.
Those values bind the read; they do not grant authority or prove BReg verified a Casework task exists.
BReg can match the request ID and exact policy against its accepted review binding; the task ID and purpose remain Casework correlation.
There is no generic Proposal read or source synchronisation in this integration.

### Read decided and settled work

Decided tasks and settled requests release their retained Casework-owned task, decision, history and existing notes under current Casework authority and retention.
Their `/context` read still requires current source disclosure.
New notes still require current source disclosure.

Once the request has left review (it is terminal) and the exact source binding remains disclosed but is no longer reviewable, the reviewer who recorded a task's retained decision can read that task's context, and only that task's.
Other eligible reviewers, including the authors of other tasks on the same request, receive not found.
An earlier stage's author receives not found while the request is still in review.
The author reads the source's current projection, still authorised by the source with the caller's own token and source profile, until the result's retention ends.
Casework checks authorship and the reviewer's current membership, profile and retention before the provider read, and checks them again after it.

### Read the operator summary

An inbox page that omits current-source work emits one value-free operator summary.
Expected concealment, source authorisation filtering or binding movement is `INFO`.

### Who does what

The trusted BReg producer creates or recovers the ReviewRequest and later fetches the immutable ReviewResult.

## Staff and account for review work

All staffing operates on `ReviewTask`.
Six supported outcomes share the same current Directory, policy, task and source-disclosure checks:

1. `GET /v1/review-tasks/next` returns the earliest due visible eligible task; it ignores `sort`, `limit` and `cursor`.
2. `GET /v1/review-tasks/holdings` returns the caller's claimed or assigned tasks.
3. `POST /v1/directory/caseload/preview` and `/apply` move an exact, revision-fenced set atomically.
4. `GET /v1/review-tasks` filters by an exact five-part SubjectBinding or a visible reference and sorts by due date, subject or reference.
5. `POST /v1/directory/clocks/recompute/preview` and `/apply` recompute deadlines against the request's pinned policy closure.
6. Authored routing evaluates only declared fields at task or stage creation.

{/* Evidence: crates/registry-casework/src/http.rs review-tasks/next, review-tasks/holdings, caseload/preview, clocks/recompute */}

### Find tasks

Selection never discovers arbitrary source records.
Follow `nextCursor` unchanged; restart the walk when a live source change makes a cursor stale.
The reference filter and sort match the exact reference the producer or provider supplies.
A BReg producer supplies its machine string `breg:{registry}:{action}:{proposal}:{version}`, so staff cannot find a BReg review by a business number such as a licence number.

A subject clock covers one request, and a resubmission starts a new budget.
Submitted routing reads the admitted snapshot; current-source routing uses the provider's minimised routing capability and retains derived metadata.

### Recover and supervise

`GET /v1/review-tasks/own-decisions` lets an eligible reviewer recover their own retained decision receipts.
Supervisors can inspect their serving queues through `/v1/review-tasks/supervision` and the independently authorised, audited `/v1/review-accountability/{eventId}`.
Own receipts omit private reasons and producer results; accountability does not release review context.

Directory teams, absence cover, membership and queue service remain current authority.
An opaque task reference or cursor grants no access.
A decided row in either list still asks the current source whether the caller can see the subject, with the caller's bearer and source profile.
A concealed subject is omitted and any source error fails closed.

A decided task read and the history, including notes, of a settled request instead release retained Casework-owned records under current Casework authority until terminal retention expires.
They do not release source context: `/v1/review-tasks/{taskId}/context` still asks the source and answers not found when the source conceals the subject.
Adding a new note also retains the current source-visibility check.

Supervisory discovery deliberately omits holder identities and due dates.
It is an accountability view, not a team holdings board.
Use the Directory to choose the source officer and an authorised caseload preview to inspect the proposed move.
Reviewer eligibility is not a substitute for supervisor authority.

{/* Evidence: crates/registry-casework/src/http.rs own-decisions, review-tasks/supervision, review-accountability */}

### Bound the list reads

List, next-task and holdings reads ordered by due date or subject select a bounded SQL page before current-source reads.
Their opaque continuation binds the caller, profiles and query, and rechecks the anchor's current authority.
Live-reference filtering or sorting still completes a bounded scan before returning globally ordered results; a smaller page cannot reduce that scan.

Three `inbox` settings bound the work:

- `inbox.maximumCandidateScan` defaults to 100.
- `maximumSourceReads` defaults to 25.
- `pageDeadlineMilliseconds` defaults to 2000.

Source observations are shared by task slots belonging to the same request for this invocation only.
Continuation anchor validation consumes the same source-observation budget as candidates.
Exceeding a scan or source-observation budget refuses the whole ordinary read with `review.query-too-broad`; a provider timeout reports source unavailability.
Narrow the queue or exact subject, reduce an ordinary page size, or size the budgets for the candidate page and measured source latency.
These three reads do not return partial budget-exhausted pages.

{/* Evidence: crates/registry-casework-core/src/config.rs maximum_candidate_scan, maximum_source_reads, page_deadline_milliseconds;
    crates/registry-casework/src/problem.rs query-too-broad */}

### Move caseloads

Caseload preview selects all of the source officer's claimed tasks, optionally restricted to one queue, with a maximum of 100 tasks.
It has no subset, limit or continuation parameter.
Apply moves that exact revision-fenced set atomically.
Use individual authorised task assignments for a selected subset; those assignments are independent transactions.

Apply a caseload or clock recompute preview within 15 minutes.
Once applied, a retry with the same preview answers the same result for 24 hours, even if the Directory changed since, so a lost response can be recovered.

### Staffing notices

An authorised ReviewTask read or supervisory row can include `staffingDiagnostic: no-cover-available` when assignment or absence recompute finds no eligible cover.
This notice reveals no holder or source context.
Successful assignment, claim, caseload transfer, release or task closure clears it; a closed task does not display an old staffing notice.

If you are writing the policy a Registry Casework deployment will run, you author a project
directory and check it offline, with no database and no network. This page reads the project
[Decide your first ReviewRequest](../../tutorials/first-casework/) left in
`tutorial-work/casework`, adds queues, teams, and calendars from the product's tracked examples,
and ends with a package digest ready for activation.

## Read the project files

`caseworkctl init` wrote three files you edit. Each names its format in `kind`:

```yaml title="tutorial-work/casework/casework.yaml" test-excerpt="tutorial-work/casework/casework.yaml"
apiVersion: id.registrystack.org/formats/casework/project/v1alpha1
kind: CaseworkProject
project:
  id: standalone-decision
  version: "1"
```

`casework.yaml` is the policy. `dev-clients.yaml` (`CaseworkDevClients`) names the local callers
and teams for `caseworkctl dev`, and `fixtures/` holds `CaseworkFixture` documents that `test`
proves. `runtime.example.yaml` is runtime configuration, which
[Deploy Registry Casework](../../operate/casework/) covers. `.casework/schemas/` holds the JSON
Schemas your editor reads through each file's first-line comment.

```sh
caseworkctl check tutorial-work/casework
```

```json test-excerpt
{
  "policyBindings": [
    {"digest": "sha256:<digest>", "id": "decision", "version": "1"}
  ],
  "networkAccess": false,
  "databaseAccess": false
}
```

Check reads `casework.yaml`, `dev-clients.yaml`, any retained `caseworkctl dev` state, and
`holiday-sets/`, and prints one binding for each [review policy](../../reference/glossary/#review-policy).

## Declare access profiles and queues

```yaml title="tutorial-work/casework/casework.yaml" test-excerpt="tutorial-work/casework/casework.yaml"
accessProfiles:
  staff:
    principalClaim: sub
    requiredScopes: [casework:staff]
    role: staff
```

An [access profile](../../reference/glossary/#access-profile) admits a token that carries its
required scopes, takes the caller's identity from `principalClaim`, and gives the caller one role:
`staff`, `supervisor`, `administrator`, or `requester`. The project declares one of each.

```yaml title="tutorial-work/casework/casework.yaml" test-excerpt="tutorial-work/casework/casework.yaml"
queues:
  decisions:
    label: Decisions awaiting review
```

A [queue](../../reference/glossary/#queue) is where a stage's review tasks wait for staff. Every
stage, routing rule, and clock step that moves work names a declared queue.

## Declare a review policy and its producer

```yaml title="tutorial-work/casework/casework.yaml" test-excerpt="tutorial-work/casework/casework.yaml"
reviewPolicies:
  decision:
    version: "1"
    purpose: answer
    context: {mode: submitted}
    stages:
      - id: answer
        queue: decisions
        decidingProfiles: [staff]
        requiredApprovals: 1
    retention:
      terminalRetentionDays: 90
      accountabilityRetentionDays: 365
```

A review policy fixes the purpose, the stages in order, the profiles that decide each stage, the
display schema reviewers see, and the outcomes a decision may record. Each outcome sets its
`settlement`, whether a reason is required, and whether a public reason is `required`, `optional`,
or `none`. The `retention` windows are covered in
[Review retention and audit](../../operate/casework-retention/).

`trustedProducers` names each calling system: its access profile, issuer, subject, source
namespaces, and the review policies it may request. Explain shows what the policy compiles to:

```sh
caseworkctl explain tutorial-work/casework
```

```json test-excerpt
{
  "binding": {"digest": "sha256:<digest>", "id": "decision", "version": "1"},
  "contextCustody": "admitted bounded snapshot"
}
```

```json test-excerpt
{
  "id": "requester",
  "issuer": "<issuer>",
  "profile": "requester",
  "reviewPolicies": ["decision"],
  "sourceNamespaces": ["standalone"]
}
```

The digest covers the policy's behavior and everything it depends on: stages, context, outcomes,
access profiles, queues, teams, producers, and the clocks and calendars it uses. Labels and
`because` text are excluded. A producer pins the exact binding in every request, so a changed
digest refuses requests pinned to the old one with `review.policy-mismatch`.

## Choose context custody

`context: {mode: submitted}` reviews the snapshot the producer sent: Casework admits it once
against the display schema and keeps it. When reviewers must instead see the source's current
record, the policy names a context provider and the exact contract it serves. This is from
`products/casework/examples/canonical-review/casework.yaml`:

```yaml title="products/casework/examples/canonical-review/casework.yaml"
contextProviders:
  facility-proposal-context:
    capabilities: [human-display, service-status]
    sourceNamespace: facility-registry
    deploymentRef: facility-registry
    serviceProfiles:
      service-status: casework-review-status
```

```yaml title="products/casework/examples/canonical-review/casework.yaml"
    context:
      mode: current-source
      provider: facility-proposal-context
      contract:
        id: urn:registry:breg:review-context:facility-registry:correct-address:facility-address-context
        revision: sha256:d66f9fa80d136e3f8a9e8c30bf03e5922e7ecfe980854282413f6e4f07694b47
        schemaDigest: sha256:33542e9f3cc7b5e16a6d9e50709d38318040147e0576b151e1fccc0455626869
```

The source keeps disclosure: each read asks it again, under its own authorization.
[Review a Proposal in Casework](../../tutorials/review-breg-changes-in-casework/) pins this
contract to a Base Registry Engine export and pairs the provider with it.

## Route stages, staff teams, and set clocks

The tracked example `products/casework/examples/multi-stage-routing-clocks/casework.yaml` has two
stages, a route, and two clocks. Its policy routes and stages:

```yaml title="products/casework/examples/multi-stage-routing-clocks/casework.yaml"
    routing:
      - id: northern-requests
        because: The submitted region is north.
        when:
          stage: technical
          fields: {region: {equals: north}}
        queue: northern-review
    stages:
      - id: technical
        queue: triage
        decidingProfiles: [staff]
        requiredApprovals: 1
      - id: signoff
        queue: signoff
        decidingProfiles: [supervisor]
        requiredApprovals: 1
        excludePreviousStageReviewers: true
    clocks: [review-deadline, response-budget]
```

The first matching rule picks the queue; a task no rule matches stays in its stage's queue.
`excludePreviousStageReviewers` keeps an earlier stage's reviewer from deciding signoff.

A [team](../../reference/glossary/#team) declares the queues it serves and the profiles its
members and supervisors must hold:

```yaml title="products/casework/examples/multi-stage-routing-clocks/casework.yaml"
teams:
  regional-team:
    label: Regional review team
    serves: [triage, northern-review, overdue-review, signoff]
    memberProfiles: [staff]
    supervisorProfiles: [supervisor]
```

A [clock](../../reference/glossary/#clock) measures a deadline. A `subject` clock counts elapsed
time from acceptance; a `stage` clock counts working days on a
[calendar](../../reference/glossary/#calendar) and may reassign work when it falls due:

```yaml title="products/casework/examples/multi-stage-routing-clocks/casework.yaml"
calendars:
  office:
    timezone: Asia/Bangkok
    workingWeekdays: [monday, tuesday, wednesday, thursday, friday]
    holidaySet: office-holidays
clocks:
  response-budget:
    type: subject
    anchor: {type: request-accepted}
    after: {hours: 48}
  review-deadline:
    type: stage
    anchor: {type: stage-entered}
    calendar: office
    after: {workingDays: 5}
    dueTime: "17:00"
    atRisk: {before: {workingDays: 1}}
    reminders:
      due-soon: {before: {workingDays: 1}}
    steps:
      - id: supervisor-at-deadline
        because: The review deadline passed while the review remained active.
        at: due
        action: {reassign: {queue: overdue-review}}
```

A calendar names a holiday set; the dates come from a revision, which `check` validates offline
from `holiday-sets/`. This is `holiday-sets/office-holidays-7.yaml` beside that example:

```yaml title="products/casework/examples/multi-stage-routing-clocks/holiday-sets/office-holidays-7.yaml"
apiVersion: id.registrystack.org/formats/casework/holiday-set/v1alpha1
kind: CaseworkHolidaySet
holidaySet: office-holidays
revision: 7
dates: [2026-09-07]
```

An operator publishes the live revision to the runtime. From a repository checkout, check and
explain the example to see its compiled route and clocks:

```sh test-skip="the reader directory holds no repository checkout"
caseworkctl check products/casework/examples/multi-stage-routing-clocks
caseworkctl explain products/casework/examples/multi-stage-routing-clocks
```

## Seed local teams in dev-clients.yaml

Which people belong to a team is live directory state, not policy. For a local run,
`dev-clients.yaml` binds one client to each access profile and lists the directory `caseworkctl dev`
seeds as an Administrator on its first start:

```yaml title="tutorial-work/casework/dev-clients.yaml" test-excerpt="tutorial-work/casework/dev-clients.yaml"
  - id: staff
    accessProfile: staff
    scopes: [casework:staff]
    claims:
      registry_actor_kind: human
```

```yaml title="tutorial-work/casework/dev-clients.yaml" test-excerpt="tutorial-work/casework/dev-clients.yaml"
directory:
  - team: decisions-team
    queue: decisions
    staff: [staff]
    supervisors: [supervisor]
```

A person's client carries `registry_actor_kind: human`; the requester, a calling system, does not.
Each directory entry serves one declared queue, one team per queue, with at most eight teams. Its
`staff` must bind a Staff profile and its `supervisors` a Supervisor profile. In a deployment, an
Administrator sets the directory through the API instead.

{/* Evidence: crates/registry-caseworkctl/src/dev/config.rs, DirectoryTeam;
    products/casework/examples/standalone-decision/dev-clients.yaml. */}

review:
  policy: decision
  display:

caseworkctl test tutorial-work/casework

## Run the authoring loop

Generate the typed bindings a producer uses to build requests, into a directory outside the
project:

```sh
caseworkctl types tutorial-work/casework --output tutorial-work/casework-types
```

```json test-excerpt
{
  "files": ["casework.ts", "casework.py", "contexts.schema.json"],
  "output": "tutorial-work/casework-types"
}
```

Then plan the package without writing it:

```sh
caseworkctl package tutorial-work/casework --dry-run
```

```json test-excerpt
{
  "dryRun": true,
  "files": ["casework.yaml"],
  "packageDigest": "sha256:<digest>"
}
```

The [package digest](../../reference/glossary/#package-digest) covers the bytes of every packaged
file, so any edit changes it. A refusal names the file, line, pointer, and next step. To see one,
start a second project and break a stage's queue:

```sh
caseworkctl init tutorial-work/casework-draft --template standalone-decision
```

```diff test-edit title="tutorial-work/casework-draft/casework.yaml"
-queue: decisions
+queue: decision
```

```sh test-exit="1"
caseworkctl check tutorial-work/casework-draft
```

```text test-excerpt
error[casework.review-policy.unknown-queue] <location> /reviewPolicies/decision/stages/0/queue
  no queue in queues has this id
  next: Name a queue declared under queues.
```

Each command's options are in the [`caseworkctl` reference](/reference/cli/caseworkctl/).

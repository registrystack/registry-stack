If you are preparing a Registry Casework deployment for a review team, start with a submitted-context policy, check its stages and outcomes, then add current-source context when reviewers need a fresh authorized view. Casework returns a review result; the producer remains responsible for the subject and any later business mutation.

{/* Evidence: products/casework/README.md; crates/registry-review-protocol/src/lib.rs, ReviewResult. */}

## The project file `casework.yaml`

With `caseworkctl` installed, create a complete starter in a new directory:

```sh
caseworkctl init ./decisions --template standalone-decision
caseworkctl check ./decisions
caseworkctl explain ./decisions
```

`init` refuses an existing destination. The starter includes `casework.yaml`, a runtime example, local callers, synthetic fixtures, and editor settings. Its local issuer and producer identity are teaching values. Replace them with the exact issuer, subject, profiles, and scopes your deployment admits before packaging a production policy.

`check` reports configuration problems at their source fields. `explain` shows compiled policy bindings, context custody, stages, outcomes, routing, clocks, dependency definitions, and recovery guidance. Check these before handing the package to an operator.

{/* Evidence: crates/registry-caseworkctl/src/project.rs, init(), check(), explain(), and STANDALONE_YAML;
    crates/registry-caseworkctl/src/report.rs, ExplainPolicy. */}

The project envelope and identity are:

```yaml
apiVersion: id.registrystack.org/formats/casework/project/v1alpha1
kind: CaseworkProject
project:
  id: decisions
  version: "1"
```

| Member | Purpose |
| --- | --- |
| `accessProfiles` | Token scopes, principal claims, and human or requester roles |
| `queues` | Stable queue identifiers and display labels |
| `reviewPolicies` | Review purpose, stages, context, schemas, outcomes, and retention |
| `trustedProducers` | Exact service identities allowed to submit each policy |
| `contextProviders` | Read capabilities and purpose-specific service profiles |
| `teams` | Authored serving-team requirements, when configured |
| `calendars` and `clocks` | Working time and request or stage deadlines |
| `inbox` | Bounded page, candidate, and source-read budgets |
| `taskTemplates` | Bounded task-grant authority, when configured |

Keep identifiers stable. Queue labels, outcome labels, and routing explanations can change without changing the behavioral policy binding. Stages, thresholds, eligibility, context contracts, routing selection, clocks, and other behavioral dependencies are covered by that binding. Package integrity also covers the presentation bytes.

### Access profiles and queues

Keep human review authority separate from the requesting service:

```yaml
accessProfiles:
  - id: staff
    principalClaim: sub
    requiredScopes: [casework:staff]
    role: staff
  - id: supervisor
    principalClaim: sub
    requiredScopes: [casework:supervisor]
    role: supervisor
  - id: administrator
    principalClaim: sub
    requiredScopes: [casework:admin]
    role: administrator
  - id: requester
    principalClaim: sub
    requiredScopes: [casework:request]
    role: requester
queues:
  - id: decisions
    label: Decisions awaiting review
```

Human profiles also require the runtime's configured human-identity assertion. A token's profile and scopes do not establish Directory membership. An Administrator gives a team queue service, staff, and supervisors through the Directory API. Administrator authority does not release review context or authorize decisions.

### Review policies and producers

This submitted-context fragment adds a structured answer to the starter. Both schemas stay closed, and each structured result field declares its type:

```yaml
reviewPolicies:
  - id: decision
    version: "1"
    purpose: answer
    context:
      mode: submitted
    stages:
      - id: answer
        queue: decisions
        decidingProfiles: [staff]
        requiredApprovals: 1
    retention:
      terminalDays: 90
      accountabilityDays: 365
    displaySchema:
      type: object
      additionalProperties: false
      required: [summary, reference]
      properties:
        summary:
          type: string
          maxLength: 160
        reference:
          type: string
          maxLength: 120
    resultSchema:
      type: object
      additionalProperties: false
      required: [batchStatus]
      properties:
        batchStatus:
          type: string
          enum: [valid, partial, invalid]
        acceptedCount:
          type: integer
          minimum: 0
          maximum: 100000
    outcomes:
      - id: confirmed
        label: Confirm
        settlement: answered
        reasonRequired: false
        resultRequired: true
      - id: rejected
        label: Return for correction
        settlement: answered
        reasonRequired: true
trustedProducers:
  - id: requester
    profile: requester
    issuer: https://identity.example.test
    subject: requester-service
    sourceNamespaces: [standalone]
    reviewPolicies: [decision]
    recoveryDays: 30
```

A stage names its queue, eligible human profiles, and approval threshold. Optional `excludeInitiator` and `excludePreviousStageReviewers` rules restrict who may decide. Initiator exclusion requires the producer's `trustedInitiatorIssuer` and an issuer-qualified initiator in the request. Match principal claims across the producer and reviewer deployment so the exclusion identifies the same person.

Display snapshots, private drafts, structured results, and result constraints each have a 16 KiB bound. Schemas are closed JSON Schema 2020-12 objects, with a 64 KiB schema bound and bounded nesting. Declare only the fields the reviewer needs; increasing disclosure is not a recovery for an oversized payload.

The producer must submit the exact compiled `policy` binding, `{id, version, digest}`, with an immutable subject binding and its context. Use `data.policyBindings` from `caseworkctl --format json check`, the generated types, or authenticated policy discovery at the deployment. A policy identifier alone is insufficient; an unexpected binding is refused with `review.policy-mismatch`.

Approval policies use approval, rejection, or changes-requested decisions. Answer policies use a configured outcome. A required reason or structured result must be supplied at decision time. The producer may narrow declared result properties with `resultConstraints`; it cannot widen the schema or introduce fields. Keep result data within the purpose of the review.

`terminalDays` and `accountabilityDays` run from terminal settlement, with the accountability period at least as long as result availability. Open reviews have no terminal retention deadline yet. [Review retention and audit](../../operate/casework-retention/) explains erasure and recovery.

## Choose context custody

A submitted policy retains the admitted snapshot until its retention deadline. A current-source policy retains a binding and derived task metadata, then reads a fresh bounded projection under the human caller's source authority. Choose the mode according to what the reviewer needs to see and what Casework is allowed to keep.

For current-source context, the policy names one provider and an exact producer contract. This fragment shows the values you replace with a checked export:

```yaml
context:
  mode: current-source
  provider: facility-proposal-context
  contract:
    id: <context-id-from-export>
    revision: <revision-digest-from-export>
    schemaDigest: <schema-digest-from-export>
displaySchema:
  $ref: schemas/correct-address.schema.json
```

Declare the provider's read purposes separately:

```yaml
contextProviders:
  - id: facility-proposal-context
    capabilities: [human-display, service-status]
    sourceNamespace: facility-registry
    deploymentRef: facility-registry
    serviceProfiles:
      service-status: casework-review-status
```

The schema digest binds exact referenced file bytes. Vendor the schema and provider export into the project, then use the native pairing command against the matching Base Registry Engine (BReg) package:

```sh
caseworkctl provider pair ./facility-review \
  --provider-id facility-proposal-context \
  --breg-package /srv/registry/facility-package \
  --action-id correct-address
caseworkctl provider pair ./facility-review \
  --provider-id facility-proposal-context \
  --breg-package /srv/registry/facility-package \
  --action-id correct-address --apply
caseworkctl check ./facility-review \
  --against-breg-package /srv/registry/facility-package
```

Run pairing on a project already configured for that provider and action. The first command previews the proposed changes; review them before repeating with `--apply`. A contract or schema mismatch means the producer export and Casework policy differ; rebuild and pair matching packages rather than editing a digest to suppress the refusal.

The provider declaration separates `human-display`, `service-status`, `routing-context`, and `task-grant-context`. Only capabilities used by the policy become required dependencies. Human display uses the caller's bearer and selected `Registry-Source-Profile`; a service status credential never substitutes for a human disclosure. Routing and task-grant context require their own declared purpose bindings when used. Configure transport URLs and secret references in the deployment runtime file, outside the authored policy.

Concealed or moved context cannot authorize a decision. A malformed provider display returns `source.bad-gateway`; the runtime logs the policy identifier and a closed validation reason without source fields or values. Fix the provider/schema mismatch rather than broadening human disclosure as a workaround. Casework has no source write or apply authority. An approved result is input to the producer's separately authorized mutation.

## Local callers in `dev-clients.yaml`

The local callers file names teaching identities and the Directory seed for a retained development session:

```yaml
apiVersion: id.registrystack.org/formats/casework/dev-clients/v1alpha1
kind: CaseworkDevClients
clients:
  - id: administrator
    accessProfile: administrator
    scopes: [casework:admin]
    claims:
      registry_actor_kind: human
  - id: supervisor
    accessProfile: supervisor
    scopes: [casework:supervisor]
    claims:
      registry_actor_kind: human
  - id: staff
    accessProfile: staff
    scopes: [casework:staff]
    claims:
      registry_actor_kind: human
  - id: requester
    accessProfile: requester
    scopes: [casework:request]
directory:
  - team: decisions-team
    queue: decisions
    staff: [staff]
    supervisors: [supervisor]
```

`check` validates profile, scope, claim, and Directory references against the project. `dev` creates owner-only client credentials; this file contains no credential and is excluded from the deployment package. For current-source development, start the source separately and configure its provider bindings explicitly. A retained `dev stop` preserves the database; `--remove` destroys that owned local session, so use it only when you intend to discard its reviews.

## Routing, clocks, and calendars

Routing selects a queue when a task or stage is created. Declare ordered `routing` rules on the review policy using fields from its display schema. The compiler derives the required routing projection. Submitted routing reads the admitted snapshot; current-source routing reads only the provider's routing context. The first matching rule wins, and the stage queue is the fallback. Derived routing metadata does not grant access to source records.

### Subject and activity clocks

A subject clock starts when the request is accepted and completes when its result becomes terminal. Each request has its own budget, including a new request after changes were requested. Declare the clock at project level and name it in the policy's `clocks` list:

```yaml
clocks:
  - id: review-deadline
    type: subject
    anchor: request-accepted-at
    completeOn: result-terminal
    after:
      elapsed: PT48H
```

An activity clock starts at stage entry and uses a declared working calendar. A due step can move a task to a served queue; an unserved target defers the unapplied step until service is restored.

### Calendars and holiday revisions

An Administrator publishes immutable holiday-set revisions. Missing holiday facts defer activity-clock scheduling. When the facts arrive, maintenance computes the occurrence and refreshes the task deadline. Existing calculations remain pinned until an authorized preview/apply recompute changes them. Inspect the affected task set, then apply the same unexpired preview; create another preview when Directory, task, or holiday state changed.

## The verification loop

Check the authored policy, inspect the closure, exercise its synthetic fixtures, and generate client types:

```sh
caseworkctl check ./decisions
caseworkctl explain ./decisions
caseworkctl test ./decisions
caseworkctl types ./decisions --output ./decision-types
caseworkctl package ./decisions --dry-run
caseworkctl package ./decisions --output ./decision-package
```

Synthetic fixture tests are offline authoring checks. They do not prove deployed authentication, source disclosure, or a producer's later mutation. Verify those boundaries with the applications and identities that will call the deployment.

The package includes `casework.yaml`, referenced local schemas, provider exports, and `SHA256SUMS`. The package digest covers that exact file closure. Hand the package and digest to the operator, together with the required identity claims, Directory setup, context-provider purpose profiles, and retention choices. Keep transport credentials out of the package.

Use `--format json` for automation. Reports carry one versioned envelope with diagnostics and suggested actions. Success exits `0`, a domain refusal `1`, invalid usage `2`, and an operational failure `3`. Correct the named field or dependency and rerun the failed check; a changed request body must not be retried under an existing idempotency key.

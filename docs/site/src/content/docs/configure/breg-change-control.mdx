If you are authoring Base Registry Engine (BReg) writes, use generated CRUD for
ordinary record maintenance, an immediate Action for atomic effects, and a
Proposal Action for durable work that applies later.

## Inspect a complete model

```sh
bregctl init ./facility-registry --template facility-registry
bregctl check ./facility-registry
bregctl --format json explain actions ./facility-registry
bregctl --format json explain proposals ./facility-registry
```

Read the generated project's README and `registry.yaml`. `register-facility`
creates a facility and assignment together. `correct-address` uses a named Rhai
Function and external review. `deactivate-facility` uses an explicit no-review,
manual Proposal. Callers cannot select or change an Action's execution mode.

## Choose a plan and guards

An Action declares `inputs`, `execution`, and `plan`. A fixed plan declares ordered
effects. A function plan names a local Function and bounds its inputs, writes,
and refusals. Values come from `fromInput`, an earlier `fromEffect`, or an explicit
literal `value`; clearing a field is explicit. Forward references and conflicting
writes refuse compilation. A function computes effects within its write ceiling.

`commitGuards` checks current target facts and revision requirements. Every
existing target requires current authority, including link-only references.
All effects, revisions, receipt, audit, and outbox commit atomically.

Require durable work on a Record type independently of grants:

```yaml
mutationPolicy:
  patch: proposal-required
```

Direct Patch and immediate Actions cannot bypass this policy.

## Declare Proposal review and application

```yaml
execution:
  mode: proposal
  proposal:
    review:
      type: required
      authority: casework
      source: facility-registry
      policy:
        id: facility-address-review
    retention:
      mode: retain
```

Select a policy by ID. The review authority freezes its concrete version and digest
when it accepts the submission. Add both `version` and `digest` to `policy` when you
require an exact independently compiled binding. BReg freezes inputs, effects, target
revisions, Action revision, and effect digest at submission. A later planner or policy
change cannot silently reinterpret the approved work.

Automatic application is the default. The built-in executor receives restricted
system authority for that exact frozen submission. It uses no self-HTTP call,
OAuth executor client, or general record permission. To wait for a separately
authorized caller, declare `application.mode: manual` inside `proposal`.
Use `review.type: none` when external review is intentionally unnecessary.

## Split the powers

`permissions.actions` grants Invoke or Start. `permissions.proposals` grants
Get, List, Edit, Submit, Revise, Rebase, Retry, Cancel, Apply, or review operations
independently, with ownership and target boundaries. List needs its own grant.
A reader's target context still follows current record disclosure.
External recovery of automatic application requires a verified human with an
explicit grant. It never inherits the built-in executor's authority.

Deployment `reviewAuthorities` binds each logical authority to its endpoint,
producer identity, selected profile, and credential. Missing optional bindings
disable only dependent operations. An unavailable authority never means approval.
Every uncommitted application requires fresh authenticated and unexpired approval
when review is required. [Connect a review authority](../../tutorials/review-breg-changes-in-casework/)
explains that boundary.

## Pair Casework review context

A BReg Proposal can require a ReviewPolicy from a separate Casework service.
Use the Casework policy ID in the BReg review declaration. Add its actual compiled
version and digest together when you require an exact pin.
BReg owns the frozen Proposal, sends its bound review request as the trusted producer, and consumes
only the exact correlated result before its own independently authorized application step.

Expose the Proposal's bounded native review-context contract in the tested BReg package.
Vendor that exact schema and contract in the Casework policy, then use
`caseworkctl provider pair` to verify and retain the provider export.
[Pair BReg review context with Casework](../../tutorials/review-breg-changes-in-casework/) gives the
preview, apply, and package checks.
Pairing modifies no BReg grant and activates neither runtime.

A Casework Review holds the policy-bound human review, and its immutable Decision
records the outcome. BReg remains responsible for source application.
Give the Casework status service only native `get-review-status` authority.
A human separately selects a profile authorized for `get-review-context`; the provider forwards the
human's current bearer for that read. Neither read confers Proposal application authority.
Bind transport and credential references in each product's operator runtime configuration.
A configured completion destination sends a payload-free wake so the producer can fetch and
correlate the retained result; it carries no decision payload or application authority.

## Observe and recover an exact submission

Use caller-filtered Action metadata to Start, then use promoted Proposal links
for transitions. Refetch after a transition. Record ETags and Proposal lifecycle
conditions are separate.

An authorized Get identifies the Proposal, Action revision, submission version,
effect digest, state, and local application status. Preserve that exact binding.
Revise or Rebase invalidates the earlier observation; do not follow a successor
implicitly. Applied work includes retained application evidence. Blocked work
includes a safe reason, recovery hint, and authorized transitions. `turn` says
whether the party, an official or nobody acts next.

A Review rejection of the current submission is final: the Proposal moves to
the terminal `rejected` state with a `rejected` lifecycle event, and Revise is
no longer offered. Changes requested keep the Proposal `submitted`, record a
`review-returned` event, and promote Revise. The Proposal's `decision` carries
the outcome, its time and the reviewer's public reason, if any.

For an uncertain command, retain and replay its original prepared request and
idempotency key. A later Get does not establish whether that command executed.
Replay recovers retained results without replanning. Expired or erased receipts
refuse execution and keep the key spent.

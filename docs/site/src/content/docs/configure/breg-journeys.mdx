If you are verifying a Base Registry Engine (BReg) project, compile it offline, inspect what the
compiler derived, and run its journeys against an isolated database before packaging it. Start
from the facility template in [Author a registry project](../breg/):

```sh
bregctl init --template facility-registry facility
```

## Check the project

```sh
bregctl check facility
```

```text test-excerpt
Authoring check passed; registry revision sha256:<digest>.
```

An error refuses the project; a warning is a decision to review. Add `--production` for
production package rules and `--deny-warnings` if your policy requires it. Check also reads `dev-clients.yaml` and the journey
files under `tests/`, so a renamed Record type, profile, or Action fails there too.

## Explain what the compiler derived

`bregctl explain <subject> facility` prints one compiled inventory without a database. The
subjects are `model` (Record types and fields), `access` (what each profile may do), `routes`,
`queries` (list queries per profile), `actions`, `proposals` (Proposal Actions only), `events`
(declared deliveries), and `lifecycle` (the engine's Proposal state transitions; it takes no
project).

```sh
bregctl explain actions facility
```

```text test-excerpt
  correct-address (proposal)
    inputs  facility, address-line, city, postal-code
    plan function  plans/correct-address.rhai
    write ceiling: patch facility, fields address-line, city, postal-code
    commit guard facility: revision unchanged
```

Add `--format json` for the complete definition and `--production` for production rules. For
`access`, `--scenario <file>` evaluates synthetic claims against the profiles without verifying
a token or reading a record. Explain shows the compiled contract, not runtime success.

## Generate application artifacts

```sh
bregctl generate openapi facility --output facility-openapi
```

Every artifact family (`bregctl generate --help`) derives from the same model: fix the project,
never a generated copy.

## Declare a journey

`tests/journeys.yaml` lists journeys, each a sequence of steps. A step names a Record type or Action, a profile, synthetic claims, a request, and the expected
outcome. The facility journey registers a facility, then reads it as a caller from another
jurisdiction:

```yaml title="facility/tests/journeys.yaml" test-excerpt="facility/tests/journeys.yaml"
      - id: conceal-foreign-facility
        recordType: facility
        accessProfile: facility-reader
        claims:
          principal: synthetic-foreign-reader
          scopes: [registry:facility:read]
          purpose: facility-administration
          directClaims: {jurisdiction: zone-b}
        request: {type: get, recordCapture: facility}
        expect: {outcome: refusal, status: 404, problemCode: resource.not_found}
```

Keep the success and the refusal; add a step for each invariant your change affects.

A plan Function has an offline loop, with input keyed by authored input ID:

```json title="correction-input.json" test-file
{"facility": "018f0c3e-7b1a-7c00-8000-000000000001", "address-line": "2 Corrected Road", "city": "Corrected city", "postal-code": "10300"}
```

```sh
bregctl project action-test facility --action correct-address --input correction-input.json
```

```text test-excerpt
Ran the handler. Returned 1 effect.
```

`--expect <file>` asserts exact effects or a refusal. This proves the plan, not authority,
guards, or a transaction.

## Run with real credentials

This needs a separate schema-test database and runtime file with migration and runtime roles. Bind
each protected step to a real short-lived credential whose claims match the step; synthetic claims
authenticate nothing. Keep credentials outside the project.

```sh test-skip="needs a PostgreSQL schema-test database and real credentials"
bregctl test facility --runtime-config /path/to/runtime-test.yaml \
  --credentials /path/to/credentials.yaml --output /path/to/test-receipt.json
```

A passing run writes a receipt for that exact candidate; packaging accepts it and refuses changed
inputs. A refused step names the failure; repair it and rerun into a fresh receipt path.

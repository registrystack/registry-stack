A Registry Casework completion wakes your producer so it can read the immutable result under its own authority.
Authenticate and durably enqueue the wake before you acknowledge it.
A wake never authorises a source mutation.

## Wire and delivery contract

Casework sends a POST with a JSON body that carries exactly these business fields:

```json
{"type":"review.completed","eventId":"11111111-1111-4111-8111-111111111111","requestId":"22222222-2222-4222-8222-222222222222","resultId":"33333333-3333-4333-8333-333333333333","completedAt":"2026-09-19T12:34:56Z"}
```

The body contains event, request and result identifiers and a completion time.
It carries no review decision and no source record payload.

Casework sends `Accept: application/json` and `Content-Type: application/json` with these delivery headers:

- `registry-recipient-binding` identifies the producer's configured recipient.
- `webhook-id` is the string form of `eventId`.
- `webhook-timestamp` is the attempt time in Unix seconds, in decimal.
- `webhook-signature` carries one or two space-separated `v1,<base64>` signatures, with the current key first.

Check each delivery in this order.

1. Match `registry-recipient-binding` to your configured recipient and select its signing keys.
   Require a single header value for the binding and for each of the three `webhook-*` headers.
   Return the same 401 response for an unknown binding and a bad signature.
   This unsigned binding only selects keys.
   Use distinct keys for each recipient so a substituted binding selects a different key.
2. Read the raw body with a size limit.
3. Verify the Standard Webhooks HMAC-SHA256 signature over the exact bytes of `webhook-id + "." + webhook-timestamp + "." + body`.
   Give a Standard Webhooks library the raw key bytes.
   Accept a valid signature for either configured key and require the signed timestamp to be within 300 seconds of your clock in either direction.
4. Require the `application/json` content type.
5. Parse the JSON strictly as the five fields above.
   Require the `review.completed` type, valid UUIDs and a valid completion timestamp.
   Refuse duplicate, unknown or missing members.
6. Require `eventId` to equal `webhook-id`.

For canonical hook envelopes, the maintained Rust verifier is `registry_platform_hooks::receiver::verify_hook_delivery`.
For the Casework completion body shown above, use `registry_platform_crypto::delivery_signature::verify` and then parse the authenticated bytes as described in steps 4 through 6.
See the receiver procedure and tested example in the [delivery signing reference](../../reference/delivery-signing/).

### Acknowledgement

Any 2xx response acknowledges delivery.
Casework decides from the status line and drops the response without reading its body, including an unfinished stream.
An empty 204 response is sufficient.
Casework does not follow redirects.

{/* Evidence: crates/registry-casework/src/runtime.rs completion_acknowledged */}

### At-least-once delivery

Delivery is at-least-once: after a lost acknowledgement Casework can send again.
The same `webhook-id`, payload and recipient binding survive retries.
Casework signs each attempt with its own timestamp.
Store the verified event ID and payload durably before acknowledging, and use the event ID to deduplicate retries.

{/* Evidence: crates/registry-casework/tests/review_postgres.rs at_least_once_completion_durably_deduplicates_after_lost_ack_and_exhausts_bounded_retries */}

### Retry bounds

Three settings on the completion destination control retries:

- `attemptTimeoutMilliseconds` defaults to 5000 and accepts 100 through 30000.
- `retryDelaySeconds` defaults to 30 and accepts 1 through 86400.
- `maximumAttempts` defaults to 12 and accepts 1 through 100.

A failed attempt returns to pending until the configured attempt bound or the retention deadline exhausts it.
Exhausted work is terminal for this dispatcher.
Recover missed work through the producer's authenticated result feed.

The outbox writes one value-free failure diagnostic per settled failed attempt and one terminal diagnostic at exhaustion.
Only the destination identifier, the attempt number and fixed failure or terminal labels are emitted.
URLs, credentials, payloads and subject identifiers stay absent.
A stale lease owner cannot settle or log another owner's attempt as exhausted.

## Persist the wake

Create an inbox in your receiver database.

```sql
CREATE TABLE completion_inbox (
  event_id uuid PRIMARY KEY,
  payload jsonb NOT NULL
);
```

After verification, insert the event under its verified `webhook-id` in a transaction.
If the ID already exists, compare the stored payload and acknowledge an identical event.
Return 409 if the payload differs.
Acknowledge only after the transaction commits.
Return 503 if the database cannot confirm the commit.

Keep inbox entries through your reconciliation and retry window.
Retries carry fresh signatures, so a 300-second signature window alone cannot bound inbox retention.

## Read the result

A worker reads the persisted inbox and your application's previously accepted binding.
For Python, call `client.review_result(resource_token, requester_profile, persisted_accepted)`.
Node uses `client.reviewResult(resourceToken, requesterProfile, persistedAccepted)`.

Persisted acceptance has `requestId`, `policy`, `subject` and `submissionDigest`.
Validate that the event belongs to a known accepted request, then let the maintained client correlate the fetched result to that binding.
You may retain an unmatched authenticated wake until your request acceptance is durably recorded.
Neither the notification's `resultId` nor an approved result replaces the source's current authorisation, revision guards or transaction checks.

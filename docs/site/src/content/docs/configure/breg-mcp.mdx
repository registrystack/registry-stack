Run `breg-mcp` and `breg-review` beside your Base Registry Engine (BReg) so a citizen can ask a
chat host, for example an AI assistant, to read their own Record and prepare a change to it. The
citizen then submits that change on a review page you host. You need a registry project with a
proposal-mode Action, an issuer that exchanges tokens and carries task grants, and a TLS proxy.

## What the two services do

`breg-mcp` is a Model Context Protocol (MCP) gateway. A chat host calls it at `/mcp` with a token
issued for one signed-in citizen. The gateway reads that citizen's Record and starts or edits a
Proposal draft, which its tools call an application. `breg-review` is a server-rendered page where
the citizen signs in, compares the draft with their Record, and submits it.

Neither service adds registry semantics: BReg decides what the citizen may see or change, under the
access profile each service names. The two run with separate credentials, so no process can both
prepare a change and submit it.

Both services ship in releases as an
[experimental surface](../../reference/api-stability/#experimental-surfaces): they stay outside
the compatibility promise and may change in any minor release. Neither provides the task authority
that issues the citizen's grants, so your deployment integrates its own (see
[An issuer and a task authority](#an-issuer-and-a-task-authority)).

| Tool | What it does |
|---|---|
| `describe_service` | Returns the configured name, description, and disclosure |
| `get_my_details` | Returns the citizen's own Record |
| `start_application` | Starts a draft, keyed by a `startAttemptId` UUID |
| `list_applications` | Lists the citizen's applications, a page at a time |
| `update_application` | Edits a draft at an `expectedRevision`, with 1 to 64 patch operations |
| `prepare_review` | Returns the draft and its `reviewUrl` |
| `get_application_status` | Returns the application's `status` |

Each input schema offers only the fields the gateway's access profile may write, and never the
target input. Registry text comes back labelled as data, never as instructions.

A chat host that reaches past that split gets these results:

| The chat host tries to | Result |
|---|---|
| Pass the target input, or a field it may not write | `invalid-arguments`, before any call to BReg |
| Start when BReg returns no single Record for the citizen | `record-not-resolved`; nothing is created |
| Reach an application the citizen does not own, or whose target is no longer theirs | `not-found` |
| Edit with an outdated `expectedRevision` | `stale-application` |
| Edit after submission | `application-not-editable` |
| Submit, cancel, or apply | No tool exists, and the gateway's profile holds no such operation |

`status` reads `draft` until the citizen submits, then `submitted`, then `applied`, `rejected`, or
`cancelled` as the Action's review and application settings decide.

The review page re-reads the draft and its target under the citizen's token before it shows the
form and at submit. An unreadable target gets the same 404 as a missing draft, and a changed draft
is shown again with a notice.

## What you need

### A registry project

Declare a Record type with an owner field the citizen cannot write, a proposal-mode Action whose
reference input targets it, and two access profiles.
[Actions and Proposals](../breg-actions/#proposals) shows the Action. The gateway's agent profile
carries a task grant:

```yaml
accessProfiles:
  - id: citizen-agent
    principalClaim: sub
    actorKind: agent
    requesterClients: [<gateway-exchange-client-id>]
    requiredScopes: [address-correction:self]
    requiredPurposes: [address-correction]
    taskGrant:
      sourceIssuer: https://tasks.example.com
    permissions:
      records:
        - recordType: person-address
          operations: [get, list]
          readableFields: [address-line, locality, postal-code]
          rowBoundaries:
            - field: owner
              claim: sub
              operator: equals
      actions:
        - action: correct-address
          operations: [start]
          targets:
            - recordType: person-address
              rowBoundaries:
                - field: owner
                  claim: sub
                  operator: equals
      proposals:
        - action: correct-address
          operations: [get, list, edit]
          ownership: caller
          readableInputs: [address, new-address-line, new-locality, new-postal-code]
          targets:
            - recordType: person-address
              rowBoundaries:
                - field: owner
                  claim: sub
                  operator: equals
```

The gateway needs Proposal Get to prepare a review and report status. Without `taskGrant`, an agent
profile may only Start and Edit, and the project check refuses any other Proposal operation with
`breg.proposal.standing-agent-operation-forbidden`. A task-grant profile must name
`requesterClients` and `requiredPurposes`, and may not write Records directly.

The review page's profile, `citizen-review` here, uses `actorKind: human`, its own client, and no
task grant. It adds `submit` and `cancel` on the Proposal.
[Control access and reads](../breg-access/) explains each permission.

### The registry runtime

In BReg's runtime configuration, admit both clients, trust the gateway as an actor, and name the
task authority:

```yaml
authentication:
  oidc:
    audience: https://registry.example.com/citizen-address-correction
    allowedClients:
      - <gateway-exchange-client-id>
      - <review-page-client-id>
  authorityClaims:
    principal: sub
    purpose: registry_purpose
    trustedActors:
      <gateway-exchange-client-id>: <gateway-actor-subject>
taskGrantStatus:
  - sourceIssuer: https://tasks.example.com
    baseUrl: https://tasks.example.com
    tokenEndpoint: https://login.example.com/token
    clientAssertionAudience: https://login.example.com
    clientId: <registry-status-client-id>
    privateKeyRef: secret:file/task-status-key
    statusResource: <task-authority-resource>
```

BReg accepts a delegated token only when its `act` claim names the subject `trustedActors` maps to
the gateway's exchange client. Before every Proposal read and change, BReg asks the
`taskGrantStatus` authority whether the grant is still current.
[What a token must carry](../../operate/breg/#what-a-token-must-carry) gives the rest of the token
contract.

### An issuer and a task authority

Neither service serves an authorization endpoint. Register each chat host, the gateway's exchange
client, and the review page's client with your issuer ahead of time, each with its own key.

The chat host's token is an RFC 9068 `at+jwt` whose audience is exactly the gateway's
`resourceServer.resource`.

For the gateway, the issuer must support:

- `private_key_jwt` authentication for the exchange client.
- A `client_credentials` grant that honours the RFC 8707 `resource` parameter, so the actor token
  is issued for the gateway and never for BReg.
- RFC 8693 exchange of the chat host's token. The issued token names the citizen in `sub`, carries
  BReg's audience, and has an `act` claim of exactly `sub`, or `sub` and `iss`.

Each exchanged token also carries the task grant: `registry_grant_id`,
`registry_grant_source_issuer`, `registry_grant_client`, `registry_grant_resource`,
`registry_grant_exp`, `registry_grant_bounds`, `registry_approver`, `registry_purpose`,
`registry_actor_kind` set to `agent`, and an `identity` object of 1 to 32 members. The bounds cover
the agent profile's Record and Action permissions, plus one entry for each Proposal:

```json
{
  "type": "breg",
  "permissions": [
    { "collection": "person-addresses", "operations": ["get", "list"] },
    { "collection": "action:correct-address", "operations": ["start"] },
    { "collection": "proposal:<proposal-id>", "operations": ["get", "list", "edit"] }
  ]
}
```

Whoever issues grants must therefore learn each Proposal the gateway starts and name it in that
citizen's later grants; a Start grant gives no later Get, List, or Edit access. Neither service
provides this task authority or provisions those grants, and token exchange alone creates no
per-Proposal authority. The task authority answers BReg's status request at
`/v1/task-grants/{grantId}/status`, unless `statusPath` names another route.

For the review page, the issuer must offer OpenID Connect discovery, the code flow with PKCE (S256),
`private_key_jwt` with the issuer as assertion audience, and the RFC 8707 `resource` parameter. ID
tokens are signed with EdDSA, ES256, ES384, RS256, or PS256. The registry token carries
`registry_actor_kind` set to `human`.

## Configure the gateway

`breg-mcp` reads one closed YAML document at the absolute `--runtime-config` path. It refuses
unknown and duplicate keys, and names the replacement for a renamed one. String values accept
`${VAR}`, `${VAR:-default}`, and `${VAR:?message}`; secret references never do.

```yaml
apiVersion: id.registrystack.org/formats/breg/mcp-runtime/v1alpha1
kind: BRegMcpRuntimeConfig
listener:
  bind: 10.0.0.10:8110
  tlsTermination: operator-controlled-upstream
  networkExposure: private-address
secretProviders:
  file:
    root: /run/secrets/breg-mcp
resourceServer:
  resource: https://assistant.example.com/mcp
  issuer: https://login.example.com
  jwksSource:
    type: uri
    uri: https://login.example.com/jwks.json
  algorithms:
    - ES256
  allowedClients:
    - <chat-host-client-id>
  requiredScopes:
    - address-correction:self
registry:
  baseUrl: https://registry.example.com/
  accessProfile: citizen-agent
  audience: https://registry.example.com/citizen-address-correction
  scopes:
    - address-correction:self
exchange:
  tokenEndpoint: https://login.example.com/token
  clientId: <gateway-exchange-client-id>
  privateKeyRef: secret:file/gateway-key
service:
  name: Address correction
  description: Correct the postal address the registry holds for you.
  disclosure: The assistant you use will see your current address and the correction you request.
  details:
    recordType: person-address
  application:
    action: correct-address
    targetInput: address
  reviewBaseUrl: https://review.example.com/
audit:
  destination: file
  path: /var/lib/breg-mcp/audit/audit.jsonl
  hashKeyRef: secret:file/audit-key
rateLimits:
  perCitizen:
    requestsPerMinute: 30
    burst: 10
  perClient:
    requestsPerMinute: 600
    burst: 100
```

The table below gives each key. Rules that span keys or services:

- `registry.audience` is BReg's audience and must differ from `resourceServer.resource`, or
  `check` reports `breg.mcp-runtime.audience-reused`.
- `exchange.clientId` is the client BReg's `trustedActors` names. Listing it in
  `resourceServer.allowedClients` is refused with
  `breg.mcp-runtime.exchange-client-admitted-inbound`.
- `registry.accessProfile` names the task-grant agent profile. `service.application.targetInput`
  takes the input's identifier, not its API name.
- `service.reviewBaseUrl` is the review page's `publicOrigin`. Review links take the form
  `<reviewBaseUrl>/proposals/<applicationId>`.
- Plain `http` URLs are accepted only on a loopback host under
  `tlsTermination: development-loopback`.
- A fetched key set may not sit at a loopback, private, or cloud-metadata address. Use
  `jwksSource.type: static` for an issuer on a private network.

## Configure the review page

`breg-review` reads its own document under the same rules.

```yaml
apiVersion: id.registrystack.org/formats/breg/review-runtime/v1alpha1
kind: BRegReviewRuntimeConfig
listener:
  bind: 10.0.0.11:8115
  tlsTermination: operator-controlled-upstream
  networkExposure: private-address
publicOrigin: https://review.example.com
secretProviders:
  file:
    root: /run/secrets/breg-review
signIn:
  issuer: https://login.example.com
  clientId: <review-page-client-id>
  clientKeyRef: secret:file/client-key.jwk
  scopes:
    - address-correction:self
registry:
  baseUrl: https://registry.example.com
  resource: https://registry.example.com/citizen-address-correction
  action: correct-address
  targetInput: address
  accessProfile: citizen-review
audit:
  destination: file
  path: /var/lib/breg-review/audit/audit.jsonl
  hashKeyRef: secret:file/audit-key
```

Rules that span keys or services:

- Register `publicOrigin` followed by `/signin/callback` as the client's redirect URI.
- The private JWK that `signIn.clientKeyRef` names must carry a `kid`. The page always requests
  `openid`, so listing it in `signIn.scopes` is refused.
- `registry.resource` equals the gateway's `registry.audience`. `registry.action` and
  `registry.targetInput` match its `service.application`, and `registry.accessProfile` names the
  human profile.
- The issuer must be reachable at a public address.
- `session.maximumPendingSignIns` must hold every sign-in that `rateLimits.globalSignIn` admits
  within `session.signInLifetimeSeconds`.
- One citizen holds at most three sessions, and a fourth sign-in ends the oldest.
- `development-loopback` also drops the `Secure` attribute and the `__Host-` prefix from the
  session cookie.

## Run and check

Check each document with the binary you will serve, then start both:

```sh
breg-mcp --runtime-config /etc/breg-mcp/runtime.yaml check
breg-review --runtime-config /etc/breg-review/runtime.yaml check
breg-mcp --runtime-config /etc/breg-mcp/runtime.yaml serve
breg-review --runtime-config /etc/breg-review/runtime.yaml serve
```

`check` reads the file offline: no secret, no socket, no audit file. It exits 0 when the file is
accepted, 1 when something is refused, 2 on a usage error, and 3 when the file cannot be read.
`--format json` prints one report, `--deny-warnings` makes a warning exit 1, and `--environment`
substitutes `${NAME}` expressions first.

`serve` then refuses an unsafe or missing secret, or an unwritable audit directory, before it
binds. Only the first real call proves the issuer and BReg accept the configuration.

### Put a proxy in front

Neither service terminates TLS. Your proxy forwards plain HTTP to the private listeners, and:

- Serves the review page at exactly `publicOrigin`.
- Keeps the gateway's `Host`, or rewrites it to the authority of `resourceServer.resource`. Any
  other `Host` gets 403.
- Never adds an `Origin` header, which the gateway refuses before it verifies the token, and passes
  `Authorization` unchanged.
- Rate limits by client address, more tightly on `/signin` and `/signin/callback`. The review page
  reads no peer address, so its `rateLimits.globalSignIn` is shared by everyone.

`GET /health` answers 200 `{"status":"alive"}`. `GET /ready` answers 200 `{"status":"ready"}`
while the audit journal is writable, and 503 `{"status":"not-ready"}` otherwise. Neither probe
calls BReg or the issuer.

### Install or run the images

Each release publishes both services as `linux-amd64` binaries, verified as
[Obtain the runtime](../../operate/breg/#obtain-the-runtime) describes, and as images under
`ghcr.io/registrystack/`. Deploy both from one tag, and images by digest.

Each image runs as the Distroless `nonroot` user and reads `/etc/<service>/runtime.yaml`. Mount
configuration and secrets read-only, and a volume at `/var/lib/<service>` for the journal. Bind
`0.0.0.0` with `networkExposure: container-private`. The image has no shell, so probe it from your

## Operate

### Handle secrets

Every credential is a reference. `secret:file/<name>` reads a file under
`secretProviders.file.root`, and `secret:env/<NAME>` reads a variable once
`secretProviders.environment` is declared. Secret files follow the ownership and mode rules in
[Create the secret files](../../operate/breg/#create-the-secret-files). Each service needs its own
private JSON Web Key (JWK) and an audit key of at least 32 bytes.

Secrets are read at startup. To rotate a client key, register the new public key beside the old
one, replace the file, restart, and then retire the old key. A fetched issuer key set picks up a new
key by itself; with `jwksSource.type: static`, add it and restart before the issuer uses it.

Keep the audit key stable, because it keys the pseudonyms and the gateway's retry identity. To
change it, restart with no retry outstanding and write to a fresh `audit.path`.

### Keep the audit journal

Each service writes its own journal through the
[shared audit writer](../../security/hardening-checklist/#audit-destination-and-retention), which
owns rotation, retention, and fail-closed behaviour. BReg audits the delegated calls separately.
Give each process its own `audit.path` on durable storage, and ship sealed files before
`audit.retentionDays` removes them.

Each gateway tool call ends with an `outcome`: `ok`, `refused` with no registry effect, or
`unfinished` when a sent start or edit has an unknown effect. Citizens and clients appear only as
keyed pseudonyms. No field value, tool argument, token, or cookie is written. When the journal
refuses an entry, the gateway answers `service-unavailable` and the review page `audit-unavailable`.

### Read the logs

Both services write JSON lines on standard output. `BREG_MCP_LOG` or `BREG_REVIEW_LOG` sets the
level to `error`, `warn`, or `info`, the default; any other value exits 2. A refused configuration
exits 1 on standard error. Later startup failures go to standard output from `breg-mcp` and to
standard error from `breg-review`, so collect both.

| Service | Level | Message |
|---|---|---|
| `breg-mcp` | info | `tool call`, with `request_id`, `tool`, and `outcome` |
| `breg-mcp` | warn | `the access-token key set is unavailable` |
| `breg-mcp` | error | `tool audit request refused` or `tool audit response refused` |
| `breg-review` | warn | `a rate limit refused a request` |
| `breg-review` | warn | `the registry declined a review request` or `the registry could not answer a review` |
| `breg-review` | error | Any message ending `could not be audited` |

Neither service logs a token, secret, cookie, or field value.

### Upgrade

Run the new binary's `check` before you replace the old one. Both services finish requests in
flight on `SIGTERM` or `SIGINT`. The gateway keeps no state, but the review page holds sessions in
memory, so a restart signs every citizen out. Run one review page instance, or pin each browser to
one, because every limit counts per instance. After a registry package changes the Action, the
review page answers older drafts with 409 `action-changed`.

## Tool errors

A failed tool call answers `{"error":{"code":"<code>","message":"<text>"}}`, with a `traceId` when
BReg supplied one. Each code has one fixed message:

| Code | Cause |
|---|---|
| `invalid-arguments` | The arguments do not fit the tool |
| `record-not-resolved` | BReg returned no single Record for the citizen |
| `not-found` | No such application for this citizen |
| `application-not-editable` | The application is no longer a draft |
| `stale-application` | The gateway compared revisions and found the application or its Action definition changed |
| `change-refused` | BReg refused a required condition, a current-state conflict, or an expired idempotency receipt |
| `idempotency-conflict` | An earlier request with the same key is running or differed |
| `not-permitted` | The Action refused the request |
| `authorization-failed` | A credential is missing, unusable, or no longer accepted; signing in again resolves it |
| `authorization-refused` | The issuer refused delegated access or granted too few scopes; signing in again alone may not resolve it |
| `registry-unavailable` | BReg, the issuer, or the task authority did not answer |
| `service-unavailable` | The gateway cannot record or run the call |
| `unexpected-response` | BReg answered in a form the gateway cannot use |

`change-refused` establishes neither a stale revision nor a withdrawn grant. BReg answers a
withdrawn grant with the same value-free `412` as any other failed condition, so the gateway
cannot tell the two apart and never reports a withdrawn grant as `stale-application`.

Generate one `startAttemptId` for each application the citizen intends, and reuse it on every
retry, including after an uncertain answer. The same ID replays the original Start, and a new ID
opens another application even with identical input. The task authority must reissue the original
grant for the retry, because a new or widened grant cannot replay the earlier Start.

A request refused before any tool runs gets an RFC 9457 problem:

| Status | `code` |
|---|---|
| 401 | `unauthorized` or `invalid-token`, with a `WWW-Authenticate` challenge |
| 403 | `insufficient-scope`, or `forbidden` for a wrong `Host` or any `Origin` header |
| 404 | `not-found` |
| 429 | `rate-limited`, with `Retry-After` |
| 503 | `temporarily-unavailable` |

## What the design guarantees

Whatever the chat host does:

- The gateway never submits, cancels, or applies a Proposal, or writes a Record. Its lint
  configuration disallows those client methods, and a boundary check proves it.
- BReg holds the same line: the gateway's task-grant profile cannot write Records and stays within
  the grant.
- The target comes from the citizen's own Record. BReg checks the `targets` row boundaries on every
  Start, edit, and submit, and takes ownership from the verified caller.
- The chat host's token is never forwarded, and no delegated token outlives the citizen's own.
- BReg checks the grant's status before every Proposal read and change.
- The review page re-reads the target under the citizen's own token before it submits.

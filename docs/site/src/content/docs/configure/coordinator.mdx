You know which product calls your workflow makes and in what order, and now you want to write it as a
Registry Coordinator project. Write
the steps, check and test them offline, and hand the package, digest, and connection requirements
to the operator who serves it. Endpoints, credentials, caller policies, and keys never enter the package;
[Deploy Registry Coordinator](../../operate/coordinator/) covers them.

## Get `coordinatorctl`

Build `coordinator` and `coordinatorctl` from a Registry Stack checkout of the release you deploy.
On Linux, install both binaries in a directory on your `PATH`:

```sh
cargo build --locked --release -p registry-coordinator --bins
mkdir -p "$HOME/.local/bin"
install -m 755 target/release/coordinator target/release/coordinatorctl "$HOME/.local/bin/"
export PATH="$HOME/.local/bin:$PATH"
```

On macOS arm64, each binary has to carry the FIPS library the build links, so copying the executable
alone loses a runtime dependency. Follow the macOS steps in the
[deployment runbook](https://github.com/registrystack/registry-stack/blob/main/products/coordinator/DEPLOYMENT.md#install-and-package),
which package each binary with its library and install the result.

{/* Evidence: products/coordinator/DEPLOYMENT.md, Install and package. */}

The authoring commands `init`, `check`, `explain`, `test`, and `package` work offline: they read no
credential and send no request. Each prints readable text by default, or one JSON report of kind
`CoordinatorCtlReport` with `--format json`, carrying `ok`, `command`, `status`, and a
`diagnostics` array for a refusal. A command exits 0 when it accepts its input, 1 when it refuses
it, 2 on a usage error, and 3 when a resource it needs is unavailable. Run
`coordinatorctl <command> --help` for each command's arguments.

    products/coordinator/README.md, Create and check a project. */}

## Start a project

`coordinatorctl init` writes a starter into a new or empty directory, and refuses a directory that
already has content:

```sh
coordinatorctl init --directory ./follow-up
```

The project ID is the directory name unless you pass `--id`. The starter holds four files and a
`.gitignore` that keeps the local `.coordinator/` directory out of version control:

- `workflow.yaml` names the project and its one `workflow`, plus optional reusable `contracts`,
  `types`, `functions`, and `operations` assets.
- `functions.rhai` contains pure Function entrypoints. Projects that need no Functions can omit it.
- `runtime.yaml` binds logical connections. The deployment copy adds identities, keys, and policies.
- `scenarios.yaml` holds offline cases with fake replies and expected results.

One project is one workflow, and its workflow ID is the workflow name callers start.

## Write the steps

Each step declares `type`: `call`, `choose`, `wait-until`, `wait-for`, or `finish`.
Declare an Operation alias first, then name that alias from a call. Endpoints and credentials
stay in the deployment's tagged `connections` map:

```yaml
operations:
  read-application:
    uses: breg.read-record/v1
    connection: applications
```

The call uses that alias and a typed mapping:

```yaml
read-application:
  type: call
  operation: read-application
  input:
    type: fields
    fields:
      collection:
        type: literal
        value: applications
      recordId:
        type: input
        path: /applicationId
  next: permission
```

A reference names one value. `type: input` reads the run's input, `type: step` with a `step` reads
an earlier call's output, and `type: literal` with a `value` supplies a JSON value. An input or
step reference may add an RFC 6901 `path`, such as `/applicationId`, to select one member. A call
`input` or a finish `output` is a reference, `type: fields` with up to 64 members, or `type: function` with an `inputs`
object of up to sixteen named references. Declare each Function's runtime, source, entrypoint,
named input schemas, and output schema. Its Rhai entrypoint takes one object of named inputs.
The host validates input and output and enforces pure execution limits.

Functions read no clock. `add_seconds(instant, seconds)` and `seconds_between(first, second)`
compute over the RFC 3339 instants a function is given, such as an input value or a field of an
earlier call's output.

directory read, and a bounded external job completion. Starting from the closest one is usually faster than starting from the starter.

## Check and explain

```sh
coordinatorctl check --project ./follow-up --explain
```

`check` validates the graph, the function exports, references, input and outcome schemas, and
execution bounds, and fits every mapping to the schemas it reads and feeds, before any run. A
structural error names its file, line, column, and a repair. A mapping refusal names the step, the
field path, what was expected, and the fix. Some errors hide the checks that depend on them, so run
the same check again after each repair. Add `--runtime-config ./follow-up/runtime.yaml` to check
the logical bindings too.

An accepted check prints the computed Workflow revision on its `Definition:` line. With `--explain`, or
through `coordinatorctl explain --project ./follow-up`, it also lists the steps in graph order from
the start, one line each, with each call's product, effect, and recovery.

## Test against scenarios

```sh
coordinatorctl test --project ./follow-up
```

`test` runs `scenarios.yaml` with a virtual clock and fake product replies, using the same graph,
mapping, and function semantics as the service, and reports each case by name. A case whose steps,
end state, or outcome differs from its expectation names both sides. `test` also holds every
computed call input to its operation's input contract and every fake success reply to its
operation's output. A passing case proves the workflow's logic, not that a product accepts the call:
scenarios never acquire credentials or send requests.

## Package the workflow

```sh
coordinatorctl package --project ./follow-up --output ./follow-up-package
```

When the project has a `scenarios.yaml`, `package` runs it first and writes nothing unless every
case passes. It writes the workflow's immutable snapshot, `definition.json`, and `SHA256SUMS` into a new
directory, and refuses an output that already exists, so build a fresh directory for each change.
It prints the package digest.

Pin the package digest for exact bytes and retain the computed Workflow revision for starts:

- The package digest is the SHA-256 of `SHA256SUMS`, covering the exact snapshot bytes.
- `workflowRevision` hashes execution semantics: input, graph, outcomes, used Operation and
  Function revisions, and host execution contracts. Titles and descriptions do not change it.
  Each run reports the revision it was admitted under, even after activation changes.

Once a workflow version has admitted runs, give a changed definition a new `project.version`.
`plan` and `apply` refuse a changed definition under a version already used, with
`coordinator.command.workflow-version-conflict`.

## Export a typed caller

```sh
coordinatorctl types --project ./follow-up --language typescript --output ./follow-up.ts
coordinatorctl types --project ./follow-up --language python --output ./follow_up.py
```

The generated wrappers provide typed `start`, `get`, and `cancel` through the maintained public
generic clients. They pin the computed `workflowRevision` and check returned identity and declared
outcome names. Keep a start's original identity, key, revision, and input through unknown admission.
A fresh start must match the deployed active revision, which `coordinatorctl workflow` discovers.
Regenerate the wrapper after an execution contract change; runtime schema checks remain with
Coordinator.

## Hand over the package

Give the operator the package directory and its package digest, plus a sanitized `runtime.yaml`
template. List each logical connection's product, required access profile or review kind, OAuth
client scopes and resource, completion destination, and Messaging template and provider. The
operator supplies endpoint addresses, registered identities, private JWKs and other secret files,
and checks those contracts in the receiving products. Share secret references, never secret values.

The maintained examples show these handoffs with synthetic offline scenarios. A passing scenario
does not establish the owning products' live review or application policy.

The operator installs the
directory read-only and pins it as one entry of `deployment.packages`, with its `root` and the
digest as `expectedDigest`. One deployment serves up to sixteen workflows, one package each, and each
workflow is applied, upgraded, and rolled back on its own. Runs already admitted keep the definition
they started with, and new starts use the active one.

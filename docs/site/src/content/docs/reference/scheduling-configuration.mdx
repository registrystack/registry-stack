Look up configuration keys for `scheduling.yaml`, `records.yaml`, the files under `fixtures/`, and
the operator's `runtime.yaml`.

## Scope

These keys are not a frozen contract.

`scheduling.yaml` is the authored policy: services, openings, holiday sets, offerings, the hold
policy, and hooks. `records.yaml` holds the runtime records the policy names by identifier:
locations, resource pools and their members, published windows, and dated exceptions. Files under `fixtures/` drive local checks. `runtime.yaml` is the operator's
deployment file: listener, database, package, identity, task-grant status, audit, retention, and hook
destinations.

A schema-valid document can still fail the checks `schedulingctl` runs, because some rules span
fields or files.
[Configuration files](../configuration-files/) describes the YAML rules and environment
substitution that apply when the runtime reads `runtime.yaml`.

## Read the tables

`fields[]` means an array item; `destinations.hooks.*` means a map entry whose name you choose.
Required fields inside an optional object apply when that object is present.
Conditional fields depend on the selected variant or another configuration value.
Accepted values list the union across variants; constraints separated by `or` are alternatives.
A schema default applies only where that variant declares it. `Not specified` does not mean
that every value is accepted.

Look up configuration keys for `messaging.yaml`, each template version's `template.yaml`, each
provider package's `provider.yaml`, and the operator's `runtime.yaml`.

## Scope

Keys follow the current grammar, which is not frozen.

`messaging.yaml` is the authored package: sender profiles, access profiles, and the templates and
providers it uses. `templates/<id>/<version>/template.yaml` declares one template version's channel,
locales, and parts. `providers/<id>/provider.yaml` declares an HTTP provider package and its
capabilities. `runtime.yaml` is the operator's deployment file: listener, database, package,
identity, authentication, provider connections, audit, and retention.

A schema-valid document still needs the checks `messagingctl check` runs, because cross-file
references, template rendering, and provider scripts cannot be expressed in a schema.
[Configuration files](../configuration-files/) describes the YAML rules and environment
substitution that apply when the runtime reads `runtime.yaml`.

## Read the tables

`fields[]` means an array item; `providers.*` means a map entry whose name you choose.
Required fields inside an optional object apply when that object is present.
Conditional fields depend on the selected variant or another configuration value.
Accepted values list the union across variants; constraints separated by `or` are alternatives.
A schema default applies only where that variant declares it. `Not specified` does not mean
that every value is accepted.

## Deployment posture

With neither `--posture` nor `REGISTRY_STACK_POSTURE`, the deployment uses `production`.
The two inputs must agree when both are present.
Use `--posture development` for a development runtime file.
`check` reports development settings as errors in production and warnings in development.

The listener's `tlsTermination: loopback-plaintext` restricts its bind address to loopback in either posture.
`database.transport: loopback-plaintext` allows a PostgreSQL socket, a loopback IP, or `localhost`.
`database.transport: private-network-plaintext` requires development.
A non-loopback HTTP issuer requires development and `authentication.oidc.allowInsecureHttp: true`.
A loopback HTTP issuer needs no opt-in.

## The runtime file

Registry Messaging reads one versioned operator document, selected with
`messaging --runtime-config ABSOLUTE_FILE serve`.
The selected file path and every operated resource path are absolute.
The document is at most one mebibyte.

The closed envelope is:

```yaml
apiVersion: id.registrystack.org/formats/messaging/runtime/v1alpha1
kind: MessagingRuntimeConfig
```

The former `registry.registrystack.org/messaging-runtime/v1alpha1` is refused with this replacement named.
A removed key is refused with the key that replaced it.
Every mapping is closed: an unknown key is refused with its path, so a misspelled setting never falls back to a default silently.
The JSON Schema for editors states the same grammar, and the
[starter runtime example](https://github.com/registrystack/registry-stack/blob/main/products/messaging/examples/starter/runtime.example.yaml)
is a complete, commented document.

`messagingctl check --runtime-config FILE` checks the same document offline, with no built package, database, network, or secret.
It checks against the authoring project or package that `--project` or `--package` names, or else against the package that `package.root` names, its pinned digest included.
Each `${VAR}` expression is checked by its syntax and position, and with `--environment` it is filled from the environment and checked by its value.
The check reports every finding at once, each with its code, member, and line and column.
It exits 0 when the document is accepted, 1 when it is refused, 2 for a usage error, and 3 when the file or the package it names cannot be read.
`--deny-warnings` refuses a document with a warning.

## Environment expressions

The shared runtime configuration loader parses YAML before it substitutes `${VAR}`, `${VAR:-default}`, or `${VAR:?message}` inside string values.
Comments are not expanded.
Substitution cannot create keys, lists, or YAML documents, and an expanded string remains a string.
A missing required variable fails with a field-addressed diagnostic that does not reveal its value.

Keys remain literal.
Expressions are refused in or under members whose names end in `Ref` or `Refs`, and in secret-provider declarations.
Credentials remain literal `secret:` references to an explicitly declared provider.
The loader never substitutes a secret value into runtime configuration.

## Package, listener and metrics

`package.root` is an installed package produced by `messagingctl package`, including `SHA256SUMS`, `messaging.yaml`, `providers/`, and `templates/`.
`package.expectedDigest`, when set, pins the package to a `sha256:` digest.
The runtime, `messagingctl check`, and `messagingctl apply` refuse a package whose digest differs, before any database is reached.
`messagingctl check` reports the digest to pin.

`listener` is required.
`listener.bind` is one numeric socket address and must be explicit, such as `127.0.0.1:8107`.
`listener.tlsTermination` is required: use `operator-controlled-upstream` behind an operator-managed TLS edge, or `loopback-plaintext` for direct local development, which is refused on any non-loopback bind.
`listener.networkExposure` defaults to `private-address`; `container-private` permits an unspecified bind only for a listener kept on a private container network.
A public unicast address is refused under every combination.

`metricsListener` is optional.
When it is present, its `bind` is required and `/metrics` is served on that socket only; when it is absent, no metrics are served.
The address must be a concrete loopback or private address on a non-zero port, and must not share a socket with the public listener (a wildcard on the listener's port counts as shared).
`metricsListener.networkExposure` defaults to `private-address`.
`container-private` also permits `0.0.0.0` or `::`, for a container whose private address is not known when the file is written, and every other refusal still applies.

The metrics are Prometheus text, and every label is closed:

| Series | Type | Labels |
|---|---|---|
| `messaging_http_requests_total` | counter | `route` (template), `method`, `status` (class) |
| `messaging_authentication_refusals_total` | counter | `reason` |
| `messaging_provider_callbacks_total` | counter | `outcome` |
| `messaging_provider_attempts_total` | counter | `outcome`: `accepted`, `transient`, `permanent`, `maybe-sent` |
| `messaging_limit_refusals_total` | counter | `limit`: `rate`, `daily`, `pacing`, `callback` |
| `messaging_request_refusals_total` | counter | `check`: the closed set of 45 failed checks, every value published at zero |
| `messaging_retention_runs_total` | counter | `outcome`: `erased`, `idle`, `failed` |
| `messaging_dispatch_jobs` | gauge | `state`: `pending`, `leased`, `unknown` |

Counters are per process and start at zero.
`messaging_dispatch_jobs` is read from the database on each scrape.
The queue depth is `pending` plus `leased`, and `unknown` is the number of messages waiting for an operator to settle.
When the database cannot answer, that scrape has no `messaging_dispatch_jobs` samples, and the runtime logs a warning.
A `messagingctl retention erase-expired` run is a separate process and is recorded in the audit journal, not in these counters.

## Secrets, database, authentication and audit

`secretProviders` explicitly enables each accepted reference form.
Declare `file: {root: ABSOLUTE_DIRECTORY}` before you use `secret:file/name`, and `environment: {}` before you use `secret:env/NAME`.
At least one is required, and the runtime does not fall back from one provider to another.

`database.runtimeUrlRef` supplies the service connection and `database.migrationUrlRef` the operator-run migration connection, each a PostgreSQL URL held in a secret.
The runtime requires TLS on both.
`database.caBundleRef` optionally selects the PEM bundle of a private CA.
`database.testOnlyPlaintext: true` is accepted only by a build that carries the `postgres-test` feature.

`authentication.oidc` requires `issuer`, `audience`, and `allowedClients`.
`allowedClients` is required. Write `from-package` to admit exactly the requester clients of the package's access profiles, so the clients are written once, in the package. A list is also accepted. It lists at least one distinct client and must include every requester client that an access profile names, or the runtime refuses to start with `messaging.runtime.profile-client-not-allowed`. A profile that no admitted client could reach is refused at load.
An omitted member, an empty list, and a repeated client are refused when the file is read, and so is the `unrestricted` keyword that the sibling runtimes accept on development loopback, with `messaging.runtime.allowed-clients-required`.
`scopeClaim` defaults to `scope`.
`jwksSource` defaults to issuer discovery and can instead select `{type: static, documentRef: secret:...}` or `{type: uri, uri: HTTPS_URL}`.
The former `jwksUri` member is refused.
`assertionIssuers` maps an allowed client to at least one and at most 16 assertion authorities that it may exchange a subject token from.
A deployment that performs no token exchange leaves it empty, and an exchanged token is then refused.
Tokens must be `at+jwt` access tokens.
[Request an access token from your own code](../../configure/request-an-access-token/) describes the shared per-resource access-token profile: algorithms, token type, audience, scope and actor separation, issuer-network policy, lifetime and safe diagnostics.

`audit.destination` selects `file` (the default) or `stdout`.
File mode uses `audit.path`, `audit.rotateBytes`, and `audit.retentionDays` for a per-process JSON Lines stream.
File acceptance includes fsync; stdout is best-effort and requires the deployment's log pipeline for durable retention.
Each process uses its own destination: applied operator commands write a sibling `messagingctl` file, or stderr when the runtime uses stdout, which keeps command stdout machine-readable.

`audit.hashKeyRef` supplies the key for minimised identifier references.
It does not sign or chain the journal.
Rotating it changes the caller and recipient pseudonyms that later audit records carry, so records written before and after the rotation no longer join on them.
It frees no idempotency key, because that key is scoped to the caller's issuer and subject.
External tamper evidence and complete off-host retention are deployment responsibilities.
`retentionDays` removes local rotated segments, so ship required records before that retention expires.
A failed writer remains unhealthy until restart and makes `/ready` fail.

## Retention

`retention` bounds how long data is kept:

| Key | Default | Bounds |
|---|---|---|
| `payloadRetentionDays` | 7 | 1 to 30 |
| `recordRetentionDays` | 90 | `payloadRetentionDays` to 3650 |
| `receiptRetentionDays` | 7 | 1 to 365, and at most `recordRetentionDays` |

The start record carries the deployed values.
`receiptRetentionDays` is also the idempotency window.
A submission that repeats the request of a key whose receipt is older is refused with `idempotency.expired`, and one that changes the request under the key is refused with `idempotency.key-reused` whatever the key's age.
A submission whose `expiresAt` is already past, or falls more than `payloadRetentionDays` after acceptance, is refused with `request.unprocessable`, so a message is never still waiting to send when its payload's period could end.

Each period counts from the moment the message reached a terminal state (delivered, failed, expired, or cancelled), not from acceptance, so a message still waiting in a retry keeps its payload.

- `payloadRetentionDays` after that moment, the rendered parts and the recipient contact are erased and the message record stays.
- `recordRetentionDays` after it, the record is deleted with its attempts and receipts.
  The idempotency key stays spent, held only as a digest of the caller and the key with its times, and a repeat of it, with the same request or another, is refused with `idempotency.expired`.
- `receiptRetentionDays` after acceptance, the stored submission receipt is dropped together with the raw issuer, subject, and key beside it.
  The request hash stays with the message record.
  The same caller's repeat of its request under the key is refused with `idempotency.expired` and a changed request with `idempotency.key-reused`; their SHA-256 digest keeps the key spent for that caller alone.

A message that is queued, sending, or in an unknown outcome is never erased, and an operator retry committed while a sweep waits for the message keeps its payload.

The runtime sweeps once at start and then hourly, under the runtime credential.
A sweep erases in batches of at most 1,000 of each kind, each batch its own transaction, and journals `messaging.retention.erased` with the counts for every batch that erased something.
`messagingctl retention erase-expired --before <RFC 3339 instant>` runs the same sweep on demand under the migration credential.
It previews by default and erases with `--apply`.
It journals every applied batch through its process audit writer (the first one even when it erased nothing), and refuses a cutoff later than the database's clock.
Batches committed before a failure stay erased and journaled.
One advisory lock, taken by each batch, serialises the runtime's sweep and the command.

## Provider connections

`providers` gives each provider that `messaging.yaml` declares its connection, keyed by the provider id and tagged with the same `type`.
A connection for a provider the package does not declare, or with another type, is refused.
A declared provider with no connection is not activated: startup logs a warning, and its messages fail with the attempt failure code `provider-unconfigured` without a send.
Every credential, trust bundle, and callback secret is a `secret:` reference, resolved once at startup before either listener binds.
A provider that cannot be activated stops the runtime with an error that names the provider and the member, never a value.

An `smtp` connection takes these keys:

| Key | Required | Meaning |
|---|---|---|
| `host` | yes | The relay's DNS name or IP literal, at most 253 bytes; the name TLS verifies |
| `tls` | yes | `starttls`, `implicit`, or `loopback-plaintext` (plaintext to a loopback relay, valid in either posture) |
| `port` | no | Defaults to 587 for `starttls` and 465 for `implicit`; required for `loopback-plaintext` |
| `authentication` | no | `usernameRef` and `passwordRef` |
| `attemptTimeoutMilliseconds` | no | One attempt's whole budget, 1000 to 60000, default 30000 |
| `caBundleRef` | no | A PEM root trusted besides the public web roots |
| `allowedPrivateCidrs` | no | Exact private networks the relay may resolve into |

An `http` connection takes these keys:

- `baseUrl` (required): origin and path prefix ending in `/`; `https`, or `http` only to a loopback host.
- `attemptTimeoutMilliseconds` (required): one send's whole budget, 1 to 10000.
- `maximumResponseBytes` (required): the largest response body read, at most 1 MiB.
- `maximumConcurrentRequests` (required): sends in flight, 1 to 64 and at most the package's `capabilities.maximumConcurrentRequests`.
- `redirects` (required): `deny`, the only policy.
- `authentication` (required): one of the types that follow.
- `callbackVerifier`: required when the package declares `receipts: callback`, and only then.
  See the next section.
- `tlsTrustProfile` (optional): a `tlsTrustProfiles` name whose bundle is trusted in addition to the system roots.
- `allowedPrivateCidrs` (optional): exact private networks an `https` provider may resolve into.
- `acknowledgeQueryStringContent`: required when, and only when, the package sends with `get`; it acknowledges that content travels in the query string.

`authentication.type` is one of these:

- `none`, only for a loopback `http` `baseUrl`.
- `basic`, with `usernameRef` and `passwordRef`.
- `static-authorization`, with `tokenRef` and `scheme`, which may only be `Bearer`.
- `static-api-key`, with `headerName` and `valueRef`.
- `static-api-key-query`, with `parameterName` and `valueRef`.
- `aws-sigv4`, with `region`, `service`, `accessKeyIdRef`, `secretAccessKeyRef`, and optional `sessionTokenRef`.
- `oauth2-client-credentials`, with `tokenEndpoint` on the `baseUrl`'s scheme, `clientIdRef`, `clientSecretRef`, and `maximumCacheSeconds` from 10 to 86400, and optionally `scope`, `audience`, `resource`, `assumedLifetimeSeconds`, and `credentialPlacement: form-body`.

A resolved credential value is at most 4096 bytes.
AWS access key identifiers and secret access keys have a tighter 128-byte limit; AWS session tokens keep the 4096-byte credential limit.

`tlsTrustProfiles` names at most 64 PEM trust bundles, each `{bundleRef: secret:...}`, that an `http` connection's `tlsTrustProfile` selects.

### AWS SigV4 providers

For `aws-sigv4`, `baseUrl` must name the JSON API root, ending in `/` with no other path.
The provider must declare POST and exactly the `x-amz-target` request header.
Its prepare script uses an empty relative target, `bodyFormat: json`, and the AWS action in `x-amz-target`.
Registry Messaging supplies the JSON 1.0 content type and signs the actual destination host, action, timestamp, session token when present, and exact serialised body.
Signing credentials never enter scripts.
The signing profile supports root JSON RPC requests, not AWS Query APIs such as Amazon SNS Publish, S3, or arbitrary AWS REST paths.

The included
[AWS SMS provider example](https://github.com/registrystack/registry-stack/tree/main/products/messaging/examples/providers/aws-sms)
uses AWS End User Messaging SMS `SendTextMessage`, with `service: sms-voice` and an explicit region.
Configure the matching regional endpoint and restrict its AWS principal to the required send action and resources.
Access keys and optional temporary session credentials are explicit `secret:` references resolved at activation.
There is no ambient AWS credential chain, metadata lookup, role assumption, or token refresh, so replace the secret values and restart before temporary credentials expire.
The local fixture tests exercise no real AWS account or carrier delivery.

This adapter records AWS acceptance as `submitted`.
It does not ingest SNS or EventBridge delivery events and declares no receipt capability.
AWS provides no submission idempotency token on this operation, so keep `onUncertain: hold`: a possibly accepted send cannot be retried automatically and safely.
Sender registration, account sandbox and production access, spend limits, and destination country requirements remain AWS account prerequisites.
The provider example contains the installation steps and links to AWS's maintained documentation.

## Provider callbacks

An `http` provider whose package declares `receipts: callback` reports delivery to `POST /v1/provider-callbacks/{provider_id}` on the public listener, or, for `path-token`, to `POST /v1/provider-callbacks/{provider_id}/{token}`.
These routes take no bearer token.
The connection's `callbackVerifier` authenticates each callback, and is one of these:

| `type` | Keys | Verifies |
|---|---|---|
| `hmac-sha1-url-form` | `url`, `header`, `secretRef` | HMAC-SHA1 over `url` and the request's query, then the form parameters sorted by name, base64 in `header` |
| `hmac-sha256-body` | `header`, `encoding` (`hex` or `base64`), `secretRef` | HMAC-SHA256 over the raw body, encoded in `header` |
| `path-token` | `tokenRef` | The secret token as the last path segment; it must resolve to UTF-8 of at most 1024 bytes |

`url` is the external callback URL that the provider was given and signs, exactly as given, `http` or `https`, without a query or fragment, at most 2048 bytes.
A reverse proxy in front of the runtime must not change it for the provider.
`header` is an HTTP header name of at most 128 bytes.
There is no unauthenticated type.

The receipt script reads only what the verifier signed: under `hmac-sha256-body` its `query` is empty, under `hmac-sha1-url-form` its `json` is `()`, and under `path-token` it reads the whole request.

A verified callback answers 204 whether its receipt moved the report, changed nothing, reported a state the runtime does not record, or named no message.
These other outcomes have their own answers:

- A callback that does not verify, names a provider without a verifier, or arrives on the route its verifier does not use answers `403 callback.unverified`.
- A callback the receipt script cannot read answers `422 callback.unreadable`.
- A body over the request edge's limit answers `413 request.body-too-large`.
- A store failure answers `503 service.unavailable`, so the provider retries.

The metrics listener counts callbacks in `messaging_provider_callbacks_total{outcome}`, with `outcome` one of `unverified`, `unreadable`, `ignored`, `applied`, `unchanged`, `unmatched`, `ambiguous`, or `unavailable`.

Callbacks are rate limited before they are verified, at a fixed 6000 a minute with a burst of 600 for each provider with a verifier, and the same again shared by every other callback path.
The rate is not configurable.
A callback past it answers `429 rate-limit.exceeded` with `Retry-After`, which a provider retries, and is counted in `messaging_limit_refusals_total{limit="callback"}`, not in `messaging_provider_callbacks_total`.

### Access profiles

`accessProfiles`, `providers`, and `senderProfiles` are mappings from each item's id to the rest of its entry, written with no `id` member.
The list form and an `id` member inside an entry are refused as `config.removed-key`, and a repeated key is refused as `yaml.duplicate-key`.
`templates` stays a list, because a template is named by its id and version.
Each access profile has the members `principalClaim`, `requiredScopes`, `requesterClients`, `actorKind`, `actsAs`, `senderProfiles`, `templates`, `allowDirectContent`, `requestsPerMinute`, `burst`, and `maximumMessagesPerDay`.

- The key is the profile id, a local identifier: a lowercase letter, then at most 63 lowercase letters, digits, underscores, or hyphens.
- `requiredScopes` is required: a list of at least one scope a token must carry, or `unrestricted` to require none.
- `requesterClients` lists at least one client.
  A requester client belongs to exactly one profile.
- `actorKind` is `human`, `agent`, or `service`, and omitted means any.
- `actsAs` is `sender` or `operator`.
  A sender lists at least one sender profile and one template; an operator lists none and may not allow direct content.
- `requestsPerMinute` is 1 to 60000, `burst` 1 to 10000, and `maximumMessagesPerDay`, when set, 1 to 10000000.

`requestsPerMinute` and `burst` bound how fast each caller of the profile submits.
Every `POST /v1/messages` after the role check is charged to a token bucket keyed by the caller's issuer and subject, and one past the burst is refused `429 rate-limit.exceeded` with `Retry-After`.
The bucket lives in the runtime process, so each replica enforces it on its own and a restart refills it.

`maximumMessagesPerDay`, when set, bounds the messages the whole profile has accepted in the last 24 hours.
It is counted from the accepted messages in the acceptance transaction, so it holds across replicas and restarts.
A submission past it is refused `429 quota.exceeded` with `Retry-After` set to when the oldest counted message leaves the window.
A replayed submission is charged to the rate but not to the daily limit.

### Providers, sender profiles and templates

The rest of the manifest declares what callers send through:

```yaml
providers:
  mail-relay:
    type: smtp
  sms-gateway:
    type: http
    idempotentSubmit: true
senderProfiles:
  transactional:
    channel: email
    provider: mail-relay
    sender: notices@example.org
  reminders-sms:
    channel: sms
    provider: sms-gateway
    sender: Registry
    maximumSegments: 2
templates:
  - id: appointment-reminder
    version: "1"
```

A provider declares its `type`, `smtp` or `http`, and `idempotentSubmit` when it deduplicates submissions on the idempotency key that the runtime sends.
`idempotentSubmit` is the one declaration of that capability: only an `http` provider may set it, and only then does its prepare script see the key.
A provider's endpoint and credentials are runtime configuration.

A sender profile names its `channel` (`email` or `sms`), a declared provider that can carry it, and the `sender` identity.
An SMS sender profile sets `maximumSegments`, from 1 to 10; a rendered SMS that needs more segments is refused `422 content.too-many-segments`.
Each entry of `templates` names a version that the package ships; a version is a label, so quote a numeric one.

### Dispatch policy

A sender profile also sets how the worker sends its messages.
Each message keeps the policy that its profile had when it was accepted.

| Key | Default | Bounds |
|---|---|---|
| `retry.maximumAttempts` | 5 | 1 to 20 |
| `retry.initialDelaySeconds` | 30 | at least 1 |
| `retry.maximumDelaySeconds` | 3600 | `initialDelaySeconds` to 86400 |
| `onUncertain` | `hold` | `hold` or `retry` |
| `acceptDuplicates` | `false` | |
| `defaultExpirySeconds` | 86400 | 60 to 2592000 |

A send that definitely failed is retried with exponential backoff, doubling from the initial delay up to the maximum, with jitter.
A send that may have reached the provider, including one cut off by its time budget, stops the message as `unknown` under `hold` until an operator settles it with `messagingctl messages settle`.
`retry` sends it again under the same provider idempotency key.
It is accepted only when the profile's provider declares `idempotentSubmit: true`, meaning it deduplicates on that key, or the profile sets `acceptDuplicates: true`, the operator's choice that a duplicate is better than a missed message.
A message whose request names no `expiresAt` expires `defaultExpirySeconds` after acceptance, or at `retention.payloadRetentionDays` if that comes first, and is not sent after it expires.

### HTTP provider packages

Every `http` provider has a directory `providers/<id>/` that holds `provider.yaml` and the scripts it names, at the paths it names relative to that directory:

```yaml
apiVersion: id.registrystack.org/formats/messaging/provider/v1alpha1
kind: MessagingProvider
prepareScript: scripts/prepare.rhai
interpretScript: scripts/interpret.rhai   # optional; the status code decides without one
receiptScript: scripts/receipt.rhai       # exactly when receipts is callback
request:
  method: post                            # or get, which runtime settings must acknowledge
  headers:
    - idempotency-key
    - x-request-id
responseHeaders:
  - x-request-id
capabilities:
  receipts: callback                      # none, callback, or reconcile
  maximumConcurrentRequests: 8            # 1 to 64
  ratePerSecond: 20                       # optional, 1 to 1000
```

`ratePerSecond` paces the worker.
An attempt waits for the provider's next send slot after it is leased and before anything reaches the provider, so at most one send starts every `1 / ratePerSecond` seconds per runtime process.
A paced attempt first waits for one of the connection's `maximumConcurrentRequests` sends in flight and holds it through the send, so the rate spaces requests as they leave, including ones queued behind a slow send.
Both waits share their own ten-second allowance on top of the send's time budget, and stop at the message's `expiresAt`.
An attempt whose slot does not open in time is retried under its dispatch policy without a send.
One past its expiry is not sent again: it expires, or stays `unknown` when an earlier attempt may have reached the provider and its policy retries.

`provider.yaml` is closed and at most 1 MiB; each script is at most 64 KiB and must compile with exactly its entry point when the package loads.
These are refused with their path:

- A directory for an `smtp` provider or an undeclared id.
- A file the provider does not name.
- A hidden entry.
- A symbolic link under `providers/`.

A declared `http` provider without its directory or a named script is refused as missing.
`providers/` is digested with the rest of the package.
The repository's
[provider examples](https://github.com/registrystack/registry-stack/tree/main/products/messaging/examples/providers)
are the maintained ones, and the starter ships the mock one as `sms-gateway`.

### Templates

Each template version lives under `templates/<id>/<version>/`:

- `template.yaml` is closed.
  It carries the envelope `apiVersion: id.registrystack.org/formats/messaging/template/v1alpha1` and `kind: MessagingTemplate`, then `channel`, `locales` (at most 32 simple language tags such as `en` or `pt-BR`), and `parts`.
  An email version renders `subject`, `text`, and optionally `html`; an SMS version renders exactly `text`.
- `schema.json` is a JSON Schema (draft 2020-12) that the data must satisfy before anything renders.
  It may not reference anything outside itself.
- `sample.json` is optional: data that every locale must render at load, so `messagingctl check` shows each locale's SMS segment count.
- `<locale>/<part>.j2` exists for every declared locale and part, at most 64 KiB each.

Templates are Jinja without a loader: no `include`, `import`, `extends`, or macros, no built-in filters or globals, and no file, network, or clock access.
A missing or null value refuses the render rather than printing empty.
Two filters format for the requested locale: `date` for an ISO calendar date and `number(decimals)` for a number.
Each part has a fuel budget and a byte ceiling: 512 bytes for a subject, 64 KiB for text, 256 KiB for HTML.
HTML parts escape every value and cannot opt out; text and SMS parts strip control characters, and a subject strips newlines.
A locale the version does not declare is refused `422 template.locale-unavailable`, never answered in another language.

Symbolic links and unknown product files are refused in installed packages.
`messagingctl package PROJECT --output DIRECTORY` selects `messaging.yaml`, `templates/`, and `providers/` from the editable project and excludes runtime configuration, secrets, and development state.
The output is write-once, and an optional `--revision TEXT` records provenance.
`--dry-run` reports the plan without writing.
Use `check --project PROJECT` and `preview --project PROJECT` while you author, and `--package DIRECTORY` for installed output.

## Package activation

The package identity is the shared SHA-256 digest of `SHA256SUMS`.
The runtime verifies the envelope and optional pin, then rechecks each bounded file buffer against its verified digest before it parses or compiles it.
Rendering and scripts use those owned buffers, so later filesystem changes cannot replace the bytes accepted at startup.

- `messagingctl plan --runtime-config FILE` reports the package, database identity, pending schema versions, and runtime role boundary without writing.
- `messagingctl apply --runtime-config FILE` applies that plan in one locked transaction.
- `messagingctl status --runtime-config FILE` reads activation history with the runtime credential.

`messaging serve` refuses unless the package and `identity.databaseId` equal the active row and the runtime role still has the recorded authority.
A package change takes effect on restart after `apply`, and an edited file never changes what a running deployment sends.

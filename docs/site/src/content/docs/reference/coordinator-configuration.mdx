Registry Coordinator uses three pre-1.0 file contracts: `CoordinatorProject`,
`CoordinatorRuntimeConfig`, and `CoordinatorScenarios`. The maintained generated JSON Schemas and
owning runtime implementation define accepted fields. This manually maintained reference describes
their execution and authority rules; use files and binaries from the same source version.

## Project assets

`workflow.yaml` has the project API version
`id.registrystack.org/formats/coordinator/project/v1alpha1` and kind `CoordinatorProject`.
`project.id` names the Workflow, while `project.version` is a human release label.
The one `workflow` graph declares `input`, `deadlineSeconds`, `start`, `steps`, and `outcomes`.
Optional reusable assets are:

- `contracts`: Generated local public product contracts, each with `type` and `source`.
- `types`: Named JSON Schemas.
- `functions`: Typed bounded pure computations with source assets and entrypoints.
- `operations`: Local aliases for exact versioned host operations and logical connections.

Schema positions accept JSON Schema or compile-time references: `typeRef`, `operationInput`,
`operationOutput`, `operationRefusal`, and `completionOutput`. A `completionOutput` names
`operation` and `name`. Imports and references resolve locally. Titles and descriptions are
presentation metadata and do not change the computed execution revision.

JSON Schema fragments and scenario payloads retain foreign JSON value semantics, including nulls.
Omit ordinary optional configuration members rather than writing null.

## Functions and mappings

A Function declares `runtime: rhai`, a project-relative `source`, `entrypoint`, named `inputs`, and
`output`. Every entrypoint takes one object whose named members exactly match those inputs.
The host validates inputs and output and enforces the bounded pure profile. Optional `limits`
can narrow its ceilings: 100,000 operations, 32 call levels, 64 expression depth, 16,384 string
bytes, 256 array entries, 256 map entries, and 65,536 source bytes.
Functions have no clock, credentials, network, database, or filesystem capability.
`add_seconds` and `seconds_between` compute only over supplied RFC 3339 instants.

A mapping has a `type`. `input` reads workflow input, `step` reads an available prior output,
and `literal` supplies a JSON value. Input and step references can select an RFC 6901 `path`.
`fields` constructs up to 64 named members. A `function` mapping names its Function and supplies
an `inputs` object of up to sixteen references:

```yaml
type: function
function: notice-route
inputs:
  record:
    type: step
    step: read-application
```

A referenced output must exist on every incoming route. A `wait-for` result is available only
on routes through its `next`. Success and declared-refusal outputs are available only on their
respective routes. A join reachable from both has no unambiguous output shape.
Check fits mappings to schemas; runtime validates computed commands before preparation or dispatch.
Invalid commands report `failurePath`, never their values.

## Operations and governed contracts

A call step names a local Operation alias. The alias declares exact `uses` and `connection`:

```yaml
operations:
  read-application:
    uses: breg.read-record/v1
    connection: applications
```

The host catalog covers Base Registry Engine (BReg) record reads, exact Actions and Proposal submit/apply/retry/cancel;
Casework review submit/cancel; Scheduling reads and appointment creation; Messaging submission;
bounded external GET; and typed evaluation. The generated operation schemas own each input,
output, effect classification, preparation, and recovery contract.
There is no arbitrary HTTP method, SQL step, or dynamic call destination.

For `breg.invoke-action/v1`, `action.contract` and `action.id` select an exact Action from an
imported BReg-generated contract. Compilation pins its revision, mode, review policy,
application policy, input, output, and declared refusals. Immediate Actions return their exact
result. Proposal Actions return a draft under `proposal`. `breg.submit-proposal/v1` is a separate
mutation that evaluates the plan, freezes the submission, and exposes `application` completion.
Draft creation has no declared-refusal route. A known no-effect plan refusal stops generic Submit,
which exposes no Action-specific typed refusal edge, before observation or a notice.

Only exact authoritative evidence for the Proposal, Action revision, submission version, and
effect digest can settle application. Approval alone is insufficient. Blocked or uncertain
application state stays held. Apply, retry, cancel, and any later Messaging notice each need the
receiving product's own current authority. On an immediate Action, `onDeclaredRefusal` routes only
a validated declared no-effect refusal as `{refusalCode}`. Operational failures and previous uncertain effects cannot
enter that branch.

## Durable waits and observation budgets

`wait-until` persists a supplied or computed instant. An elapsed instant continues immediately;
a wait that reaches the run deadline expires the run.
`wait-for` names a completion of an earlier accepted call on every incoming route:

```yaml
await-review:
  type: wait-for
  completion:
    step: submit-review
    name: result
  timeoutSeconds: 1209600
  next: report
  onTimeout: withdraw
  onCancel: withdraw
```

Casework submission exposes `result`; BReg Proposal submission exposes `application`.
`timeoutSeconds` is required, from one second to one year, and shorter than `deadlineSeconds`.
A settled completion takes `next`; timeout takes `onTimeout`, or reports `wait-timed-out`.
`onCancel` takes a durable authored cleanup route. A leased read records intent and routes when
the read settles or its lease expires. Repeated cancellation preserves cleanup.
Neither timeout nor cancellation reverses an accepted downstream effect.

Every observation has a persistent minimum spacing of at least 30 seconds.
Top-level `minimumObservationIntervalSeconds` defaults to 30 and accepts 30 to 86,400.
Casework and BReg pending reads default to 900 seconds. Casework `resultCheckSeconds` accepts
60 to 86,400; external polling declares `intervalSeconds`. These intervals and deployment
minimums constrain the effective read floor. Restart, wake-up, timeout, and recovery retain
that floor and the original deadline. Retry hints can delay observations within the host ceiling
of 86,400 seconds; unusable hints hold the wait.

Unavailable observations remain pending within the original budget. Invalid, refused, blocked,
or mismatched evidence holds the wait for recovery and cannot become a business-failure outcome.
Inspection reports the completion revision, next observation, persistent floor, count, and limit.
Protected correlation values remain absent. A Coordinator timeout does not establish that a BReg
Proposal failed or stop source-owned work.

## Standalone Casework review

A `casework-review-producer` connection names its endpoint, `profile`, `producer`, and ordinary
service `authorization`. It accepts no task authority. Submission carries a `PolicySelection`,
subject, reviewer context, and requester reference. Select a policy by ID, or require an exact
version and digest together. Casework freezes the concrete `PolicyBinding` at acceptance;
completion must agree with that accepted policy, subject, and submission digest.
The [Casework API contract](../apis/registry-casework/#policy-and-submission-binding) defines selection
and recovery. Casework owns review authority and outcomes.
Standalone review needs no BReg connection and creates no registry effect.

The optional `completion` block authenticates minimized Casework wake-ups by `recipientBinding`
and `bearerTokenRef`. The sender presents the same token and binding to
`POST /v1/review-completions`. An authentic event advances an eligible result read; it starts no
run and supplies no decision authority. Omit the block to use polling alone.

A cancellation returns `cancelled` or `already-terminal`. Only the former establishes withdrawal;
the latter carries the decision that won the race. Both review mutations use same-command
recovery without a read-only original-key receipt.

## External HTTP and evaluation

An `external-http` connection supplies `baseUrl`, exact `paths`, optional `queryParameters`,
optional ordinary service `authorization`, and required `responseSchema` for `{status, body}`.
HTTPS is required except for numeric loopback HTTP. A call supplies a permitted relative path
and optional string query values, never a URL, method, headers, or body. Redirects are refused.
Attempt timeout defaults to 2000 milliseconds and response size to 65,536 bytes; both can narrow.
Omitted authorization means a public read, with no forwarded caller token.

An `external.get/v1` alias can specialize `responseSchema` and declare a named `bounded-poll`
completion with `interpret` and `intervalSeconds`. The typed pure interpreter receives `command`
and `response`, returning `pending`, `complete` with a typed `result`, or `refused` with a declared
code. The host repeats the saved original read and enforces transport and observation budgets.
This external completion path is independent of review and registry application.

An `evaluation` connection selects `system-one` or `openai-decisions`, `baseUrl`, `model`, and
bearer authorization with a stable account `principal`, or explicit local authorization on
numeric loopback. Attempt timeout defaults to 8000 milliseconds; request and response limits
to 65,536 bytes. Typed questions cover predicates, choices, and rubric scores. Provider confidence
is neither normalized across models nor proof of correctness. Review data disclosure and cost
before activation. A saved request that may have dispatched remains held without automatic or
operator replay; a completed result is reused. A later effect needs its own product authority.

## Runtime, callers, and state

`runtime.yaml` uses API version `id.registrystack.org/formats/coordinator/runtime/v1alpha1` and
kind `CoordinatorRuntimeConfig`. One `connections` map contains one to sixteen entries, each with
`type`: `breg`, `casework-review-producer`, `messaging`, `scheduling`, `external-http`, or
`evaluation`. The variant selects the complete connection and authority contract.
`secretProviders`, `database`, and `namespace` configure protected custody. Secret references
remain outside the immutable authored package. The service requires an absolute runtime path.

`deployment.packages` pins up to sixteen Workflow packages by `root` and `expectedDigest`.
Caller `authentication.policies` is a map keyed by exact verified client identity. Run actions
are scoped by `workflows`. Deployment-wide actions need `operator: true` and a policy listing only
those actions omits `workflows`. Ownership follows verified issuer and subject, never input fields.

A fresh start names `workflow`, expected `workflowRevision`, and `input`. Discover the permitted
active contract or generate a revision-pinned TypeScript/Python wrapper. Recover an unknown start
with its exact original identity, key, revision, and input even after activation changes.
Generated wrappers offer typed `start`, `get`, and `cancel` over maintained public generic clients.

Protected state schema version 3 replaces earlier pilot layouts without migration. Preserve and
settle old work under its matching binary before provisioning fresh state. Use the
[deployment procedure](../../operate/coordinator/) for custody, activation, rotation, and restore.

## Check commands

<ConfigurationFormatChecks product="coordinator" />

```sh
coordinatorctl check --project ./follow-up --explain
coordinatorctl test --project ./follow-up
coordinatorctl check --runtime-config ./runtime.yaml --deny-warnings
```

Project checks load `workflow.yaml`, referenced assets, and optional runtime/scenario companions.
They aggregate independent diagnostics without resolving secrets or making requests. Correct the
reported path and rerun, because a structural refusal can mask dependent checks.
`--environment` explicitly substitutes environment expressions; `--deny-warnings` refuses deferred
checks. A successful offline check neither activates a package nor proves downstream acceptance.

Registry Coordinator reads three files: the `workflow.yaml` project you author, the
`scenarios.yaml` cases `coordinatorctl test` runs, and the `runtime.yaml` an operator deploys.

## Contract status

| File | Kind | Status | Source |
| ---- | ---- | ------ | ------ |
| `workflow.yaml` | `CoordinatorProject` | Promised at 1.0 | [`project.schema.json`](https://github.com/registrystack/registry-stack/blob/main/products/coordinator/generated/project/project.schema.json) |
| `scenarios.yaml` | `CoordinatorScenarios` | Promised at 1.0 | [`scenarios.schema.json`](https://github.com/registrystack/registry-stack/blob/main/products/coordinator/generated/scenarios/scenarios.schema.json) |
| `runtime.yaml` | `CoordinatorRuntimeConfig` | Promised at 1.0 | [`runtime.schema.json`](https://github.com/registrystack/registry-stack/blob/main/products/coordinator/generated/runtime/runtime.schema.json) |

JSON Schema is not the acceptance path: a document these schemas accept still has to pass
`coordinatorctl check`, which resolves operation aliases, mapping paths, step routes, and
completion references no schema can express
([Author a Coordinator workflow](../../configure/coordinator/)).

Three rules in `runtime.yaml` are written as exclusions the tables do not show. A policy under
`deployment.authentication.policies` whose actions are all deployment-wide (`doctor`,
`restore-hold`, `release-restore-hold`, `release-admission-hold`, `complete-execution-recovery`,
and `retain`) omits `workflows`, and every other policy sets it. On a `type: scheduling`
connection, `observationAuthorization` is required when `authorization.taskAuthority` is set and
omitted otherwise. On a `type: external-http` connection, `authorization.taskAuthority` is
refused. The project and scenarios schemas carry no such rule.

choose as `name.*`, as in `workflow.steps.*.next` or `operations.*.uses`.

## Deployment posture

Declare `development` or `production` with `REGISTRY_STACK_POSTURE` or `--posture`.
An undeclared posture is production. If you set both, use the same value.
Run `rstack dev` for development, or declare it on the command you run. The
`check` command reports development settings as warnings in development and
errors in production. `check --production` declares production.

Use `listener.tlsTermination: loopback-plaintext` for a loopback bind. Configure
PostgreSQL separately with `database.transport`. Its default is `verified-tls`.
Use `loopback-plaintext` for a socket or a loopback host, or
`private-network-plaintext` in development for a private-network host. A
loopback HTTP issuer needs no exception. `allowInsecureHttp: true` and
`jwksSource.type: test-issuer` require development.

## Host operations

An entry under `operations` in `workflow.yaml` names one of these in `uses` and a connection from
`runtime.yaml` in `connection`. There is no other call: no arbitrary HTTP method, SQL, or dynamic
destination. Effect says what the call can change, Recovery what Coordinator does when a response
is lost, and Key whether the call carries an idempotency key. Completion names what a later
`wait-for` step can wait on. Every operation runs under the connection's current authority, with
at most {reference.operations[0].maximum_call_attempts} attempts of
{reference.operations[0].attempt_timeout_seconds} seconds each.

## Connections

`runtime.yaml` declares every logical connection in one `connections` map, at most sixteen names.
Each entry selects its complete contract with `type`: `breg`, `casework-review-producer`, `messaging`, `payments`, `scheduling`, `external-http`, or `evaluation`.
The [deployment runbook](../../operate/coordinator/) covers the rest of the `deployment` block.

### Base Registry Engine connections

A `breg` connection to Base Registry Engine (BReg) serves `breg.invoke-action/v1` and the Proposal operations.
Give it an ordinary service `authorization` and an explicitly permitted `profile`.
The `authorization` block's `clientAssertionAudience` is required: the issuer identifier, exactly as its metadata publishes it, which the client assertion carries as its only audience (RFC 10070 section 4).
Do not set `authorization.taskAuthority` on a connection used by `breg.invoke-action/v1`: that operation accepts no Casework grant and has no task-authority fallback.
Keep a task-bound record-read connection separate when a workflow needs both authority types.

The Proposal operations use the same connection type.
In the BReg project, grant the connection's profile `get` on every Action the workflow follows, under `permissions.proposals`.
Where the workflow starts or submits requests itself, also grant `start` on the Action under `permissions.actions`, and `cancel`, plus `submit` when the workflow submits, under `permissions.proposals` with `ownership: caller`.
Leave `writableInputs` off that Proposal grant, or list every input the workflow sends: with the list, Start refuses a value for any other input.
Never grant `apply`, because no Coordinator operation applies a Proposal.
Two optional members serve Proposal waits:

```yaml
connections:
  licences:
    type: breg
    baseUrl: https://licences.example.org
    profile: coordinator-follow
    authorization:
      tokenEndpoint: https://issuer.example.org/oauth/token
      clientAssertionAudience: https://issuer.example.org
      clientId: coordinator-licences
      signingKeyRef: secret:file/licences-jwk
    resultCheckSeconds: 300
    requestLink: https://staff.example.org/proposals/{proposalId}
```

`resultCheckSeconds` runs from 60 to 86,400 and defaults to 900.
It spaces the Proposal reads of a waiting run, and each read is one request to BReg per waiting run.
`requestLink` is an `https` template with exactly one `{proposalId}`, or `http` on a loopback IP address such as `127.0.0.1` for a local staff app.
Inspection shows it as "Open the request".
Neither member is part of a live run's binding, so you can change both while runs wait.
A missing `get` grant shows on the waiting run as the hold `proposal-unreadable`.
A missing `start` or `submit` grant shows as BReg's refusal of that step.

### External provider connections

An `external-http` connection serves `external.get/v1` and `external.command/v1`.
For reads, set `baseUrl`, exact `paths`, optional `queryParameters`, optional ordinary service `authorization`, and the required `responseSchema` for `{status, body}`.
Omitted authorisation means a public read.
The attempt timeout defaults to 2000 milliseconds and the response size to 65,536 bytes, and you can reduce both.
Use HTTPS for institutional endpoints; HTTP requires numeric loopback.
`authorization.taskAuthority` is refused on this connection type.

For `external.command/v1`, add `commandPath`: the one exact relative path, resolved against `baseUrl`, that the command may POST to.
The command uses the connection's `authorization`, `responseSchema`, attempt timeout, and response size bound, and its request body is limited to 65,536 bytes.
The attempt timeout also covers DNS resolution and token acquisition, so a slow token endpoint leaves less time for the answer and makes a timeout after the send, which holds the run as uncertain, more likely.
Omit `commandPath` to keep a connection read-only; `paths` still lists at least one read path.
Use a separate connection when commands need a different credential or scope than reads.

```yaml
connections:
  legacy-provider:
    type: external-http
    baseUrl: https://legacy.example.org/api/
    paths:
      - requests/status
    commandPath: requests
    authorization:
      tokenEndpoint: https://issuer.example.org/oauth/token
      clientAssertionAudience: https://issuer.example.org
      clientId: coordinator-legacy-provider
      signingKeyRef: secret:file/legacy-provider-jwk
      resource: https://legacy.example.org
      scopes:
        - requests:create
    responseSchema:
      type: object
      required:
        - status
        - body
      properties:
        status:
          type: integer
```

The provider must deduplicate on the `Idempotency-Key` header.
A repeated key must return the original result and never apply the command twice, for at least as long as a run can be held and retried, which is until its deadline.
Coordinator sends the same key on every attempt of a step, including after a restart and `retry-same`.
A provider that cannot deduplicate is not safe for same-command recovery: do not use `retry-same` with it, and resolve a held run from the provider's own records.
Coordinator trusts a 429 to mean the provider did not process the command, so the provider must never answer 429 after applying it.

### Payment connections

A `payments` connection serves the native payment operations over the Registry Adapter payment host.
`baseUrl` names the Adapter, and `paymentConnection` selects one Adapter-owned payment connection.
That selection is part of a live run's binding identity, and the workflow cannot replace either value.
Use an ordinary service `authorization` without `taskAuthority`; the Adapter authorises the current credential on each call.
`resultCheckSeconds`, from 60 to 86,400 and 900 by default, spaces the authoritative collection or disbursement reads of a waiting run and is not part of the binding identity.

```yaml
connections:
  licence-fees:
    type: payments
    baseUrl: https://adapter.example.org
    paymentConnection: licence-fees
    authorization:
      tokenEndpoint: https://issuer.example.org/oauth/token
      clientAssertionAudience: https://issuer.example.org
      clientId: coordinator-payments
      signingKeyRef: secret:file/payments-jwk
      resource: https://adapter.example.org
      scopes:
        - payments:collect
    resultCheckSeconds: 900
```

Grant Coordinator only the Adapter payment capability.
Any BReg grant that binds a bill or records a receipt, and any instruction-registry grant that reads an instruction or reports provider confirmation, belongs to the Adapter's configured reporter identity.
An unresolved original-request lookup requires inspection; it never licenses a fresh collection or disbursement attempt.
`payments.request-disbursement/v1` cannot use `retry-same` after uncertainty, and reconciles only through its read-only original-command lookup.
The separate `payments.record-provider-confirmation/v1` report may use `retry-same`, because the Adapter owns that idempotently keyed reporting command.

### Evaluation connections

An `evaluation` connection serves `evaluation.evaluate/v1`.
Set protocol `system-one` or `openai-decisions`, `baseUrl`, `model`, and either `authorization.bearer` (`tokenRef` and a stable account `principal`) or an explicit `authorization.local: {}` on numeric loopback.
Request and response limits default to 65,536 bytes and the attempt limit to 8000 milliseconds.
Rotate credentials under the same provider account and binding.

Review the data your mappings disclose before you activate a remote model binding.
Model calls may incur cost.
Inputs and results use Coordinator's existing protected state and retention; provider retention stays under your provider account contract.
A model alias can change upstream even when the local binding is unchanged, so use an immutable release or deployment identifier when your provider offers one.
No failover or model substitution occurs within an admitted command.

An accepted response must include the returned model and provider usage metadata.
OpenAI Decisions must supply its documented nonnegative token counts; malformed metadata leaves the result uncertain instead of advancing the workflow.

If evaluation completion becomes unknown, inspection reports `hold-after-dispatch` and refuses `retry-same` and reconciliation.
Cancellation sets `cancelRequested` while preserving `uncertain` and the attention state; it cannot undo provider processing.
A separately authorised new start can evaluate again, with possible additional cost and a different answer.
The same conservative hold applies to HTTP 429, including temporary rate limits with `Retry-After`: these bindings do not automatically resend an evaluation.
Terminal `needs-review` returns control to the caller and creates no resumable approval task.
The [decision follow-up example](https://github.com/registrystack/registry-stack/tree/main/products/coordinator/examples/decision-follow-up) includes refusal and unknown-result cases.

### Casework review producer connections

`casework.submit-review-request/v1` and `casework.cancel-review-request/v1` use a `casework-review-producer` connection configured as one of Casework's review producers.
`profile` names the Casework access profile the producer's client is admitted to.
`producer` names the producer's `id` in the Casework project's `trustedProducers`.
The ordinary service `authorization` obtains a token whose issuer and subject are the ones that producer declares.
Do not set `authorization.taskAuthority`: a review producer acts under its own identity, and `check` refuses a task authority on a Casework connection.
Configure one connection for each producer.
A `wait-for` step reads the result through the same connection, with the same producer authorisation.

Add a `completion` block to let Casework wake a waiting run as soon as a review completes:

```yaml
connections:
  review:
    type: casework-review-producer
    baseUrl: https://casework.example.org
    profile: coordinator-producer
    producer: coordinator
    authorization:
      tokenEndpoint: https://issuer.example.org/oauth/token
      clientAssertionAudience: https://issuer.example.org
      clientId: coordinator-review-producer
      signingKeyRef: secret:file/review-jwk
      resource: urn:example:casework
      scopes:
        - casework:review
    completion:
      recipientBinding: coordinator-v1
      hmacSha256KeyRef: secret:file/review-completion-key
    resultCheckSeconds: 900
```

Coordinator then accepts Casework's completion events at `POST /v1/review-completions` on the service listener.
The `Registry-Recipient-Binding` header selects the connection. Its configured key verifies the Standard Webhooks signature over the webhook ID, Unix timestamp, and exact body.
An unknown binding or a refused signature answers HTTP 401 `authentication.refused`. The signed timestamp must be within 300 seconds in either direction.
`recipientBinding` is 1 to 256 visible ASCII characters and differs between Casework connections.
A body larger than 2048 bytes answers HTTP 413 `request.body-too-large`. Once its signature verifies, the event must meet these requirements. An invalid body answers HTTP 400 `request.invalid` and an unsupported media type answers HTTP 415 `request.unsupported-media-type`.

- It uses exactly `application/json`.
- It names non-nil identifiers.
- Its `eventId` equals `webhook-id`.
- It carries a `completedAt` no older than 365 days and no more than 5 minutes ahead of the Coordinator's clock.

Every authentic event answers HTTP 204, whether or not a run waits on its request, and an event only brings forward the next result read of a run that does.
HTTP 503 `service.unavailable` asks Casework to deliver it again.
Without a `completion` block the route refuses every event, and waits rely on result checks alone.

`resultCheckSeconds` runs from 60 to 86,400 and defaults to 900.
It spaces the reads of a waiting run when no event arrives.
Lower it when completion events cannot reach Coordinator; each read is one request to Casework per waiting run.
A live run's binding includes `producer` but neither `completion` nor `resultCheckSeconds`, so you can change either while runs wait. To rotate the completion key, put new bytes behind the current reference and supply the old bytes through `previousHmacSha256KeyRef`.

Select the review policy by ID from the owning Casework project's compiled `policyBindings` report.
Casework binds its current concrete policy at first acceptance.
If the workflow requires an exact policy, also copy both its compiled version and digest; a synthetic fixture digest is not a deployable pin.
Preserve the original selection and idempotency key when you recover work.
Submitted context uses `mode: submitted`; current-source context uses the owning policy's `mode: current-source` and configured context provider.
Review policy and trusted producer configuration stay with Casework.

Configure the same producer on the Casework side.
In the Casework project, the producer's `completion` block names a destination and the same recipient binding:

```yaml
trustedProducers:
  coordinator:
    profile: coordinator-producer
    issuer: https://issuer.example.org
    subject: coordinator-review-producer
    sourceNamespaces:
      - applications
    reviewPolicies:
      - application-review
    retention:
      receiptRetentionDays: 7
    completion:
      destinationId: coordinator
      recipientBinding: coordinator-v1
```

In the Casework runtime file, bind that destination to the Coordinator route and to Casework's own reference to the same key file.
`attemptTimeoutMilliseconds`, `maximumAttempts`, and `retryDelaySeconds` bound Casework's delivery, as the Casework runtime configuration describes:

```yaml
reviewCompletionDestinations:
  coordinator:
    url: https://coordinator.example.org/v1/review-completions
    hmacSha256KeyRef: secret:file/review-completion-key
```

The [reviewed notice example](https://github.com/registrystack/registry-stack/tree/main/products/coordinator/examples/reviewed-notice) lists the full set of Casework prerequisites for one review producer.

### Event sources

Key each trusted producer by the alias its workflows declare.
Set its exact producer URI and assign a distinct key to each workflow and trigger in the delivery URL.

```yaml
eventSources:
  scheduling:
    source: urn:registrystack:scheduling:coordinator-lifecycle
    triggers:
      scheduling-lifecycle:
        confirmed:
          hmacSha256KeyRef: secret:file/scheduling-confirmed-event-key
        cancelled:
          hmacSha256KeyRef: secret:file/scheduling-cancelled-event-key
```

You can declare up to 16 sources, 16 workflow entries per source, and 16 trigger entries per workflow.
Every deployed trigger needs its own entry and every key entry must match a deployed trigger using that alias.
The key holds 32 to 64 exact bytes.
You can omit the optional `previousHmacSha256KeyRef` for each trigger and each completion connection.
All current and previous keys must be distinct across triggers and completion connections.

### Observation authorisation

Configure `observationAuthorization` only on task-bound Scheduling connections.
Other adapters do not consume that identity, and offline validation refuses it there instead of presenting an unused credential as part of recovery authority.
Downstream bindings use HTTPS, or explicit loopback HTTP for supervised local fixtures.
Token signing-key rotation preserves the registered downstream client identity, endpoint, audience, resource, scopes, and approved task authority.

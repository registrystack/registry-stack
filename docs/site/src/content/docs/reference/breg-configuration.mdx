## How to read the tables

`fields[]` is an array item; `destinations.hooks.*` is a map entry whose name you choose. A required
key inside an optional object is required only when that object is present. Constraints joined
by `or` are alternatives. `Not specified` does not mean any value is accepted: the compiler and the
runtime also check cross-field rules and references that no table can show.

## Authored values and display

Use `bregctl --format json explain model <project>` when a tool needs to distinguish an authored
value from a compiled default. `authoring.documents` lists the project and each module file,
with the RFC 6901 JSON Pointers present before defaults and module composition. Each document's `bindings` links an `explanationPointer` in the explanation to a
`sourcePointer` in that file, including members contributed by module extensions. Find the
object's binding, append `/display/label` to its source pointer, and check that exact path in
that document's `authoredPaths`. An absent path means the source omitted the label. The same
rule applies to unchanged source members such as a stored field's `required`; generated
fields and other derived output are not necessarily defaults.

`display.label` and `display.description` describe authored objects without changing their
IDs or permissions. Keep IDs visible alongside labels in selection and approval interfaces.
Action inputs keep their existing `label` fallback to `apiName`; the separate optional
`display` member tells you whether display was authored.
`check` warns when two access profiles in the same namespace have equivalent labels,
naming both IDs. Use `check --deny-warnings` when that warning must block a review.

Take labels and refusal wording from the law and the forms your programme already uses, not from
product terms. Keep a short table of the programme's terms; author the labels from a table a programme officer
agrees is a good source. BReg labels are a single string each; for documents in more
than one language, put the translations in the per-locale label tables of the
[Render bundle](../render-configuration/).

## Indexes

The compiler appends the record id, the last sort key of every list, to each index under
`recordTypes.<id>.indexes`; do not declare it. An index declares at most 31 fields
(`breg.index.fields-too-many`). Every `reference` field gets an index of its own unless a declared
index, or a unique constraint without `when`, already leads with it.

`bregctl check` reports `breg.record-type.list-unindexed-filter` and
`breg.record-type.list-unindexed-sort` for a filterable or sortable list field that no index leads
with; they fail a check only under `--deny-warnings`.

## Statistical dataset declarations

`unit` on a `statisticalDatasets` entry names the Record type a dataset aggregates. `measures` is an optional list
whose items are tagged by `type`: `{id, type: count}`, `{id, type: sum, field}`, and
`{id, type: mean, field, scale}`, `{id, type: distinct-count, field}`,
`{id, type: ratio, numerator, denominator, scale}`, and
`{id, type: percentile, field, percentile, scale}`, where `scale` is required and an integer from 0 to 38, and
`percentile` is an integer from 1 to 99. Omitting the list
declares one count measure with the id `count`. `bregctl check` refuses an empty list
(`breg.statistical-dataset.measures-empty`), a repeated id (`breg.statistical-dataset.measure-duplicate`), ids that differ only by `-` versus `_` (`breg.statistical-dataset.measure-id-collision`, reported at the second id),
and more than one `count` measure (`breg.statistical-dataset.measure-count-duplicate`). The `field` of a sum,
a mean, a percentile, or a distinct count must be a declared, unencrypted field of the unit
(`breg.statistical-dataset.field-unknown`, `breg.statistical-dataset.field-encrypted`) of type `int64` or
`decimal` for a sum, a mean, or a percentile, and `reference` for a distinct count
(`breg.statistical-dataset.measure-field-type`). A percentile's field must be readable, not only filterable. Two distinct counts over the same field are refused
(`breg.statistical-dataset.measure-distinct-count-duplicate`). A distinct count's `value` is a JSON integer,
0 for an empty cell, and it is not additive: a total is counted over the records, so a reader must not add its
cells, and neither is a percentile. A dataset that declares a distinct count or a percentile declares at most
4 dimensions (`breg.statistical-dataset.non-additive-dimensions`). A `ratio` divides its `numerator` measure
by its `denominator` measure, each the id of a `count`, `distinct-count`, or `sum` measure of the same dataset;
a ratio, a mean, a percentile, an unknown id, the ratio's own id, or the same measure on both sides is refused
(`breg.statistical-dataset.ratio-operand`). It is computed from the operands' exact values and rounded half away
from zero to `scale` digits, and a total's ratio is the ratio of the totals. A `percentile` over the cell's
values, records with no value being left out, is `(x[j] + x[j+1]) / 2` when `n * percentile / 100` is a whole
number `j`, and `x[ceil(n * percentile / 100)]` otherwise, with the values sorted as `x[1]` to `x[n]` (Hyndman
and Fan definition 2), rounded to `scale` digits. A ratio's and a percentile's `value` is a decimal string with
exactly `scale` digits, or null with status `not-applicable` for a zero denominator or a cell with no values.
Every profile with `read-live` on the dataset, the publisher, and the `exactReads` profile must
be able to read that field (`breg.statistical-dataset.measure-field-not-readable`). Every measure type is
available on `read-live`, `read-exact`, and a release under `exact-public-values`; a dataset with a mean,
a ratio, or a percentile cannot have a `publish` or `read-releases` grant under `minimum-count-and-rounding`
(`breg.statistical-dataset.measure-release-unsupported`), because that method releases counts, distinct
counts, and sums only. A dataset with a sum cannot have a `publish` or `read-releases` grant under that method while the sum rules
are held for review (`breg.statistical-dataset.sum-release-held`). A distinct count in such a release is thresholded and rounded on its own value, independently of
the record count of the same cell.
`disclosure` is a union tagged by a required `type`. `type: minimum-count-and-rounding` takes
`minimumCount` and `roundingBase`, both required, with no value below 2, and the two members below
when the dataset releases a sum. `type: exact-public-values`
takes no other member and releases exact values for every measure type. It compiles only when the unit
Record type, every field the dataset reads, and every source Record type of a derived field it reads are
classified `public`; otherwise `bregctl check` reports `breg.statistical-dataset.exact-release-not-public`,
one diagnostic per item to reclassify. The definition digest covers the disclosure method and its
parameters, except `dominancePercent`.

`disclosure.contributor` names whom a summed value belongs to. `{type: field, field}` names a `reference` field
of the unit that the publisher can read (`breg.statistical-dataset.disclosure-contributor-field`);
`{type: each-record}` states that every record is its own contributor. Records with no contributor value count
as one contributor together. `disclosure.dominancePercent` is the p of the p% rule, an integer from 1 to 100.
Both are required when a dataset that grants `publish` declares a sum, and there are no defaults:
`breg.statistical-dataset.disclosure-contributor-missing` and `breg.statistical-dataset.disclosure-dominance-missing`
refuse a missing member, and `breg.statistical-dataset.disclosure-contributor-unused` and
`breg.statistical-dataset.disclosure-dominance-unused` refuse a member on a dataset that does not need it. A
summed `decimal` field must declare a `minimum` of zero or more
(`breg.statistical-dataset.sum-release-negative-values`). Day periods are refused
(`breg.statistical-dataset.sum-release-day-granularity`), a dataset that releases a sum declares at most 4
dimensions (`breg.statistical-dataset.non-additive-dimensions`), and two datasets that release a sum of the
same field over the same unit are refused, whatever their dimensions, populations, and granularities
(`breg.statistical-dataset.sum-field-released-twice`). The contributor joins the definition digest, so changing it
starts a new release series; `dominancePercent` does not. See [Release sums](../../configure/breg-statistics/#release-sums).

`period`, `measure`, `value`, and `status` are reserved column names, so no dimension may use them
(`breg.statistical-dataset.dimension-reserved`).
A dataset declares at most 12 dimensions (`breg.statistical-dataset.dimensions-exceeded`). At most one access profile holds `publish`
on a dataset. Once one does, it and every `read-live` profile must also hold `read-releases`;
without one, no profile may hold `read-releases`.
`exactReads` is an optional member, `{accessProfile}`, naming the profile an exact read computes under. A
dataset with a `read-exact` grant needs it (`breg.statistical-dataset.exact-reads-missing`), and `exactReads`
needs a `read-exact` grant (`breg.statistical-dataset.exact-reads-unused`) and a known profile
(`breg.statistical-dataset.exact-reads-profile-unknown`). The compiler checks the profile as it checks a
publisher: its visibility must not depend on the caller, its `list` grant must cover what the dataset filters
and groups by, and it must be able to read each sum, mean, percentile, or distinct-count field; those checks report codes beginning
`breg.statistical-dataset.exact-reads-`. A standing agent cannot hold `read-exact`
(`breg.access-profile.standing-agent-read-exact-forbidden`), and a standing-agent or
task-grant profile, from the project or contributed by a module, cannot be the `exactReads` profile
(`breg.statistical-dataset.exact-reads-profile-agent`). `read-exact` works under either disclosure method and
needs no publisher. `exactReads` and `read-exact` grants do not change the definition digest. See [Publish a statistical
series](../../configure/breg-statistics/).

## Attachment storage

Attachments of Proposal Actions are stored in PostgreSQL unless `runtime.yaml` selects
`attachmentStorage` of `type: s3`. `breg` checks an S3 binding at startup:

- `url` is a root HTTPS URL with no path, query, fragment, or user information; plain HTTP
  is accepted only for a numeric loopback address. A runtime file that still names it `endpoint`
  is refused: rename `endpoint` to `url` under `attachmentStorage` and `attachmentVerification`,
  keeping the value.
- `pathStyle: false` (virtual-host addressing) needs a DNS host name in `url`.
- `bucket` uses lowercase letters, digits, hyphens, and dots, starts and ends with a letter or
  digit, and is not an IP address. `region` uses lowercase letters, digits, and hyphens.
- Every credential is a secret reference resolved through the runtime's secret providers.
- The bucket must never have had versioning enabled. `breg` reads its versioning state at startup
  and before each deletion, and refuses it when enabled or suspended, because a delete marker does
  not erase older object versions.

The runtime needs to read the bucket's versioning state and to get, put, and delete objects.
Content is stored once per SHA-256 digest within one database and registry, so give each
independent database its own `identity.databaseId`. Deletion is a retried cleanup
([Retry external attachment cleanup](../../operate/breg-retention/#retry-external-attachment-cleanup)).

:::caution
The first stored attachment pins the storage binding (database, or S3 bucket URL, region, and
registry) and the verification binding (disabled, or `url` and `policyId`) in the database.
`breg` then refuses to start with a different binding, even after every attachment is erased.
Configure both before the first upload; rotating a secret or changing a timeout keeps the binding.
:::

## External attachment verification

`attachmentVerification` of `type: http` holds every uploaded file in quarantine until an external
verifier approves it; the default, `type: disabled`, needs no verdict. `url` is an HTTPS URL,
or plain HTTP to a numeric loopback address, and may carry a fixed query but no user information or
fragment. `policyId` names the verifier's rules generation and is not secret. A background worker
sends:

- `POST` to `url` with the file's raw bytes as the body;
- `Authorization: Bearer <token>`, the token read from `authorizationRef`;
- the file's `Content-Type`, `Accept: application/json`, and its lowercase hexadecimal SHA-256
  digest in `X-Content-SHA256`.

The verifier answers HTTP 200 with at most 1,024 bytes holding exactly one of:

```json
{"verdict":"approved"}
```

```json
{"verdict":"rejected"}
```

Anything else, a timeout, or an unreachable verifier leaves the file pending; the worker logs
`attachment_verification.retry_pending` and retries it. The first retry follows 15 to 30 seconds
later, and each further delay doubles, to at most one hour with jitter included. Each attempt has 60 seconds for the storage read and the
verifier call together, so `breg` refuses to start when `attemptTimeoutMilliseconds` under
`attachmentStorage` (when it is `type: s3`) plus the one under `attachmentVerification` exceeds
55,000; the rest of the minute is kept for recording the outcome. The request follows no redirect
and uses no proxy.

A pending or rejected file blocks its download and the submission of its Proposal, optional slots
included. A verdict is reused for the same digest, content type, and verification binding, so
re-uploading rejected bytes is rejected again. Registry erasure does not reach the verifier: agree
its logging and retention separately.

## Development plan and scenarios

`dev.yaml` declares the products, the synthetic people and the scenario file that `rstack dev`
runs for a project. A scenario file holds the named requests that `rstack dev start` sends once the
registry is running, each step as one person and access profile. A BReg project keeps its scenario
file outside `tests/`, because the registry reads every YAML file under `tests/` as one of its own
checks. [Run a project with rstack dev](../../configure/run-a-project-with-rstack-dev/) describes
both files, and `products/breg/examples/minimal/` shows a plan and scenario file for a BReg
project. The plan format is `products/platform/generated/dev/dev.v1alpha1.schema.json`.

## Schema test credentials

`bregctl test --credentials <absolute-file>` reads one binding for every step of the packaged
journeys, and refuses a file that misses a step or binds one twice. Each credential is a bearer
token named by a secret reference, never inline
([Check, test, package](../../operate/breg/#check-test-package)).

```yaml
apiVersion: id.registrystack.org/formats/breg/schema-test-credentials/v1
kind: BRegSchemaTestCredentials
bindings:
  - journeyId: asset-and-site-caller-surfaces
    stepId: create-asset
    credential:
      type: bearer
      tokenRef: secret:file/operator-token
  - journeyId: asset-and-site-caller-surfaces
    stepId: planner-gets-asset
    credential:
      type: bearer
      tokenRef: secret:env/PLANNER_TOKEN
```

## Check commands

`bregctl check <project>` compiles the project offline. Adding `--runtime-config <file>` also
checks `runtime.yaml` as `breg` reads it at startup, against the project's access profiles, without
a database, network, or secret. `bregctl doctor --runtime-config <absolute-file>` then checks the
deployment: the package, database, audit destination, identity provider, and the other dependencies
`breg` opens. [Check a file before you deploy
it](../configuration-files/#check-a-file-before-you-deploy-it) describes diagnostics and exit codes.

In JSON check output, every warning has a `rank`. `widens-access` identifies an unrestricted or
otherwise additional disclosure path that deserves authority review. `performance` identifies an
unindexed list filter or sort. `hygiene` covers the remaining warnings. Errors omit `rank` because
they already block the check.

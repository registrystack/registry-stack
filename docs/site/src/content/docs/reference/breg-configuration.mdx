## How to read the tables

`fields[]` is an array item; `eventDestinations.*` is a map entry whose name you choose. A required
key inside an optional object is required only when that object is present. Constraints joined
by `or` are alternatives. `Not specified` does not mean any value is accepted: the compiler and the
runtime also check cross-field rules and references that no table can show.

## Indexes

The compiler appends the record id, the last sort key of every list, to each index under
`recordTypes[].indexes`; do not declare it. An index declares at most 31 fields
(`breg.index.fields-too-many`). Every `reference` field gets an index of its own unless a declared
index, or a unique constraint without `when`, already leads with it.

`bregctl check` reports `breg.record-type.list-unindexed-filter` and
`breg.record-type.list-unindexed-sort` for a filterable or sortable list field that no index leads
with; they fail a check only under `--deny-warnings`.

## Statistical dataset declarations

`statisticalDatasets[].unit` names the Record type a dataset counts. `minimumCount` and
`roundingBase` are required and take no value below 2. At most one access profile holds `publish`
on a dataset. Once one does, it and every `read-live` profile must also hold `read-releases`;
without one, no profile may hold `read-releases`. See [Publish a statistical
series](../../configure/breg-statistics/).

## Attachment storage

Attachments of Proposal Actions are stored in PostgreSQL unless `runtime.yaml` selects
`attachmentStorage` of `type: s3`. `breg` checks an S3 binding at startup:

- `endpoint` is a root HTTPS URL with no path, query, fragment, or user information; plain HTTP
  is accepted only for a numeric loopback address.
- `pathStyle: false` (virtual-host addressing) needs a DNS host name in `endpoint`.
- `bucket` uses lowercase letters, digits, hyphens, and dots, starts and ends with a letter or
  digit, and is not an IP address. `region` uses lowercase letters, digits, and hyphens.
- Every credential is a secret reference resolved through the runtime's secret providers.
- The bucket must never have had versioning enabled. `breg` reads its versioning state at startup
  and before each deletion, and refuses it when enabled or suspended, because a delete marker does
  not erase older object versions.

The runtime needs to read the bucket's versioning state and to get, put, and delete objects.
Content is stored once per SHA-256 digest within one database and registry, so give each
independent database its own `identity.databaseId`. Deletion is a retried cleanup
([Retry external attachment cleanup](../../operate/breg-retention/#retry-external-attachment-cleanup)).

:::caution
The first stored attachment pins the storage binding (database, or S3 bucket URL, region, and
registry) and the verification binding (disabled, or endpoint and `policyId`) in the database.
`breg` then refuses to start with a different binding, even after every attachment is erased.
Configure both before the first upload; rotating a secret or changing a timeout keeps the binding.
:::

## External attachment verification

`attachmentVerification` of `type: http` holds every uploaded file in quarantine until an external
verifier approves it; the default, `type: disabled`, needs no verdict. `endpoint` is an HTTPS URL,
or plain HTTP to a numeric loopback address, and may carry a fixed query but no user information or
fragment. `policyId` names the verifier's rules generation and is not secret. A background worker
sends:

- `POST` to `endpoint` with the file's raw bytes as the body;
- `Authorization: Bearer <token>`, the token read from `authorizationRef`;
- the file's `Content-Type`, `Accept: application/json`, and its lowercase hexadecimal SHA-256
  digest in `X-Content-SHA256`.

The verifier answers HTTP 200 with at most 1,024 bytes holding exactly one of:

```json
{"verdict":"approved"}
```

```json
{"verdict":"rejected"}
```

Anything else, a timeout, or an unreachable verifier leaves the file pending; the worker retries
and logs `attachment_verification.retry_pending`. The request follows no redirect and uses no proxy.

A pending or rejected file blocks its download and the submission of its Proposal, optional slots
included. A verdict is reused for the same digest, content type, and verification binding, so
re-uploading rejected bytes is rejected again. Registry erasure does not reach the verifier: agree
its logging and retention separately.

## Schema test credentials

`bregctl test --credentials <absolute-file>` reads one binding for every step of the packaged
journeys, and refuses a file that misses a step or binds one twice. Each credential is a bearer
token named by a secret reference, never inline
([Check, test, package](../../operate/breg/#check-test-package)).

```yaml
apiVersion: id.registrystack.org/formats/breg/schema-test-credentials/v1
kind: BRegSchemaTestCredentials
bindings:
  - journeyId: asset-and-site-caller-surfaces
    stepId: create-asset
    credential:
      type: bearer
      tokenRef: secret:file/operator-token
  - journeyId: asset-and-site-caller-surfaces
    stepId: planner-gets-asset
    credential:
      type: bearer
      tokenRef: secret:env/PLANNER_TOKEN
```

## Backup binding

A backup binding is the JSON document you write beside a database backup and pass to
`bregctl plan` and `bregctl apply` as `--backup <backupBindingPath>=<binding file>` for a
destructive migration. It stays outside the package, because each environment backs up its own
database ([Activate the successor](../../operate/breg-changes/#activate-the-successor)).

## Check commands

`bregctl check <project>` compiles the project offline. Adding `--runtime-config <file>` also
checks `runtime.yaml` as `breg` reads it at startup, against the project's access profiles, without
a database, network, or secret. `bregctl doctor --runtime-config <absolute-file>` then checks the
deployment: the package, database, audit destination, identity provider, and the other dependencies
`breg` opens. [Check a file before you deploy
it](../configuration-files/#check-a-file-before-you-deploy-it) describes diagnostics and exit codes.

One package carries every maintained Registry Stack client API: `@registrystack/client` on npm and
`registry-stack-client` on PyPI. It holds one namespace per product: `discovery` for Registry
Discovery, `evidence` for Registry Evidence, `breg` for Base Registry
Engine (BReg), `casework` for Registry
Casework<DocsetProduct product="registry-messaging">, `messaging` for Registry Messaging</DocsetProduct>, and `scheduling` for
Registry Scheduling<DocsetProduct product="registry-coordinator">, with `coordinator` for Registry Coordinator from the v0.44.0 client roster</DocsetProduct>. Each namespace keeps its own routes,
authentication, errors, and verification rules, because those contracts differ.

Rust is the canonical implementation. The Python and Node packages are thin bindings over it: they
convert native values, construct the Rust client, run one method, and map the validated result or
error. They implement no Python or JavaScript HTTP, route, authentication, Problem, redirect, retry,
cache, or pagination policy.

## Availability and compatibility

Registry Stack is pre-1.0 Beta software. Keep a client on the same Registry Stack release as the
deployment it calls unless a release note states a wider compatibility range.

The unified packages are published beginning with Registry Stack v0.26.1. Releases through v0.26.0
carry no Base Registry Engine client package and no unified package; they distribute one standalone
package per product instead. The `casework` namespace is present in those same unified packages
beginning with Registry Stack v0.30.0<DocsetProduct product="registry-messaging">; the `messaging` namespace is present
beginning with Registry Stack v0.38.0</DocsetProduct>; the `scheduling` namespace is present
beginning with Registry Stack v0.40.0. The `coordinator` namespace is selected
from v0.44.0. Published v0.43.0 packages have no Coordinator namespace; use a
Coordinator-enabled candidate until its matching package is published. Runtime
binary and image availability are separate release prerequisites.
Python requires version 3.11 or later and the wheels use the
Python 3.11 stable ABI (`abi3-py311`), so a later Python imports the same file. Node requires version 24.11
or later. Both packages select a native build for Linux amd64 with glibc, Linux arm64 with glibc, or
macOS arm64, and require glibc 2.17 or newer on Linux. The version-specific GitHub Release retains
the exact wheel and npm tarballs for an offline install.

The Rust crates have `publish = false`, stay source-only in the Registry Stack workspace, and are
not published to crates.io.

## Install a client

Read the version from the deployment's binary rather than typing it, then install that exact
version:

```sh
python -m pip install "registry-stack-client==<version>"
```

```sh
npm install "@registrystack/client@<version>"
```

The distribution installs as `registry-stack-client` and imports as `registry_client`. The two
spellings differ, so `import registry_stack_client` raises `ModuleNotFoundError`.

A TypeScript consumer also needs the Node type definitions, and must name them. The published
declarations use `Buffer`, a Node.js global, and TypeScript 6 does not load installed `@types`
packages on its own, so a project compiling against the declarations reports `TS2591` on every use
of `Buffer` until it has both installed the package and listed it in `compilerOptions.types`:

```sh
npm install --save-dev "@types/node"
```

```json
{
  "compilerOptions": {
    "types": ["node"]
  }
}
```

The package does not declare that dependency itself, because a JavaScript consumer does not need it.

A Rust application takes the source crate from the matching release tag. `registry-stack-client` is
the facade that re-exports the product clients under `breg`, `casework`, `discovery`,
`evidence`<DocsetProduct product="registry-messaging">, `messaging`</DocsetProduct>, `scheduling`, and `coordinator` modules in the v0.44.0 source; a single-product application can depend on that product's crate
directly instead.

```toml
[dependencies]
registry-stack-client = { git = "https://github.com/registrystack/registry-stack", tag = "v<version>" }
```

## Shared protocol and authentication

The [HTTP problem and recovery contract](https://github.com/registrystack/registry-stack/blob/main/products/platform/HTTP-PROBLEMS.md)
defines the common fields, bodyless Casework result states, Scheduling concealment,
meaningful Retry-After intervals and portable idempotency guidance. BReg keeps
`$top`/`$skiptoken`; Casework, Scheduling and Coordinator use `limit`/`cursor`.

Use Python `from registry_client.auth import PrivateKeyJwt` for a product-neutral
provider. The compatibility `breg.PrivateKeyJwt` is the same native class. Construct
one provider per resource/audience and scope set; one OAuth registration may request
separate tokens, and no bearer token grants universal product access. The
[per-resource profile](https://github.com/registrystack/registry-stack/blob/main/products/platform/ACCESS-TOKENS.md)
records token type, algorithms, actor rules, lifetime and network policy.

## What every client shares

The naming convention is fixed across the bindings:

- Rust methods that perform an exchange are asynchronous.
- Python uses the Rust method and option names in snake case, takes options as keyword arguments,
  and is synchronous. Each method releases the global interpreter lock while a private Tokio runtime
  performs the exchange, so other Python threads keep running. Nothing here crosses into `asyncio`.
- Node uses the camel case form, takes read options as one object, and returns a promise from every
  method that performs an exchange. A method that performs none returns its value directly.
- Reads return language-native values: dicts, lists, and `bytes` in Python; plain objects, arrays,
  and `Buffer` in Node. No wrapper type is needed to read a result.
- Timeouts are seconds in Python and milliseconds in Node. `trusted_root_certificates` accepts a PEM
  bundle as `bytes` in Python; `trustedRootCertificates` accepts it as a string in Node, except in
  the Discovery namespace, where it is a `Buffer`.

A method that sends an already-prepared request performs at most one service exchange, except for
the [same-key retry](#unknown-outcomes-and-the-same-key-retry) of a keyed mutation. A configured
private-key-JWT provider can make a separate token-endpoint exchange when it needs to acquire or
refresh a bearer. No client follows redirects, reads ambient proxy configuration, fetches referenced
schemas, or advances pagination on its own, and none retries any other exchange.

The Evidence client's profile-driven methods are the exception. `request`, `prepare_progressive`,
`contracts_candidate`, and `refresh_metadata` assemble or refresh a cached service snapshot first,
which can cost a protected-resource metadata fetch, an authorization-server metadata fetch, and, for
the `https-discovery` and `local-loopback-discovery` trust profiles, a service JWKS fetch. `request`,
`prepare_progressive`, and `contracts_candidate` also fetch the published definitions catalog when
the profile's contracts are `published` rather than a reviewed file. A cached, unexpired snapshot
skips all of it.

Base URLs may carry a deployment prefix. HTTPS is required except for loopback HTTP, and the URL
cannot contain credentials, a query, a fragment, or ambiguous empty path segments.

### Unknown outcomes and the same-key retry

A 5xx answer may follow a commit. A BReg, Casework<DocsetProduct product="registry-messaging">, Messaging,</DocsetProduct>
or Scheduling mutation that carries an idempotency key has an unknown outcome after every 5xx answer,
after a timeout or a broken exchange once the request was sent, and after a protocol failure: a 3xx
answer, or an answer that is oversized, cannot be parsed, or does not meet the contract. Its outcome
is known after a refusal before sending, a connection that was never established (a connect timeout
or a TLS failure included), and every typed 4xx refusal, such as a `429` limit or an idempotency
conflict. A credential the BReg token provider could not supply is known too: the client acquires it
once, before the first send. BReg's `410 idempotency.expired` is a known refusal as well: the first
attempt committed, and only its held response is gone.

Two typed BReg 500 failures are known outcomes too: `action.handler_failed` and
`statistical_dataset.domain_violation`. The engine returns them only with the attempt rolled back,
and the same request fails the same way, so the client never resends them. Every other 5xx answer
stays unknown.

The client resends the identical request, with the same key, headers, and body bytes, after a 5xx
answer with an unknown outcome, a timeout, or a broken exchange: at most twice by default, waiting 250 ms and then 500 ms, or
the service's `Retry-After` when that is longer and at most 5 seconds. A longer requested wait, or a
`Retry-After` that is not one delta-seconds value, ends the retries. A protocol failure is resent
only when its answer carried a 5xx status, and nothing is resent after a 4xx status line, even when
the rest of that answer could not be read. Each attempt has the full request timeout. Reads, and
operations that carry no idempotency key, are never resent.

In Rust, `is_outcome_unknown()` on the client error reports the classification, and
`with_maximum_mutation_retries` on the client configuration sets the count from 0, which sends once, to
2. The Python and Node clients run the Rust client and apply the same rule. Python takes the count
as the `maximum_mutation_retries` constructor keyword and Node as the `maximumMutationRetries` config member;
a value outside 0 to 2 is a `configuration` error. The Python error's `outcome_unknown` attribute and
the Node error's `outcomeUnknown` property report the classification as a boolean.

When the returned error still has an unknown outcome, the safe recovery is the same request with the
same key, sent within the service's receipt horizon: the service replays or settles it. A new key can
apply the mutation twice. A refusal that answers a resend does not prove the earlier attempt left no
effect, so the client returns the earlier unknown-outcome error instead of that refusal.

The receipt horizon is how long a service holds a key's first answer: BReg's
`retention.receiptRetentionDays`, 7 days by default<DocsetProduct product="registry-messaging">,
Messaging's `retention.receiptRetentionDays`,</DocsetProduct> and Scheduling's
`retention.receiptRetentionDays`. Every service answers a spent key by one rule: a different request
under it is an idempotency conflict, `409 idempotency.key-reused`, whatever the key's age. Past the
horizon the same request is refused with `410 idempotency.expired` and the key stays spent. In BReg
that `410` means the first attempt committed: read the record or its history rather than sending
the write again under a new key. In Casework it means an earlier attempt under the key committed and
retention erased only its stored response: reconcile by reading the review request, task, or
Directory before choosing a new key.<DocsetProduct product="registry-messaging"> In Messaging, once retention deletes
the message record after `retention.recordRetentionDays`, the request hash goes with it and any request under
the key is refused with `410`.</DocsetProduct>

## Registry Discovery

The Discovery client searches a published index, resolves a requirement to Evidence Types, and
records an inert exact selection. It is not a trust broker: a selection carries catalog metadata and
proves nothing about origin authenticity, catalog currentness, authorization, or adopter trust.
Endpoint trust and the call that follows stay with the relying application.

### Construct a Discovery client

```rust
use registry_discovery_client::{DiscoveryClient, DiscoveryClientConfig};
use url::Url;

let config = DiscoveryClientConfig::new(Url::parse("https://discovery.example.invalid/")?);
let client = DiscoveryClient::new(config)?;
```

```python
from registry_client import discovery

client = discovery.DiscoveryClient(
    base_url="https://discovery.example.invalid/",
    attempt_timeout_seconds=30,
    connect_timeout_seconds=10,
    maximum_response_bytes=8 * 1024 * 1024,
)
```

```js
const { discovery } = require('@registrystack/client');

const client = new discovery.DiscoveryClient({
  baseUrl: 'https://discovery.example.invalid/',
  attemptTimeoutMilliseconds: 30_000,
  connectTimeoutMilliseconds: 10_000,
  maximumResponseBytes: 8 * 1024 * 1024,
});
```

Node also accepts the base URL as a bare string. The client sends no credentials: a Discovery index
is public by construction, so there is no authorization option to set.

`DiscoveryClientConfig` provides `with_attempt_timeout`, `with_connect_timeout`,
`with_maximum_response_bytes`, and `with_trusted_root_certificates`.

### Discovery operations

| Operation | Rust | Python | Node |
| --- | --- | --- | --- |
| Resolve a requirement to Evidence Types | `resolve_evidence_types` | `resolve_evidence_types` | `resolveEvidenceTypes` |
| Search the catalog | `search_services` | `search_services` | `searchServices` |
| Search Evidence services | `search_evidence_services` | `search_evidence_services` | `searchEvidenceServices` |

Only those four operations reach the network. Every selection below is local and offline.

### Selections

A search returns `ServiceSearchResponse`, holding a `catalog_revision` and the matched
`ServiceRecord` items. Selecting turns exactly one record into a selection bound to the capability
that matched it.

| Selection | Rust | Python and Node |
| --- | --- | --- |
| One record by identifier and capability | `response.select_exact(request)` | `select_exact` and `selectExact` |
| One Registry Evidence service | `response.select_evidence(request)` | `select_evidence_service` and `selectEvidenceService` |
| One Evidence Type mapping alternative | `response.select_alternative(id)` | `select_evidence_alternative` and `selectEvidenceAlternative` |

Rust supplies the selections as extension traits on the response, `ServiceSearchSelectionExt` and
`EvidenceTypeResolveSelectionExt`. Python and Node expose the same four both as client methods and
as module functions, so an application that stored a response can select from it without holding a
client.

Three local operations act on a stored selection in Python and Node:

- `validate_selection_structure` and `validateSelectionStructure` check closed shape and capability
  binding, and nothing else. Structural validation grants no trust.
- `accept_selection` and `acceptSelection` apply an adopter-owned local policy callback and return
  an `AcceptedServiceSelection` carrying `endpoint_url` or `endpointUrl`. A callback that returns
  false raises kind `local-acceptance-refused`.
- `renew_unchanged_selection` and `renewUnchangedSelection` return a freshly reselected service only
  when its trust-relevant semantics are unchanged, and raise kind `selection-changed` otherwise. The
  current selection must come from a new online lookup.

Rust names the same three `validate_service_selection_structure`, `accept_service_selection`, and
`renew_unchanged_service_selection`.

### Discovery error contract

Python raises `discovery.DiscoveryClientError` and Node throws the same named class. Both carry
`kind` plus `status`, `problem`, and the transport subcategory (`transport_kind` in Python,
`transportKind` in Node) when the failure carries them. `kind` is one of `configuration`, `query`,
`no-matching-service`, `ambiguous-selection`, `no-matching-alternative`, `ambiguous-alternative`,
`capability-mismatch`, `local-acceptance-refused`, `selection-changed`, `transport`, `problem`,
`protocol`, and `client`. Rust returns the matching `DiscoveryClientError` variants.

For kind `problem`, `problem` is one of `invalid-request`, `not-found`, `result-bound-exceeded`,
`unavailable`, or `unknown`.

## Registry Evidence

The Evidence client requests minimum-disclosure assertions over the public Evidence HTTP contract
and verifies every response. Verification is the point of the client: a client built directly with
`EvidenceClientConfig::new`, or read `from_profile` with the `pinned-jwks` trust profile, verifies
against only a key set the caller pinned out of band; the deployment's own published key set is
never fetched to judge a response it also produced. A profile using the default `https-discovery`
trust (or `local-loopback-discovery`) instead fetches that published key set itself before verifying
against it.

### Construct an Evidence client

`trusted_jwks` and `revoked_key_ids` are mandatory trust inputs pinned out of band. A key set or
revoked-key list the verifier could never use is refused at construction.

```rust
use std::sync::Arc;
use registry_evidence_client::{EvidenceClient, EvidenceClientConfig, StaticToken};
use url::Url;

let config = EvidenceClientConfig::new(
    Url::parse("https://evidence.example.invalid/")?,
    Arc::new(StaticToken::new(token)?),
    trusted_jwks,
    Vec::new(),
);
let client = EvidenceClient::new(config)?;
```

```python
from registry_client import evidence

client = evidence.EvidenceClient(
    base_url="https://evidence.example.invalid/",
    trusted_jwks=trusted_jwks,
    revoked_key_ids=[],
    token=token,
    attempt_timeout_seconds=30,
    connect_timeout_seconds=10,
)
```

```js
const { evidence } = require('@registrystack/client');

const client = new evidence.EvidenceClient({
  baseUrl: 'https://evidence.example.invalid/',
  trustedJwks: trustedJwks,
  revokedKeyIds: [],
  token: { static: token },
  attemptTimeoutMilliseconds: 30_000,
  connectTimeoutMilliseconds: 10_000,
});
```

`maximumResponseBytes` and `maximum_response_bytes` bound the signed response `send` reads.
`maxMetadataBytes` and `max_metadata_bytes` bound the documents `discover` and `fetch_jwks` read,
which are neither signed nor verified, and are a separate decision. `user_agent` and `userAgent`
replace the default; `trusted_root_certificates` and `trustedRootCertificates` add trust roots for
the deployment.

### Token configurations

`token` names exactly one credential source. A configuration naming two is refused, so merging two
authentication settings cannot silently pick one. The two bindings spell the choice differently, and
this is the one place in the package where they do:

| Source | Python | Node |
| --- | --- | --- |
| A fixed bearer, sent unchanged | the bearer as a plain string | `{ static: token }` |
| A private-key-JWT client-credentials exchange | `{"private_key_jwt": {...}}` | `{ privateKeyJwt: {...} }` |

A Python `token` that is neither a string nor an object carrying exactly the one key
`private_key_jwt` is refused at construction with kind `configuration`. Note that this differs from
the `authorization` option of the BReg namespace, which names the static case explicitly
in both languages.

The private-key-JWT configuration requires `token_endpoint`, `client_id`, and `client_key` (Node:
`tokenEndpoint`, `clientId`, `clientKey`). Its optional members in Python are `audience`,
`resource`, `scopes`, `assertion_lifetime_seconds`, `refresh_margin_seconds`,
`attempt_timeout_seconds`, `connect_timeout_seconds`, and `user_agent`. Node takes the same eight
in camel case, with `attemptTimeoutMilliseconds` and `connectTimeoutMilliseconds` for the timeouts, and adds string-valued
`trustedRootCertificates` for the token endpoint. Python has no nested trust anchor for the token
endpoint: its top-level `trusted_root_certificates` crosses as genuine `bytes` and the nested
configuration crosses as JSON, which carries no byte values. `client_key` holds the private half; it
stays in the process and reaches nothing but the token endpoint. Rust passes an
`Arc<dyn TokenProvider>` instead, and can implement a custom provider.

The built-in exchange sends `grant_type`, `client_id`, `client_assertion_type`, and
`client_assertion`, adds `scope` when `scopes` is set, and adds the RFC 8707 `resource` when
`resource` is set. It sends no other form member. Use a pre-acquired short-lived static bearer when
an issuer requires one.

### Read a client from a profile

`from_profile` and `fromProfile` read an application-owned Evidence client profile, which carries
the base URL, a trust configuration, a contracts configuration, and the credential configuration in
one file; each is a reference to material, never the material itself. The profile is the owner-only
JSON document `evidencectl client profile create --output` writes. The trust configuration decides
whether the deployment's published key set is fetched: the default `https-discovery` trust (and
`local-loopback-discovery`) fetches and verifies against it, while `pinned-jwks` instead points to a
reviewed local key set file, so nothing is fetched. The optional second argument is a private JWK
held in memory, for an application that reads its key from a secret manager rather than from disk.
It is never retained by the wrapper, and profile paths and file-backed secrets are redacted from
every error.

```python
client = evidence.EvidenceClient.from_profile("evidence-client.json")
```

```js
const client = evidence.EvidenceClient.fromProfile('evidence-client.json');
```

Rust names the same entry points `EvidenceClient::from_profile`,
`EvidenceClient::from_profile_with_key`, `EvidenceClient::from_profile_path`, and
`EvidenceClient::from_profile_path_with_key`.

### Prepare, send, and verify

The three-step path closes what an application expects before anything is sent, spends that
expectation on one exchange, and judges the bytes that come back:

| Step | Rust and Python | Node | Returns |
| --- | --- | --- | --- |
| Close the expectations and generate a nonce | `prepare(spec)` | `prepare(spec)` | `PreparedEvidenceRequest` |
| Send the prepared request | `send(prepared)` | `send(prepared)` | `RawEvidenceResponse` |
| Verify the response against the request | `verify(prepared, response)` | `verify(prepared, response)` | `VerifiedEvidence` |

| Read the published key set | `fetch_jwks()` | `fetchJwks()` | A JWKS document |
| Refresh cached deployment metadata | `refresh_metadata()` | `refreshMetadata()` | Nothing |

`prepare` performs no input or output. The request it returns is good for exactly one exchange:
spend it with `send` or `request_and_verify`. Python takes the instant for `verify_as_of` as Unix
seconds; Node takes `asOfMillis` as Unix milliseconds.

The batch forms take the same shape one level up: `prepare_batch`, `send_batch`, `verify_batch`,
`request_and_verify_batch`, and `verify_batch_as_of` (camel case in Node). A verified batch carries
`items`, each `{"status": "available", "verified": ...}` or `{"status": "not_available"}` (Node:
`notAvailable`). `SdJwtVcBatchResponse` reads the issuance envelope answering a request that
presented several holder keys: `credentials` in the order the request presented them, `count`, and
`credential_for_holder_key(index)` or `credentialForHolderKey(index)`. Reading the envelope judges
nothing; each credential is verified individually.

A `VerifiedEvidence` carries `evidence` (the verified payload, field for field), the trace
identifier, and `pinned_subject_expectations` or `pinnedSubjectExpectations`. Persist those bindings
after a first-use acceptance and pass them back in the next request specification. Python spells the
specification member `subject_expectations`, taking either `"accept_first_use"` or the sequence of
role bindings itself. Node spells it `subjectExpectations`, taking either `'acceptFirstUse'` or
`{ pinned: [...] }`.

### Verify a hook delivery

`verifyHookDelivery` in Node and `verify_hook_delivery` in Python authenticate one exact BReg
Version 1 hook request with the shared Rust verifier. Pass the received method, request target,
headers, body bytes, and key without normalizing them. The result carries the authenticated
CloudEvents attributes, delivery metadata, and body. It does not decide whether the delivery is
fresh, expected by this receiver, or already applied; the receiver checks those, in this order.

In both examples, `event_store.apply_once()` (`eventStore.applyOnce()` in Node) is an
application-owned transaction that claims the event identity and commits the effect once, and
`apply_registry_event()` applies the payload the receiver expects.

```js
const { breg } = require('@registrystack/client');

const MAX_BODY_BYTES = 1_048_576;
const MAX_CLOCK_SKEW_MS = 5 * 60 * 1_000;
const EXPECTED_SOURCE = 'urn:registrystack:registry:example:instance:primary';
const EXPECTED_TYPE = 'case-created-v1';
const EXPECTED_DATASCHEMA =
  'urn:registrystack:registry:example:event:case-created-v1:schema:sha256:aaa';

function exactHeaders(rawHeaders) {
  const headers = Object.create(null);
  const names = new Set();
  for (let index = 0; index < rawHeaders.length; index += 2) {
    const name = rawHeaders[index];
    const normalized = name.toLowerCase();
    if (names.has(normalized)) throw new Error('duplicate webhook header');
    names.add(normalized);
    headers[name] = rawHeaders[index + 1];
  }
  return headers;
}

async function exactBody(request) {
  const chunks = [];
  let length = 0;
  for await (const chunk of request) {
    const bytes = Buffer.from(chunk);
    length += bytes.length;
    if (length > MAX_BODY_BYTES) throw new Error('webhook body is too large');
    chunks.push(bytes);
  }
  return Buffer.concat(chunks, length);
}

async function receiveWebhook(request, response, key, eventStore) {
  const body = await exactBody(request);
  const delivery = breg.verifyHookDelivery({
    method: request.method,
    path: request.url,
    headers: exactHeaders(request.rawHeaders),
    body,
    key,
  });

  const skew = Math.abs(Date.now() - Date.parse(delivery.deliveryTime));
  if (!Number.isFinite(skew) || skew > MAX_CLOCK_SKEW_MS) {
    throw new Error('hook delivery is outside the accepted clock skew');
  }
  if (delivery.source !== EXPECTED_SOURCE
      || delivery.type !== EXPECTED_TYPE
      || delivery.dataschema !== EXPECTED_DATASCHEMA) {
    throw new Error('unexpected webhook contract');
  }

  const eventIdentity = JSON.stringify([delivery.source, delivery.id]);
  await eventStore.applyOnce(eventIdentity, async () => {
    await applyRegistryEvent(JSON.parse(delivery.body.toString('utf8')));
  });
  response.writeHead(204).end();
}
```

```python
import json
from datetime import datetime, timezone

from registry_client import breg

MAX_CLOCK_SKEW_SECONDS = 5 * 60
EXPECTED_SOURCE = "urn:registrystack:registry:example:instance:primary"
EXPECTED_TYPE = "case-created-v1"
EXPECTED_DATASCHEMA = (
    "urn:registrystack:registry:example:event:case-created-v1:schema:sha256:aaa"
)


def receive_webhook(method, path, headers, body, key, event_store):
    delivery = breg.verify_hook_delivery(
        method=method, path=path, headers=headers, body=body, key=key,
    )

    sent = datetime.fromisoformat(delivery["delivery_time"])
    skew = abs((datetime.now(timezone.utc) - sent).total_seconds())
    if skew > MAX_CLOCK_SKEW_SECONDS:
        raise ValueError("hook delivery is outside the accepted clock skew")
    if (delivery["source"], delivery["type"], delivery["dataschema"]) != (
        EXPECTED_SOURCE, EXPECTED_TYPE, EXPECTED_DATASCHEMA,
    ):
        raise ValueError("unexpected webhook contract")

    event_identity = json.dumps([delivery["source"], delivery["id"]])
    event_store.apply_once(
        event_identity, lambda: apply_registry_event(json.loads(delivery["body"])),
    )
```

Python takes `headers` as a dict, which cannot hold a repeated header, so refuse a request that
repeats one before building the dict, and bound the body size before reading it. Node refuses body
and key buffers backed by shared memory and copies the rest before verifying.

Keep the key in server-side secret storage and never log the input or a failed delivery. A failure
raises `BaseRegistryClientError` with kind `hook-verification`; its `code` and message name the
input to check without rendering its value. Generation and attempt are decimal strings, so a 64-bit
generation never rounds in JavaScript. A delivery outside the skew bound can still carry a valid
signature, so reject it before deduplication. The idempotency key identifies one delivery generation
and survives automatic retries, but an operator replay creates a new generation and key. Deduplicate
an effect that must happen once on `source` plus `id`, or on a business key.
[Webhooks](../../operate/breg-webhooks/) covers provisioning the key and building a receiver.

### Bindings and writes

Select a binding from `BRegMetadata` before a write: `selectCreate` or `selectPatch` (snake case in
Python; `select_direct_write` in Rust), then pass it back to the client. A binding exposes nothing and
grants nothing; it ties the call to the client's origin, profile, route, and request contract. If the
metadata does not offer the operation, selection fails with kind `metadata-selection`.

Python: `create_record(binding, data, idempotency_key, *, format="json")` and
`patch_record(binding, record_identifier, etag, operations, idempotency_key, *, format="json")`.
Node: `createRecord(binding, data, idempotencyKey, format)` and
`patchRecord(binding, recordIdentifier, etag, operations, idempotencyKey, format)`. `data` maps API
field names to JSON values. Each patch operation is `{"op": "add" | "replace" | "test", "field":
..., "value": ...}` or `{"op": "remove", "field": ...}`. A patch needs the ETag from a fresh read
through the same route and profile. The client checks field names, value bounds, nesting, and body
size before sending; an input it refuses raises kind `invalid-request` with no exchange.

An idempotency key is 1 to 256 visible ASCII characters, excluding comma and semicolon. The client
never creates one, and resends a write only under the
[same-key retry](#unknown-outcomes-and-the-same-key-retry): same binding, body, precondition,
representation, and key. BReg keeps the response for a committed write for
`retention.receiptRetentionDays`. A resend within that horizon replays it; a resend after it answers
`410 idempotency.expired`. That `410` is a known outcome: the write committed.

### BReg error contract

Python raises `breg.BaseRegistryClientError`, an `Exception`, with `kind`, `code`, `refusal_code`,
`reason_code`, `field_path`, `constraint`, `status`, `trace_id`, `transport_kind`, `token_kind`, and
the boolean `outcome_unknown`; an absent member is `None`. Node rejects with
`breg.BaseRegistryClientError`, an `Error` with `kind`, the boolean `outcomeUnknown`, and the
optional `code`, `refusalCode`, `reasonCode`, `fieldPath`, `constraint`, `status`, `traceId`,
`transportKind`, and `tokenKind`.

| Kind | Meaning |
| --- | --- |
| `configuration` | Construction inputs were refused |
| `invalid-request` | An input was refused before any exchange |
| `token` | The token provider could not supply a bearer |
| `transport` | The exchange failed below HTTP |
| `not-found` | The server answered `resource.not_found` |
| `problem` | The server answered with any other Problem |
| `protocol` | The response broke the contract |
| `metadata-selection` | No binding matched the metadata |
| `hook-verification` | A hook delivery failed authentication |
| `client` | Any other client-side failure |

`refusalCode` carries the declared reason for `action.refused` or
`statistical_dataset.release_refused`, and `reasonCode` the reason for
`statistical_dataset.version_withdrawn`. A row-local constraint conflict sets `constraint`, with
`recordType`, `constraintId`, `constraintKind`, and `left` and `right` for `compare` or `field` for
`int-range` and `vocabulary`. The server omits it when any field involved is unreadable to the
caller, and default error rendering leaves it out.

A Problem code this client does not know arrives as kind `problem` with only `status` and the trace
identifier. Decide on the status: an unknown `4xx` is a refusal, and an unknown `5xx` may have
committed, so follow the same-key retry. `idempotency.expired` is a known code. The
[error tables](../breg-client-capabilities/#errors) list which attributes each kind sets and every
`code` value.

### Submit and recover a review

Select the policy by ID in `ReviewCreateRequest.policy`; Casework freezes its concrete version and

current-source context uses `mode: current-source` and a reference binding.
The subject supplies all five immutable binding fields.

These host-side functions take your complete `ReviewCreateRequest`, declared trusted-producer ID,
and retained idempotency key. They use the shared Rust canonicalizer, including its portable JSON

  return client.createOrRecoverReviewRequest(token, 'requester', key, request, digest);

### Revisions, actions, and recovery

Task mutations take the task UUID, displayed numeric revision, and caller-chosen idempotency key.
The client constructs the route and quoted revision header. Follow the
[same-key retry contract](#unknown-outcomes-and-the-same-key-retry) for ambiguous keyed mutations;
never invent a replacement key merely because the response was lost.

Read `review_task` to recover the caller's retained `decisionReceipt`, or use
`own_review_decisions` after a fresh sign-in. Receipts disclose the deciding caller's outcome and
pinned label without private reason or structured result data. Supervisory discovery returns
bounded task/accountability references with a holder-free state; it grants no decision or context
authority. It intentionally omits holder identities and due dates and does not provide a team
holdings board. The separate audited accountability read has its own retention.

Caseload preview selects the source officer's complete claimed set, optionally within one queue,
up to 100 tasks. It has no subset, limit or continuation parameter. A larger set refuses with
`review.query-too-broad`. Apply is atomic over the exact previewed set; individual task assignments
remain available for a selected subset, with independent revisions and outcomes.

### Casework error contract

`CaseworkClientError` is distinct from every other product's error. Rust uses `Configuration`,
`InvalidRequest`, `Transport`, `Problem`, and `Protocol`. Python raises
`casework.CaseworkClientError`; Node rejects with the same named error class. The language bindings
expose `kind`, status, problem code, validated trace context, bounded validation detail, transport
category, protocol failure, and `outcome_unknown` (Node: `outcomeUnknown`) when applicable.
Errors do not repeat rejected values or credentials.

Unknown problem codes retain the status and trace context without gaining known recovery meaning.
`review.policy-mismatch` is a `409` refusal of the expected policy binding. Validation details name
a bounded field `path` and closed `reason`, such as `policy-not-allowed`, `schema-mismatch`,
`outcome-not-declared`, `result-required`, or `constraint-violated`. A `410 idempotency.expired`
requires reconciling the original task, request, or Directory operation before choosing a new key.

## Registry Messaging

The Messaging client covers six routes: liveness, readiness, the submission of one message, the
read of one message's status, the cancellation of one message before dispatch, and the preview of
one template version. It carries no operator route and no provider callback route. The client never
reaches the Messaging runtime or its operator tooling; it speaks the public HTTP contract any caller
uses.

### Construct a Messaging client

```rust
use registry_messaging_client::{MessagingClient, MessagingClientConfig};
use url::Url;

let client = MessagingClient::new(MessagingClientConfig::new(
    Url::parse("https://messaging.example.invalid/")?,
))?;
```

```python
from registry_client import messaging

client = messaging.MessagingClient("https://messaging.example.invalid/")
```

```js
const { messaging } = require('@registrystack/client');

const client = new messaging.MessagingClient({
  baseUrl: 'https://messaging.example.invalid/',
});
```

`MessagingClientConfig` provides `with_attempt_timeout`, `with_connect_timeout`,
`with_maximum_response_bytes`, `with_user_agent`, and `with_trusted_root_certificates`. The Python
constructor takes the same settings as snake case keyword arguments, including
`maximum_response_bytes`; the Node constructor takes camel case config members, including
`maximumResponseBytes`.
`with_maximum_mutation_retries`, the Python `maximum_mutation_retries` keyword, and the Node
`maximumMutationRetries` member set the [same-key retry](#unknown-outcomes-and-the-same-key-retry) count
for `submit`.
A response is bounded to 4 MiB by default and to 16 MiB at most. The configuration holds no
credential, and its debug output redacts the base URL, the user agent, and any trusted root
certificates.

### Messaging operations

Method names are given in the Rust and Python form. Node uses the camel case form of the same name.

| Method | Takes | Returns |
| --- | --- | --- |
| `health` | Nothing | An empty value while the process serves |
| `ready` | Nothing | An empty value when the runtime can serve, and a `service.unavailable` problem otherwise |
| `submit` | The bearer token, an idempotency key, and the submission | The `MessageReceipt`: the message `id`, its `status`, and `links` |
| `message` | The bearer token and a message identifier | The `MessageView`: `status`, `dispatch`, `report`, the attempt summaries, and `links` |
| `cancel` | The bearer token and a message identifier | The `MessageView` as the cancellation left it |
| `preview` | The bearer token, a template identifier, a version, and a `TemplatePreviewRequest` of `locale` and `data` | The `TemplatePreview`: the template reference, `locale`, `channel`, `packageDigest`, the rendered `parts`, and `sms` segment counts for an SMS template |

Every call that reaches a caller route takes the request's bearer token as its first argument and
retains none. In Rust it is a `BearerToken`, built with `BearerToken::new(token)`. The module is for
a trusted server host, the way the Casework module is.

A submission requires an idempotency key the caller chose: 1 to 128 visible ASCII characters,
refused before any exchange otherwise. A key is scoped to the caller's verified issuer and subject.
The client never generates or replaces a key, and resends a submission only under the
[same-key retry](#unknown-outcomes-and-the-same-key-retry). After a lost response it still reports,
send the same key with the same submission within `retention.receiptRetentionDays`, and the runtime
answers the stored receipt instead of accepting a second message. A `403` or `422` answering an exact
retry does not show that the first attempt failed, so never resubmit under a new key: have the
operator restore the access, template version, or locale the refusal names, then retry under the
same key within `retention.receiptRetentionDays`, as the
[replay rule](../apis/registry-messaging/#contract-boundary) explains. A message
identifier must be the lowercase hyphenated UUID the runtime answered; any other value is refused
before any exchange. The view carries the recipient's channel with the value `redacted`, and no
rendered content.

### Messaging error contract

`MessagingClientError` is distinct from every other namespace's error type. Rust answers with
`Configuration`, `InvalidRequest`, `Transport`, `Problem`, or `Protocol`. A `Problem` carries the
status, the typed `ProblemCode` from the Messaging problem catalogue, and the validated trace
identifier. A `Protocol` carries a `MessagingProtocolFailure` of `HeaderBounds`, `TraceContext`,
`Body`, `MediaType`, `Problem`, or `Status`.

The catalogue is closed. A problem becomes a typed `Problem` only when its code is in the
catalogue, its status is the one the code pins, its type URI is the pinned one, and its trace
identifier matches the response's trace header. Anything else, including a code the client does
not know, is a `Protocol` failure with `Problem`. The title and detail are not compared: the caller
reads the pinned copies through `code.title()` and `code.detail()`, so a deployment that rewords
them still answers a refusal the caller can match.

A submission over its access profile's request rate or daily limit is refused with
`rate-limit.exceeded` or `quota.exceeded` and status 429. That `Problem` also carries
`retry_after_seconds`, the whole seconds the response's `Retry-After` asked the caller to wait. The
client accepts only a single delta-seconds value from 1 through `MAXIMUM_RETRY_AFTER_SECONDS`
(86,400, one day); an absent, repeated, or out-of-range header leaves the wait unset and the refusal
still typed. The wait is unset on every other status. The client never waits out a 429 or resends
the refused submission.

Python raises `messaging.MessagingClientError`, an `Exception` whose attributes are `kind`, `code`,
`title`, `detail`, `status`, `trace_id`, `retry_after_seconds`, `transport_kind`,
`protocol_failure`, and the boolean `outcome_unknown`; an absent member is `None`. Node rejects with
`messaging.MessagingClientError`, an `Error` with `kind`, the boolean `outcomeUnknown`, and the
optional `code`, `title`, `detail`, `status`, `traceId`, `retryAfterSeconds`, `transportKind`, and
`protocolFailure`; an absent member is undefined. The
`MessagingProblemCode` type in both bindings names every code of the catalogue, including
`rate-limit.exceeded` and `quota.exceeded`.

| Kind | Meaning | Members set |
| --- | --- | --- |
| `configuration` | The construction inputs were refused | none |
| `invalid-request` | An input was refused before any exchange | none |
| `transport` | The exchange failed below HTTP | `transport_kind` |
| `problem` | Messaging answered with an accepted problem | `status`, `code`, `title`, `detail`, and `trace_id`, plus `retry_after_seconds` on a 429 that named a wait |
| `protocol` | The response violated the contract | `status`, `protocol_failure`, and `trace_id` when one was validated |

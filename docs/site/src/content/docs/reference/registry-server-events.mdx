## Event configuration

Location: `entities[].events[]` or `extendEntities[].events[]` in a module.
Field paths in this table are relative to one event.
Types, requiredness, defaults, and descriptions come from the generated module schema.
Requiredness describes the YAML grammar; compiler rules follow the table.

<ConfigurationReference contracts={eventConfiguration(configuration)} prefix="server-events" compact />

Compiler rules:

- Event IDs must be unique across the registry.
- Projection must name at least one declared field.
- Production compilation requires a webhook destination.
- Conditions and projections use authored field IDs, not the record API's camel-case property names.
- Event classification is the highest classification of every projected or condition field.

Destination URLs, keys, network policy, and operational ceilings belong in runtime
`eventDestinations`, keyed by `webhook.destinationId`.
The runtime must bind the exact compiled destination set.
Its `classificationCeiling` must cover the event classification; runtime configuration cannot
add projected fields. See the [configuration reference](../registry-server-configuration/) for
destination fields and `eventDelivery.payloadRetentionDays`.

## Triggers and conditions

<EventReferenceTable id="triggers" />

A create-only entity permits only `created`; `tombstoned` also requires tombstone support.
Omitting `when` selects every matching trigger.
When present, `kind: fields` requires at least one nonempty test.
All tests combine with AND, including every field within each test.
`changed` compares before and after values, not whether a field appeared in the patch.
Comparison literals must be scalar or null and valid for the declared field type.

Capture and mutation commit in one transaction.
Delivery uses the captured projection; subsequent record or package changes do not recompute it.

## HTTP request

Method: `POST`. Target: the configured fixed path, without query parameters.
Encoding: [CloudEvents 1.0 HTTP binary mode](https://github.com/cloudevents/spec/blob/v1.0.2/cloudevents/bindings/http-protocol-binding.md),
with canonical JSON data in the body. All listed headers are present.

<EventReferenceTable id="headers" />

The package carries each event schema at
`generated/event-schemas/<entity-id>.<event-id>.schema.json`.
Record identifiers appear in the body, not in CloudEvents headers.

## Signature format

Algorithm: HMAC-SHA-256, a keyed hash shared by Server and the receiver.
Key: the exact secret bytes resolved by `hmacSha256KeyRef`, at least 32 bytes.
File secret bytes are neither trimmed nor hex-decoded.
This is a Registry Server format, not a CloudEvents signing standard.

Signing input starts with the ASCII bytes `registry-server-webhook-signature-v1`, without a
prefix or separator. Each subsequent value is prefixed with its byte length encoded as an
unsigned 64-bit big-endian integer, in this exact order:

1. `ce-specversion`
2. `ce-id`
3. `ce-source`
4. `ce-type`
5. `ce-time`
6. `ce-dataschema`
7. `X-Registry-Event-Generation`
8. `X-Registry-Delivery-Attempt`
9. `X-Registry-Delivery-Time`
10. Method bytes: `POST`
11. Configured request path bytes, without the origin
12. Content-type bytes: `application/json`
13. `Idempotency-Key`
14. Exact body bytes

Header values retain their original bytes; header names are not included.
The header value is:

```text
v1=BASE64URL_WITHOUT_PADDING(HMAC_SHA256(key, signing_input))
```

Verification requires a constant-time signature comparison, expected source/type/schema and
payload validation, bounded delivery-time skew, and deduplication before effects.
Freshness uses `X-Registry-Delivery-Time`, not `ce-time`.
The accepted skew is receiver policy, not a fixed Server limit.

## Delivery contract

<EventReferenceTable id="delivery" />

Runtime ceilings may tighten, never widen, compiled limits.
A durable attempt audit precedes the send.
Terminal audit, state transition, and successful payload erasure commit together.
Activation refuses destination changes that would strand retained nonterminal work.

### Retry and replay identity

<EventReferenceTable id="retry-replay" />

An idempotency key identifies one delivery generation, not an event across all generations.

:::caution[Replay can repeat an external action]
A new generation has a new idempotency key.
For effects that must happen only once across generations, receiver deduplication must also use
event identity (`ce-source` and `ce-id`) or a business key.
:::

{/* Evidence: crates/registry-server/src/webhook.rs, replay() and webhook_idempotency_key(). */}

## Operator commands

Command prefix: `registry-serverctl`. Add `--format json` for machine-readable reports.

<EventReferenceTable id="commands" />

`list` and `replay` connect directly to PostgreSQL using the runtime configuration.
The public record API has no outbox, payload, delivery, or replay endpoint.
Replay requires a retained, unexpired dead letter and the matching generation and activated
destination binding.

### List response fields

The JSON result contains a `deliveries` array. Each entry has these fields and no record values.

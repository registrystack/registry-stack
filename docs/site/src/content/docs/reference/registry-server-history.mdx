Use this reference for Registry Server retained history, corrections, and saved snapshot queries.
For model and deployment setup, use [configure your registry](../../configure/registry-server/).

## Query inputs

The snapshot query route is the configured record collection path with `:snapshot` appended.
It accepts the same permitted `$select`, `$filter`, `$orderby`, `$top`, and `$count` query options
as a live list route. It also accepts these history inputs:

| Input | Required | Meaning |
| --- | --- | --- |
| `snapshot` | No | Committed registry state to reproduce. Omit it to capture the latest committed state once. |
| `validAt` | No | Effective date or UTC timestamp within that recorded state. Omit it to return recorded state without an effective-time filter. |
| `$skiptoken` | No | Expiring continuation of an already authorized query, including its exact snapshot and effective time. |

Follow a continuation with only `$skiptoken` and, when needed, `accessProfile`.
Do not repeat or override the snapshot, effective time, selected fields, filters, ordering, count,
or page size bound into the cursor.

## Access boundary

A snapshot reference is a bookmark, not a credential.
The caller must use an authenticated access profile that explicitly grants the `snapshot`
operation on the route. Live `list` access and per-record `revisions` access do not grant
snapshot access. Current access rules apply on every request, including after a package or policy
upgrade.

Configure readable, filterable, and sortable fields, count permission, purpose restrictions, and
row restrictions through the usual access profile.
Historical queries use stored fields only. They cannot select, filter, or order by live derived
fields, and they cannot traverse live relationships.

## Effective time

An entity can declare a validity interval:

```yaml
temporal:
  startField: valid-from
  endField: valid-to
```

The start field is required. Both fields use the same `date` or `timestamp` type.
The end field can be null. Intervals include the start and exclude the end.
A non-null end must be later than the start.

Use a `temporal-non-overlap` constraint when intervals for the same subject must not overlap.
Its `scopeFields`, `startField`, and `endField` define the exclusion boundary.
The deprecated `temporal.scopeFields` spelling is accepted only as a transition aid and must match
an explicit non-overlap constraint.

Date intervals accept calendar dates such as `2026-06-05`.
Timestamp intervals require a UTC RFC 3339 timestamp such as `2026-06-05T00:00:00Z`.
Non-temporal entities reject `validAt`.
`recordedAsOf` is not supported.
Live-query `asOf` keeps its existing meaning.

## Correction context

Use the configured same-entity batch route to correct related intervals atomically.
Each patch item carries the record's current `ifMatch` ETag.
A batch can include one optional top-level context:

```json
{
  "kind": "correction",
  "reasonCode": "effective-date-corrected",
  "sourceReferences": ["case-document:correction-001"]
}
```

Place the object in `changeContext` beside `items`.
A correction requires a nonempty reason code.
The context is shared by the batch; item-level overrides are rejected.
`reasonCode` is limited to 64 UTF-8 bytes, `reasonText` to 4 KiB, and
`sourceReferences` to at most 16 entries of 256 bytes each.
Unknown members are rejected.

Only compiled temporal exclusion constraints are deferred until the final batch state.
Both interval-edit orders work. A final overlap or stale ETag rolls back the entire batch.
A stale edit returns `412 precondition.failed`.
Reusing an idempotency key with different items or context conflicts.

Correction context is absent from snapshot responses and default revision output.
A `revisions` grant can explicitly allow `provenanceFields` from `kind`, `reasonCode`,
`reasonText`, and `sourceReferences`. Shared context is omitted unless every affected revision is
currently visible to that caller.

## Coverage limits

History starts at an exact empty or verified existing-data baseline.
A saved reference never falls back to current data.
Authorized historical queries return `503 source.unavailable` when required history, compatible
field metadata, or a database execution budget is unavailable.
Unauthorized callers retain ordinary resource concealment.

Historical database statements have a two-second budget. Existing HTTP, projection, page, cell,
and response bounds also apply. One query can resolve at most 64 originating schema descriptors.
Descriptors retain field interpretation, not old access policy or executable code.

Supported policy-only and unrelated additive upgrades preserve queries over compatible requested
fields. A newly required or incompatible historical field makes the query unavailable instead of
inventing today's default. Reviewed bounded data migrations append internal `migration` revisions
and commit membership. They do not fabricate user patches or business events.

## Erasure maintenance

The migration authority can erase retained revisions for one record through a specified revision
number. This is irreversible maintenance, not a runtime API permission. It does not remove the
current record.
Apply the institution's live-data removal policy separately when required.

:::danger[History erasure is irreversible]
Confirm the target and approved revision boundary before running the command. Account for backups,
saved exports, and copies already delivered to consumers. A saved snapshot reference cannot restore
erased bytes.
:::

Prepare an absolute, owner-only JSON file, using permissions `0600` on Unix:

```json
{
  "entityId": "membership-record",
  "recordId": "00000000-0000-4000-8000-000000000001",
  "eraseThroughRevision": 2,
  "operatorReference": "approved-maintenance-001",
  "reason": "approved-retention-request"
}
```

Use the actual entity ID and record ID.
Keep this file private, including after the operation.
The command accepts a file so record identifiers and reasons do not need to appear in process
arguments:

```sh
registry-serverctl history erase \
  --runtime-config /absolute/path/runtime.yaml \
  --request-file /absolute/path/erasure.json
```

One transaction erases at most 10,000 retained revisions, scrubs affected shared correction
context and retained outbox payloads, and replaces affected cached idempotency responses with
refusal tombstones. Retrying those mutation keys cannot replay their old bodies or execute them
again. Required schema descriptors remain retained. The result and keyed audit contain counts,
not record values or reason text.

Snapshots at or after the earliest erased commit become unavailable, including later snapshots.
Erasing baseline data makes all snapshot coverage unavailable. Earlier complete snapshots may
remain usable. The command never silently re-baselines the registry.
Live writes and separately authorized maintenance remain available.

Operators remain responsible for current records, saved exports, copies already delivered to
external consumers, and backup expiry. Change-request proposals and application receipts have
their own retention policy and maintenance commands. Erasing record history does not erase those
separate workflow records. Neither a hash nor an opaque identifier is automatically anonymous, and
a saved bookmark cannot restore erased bytes.

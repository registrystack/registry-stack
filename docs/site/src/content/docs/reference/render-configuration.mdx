## Scope

This grammar is not frozen.

`manifest.yaml` declares the bundle's document types: each one's template, data schema, label
locales, version, and PDF standard. Each `labels/<locale>.yaml` holds one label table, and every
table must carry the same keys. `runtime.yaml` is what `registry-render serve` reads: listener,
package, secret providers, API key, limits, and audit.

The JSON Schema a document type names for its data is yours to write; Render applies it to every
request and has no schema of its own for it. A schema-valid file still needs `registry-render
check`, because rules across files, such as a label key the template reads, are not in these
tables. [Configuration files](../configuration-files/) describes the YAML rules and environment
substitution that apply when serve reads `runtime.yaml`.

Two rules are written as exclusions the tables do not show: each document's `entryFile` and
`schemaFile` is relative to the bundle root and contains no `..`, and `package.root` has no `.` or
`..` segment.

## Read the tables

`documents[]` means an array item; `labels.*` means a map entry whose name you choose. Required
fields inside an optional object apply when that object is present. Conditional fields depend on
another value, such as `audit.path` on `audit.destination`. `audit.rotateBytes` defaults to
100 MiB and `audit.retentionDays` to 90.

## Seal documents

The tables above list the `signing.seals.<id>` keys and the manifest's per-document `seal`. These
rules are not in the tables.

- Omit `signing` to leave sealing off. With it, at least one seal is required, and `serve` mounts
  `POST /v1/seal/{type}`. Without it, that path is an unknown route and `/ready` has no `signing`
  member.
- `signing` needs `auth.oidc`. Each seal has exactly one of `timestampAuthority` (B-T) and
  `withoutTimestamp: seal-stops-validating-when-certificate-expires` (B-B).
- `timestampAuthority.url` is `https`; `http` is accepted only for `localhost`, `127.0.0.0/8`, and
  `[::1]`. `attemptTimeoutMilliseconds` is 1000 to 60000 and defaults to 10000.
- The timestamp authority must answer in DER, as RFC 3161 specifies; a BER answer, such as one
  with indefinite lengths, is refused as `malformed-response`. Its token must be signed with
  RSA PKCS#1 v1.5 or ECDSA over SHA-256, SHA-384, or SHA-512; RSA-PSS and SHA-1 are refused as
  `token-signature-invalid`. Its signer must carry an ESS signing-certificate attribute (v1 or
  v2, RFC 5816) naming the authority's certificate, or the token is refused as
  `tsa-certificate-not-named-by-token`. Seal one test document through each authority before you
  rely on it for B-T.
- `certificateChainFile` is an absolute path with no `.` or `..` segment. The file is PEM, the
  seal certificate first. `privateKeyRef` is a secret reference to one ES256, ES384, RS256, or
  RS384 private JWK; EdDSA is refused.
- `allowedClients` is a list of at least one named client. `unrestricted` and any item containing
  `*` are refused. When `auth.oidc.allowedClients` lists clients, each seal client must be in it.
- `trust: test-only` is the only value. It sets `signing.testOnly` in the template payload, and
  every answer about the seal says so: `testOnly: true` in the JSON `seal` member, the `/ready`
  entry, and each audit entry of the call, and `X-Registry-Seal-Test-Only: true` on the PDF answer.
  `serve` logs one `test-only seal` warning per such seal at startup. A seal without `trust` carries
  none of these.
- A document type's `seal` must name a seal in `signing.seals`. A package that names an unbound
  seal is refused at `serve`; `check` reports it, and warns about a runtime seal no document type
  names.
- The seal is a certification signature (DocMDP permission 2) in an invisible field named
  `RegistrySeal`. The space it reserves is the certificate chain, twice the seal certificate's
  issuer name and serial number, and 2112 bytes of structure and signature allowance, plus 16 KiB
  when timestamped. A chain that needs more than 256 KiB is refused.

### Runtime and check problem codes

Serve and `check` report these as runtime problems at the position of the key.

| Code | Meaning |
|---|---|
| `render.runtime.signing-requires-oidc` | `signing` is declared with the legacy API key. |
| `render.runtime.no-seals` | `signing.seals` is empty. |
| `render.runtime.relative-path` | `certificateChainFile` is relative or has a `.` or `..` segment. |
| `render.runtime.seal-timestamp-undecided` | Neither `timestampAuthority` nor `withoutTimestamp` is declared. |
| `render.runtime.seal-timestamp-conflict` | Both are declared. |
| `render.runtime.insecure-timestamp-url` | The timestamp URL is `http` and not loopback. |
| `render.runtime.seal-clients-not-listed` | `allowedClients` is missing, empty, or not a list. |
| `render.runtime.seal-client-wildcard` | A client is `unrestricted` or contains a wildcard. |
| `render.runtime.seal-client-not-admitted` | A seal client is not in `auth.oidc.allowedClients`. |
| `render.runtime.seal-not-bound` | A document type names a seal `signing.seals` does not bind (error). |
| `render.runtime.seal-unused` | A runtime seal is named by no document type (warning). |
| `render.runtime.seals-not-served` | Document types name seals and the runtime has no `signing` block: they render unsealed (warning). |

`check --environment` and `serve` read the chain file and report:

| Code | Severity | Meaning |
|---|---|---|
| `render.runtime.seal-chain-unreadable` | error | The chain file cannot be read. |
| `render.runtime.seal-chain-invalid` | error | The file is not a usable certificate chain. |
| `render.runtime.seal-certificate-usage` | error | The seal certificate has neither the digitalSignature nor the nonRepudiation key usage. |
| `render.runtime.seal-chain-too-large` | error | The chain exceeds the signature space a seal may reserve. |
| `render.runtime.seal-certificate-expired` | warning | The certificate is expired; the seal is unavailable. |
| `render.runtime.seal-certificate-not-yet-valid` | warning | The certificate is not yet valid; the seal is unavailable. |
| `render.runtime.seal-certificate-expiring` | warning | The certificate expires within 30 days. |
| `render.runtime.seal-certificate-purpose` | warning | The certificate's extended key usage names none of document signing (RFC 9336 or Microsoft's), Adobe Authentic Documents, email protection or anyExtendedKeyUsage; validators such as Acrobat flag its seals. `serve` logs it at startup too. |

Each sealed document type is checked against its `pdfStandard`, at its `seal` member in
`manifest.yaml`:

| Code | Severity | Meaning |
|---|---|---|
| `render.bundle.seal-space-exceeds-standard` | error | The seal reserves more signature space than the standard's string limit holds: 65535 bytes under PDF/A-1, 32767 under PDF/A-2 and PDF/A-3. `check --environment` reports it, and `serve` refuses to start. |
| `render.bundle.seal-standard-unverified` | warning | No validator run has checked a file sealed under this PDF/A level: A-1a, A-2a, A-2u, A-3a, A-3b, A-3u, A-4e or A-4f. veraPDF has passed sealed A-1b, A-2b, A-4 and PDF/UA-1 files. `check` reports it from the bundle alone; `serve` logs it at startup for a seal it serves. |

Without `--environment`, `check` reads no chain file and says so: the human output ends with
`seal chains not read: pass --environment to check them`, and the JSON report has
`"sealChains": "not-read"`.

`serve` alone also reads the key and reports `render.runtime.seal-key-unreadable` (with the
secret provider's reason; a key file must be a regular file owned by the serving user, with mode
0600 or 0400 and one link), `render.runtime.seal-key-invalid`, `render.runtime.seal-key-unsupported`,
`render.runtime.seal-key-mismatch` (the key is not the one the certificate certifies), and
`render.runtime.seal-timestamp-client` (the timestamp client cannot be built from the URL).

### The seal route

`POST /v1/seal/{type}` takes the render route's request body and returns the document sealed. It
requires the `render:seal` scope, which `render:render` does not imply, from a client the seal's
`allowedClients` names. The legacy API key never seals. The signing time is the server's clock,
truncated to seconds. `GET /v1/documents` names the seal of each document type this route takes
as `seal`; a document type without it is refused here with `document-not-sealable`.

The default answer is `application/pdf` with these headers:

| Header | Value |
|---|---|
| `X-Registry-Document-Sha256` | SHA-256 of the first revision, the document Render rendered. |
| `X-Registry-Signed-File-Sha256` | SHA-256 of the whole signed file. |
| `X-Registry-Data-Sha256` | SHA-256 of the canonical request data. |
| `X-Registry-Document-Version` | Document type and version. |
| `X-Registry-Bundle-Hash` | The package hash `/v1/documents` reports as `bundleHash`. |
| `X-Registry-Warning-Count` | Number of render warnings. |
| `X-Registry-Seal-Id` | The seal id. |
| `X-Registry-Seal-Level` | `b-t` or `b-b`. |
| `X-Registry-Certificate-Sha256` | SHA-256 of the seal certificate. |
| `X-Registry-Timestamp-Time` | The timestamp token's time; B-T only. |
| `X-Registry-Seal-Test-Only` | `true`; only for a seal declared `trust: test-only`. |

With `Accept: application/json` the body is `pdfBase64`, `documentSha256`, `signedFileSha256`,
`dataSha256`, `documentVersion`, `bundleHash`, `warnings`, and `seal` (`id`, `level`,
`certificateSha256`, `timestampTime` for B-T, and `testOnly: true` for a test-only seal). A client granted only `render:seal` pins the
package from `bundleHash` without reading `/v1/documents`. There is no `pdfSha256`. Because the payload carries the `signing`
member, a sealed render's `dataSha256` differs from a plain render of the same request.

The problems specific to this route, from a closed vocabulary shared with the render route:

| Problem | HTTP | Exit code | Meaning |
|---|---|---|---|
| `forbidden` | 403 | 23 | The credential lacks `render:seal`, or is the legacy API key. |
| `seal-client-not-allowed` | 403 | 30 | The verified client is not in the seal's `allowedClients`. |
| `document-not-sealable` | 400 | 29 | The document type names no seal. |
| `signing-unavailable` | 503 | 26 | The seal's key provider is not ready. |
| `seal-certificate-invalid` | 503 | 27 | The seal certificate is expired, not yet valid, or cannot sign. |
| `timestamp-failed` | 502 | 28 | The timestamp authority gave no usable token. No file is returned and no retry is made. |
| `rate-limited` | 429 | 18 | As many seals as `limits.maximumConcurrentRenders` are already in flight. The call is refused, not queued. |

`/ready` adds `signing`, one member per seal: `{"status": "ready"}` or `{"status": "unavailable",
"reason": ...}` with `certificate-expired`, `certificate-not-yet-valid`, or `provider-not-ready`,
plus `"testOnly": true` for a test-only seal. It never changes the status code. At startup,
`serve` logs a `seal unavailable` warning with `seal_id` and the same `reason` for each seal that
cannot sign, and a `seal certificate expiring` warning for one whose certificate expires within
30 days.

Each seal call adds `sealId` to its audit entries, and `testOnly: true` when the seal is
test-only. The response entry adds `documentSha256`,
`signedFileSha256`, `certificateSha256`, and, for B-T, `timestampTokenSha256`.

A `timestamp-failed` response entry adds `reason`, the failing check, and the log has one
`seal refused` warning with the same `reason`. Neither carries a value from the exchange.

| `reason` | Piece |
|---|---|
| `connection-failed`, `timed-out` | The authority could not be reached within the attempt timeout. |
| `http-status`, `not-granted` | The authority answered with an HTTP error, or a status that grants no token. |
| `not-a-timestamp-reply`, `malformed-response`, `missing-token`, `not-tst-info`, `malformed-tst-info` | The answer is not a DER timestamp reply carrying a token. |
| `message-imprint-mismatch`, `nonce-mismatch` | The token does not answer this request. |
| `token-signature-invalid`, `tsa-certificate-not-named-by-token`, `tsa-certificate-not-for-timestamping`, `tsa-certificate-not-valid-at-gen-time` | The token does not verify under a timestamping certificate it names and that is valid at its time. |
| `token-not-embeddable`, `gen-time-not-rfc3339` | The token cannot be added to the signature. |
| `invalid-token` | Any other refusal of the token. |
| `response-too-large`, `token-too-large` | The answer exceeds 64 KiB, or the token does not fit the space the seal reserves. |

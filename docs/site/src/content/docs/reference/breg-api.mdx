registry serves the same route shapes over the Record types, fields, profiles, and Actions your

routes, with the exact schemas its package compiled.

## Authentication and profile selection

Every request except `/health`, `/healthz`, and `/ready` carries `Authorization: Bearer <token>`.
The token is a JWT from the configured issuer that carries `iss`, `aud`, and `exp`. Its scopes come
from the claim named by `scopeClaim`, split on `scopeSeparator`; the principal and purpose claims are
the ones named under `authorityClaims`. A missing or rejected token answers
`401 authentication.refused` before any profile is selected.

Each route has one default access profile; select another with the `accessProfile` query option. A
profile admits the caller when the token satisfies its `requiredScopes`, `requiredPurposes`, and
`principalClaim`, and the profile grants the operation on that Record type.

An unknown route, an unsupported method, an unknown or ungranted profile, and an ungranted
operation all answer the same `404 resource.not_found`. Reads conceal records outside the caller's
boundary; see [Read refusals](#read-refusals). A direct Create, direct Batch item, or Patch that
moves a visible Record outside the selected profile's row boundary answers
`403 write.outside-boundary`. The fixed problem has no field, value, claim, or location extension,
and no item commits. A hidden or absent Patch target and a stale condition remain the same value-free
`412 precondition.failed`. Ingestion items, immediate Action effects, and Proposal targets and
effects also retain their generic `412` boundary refusal.

## Record envelope

Reads, creates, patches, tombstones, revisions, and snapshots return the Registry Record envelope:

```json
{
  "data": {
    "recordIdentifier": "2d7e5e0c-5b2c-4b8e-9f1e-0d3c1a2b3c4d",
    "revisionIdentifier": "3",
    "domainData": {
      "code": "SITE-001",
      "label": "North depot",
      "location": {"type": "Point", "coordinates": [30.5234, -1.9441]}
    }
  },
  "meta": {
    "registryIdentifier": "asset-registry",
    "datasetIdentifier": "asset-sites",
    "recordTypeIdentifier": "asset-site"
  }
}
```

| Member | Type | Meaning |
| --- | --- | --- |
| `data.recordIdentifier` | string, UUID | Stable identity of the record. |
| `data.revisionIdentifier` | string, `^[1-9][0-9]*$` | Revision counter, starting at `1`. Compare as a string. |
| `data.domainData` | object | The record's fields under their `apiName`, narrowed to the grant's `readableFields` and to `$select`. |
| `meta.registryIdentifier`, `meta.datasetIdentifier`, `meta.recordTypeIdentifier` | strings | The registry, dataset, and Record type IDs from the compiled package. |

Fields travel under their `apiName`: by default the camelCase form of the field ID, so
`household-code` is `householdCode`. The field ID is never accepted in its place.

| Header | Value |
| --- | --- |
| `Content-Type` | `application/json`, or `application/ld+json` when the request sent `Accept: application/ld+json`. The JSON-LD form adds `@context` pointing at `https://id.registrystack.org/contexts/registry-record/v1`. |
| `ETag` | `"breg-hmac-sha256:<64 hex>"`, a strong validator of the current revision. Send it back in `If-Match`. |
| `Link` | `<https://id.registrystack.org/profiles/registry-record/v1>; rel="profile"`, then `</v1/schemas/{record_type_id}>; rel="describedby"`. |
| `Location` | On `201 Created`: `/v1/records/{route}/{record_id}`. |

Each Record type's generated JSON Schema carries these encodings.

### Response shapes

Generated and caller-filtered OpenAPI documents declare each route's response shape and a closed schema per media type.
A route family maps to a shape as follows:

| Route family | Response shape |
| --- | --- |
| Get, lookup, create, patch, tombstone | `RegistryRecordSingleV1` |
| List, relationship traversal | `RegistryRecordCollectionV1` |
| Revision detail | `BRegRevisionRecordV1`, a shared record with closed BReg history metadata |
| Revision list | `BRegRevisionCollectionV1`, a shared collection of revision records |
| Snapshot query | `BRegSnapshotCollectionV1`, a shared collection with snapshot selection metadata |
| Batch mutation | `BRegAtomicBatchMutationResponseV1` |
| Actions and Proposals | Their operation-specific BReg response shapes |
| GeoJSON get and list | `BRegGeoJsonFeatureV1` and `BRegGeoJsonFeatureCollectionV1` |

An operation that also serves GeoJSON carries `x-registry-responseShapes`, which assigns a shape to every media type.
The singular `x-registry-responseProfile` marker governs only the `application/json` and `application/ld+json` branches.
The GeoJSON branch keeps its named BReg shape in the `x-registry-responseShapes` map.
`ETag` values and idempotency request identity include the negotiated response representation.

## Collections and paging

A collection read returns `items`, `pageInfo`, and the same `meta` as a single record. Collection
members carry `recordIdentifier`, `revisionIdentifier`, and `domainData` directly, so the field path
is `items[0].domainData`, not `items[0].data.domainData`:

```json
{
  "items": [{"recordIdentifier": "…", "revisionIdentifier": "1", "domainData": {}}],
  "pageInfo": {"nextCursor": "eyJ…"},
  "meta": {"registryIdentifier": "asset-registry", "datasetIdentifier": "asset-sites", "recordTypeIdentifier": "asset-site"}
}
```

`nextCursor` is `null` on the last page. To continue, send it as `$skiptoken` with no other option
except `accessProfile`. The cursor is signed with the runtime `cursor.secretRef`, binds the whole
original query, and expires after `cursor.maximumAgeSeconds`; a cursor that fails any of those
checks answers `400 query.cursor_invalid`. With `$count`, the response carries the matching total.

## Query options

Options apply only where the grant permits them: `$select` draws from `readableFields`, `$filter`
from `filterableFields`, `$orderby` from `sortableFields`, and `$count` needs `allowCount`. Anything
else answers `400 query.invalid` with `fieldPath` naming the parameter. An unknown field and a
withheld field return the same problem, and the field itself is never named.

A grant that sets `requiredFilters` also refuses a list, and a `$count`, whose `$filter` does not
pin every field of one listed set with a top-level `eq` predicate. The answer is
`400 query.filter_required`, whose `requiredFilters` member names the acceptable sets as API field
names.
See [Require search criteria for lists](../../configure/breg-access/#require-search-criteria-for-lists).

$filter=status eq 'active' and (region in ('north','east') or startswith(label,'Depot'))
$filter=not contains(label,'closed') and validFrom ge 2026-01-01
bbox=30.0,-2.1,30.9,-1.8

### Access reason

A profile that sets `requireAccessReason` refuses a request without a `Registry-Access-Reason` header
with `400 request.access_reason_required`. The value is the reason as UTF-8 text, base64url-encoded
without padding. It must be one header, at most 684 characters encoded, decode to at most 512 bytes,
and be neither blank nor contain a control character. The reason is checked on Record reads and
direct writes, stored with each subject access log entry, and carried by a `read` event. On a Record
type with `accessLog`, a direct Create, Patch, Batch item or Tombstone stores one entry with
`accessKind: write` and the reason. A Record type without `accessLog` stores neither.

### Withheld records and fields

A `disclosureConditions` entry on a Record type withholds a record, its history or named fields from
the profiles it does not exempt. A withheld record answers as an absent one. A withheld member is
returned as `null` on reads and revisions, and is dropped from write responses. A Patch `test` on a
withheld member is refused like a guess at an absent one.

## Mutations

Every write needs `Content-Type: application/json`, except a patch, which needs
`application/json-patch+json`. A refused body answers `400 request.invalid`; see
[Problem documents](#problem-documents) for its `fieldPath`.

### Create

`POST /v1/records/{route}` with the fields the grant lists in `writableFields`:

```json
{"data": {"code": "SITE-001", "label": "North depot", "location": {"type": "Point", "coordinates": [30.5234, -1.9441]}}}
```

The response is `201 Created` with the envelope, `ETag`, and `Location`. Missing required fields,
values outside their type bounds, a reference to a missing or tombstoned target, and a violated `unique`
constraint are refused before anything is written.

### Patch

`PATCH /v1/records/{route}/{record_id}` takes a JSON Patch document whose paths are `/data/`
followed by the field's `apiName`:

```json
[
  {"op": "replace", "path": "/data/label", "value": "North depot (annex)"},
  {"op": "add", "path": "/data/closedOn", "value": "2026-12-31"}
]
```

`If-Match` must carry the `ETag` of the revision you read: a stale value answers
`412 precondition.failed` and a missing one `428 precondition.required`. The response is the new
revision's envelope.
Reference values must name active targets, as on Create.

### Tombstone

`DELETE /v1/records/{route}/{record_id}` with `If-Match` writes a final revision that marks the
record tombstoned and returns that revision's envelope. The record stays readable through its
revisions and leaves live collection reads. The route exists only when the Record type sets
`tombstone: true`.

An active Record that references the target prevents its tombstone, including when you cannot
read that referencing Record. The response is the generic `409 mutation.conflict`.
Clear an optional reference, point it at an active replacement, or tombstone its source Record
before tombstoning the target. Tombstoned Records and retained history keep their reference IDs.

### Batch

`POST /v1/records/{route}:batch` applies several items to one Record type in one transaction,
bounded by its `batch.maximumItems` and `batch.maximumBytes`:

```json
{
  "items": [
    {"operation": "create", "data": {"code": "SITE-002", "label": "East depot"}},
    {"operation": "patch", "recordIdentifier": "2d7e5e0c-…", "ifMatch": "\"breg-hmac-sha256:…\"", "patch": [{"op": "replace", "path": "/data/label", "value": "West depot"}]}
  ],
  "changeContext": {
    "kind": "correction",
    "reasonCode": "effective-date-corrected",
    "reasonText": "Site start date was recorded one month late.",
    "sourceReferences": ["case-document:correction-001"]
  }
}
```

The response is `{"snapshot", "results"}`. Each result carries `operation`, `recordIdentifier`,
`revisionIdentifier`, `etag`, and `domainData`.

`changeContext` is optional and covers the whole batch; an item-level override is refused. A
`correction` requires a nonempty `reasonCode`. `reasonCode` holds at most 64 UTF-8 bytes,
`reasonText` at most 4 KiB, and `sourceReferences` at most 16 entries of 256 bytes each. Temporal
non-overlap constraints are checked on the final state of the batch. One stale `ifMatch` or one
violated constraint rolls back every item.

### Idempotency

Send `Idempotency-Key` (1 to 256 visible ASCII bytes, without a comma or semicolon) on any create,
patch, tombstone, or batch. Proposal starts and transitions, attachment changes, immediate Actions,
and statistics publications require it.

- Keys are scoped to the verified issuer and principal; two callers never share one.
- A spent key answers `409 idempotency.key-reused` on any different request: the binding names the
  route, method, target, body, package activation, profile, and verified claims.
- Only successes spend a key. Correct a refused request and retry with the same key.
- An exact repeat returns the held response without writing, for
  `retention.receiptRetentionDays` after the commit (7 days by default), then answers
  `410 idempotency.expired` and is never executed; read the record instead.

## Ingestion runs

An ingestion run is the durable checkpoint of one bulk load that the client drives one chunk at a
time. The client keeps the source; the server keeps the checkpoint and never recomputes the source.
Only a chunk submission advances a run, and every operation rechecks the caller's authority against
the compiled batch route. A run is visible only to the issuer and principal that created it;
another caller's run and an unknown run answer the same 404. Run responses carry operational
metadata only, never source rows or record values. Every ingestion response carries
`Cache-Control: no-store`.

The ingestion routes refuse an `Idempotency-Key` header with `400 request.invalid`. The server
derives each chunk's attempt key from the run ID, input digest, chunk index, and chunk digest, so
resubmitting the exact chunk is always safe. For the procedure, see
[load records through an import window](../../operate/breg-data/#load-records-through-an-import-window).

### Create a run

`POST /v1/records/{route}/ingestion-runs`, `Content-Type: application/json`, a body of at most
4 KiB with exactly these members:

```json
{
  "operation": "create",
  "profileId": "operator",
  "packageRevision": "sha256:9f2c…",
  "schemaFingerprint": "sha256:1a7b…",
  "inputDigest": "5e8d…",
  "inputLength": 48211,
  "itemCount": 12000,
  "chunkCount": 13,
  "chunkAlgorithmVersion": "greedy-canonical-http-batch-v1"
}
```

| Member | Rule |
| --- | --- |
| `operation` | `create` or `patch`. A profile that holds `import` announces `create`. |
| `profileId`, `packageRevision`, `schemaFingerprint` | Nonempty strings that must match the selected profile and the active package. |
| `inputDigest` | SHA-256 of the whole source, 64 lowercase hexadecimal characters. |
| `inputLength`, `itemCount`, `chunkCount` | Integers from 1 to 2^53 − 1. |
| `chunkAlgorithmVersion` | Exactly `greedy-canonical-http-batch-v1`. |

The answer is `201 Created` with `{"run": <run document>}`. An import run is created only while the
Record type holds an open import authority for the profile whose remaining volume covers
`itemCount` and, when the authority pins digests, lists this `inputDigest`; otherwise the answer is
`412 precondition.failed` and no run exists.

### The run document

| Member | Meaning |
| --- | --- |
| `runId` | The run identifier, a lowercase UUID. |
| `status` | `open`, `complete`, `cancelled`, or `blocked`. |
| `blockedReason` | `null`, or `activePackageChanged` or `importAuthorityClosed` while `blocked`. |
| `recordType`, `operation`, `profileId` | The bound Record type, operation, and profile. |
| `packageRevision`, `schemaFingerprint` | The binding the run was created under. |
| `inputDigest`, `inputLength`, `itemCount`, `chunkCount`, `chunkAlgorithmVersion` | The announced source. |
| `maximumItems`, `maximumBytes` | The batch bounds every chunk stays inside, fixed at creation. |
| `nextChunkIndex` | The chunk index the next submission must name. |
| `committedItems`, `committedPrefixDigest` | Items committed so far and the prefix digest of the last committed chunk; the SHA-256 of empty input before the first. |
| `lastAttempt` | `null`, or `{"outcome", "chunkIndex"}`. |
| `createdAt`, `updatedAt` | RFC 3339 timestamps. |
| `complete` | `true` when `status` is `complete`. |

`lastAttempt.outcome` is `committed`, `replayed`, `invalidItem`, `refused`, `bindingChanged`,
`importAuthorityClosed`, `chunkMismatch`, `runNotOpen`, or `unavailable`. `invalidItem` and
`refused` leave the checkpoint where it was: continue the remainder in a successor run.

A run whose binding no longer matches the active package reports `blocked` with
`activePackageChanged`. An import run whose authority closed, expired, or ran out of volume reports
`blocked` with `importAuthorityClosed` at its next chunk, which commits nothing and answers
`409 ingestion.run_blocked`. A blocked run stays readable and never resumes; continue in a successor
run.

### Submit a chunk

`POST /v1/records/{route}/ingestion-runs/{run_id}/chunks`, `Content-Type: application/json`, with
exactly these members:

| Member | Rule |
| --- | --- |
| `chunkIndex` | Nonnegative integer. A fresh chunk must equal `nextChunkIndex`. |
| `items` | 1 to `maximumItems` batch items, each the object the `:batch` route accepts, all with the run's operation. |
| `digest` | SHA-256 of the canonical JSON of `{"items": [...]}`, 64 lowercase hexadecimal characters. That canonical body must fit in `maximumBytes`. |
| `prefixDigest` | SHA-256 of the source bytes from the start through the end of this chunk's last item. On the last chunk it must equal `inputDigest`. |

The chunking algorithm is greedy: each chunk takes as many consecutive source items as fit in
`maximumItems` and `maximumBytes`, and every remaining chunk must still hold at least one item.

A committed chunk answers `200` with `{"run", "receipt"}`. Its records, revisions, audit, receipt,
and checkpoint advance commit in one transaction. A chunk index below `nextChunkIndex` is a replay:
when its `digest` and `prefixDigest` equal the stored ones, the answer is the stored receipt with
`replayed: true` and nothing is written. Any other mismatch of index, digest, prefix digest, count,
or operation answers `409 ingestion.chunk_mismatch` and writes nothing.

An item whose prospective row falls outside the run profile's row boundary answers the run
protocol's value-free `412 precondition.failed`, records `lastAttempt.outcome` as `refused`, and
leaves the checkpoint unchanged. An ingestion item never answers the distinct
`403 write.outside-boundary`.

| Receipt member | Meaning |
| --- | --- |
| `chunkIndex`, `digest` | The committed chunk. |
| `replayed` | `true` when this answer replays an earlier commit. |
| `erased` | Always `false` in a served receipt. |
| `batch` | The `{"snapshot", "results"}` answer the chunk committed, projected to the fields the run's profile can read now. |

`GET /v1/records/{route}/ingestion-runs/{run_id}/chunks/{chunk_index}/receipt` returns the same
receipt without resending the chunk. A receipt is erased with the record history it describes;
then the read, and an exact replay of that chunk, answer `410 ingestion.receipt_erased`. The
chunk's counts stay in the run.

### List, read, and cancel

The list and read routes are in the [routes table](#routes). A restarting client rebuilds its
plan from the run document alone and never resends a committed chunk.

`POST /v1/records/{route}/ingestion-runs/{run_id}/cancel` takes an empty body with no
`Content-Type` and cancels an `open` or `blocked` run, answering `200` with `{"run"}`. A `complete`
or `cancelled` run answers `409 ingestion.run_not_open`. The counts, committed prefix, receipts, and
audit stay.

## History reads

`GET /v1/records/{route}/{record_id}/revisions` returns a collection of the record's revisions,
at most 100 per read, and `.../revisions/{revision}` returns one. Revisions show stored field
values only; derived fields and read paths are not evaluated over history. Correction context from
a batch appears only when the `revisions` grant lists `provenanceFields` (from `kind`,
`reasonCode`, `reasonText`, `sourceReferences`) and every revision that batch produced is visible
to the caller.

A revision written by applying a Proposal carries an optional `proposal` member,
`{"actionId", "proposalId", "submissionVersion"}`, on list items and on revision detail. It names the
Proposal submission that produced the revision. The member appears only when the access profile
that reads the history could also read that Proposal: it needs a `proposals` grant with `get` for
the Action, the same ownership and row boundaries a Proposal read applies, and a plain (not task)
grant. Otherwise the member is absent and the response is the same as one for a revision no
Proposal produced. A revision written by an immediate Action, a direct write, a batch or an import
never carries it. Operator erasure of a Proposal's detail (`bregctl proposal-retention erase`) keeps
the link: the identifier and state survive, and the Proposal read reports that its detail was
erased. The member disappears once a record the Proposal targeted is tombstoned, because a Proposal
read sees only active target records. If the check cannot finish, the read answers
`503 source.unavailable` instead of leaving out the member. The generated OpenAPI document declares
`proposal` only for a registry with a Proposal Action, and the caller-filtered `/openapi.json`
declares it only on the revision routes where the caller would receive it.

A temporal Record type, one with `temporal.startField` and `temporal.endField`, gains `:current`,
the records whose interval contains now, and `:as-of`, the records whose interval contains `asOf`.
Intervals include the start and exclude the end; a null end is open. A `date` interval whose
source records the last day in force names it with `temporal.lastDayField` in place of `endField`:
the interval then includes that day, a last day equal to the start is one day long, and two
intervals sharing a day overlap under `temporal-non-overlap`, which names the same `lastDayField`.
Responses return the stored last day unchanged. `asOf` follows the same rule
as `validAt`: a calendar date such as `2026-06-05` for a `date` start field, and a UTC RFC 3339
timestamp such as `2026-06-05T00:00:00Z` for a `timestamp` one. Both routes echo the value they
used as `meta.asOf` in JSON and JSON-LD responses.

On a `date` interval, now is today's date in the registry's time zone, `project.timezone`, an
IANA name such as `Asia/Colombo` or `UTC`. A project that answers today, through a `:current` read
of a `date` interval, a `currentDate` requirement, a live derived field that reads the
evaluation date, or a statistics dataset, must declare it; compilation otherwise fails with `breg.timezone.required`, and
an unknown name fails with `breg.timezone.unknown`. A `timestamp` interval uses the current
instant and needs no time zone.

## Proposals

An Action with `execution.mode: proposal` starts a durable Proposal at
`POST /v1/actions/{action}/proposals`. The routes are in the [routes table](#routes);
[Actions and Proposals](../../configure/breg-actions/#proposals) explains the model.

<ApiReferenceTable id="proposal-transitions" />

A Proposal read carries an `ETag`. Every transition, attachment upload, and attachment removal
requires `If-Match` with that value and answers `428 precondition.required` without it. The
Proposal `ETag` is distinct from a record `ETag` and is bound to the caller's profile, principal,
purpose, and target scope as well as the Proposal revision, so refetch after every transition and
never reuse another caller's value. Follow only the transition and attachment links the current
representation promotes.

### Observe an exact submission

`GET /v1/proposals/{proposal_id}/submissions/{submission_version}` reads one exact submission under
the Proposal Get authority: its frozen `effectDigest`, its `review` result, its `decision`, and its
`application` outcome as separate members. Only the current submission reports application
progress. Once its result window has lapsed and no application receipt remains, it answers
`410 proposal.submission_expired`; the Proposal stays readable.

### Proposal attachments

`GET`, `PATCH`, and `DELETE /v1/proposals/{proposal_id}/attachments/{slot_id}` read, upload, and
remove one slot's bytes. Slot descriptors on the Proposal carry requiredness, byte limit, content
types, classification, verification, and the links the caller may follow. Submission binds the
exact content digest; changed content needs a new submission and fresh review.

## Immediate actions

An Action with `execution.mode: immediate` runs one atomic plan at `POST /v1/actions/{action}` with
`Idempotency-Key`. Input names are exact `apiName` values, validated against the compiler-emitted
JSON Schema in the Action descriptor. Invoke requires Action authority over every existing
reference target, including each of several inputs that reference the same Record type. The
descriptor's `requiredConditionKeys` separately lists the input API names that require concurrency
conditions: existing write targets and inputs governed by an `unchanged` revision guard.

When `requiredConditionKeys` is nonempty, `conditionRoute` and `routes.targetConditions` advertise
`POST /v1/actions/{action}/target-conditions`. Send an `input` object containing exactly those
condition inputs. The response's `preconditions` object carries one opaque `ifMatch` value for
each key; send that object unchanged with Invoke. A target-condition request or Invoke
`preconditions` member for any other input is refused.
When `requiredConditionKeys` is empty, the descriptor advertises no target-conditions route and
the Invoke schema and runtime allow `preconditions` to be omitted or supplied as an empty object.
Prefer to omit the member for such an Action.

Send `Content-Type: application/json`.
When the Action declares files, include every declared file in an `attachments` object beside `input`.
Each file has `contentType`, a lowercase hexadecimal `sha256` digest and base64 `content`.
The [record slot configuration](../../configure/breg/#keep-a-file-with-a-record) shows the request format.
Availability and target-condition requests refuse an `attachments` member.
An Invoke refuses a file whose stored verification verdict is already rejected with `412 precondition.failed`.
An unseen or pending file can commit, but downloads stay concealed until verification approves it.

Effects, revisions, audit, receipt, and outbox commit together or not at all; resend the original
request with its original key when the outcome is uncertain. See
[Actions and Proposals](../../configure/breg-actions/) for the model.

An immediate Action with a reference input advertises one `routes.availability` endpoint at
`POST /v1/actions/{action}/availability`. Send `targetInput` with the reference input's exact
`apiName`, plus an `input` object containing its UUID and any declared form values already known.
Each request checks one target. Query several reference inputs separately.
The response reports advisory `available` as `true`, `false`, or `null`. A known answer includes
`observedRevision`. `guard-not-satisfied` means a field guard failed. `input-required` names a
nonempty set of declared API input names in `missingInputs`. `not-disclosed` carries
`observedRevision: null` and no missing-input names because the selected profile cannot safely
inspect the guard or boundary. A known failed guard takes precedence over missing guard input.
No availability response names a guard ID or a Record value.
The route evaluates only field guards for that one target. It does not run a Function, test SQL
uniqueness or Evidence, inspect other targets, supply a condition token, or grant mutation
authority. A true answer means only that the selected target's field guards are currently satisfied,
including when it has none. Form completeness, Functions, Evidence, other targets, and SQL
constraints may still refuse. Invoke checks authority, concurrency, and every guard in the commit
transaction.

## Registry metadata

`GET /v1/registry?accessProfile=<profile>` describes the active BReg contract under the selected caller and profile.
Discovery grants no authority: execution rechecks current package identity, verified claims, fields, rows, and operation grants.
Unknown and ungranted work remains concealed.
Discard metadata, Records, ETags, cursors, and drafts when the caller or profile identity changes.

The served format is `metadataVersion: "2"`.
Clients refuse version 1 before interpreting its shape, and there are no aliases for retired members.
Unknown optional extensions remain ignorable within the validated version-2 grammar.

### Record types and operations

Runtime metadata describes configured Record operations, their exact method and path, selected access profile, fields, request contract, query capabilities, and required capabilities.
Use the served operation descriptor instead of constructing a path from a Record label.

Field IDs are stable authored identities, and `apiName` is the exact wire property, so never derive it by changing case or punctuation.
Requiredness, nullability, readability, writability, removability, value schema, and native storage validation are separate properties.
PostgreSQL regular-expression validation is not a JavaScript validator.
Preserve int64 values and fixed-scale decimals without lossy conversion.

Display labels and safe instance titles help applications present the contract, so render them as plain text.
A title exposes only fields the current profile can read.
Reference descriptors and bounded forward and inverse navigation reuse normal Record authority, and a link or relationship never grants target disclosure.

Use the advertised `$filter`, `$orderby`, `$select`, `$top`, and `$count` query capabilities and bounds.
Filters reduce a permitted collection; they do not supply authorisation.
Continuation uses the opaque cursor and selected profile.
References, spatial reads, historical reads, and statistical datasets expose only their declared capability variants.

Record routes use the shared Registry Record v1 envelope.
Its independently versioned `recordTypeIdentifier` names the Record type; it is not a BReg authoring key.
Action receipts and Proposals have separate response contracts.
All responses use `Cache-Control: no-store`.

`requiredCapabilities` is a must-understand execution gate, and an unsupported capability disables its operation.
Unknown optional object members remain ignorable within the client's validated grammar.
Malformed required members, duplicate identities, resource bounds, and broken references refuse selection.
A descriptor alone never permits an operation under another profile.

Runtime metadata flags `mayBeWithheld: true` on each field a `fields` condition names for the selected
profile. It also lists the bound conditions as `disclosure`, each with its `id` and `withhold`, and the
field names of a `fields` condition. It never carries the `when` literals. A profile that no condition
binds sees neither member.

### Event records

A Record type that declares an event record descriptor carries an `eventRecord` member, filtered for the caller and profile.
It holds `descriptorVersion`, `label`, `recordedTime`, and only those subjects, sources, summary, correction, source event identifier, and time mappings whose fields the profile can read.
BReg omits withheld and undeclared members rather than sending `null`.
A native `target` is kept only when that Record type is visible to the caller.
The member is additive and ignorable within `metadataVersion: "2"`, and it grants nothing.
[Event records](../../configure/breg-event-records/) describes the declaration.

### Actions in metadata

One Action descriptor carries a fixed `mode`: `immediate` or `proposal`.
It includes stable identity and revision, public names, typed inputs, reference inputs, bounds, permitted results, required capabilities, and the promoted route for Invoke or Start.
Selection validates the descriptor before producing an opaque client binding.
Every input requires the compiler-emitted JSON Schema; clients do not reconstruct a partial schema from a field type.
The MCP gateway copies that schema exactly, and the caller cannot change an Action's execution mode.

Request metadata for the intended `accessProfile`, select the Action from that caller-filtered document, and prepare from the resulting binding.
Do not discover profiles by probing an Action route: an omitted profile when no default exists, an unknown profile, and a profile unusable by the caller all return the same concealed 404, with no list of alternatives.

For an immediate Action, `required` means the value must be present at Invoke.
For a Proposal Action, Start, Edit, Revise, and Rebase can retain an incomplete draft, and Submit enforces required inputs before any plan runs.
Supplied values are always typed and remain subject to the selected profile's input authority.
Immediate Invoke commits one atomic plan, and Proposal Start returns a durable Proposal with its own locator and revision.
Generated TypeScript and Python project types come from the same compiled contract, and generic metadata clients remain available.

For build-time form generation, `bregctl generate actions PROJECT --output DIR` writes the public `action-contracts/v1` document and its schema under `generated/`.
Check the format version and each Action's revision when consuming it.
This export is a build artifact, not an activated-package discovery endpoint.
It describes the authored contract without a caller's grants, so use runtime metadata and promoted Proposal links for current permissions and availability.
Regenerate it when the authored Action changes.

A caller-visible Proposal Action includes declared `attachments` summaries: slot `id`, `required`, `contentTypes`, and `maximumBytes`.
A starter can explain document requirements before creating a draft.
A Get-only Action description includes only that profile's readable slots.
These summaries disclose no bytes or lifecycle links and grant no upload, download, or delete authority.

A Proposal Action's `execution` also carries `review` and `application`, for example `{"mode": "proposal", "review": "required", "application": "automatic"}`.
`review` is `none` or `required`: whether a submitted request is reviewed before it can be applied.
`application` is `manual` or `automatic`: whether an approved or review-free submission waits for Apply or the built-in executor applies it.
An immediate Action carries neither member.
The values let a host explain what happens after Submit.
`required` does not say who reviews: a review provider can assess a request automatically, so a host should not promise that a person will read it.
They name no review authority, source, or policy, and grant no review or Apply authority.
Rust exposes `review()` and `application()`, Node exposes `review` and `application`, and Python exposes `action["review"]` and `action["application"]`.
An absent member means an immediate Action or a server that predates these members, so treat it as unknown rather than guessing a default.
Rust keeps a value this client version does not recognise as `Unknown`, and Node and Python return it as served.
A member that is not a lowercase identifier string fails the whole metadata document as a protocol error.

`proposals.actions` is a read-only inventory of each visible `actionId` and `accessProfile` pair, its `operations`, and its `readableInputs`.
Rust exposes `proposal_actions()`, Node exposes `proposalActions`, and Python exposes `proposal_actions`, all from one validated client model.
Profiles are never unioned.
Start does not imply Get, and List or Apply can be advertised without a Start route.
Hosts can use the exact inventory to choose their UI, while per-Proposal links still determine currently available lifecycle operations.

### Proposals and promoted links in metadata

Proposal representations are distinct from Registry Record envelopes.
An ordinary authorised Get carries `id`, `actionId`, `actionRevision`, `submissionVersion`, `revision`, `state`, the frozen `effectDigest` when known, and caller-authorized links.
Disclosed inputs, attachments, application evidence, and `applicationStatus` follow their independent permissions and retention.

Keep the exact Action revision, submission version, and effect digest while observing progress.
Revise or Rebase makes the earlier frozen binding stale, and a consumer must not silently follow the successor.
`applicationStatus` reports local application state, a safe blocked reason and recovery hint, and bounded automatic retry information where applicable.
Applied work exposes retained application evidence.
Get does not aggregate another product's live status or reconcile an uncertain Start or Submit.

Promote links only through a client-bound Proposal.
Validate origin, registry base, method, selected profile, operation binding, and the strong lifecycle condition.
Never substitute a Record ETag, invent a lifecycle URL, or follow a credential-bearing redirect.
Refetch after a transition and select a new link.
List requires explicit List authority and conceals inaccessible work before filtering or counting, and Get alone does not permit collection discovery.

Attachments expose only granted slots and operations.
Respect each slot's byte bound, content types, required-for-submit rule, verification status, and current revision.
Submission binds content digest and verification, so changed bytes cannot inherit an earlier approval.
BReg sends review context, not raw attachment bytes, to the review authority.

### Prepare, execute, and recover

Retain the original prepared command with its input, target conditions, selected binding, and idempotency key until its outcome is known.
Replay of that exact command recovers a retained result without replanning or reacquiring Evidence.
A changed command returns `409 idempotency.key-reused`, the only wire code for a key bound to another request.

## Problem documents

A refusal is an RFC 9457 problem document with `Content-Type: application/problem+json`:

```json
{
  "type": "https://id.registrystack.org/problems/registry-breg/request/invalid",
  "title": "Bad Request",
  "status": 400,
  "detail": "The request is invalid.",
  "code": "request.invalid",
  "traceId": "3f1a9c2e5b7d4e6f8a9b0c1d2e3f4a5b",
  "fieldPath": "/data/householdCode"
}
```

Branch on `code`. `type` is the same code with each dot read as a path segment under
`https://id.registrystack.org/problems/registry-breg/`. `detail` is the registered text of the code.
`traceId` is 32 hexadecimal characters that also appear in the request log and, for every journaled
request, in its audit record. A request refused before admission for presenting no credential is
counted on the metrics listener rather than journaled; see
[scrape metrics](../../operate/breg-monitor/#scrape-metrics).

`fieldPath` is present only when one member is at fault:

| Refusal | `fieldPath` |
| --- | --- |
| Create body | `/data` for a missing `data` member or a field you may not write, known or not; `/data/<apiName>` for a missing required field or a wrong value of a field you may write. |
| Patch document | `/<n>` for operation `n`, `/<n>/op`, `/<n>/path` for a path outside `/data/` or a field you may not write, known or not, and `/<n>/value`. |
| Batch body | `/items`, `/changeContext`, `/items/<n>`, `/items/<n>/operation`, `/items/<n>/recordIdentifier`, `/items/<n>/ifMatch`, `/items/<n>/patch`, and the create and patch forms above under `/items/<n>` and `/items/<n>/patch`. |
| Header | `Idempotency-Key` when it is missing or malformed; `If-Match` when a batch request sends one, because each batch item carries its own `ifMatch`. |
| Query | The parameter: `$select`, `$filter`, `$orderby`, `$top`, `$count`, `$skiptoken`, `bbox`, `accessProfile`, `asOf`, `snapshot`, or `validAt`; on statistics routes also `from`, `to`, or `status`. A revision route takes none but `accessProfile` and names the first other one you sent. |

A name you sent is never echoed: an unknown member and a withheld one stop at the same location.
An oversized or non-JSON body, an undefined query parameter, a malformed query string, and the
lookup, ingestion, attachment, and GIS routes carry no `fieldPath`.

A direct create, patch, or batch that violates an authored row-local constraint answers
`409 mutation.conflict` and may add the declared location:

```json
{
  "recordType": "permit",
  "constraintId": "chronological-validity",
  "constraintKind": "compare",
  "left": "valid-from",
  "right": "valid-to"
}
```

`compare` carries `left` and `right`; `int-range` and `vocabulary` carry `field`. The members appear
only when the selected profile can read every referenced field, and never on Action or Proposal
effects. They hold declared identifiers only, never a submitted value or database message. An
explicit constraint `id` is the stable key to map on; an omitted one is compiler-derived and
changes with the declaration. `unique` and `temporal-non-overlap` conflicts stay generic.

### Signature

exact body. The body is at most 1 MiB and the other fields together at most 32 KiB.

## Spatial adapter

A Record type with a `crs84-point` or `crs84-polygon` field and a `geojson.geometryField` is also
served under `/v1/gis` for desktop GIS clients, with `bbox`, `limit` (at most 10000), and `cursor`
on the item route. The polygon field accepts GeoJSON Polygon and MultiPolygon values. The adapter
answers GeoJSON feature collections under the same profile, grant, readable-field, and row-boundary
rules as the record routes.

The landing document declares `breg-gis-bounded-crs84-point-bbox-v1` when the caller sees only
Point collections. It declares `breg-gis-bounded-crs84-geometry-bbox-v1` when at least one visible
collection uses a Polygon or MultiPolygon. Point collection details keep
`bounded-crs84-point-bbox`. Polygon collection details declare `bounded-crs84-polygon-bbox`.

A bbox match is inclusive and uses actual geometry intersection. A Polygon or MultiPolygon whose
envelope overlaps the box does not match unless its geometry does. The adapter makes no OGC API
Features conformance claim, computes no collection extents or areas, and does not change ring order
or winding.

## Statistical datasets

<ApiReferenceTable id="statistical-dataset-routes" />

Every statistical operation requires a profile selected with `accessProfile`; a released-data
reader needs no record permissions.

`GET /v1/statistics/{dataset}:exact` serves exact values for ended periods to a profile holding
`read-exact`, which needs no record permissions. `from` and `to` are required and name ended periods at or
after `firstPeriod`; there is no default. A range that reaches a period that has not ended is refused with
`422` `statistical_dataset.release_refused` and `refusalCode` `period-not-ended`. `accessProfile` and `Accept` (JSON or CSV) work as on the live
route, with the same cell and document size bounds. A dataset whose derived field reads the evaluation
date accepts one period per request (`from` equal to `to`). The document carries
`exact: {"evaluatedAt": "<date>", "accessProfile": "<caller profile>"}` in place of `live`, with no
`release` and no `disclosure`, and its statuses are `exact` and `not-applicable` only. The read computes
under the dataset's `exactReads` profile, not the caller's; each read is audited as `read-exact` with
`periodFrom` and `periodTo`.

`POST /v1/statistics/{dataset}/releases/{period}/versions:dry-run` is the publisher's dry run, for every
dataset with releases. It takes the body of a publication, `{"status":"provisional"}` or `{"status":"final"}`,
and no `Idempotency-Key`. It runs the publication's computation and checks and answers `200` with
`{"document", "suppressions"}`: `document` is the release document a publication made at that moment would
store, including its next version number (a dry run takes no publication lock, so a publication made in
between takes that number), and `suppressions` lists each suppressed cell as its index in
`document.cells` and a `reason`, one of `minimum-count`, `minimum-contributors`, `dominance`, or
`contains-suppressed-sum`. The list of reasons can grow. `suppressions` adds about 50 bytes per suppressed cell
to a document of at most 8 MiB, so a client reading the dry run of a dataset near that bound needs a response
limit above its 8 MiB default. A dry run stores nothing and reserves no version; it writes an audit attempt and
one terminal entry. It is refused as a publication is, with `422` `statistical_dataset.release_refused`
and a `refusalCode` such as `negative-value`.

Document reads from the live, exact, series, latest-version, and exact-version routes send
`Cache-Control: no-store`, `Vary: authorization, accept`, and `Repr-Digest` for the exact JSON or
CSV bytes. The release listing omits `Repr-Digest`. A version header's `contentDigest` identifies
the canonical stored JSON; a withdrawn version's header omits it. No strong `ETag` is issued.

A JSON document lists the declared measures in `dataset.measures`, and each cell names its measure
in `measure`. A count's and a distinct count's `value` is a JSON integer. A sum's, a mean's, a ratio's, and a percentile's `value` is a decimal string such as
`"1234.50"` with exactly the measure's `scale` digits after the point, or null for a mean or a percentile over no values and
for a ratio with a zero denominator, whose status is `not-applicable`. Statuses are `exact`, `suppressed`, `rounded`, and `not-applicable`; the
vocabulary can grow, so treat an unknown status as no usable value. A release under
`minimum-count-and-rounding` uses `exact`, `suppressed`, and `rounded`, and carries counts, distinct counts, and sums
(whose publication is held for review); means, ratios, and percentiles are read live or exactly. A release under `exact-public-values` uses `exact` and `not-applicable` only, and
carries every measure type.

A released document's `disclosure` member has one of two shapes. Under `minimum-count-and-rounding` it is
an object with `method`, `minimumCount`, `roundingBase`, `roundingRule`, and `totals`, and, for a dataset that
releases a sum, `contributor`, `dominanceRule`, and `sumTotals`, never the dominance percentage. Under
`exact-public-values` it is exactly `{"method": "exact-public-values"}`. CSV columns are `period,periodStart,periodEnd,<dimension field IDs...>,measure,value,status`.
A suppressed or null value is blank, and a decimal string is written as it is; a zero stays zero with its status. Totals round independently; see
[publish statistics](../../configure/breg-statistics/#review-what-a-release-discloses) for the
inference risks. Unknown datasets and ungranted profiles answer the concealed 404, and invalid
ranges `400 query.invalid`.

registry serves the same route shapes over the Record types, fields, profiles, and Actions your

## Authentication and profile selection

Every request except `/health`, `/healthz`, and `/ready` carries `Authorization: Bearer <token>`.
The token is a JWT from the configured issuer that carries `iss`, `aud`, and `exp`. Its scopes come
from the claim named by `scopeClaim`, split on `scopeSeparator`; the principal and purpose claims are
the ones named under `authorityClaims`. A missing or rejected token answers
`401 authentication.refused` before any profile is selected.

Each route has one default access profile; select another with the `accessProfile` query option. A
profile admits the caller when the token satisfies its `requiredScopes`, `requiredPurposes`, and
`principalClaim`, and the profile grants the operation on that Record type.

An unknown route, an unsupported method, an unknown or ungranted profile, and an ungranted
operation all answer the same `404 resource.not_found`. Reads conceal records outside the caller's
boundary; see [Read refusals](#read-refusals). A mutation rechecks authority over its targets and
prospective values and answers `412 precondition.failed` when that fails, with no protected values
and no effects.

Placeholders use the router's snake_case form. `{route}` is the Record type's configured route,
`{record_id}` a record UUID, `{read_path}` a declared read path, `{action}` an Action ID, and
`{transition}` one of the promoted Proposal transitions. Read routes answer GET only; only the
probes also answer HEAD.

## Record envelope

Reads, creates, patches, tombstones, revisions, and snapshots return the Registry Record envelope:

```json
{
  "data": {
    "recordIdentifier": "2d7e5e0c-5b2c-4b8e-9f1e-0d3c1a2b3c4d",
    "revisionIdentifier": "3",
    "domainData": {
      "code": "SITE-001",
      "label": "North depot",
      "location": {"type": "Point", "coordinates": [30.5234, -1.9441]}
    }
  },
  "meta": {
    "registryIdentifier": "asset-registry",
    "datasetIdentifier": "asset-sites",
    "entityTypeIdentifier": "asset-site"
  }
}
```

| Member | Type | Meaning |
| --- | --- | --- |
| `data.recordIdentifier` | string, UUID | Stable identity of the record. |
| `data.revisionIdentifier` | string, `^[1-9][0-9]*$` | Revision counter, starting at `1`. Compare as a string. |
| `data.domainData` | object | The record's fields under their `apiName`, narrowed to the grant's `readableFields` and to `$select`. |
| `data.snapshot` | string | On mutation responses only: an opaque token for `:snapshot` reads, at most 4096 bytes. |
| `meta.registryIdentifier`, `meta.datasetIdentifier`, `meta.entityTypeIdentifier` | strings | The registry, dataset, and Record type IDs from the compiled package. |

Fields travel under their `apiName`: by default the camelCase form of the field ID, so
`household-code` is `householdCode`. The field ID is never accepted in its place.

| Header | Value |
| --- | --- |
| `Content-Type` | `application/json`, or `application/ld+json` when the request sent `Accept: application/ld+json`. The JSON-LD form adds `@context` pointing at `https://id.registrystack.org/contexts/registry-record/v1`. |
| `ETag` | `"breg-hmac-sha256:<64 hex>"`, a strong validator of the current revision. Send it back in `If-Match`. |
| `Link` | `<https://id.registrystack.org/profiles/registry-record/v1>; rel="profile"`, then `</v1/schemas/{record_type_id}>; rel="describedby"`. |
| `Location` | On `201 Created`: `/v1/records/{route}/{record_id}`. |

Each Record type's generated JSON Schema carries these encodings.

## Collections and paging

A collection read returns `items`, `pageInfo`, and the same `meta` as a single record. Collection
members carry `recordIdentifier`, `revisionIdentifier`, and `domainData` directly, so the field path
is `items[0].domainData`, not `items[0].data.domainData`:

```json
{
  "items": [{"recordIdentifier": "…", "revisionIdentifier": "1", "domainData": {}}],
  "pageInfo": {"nextCursor": "eyJ…"},
  "meta": {"registryIdentifier": "asset-registry", "datasetIdentifier": "asset-sites", "entityTypeIdentifier": "asset-site"}
}
```

`nextCursor` is `null` on the last page. To continue, send it as `$skiptoken` with no other option
except `accessProfile`. The cursor is signed with the runtime `cursor.secretRef`, binds the whole
original query, and expires after `cursor.maximumAgeSeconds`; a cursor that fails any of those
checks answers `400 query.cursor_invalid`. With `$count`, the response carries the matching total.

## Query options

Options apply only where the grant permits them: `$select` draws from `readableFields`, `$filter`
from `filterableFields`, `$orderby` from `sortableFields`, and `$count` needs `allowCount`. Anything
else answers `400 query.invalid` with `fieldPath` naming the parameter. An unknown field and a
withheld field return the same problem, and the field itself is never named.

<ApiReferenceTable id="query-options" />

```text
$filter=status eq 'active' and (region in ('north','east') or startswith(label,'Depot'))
$filter=not contains(label,'closed') and validFrom ge 2026-01-01
bbox=30.0,-2.1,30.9,-1.8
```

Strings are single quoted, numbers and dates are bare, and `null` compares with `eq` and `ne`.
Literals must fit the field type.

## Mutations

Every write needs `Content-Type: application/json`, except a patch, which needs
`application/json-patch+json`. A refused body answers `400 request.invalid`; see
[Problem documents](#problem-documents) for its `fieldPath`.

### Create

`POST /v1/records/{route}` with the fields the grant lists in `writableFields`:

```json
{"data": {"code": "SITE-001", "label": "North depot", "location": {"type": "Point", "coordinates": [30.5234, -1.9441]}}}
```

The response is `201 Created` with the envelope, `ETag`, and `Location`. Missing required fields,
values outside their type bounds, a reference to a missing or tombstoned target, and a violated `unique`
constraint are refused before anything is written.

### Patch

`PATCH /v1/records/{route}/{record_id}` takes a JSON Patch document whose paths are `/data/`
followed by the field's `apiName`:

```json
[
  {"op": "replace", "path": "/data/label", "value": "North depot (annex)"},
  {"op": "add", "path": "/data/closedOn", "value": "2026-12-31"}
]
```

`If-Match` must carry the `ETag` of the revision you read: a stale value answers
`412 precondition.failed` and a missing one `428 precondition.required`. The response is the new
revision's envelope with `data.snapshot`.
Reference values must name active targets, as on Create.

### Tombstone

`DELETE /v1/records/{route}/{record_id}` with `If-Match` writes a final revision that marks the
record tombstoned and returns that revision's envelope. The record stays readable through its
revisions and leaves live collection reads. The route exists only when the Record type sets
`tombstone: true`.

An active Record that references the target prevents its tombstone, including when you cannot
read that referencing Record. The response is the generic `409 mutation.conflict`.
Clear an optional reference, point it at an active replacement, or tombstone its source Record
before tombstoning the target. Tombstoned Records and retained history keep their reference IDs.

### Batch

`POST /v1/records/{route}:batch` applies several items to one Record type in one transaction,
bounded by its `batch.maximumItems` and `batch.maximumBytes`:

```json
{
  "items": [
    {"operation": "create", "data": {"code": "SITE-002", "label": "East depot"}},
    {"operation": "patch", "recordId": "2d7e5e0c-…", "ifMatch": "\"breg-hmac-sha256:…\"", "patch": [{"op": "replace", "path": "/data/label", "value": "West depot"}]}
  ],
  "changeContext": {
    "kind": "correction",
    "reasonCode": "effective-date-corrected",
    "reasonText": "Site start date was recorded one month late.",
    "sourceReferences": ["case-document:correction-001"]
  }
}
```

The response is `{"snapshot", "results"}`. Each result carries `operation`, `id`, `revision`,
`etag`, and `data`.

`changeContext` is optional and covers the whole batch; an item-level override is refused. A
`correction` requires a nonempty `reasonCode`. `reasonCode` holds at most 64 UTF-8 bytes,
`reasonText` at most 4 KiB, and `sourceReferences` at most 16 entries of 256 bytes each. Temporal
non-overlap constraints are checked on the final state of the batch. One stale `ifMatch` or one
violated constraint rolls back every item.

### Idempotency

Send `Idempotency-Key` (1 to 256 visible ASCII bytes, without a comma or semicolon) on any create,
patch, tombstone, or batch. Proposal starts and transitions, attachment changes, immediate Actions,
and statistics publications require it.

- Keys are scoped to the verified issuer and principal; two callers never share one.
- A spent key answers `409 idempotency.conflict` on any different request: the binding names the
  route, method, target, body, package activation, profile, and verified claims.
- Only successes spend a key. Correct a refused request and retry with the same key.
- An exact repeat returns the held response without writing, for
  `retention.receiptRetentionDays` after the commit (7 days by default), then answers
  `410 idempotency.expired` and is never executed; read the record instead.

## Ingestion runs

An ingestion run is the durable checkpoint of one bulk load that the client drives one chunk at a
time. The client keeps the source; the server keeps the checkpoint and never recomputes the source.
Only a chunk submission advances a run, and every operation rechecks the caller's authority against
the compiled batch route. A run is visible only to the issuer and principal that created it;
another caller's run and an unknown run answer the same 404. Run responses carry operational
metadata only, never source rows or record values. Every ingestion response carries
`Cache-Control: no-store`.

The ingestion routes refuse an `Idempotency-Key` header with `400 request.invalid`. The server
derives each chunk's attempt key from the run ID, input digest, chunk index, and chunk digest, so
resubmitting the exact chunk is always safe. For the procedure, see
[load records through an import window](../../operate/breg-data/#load-records-through-an-import-window).

### Create a run

`POST /v1/records/{route}/ingestion-runs`, `Content-Type: application/json`, a body of at most
4 KiB with exactly these members:

```json
{
  "operation": "create",
  "profileId": "operator",
  "packageRevision": "sha256:9f2c…",
  "schemaFingerprint": "sha256:1a7b…",
  "inputDigest": "5e8d…",
  "inputLength": 48211,
  "itemCount": 12000,
  "chunkCount": 13,
  "chunkAlgorithmVersion": "greedy-canonical-http-batch-v1"
}
```

| Member | Rule |
| --- | --- |
| `operation` | `create` or `patch`. A profile that holds `import` announces `create`. |
| `profileId`, `packageRevision`, `schemaFingerprint` | Nonempty strings that must match the selected profile and the active package. |
| `inputDigest` | SHA-256 of the whole source, 64 lowercase hexadecimal characters. |
| `inputLength`, `itemCount`, `chunkCount` | Integers from 1 to 2^53 − 1. |
| `chunkAlgorithmVersion` | Exactly `greedy-canonical-http-batch-v1`. |

The answer is `201 Created` with `{"run": <run document>}`. An import run is created only while the
Record type holds an open import authority for the profile whose remaining volume covers
`itemCount` and, when the authority pins digests, lists this `inputDigest`; otherwise the answer is
`412 precondition.failed` and no run exists.

### The run document

| Member | Meaning |
| --- | --- |
| `runId` | The run identifier, a lowercase UUID. |
| `status` | `open`, `complete`, `cancelled`, or `blocked`. |
| `blockedReason` | `null`, or `activePackageChanged` or `importAuthorityClosed` while `blocked`. |
| `recordType`, `operation`, `profileId` | The bound Record type, operation, and profile. |
| `packageRevision`, `schemaFingerprint` | The binding the run was created under. |
| `inputDigest`, `inputLength`, `itemCount`, `chunkCount`, `chunkAlgorithmVersion` | The announced source. |
| `maximumItems`, `maximumBytes` | The batch bounds every chunk stays inside, fixed at creation. |
| `nextChunkIndex` | The chunk index the next submission must name. |
| `committedItems`, `committedPrefixDigest` | Items committed so far and the prefix digest of the last committed chunk; the SHA-256 of empty input before the first. |
| `lastAttempt` | `null`, or `{"outcome", "chunkIndex"}`. |
| `createdAt`, `updatedAt` | RFC 3339 timestamps. |
| `complete` | `true` when `status` is `complete`. |

`lastAttempt.outcome` is `committed`, `replayed`, `invalidItem`, `refused`, `bindingChanged`,
`importAuthorityClosed`, `chunkMismatch`, `runNotOpen`, or `unavailable`. `invalidItem` and
`refused` leave the checkpoint where it was: continue the remainder in a successor run.

A run whose binding no longer matches the active package reports `blocked` with
`activePackageChanged`. An import run whose authority closed, expired, or ran out of volume reports
`blocked` with `importAuthorityClosed` at its next chunk, which commits nothing and answers
`409 ingestion.run_blocked`. A blocked run stays readable and never resumes; continue in a successor
run.

### Submit a chunk

`POST /v1/records/{route}/ingestion-runs/{run_id}/chunks`, `Content-Type: application/json`, with
exactly these members:

| Member | Rule |
| --- | --- |
| `chunkIndex` | Nonnegative integer. A fresh chunk must equal `nextChunkIndex`. |
| `items` | 1 to `maximumItems` batch items, each the object the `:batch` route accepts, all with the run's operation. |
| `digest` | SHA-256 of the canonical JSON of `{"items": [...]}`, 64 lowercase hexadecimal characters. That canonical body must fit in `maximumBytes`. |
| `prefixDigest` | SHA-256 of the source bytes from the start through the end of this chunk's last item. On the last chunk it must equal `inputDigest`. |

The chunking algorithm is greedy: each chunk takes as many consecutive source items as fit in
`maximumItems` and `maximumBytes`, and every remaining chunk must still hold at least one item.

A committed chunk answers `200` with `{"run", "receipt"}`. Its records, revisions, audit, receipt,
and checkpoint advance commit in one transaction. A chunk index below `nextChunkIndex` is a replay:
when its `digest` and `prefixDigest` equal the stored ones, the answer is the stored receipt with
`replayed: true` and nothing is written. Any other mismatch of index, digest, prefix digest, count,
or operation answers `409 ingestion.chunk_mismatch` and writes nothing.

| Receipt member | Meaning |
| --- | --- |
| `chunkIndex`, `digest` | The committed chunk. |
| `replayed` | `true` when this answer replays an earlier commit. |
| `erased` | Always `false` in a served receipt. |
| `batch` | The `{"snapshot", "results"}` answer the chunk committed, projected to the fields the run's profile can read now. |

`GET /v1/records/{route}/ingestion-runs/{run_id}/chunks/{chunk_index}/receipt` returns the same
receipt without resending the chunk. A receipt is erased with the record history it describes;
then the read, and an exact replay of that chunk, answer `410 ingestion.receipt_erased`. The
chunk's counts stay in the run.

### List, read, and cancel

The list and read routes are in the [routes table](#routes). A restarting client rebuilds its

## History reads

`GET /v1/records/{route}/{record_id}/revisions` returns a collection of the record's revisions,
at most 100 per read, and `.../revisions/{revision}` returns one. Revisions show stored field
values only; derived fields and read paths are not evaluated over history. Correction context from
a batch appears only when the `revisions` grant lists `provenanceFields` (from `kind`,
`reasonCode`, `reasonText`, `sourceReferences`) and every revision that batch produced is visible
to the caller.

A temporal Record type, one with `temporal.startField` and `temporal.endField`, gains `:current`,
the records whose interval contains now, and `:as-of`, the records whose interval contains `asOf`.
Intervals include the start and exclude the end; a null end is open. `asOf` is a UTC RFC 3339
timestamp such as `2026-06-05T00:00:00Z`.

`GET /v1/records/{route}:snapshot` without `snapshot` captures the latest committed state and
returns its token with the page, so paging stays consistent while writes continue. With
`snapshot`, it reproduces that earlier state. `validAt` filters by effective time inside the
snapshot and is refused on a non-temporal Record type; it takes a calendar date for a `date` start
field and a UTC RFC 3339 timestamp for a `timestamp` one. `asOf` and `recordedAsOf` are refused
on this route.

A snapshot token grants nothing: the caller needs the `snapshot` operation, and current row
boundaries apply. A snapshot whose history was erased, whose field metadata no longer matches, or
whose two-second database budget runs out answers `503 source.unavailable`.

## Proposals

An Action with `execution.mode: proposal` starts a durable Proposal at
`POST /v1/actions/{action}/proposals`. The routes are in the [routes table](#routes);
[Actions and Proposals](../../configure/breg-actions/#proposals) explains the model.

<ApiReferenceTable id="proposal-transitions" />

A Proposal read carries an `ETag`. Every transition, attachment upload, and attachment removal
requires `If-Match` with that value and answers `428 precondition.required` without it. The
Proposal `ETag` is distinct from a record `ETag` and is bound to the caller's profile, principal,
purpose, and target scope as well as the Proposal revision, so refetch after every transition and
never reuse another caller's value. Follow only the transition and attachment links the current
representation promotes.

### Observe an exact submission

`GET /v1/proposals/{proposal_id}/submissions/{submission_version}` reads one exact submission under
the Proposal Get authority: its frozen `effectDigest`, its `review` result, its `decision`, and its
`application` outcome as separate members. Only the current submission reports application
progress. Once its result window has lapsed and no application receipt remains, it answers
`410 proposal.submission_expired`; the Proposal stays readable.

### Proposal attachments

`GET`, `PATCH`, and `DELETE /v1/proposals/{proposal_id}/attachments/{slot_id}` read, upload, and
remove one slot's bytes. Slot descriptors on the Proposal carry requiredness, byte limit, content
types, classification, verification, and the links the caller may follow. Submission binds the

## Immediate actions

An Action with `execution.mode: immediate` runs one atomic plan at `POST /v1/actions/{action}` with
`Idempotency-Key`. Input names are exact `apiName` values, validated against the compiler-emitted
JSON Schema in the Action descriptor. When the descriptor advertises target conditions, read them
first at `POST /v1/actions/{action}/target-conditions`. Invoke requires Action authority over every
target. Effects, revisions, audit, receipt, and outbox commit together or not at all; resend the
original request with its original key when the outcome is uncertain. See
[Actions and Proposals](../../configure/breg-actions/) for the model.

An immediate Action with a reference input advertises one `routes.availability` endpoint at
`POST /v1/actions/{action}/availability`. Send `targetInput` with the reference input's exact
`apiName`, plus an `input` object containing its UUID and any declared form values already known.
Each request checks one target. Query several reference inputs separately.
The response reports advisory `available` as `true`, `false`, or `null`. A known answer includes
`observedRevision`. `guard-not-satisfied` means a field guard failed. `input-required` names a
nonempty set of declared API input names in `missingInputs`. `not-disclosed` carries
`observedRevision: null` and no missing-input names because the selected profile cannot safely
inspect the guard or boundary. A known failed guard takes precedence over missing guard input.
No availability response names a guard ID or a Record value.
The route evaluates only field guards for that one target. It does not run a Function, test SQL
uniqueness or Evidence, inspect other targets, supply a condition token, or grant mutation
authority. A true answer means only that the selected target's field guards are currently satisfied,
including when it has none. Form completeness, Functions, Evidence, other targets, and SQL
constraints may still refuse. Invoke checks authority, concurrency, and every guard in the commit
transaction.

## Problem documents

A refusal is an RFC 9457 problem document with `Content-Type: application/problem+json`:

```json
{
  "type": "https://id.registrystack.org/problems/registry-breg/request/invalid",
  "title": "Bad Request",
  "status": 400,
  "detail": "The request is invalid.",
  "code": "request.invalid",
  "traceId": "3f1a9c2e5b7d4e6f8a9b0c1d2e3f4a5b",
  "fieldPath": "/data/householdCode"
}
```

Branch on `code`. `type` is the same code with each dot read as a path segment under
`https://id.registrystack.org/problems/registry-breg/`. `detail` is the registered text of the code.
`traceId` is 32 hexadecimal characters that also appear in the request log and, for every journaled
request, in its audit record. A request refused before admission for presenting no credential is
counted on the metrics listener rather than journaled; see
[scrape metrics](../../operate/breg-monitor/#scrape-metrics).

`fieldPath` is present only when one member is at fault:

| Refusal | `fieldPath` |
| --- | --- |
| Create body | `/data` for a missing `data` member or a field you may not write, known or not; `/data/<apiName>` for a missing required field or a wrong value of a field you may write. |
| Patch document | `/<n>` for operation `n`, `/<n>/op`, `/<n>/path` for a path outside `/data/` or a field you may not write, known or not, and `/<n>/value`. |
| Batch body | `/items`, `/changeContext`, `/items/<n>`, `/items/<n>/operation`, `/items/<n>/recordId`, `/items/<n>/ifMatch`, `/items/<n>/patch`, and the create and patch forms above under `/items/<n>` and `/items/<n>/patch`. |
| Header | `Idempotency-Key` when it is missing or malformed; `If-Match` when a batch request sends one, because each batch item carries its own `ifMatch`. |
| Query | The parameter: `$select`, `$filter`, `$orderby`, `$top`, `$count`, `$skiptoken`, `bbox`, `accessProfile`, `asOf`, `snapshot`, or `validAt`; on statistics routes also `from`, `to`, or `status`. A revision route takes none but `accessProfile` and names the first other one you sent. |

A name you sent is never echoed: an unknown member and a withheld one stop at the same location.
An oversized or non-JSON body, an undefined query parameter, a malformed query string, and the
lookup, ingestion, attachment, and GIS routes carry no `fieldPath`.

A direct create, patch, or batch that violates an authored row-local constraint answers
`409 mutation.conflict` and may add the declared location:

```json
{
  "recordType": "permit",
  "constraintId": "chronological-validity",
  "constraintKind": "compare",
  "left": "valid-from",
  "right": "valid-to"
}
```

`compare` carries `left` and `right`; `int-range` and `vocabulary` carry `field`. The members appear
only when the selected profile can read every referenced field, and never on Action or Proposal
effects. They hold declared identifiers only, never a submitted value or database message. An
explicit constraint `id` is the stable key to map on; an omitted one is compiler-derived and
changes with the declaration. `unique` and `temporal-non-overlap` conflicts stay generic.

### Signature

`X-Registry-Signature` is `v1=` followed by the unpadded base64url HMAC-SHA-256 of the signing
input, under a key of at least 32 bytes. The signing input is the bytes `breg-webhook-signature-v1`
followed by these fields in order, each as an unsigned 64-bit big-endian length and then its bytes:
the version `1.0`, `ce-id`, `ce-source`, `ce-type`, `ce-time`, `ce-dataschema`,
`X-Registry-Event-Generation`, `X-Registry-Delivery-Attempt`, `X-Registry-Delivery-Time`, the method,
the request target (the destination's configured path), `Content-Type`, `Idempotency-Key`, and the
exact body. The body is at most 1 MiB and the other fields together at most 32 KiB.

Compare in constant time, then check the expected source, type, schema, and the freshness of
`X-Registry-Delivery-Time`, not of `ce-time`, before accepting durably.

## Statistical datasets

<ApiReferenceTable id="statistical-dataset-routes" />

Every statistical operation requires a profile selected with `accessProfile`; a released-data
reader needs no record permissions.

Document reads from the live, series, latest-version, and exact-version routes send
`Cache-Control: no-store`, `Vary: authorization, accept`, and `Repr-Digest` for the exact JSON or
CSV bytes. The release listing omits `Repr-Digest`. A version header's `contentDigest` identifies
the canonical stored JSON; a withdrawn version's header omits it. No strong `ETag` is issued.

CSV columns are `period,periodStart,periodEnd,<dimension field IDs...>,value,status`. A suppressed
value is blank; a zero stays zero with its status. Totals round independently; see
[publish statistics](../../configure/breg-statistics/#review-what-a-release-discloses) for the
inference risks. Unknown datasets and ungranted profiles answer the concealed 404, and invalid
ranges `400 query.invalid`.

Registry Stack HTTP products own their error contracts. Use the product reference that matches the
service you call instead of assuming codes or response shapes carry across products.

Use the owning route contract to decide whether an operation completed, was refused, or has an
unknown outcome.
A shared envelope does not change a product's authorisation, concealed existence, or retry semantics.

## Problem envelope

The common RFC 9457 response is `application/problem+json` with six fields:

| Field | Contract |
| --- | --- |
| `type` | Absolute opaque problem URI owned by the product. Never dereference it to authorise recovery. |
| `title` | Fixed safe category text. |
| `status` | Integer equal to the HTTP status. |
| `detail` | Fixed safe guidance, with no submitted or source values. |
| `code` | At most 128 ASCII bytes, `family.reason`. Each segment starts with a lowercase letter and contains lowercase letters, digits, or hyphens. The snake_case codes of Base Registry Engine (BReg) are an exception (see the BReg note under deliberate response exceptions). |
| `traceId` | Canonical nonzero 32 lowercase hexadecimal characters, equal to the trace in the response `traceparent`. |

The shared HTTP security crate supplies the problem body, the trace context, and the strict client problem document.
The server replaces malformed or repeated trace input and never reflects `tracestate`.
A product may create a fresh response trace.
Problems use `Cache-Control: no-store`.

{/* Evidence: crates/registry-platform-httpsec/src/server.rs ProblemBody, TraceContext;
    crates/registry-platform-httpsec/src/client.rs ProblemDocument. */}

Extensions must be explicitly defined, structurally bounded, and safe.
A field path may name declared structure, never a record identifier or submitted value.
Render's bounded pointer list and Casework's validation metadata remain product contracts.
Clients reject duplicate members, excessive bytes, and invalid known members.
A closed client rejects extensions unless its owning contract explicitly accepts them; sharing the core envelope does not widen it.

{/* Evidence: crates/registry-platform-httpsec/src/client.rs ProblemDocument. */}

### Discovery and Render

Discovery preserves its problem type URIs and adds the codes `request.invalid`, `request.not-found`, `request.result-bound-exceeded`, and `service.unavailable`, a fixed `detail`, and `traceId`.
Its indeterminate 503 carries no guessed retry interval.
Its client classifies a problem by HTTP status and the original `type`, `title`, and `status` trio; a supplied `code` must agree for known problem types.
Additive members, `detail`, `traceId`, and the response `traceparent` are opaque to classification.
The entire problem body is bounded at 4 KiB.
Unknown future Discovery problem types keep a bounded, status-only fallback.

{/* Evidence: crates/registry-discovery-client/src/client.rs request.result-bound-exceeded;
    crates/registry-discovery/src/openapi.rs request.result-bound-exceeded. */}

Render uses the same core with its own vocabulary and extensions.
Its `code` values are `render.<reason>`, and its type base is its own released `https://render.registrystack.org/problems`.
That vocabulary includes `render.unauthorized` for invalid credentials, in place of `authentication.refused`.

{/* Evidence: crates/registry-render/src/problem.rs render.unauthorized, render.timestamp-failed. */}

## Deliberate response exceptions

Casework `GET /v1/review-requests/{requestId}/result` returns a bodyless 202 for pending, 404 for concealed or unknown, and 410 for expired.
The shared Review client maps these states without requiring a problem body.
A result still must match the persisted accepted request, policy, subject, and submission digest.

{/* Evidence: crates/registry-casework/src/http.rs /v1/review-requests/{request_id}/result. */}

Scheduling returns the same public appointment outcome when the appointment is missing or denied.
Keep that concealment when presenting or classifying a failure.
Its readiness route follows its own deployment health contract.

Invalid credentials use a generic 401 `authentication.refused`, except Render, whose own vocabulary answers 401 `render.unauthorized`.
Profile or route authority failures keep the product's documented 403 or concealment; a verifier outage keeps its documented 503.
Internal stage diagnostics do not become public error details.

{/* Evidence: crates/registry-adapter-core/src/problem.rs AUTHENTICATION_REFUSED_PROBLEM;
    crates/registry-render/src/problem.rs render.unauthorized. */}

BReg's codes are snake_case in their reason segment (`runtime.not_ready`, `resource.not_found`, `ingestion.chunk_mismatch`), where the code grammar in the table allows hyphens only.
They are released wire values, so BReg keeps them and its clients match them as written.
A new BReg code follows its existing spelling until a breaking release respells them all at once.

{/* Evidence: crates/registry-breg/src/problem.rs RuntimeNotReady, IngestionChunkMismatch;
    crates/registry-breg-client/src/error.rs RuntimeNotReady. */}

## Upstream failures and readiness

An upstream that answered badly (an unusable, malformed, or contract-violating response) is 502.
An upstream or a local dependency that is unavailable (unreachable, timed out, circuit open, store down) is 503.
Adapter `adapter.upstream.unmapped` and Render `render.timestamp-failed` are 502; Evidence `source.unavailable` is 503.

{/* Evidence: crates/registry-adapter-core/src/problem.rs adapter.upstream.unmapped;
    crates/registry-render/src/problem.rs render.timestamp-failed;
    crates/registry-breg-client/src/error.rs source.unavailable. */}

`/ready` answers 200 when the instance can serve and 503 when it cannot.
The body is optional.
When present it is `{"status":"ready"}` or `{"status":"not-ready"}`, and it may add per-dependency members that use the same two status words.
Readiness carries no source-data probes.
These products differ:

- BReg answers 503 with a problem body (`runtime.not_ready`).
- OID4VCI answers 503 with `{"status":"not_ready"}`.
- Casework and Scheduling answer 200 with the shared body `{"status":"ready"}`, and `/health` with `{"status":"ok"}`.
- Coordinator answers 200 with `{"ready":true,"status":"ready"}` and 503 with `{"ready":false}`.
- Scheduling also serves `/readyz`, a bodyless probe on the same readiness test, under its deployment health contract.
- Messaging and Documents answer 200 without a body, and 503 with a `service.unavailable` problem body and a `Retry-After` header.

{/* Evidence: crates/registry-breg/src/problem.rs RuntimeNotReady;
    crates/registry-evidence-oid4vci/src/service.rs not_ready;
    crates/registry-platform-httputil/src/probe.rs READY_BODY;
    crates/registry-casework/src/http.rs ready;
    crates/registry-coordinator/src/http.rs ready;
    crates/registry-scheduling/src/http.rs ready, readyz;
    crates/registry-messaging/src/http.rs ready;
    crates/registry-documents/src/http.rs ready. */}

## Idempotency and retries

Use a caller-owned key, and keep the original body, headers, and accepted binding when reconciling an uncertain mutation.
Reusing a key with another request is 409 `idempotency.key-reused` from BReg, Casework, Coordinator, Messaging, and Scheduling.
Classify a 409 by the product that returned it.

{/* Evidence: crates/registry-coordinator/src/problem.rs IDEMPOTENCY_KEY_REUSED_PROBLEM;
    crates/registry-casework/src/problem.rs IDEMPOTENCY_KEY_REUSED_PROBLEM;
    crates/registry-breg/src/artifacts.rs idempotency.key-reused. */}
{/* TODO[evidence]: Messaging and Scheduling 409 `idempotency.key-reused` anchors were not located. */}

A key of 128 bytes is portable guidance, not a replacement for route limits.
BReg and Coordinator keep their existing 256-byte bounds; Casework, Scheduling, and Messaging keep their owning limits.
`idempotency.key-invalid` means a missing or invalid key under that route's rules.
Never classify a valid key of 129 to 256 bytes on BReg or Coordinator as invalid for portability.

{/* Evidence: crates/registry-breg/src/idempotency.rs MAX_IDEMPOTENCY_KEY_BYTES;
    crates/registry-coordinator/src/problem.rs IDEMPOTENCY_KEY_INVALID_PROBLEM. */}

`Retry-After` appears only when the server knows a useful interval.
Messaging rate and quota refusals supply bounded waits; Casework polling and readiness use their owning response contracts.
Evidence `503 source.unavailable` omits `Retry-After` when upstream recovery time is unknown, while meaningful rate-limit hints remain.
Source-data reachability does not decide Evidence `/ready`: an instance with healthy required dependencies can remain ready during a source-data outage.
No data-endpoint probes are added to readiness.

An indeterminate outage, a deterministic non-retryable failure, or a readiness contract without a known interval need not carry it.
Clients preserve absent, invalid, and bounded interval states; waiting remains a caller decision.
A header never authorises a fresh-key repeat of an uncertain mutation.
Client retry rules are in the client crates' documentation.

{/* TODO[evidence]: the `Retry-After` and no-source-probe readiness claims are carried from the source; no single test anchors them. */}

BReg pagination uses `$top` and `$skiptoken` (Python `top`); Casework, Scheduling, and Coordinator use `limit` and `cursor`.
SDKs expose each actual contract and do not automatically follow continuations.

## Product problem contracts

## Registry Evidence

[Registry Evidence problem types](../evidence-problems/) is the maintained reference for the
Gateway's closed problem set. The runtime-owned generator reproduces its committed schema and
OpenAPI artifacts under CI.

## Evidence OID4VCI supporting service

The OID4VCI delivery service has its own protocol error vocabulary in the
[committed OpenAPI artifact](https://github.com/registrystack/registry-stack/blob/main/products/evidence/generated/registry-evidence-oid4vci.openapi.json).
A request the web framework refuses before the protocol handler runs, for a malformed body, an
oversize body, or an unsupported content type, is answered in the same JSON error shape as the
service's own refusals. A request over its rate budget is answered `429` with `Retry-After`.

## Evidence OID4VP supporting service

The OpenID4VP verifier answers wallets with the OAuth error shape and no description, and answers
callers with problem responses defined in its
[committed OpenAPI artifact](https://github.com/registrystack/registry-stack/blob/main/products/evidence/generated/registry-evidence-oid4vp.openapi.json).
A session that failed because the wallet reported an error carries one `failureCategory` from a
closed set; a refusal for a spent budget or a full presentation store is `503` or `429` with
`Retry-After`.

## Secret file codes

A secret file the runtime refuses carries one of these `platform.secret-file.*` codes. The text
names the failed check and never a path, a reference, or a value. A product's own refusal keeps its
product code and repeats the check's text and fix. A process that declares the development posture
loads a file for `world-readable`, `group-access`, and `mode-bits`, and logs the code in the
`error_code` field of one warning per check. The [secret file rule](../../security/hardening-checklist/#secret-files)
states what each check accepts.

| Code | Meaning | Fix |
| --- | --- | --- |
| `platform.secret-file.link-leaves-root` | The secret file is reached through a link that leaves `secretProviders.file.root`. | Put the file under `secretProviders.file.root`, or use a relative link without `..` that stays below it. |
| `platform.secret-file.too-many-links` | The secret file is reached through more than 8 links. | Point the name at the file, or at a chain of at most 8 links below `secretProviders.file.root`. |
| `platform.secret-file.cannot-open` | The runtime user cannot open the secret file. | Make the file readable by the runtime user: mode `0400` or `0600` owned by that user, or `0440` owned by root with the runtime user's group. On Kubernetes, set the secret volume's `defaultMode` to `0440` and the pod's `securityContext.fsGroup` to the runtime user's group. |
| `platform.secret-file.not-regular` | The secret file is not a regular file. | Point the name at a regular file, not a directory, device, socket or pipe. |
| `platform.secret-file.hard-linked` | The secret file has more than one hard link. | Replace it with a copy that has one link. |
| `platform.secret-file.owner` | The secret file is owned by neither the runtime user nor root. | Give it to the runtime user with mode `0400` or `0600`, or to root with mode `0440` and the runtime user's group. |
| `platform.secret-file.world-writable` | Users outside the file's owner and group can write the secret file. | Remove all access for others (`chmod o-rwx`). |
| `platform.secret-file.world-readable` | Users outside the file's owner and group can read the secret file. | Remove access for others: mode `0400` or `0600` for a file the runtime user owns, `0440` for a root-owned file. On Kubernetes, set the secret volume's `defaultMode` to `0440` and the pod's `securityContext.fsGroup` to the runtime user's group. |
| `platform.secret-file.group-access` | The secret file's group has access the rule does not allow. | Use mode `0400` or `0600` for a file the runtime user owns. Group read is accepted only on a root-owned file (`0440` or `0640`) read by a non-root runtime. |
| `platform.secret-file.mode-bits` | The secret file has an execute, setuid, setgid or sticky bit, or its owner cannot read it. | Set mode `0400` or `0600`. |

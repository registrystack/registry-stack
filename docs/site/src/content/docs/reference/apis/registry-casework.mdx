Registry Casework serves policy-bound review requests, human tasks, decisions, and results.
The generated [API operations](../casework/) own exact routes, parameters, schemas, and response
statuses. This manually maintained reference explains authentication and recovery around them.
The API is current and remains changeable before 1.0; [API stability](../../api-stability/)
states the versioning contract.

## Authentication and context

Authenticated calls present `Authorization: Bearer <token>` and one `Registry-Casework-Profile`.
The profile selects a governed access profile; it does not add scopes to the token.
Liveness at `/health` and readiness at `/ready` are unauthenticated.

Current-source human reads and decisions additionally select `Registry-Source-Profile`.
The read-only context provider forwards the human's bearer for that purpose-specific disclosure.
Submitted-context tasks require no source profile.
A status service credential never substitutes for a human display credential.

## Policy and submission binding

`GET /v1/review-policies` and `GET /v1/review-policies/{policy_id}` describe compiled policy closures.
A producer submits a `PolicySelection` in `POST /v1/review-requests`, alongside its immutable
subject, requester reference, and submitted or current-source context.
The selector requires `id`. Omit `version` and `digest` to select the active policy at admission,
or supply both to require the exact discovered `identity`. Partial pins and explicit nulls are
invalid. An exact pin that differs from the active binding is refused with `review.policy-mismatch`.
Casework validates context against the selected policy and atomically retains its concrete
`PolicyBinding`, including ID, version, and digest, in the acceptance.
The accepted producer identity and namespace govern later request, cancellation, history, and result
access. The submission digest includes the original selector; it is separate from the subject's
content digest and the accepted policy's digest. Replacing an ID-only selector with the accepted
binding changes the submitted body and is not recovery.

An authenticated `ReviewResult` repeats those bindings and conveys the review answer.
The consumer validates correlation and authorizes any business mutation independently.
A configured payload-free completion wake prompts an authenticated read and carries no decision
payload or external authority.

## Revisions, retries, and expiry

Revisioned mutations send the displayed task or Directory revision in `If-Match`.
Keyed mutations send an `Idempotency-Key`, bounded to 128 bytes.
Reuse the original key and exact body after a lost response; a changed body under the same key is
refused. A fresh key is a fresh operation, not recovery.

Recovery retains the original concrete policy binding even after an active-policy update and
still requires current producer authority. Producer clients validate acceptance against the
original selector, subject, and submission digest, then validate results against the accepted
concrete binding. Results return `202` while pending, `200` while retained,
and `410` after expiry. A terminal task decision does not require a source-action recovery route;
Casework performs no source action.
Human decision receipts and protected accountability have separate disclosure checks.

## Problems and validation

Refusals use `application/problem+json` with a closed problem code, fixed detail, status, and trace ID.
The body does not echo submitted values.
Review validation may add `Registry-Casework-Validation-Path` and
`Registry-Casework-Validation-Reason`, providing a bounded field path and closed reason.
Use the trace ID with private operator logs; retain no bearer token or protected request body in a
support report.

## Route families and authority

- `/v1/review-policies` describes review behavior under authenticated policy access.
- `/v1/review-requests` and `/v1/review-results` serve the bound producer's request and result lifecycle.
- `/v1/review-tasks` serves eligible human work, holdings, decisions, drafts, clocks, and supervision.
- `/v1/review-accountability/{event_id}` resolves retained accountability under separate audited authority.
- `/v1/directory` manages teams, membership, absences, caseload previews, calendars, and clock recomputation.
- `/v1/task-grants` serves bounded institutional task authority where a project enables it.

The generated operations specify the caller and refusal for each route.
Administrator status grants no review payload or decision authority, and producer status grants no
human task authority. Source concealment remains effective on current-source task reads, context,
history, and decisions. An opaque ID or cursor grants no access.

## Source of truth

The product generator derives OpenAPI from Rust-owned DTOs, problems, routes, extraction rules,
and operation contracts. Its drift check refuses generated bytes that differ from those sources.
The running service serves the described operations, not the OpenAPI document itself.
The problem table is generated from maintained data checked against the runtime catalogue.

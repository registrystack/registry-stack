Registry Scheduling serves one HTTP surface for the published catalogue, availability, holds, and
appointments. Every call presents a bearer access token, and one of three authority profiles decides
what that token must carry: a read scope for catalogue and owned-record reads, a separate explain scope
for the diagnostic availability read, or a complete task grant for every commitment. The contract is
unreleased and carries no frozen compatibility promise.

[Open the Registry Scheduling API operations](../scheduling/) for every route, parameter, schema, and
reachable problem code. This page holds the authority, revision, and recovery rules those operations
assume.

## Obtain the operator tool and runtime

Registry Stack releases publish `schedulingctl` for Linux amd64, Linux arm64, and macOS arm64. Pick
a published tag from the
[latest release](https://github.com/registrystack/registry-stack/releases/latest), authenticate the
asset for your platform through
`https://github.com/registrystack/registry-stack/blob/<tag>/release/VERIFY.md`, then install it. For
Linux amd64:

```sh
tag="${TAG:?set TAG to a published Registry Stack tag}"
mkdir -p ~/.local/bin
install -m 0755 "schedulingctl-${tag}-linux-amd64" "$HOME/.local/bin/schedulingctl"
export PATH="$HOME/.local/bin:$PATH"
schedulingctl --version
```

From v0.38.0, the release also includes the Linux amd64 runtime binary
`scheduling-<tag>-linux-amd64`. Authenticate it through the same checksum chain, install it alongside
`schedulingctl`, and run `scheduling --runtime-config /etc/registry-scheduling/runtime.yaml serve`.
Earlier releases ship the runtime through its image.

The runtime is published as `ghcr.io/registrystack/scheduling:<tag>`. Authenticate the image digest
through the release manifest and deploy the digest instead of the mutable tag. The Distroless
`cc-debian13` image runs `/usr/local/bin/scheduling` as the nonroot user, reads
`/etc/registry-scheduling/runtime.yaml`, and uses `/var/lib/registry-scheduling` as its working
directory. Mount the runtime file, package, and serving secrets read-only, and mount the audit
directory read-write.

Images published from v0.36.0 also contain the matching `/usr/local/bin/schedulingctl`. Run
`plan`, `apply`, or `status` against the exact image bytes by overriding the entrypoint:

```sh
docker run --rm \
  --entrypoint /usr/local/bin/schedulingctl \
  -v /etc/registry-scheduling/runtime.yaml:/etc/registry-scheduling/runtime.yaml:ro \
  -v /etc/registry-scheduling/package:/etc/registry-scheduling/package:ro \
  -v /etc/registry-scheduling/operator-secrets:/etc/registry-scheduling/secrets:ro \
  -v /var/lib/registry-scheduling/audit:/var/lib/registry-scheduling/audit:rw \
  "ghcr.io/registrystack/scheduling@sha256:<verified-digest>" \
  plan --runtime-config /etc/registry-scheduling/runtime.yaml
```

Use the same mounts for `apply` or `status`. The migration secret needed by `apply` should stay out
of the serving container.

## Contract boundary

Every request presents `Authorization: Bearer <token>` holding an RFC 9068 access token, `typ:
at+jwt`, whose claims name the caller's actor kind in `registry_actor_kind` as `human`, `agent`, or
`service`. Liveness and readiness are the only routes that take no token.

{/* Evidence: crates/registry-scheduling/src/auth.rs, authenticate_mutate() and validate_compact_access_token;
    crates/registry-platform-oidc/src/authorization_claims.rs, actor_kind(). */}

The four caller-driven commitments carry an `Idempotency-Key` the caller chooses, bounded to 128
bytes: creating a hold, creating an appointment, rescheduling one, and cancelling one. A retry under
the same key with the same request returns the stored first answer, and the same key with a different
request is refused with `idempotency.key-reused`. Releasing a hold carries no caller key: the hold's
own identifier is the idempotency key, so a retried release replays the first answer without the
caller holding anything back.

{/* Evidence: crates/registry-scheduling/src/http.rs, idempotency_key() and router();
    crates/registry-scheduling/src/service.rs, release_hold();
    crates/registry-scheduling-core/src/naming.rs, MAXIMUM_IDEMPOTENCY_KEY_BYTES. */}

A 5xx answer may follow a commit, and so may a timeout or a broken exchange after the request was
sent. The safe recovery is the same request with the same key: the runtime replays the stored answer
or settles the command, while a new key can commit it twice. The Rust client in
`registry-scheduling-client` does this for the four keyed commitments: its error's
`is_outcome_unknown()` is true in those cases and false for a typed 4xx refusal, and it resends the
identical request at most twice by default, waiting 250 ms and then 500 ms, or the runtime's
`Retry-After` when that is longer and at most 5 seconds. `with_max_mutation_retries` on its
configuration sets the count from 0, which sends once, to 2. It never resends a read or a release.

{/* Evidence: crates/registry-scheduling-client/src/error.rs, is_outcome_unknown;
    crates/registry-scheduling-client/src/config.rs, with_max_mutation_retries;
    crates/registry-scheduling-client/tests/mutation_retry.rs;
    crates/registry-platform-httputil/src/client/retry.rs, retry_keyed_mutation. */}

Observed revisions travel in request bodies, not in an `If-Match` header: an admission names the
`policyRevision` it resolved the offering under, and a reschedule or cancel names the appointment
revision it acted on. A stale revision is refused with `policy.changed` or `revision.mismatch`, and
the caller reloads the catalogue and tries again. An offering the deployed policy does not publish
is a separate answer, `request.not-found`: it does not exist, so no reload produces it, and the
offering listing every caller holding the reads scope can read is where the published ones are
named.

{/* Evidence: crates/registry-scheduling-core/src/model.rs, AdmissionRequest;
    crates/registry-scheduling-core/src/admission.rs, check_duplicate();
    products/scheduling/generated/registry-scheduling.openapi.json. */}

A refusal answers `application/problem+json` with `type`, `title`, `status`, `detail`, `code`, and
`traceId`. The `type` is the code with each dot replaced by a slash under
`https://id.registrystack.org/problems/registry-scheduling/`, and `detail` is the fixed sentence that
belongs to the code. No field repeats a submitted value. Every response, refusals included, carries
`Cache-Control: no-store` and propagates or mints a `traceparent` value.

{/* Evidence: crates/registry-platform-httpsec/src/server.rs, security_headers() and ProblemBody;
    crates/registry-scheduling-core/src/problem.rs, ProblemCode. */}

Availability pages list a slot only while it holds a free unit: a slot whose members are all
committed, held, or closed leaves the page rather than appearing with zero free. A caller watching a
slot disappear therefore reads the same fact as one reading `free: 0`.

{/* Evidence: crates/registry-scheduling/src/service.rs, exact_time_slots(). */}

## Authority profiles

The three profiles are disjoint. A token carrying a product scope does not thereby gain a commitment
path, and a task grant does not thereby gain a catalogue read.

| Profile | Routes | The token must carry |
| --- | --- | --- |
| Catalogue read | `/v1/scheduling`, `/v1/services`, `/v1/offerings`, `/v1/resources`, `/v1/locations`, `/v1/availability`, owned appointments listed by external reference, one appointment read, its history | The configured read scope, `scheduling-read` by default, in `registry_scopes` |
| Explain | `/v1/availability/explain` | The separately configured explain scope, `scheduling-explain` by default, which is never the read scope |
| Commitment | Hold create and release, appointment create, reschedule, cancel | A complete task grant; no product scope |

{/* Evidence: crates/registry-scheduling/src/auth.rs, authenticate_read(), authenticate_explain(), and
    authenticate_mutate(); crates/registry-scheduling/src/http.rs, router(). */}

The explain path is separately authorized because it can name the member-level cause
`resource.unavailable`. The public availability path answers the same state as `capacity.exhausted`
and names no member.

{/* Evidence: crates/registry-scheduling-core/src/admission.rs, detailed_code();
    products/scheduling/generated/registry-scheduling.openapi.json. */}

`POST /v1/appointments/receipt` uses ordinary read authority, the original `Idempotency-Key`,
and the original `CreateAppointmentRequest` body to observe a retained successful creation
receipt. Its verified issuer and subject must exactly match the original caller. It returns
`200` with the original appointment projection and never creates or replays a capacity command.
Observation can therefore continue after the original task grant ends, using a current token
with read authority. Missing, expired, changed, or refused receipts answer
`409 receipt.unresolved`. This refusal leaves the original outcome unknown and is not evidence
that no appointment was created.

{/* Evidence: crates/registry-scheduling/src/http.rs, appointment_receipt();
    crates/registry-scheduling/src/service.rs, appointment_receipt();
    crates/registry-scheduling-core/src/problem.rs, ReceiptUnresolved. */}

## Task grants

A commitment carries no product scope. Its authority is a task grant inside the access token: the six
`registry_grant_*` members that make a grant detectable, plus `registry_purpose` and
`registry_approver`, bound to the verified client and to this deployment's audience before the caller
reaches the service. An incomplete grant set is refused as a credentials problem
(`authentication.refused`), never honored partially.

{/* Evidence: crates/registry-platform-oidc/src/authorization_claims.rs, grant_claims(), core_grant_names(),
    and verify_context(); crates/registry-scheduling/src/auth.rs, verified_caller(). */}

The grant's bounds carry one permission per location, and a permission names an offering's service, an
offering's location, and the actions it allows:

- `hold.create` and `hold.release`
- `appointment.create`, `appointment.reschedule`, and `appointment.cancel`

A permission matches an offering only when its service and location both equal the offering's own and
the action is listed. The match is exact: a broader service or location never covers a narrower one,
and the grant's client must equal the client the deployment verified.

{/* Evidence: crates/registry-scheduling/src/service.rs, require_permission(), HOLD_CREATE_ACTION,
    HOLD_RELEASE_ACTION, APPOINTMENT_CREATE_ACTION, APPOINTMENT_RESCHEDULE_ACTION, and
    APPOINTMENT_CANCEL_ACTION; crates/registry-platform-oidc/src/authorization_claims.rs,
    SchedulingPermission. */}

The grant's bounds are matched at the service before the capacity transaction opens. When the runtime
has any `taskGrantStatus` entry, Scheduling also obtains a fresh exact answer from the authority selected
by the signed source issuer before every commitment and idempotent receipt replay. The authority must say
the grant is active and reproduce its exact identity, bounds, signed subjects, and deadline. An inactive,
mismatched, unlisted, or incompletely bound grant answers `operation.not-authorized`; an authority or service
credential outage, including an unusable authority response, answers `service.unavailable`. Positive answers
are not cached, and the complete attempt is limited to ten seconds. No capacity lock is held during the outbound call.
This is a fresh observation rather than a distributed transaction: withdrawal after a positive answer can race
the in-flight local commit.

Inside the transaction, after lock waits and immediately before commit, Scheduling checks the earlier of
the verified access-token and grant deadlines. A credential that expires after the status answer cannot
take capacity through a delayed transaction. The earlier deadline bounds the status-to-commit race but does
not make revocation atomic across products. An entirely unconfigured deployment accepts only the legacy
offline path for grants with no more than 900 seconds remaining. Any configured entry disables that
fallback for every source. Because the token does not name the original authorization mode, the final 15
minutes of a deferred grant can use the legacy path on an unconfigured deployment; deployments accepting
deferred grants should configure status.

{/* Evidence: products/scheduling/contracts/security-invariant-matrix.yaml, SCHEDULING-SEC-03;
    crates/registry-scheduling/src/service.rs, require_current_task_grant(), audit_request(), and
    commitment(); crates/registry-scheduling/tests/postgres_commitments.rs,
    configured_task_status_is_fresh_for_a_capacity_commit_and_its_replay,
    inactive_mismatched_and_unavailable_task_status_commit_no_capacity,
    unconfigured_status_accepts_only_the_legacy_remaining_lifetime, and
    a_commitment_blocked_past_its_access_token_deadline_never_books. */}

A commitment writes a request audit entry, schema `registry-scheduling-audit/v1`, before the capacity
transaction opens, and a response entry with the same correlation after the transaction commits or
rolls back. The response carries `authorization.allowed` or `authorization.refused` as an audit reason,
never as a problem code. When the audit destination refuses the request entry, no transaction opens and
the call answers `service.unavailable`; when it refuses the response entry of a committed commitment,
the call answers `service.unavailable` with the commitment in place. A permission the service refuses
before any commitment is reached is one response entry with a correlation of its own.

{/* Evidence: crates/registry-scheduling/src/store.rs, check_grant_current();

## Recover an unknown outcome

Send `externalReferences` naming the record you book for on every create an orchestrator makes. The
reference is how you find an outcome you never received without the idempotency key or the task grant
that produced it.

A lost answer or a `503 service.unavailable` from a commitment does not prove that nothing was written:
when the audit destination refuses the response entry of a committed commitment, the call answers
`service.unavailable` with the commitment in place. Retry with the same `Idempotency-Key` and the same
request. The retry answers with the stored first outcome once the audit destination accepts its entry,
and it never commits a second time. A retry is itself a commitment, so it needs a live task grant that
covers the action. The Scheduling Rust client classifies an answer whose outcome is unknown and retries
it under the same key.

{/* Evidence: crates/registry-scheduling/src/store.rs, replay_stored_attempt() runs before
    check_grant_current(); crates/registry-scheduling/src/service.rs, require_permission();
    crates/registry-scheduling/tests/postgres_commitments.rs,
    a_refused_response_entry_answers_unavailable_with_the_commitment_committed and
    a_replayed_receipt_is_released_only_after_its_response_entry_is_accepted. */}

Once a task grant has expired, the token that carries it is refused with `authentication.refused` on
every `/v1` route, its read scope included, and once the stored response has passed
`retention.attemptReceiptRetentionDays`, a retry answers `410 idempotency.expired`. The sweep that erases the
stored response also clears the token issuer, subject, and key it was filed under, and keeps only a
SHA-256 digest of them and the command, so the key stays spent for that caller: a changed request
under it is still `409 idempotency.key-reused`, and another caller's identical key is unrelated. In
both cases, observe the outcome by reading:

- After a create, present a token for the same issuer and subject that carries the read scope and no
  task grant, and call `GET /v1/appointments` with `externalReferenceProduct`,
  `externalReferenceRecordType`, and `externalReferenceIdentifier`. A hold is not listed; one that is
  never confirmed expires and returns its capacity.
- After a reschedule or a cancel, read `GET /v1/appointments/{appointmentId}` with the same kind of
  token and compare its `revision` and `state` with the ones you acted on.

The listing is per principal by design. A hold or appointment is owned by the verified token issuer
and subject that booked it, so another principal sees an empty page even when it serves the same
product. Book and observe under one principal. History and audit carry a pseudonym keyed with the
deployment's audit hash key (`audit.hashKeyRef`) instead, which decides nothing: rotating that key
leaves every hold and appointment with the caller that booked it.

{/* Evidence: crates/registry-scheduling/src/store.rs, list_appointments_by_external_reference(),

    crates/registry-scheduling/src/service.rs, list_appointments(), get_appointment(), and
    owned_booking(); crates/registry-platform-oidc/src/authorization_claims.rs, grant_claims();
    crates/registry-scheduling/tests/postgres_commitments.rs,
    a_booking_stays_observable_by_reference_after_its_grant_expires and

## Problem codes

Every Scheduling problem response carries one `code` from this closed catalogue, always answered with
the HTTP status listed beside it.

Two codes are reserved: `eligibility.unavailable` and `hook.unavailable` are defined, titled, and
status-pinned for future synchronous decision paths, and no path in this milestone answers them yet.
Scheduling hooks are asynchronous observers, so their delivery failures never become caller problem
responses. The authored policy accepts only `after` URL handlers for `appointment.confirmed`,
`appointment.rescheduled`, and `appointment.cancelled`. Confirmed and rescheduled events may project
the appointment identifier, revision, offering, start, end, state, and policy revision. Cancelled
events may project only the appointment identifier, revision, and state. Conditions, principals,
local handlers, and observer proposals are refused.

## Route families

The served routes group into these families. A family name grants nothing on its own; authority is
checked per route.

| Family | Base paths | Authority profile |
| --- | --- | --- |
| Service description | `/v1/scheduling` | Catalogue read |
| Catalogue | `/v1/services`, `/v1/offerings`, `/v1/resources`, `/v1/locations` | Catalogue read |
| Availability | `/v1/availability`, `/v1/availability/explain` | Catalogue read; Explain |
| Holds | `/v1/holds`, `/v1/holds/{holdId}` | Commitment |
| Appointments | `/v1/appointments`, `/v1/appointments/{appointmentId}`, its `reschedule`, `cancel`, and `history` | Commitment for the mutations; Catalogue read for the reads |
| Appointment receipt observation | `/v1/appointments/receipt` | Catalogue read, matching the exact original owner, key, and creation request |
| Liveness and readiness | `/healthz`, `/readyz` | Any caller, without a token |

`/readyz` answers `service.unavailable` while PostgreSQL is unreachable or the audit writer is not
ready.

## Source of truth

The implementation is the source of truth, and the generated document is the published form of it.
The product generator builds the OpenAPI document from the Rust-owned route inventory, authority
profiles, wire schemas, and the exported problem catalogue, and the product check regenerates the
document and refuses byte drift. A running Scheduling process serves the routes in that document, and
does not serve the document itself.

{/* Evidence: products/scheduling/scripts/{generate_openapi.py,check-checkpoint.sh};
    products/scheduling/generated/registry-scheduling.openapi.json. */}

The problem code table is generated from maintained data whose codes and statuses match the generated
document. The route families table and the header rules are maintained by hand against the cited
source.

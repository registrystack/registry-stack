`registry-server-client` is the Rust client for Registry Server. It owns Server routes, query
types, Problems, entity tags, capability bindings, and lifecycle actions. The separate Relay
client owns Relay transport and product types. Both clients depend on the neutral `registry-record`
DTOs for strict Registry Record response decoding.

## Availability

Registry Stack is pre-1.0 Beta software. Keep the client on the same Registry Stack release as the
Server deployment unless a release note states a wider compatibility range. The crate has
`publish = false`, remains source-only in the Registry Stack workspace, and is not published to
crates.io.

```toml
[dependencies]
registry-server-client = { git = "https://github.com/registrystack/registry-stack", tag = "v<version>" }
```

## Construct a client

```rust
use registry_server_client::{RegistryServerClient, RegistryServerClientConfig};
use url::Url;

let config = RegistryServerClientConfig::new(
    Url::parse("https://server.example.invalid/institution-a")?,
);
let client = RegistryServerClient::new(config)?;
```

The base URL may contain a deployment prefix. HTTPS is required except for loopback HTTP. The URL
cannot contain credentials, a query, a fragment, or ambiguous empty path segments.

`RegistryServerClientConfig` provides `with_token_provider`, `with_request_timeout`,
`with_connect_timeout`, `with_max_response_bytes`, `with_user_agent`, and
`with_trusted_root_certificates`. Health and readiness never acquire or send a bearer. Other
operations attach one token when a provider is configured.

## Read operations

| Operation | Method | Returns |
| --- | --- | --- |
| Liveness and readiness probes | `health()`, `ready()` | `RegistryServerComplete<RegistryServerProbeStatus>` |
| Caller-filtered documents | `openapi(access_profile)`, `registry_metadata(access_profile)` | `RegistryServerComplete<RegistryServerRawDocument>` |
| Parsed registry metadata | `registry_contract(access_profile)` | `RegistryServerComplete<RegistryServerMetadata>` |
| Entity schema | `entity_schema(entity_identifier, access_profile)` | `RegistryServerComplete<RegistryServerRawDocument>` |
| Record read | `get_record(entity_route, record_identifier, options)` | `RegistryServerComplete<RegistryRecordSingleResponse>` |
| Record list | `list_records(entity_route, request)` | `RegistryServerComplete<RegistryServerPage<RegistryRecordCollectionResponse>>` |
| List continuation | `continue_list(continuation)` | `RegistryServerComplete<RegistryServerPage<RegistryRecordCollectionResponse>>` |
| Lookup | `lookup_record(entity_route, request)` | `RegistryServerComplete<RegistryRecordSingleResponse>` |

`RegistryServerResponseMetadata::trace_id()` is always present. A record read carries a `RegistryServerEtag`; probes,
discovery documents, lists, and lookups do not. A direct patch requires an ETag from a fresh read
through the same route and access profile.

`ServerContinuation` binds an opaque skip token to the entity route, representation, and optional
access profile. Its validated projection contains no `$select`, `$filter`, `$orderby`, `$top`, or
`$count` setters, so callers cannot combine a continuation with first-page options.

## Capability bindings

`registry_contract` parses caller-filtered Registry Metadata into `RegistryServerMetadata` and binds the
metadata to the client's exact origin. `select_direct_write` returns `RegistryServerDirectWrite::Create` or
`RegistryServerDirectWrite::Patch` only when the operation, route, request contract, capabilities, registry,
dataset, entity, profile, revision, and origin match the supported shape. `select_lifecycle`
returns one `RegistryServerLifecycleAuthority` for the matching entity and profile.

A mismatch returns `RegistryServerMetadataSelectionError`. The error carries a closed reason kind and no
response-controlled values.

## Writes

`ServerCreateRequest::new(data)` and `ServerPatchRequest::builder()` validate API field names,
I-JSON-safe values, nesting depth, operation count, and encoded body size before HTTP I/O. A patch
operation serializes under `/data/<field>`.

`RegistryServerIdempotencyKey::parse(value)` accepts 1 to 256 visible ASCII bytes except comma and semicolon.
The client never creates a key or retries a mutation. A retry after an unknown outcome must reuse
the same binding, body, precondition, representation, and key.

`create_record` sends the selected create operation and requires a `201` response whose `Location`
matches the created record. `patch_record` sends the selected patch operation with `If-Match` and
requires a `200` response without `Location`.

## Lifecycle actions

Change-request records carry a Server-owned `request` extension. `lifecycle_actions` promotes only
the actor-bound actions from a fresh record against a matching `RegistryServerLifecycleAuthority`.
`execute_lifecycle_action` sends the promoted href, body, ETag, and caller-supplied idempotency key.

`RegistryServerLifecycleOperation` contains `SubmitRequest`, `ApproveRequest`, `RejectRequest`,
`RequestRevision`, `ReviseRequest`, `CancelRequest`, and `ApplyRequest`. Refetch the record after a
success or refusal before choosing the next operation. Lifecycle ETags are not record ETags.

## Error contract

`RegistryServerClientError` is distinct from `RelayClientError`. Its public accessors expose only
the fixed error kind, status, registered Server Problem code, validated trace identifier, and bounded
transport or token category.

A Problem is accepted only when its closed members, code, status, title, detail, type URI, and
header/body trace match. Unknown Problem codes and malformed responses fail closed as
`RegistryServerProtocolFailure`. Request, metadata, ETag, idempotency-key, and lifecycle validation errors do
not retain response-controlled values.

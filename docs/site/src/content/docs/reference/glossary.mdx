<dl class="glossary-dl">
  <dt id="access-profile">access profile</dt>
  <dd>A named grant a caller selects with its token. In Base Registry Engine (BReg), it states which scopes, purposes, claims, operations, fields, and rows the caller may reach; see <a href="../../configure/breg-access/">Control access per profile</a>. In Registry Casework, an entry under `accessProfiles` admits a token carrying its `requiredScopes`, takes the caller's identity from `principalClaim`, and gives one role: staff, supervisor, administrator, or requester; see <a href="../../configure/casework/">Author a Casework policy</a>.</dd>

  <dt id="accountability-record">accountability record</dt>
  <dd>The protected record Registry Casework keeps of who made a <a href="#decision">Decision</a> and their private reason, held for the pinned policy's `accountabilityRetentionDays` and never sent to the producer. See <a href="../../operate/casework-retention/">Retention in Casework</a>.</dd>

  <dt id="action">Action</dt>
  <dd>A BReg typed operation with one bounded <a href="#planner">Plan</a> and a fixed execution mode. An `immediate` Action commits its effects atomically and returns an <a href="#action-receipt">ActionReceipt</a>; a `proposal` Action starts a durable <a href="#proposal">Proposal</a>.</dd>

  <dt id="action-receipt">ActionReceipt</dt>
  <dd>The response to a successful immediate <a href="#action">Action</a>: its `applicationId` and, under `results`, the Record type, `recordId`, and new revision of each effect the caller may see. A refused invocation leaves no partial change.</dd>

  <dt id="appointment">appointment</dt>
  <dd>A confirmed claim on Registry Scheduling capacity, made from a <a href="#hold">hold</a> or directly, that the caller may reschedule or cancel within the <a href="#offering">offering</a>'s cutoff. Each change advances its revision.</dd>

  <dt id="assertion">assertion</dt>
  <dd>Registry Evidence's answer: a signed payload that carries the answer to one <a href="#requirement">requirement</a> and none of the record behind it. Signed flattened JSON Web Signature (JWS) is the default serialization; <a href="#sd-jwt-vc">SD-JWT VC</a> carries the same assertion.</dd>

  <dt id="assertion-definition">assertion definition</dt>
  <dd>One fixed question in an <a href="#evidence-project">Evidence project</a>, declared under `assertionDefinitions` with its Requirement URI, purpose, subject roles, source, permitted outputs, and the grant ceiling no caller can exceed.</dd>

  <dt id="audit-journal">audit journal</dt>
  <dd>The minimized request and response entries Base Registry Engine writes to a per-process file or stdout stream, separately from PostgreSQL; operators ship it to append-only storage. An <a href="#erasure">erasure</a> does not remove audit entries. See <a href="../../operate/breg-retention/">Retain, erase, and audit</a>.</dd>

  <dt id="base-registry-engine">Base Registry Engine (BReg)</dt>
  <dd>The PostgreSQL system of record whose data model and REST API are compiled from a <a href="#registry-project">registry project</a>, with no built-in domain types. Binaries `breg` and `bregctl`.</dd>

  <dt id="calendar">calendar</dt>
  <dd>In Registry Casework, the working week and time zone a <a href="#clock">clock</a> counts working days against, with a named holiday set whose dates arrive as a separate revision.</dd>

  <dt id="claim">claim</dt>
  <dd>In Casework, taking an eligible <a href="#review-task">ReviewTask</a> into a reviewer's holdings at its current revision, before they decide, release, or delegate it. A JWT claim is a separate meaning: a named value inside a token.</dd>

  <dt id="clock">clock</dt>
  <dd>A pinned Casework policy rule that measures a subject or a <a href="#stage">stage</a> against a deadline, in elapsed time or working days on a <a href="#calendar">calendar</a>. It can send a reminder or move a due task to another queue, and never decides an outcome.</dd>

  <dt id="configuration-revision">`configurationRevision`</dt>
  <dd>The `sha256:` digest a Registry Evidence <a href="#assertion">assertion</a> carries for what its <a href="#assertion-definition">assertion definition</a> does, which relying services pin. It moves with the source request or response shape, selector profiles, Functions, codelists, schemas, outputs, or validity, and stays put for question text, fixtures, endpoints, credentials, grants, and signing keys.</dd>

  <dt id="context-provider">context provider</dt>
  <dd>The source's read-only review interface a Casework policy names under `context.mode: current-source`. Casework asks it again under each reviewer's own credential when a task opens and keeps none of the source's data.</dd>

  <dt id="decision">Decision</dt>
  <dd>One reviewer's recorded choice of an outcome the <a href="#review-policy">ReviewPolicy</a> declares. Casework counts decisions against each <a href="#stage">stage</a>'s threshold and settles the <a href="#review-request">ReviewRequest</a>.</dd>

  <dt id="deployment-bundle">deployment bundle</dt>
  <dd>A deferred project-root packaging concept tracked by <a href="https://github.com/registrystack/registry-stack/issues/361">registry-stack issue #361</a>. Current source does not generate, sign, verify, or activate a project-root bundle. Each product uses its own bundle, and no Registry Stack component binds or atomically activates them, so this is not atomic project activation.</dd>

  <dt id="deployment-candidate">deployment candidate</dt>
  <dd>The directory `evidencectl package` writes from an <a href="#evidence-project">Evidence project</a> and one target: an immutable `bundle/`, a runtime file, and a compiled authority. Its <a href="#package-digest">package digest</a> identifies the bundle.</dd>

  <dt id="directory">directory</dt>
  <dd>Registry Casework's runtime record of <a href="#team">teams</a>, their staff and supervisors, and the <a href="#queue">queues</a> they serve, maintained by an administrator through the directory API under revisions. See <a href="../../configure/casework-directory/">Staff the directory</a>.</dd>

  <dt id="erasure">erasure</dt>
  <dd>The irreversible removal of retained detail under an approved retention request. In Base Registry Engine, `bregctl history erase` and `bregctl proposal-retention erase` remove retained revisions or Proposal detail, never the current record or the <a href="#audit-journal">audit journal</a>; Registry Casework erases expired review data through runtime maintenance.</dd>

  <dt id="evidence-gateway">Registry Evidence</dt>
  <dd>The minimum-disclosure assertion product: it answers one predefined question from a fixed read of your system with a signed <a href="#assertion">assertion</a>, never the source record. Binaries `evidence` and `evidencectl`.</dd>

  <dt id="evidence-project">Evidence project</dt>
  <dd>An `evidence.yaml` file and the scripts it names, kept in version control, declaring <a href="#assertion-definition">assertion definitions</a>, sources, selector profiles, and Functions. `evidencectl` checks, tests, and packages it with a target into a <a href="#deployment-candidate">deployment candidate</a>.</dd>

  <dt id="function">Function</dt>
  <dd>A project-local typed implementation asset. In BReg, an Action's <a href="#planner">Plan</a> uses one to compute effects within the Action's declared write ceiling; it cannot grant authority or invent a review decision. In an <a href="#evidence-project">Evidence project</a>, a <a href="#rhai">Rhai</a> script with a declared interface that turns a <a href="#source">source</a> response into facts or facts into declared outputs, under fixed operation and size limits. In a Registry Coordinator <a href="#workflow">workflow</a>, a Rhai script that routes a `choose` step or computes a value a call's input maps with `type: function`, with no clock, file, network, database, or credentials.</dd>

  <dt id="grant-ceiling">grant ceiling</dt>
  <dd>The widest authority a Registry Evidence <a href="#assertion-definition">assertion definition</a> lets any grant give for it: the authorities, actor kinds, value origins, and audiences a grant may name. A <a href="#target">target</a> authority's grant may only narrow it; Registry Evidence refuses to activate one that widens it.</dd>

  <dt id="hold">hold</dt>
  <dd>A short-lived claim on Registry Scheduling capacity that expires on its own unless the caller confirms it into an <a href="#appointment">appointment</a>.</dd>

  <dt id="holiday-set">holiday set</dt>
  <dd>A named list of dates an <a href="#opening">opening</a> excludes.</dd>

  <dt id="holder-bound">holder-bound</dt>
  <dd>The Registry Evidence subject binding mode in which the binding derives from the holder key's RFC 7638 thumbprint instead of the audience. Its requirement returns only <a href="#sd-jwt-vc">SD-JWT VC</a>, and the relying party checks the audience at presentation by verifying a key-binding JWT.</dd>

  <dt id="journey">journey</dt>
  <dd>One scenario in `tests/journeys.yaml` that `bregctl test` replays over HTTP against a throwaway database. A fully successful run writes a <a href="#receipt">receipt</a>. See <a href="../../configure/breg-journeys/">Test with journeys</a>.</dd>

  <dt id="module">module</dt>
  <dd>A reusable `modules/<id>/module.yaml` file that contributes Record types, value types, Functions, Actions, and additive extensions to a Base Registry Engine <a href="#registry-project">registry project</a>.</dd>

  <dt id="offering">offering</dt>
  <dd>One bookable Registry Scheduling service at one location, in exact-time or arrival-window mode, drawing on a <a href="#resource-pool">resource pool</a> or on published windows.</dd>

  <dt id="oid4vci">OID4VCI</dt>
  <dd>OpenID for Verifiable Credential Issuance. The `registry-evidence-oid4vci` supporting service implements a frozen OID4VCI 1.0 Final profile to deliver holder-bound `dc+sd-jwt` credentials to a wallet; Registry Evidence signs them.</dd>

  <dt id="opening">opening</dt>
  <dd>The weekly hours on which an exact-time <a href="#offering">offering</a> publishes start times, minus its <a href="#holiday-set">holiday sets</a>.</dd>

  <dt id="outbox">outbox</dt>
  <dd>A table in a product's own database that takes one row per event or intent to deliver, written in the same transaction as the change that caused it, so a worker delivers it after the commit and a slow receiver never blocks the change. A Base Registry Engine registry's outbox feeds the webhook worker inside `breg`; Registry Scheduling's holds reminder intents and observer events.</dd>

  <dt id="package">package</dt>
  <dd>The compiled and verified form of one product's reviewed authoring input.</dd>

  <dt id="package-digest">package digest</dt>
  <dd>The `sha256:` digest of a package's `SHA256SUMS` file, reported by every product that serves a package and accepted as `package.expectedDigest`. It is an integrity digest, not an authenticity proof: packages are unsigned.</dd>

  <dt id="planner">Plan</dt>
  <dd>The effects an <a href="#action">Action</a> makes, authored under `plan`: a `type: fixed` Plan lists them in order, and a `type: function` Plan names a <a href="#function">Function</a> that computes them within the Action's declared `writes`.</dd>

  <dt id="policy-package">policy package</dt>
  <dd>The directory `caseworkctl package` writes from a checked Casework project, with its exact `SHA256SUMS`. The runtime verifies that closure before serving and refuses a changed, missing, or extra file.</dd>

  <dt id="producer">producer</dt>
  <dd>The system that sends Registry Casework a <a href="#review-request">ReviewRequest</a> and reads its <a href="#review-result">ReviewResult</a>, declared under `trustedProducers`. It authenticates independently of the human reviewers.</dd>

  <dt id="proposal">Proposal</dt>
  <dd>BReg durable work created by a proposal-mode Action. Submission freezes its inputs, effects, target revisions, and the review it requests; BReg applies that exact plan automatically by default, or manually when configured.</dd>

  <dt id="purpose">purpose</dt>
  <dd>The authorized reason a caller gives for a Registry Evidence request: a configured code from the definition's declared purposes and the caller's grant, echoed into the assertion. In Base Registry Engine, an <a href="#access-profile">access profile</a>'s `requiredPurposes` lists the purposes it accepts.</dd>

  <dt id="queue">queue</dt>
  <dd>A named Casework inbox that <a href="#stage">stages</a>, routing, and clock steps send tasks to. A person reaches its tasks only as a member of a <a href="#team">team</a> serving it.</dd>

  <dt id="rebaseline">rebaseline</dt>
  <dd>The Base Registry Engine maintenance run, `bregctl history rebaseline`, that restores snapshot coverage after a history <a href="#erasure">erasure</a> by verifying every live row against its retained journal head.</dd>

  <dt id="receipt">receipt</dt>
  <dd>The JSON document a fully successful `bregctl test` run writes for one exact candidate, recording the <a href="#journey">journeys</a> that passed, so packaging can refuse a receipt taken for anything else.</dd>

  <dt id="registry-record">Record (Registry Record)</dt>
  <dd>One stored row of a BReg <a href="#record-type">Record type</a>, with a stable UUID and a revision counter each committed change advances. Registry Record v1 is the strict shape BReg and its clients return it in; see the <a href="../breg-api/#record-envelope">Base Registry Engine API reference</a>.</dd>

  <dt id="record-type">Record type</dt>
  <dd>The BReg definition of one kind of <a href="#registry-record">Record</a>: its fields, route, dataset, and `mutationPolicy`, authored under `recordTypes`.</dd>

  <dt id="registry-casework">Registry Casework</dt>
  <dd>The human-review product: a <a href="#producer">producer</a> sends a <a href="#review-request">ReviewRequest</a>, authorized people decide its <a href="#review-task">ReviewTasks</a>, and the producer reads the result. The source keeps its data, its disclosure, and all authority to change it. See the <a href="../../start/casework/">Registry Casework overview</a>.</dd>

  <dt id="registry-coordinator">Registry Coordinator</dt>
  <dd>The workflow product: it runs a reviewed <a href="#workflow">workflow</a> of product calls and <a href="#wait">waits</a>, started by an authorized caller or by a signed event from a trusted event source, and keeps each <a href="#run">run</a> going across outages and restarts. Every product it calls keeps its own authority and data, and the Coordinator is never a review provider. See the <a href="../../start/coordinator/">Registry Coordinator overview</a>.</dd>

  <dt id="registry-discovery">Registry Discovery</dt>
  <dd>A curated, read-only index that tells an application which Evidence types meet a requirement and which Registry Evidence services assert them. It holds no credentials and vouches for no provider; trust stays with the application. See the <a href="../../start/discovery/">Registry Discovery overview</a>.</dd>

  <dt id="registry-manifest">Registry Manifest</dt>
  <dd>The Rust library and `registry-manifest` command that check one portable `metadata.yaml` and render it into standards-shaped metadata, without running a service. See the <a href="../../products/registry-manifest/">Registry Manifest overview</a>; the <a href="../../products/registry-manifest/reference/">Registry Manifest reference</a> is authoritative for the current top-level keys.</dd>

  <dt id="registry-messaging">Registry Messaging</dt>
  <dd>The notification product: it sends one message to one destination over one channel for an authorized caller, rendered from a reviewed template through an operator-configured provider, and reports what is known about delivery. Why and when to send, to whom, and whether the person agreed to be contacted stay with the caller. See the <a href="../../start/messaging/">Registry Messaging overview</a>.</dd>

  <dt id="registry-project">registry project</dt>
  <dd>The directory of YAML files an adopter writes for one Base Registry Engine registry: `registry.yaml` plus optional <a href="#module">modules</a> and <a href="#journey">journeys</a>. `bregctl` checks, tests, and packages it. See <a href="../../configure/breg/">Author a registry project</a>.</dd>

  <dt id="registry-render">Registry Render</dt>
  <dd>The document product: it renders PDF documents from registry data through Typst, byte for byte the same for the same inputs, as a service with an audit journal or as a command line for authoring and counter printing. See the <a href="../../start/registry-render/">Registry Render overview</a>.</dd>

  <dt id="registry-scheduling">Registry Scheduling</dt>
  <dd>The booking product: it publishes bookable services over supply the operator anchored and gives authorized callers short <a href="#hold">holds</a> and confirmed <a href="#appointment">appointments</a>, with every capacity decision made in one transaction under a <a href="#task-grant">task grant</a>. See the <a href="../../start/scheduling/">Registry Scheduling overview</a>.</dd>

  <dt id="registry-source-profile">`Registry-Source-Profile`</dt>
  <dd>The header a Casework reviewer sends to select the source's access profile for work whose context comes from a <a href="#context-provider">context provider</a>, which reads under that profile and the reviewer's own credential. Producer, policy, and accountability routes refuse it.</dd>

  <dt id="requirement">requirement</dt>
  <dd>The question a Registry Evidence <a href="#assertion-definition">assertion definition</a> answers, named by a stable Requirement URI such as `urn:example:requirement:adult-status:v1` that a caller sends. A change in meaning gets a new URI.</dd>

  <dt id="resource-pool">resource pool</dt>
  <dd>The operator-anchored set of resources, such as counter stations, that an exact-time <a href="#offering">offering</a> draws on. It is an environment record applied to the database, not part of the policy package.</dd>

  <dt id="review-policy">`ReviewPolicy`</dt>
  <dd>The Casework declaration under `reviewPolicies` that fixes a review's context, <a href="#stage">stages</a>, schemas, outcomes, routing, clocks, and retention; its ID, version, and digest are pinned at acceptance. See <a href="../../configure/casework/">Author a Casework policy</a>.</dd>

  <dt id="review-request">`ReviewRequest`</dt>
  <dd>What a <a href="#producer">producer</a> sends Casework: the subject to review and the <a href="#review-policy">ReviewPolicy</a> to review it under. Casework pins the policy's binding and a `submissionDigest` when it accepts the request.</dd>

  <dt id="review-result">`ReviewResult`</dt>
  <dd>The immutable terminal answer a producer reads for its <a href="#review-request">ReviewRequest</a>: subject, policy binding, `submissionDigest`, status, outcome, and any public reason. It never names the reviewer and grants no authority to change the source.</dd>

  <dt id="review-task">`ReviewTask`</dt>
  <dd>One human contribution to a <a href="#review-request">ReviewRequest</a>, created when a <a href="#stage">stage</a> becomes active, with its queue, revision, holder, and <a href="#decision">Decision</a>.</dd>

  <dt id="rhai">Rhai</dt>
  <dd>The bounded scripting language for adopter-authored Functions, run under fixed operation and size limits. Registry Evidence Functions extract facts and derive outputs; Base Registry Engine Functions compute an Action's effects; Registry Coordinator Functions route a `choose` step or compute a mapped call input.</dd>

  <dt id="row-boundary">row boundary</dt>
  <dd>A rule in a Base Registry Engine <a href="#access-profile">access profile</a> that binds one record field to a verified token claim with `equals` or `in`, so a request reaches only matching rows.</dd>

  <dt id="run">run</dt>
  <dd>One admitted execution of a Registry Coordinator <a href="#workflow">workflow</a>. A run keeps the workflow revision it was admitted under, so a later upgrade never changes a run in flight.</dd>

  <dt id="scheduling-fixture">scheduling fixture</dt>
  <dd>A YAML case that `schedulingctl test` replays offline against a Registry Scheduling policy and its records, stating the bookings it expects to succeed or be refused.</dd>

  <dt id="scheduling-hook">scheduling hook</dt>
  <dd>An `after` URL observer for `appointment.confirmed`, `appointment.rescheduled`, or `appointment.cancelled`. It receives a closed projection of the <a href="#appointment">appointment</a> after the capacity transaction commits and cannot change the outcome.</dd>

  <dt id="sd-jwt-vc">SD-JWT VC</dt>
  <dd>Selective Disclosure JWT Verifiable Credential (IETF draft), the second serialization Registry Evidence offers for the same stateless <a href="#assertion">assertion</a> under its frozen profile. It adds no credential lifecycle. Media type: `application/dc+sd-jwt`.</dd>

  <dt id="selector-profile">selector profile</dt>
  <dd>The bound on what a caller may send to identify a subject in a Registry Evidence request, declared in the <a href="#evidence-project">Evidence project</a>: the fields, their sizes, and the aggregate limit. A <a href="#source">source</a> takes its request values only from those fields.</dd>

  <dt id="source">source</dt>
  <dd>One fixed read an <a href="#evidence-project">Evidence project</a> declares: an HTTP request with one method and path template, or one SQL statement over a read-only SQLite extract, with the response shape it accepts and the fields it may read. Registry Evidence reaches a source with the credential its <a href="#target">target</a> binds, never the caller's.</dd>

  <dt id="stage">stage</dt>
  <dd>One step of a <a href="#review-policy">ReviewPolicy</a>, run in order, naming its <a href="#queue">queue</a>, the profiles that may decide, and how many independent reviewers must approve.</dd>

  <dt id="subject-binding">subject binding</dt>
  <dd>The opaque value that stands for a subject in a Registry Evidence <a href="#assertion">assertion</a> in place of its identifier. An audience-scoped binding differs for each relying audience, so two cannot join their answers; a <a href="#holder-bound">holder-bound</a> binding derives from the holder's key instead.</dd>

  <dt id="target">target</dt>
  <dd>The operator-owned file, such as `local-target.yaml`, that binds an <a href="#evidence-project">Evidence project</a> to one deployment: the token issuer, each <a href="#source">source</a>'s endpoint and credential, the signer, and the audit path. Its target authority names the <a href="#access-profile">access profiles</a> that may call and the grants each holds.</dd>

  <dt id="task-grant">task grant</dt>
  <dd>The signed claim in a caller's access token that names the Registry Scheduling service, location, and actions another system has allowed. It is matched exactly before the capacity transaction opens, and its expiry is checked again immediately before the claim commits.</dd>

  <dt id="team">team</dt>
  <dd>A named Casework group that serves <a href="#queue">queues</a> and declares the profiles its members and supervisors must hold; its membership lives in the <a href="#directory">directory</a>.</dd>

  <dt id="wait">wait</dt>
  <dd>A Registry Coordinator step that holds a <a href="#run">run</a> until an instant (`wait-until`) or until a named completion an earlier accepted call exposes (`wait-for`), such as a Casework <a href="#review-result">ReviewResult</a>. A wait never renews an approval or creates downstream authority.</dd>

  <dt id="workflow">workflow</dt>
  <dd>A finite graph of steps in YAML that Registry Coordinator checks offline and packages into an immutable artifact an operator pins by digest. Its five step types call one product operation, choose the next step, wait, or finish.</dd>

</dl>

## Style notes

- Formal maintained product names use title case. Retired product names remain title case only in explicit historical context.
- Repo slugs and binary names are lowercase and monospace.
- Legacy underscore forms appear only in historical pages or `rename_status` fields.
- The glossary provides a reference for standards acronyms but does not replace per-page first-use expansion.

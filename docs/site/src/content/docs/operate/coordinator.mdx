An author has handed you Registry Coordinator packages and their digests.
You operate one Coordinator service beside PostgreSQL 17 or newer and your institution's OpenID Connect issuer.
Serve those workflows behind your TLS edge, then inspect, recover, erase, rotate, and restore them.
Receiving Registry Stack products still verify their own caller and task authority.
Coordinator runs finite reviewed workflow packages, one per workflow, and preserves every admitted run's original definition.

Authors package workflows in [Author a Coordinator workflow](../../configure/coordinator/).

The order of work is:

1. Install the binaries and pin each workflow's package digest.
2. Create the keys and secrets.
3. Create the database and roles.
4. Write the runtime file and check it offline.
5. Apply the deployment, then check it with the runtime credential.
6. Start the service under your supervisor.
7. Check health and run doctor with an operator token.
8. Scrape the metrics listener from your monitoring.

## What you provide

- **PostgreSQL 17 or newer**, with one database and two login roles: a migration role that owns the
  schema and a runtime role that serves.
- **Your OpenID Connect issuer**, whose RFC 9068 access tokens (`typ: at+jwt`) callers present; each
  product connection is a client there.
- **A TLS terminator** in front of a service listener bound to a private address.
- **Secret files** for three keys, the two database URLs, and each connection credential, owned by
  the service user.
- **Durable storage** for the audit file.
- **The package directory and digest of each workflow**, up to sixteen in one deployment, with the
  author's runtime template.
- **The downstream policy the workflows need**, such as Base Registry Engine (BReg) access profiles, the Casework trusted
  producer, and Messaging templates, granting each connection identity only what it uses.

## Install and package

Release packaging includes `coordinator` and `coordinatorctl` for Linux amd64, Linux arm64, and macOS arm64, starting with `v0.44.0`.
Set `tag` to the [release tag](https://github.com/registrystack/registry-stack/releases) you are deploying, then run its checksum-verifying installer:

```sh
tag='<tag>'
curl -fsSL "https://github.com/registrystack/registry-stack/releases/download/${tag}/coordinator-${tag}-install.sh" | bash
```

The installer keeps the macOS FIPS libraries beside their executables.
The binary release does not imply that the Coordinator container image has been released; its image-specific security evidence is a separate gate.
Install `coordinator` and `coordinatorctl` from one source version, at absolute paths.

### Build from source

On Linux, build the two binaries from the maintained checkout and install them in a service-owned executable directory:

```sh
cargo build --locked --release -p registry-coordinator --bins
mkdir -p "$HOME/.local/bin"
install -m 755 target/release/coordinator target/release/coordinatorctl "$HOME/.local/bin/"
export PATH="$HOME/.local/bin:$PATH"
```

On macOS arm64, use the maintained packager to include and relocate the exact FIPS library the build links.
Use a fresh build directory so a CMake cache configured for a different minimum OS version is not reused.
Keep each extracted binary beside its bundled library and notices; copying the executable alone loses its runtime dependency.

```sh

  python3 release/scripts/macos_fips_packaging.py archive \
```

Use the absolute executable paths in your service definition.
The operator shell links point to the complete install directories, and existing link destinations are refused.
The packager refuses an existing output directory or archive and checks the linked library's deployment target.
Retain the complete install directories.

### Package a workflow

Create and check the governed workflow package:

```sh
coordinatorctl init --directory ./follow-up
coordinatorctl check --project ./follow-up --explain
coordinatorctl package --project ./follow-up --output ./follow-up-package
```

`package` writes one immutable `definition.json` snapshot and `SHA256SUMS`.
When the project has a `scenarios.yaml`, `package` runs it first and writes nothing unless every case passes; `coordinatorctl test --project DIR` runs the same cases on their own.
Existing output is never overwritten, so build a fresh directory for each update.
Install the directory read-only, record the package digest it prints, and pin it as that workflow's `deployment.packages` entry, with `root` and `expectedDigest`.

One project is one workflow and one package; its workflow ID is the workflow name callers start.
A deployment lists one pinned package per workflow, up to sixteen.
Offline checks and startup refuse an empty list, a package root or digest listed twice, and two packages with the same workflow ID, each naming the entry to fix.
The [two-flow runtime example](https://github.com/registrystack/registry-stack/tree/main/products/coordinator/examples) serves the delayed follow-up and governed action examples from one deployment.
Runtime files, endpoints, credentials, state keys, and audit custody are deployment configuration, outside the package.

The human `project.version` is a display label.
A semantic change produces a new `workflowRevision`, and activating its package does not replace existing runs' snapshots.
Retain the keys needed to read those snapshots and the custody metadata needed for recovery.

### Package digest and definition digest

Pin the package digest for exact bytes; use `workflowRevision` for execution semantics.

- The computed workflow revision hashes the input, graph, outcomes, used Operation and Function revisions, and host execution contracts.
  Presentation labels and descriptions do not change it.
  `check` prints it on its `Definition:` line, and start, status, list, and inspect report it as `workflowRevision`.
  Existing runs keep their admitted revision.
- The package digest is the SHA-256 of `SHA256SUMS`.
  That file covers the exact `definition.json` snapshot bytes, including presentation metadata.
  `package` prints it, `plan` reports it as `packageDigest` beside `activePackageDigest`, and `deployment-status` reports package pins under `workflows`.

Put the package digest in `expectedDigest`.
`plan`, `apply`, and startup check the installed directory against it and refuse a package whose content no longer matches, with `coordinator.deployment.refused` and the advice to restore the exact pinned package.
`workflowsDigest` identifies the whole set of pinned packages; the `active` activation record in `plan`, `apply`, and `deployment-status` carries that set digest in its `packageDigest` field.

New starts must name the active `workflowRevision`.
A caller recovering an unknown admission must send the exact original start key, input, and revision, even after a new package is activated, and the original run keeps its admitted snapshot and revision.
`plan` and `apply` also check current live-run connection bindings and refuse removal of a workflow whose runs could still act or need review, so work admitted after `plan` can make `apply` refuse.

## Create the keys, secrets, and roles

Create every secret as the user that runs `coordinator` and `coordinatorctl`.
A `secret:file/NAME` reference reads the file `NAME` directly under the file provider's `root`.
That file must meet the [secret file rule](../../security/hardening-checklist/#secret-files), for example a regular file owned by that user, with mode `0400` or `0600` and exactly one link.
A `secret:env/NAME` reference reads an environment variable when `secretProviders` declares `environment: {}`.

Coordinator uses three kinds of key, each exactly 32 raw random bytes in its own file:

- The **payload state key** encrypts the run state held in PostgreSQL.
  `deployment.stateKeys` lists its versions and `activeStateKey` names the version that writes.
- The **admission key** derives start identities, owner hashes, and command keys, so it determines the spent-key namespace.
  It stays the same for the deployment's lifetime and must differ from every state key.
- The **audit key** derives the keyed private references in the audit journal.

```sh
install -d -m 0700 /run/registry-coordinator/secrets
(umask 077 && openssl rand -out /run/registry-coordinator/secrets/state-key-1 32)
(umask 077 && openssl rand -out /run/registry-coordinator/secrets/admission-key 32)
(umask 077 && openssl rand -out /run/registry-coordinator/secrets/audit-key 32)
```

Reference them from the runtime file:

```yaml
deployment:
  auditKeyRef: secret:file/audit-key
  activeStateKey: 1
  stateKeys:
    "1":
      keyRef: secret:file/state-key-1
  admissionKeyRef: secret:file/admission-key
```

Key versions are canonical decimal integers from 1 through 4294967295.
Zero is never an active or retained version, and a deployment lists at most 16 versions.
Offline checks reject invalid versions before resolving key material.

:::danger[A database without its keys cannot be read]
A restored database needs every state key version its rows used and the deployment's admission key.
Back up each key file under custody separate from the database.
:::

The database URLs are secrets too.
`database.runtimeUrlRef` names the runtime role's URL and `database.migrationUrlRef` the migration role's URL; only `apply` resolves the migration URL.
Institutional connections use `sslmode=require`.
Coordinator verifies the database certificate against the system roots, or against `database.caBundleRef` for a private root.

Enter each URL at a hidden prompt, so its password stays out of shell history.
Use a URL such as `postgresql://coordinator_runtime:...@db.example.org:5432/coordinator?sslmode=require`.
This writes new owner-only files and refuses to overwrite existing secrets:

```sh
python3 - <<'PYTHON'
import getpass
import os
from pathlib import Path

root = Path('/run/registry-coordinator/secrets')
for name in ('runtime-database-url', 'migration-database-url'):
    value = getpass.getpass(f'{name}: ')
    if not value:
        raise SystemExit('A database URL is required')
    fd = os.open(root / name, os.O_WRONLY | os.O_CREAT | os.O_EXCL, 0o600)
    with os.fdopen(fd, 'w') as secret:
        secret.write(value)
PYTHON
```

```yaml
database:
  runtimeUrlRef: secret:file/runtime-database-url
  migrationUrlRef: secret:file/migration-database-url
```

The [single-flow runtime example](https://github.com/registrystack/registry-stack/tree/main/products/coordinator/examples) reads the same two URLs from environment variables instead.

Write each connection credential the runtime file names the same way, such as the private JWK an `authorization.signingKeyRef` names.
You register its public half at the issuer, one client and key per downstream authority.
The connection's required `clientAssertionAudience` is the issuer identifier, exactly as the issuer's metadata publishes it, which the client assertion carries as its only audience (RFC 10070 section 4).
Secret values never appear in a diagnostic or a log.

### Create the database and roles

Use PostgreSQL 17 or newer; `apply` and startup refuse an older server.
`provision` creates what the two database URLs in your runtime file name: the migration role, the runtime role, and the database, and it lets only those two roles connect.
It takes the role names, the database name, and the passwords from `database.migrationUrlRef` and `database.runtimeUrlRef`, so you write each of them once, except that when the runtime file has a `deployment` block, the user of the runtime URL must be `deployment.runtimeRole`: `provision` refuses a different user before it connects, with `coordinator.runtime-config.runtime-role-mismatch`.
Without a `deployment` block, `provision` creates the role the runtime URL names, and `apply` then refuses the missing block.

Run it as a PostgreSQL administrator that can create roles and databases (`CREATEROLE` and `CREATEDB`).
It needs no superuser.
Put the administrator URL in a file or an environment variable, never on the command line.
The connection always uses verified TLS: it trusts the certificate authority behind `database.caBundleRef` when the runtime file names one, and the system roots otherwise.
The URL's `sslmode` must be `require`, `verify-ca`, or `verify-full`.
The administrator URL must name the same host and port as the two product URLs, or `provision` refuses it as `platform.provision.target-mismatch`.
It must also name a database other than the product database, such as `postgres`, or `provision` refuses it as `platform.provision.target-invalid`.
Where the administrator may connect only to the product database, `provision` cannot run: add `--print-sql` and give the script to the person who administers the server.

```sh
coordinatorctl provision --runtime-config /etc/registry-coordinator/runtime.yaml \
  --admin-url-file /run/registry-coordinator/secrets/admin-database-url
```

Use `--admin-url-env NAME` for a variable instead of a file.
Run again at any time: it creates only what is missing, refuses a role or database that exists in another shape, and never changes a password or drops anything.
Add `--format json` for a machine-readable report.
The report and the errors never contain a password, a password verifier, or a URL.

To review the statements first, or to run them yourself with `psql`, add `--print-sql`.
It connects to nothing and prints a script with a `\password` line after each role instead of a password:

```sql
-- provision script, product coordinator. Nothing was run.
-- For a server where these objects do not exist yet. Review, then run with psql as an
-- administrator that has CREATEROLE and CREATEDB. It stops at the first error.
\set ON_ERROR_STOP on
SET createrole_self_grant = 'set,inherit';
CREATE ROLE "coordinator_migration" LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS;
\password "coordinator_migration"
CREATE ROLE "coordinator_runtime" LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS;
\password "coordinator_runtime"
CREATE DATABASE "coordinator" WITH ALLOW_CONNECTIONS false;
REVOKE ALL ON DATABASE "coordinator" FROM PUBLIC;
GRANT CONNECT ON DATABASE "coordinator" TO "coordinator_migration", "coordinator_runtime";
GRANT CREATE ON DATABASE "coordinator" TO "coordinator_migration";
ALTER DATABASE "coordinator" ALLOW_CONNECTIONS true;
```

These are the only grants `provision` makes.
The migration role needs `CREATE` on the database because `apply` creates the schema the runtime file's `namespace` names, and the migration role owns that schema and its tables.
A namespace starts with `coordinator_` and is at most 60 characters.
The runtime role needs only `CONNECT`.
`apply` grants it, in that schema:

- `USAGE` on the schema.
- `SELECT`, `INSERT`, `UPDATE`, and `DELETE` on `runs`, `jobs`, `admission_lock`, and `completion_waits`.
- `SELECT` on `control`, `coordinator_activations`, and `coordinator_migrations`.
- `UPDATE` on the four recovery-hold columns of `control`.

`apply`, `deployment-status`, and startup check the runtime role's effective authority, including indirect role membership.
They refuse a runtime role that is a superuser, bypasses row-level security, belongs to the migration role, can create objects in the schema, holds `TRIGGER`, or owns objects there.
Use the runtime role in `database.runtimeUrlRef` and set `deployment.runtimeRole` to its name.

Each service process keeps a fixed pool of at most 32 sessions as the runtime role.
Allow 32 connections per process in the role's connection limit and the server's `max_connections`.

## Write the runtime file

Runtime files use the `id.registrystack.org/formats/coordinator/runtime/v1alpha1` `apiVersion` and the `CoordinatorRuntimeConfig` kind.
Offline checking reads no credentials and contacts no endpoint.
Start from the author's `runtime.yaml` and complete it.
Keep the file outside the packages; it holds secret references, never values.
Keep the project runtime's `secretProviders`, `database.runtimeUrlRef`, `namespace`, and logical `connections`, then add the `deployment` block.

| Key | What it sets |
| --- | --- |
| `namespace` | The deployment's SQL namespace, `coordinator_` followed by lowercase letters, digits, or `_`. |
| `secretProviders` | Where references resolve: `secret:file/<name>` under `file.root`, and `secret:env/<NAME>` only when `environment: {}` is present. |
| `eventSources` | Optional trusted producers whose signed events start runs, each with its `source` URI and distinct HMAC keys under `triggers.<workflow>.<trigger>`. |
| `deployment.databaseId` | The deployment's durable identity; a mismatch refuses startup and apply. |
| `deployment.runtimeRole` | The runtime role, matching the role in `database.runtimeUrlRef`. |
| `deployment.packages` | One `root` and `expectedDigest` per workflow, up to sixteen. |
| `deployment.listener` | The service socket `bind`, with `tlsTermination: operator-controlled-upstream` behind your TLS terminator. |
| `deployment.metricsListener` | Optional private address that serves `/metrics`. |
| `deployment.authentication` | The issuer, audience, signing-key source, and caller policies. |

The `deployment` block also holds `auditFile` and the three key references from the previous section.

`databaseId` is the deployment's durable logical identity.
Keep it constant through restarts, credential rotation, and compatible package updates; an identity mismatch refuses startup or apply.
Use a distinct identity and namespace for an independent deployment.
`deployment.auditFile` must be an absolute path writable by the service user, with durable storage and custody appropriate for the institution.

The [configuration reference](../../reference/coordinator-configuration/) lists every key and bound.
Its [connections](../../reference/coordinator-configuration/#connections) section covers each connection type, up to sixteen in one deployment.

The service listener uses the shared private listener and TLS policy.
Use `operator-controlled-upstream` behind your controlled TLS terminator.
Use `loopback-plaintext` to bind the listener on loopback. For plaintext PostgreSQL on the same host, set `database.transport: loopback-plaintext` separately.
Downstream bindings use HTTPS, or explicit loopback HTTP for supervised local fixtures.
Token signing-key rotation preserves the registered downstream client identity, endpoint, audience, resource, scopes, and approved task authority.

### Expose the metrics listener

`deployment.metricsListener` is optional.
When present, its `bind` is required and `/metrics` is served on that socket only: the service listener has no metrics route, and the OpenAPI document lists none.
When absent, no metrics are served.
The address must be a concrete loopback or private address on a nonzero port.
`deployment.metricsListener.networkExposure` defaults to `private-address`; `container-private` also permits `0.0.0.0` or `::`.
It must not be the service listener's socket or one a wildcard service listener already covers; the configuration check refuses any other bind at `/deployment/metricsListener/bind`.
The key and its address rule are the ones Registry Messaging uses.

```yaml
deployment:
  metricsListener:
    bind: 127.0.0.1:9108
```

### Admit callers

Key `authentication.policies` by exact verified client identity.
Each policy declares the exact token subjects it admits, the required scopes, the actions, and, for run actions, the permitted `workflows`.
The policy keys are the admitted client set, and each verified client resolves one policy.
Coordinator reads scopes from `registry_scopes`; set `scopeClaim: scope` when the issuer uses the standard `scope` claim.
The shared `jwksSource` block selects its variant with `type`, for example `type: discovery`.

Name only confidential backend clients that your institution runs and trusts, never a browser app, mobile app, or other public client.
Whoever holds an admitted token chooses the records, subjects, and recipients a workflow acts on.

`subjects` is required and lists one to sixty-four exact `sub` values, each at most 512 bytes without control characters, compared exactly as the issuer writes them.
A producer policy lists the client's own service-account subject.
An operator policy lists the named people who operate the deployment.
A verified token from a listed client whose `sub` is not listed is refused with 403 `operation.not-authorized`, the same as a missing scope, and no run is created.
A token that carries an `act` claim is refused the same way whatever its subject, because the issuer made it for someone other than the client presenting it.
There is no `unrestricted` form.

To find a client's service-account subject, request a token with that client's own credentials (the client credentials grant, as the client will in production) and read the `sub` claim of the access token.
Or read the service-account user's identifier in your identity provider's administration console.
Many providers write a generated identifier such as a UUID rather than the client name; copy it exactly, including case.
Repeat this after you recreate the client or its service account, because the subject may change.

The run actions `start`, `status`, `inspect`, `retry-same`, `cancel`, and `reconcile` reach only the workflows the policy lists in `workflows`, which is required when the policy lists any of them.
The deployment-wide actions `doctor`, `restore-hold`, `release-restore-hold`, `release-admission-hold`, `complete-execution-recovery`, and `retain` act on every workflow at once, including workflows added later, and need `operator: true`.
They take no workflow list: a policy that lists only deployment-wide actions omits `workflows`, and the configuration check refuses one that sets it.
Keep producers and operators in separate policies, and do not give institutional producers operator authority.
A task-exchanged inbound token also requires the matching declared assertion issuer for that client, and like any other token it is admitted only when its `sub` is listed and it carries no `act`.

A run belongs to its starting token's exact verified `iss` and `sub`, never to an input field, and admission idempotency comes from the same pair.
The subject decides who owns the run, never which record the start input names.
Coordinator does not check that a record, subject, or recipient identifier in the input belongs to anyone, so the calling backend must already have authorised every identifier it passes for the person it acts for.

### Configure signed product events

Under each `eventSources.<alias>`, set the producer URI in `source` and put the delivery key for each URL under `triggers.<workflow>.<trigger>.hmacSha256KeyRef`.
Generate a separate key file for each trigger and give the same file to that trigger's sender.
Signed deliveries have the same form in both postures, so use separate deployment keys and never give production trigger keys to development producers.

{/* Evidence: crates/registry-coordinator/src/event_trigger.rs, verify_delivery. */}

```sh
(umask 077 && openssl rand -hex 32 | tr -d '\n' > key)
```

Coordinator reads these files at startup and refuses keys reused by any trigger or Casework completion connection.
To rotate a trigger key, keep its current reference fixed, put the new bytes behind it, and supply the old bytes via `previousHmacSha256KeyRef`.
Restart the receiver to load the new keys.

### Let Casework wake waiting runs

A run waiting on a Casework review reads the result every `resultCheckSeconds`, from 60 to 86,400 and 900 by default.
Each read is one request to Casework per waiting run.
A `completion` block on the Casework connection lets Casework wake the run sooner:

```yaml
connections:
  review:
    type: casework-review-producer
    producer: coordinator
    # baseUrl, profile, authorization as for any Casework connection
    completion:
      recipientBinding: coordinator-v1
      hmacSha256KeyRef: secret:file/review-completion-key
    resultCheckSeconds: 900
```

- **`producer`** is the producer's key under the Casework project's `trustedProducers`.
  That entry's `completion.destinationId` names a destination, and its `completion.recipientBinding` repeats the binding in the next block.
- **`recipientBinding`** is 1 to 256 visible ASCII characters, without spaces, and must differ between Casework connections; `check` refuses a duplicate.
- **`hmacSha256KeyRef`** names 32 to 64 exact key bytes. Generate a dedicated key file for this completion and give the same file to its Casework sender.

  ```sh
  (umask 077 && openssl rand -hex 32 | tr -d '\n' > /run/registry-coordinator/secrets/review-completion-key)
  ```

In the Casework project, the producer's `completion` block names a destination and the same recipient binding:

```yaml
trustedProducers:
  coordinator:
    profile: coordinator-producer
    issuer: https://issuer.example.org
    subject: coordinator-review-producer
    sourceNamespaces: [applications]
    reviewPolicies: [application-review]
    retention: {receiptRetentionDays: 7}
    completion:
      destinationId: coordinator
      recipientBinding: coordinator-v1
```

In the Casework runtime file, `reviewCompletionDestinations.<destinationId>` binds that destination to the Coordinator's route and to Casework's own reference to the same key file.

```yaml
reviewCompletionDestinations:
  coordinator:
    url: https://coordinator.example.org/v1/review-completions
    hmacSha256KeyRef: secret:file/review-completion-key
```

[Completion destinations](../casework-retention/#completion-destinations) describes those keys, including the delivery bounds `attemptTimeoutMilliseconds`, `maximumAttempts`, and `retryDelaySeconds`.
The [reviewed notice example](https://github.com/registrystack/registry-stack/tree/main/products/coordinator/examples) lists the full set of Casework prerequisites for one review producer.

Coordinator accepts Casework's completion events at `POST /v1/review-completions` on the service listener.
The `Registry-Recipient-Binding` header selects the connection. Its configured key verifies the Standard Webhooks signature over the webhook ID, Unix timestamp, and exact body.
An unknown binding or a refused signature answers HTTP 401 `authentication.refused`. The signed timestamp must be within 300 seconds in either direction.
The body limit is 2048 bytes. A larger body answers HTTP 413 `request.body-too-large`. An authenticated event must meet these requirements:

- use exactly `application/json`;
- name non-nil identifiers;
- repeat its `eventId` as the `webhook-id` header;
- carry a `completedAt` no older than 365 days and no more than 5 minutes ahead of the Coordinator's clock.

Anything else answers HTTP 400 `request.invalid` or 415 `request.unsupported-media-type`.
Every authentic event answers HTTP 204, whether or not a run waits on its request, and HTTP 503 `service.unavailable` asks Casework to deliver it again.
An event only brings forward the next result read of a run that waits; it never starts a run and never settles a result.
Without a `completion` block the route refuses every event, so lower `resultCheckSeconds` when events cannot reach Coordinator.

A live run's binding includes `producer` but neither `completion` nor `resultCheckSeconds`.
You can change either while runs wait. To rotate a completion key, keep the current reference fixed, write the new bytes behind it, and make the old bytes available using `previousHmacSha256KeyRef`. Restart both services to load the new keys.
Changing `producer` is a binding change that startup refuses while runs use it.

Check the file offline; it reads no credential and contacts no endpoint:


## Apply and start

Use the same declared posture for `plan`, `apply` and startup. The activation
ledger records that posture, and existing activation rows read as production.
Startup, `plan` and `apply` refuse a database activated under the other
posture. To change postures, apply to a fresh database.
`coordinatorctl deployment-status` reports a mismatch and returns the deployment status.

{/* Evidence: crates/registry-coordinator/src/deployment.rs plan, check_status, apply, check_deployment. */}

```sh
coordinatorctl --runtime-config /etc/registry-coordinator/runtime.yaml plan
coordinatorctl --runtime-config /etc/registry-coordinator/runtime.yaml apply
coordinatorctl --runtime-config /etc/registry-coordinator/runtime.yaml deployment-status
coordinator --runtime-config /etc/registry-coordinator/runtime.yaml
```

The service reads its runtime file from an absolute path; `coordinatorctl` also accepts a path relative to the current directory.

- `plan` reports, for each workflow, whether apply would `install`, `replace`, leave `unchanged`, or `remove` its package, with the configured and active package digests, the `workflowsDigest` of the listed set, and the observed activation and schema.
  It does not claim the deployment is valid.
- `apply` is the only command that reads the migration URL.
  It serialises activation with database locks, verifies each pinned package, migrates the dedicated schema, grants the runtime role, records the verified set of packages in the shared ledger, and records each workflow's active package in the control record.
- `deployment-status` uses only the runtime credential and never migrates, activates, or changes recovery holds.
- `coordinator` verifies the same things before it serves, and never migrates or activates.

`deployment-status` checks the pinned packages, the database identity, the supported migration ledger, the effective split runtime role, the narrow control grants, and the compatibility of retained live bindings.
The connected PostgreSQL `current_user`, the configured `runtimeRole`, and the activated runtime role must agree.
Its JSON output returns `status: checked`, `databaseId`, `workflowsDigest`, `workflows` (each workflow's package digest), `schemaVersion`, `runtimeRole`, the checked `active` activation, and `heldRuns`.
Refused checks exit nonzero with:

- `coordinator.deployment.refused` for deployment-contract refusals;
- `coordinator.command.live-binding-conflict` for incompatible retained bindings;
- the restore finding code for a pinned package this version does not restore, with operator recovery advice.

A refused package is named by its package digest and workflow.
This report does not replace the service's audit and recovery readiness checks.

Apply serialises activation, so a refused incompatible live binding is resolved by restoring the previous binding or finishing and reconciling the affected work.
Compatible definitions govern new admissions while old runs keep their encrypted snapshots and command identities.
Adding an unrelated logical connection does not change a workflow binding digest.
Reusing an idempotency key returns the original run rather than creating new work.

### Startup checks

Startup verifies package closure, the checksum pin, the executable ABI, the active package, the database identity, the schema, the effective runtime role, and the configured state and audit secrets before serving.
It checks retained live definitions under the admission lock before opening the normal listener.
Endpoint, client assertion audience, registered identity, scopes, and task authority must retain each live run's original binding.
New admissions repeat that check inside their insertion transaction, and worker polls keep their per-job fences without rescanning history every poll.

Startup refuses when a runtime file change alters a live run's endpoint, client assertion audience, identity, scopes, or task authority.
Restore the original binding, or investigate with `coordinator --runtime-config FILE --recovery-only`, which admits and dispatches nothing.
Recovery-only still verifies the active package, database, schema, role, and custody, and its readiness remains false.

The service requires protected state schema version 7.
An earlier layout is refused: `apply` reports `coordinator.command.schema-version`, and runtime state access, including `deployment-status`, fails closed as `coordinator.command.store-unavailable`.
Apply does not adopt or rewrite an earlier layout, and there is no in-place state migration.
Settle the retained work with its matching binary, then create a fresh namespace and database identity for this version, and keep the original keys, packages, and audit history until retention permits erasure.
The fresh namespace seeds each calendar cursor at the service's first check, so a calendar occurrence that falls due while Coordinator is drained for this reset is not run after it.

### Held runs

A live run whose retained definition this version does not restore does not stop startup, readiness, admissions, or apply.
The service holds that run alone: it writes the hold, with the restore finding code, to the durable audit before the run shows state `attention` with failure code `definition-refused`.
Nothing runs for a held run.
The worker never claims it, its deadline does not expire it, and `retry-same`, `reconcile`, and `cancel` answer 409 `run.definition-incompatible`, so no cleanup step runs for it either.
Its uncertain effects, prepared commands, spent keys, and restore-review marks stay as they are, and every other run continues.

Held runs appear in `attention=true`, the doctor report, and `deployment-status`.
`deployment-status` lists each live run whose retained definition this version does not restore, held or not yet held, as an entry of `heldRuns`.
Each entry carries `runId`, `workflow`, `workflowRevision`, `reason` (`definition-refused`), `findingCode` (the restore finding, such as `definition.review-request-not-run-owned`), and `advice`.
The report holds no run; the service holds them when it starts.

This version cannot end a held run: only a release that accepts its definition can.
A retained snapshot that cannot be opened, or a database that cannot be reached, still refuses the check and holds nothing.
A pinned package this version does not restore still stops the service in either mode, naming its package digest, workflow, and restore finding code.

### Calendar checks

The serving process checks each reviewed calendar trigger once a second, in a loop beside the worker.
PostgreSQL transaction time, not the process clock, decides which occurrence is due, and a trigger's first check seeds its cursor at that database time.
[Start runs on a calendar](../../configure/coordinator/#start-runs-on-a-calendar) describes the trigger an author writes.

- A sweep first deletes the cursors of triggers the served workflows no longer declare, so a trigger added back later is seeded afresh.
  When none is stale, the sweep reads without the admission lock and a hold does not refuse it.
  The delete itself takes the admission lock and is refused under a hold or a moved activation.
- Each check locks only its own cursor row and skips a row another replica holds, so replicas share the triggers without waiting on each other.
- A due check holds the cursor row and the ordinary admission lock, admits only the latest due occurrence, adds older due occurrences to the skipped count, and advances the cursor in the run admission transaction.
  An idle check performs no cursor update, so a backward database clock cannot rewind it.
- A new workflow revision keeps the cursor while the trigger's cron and timezone are unchanged, so an occurrence already due still runs under the new revision.
- Changing the cron or timezone moves the cursor to the database time of the first check under the new schedule and admits nothing on it.
  The occurrences of the previous schedule that were due and not run are added to the skipped count, logged as a warning with that count, and audited as `calendar-reschedule` with it.
- Each admission and reschedule writes its audit record first; without durable audit the check changes nothing.
- A changed activation, restore hold, or admission hold refuses a due check before it advances.
  A refusal is logged with its bounded code, and the loop then pauses for one second, doubling to 30 seconds.
  The ordinary worker keeps progressing runs already admitted.

Recovery-only mode performs no calendar checks.

### Logs, outages, and shutdown

The service writes JSON lines to standard error at the `info` level.
A worker poll that fails does not stop the service: it logs a warning with the failure code, pauses, and repeats the full deployment check before it polls again.
The pause starts at 1 second and doubles up to 30 seconds while failures continue.

When that check cannot open a database connection, the worker polls nothing, logs `store-unavailable` with the fix `restore database connectivity`, and waits out the outage.
Meanwhile `/ready` answers 503 and admissions answer 503 `service.unavailable`.
The periodic deployment check in recovery-only mode waits out an unreachable database the same way.
The service logs `worker loop resumed` once a poll succeeds again.
Any other refusal stops the service with exit status 1 and its code and fix on standard error: `deployment.refused` for an activation moved by an apply, and `state-key-custody` for key custody that no longer matches what apply registered.

SIGTERM or SIGINT stops the service gracefully.
The listener accepts no new connection and finishes the requests it is answering, and the worker leases no further attempt and finishes the one in flight.
Both get 15 seconds, the 10-second attempt timeout plus the 5-second lease finalisation allowance; the service then logs `stopped` and exits 0.
Give the supervisor a stop timeout of at least 15 seconds before it sends SIGKILL.

An attempt still unfinished when the 15 seconds end, or when the process is killed, keeps its lease until the lease expires.
A `read-again` call then resumes on the ordinary retry schedule within its original attempt and deadline bounds.
Any other step, including a mutation, evaluation, or same-command call, holds for operator review.
Both transitions retain the lease-lapse audit record, and a late completion from the old worker is fenced out.

### Check health and run doctor

Probe the private service listener, then ask the service for its own report with an operator token.
With `deployment.listener.bind` at `127.0.0.1:8108`:

```sh
curl -fsS http://127.0.0.1:8108/health
curl -fsS http://127.0.0.1:8108/ready
coordinatorctl doctor --url https://coordinator.example.org --token-file /run/operator-token
```

`/health` answers `{"live":true,"status":"ok"}` while the process answers.
`/ready` answers with `ready: true`, `status: ready`, `posture` and `developmentSettings`, or HTTP 503 with `{"ready":false}` while the service cannot accept work. Development responses carry `Registry-Posture: development`.
Every `/ready` probe checks mutable schema, activation, role, state-key custody, audit, and recovery holds; a held run does not make the service unready.
The retained live-binding scan is coalesced and cached for 30 seconds, including failures.
A cache miss still waits for that scan, so the cache bounds frequency rather than latency.
Startup, explicit deployment status, admissions, and worker transactions keep their fresh authoritative checks.
Keep health endpoints on the private service listener, and pass a token by file path, never by value.

The probe accepts the doctor's HTTP 401 credential challenge or HTTP 200 success response. Production answers omit `Registry-Posture`, and a production CLI refuses a development-marked answer. The probe uses the API route and needs no access to the health endpoints.
If the mutation's response declares development and you ran the command in production posture, inspect the run before repeating the command.

In the doctor report:

- `activationReady` and `state.auditReady` are `true` on a serving deployment, and a held run leaves `activationReady` `true`.

- `findings` holds at most one `platform.activation.posture-mismatch` entry, when the activation ledger records the other posture. `activationReady` is then `false`.
- `state.states` counts runs by state.
- `state.uncertain` counts steps whose effect waits for an operator.
- `state.restoreReviewRequired` counts runs that need restore review.
- `state.oldestDueAt` is the earliest next attempt of a pending step.

### Codes you see

Each surface names a refusal in its own vocabulary.
The service's standard error carries the raw code: `store-unavailable` while the database is unreachable, `deployment.refused` or `state-key-custody` when the service stops, and `live-binding-conflict` when startup finds a live run's binding changed.
`coordinatorctl` prefixes its codes with `coordinator.`, as in `coordinator.deployment.refused`, `coordinator.deployment.workflow-unlisted`, `coordinator.deployment.workflow-live-runs`, `coordinator.command.state-key-custody`, `coordinator.command.live-binding-conflict`, and `coordinator.command.development-peer`, which a typed command raises when it runs as production and the service answers as development.
Probe refusals point to `--url`. `coordinator.command.service-unavailable` means the probe failed to receive an answer or received an unexpected status. `coordinator.command.probe-posture-invalid` means the posture header was malformed or repeated.

HTTP answers carry RFC 9457 problem documents; the ones an operator acts on are:

| Code | Status | What to do |
| --- | --- | --- |
| `service.unavailable` | 503 | The database, audit stream, or token verifier is unavailable. Try again after it recovers. |
| `audit.response-unavailable` | 503 | The operation may have completed, but its audited result was not released. Inspect the run before repeating it. |
| `deployment.refused` | 409 | The activation, runtime file, or state key custody check failed. Run `deployment-status`. |
| `deployment.activation-changed` | 409 | An apply changed the active packages after the service started. Restart it with the runtime file apply used. |
| `binding.conflict`, `binding.live-conflict` | 409 | The runtime file changed connection settings a run uses. Restore them and restart, or investigate with `--recovery-only`. |
| `check.not-waiting` | 409 | Check now named a step that is not waiting for a result. Inspect the run and name a step it lists under `waits`. |
| `execution.held`, `admission.held` | 409 | The restore hold or the admission hold is in place. |
| `admission.recovery-only` | 409 | This instance runs with `--recovery-only` and admits no runs. Send starts to the ordinary service. |
| `restore.hold-required`, `restore.unresolved`, `restore.review-required`, `restore.lease-incompatible` | 409 | A restore step is out of order, or held work still needs review. |
| `reconcile.unsupported`, `reconcile.refused`, `reconcile.raced`, `retry.refused` | 409 | The held call cannot be reconciled or retried that way, or changed meanwhile. Inspect it again. |
| `receipt.expired` | 409 | The product no longer holds the original receipt. This is not evidence the command was never sent. |
| `run.payload-erased` | 409 | Retention erased the run's payloads; it can no longer be retried or reconciled. |

## Change the workflows

Each workflow's package is applied on its own.
One deployment is one trust domain, so workflows that must not share connections run in separate deployments.
To add a workflow, list its pinned package.
To upgrade or roll one back, change only that entry's `root` and `expectedDigest` to the new or previous package, then `plan`, `apply`, and restart every service.
Apply reports each workflow's change and leaves every other workflow's active package and runs untouched.
Runs in flight on a replaced workflow keep the definition they were admitted with, and new starts of that workflow use the replacement.
Any apply that changes the listed set fences services started under the previous set until they restart.

Dropping an entry never retires a workflow by itself.
`plan` and `apply` refuse an active workflow missing from the list with `coordinator.deployment.workflow-unlisted` until it is listed again or named explicitly:

```sh
coordinatorctl --runtime-config /etc/registry-coordinator/runtime.yaml plan --remove-workflow governed-action-follow-up
coordinatorctl --runtime-config /etc/registry-coordinator/runtime.yaml apply --remove-workflow governed-action-follow-up
```

Removal is refused with `coordinator.deployment.workflow-live-runs` while the workflow has a run that retention could not yet erase: running, waiting, uncertain, recoverable, or awaiting restore review.
Let those runs settle or cancel them first; removal, unlike replacement, leaves no definition to finish them under.
Naming a workflow that is still listed or not active is refused.
A removed workflow's terminal runs stay readable and inspectable, and starts naming it are refused.

## Watch metrics

Scrape the metrics listener from your monitoring:

```sh
curl -fsS http://127.0.0.1:9108/metrics
```

The metrics are Prometheus text (`text/plain; version=0.0.4`, served with `Cache-Control: no-store`), and every label is closed:

| Series | Type | Labels |
| --- | --- | --- |
| `coordinator_runs_admitted_total` | counter | none |
| `coordinator_runs_finished_total` | counter | `state`: `finished`, `failed`, `cancelled`, `cancelled-after-effect`, `expired` |
| `coordinator_step_attempts_total` | counter | `outcome`: `accepted`, `transient`, `permanent`, `maybe-sent`, `unavailable` |
| `coordinator_authentication_refusals_total` | counter | `reason`: `refused`, `policy`, `unavailable` |
| `coordinator_request_refusals_total` | counter | `check`: the closed set of 45 failed checks, every value published at zero |
| `coordinator_metrics_sample_failures_total` | counter | `sample`: `dispatch-queue`, `run-holds` |
| `coordinator_dispatch_jobs` | gauge | `state`: `pending`, `leased`, `unknown` |
| `coordinator_runs_attention` | gauge | `reason`: `definition-refused`, `other` |
| `coordinator_runs_restore_review_required` | gauge | none |
| `coordinator_hold_active` | gauge | `hold`: `restore`, `admissions` |
| `coordinator_oldest_due_age_seconds` | gauge | none |

Counters are per process: each service process starts them at zero and counts only its own work, so a restart resets them.
They expose every label value from the first scrape.

- A run counts as admitted once its admission commits; a repeated idempotency key returns the original run and counts nothing.
- A run counts as finished each time a committed change moves it into a terminal state, whether the worker, an operator action, or `complete-execution-recovery` made the change.
  A run that recovery, for example `reconcile`, moves from one terminal state to another therefore counts under both states, and the `state` series can add up to more than the number of runs that finished.
- Every step attempt the worker makes counts, local steps included.
  `maybe-sent` is an attempt whose effect is uncertain and that waits for an operator.
  `transient` also counts a `wait-for` read that failed and left its wait open.
  `unavailable` is an attempt that ended in an internal error, such as an unreadable store, before the step answered.
- An authentication refusal records a rejected caller credential or signed completion.
  `refused` covers a missing, malformed, or unverified token and a completion with a refused signature or recipient binding.
  `policy` is a verified token no caller policy admits, and `unavailable` means the token verifier cannot answer.
  A resolved caller refused an action is not counted here, but `coordinator_request_refusals_total` counts it.
- `coordinator_request_refusals_total` counts every refused request under the check that refused it, and no label carries caller text.
  It covers a refused credential, a policy denial after authentication, an event delivery refused under the key configured for its trigger URL, a refused completion callback, a key source the service cannot reach or use (the token verifier's keys), and a run the caller cannot see.
  Each refusal also writes one `request refused` log line with `failed_check`, at most five per check per minute.

`coordinator_dispatch_jobs` is read from the database on each scrape.
`pending` steps wait for their next attempt, `leased` steps are being attempted, and `unknown` steps wait for an operator to settle an uncertain effect.
The count is a read-only query. Every database read of one scrape shares one 5 second deadline, and the server cancels a query that outlasts the time left.
When the database cannot answer, that scrape has no `coordinator_dispatch_jobs` samples rather than zeros, `coordinator_metrics_sample_failures_total{sample="dispatch-queue"}` rises by one, and the service logs a warning with the failure class (`sqlstate-<code>`, `connection-closed`, `query`, `timeout`, `no-time-left` or `pool`), never the database's message.
Alert on the gauge going absent as well as on its value.

The held-work gauges are read from the database in one read-only query on each scrape, within the same 5 second deadline. A read that starts after a slower one has used the deadline fails with `no-time-left`.
They count every row.
Unlike the run list in `coordinatorctl doctor`, which shows at most 100 held runs, the gauges are never capped.
When the database cannot answer, that scrape has no samples for any of them, `coordinator_metrics_sample_failures_total{sample="run-holds"}` rises by one, and the service logs a warning with the failure class.

- `coordinator_runs_attention` counts runs in the `attention` state, the same state `doctor` reports under `states`.
  `definition-refused` runs are held because this version does not restore their retained definition, and `other` is every other run that waits for an operator.
  Runs that `doctor` lists as held but that are not yet in `attention` are not counted until the hold is applied.
- `coordinator_runs_restore_review_required` counts runs flagged for restore review, as `doctor` reports in `restoreReviewRequired`.
- `coordinator_hold_active` is 1 while the restore hold or the admissions hold is set, as `doctor` reports in `restoreHold` and `admissionsHold`.
- `coordinator_oldest_due_age_seconds` is how long ago the oldest pending step was due, counting only steps the worker can claim.
  Steps of runs held for a refused definition, flagged for restore review, with a cancellation requested, or with an erased payload are left out, because the worker never claims them.
  The gauge is 0 when no claimable step is overdue, so a steadily rising value means the worker is not keeping up or is not running.
  While the restore hold is set the worker claims nothing, and `coordinator_hold_active` reports that.
  Because it leaves out held runs, it can read lower than the `oldestDueAt` time that `doctor` reports.

No label carries a workflow, run, input, principal, or other caller text.
A workflow is configuration, so labelling by it would grow the series with every workflow added and keep series for workflows removed.
Per-workflow and per-run detail lives in the audit journal and in `coordinatorctl status` and `inspect`.
Log lines carry fixed messages and failure codes, never tokens, run inputs, step outputs, command bodies, or caller text.
Bind the metrics listener where only your monitoring can reach it: the counts describe the deployment's traffic even though they name no caller.

## Admit and inspect work

Acquire a current audience-bound access token from your institutional issuer.
Keep it in an owner-readable file, and pass its path, never its value, to the CLI.
Use a stable key file for one logical admission and retain it through recovery.
This example starts the delayed follow-up workflow with a synthetic input; `sendAfter` is an RFC 3339 time within the workflow deadline, and `applicationId` is an application UUID present in your approved registry:

```sh
umask 077
python3 -c 'import uuid; print(uuid.uuid4())' > ./idempotency-key
coordinatorctl workflow --workflow delayed-follow-up \
  --url https://coordinator.example.org --token-file /run/producer-token
cat > ./input.json <<'JSON'
{"applicationId":"00000000-0000-0000-0000-000000000001","sendAfter":"<RFC3339_TIME>"}
JSON
coordinatorctl start --workflow delayed-follow-up --workflow-revision <workflow-revision> --input ./input.json --key-file ./idempotency-key \
  --url https://coordinator.example.org --token-file /run/producer-token
coordinatorctl status --run RUN_UUID \
  --url https://coordinator.example.org --token-file /run/producer-token
coordinatorctl inspect --run RUN_UUID \
  --url https://coordinator.example.org --token-file /run/operator-token
```

`start` sends `workflow`, the expected `workflowRevision`, and `input` to `POST /v1/runs`, with the idempotency key as `Idempotency-Key`.
Use the discovered `workflowRevision` in the start command: a fresh admission must match the active revision.
A mismatch on new work returns `workflow.revision-mismatch`, and conflicting key reuse returns `idempotency.key-reused`.
If admission is unknown, resend the original identity, key, revision, and input, including after a package change.

A start is admitted under the named workflow's active definition, and retained runs keep their original definitions.
A caller whose policy does not list the workflow is refused with HTTP 403 `operation.not-authorized`.
An allowed workflow this deployment does not serve is refused with HTTP 404 `workflow.not-served`.

Use the authenticated HTTP API for application integration, through the maintained Coordinator client where one fits: the `registry-coordinator-client` Rust crate, or the `coordinator` namespace of the unified Node.js and Python clients from `v0.44.0`.

### List and inspect runs

`GET /v1/runs`, and `coordinatorctl list`, return at most 100 of the caller's most recently admitted runs, newest first by admission time and run ID, from the workflows its policy lists.
An operator policy lists every owner's runs in those workflows.
`limit` takes 1 to 100 and defaults to 20.
Pass `nextCursor` as `cursor` with the same filters to continue; each page rechecks current caller and workflow permissions.
Keep the run ID a start returns for direct lookup with `GET /v1/runs/{run}`.

Filters, which combine:

- `state` filters by effective state.
- `attention=true` selects effective states `attention` and `failed`, and `attention=false` excludes both.
- `proposal=<id>` finds the runs waiting on one BReg request.
- `turn=party`, `official`, or `nobody` selects runs whose request last read that turn.
- `outcome=<name>` selects the runs that finished with that workflow outcome, matched exactly; a name no run finished with returns an empty page.

```sh
coordinatorctl list --attention true \
  --url https://coordinator.example.org --token-file /run/operator-token
```

Status and list show authorised progress and the reviewed terminal projection.
Inspection shows bounded durable step state, and never returns original inputs, raw product responses, or prepared command payloads; protected command and correlation values stay absent.

- Inspection reports `effects` as `accepted` or `unknown`, with pinned operation revisions.
- It reports `waits` with completion revisions, deadlines, next observations, persistent floors, and count and limit.
- A Proposal wait also shows `lastObservation` (state, turn, submission version, any hand-off refusal code, when it was read, and since when that state held, as first seen by Coordinator) and its "Open the request" link.
  A hand-off refusal on a request a person submitted shows there while the run keeps waiting; that person resubmits in BReg.
- A run held with `in-force-ambiguous` names the two record identifiers and the date in the held step's `holdDetail` until the step is retried.
  Proposal and record identifiers are opaque and grant nothing without the owning product's grant.
- `recovery.operation` describes a compatible current call, with its pinned ID, version, product, effect, key and preparation requirements, recovery, and `readReceipt` capability.
  Inspection omits the field when no compatible current call is available, such as for pure steps, erased payloads, or incompatible snapshots.
  An unresolved original binding can still refuse inspection.
  BReg action invocation declares `same-command` recovery and `readReceipt: false`.
  `retryAllowed` and `reason` describe scheduling eligibility; neither the descriptor nor that eligibility proves current product authority or the existence of an original-key receipt.

Settled terminal history remains inspectable with its recorded binding identity after an old connection is retired.
This requires no runnable or uncertain job and no outstanding restore review; a failed label alone does not qualify.
Unresolved and recoverable work still requires its original configured connections.

The [Registry Coordinator overview](../../start/coordinator/#uncertain-calls-and-recovery) explains what the states mean.

## Read a waiting step now

A run that waits for a result can be read early with Check now.
It needs only the `inspect` grant and takes no reason.
It brings the next read forward, never closer than the read floor to the last one, and each read counts against the wait's read budget.
That budget is sized at the read floor, so an early read never stops a wait reaching its timeout route, and a wait that nothing settles still does.
A step that is not waiting answers 409 `check.not-waiting`.

```sh
coordinatorctl check-now --run <run-id> --step <waiting-step> \
```

## Recover a run

Coordinator retries a call by itself only after a definite retryable answer, one the receiving product reports it did not act on, and it resends the saved command and key.
An uncertain answer is never retried automatically; it waits for you.
Inspect first, then choose one, with a `--reason` that is an investigation reference holding no personal data:

- **`reconcile`** asks Messaging or Scheduling for authoritative evidence of the stored command, using its original key and owner.
  A missing or expired receipt, or an unavailable receiver, does not prove absence.
  A BReg Action, a Casework request, or an external command has no such receipt, so `reconcile` cannot settle it.
- **`retry-same`** resends the original body, key, binding, and authority, when the receiver's recovery contract and the original deadline allow it.
- **`cancel`** takes the workflow's `onCancel` path where one exists, and otherwise stops future calls.
  It prevents future dispatch where possible and never undoes an effect a product accepted, such as an appointment, governed action, or message.

Same-command recovery keeps the saved body, key, conditions, binding, and original approval deadline while it obtains fresh credentials.
Messaging submission and Scheduling appointment creation or hold confirmation offer original-key receipt reads.
Scheduling hold creation, rescheduling, and cancellation have no original-result receipt, and a later appointment read cannot prove which command produced the current state.
Scheduling hold release is unkeyed, so an ambiguous release stays held and Coordinator never replays it.
A possibly dispatched evaluation stays held and cannot be replayed.
Messaging acceptance is separate from delivery.

{/* Evidence: crates/registry-coordinator/src/operations.rs unkeyed_mutation, ReleaseHold;
    crates/registry-coordinator/tests/scheduling_adapter.rs unkeyed_hold_release_holds_an_ambiguous_dispatch_without_replay. */}

```sh
coordinatorctl reconcile --run <run-id> --reason incident-2026-10-12 \
  --url https://coordinator.example.org --token-file /run/operator-token
coordinatorctl retry-same --run <run-id> --reason incident-2026-10-12 \
  --url https://coordinator.example.org --token-file /run/operator-token
```

:::danger[A fresh idempotency key is a fresh operation]
Starting the same work under a new key can repeat its effects.
Settle an uncertain call with `reconcile` or `retry-same`, which keep its key, and infer nothing from an ordinary record read.
:::

### Automatic retry schedule

A call step makes at most ten attempts, waiting about 1, 2, 4, 8, 16, 32, 64, 128, and then 256 seconds between them.
Each wait falls between half and all of that delay, so the nine waits add up to between 255.5 and 511 seconds (about 4.3 to 8.5 minutes), plus up to 10 seconds for each attempt.
When the Messaging client or an external service reports a `Retry-After` in whole seconds, the next attempt waits at least that long, up to five minutes, so the waits never exceed 45 minutes in total.
The BReg and Scheduling clients report a rate limit without a wait, so those calls follow the schedule alone.

Every retry is bounded by the run deadline: a retry that would start at or after it is never scheduled, and the run ends `expired` with the call's failure code.
After the tenth attempt the run reports `failed` with that code and waits for the recovery that [Recover a run](#recover-a-run) describes.

{/* Evidence: crates/registry-coordinator/src/store.rs MAXIMUM_ATTEMPTS, RETRY_INITIAL_DELAY, RETRY_MAXIMUM_DELAY;
    crates/registry-coordinator/src/operations.rs MAXIMUM_ATTEMPTS, RETRY_MAXIMUM_DELAY_SECONDS. */}

### Worker lease lapse

A worker lease that lapses has a narrower recovery rule, based on the operation in the run's protected definition snapshot:

| Lapsed step | Result after the lease expires |
| --- | --- |
| A call whose recovery is `read-again` | The saved read becomes `pending` on the ordinary backoff and runs again without `retry-same`. If its attempt limit is spent or the retry cannot start before the original run deadline, it holds `unknown` instead of becoming dead-lettered or expired. |
| A mutation, evaluation, same-command call, wait, or local step | The job holds `unknown` and the run reports `attention`; inspect it before an operator recovery action. |

The transition is audited whether it reschedules or holds.
Dispatch increments the attempt and changes the lease token before a replacement read starts, so a late result from the old worker cannot commit over it.
This is not a new effect-retry rule: ambiguous mutations, evaluations, and frozen same-command effects remain held.

{/* Evidence: crates/registry-coordinator/tests/read_lease_recovery.rs;
    crates/registry-coordinator/src/store.rs ATTEMPT_TIMEOUT. */}

### External reads and commands

An `external.get/v1` reply with status 429, 502, 503, or 504 is a definite retryable answer on every attempt but the tenth.
429 retries as `external-rate-limited` and the others as `external-unavailable`.
The tenth attempt delivers that status to the workflow like any other, held to the connection's `responseSchema`, so the workflow sees a busy status only after the retries run out.
A run deadline that ends the retries first ends the run `expired` with the retry code instead.
The ten attempts span up to about nine minutes, and longer when the service sends `Retry-After`.

Before the final attempt, these external replies must carry at most one `Retry-After` field containing a whole-second value from zero through 86,400.
A date, duplicate field, malformed value, or longer wait stops the call with `external-unusable-retry-after`.
Zero still follows the normal backoff schedule.

An `external.command/v1` call has no read-only receipt, so `reconcile` reports `reconciliation-unavailable`.
`retry-same` resends the frozen body with its original `Idempotency-Key`; before retrying, confirm with the provider that it still deduplicates that key.

- Status 429 before the tenth attempt is a definite busy answer retried on the retry schedule; on the tenth attempt it ends the call with `external-rate-limited`.
- Status 503 before the tenth attempt is retried on the same schedule.
  Because it may follow an effect, the step stays uncertain until a later attempt settles it: a run deadline reached first holds the run with the effect unknown, and on the tenth attempt a 503 holds it as uncertain.
- When the longest wait the schedule allows after a 503, including its `Retry-After` and counted from the end of the attempt's lease, would reach the run deadline, the retry is not scheduled.
  The run holds at once with the effect unknown, and `retry-same` resends the same command while the deadline is still in the future.
  A 429 the deadline ends still ends the run `expired`.
- A command ignores a `Retry-After` it cannot use, such as a date, a duplicate field, a malformed value, or a wait over 86,400 seconds, and retries on the ordinary backoff instead.
- Any other server error, a redirect, a timeout, a lost acknowledgement, or a response the interpretation Function cannot settle holds the run as uncertain.
- After an uncertain attempt, including a retried 503, a declared refusal or 429 keeps the run held.
  Check the provider's record and cancel the run if no further step is wanted.

### BReg and Casework recovery

BReg action invocation has no read-only action receipt, so `reconcile` leaves an uncertain action unresolved.
Do not infer success or absence from an ordinary record read.
Same-command retry retains the saved client preparation, conditional ETags, and key, and checks current metadata and fresh authority before dispatch.
A changed contract, denied authority, or stale condition safely stops the call rather than refreshing its command.
Preparation does not mutate BReg; cancellation, restore holds, and the original workflow deadline still fence dispatch.
Task-bound operations retain their original approval deadline too.

Casework review requests have no read-only receipt either.
`reconcile` reports `reconciliation-unavailable` for an uncertain `casework.submit-review-request/v1` or `casework.cancel-review-request/v1`, and `retry-same` resends the saved request with its original key.
Casework answers a repeated key with its stored response while it keeps one; after that the step reports an expired receipt and the effect stays unresolved.

A Casework cancellation uses current producer authority, the original key, and the run deadline.
Route on its `outcome`, because `already-terminal` means a decision won the race.
Ordinary cancellation leaves downstream work for explicit owner-authorized withdrawal.

### Payment recovery

An uncertain `payments.request-collection/v1` recovers through the Adapter's read-only original-request lookup, with the saved bill identity, version, and key under the current connection authorisation.
An unresolved, expired, held, or unknown receipt never proves that a new collection may be requested.

An uncertain `payments.request-disbursement/v1` stays held.
`reconcile` may use the Adapter's read-only lookup for the exact original instruction and key, but `retry-same` is refused, and an unresolved lookup never proves absence or licenses a fresh submission.
The separate `payments.record-receipt/v1` and `payments.record-provider-confirmation/v1` reporting commands may use `retry-same` with their frozen body and key.
Investigate an unresolved original-request receipt with the Adapter operator before any same-command recovery or cancellation decision.

A run that ended without a settled payment, such as one whose wait timed out, is resumed by starting the same workflow again with the same bill or instruction identity and version.
The Adapter reattaches the new run to that version's existing attempt instead of creating a second one, and `payments.record-receipt/v1` returns a receipt already recorded for it.
A declined, cancelled or expired collection, or a failed disbursement, leaves the bill or instruction bound to its attempt, because the Adapter permits one attempt per version.
Issue a new bill or instruction version to try again.

### Waits

A `wait-for` observes a named completion, correlated to an earlier accepted call.
Casework exposes `result`, the BReg Proposal operations expose `proposal`, and an external GET can expose an authored bounded-poll completion.
These observations are read-only and spend no mutation attempt.

- Pending Casework and BReg reads default to 900 seconds, and both allow `resultCheckSeconds` from 60 to 86,400 seconds.
  An external completion declares `intervalSeconds`.
- The durable read floor is 30 seconds by default for Casework, BReg, and external poll reads.
  Top-level `minimumObservationIntervalSeconds` can raise it up to 86,400 seconds across the deployment.
- Each Casework or BReg wait's read budget is sized at that floor, so wake-ups and Check now never exhaust it before the timeout.
- Restart, event wake-up, retry, and timeout never bypass the floor.
  Retry hints postpone reads within the host ceiling of 86,400 seconds, and unusable hints hold the wait.
- Inspection exposes the floor, next read, count, and budget without protected correlation values.
  A completion event cannot settle a result.

Transient outages leave observations pending within the original deadline.
Invalid, refused, blocked, or mismatched evidence holds the wait for investigation; it cannot route as a negative business outcome.
`retry-same` retains the same completion identity, floor, and timeout, and an ended wait cannot be restarted.
A timeout can take `onTimeout`, or report `wait-timed-out`, and does not cancel work in the owning product.

An optional `onCancel` takes an authored forward cleanup path.
An active read records the intent and routes when the lease settles or expires, and repeating cancellation preserves cleanup.

Scheduling connections with `authorization.taskAuthority` require `observationAuthorization` with ordinary receipt-read scopes and no `taskAuthority`.
Configure the same token endpoint, registered client, and resource as the mutation authorisation.
Scheduling requires the verified issuer and subject to match the original receipt owner, and this read credential must work independently of the original grant's expiry or revocation.
Recovery never requests a Casework assertion or exchanges a task token, so unavailable read authority leaves the effect unresolved.
Observation credentials never authorise Coordinator dispatch.

### Failures that need a corrected workflow

Some failures need a corrected workflow, not a retry.

- `mapping-invalid`: a product call succeeded but the wait mapping after it is invalid.
  The run reports `failed` while retaining that call's successful output and delivered job.
  `retry-same` cannot repeat the accepted call, so inspect the existing effect before planning any new run with a corrected workflow version.
  Settled failure payloads follow the same explicit retention policy, while recoverable failed jobs and uncertain effects remain protected.
- `invalid-command`: a computed call input falls outside its operation input contract.
  The run fails before the call is prepared, saved, or sent.
  The run and step status report `failurePath`, the RFC 6901 path into the input, and never the value; an unexpected member is reported at the object that holds it.
  Correct the mapping in a new workflow version, or correct the data it reads, then start a new run.

Unresolved external effects remain uncertain until authoritative observation resolves them.
Restore the original downstream binding if configuration drift blocks recovery, and rotate key material under the same registered identity rather than changing the identity.

## Rotate and replace keys

Each key has its own procedure.
Run every command as the service user.

### Rotate the payload state key

Rotation adds a key version and makes it the one that writes.
Apply registers each version in the database, and the deployment keeps every registered version for its lifetime: runs written under an older version still read with it.

1. Create the key file for the next version:

   ```sh
   (umask 077 && openssl rand -out /run/registry-coordinator/secrets/state-key-2 32)
   ```

2. Add the version to `deployment.stateKeys`, keep every version already listed, and set `activeStateKey` to the new version:

   ```yaml
   deployment:
     activeStateKey: 2
     stateKeys:
       "1":
         keyRef: secret:file/state-key-1
       "2":
         keyRef: secret:file/state-key-2
   ```

3. Put the edited runtime file and the new key file in place for every service, then apply the deployment and check it:

   ```sh
   coordinatorctl --runtime-config /etc/registry-coordinator/runtime.yaml apply
   coordinatorctl --runtime-config /etc/registry-coordinator/runtime.yaml deployment-status
   ```

4. Restart every service with the edited runtime file as soon as apply succeeds.

Roll the edited runtime file out together with apply.
Until apply registers the new version, startup and `deployment-status` refuse the edited file with `state-key-custody` and the fix to run apply.
Once apply has registered it, every service still running with the previous file refuses with `state-key-custody` until it restarts with the edited file.
An ordinary service answers starts with 409 `deployment.refused` and `/ready` with 503, and its worker's next poll dispatches nothing and stops the service with exit status 1.
A recovery-only service stops the same way at its periodic deployment check, every 30 seconds.

Apply, `deployment-status`, and startup refuse with `state-key-custody` a runtime file that omits a registered version or names different key bytes for it, and name `deployment.stateKeys` as the fix.
Keep every registered key file under backup custody, because a restored database needs the versions its rows were written with.

### Rotate the audit key

The audit key derives the keyed references in the audit journal, such as `runRef`, `actorRef`, `stepRef`, and `reasonRef`.

1. Create the new key file:

   ```sh

   ```

2. Point `deployment.auditKeyRef` at it:

   ```yaml
   deployment:
     auditKeyRef: secret:file/audit-key-2
   ```

3. Check the runtime file, then restart every service with it, so all of them write under the same key:


### Replace a compromised admission key

The admission key stays the same for the deployment's lifetime: `apply` refuses a runtime file with a different admission key with `state-key-custody`.
When the key is exposed, close the deployment and admit new work in a fresh one.

1. Stop admissions.
   Remove `start` from each caller policy's `actions`, remove a policy left with no action, and restart the service.
   Starts are then refused with HTTP 403 `operation.not-authorized`, while status, inspection, and operator actions keep working.
   Do not use `restore-hold` for this step: it also stops dispatch, so runs in flight cannot finish.

2. Let runs finish, or cancel the ones you will not wait for.
   Doctor counts the runs still `running` in `state.states` and the steps waiting for an operator in `state.uncertain`, and `list` shows the newest runs of the operator's workflows, up to 100.
   Settle each uncertain step as described in [Recover a run](#recover-a-run) before you stop the service.

   ```sh
   coordinatorctl doctor --url https://coordinator.example.org --token-file /run/operator-token
   coordinatorctl list --limit 100 --url https://coordinator.example.org --token-file /run/operator-token
   coordinatorctl cancel --run RUN_UUID --reason incident-2026-10-11 \
     --url https://coordinator.example.org --token-file /run/operator-token
   ```

3. Stop the service.
   Keep its runtime file, namespace, keys, and audit journal for as long as you need its history: the old runs stay in the old namespace.

4. Create a new admission key file:

   ```sh
   (umask 077 && openssl rand -out /run/registry-coordinator/secrets/admission-key-2 32)
   ```

5. Write a runtime file for the new deployment with a new `namespace`, a new `deployment.databaseId`, and the new key, and restore `start` to the caller policies:

   ```yaml
   namespace: coordinator_follow_up_2
   deployment:
     databaseId: coordinator-institution-follow-up-2
     admissionKeyRef: secret:file/admission-key-2
   ```

6. Plan, apply, check, and start the new deployment:

   ```sh
   coordinatorctl --runtime-config /etc/registry-coordinator/runtime-2.yaml plan
   coordinatorctl --runtime-config /etc/registry-coordinator/runtime-2.yaml apply
   coordinatorctl --runtime-config /etc/registry-coordinator/runtime-2.yaml deployment-status
   coordinator --runtime-config /etc/registry-coordinator/runtime-2.yaml
   ```

The new deployment has no record of the idempotency keys the old one spent, so an idempotency key reused against it admits a new run.
Tell producers to send a fresh start only for work the old deployment did not admit.

## Back up and restore

Back up PostgreSQL, all still-needed state-key versions, the stable admission key, the audit key, the durable audit stream, and the exact immutable package of every listed workflow.
Preserve custody records and test their restore procedure.
Never restore only the database and manufacture replacement keys.
A backup can predate a downstream effect, and nothing holds a restored database by itself: you place the hold, from an instance that cannot execute.

:::danger[Never start an ordinary worker on a restored database]
An ordinary `coordinator` resumes dispatch at once and resends prepared commands to products whose state has moved on since the backup.
First stop or externally fence the old service and all workers, including replicas using the same database or credentials.
Start only `coordinator --recovery-only` until you release the restore hold.
:::

1. Restore the database together with every state key version, the admission key, the audit key and stream, and the exact packages.
2. Start a maintenance instance with `coordinator --runtime-config <file> --recovery-only`.
   It serves authenticated recovery operations, admits no runs, takes no events, and never dispatches.
3. Place the hold with `coordinatorctl restore-hold`.
   It holds execution and, separately, admissions.
4. Inspect each held run, and `reconcile` every command that may have been sent after the backup, using the receiving product's original-key receipt APIs.
   Receipt expiry limits what can be established: hold unresolved work and consult the authoritative product records, and never infer non-existence from a missing receipt.
5. When retained evidence establishes the history, attest it with `complete-execution-recovery`.
6. Record the fencing and reconciliation evidence, then `release-restore-hold`.
   Release is an accountable operator action and cannot itself prove another deployment has been fenced.
   It is refused with `restore.unresolved` while held work is unresolved.
7. Stop the recovery-only instance, start the ordinary `coordinator`, and `retry-same` or `cancel` what remains.
8. Reopen admissions with `release-admission-hold` only once every spent key is established.

Each `--reason` and `--recovery-reference` is the investigation reference, holding no personal data:

```sh
coordinatorctl restore-hold --reason <reference> \
  --url https://coordinator.example.org --token-file /run/operator-token
coordinatorctl complete-execution-recovery --recovery-reference <reference> \
  --execution-history-complete --prior-deployment-fenced \
  --url https://coordinator.example.org --token-file /run/operator-token
coordinatorctl release-restore-hold --reason <reference> \
  --url https://coordinator.example.org --token-file /run/operator-token
coordinatorctl release-admission-hold --recovery-reference <reference> \
  --admission-history-complete --prior-deployment-fenced \
  --url https://coordinator.example.org --token-file /run/operator-token
```

The attestation flags are audited operator statements, not automated proof.
Keep the supporting evidence under institutional custody; false or omitted attestations refuse release.

### Admission history

Restore hold also persists a separate admission hold, so releasing the worker recovery hold does not reopen ingress.
An older backup can omit entire admissions, so reconciling the runs it contains does not prove that replaying an omitted idempotency key is safe.
Keep admissions held until complete PITR/WAL recovery, or separately retained authoritative admission evidence, establishes the full spent-key history.
An incomplete backup must remain closed to new admissions.

Only after the execution hold is released, complete admission history is established, and the previous deployment is externally fenced may an explicitly authorised operator run `release-admission-hold --recovery-reference REFERENCE --admission-history-complete --prior-deployment-fenced`.
Preserve the original admission key and command identities, so a restored history gap does not become a fresh effect.

{/* Evidence: crates/registry-coordinator/src/store/recovery.rs admissions_hold;
    crates/registry-coordinator/src/cli.rs admission_history_complete. */}

### Execution recovery

Execution recovery also tracks every unfinished restored run, including rows whose commands had not yet been prepared at the backup point.
Those rows may have progressed externally after the backup.
Hold release refuses until each review mark is resolved by a final authoritative receipt with no later external call, or complete execution history and prior fencing are explicitly attested.
Do not cancel a restored run to erase its unresolved external-effect history.

When complete PITR/WAL or separately retained authoritative execution evidence establishes that history, an operator may run `complete-execution-recovery --recovery-reference REFERENCE --execution-history-complete --prior-deployment-fenced` while the execution hold remains.
This audited attestation clears execution review marks for resolved work.
In that same locked transaction it can settle safe expired reads and local steps into held failed work, after validating their original protected definition and any prepared command.

- A call that never prepared its command can also be held this way, only with complete recovered history, because command preparation always precedes sending.
- The same rules apply to safe work already held after a lease lapsed, with no uncertain effect or active lease.
- It preserves the original command and deadline, invalidates stale worker completions, and starts no work.
- Prepared mutating commands left pending after a definite retryable response are also held as failed work for an explicit `retry-same` or cancellation, with their original command, key, and deadline.
- A command-free hold keeps zero attempts; it never invents one.
- Pending calls that have not prepared a command, and pending waits or local steps, also become held failed work.
  Attestation and hold release never start these steps automatically.
- Prepared safe-read retries keep their ordinary pending behaviour.
- Explicitly retry a held wait to restore its original scheduled instant atomically; a future wait does not advance early.
- Active leases, prepared mutating leased or unknown calls, uncertain outcomes, and expired receipts remain protected.
  Recovery does not establish an external outcome for any of these calls.

A cancelled uncertain evaluation can be abandoned without blocking unrelated work forever.
Once its active lease has ended, complete execution recovery can clear its restore review after validating the protected definition and prepared request, and hold release checks those conditions again.
`cancelRequested: true` and `uncertain: true` remain visible, and the request, unknown outcome, and spent start identity remain retained, so the run can never resume or replay.
This exception applies only to evaluations with `hold-after-dispatch` recovery, and prepared evaluations restored before recorded dispatch intent also retain the conservative hold, because the abandonment exception requires recorded uncertainty.
Unknown product mutations still require their original recovery procedure.

After `release-restore-hold`, inspect safe settled work and use `retry-same` only when its original deadline permits it, or cancel and retain it when no further execution is appropriate.
Calls and waits retain their original deadline, and local `choose` and `finish` steps can complete under their existing semantics.
Releasing the execution hold does not reopen admission or remove its separate history requirement.
Repeat complete execution recovery in two cases:

- An active lease later lapses, and the history and fencing attestations still hold.
- A previously active attempt returns a definite retryable result after the first attestation.
  That prepared mutation remains review-required until it is held for the explicit retry or cancellation.

### Rehearse in disposable databases

Run the maintained older-backup rehearsal against two distinct, disposable local databases.
The rehearsal creates random Coordinator and Messaging namespaces, takes an actual PostgreSQL backup before command preparation, accepts one real Messaging submission, fences the previous worker, and restores the older Coordinator namespace.
The restored deployment must remain held and produce no second effect when the backup lacks the later execution and admission history.

Use `pg_dump` and `psql` from the same PostgreSQL major version as the test server.
Do not point either test variable at institutional data or the runtime database.

```sh
export COORDINATOR_TEST_DATABASE_URL='postgresql://<test-role>@127.0.0.1:5432/coordinator_restore_test'
export COORDINATOR_MESSAGING_TEST_DATABASE_URL='postgresql://<test-role>@127.0.0.1:5432/messaging_restore_test'
export COORDINATOR_PG_DUMP=/absolute/path/to/pg_dump
export COORDINATOR_PSQL=/absolute/path/to/psql
products/coordinator/scripts/test-restore.sh
```

A passing rehearsal proves this controlled older-backup boundary.
Your institution still needs its own backup custody, complete history recovery, and external fencing evidence before reopening a restored deployment.

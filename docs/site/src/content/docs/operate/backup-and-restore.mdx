Use this procedure for a single-node deployment created by
`registryctl deploy generate`. It preserves the verified package, operator files, and
the complete state that each product lane needs after container recreation or host
replacement.

Registryctl verifies the generated package. It does not create, schedule, coordinate,
encrypt, retain, or restore backups. Keep Registryctl out of backup automation. The
deployment operator owns those controls and the recovery decision.

This page is draft. It describes the package and fail-closed recovery boundaries
implemented by the 1.0 deployment runbook, but it is not evidence that a particular
backup platform captured a coherent recovery point.

## When to use this

Use this procedure before an update, host move, storage change, or recovery exercise for
the generated single-node Compose deployment.

Use the backup and restore procedure for your database, volume, snapshot, and secret
platform when it provides stronger consistency guarantees. Preserve the same recovery
groups and identity evidence described here.

## Prerequisites

- Locate the package root containing `binding.yaml`, `operator/`, and `generated/`.
- Retain the exact approved-set file used to generate the package outside the package.
- Record the generated closure SHA-256 outside the host being protected.
- Read the package-specific `generated/RUNBOOK.md` and
  `generated/operator-files.v1.json`.
- Identify the backing store for every volume and PostgreSQL service declared by the
  generated Compose model.
- Arrange an encrypted, access-controlled destination for package files, operator
  secrets, audit state, config-trust state, database backups, and recovery records.
- Arrange a traffic and source-update freeze to capture one coordinated recovery point.

## Recovery consistency groups

Do not treat individual files as independent restore units.

The `relay-public-state` group includes the exact package, approved set, public Relay
bundle and anchor, instance and stream identities, accepted sequence, anti-rollback
state, audit state, source inputs, ingest cache, and materialization state.

The `consultation-state` group includes the exact package, approved set, consultation
Relay and Notary bundles and anchors, instance and stream identities, accepted
sequences, anti-rollback and audit state, complete Relay consultation and Notary
PostgreSQL correctness state, role and key-lifecycle records, and retained key
material.

For audited SnapshotExact materializations, freeze source updates and dependent traffic
before stopping the Relay fence holder and Notary callers.
Capture source inputs, the Relay ingest cache, and the Relay
consultation database at one coordinated recovery point. The recovery record must bind
the database active pointer and history to the exact active generation and restricted
content digest.

If all services and source writers are stopped, sequential storage copies can describe
the same logical point. If any writer remains active, use a storage or database
snapshot mechanism that proves cross-store consistency.

## Verify and stop the package

Run package verification as a manual preflight, outside the backup job:

```sh
registryctl deploy verify \
  --package . \
  --approved-set ../approved-set.v1.json \
  --check-operator-files
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  config --no-interpolate --no-env-resolution --quiet
```

Compare the reported closure digest with the value in the external recovery record.
Stop dependent traffic and source updates, then stop the generated deployment:

```sh
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  down
```

Keep the traffic and source freeze in place until every member of each selected recovery
group has been captured.

## Capture the operator-owned backup

Archive the package without editing `generated/`:

```sh
backup_root="/secure-backups/registry-stack-recovery-id"
install -d -m 700 "$backup_root"
tar -cf "$backup_root/deployment-package.tar" \
  binding.yaml operator generated
cp -p ../approved-set.v1.json "$backup_root/approved-set.v1.json"
(
  cd "$backup_root"
  sha256sum deployment-package.tar approved-set.v1.json > package-files.sha256
)
chmod 600 "$backup_root/deployment-package.tar" \
  "$backup_root/approved-set.v1.json" \
  "$backup_root/package-files.sha256"
```

The archive contains operator secrets and certificates. Encrypt it at rest, restrict
access, and do not print or copy its contents into logs.

Use the operator-owned storage procedures to capture the state named by the generated
runbook and binding:

1. Snapshot the complete `relay-public-state` group when that lane is in scope.
2. Snapshot the complete `consultation-state` group when consultation Relay or Notary is
   in scope. Back up complete product databases, not selected tables or schemas.
3. Preserve PostgreSQL role object identifiers when the product state contract binds
   them. A physical or managed cluster snapshot is required when a logical restore
   cannot preserve that identity.
4. Hash each backup artifact without logging its contents.
5. Sign or independently attest one closed recovery record that binds the artifacts to
   the package closure, approved-set digest, product release, PostgreSQL major, lane,
   instance, stream, accepted sequence, and shared recovery point.

A list of unrelated artifact hashes is not evidence that the stores belong to one
generation.

Do not restart services until all selected recovery groups are complete. Then use the
ordinary start sequence in `generated/RUNBOOK.md`.

## Restore a recovery point

Restore into an empty, isolated directory and isolated backing stores. Keep public,
consultation, and Notary traffic blocked.

1. Verify the backup system's integrity record before extracting any files.
2. Extract `deployment-package.tar` and restore the approved set outside the package.
3. Restore every member of each selected recovery group from the same recovery record.
4. Restore exact instance, stream, role, key, bundle, anchor, audit, and anti-rollback
   identities. Do not edit or regenerate them to make startup pass.
5. Restore operator-file permissions and ownership recorded by the backup.
6. Keep the initialization Compose file and every initialization service unused. They
   are only for a new identity and an empty first installation.

Verify the archived files before extraction:

```sh
backup_root="/secure-backups/registry-stack-recovery-id"
(
  cd "$backup_root"
  sha256sum -c package-files.sha256
)
```

Verify the restored package before contacting product state:

```sh
registryctl deploy verify \
  --package . \
  --approved-set ../approved-set.v1.json \
  --check-operator-files
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  config --no-interpolate --no-env-resolution --quiet
```

Compare the reported closure digest with the external recovery record. Any mismatch is
a manual abort.

Stage operator secrets, then run all three read-only state checks required by the
generated runbook:

```sh
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  run --rm --no-deps registry-runtime-stage-secrets
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  run --rm --no-deps registry-relay-public \
  'product-action' 'relay-public' 'verify_state'
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  run --rm --no-deps registry-relay-consultation \
  'product-action' 'relay-consultation' 'verify_state'
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  run --rm --no-deps registry-notary \
  'product-action' 'verify_state'
```

If any check rejects the restored state, do not delete anti-rollback state, change an
accepted sequence, drop a schema, or rerun initialization. Restore a coherent group at
the same or newer accepted sequence. If no such backup exists, provision a new instance
identity, review and sign every affected lane, generate a new package, and follow the
first-installation section of its runbook.

Start only after all checks succeed:

```sh
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  up --detach --wait --wait-timeout 120
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  ps
```

For a private-lane recovery, keep externally reachable dependants stopped until
PostgreSQL and consultation Relay are ready and verified. Then start Notary and the
remaining dependants in the order specified by `generated/RUNBOOK.md`.

## Verify the restored service

- Confirm `docker compose ... ps` reports the expected services as healthy.
- Exercise one authenticated canary for every restored public and consultation path.
- Exercise each recovered SnapshotExact materialization. Global readiness can remain
  successful while one execution rejects a stale materialization.
- Reconcile the recovery record with the last acknowledged consultation, credential,
  status, and external audit watermark before admitting traffic.
- Confirm new audit records extend the retained chain without exposing record values.

Package verification proves the generated closure and operator-file boundary. It does
not prove that the backup captured one recovery point, that a database contains the
latest acknowledged write, or that a canary covered every product path. Readiness also
does not prove restore freshness.

## Troubleshooting

| Symptom | Required response |
|---|---|
| Package verification reports a digest or ownership mismatch | Keep traffic blocked and restore the exact package and approved set named by the recovery record |
| An operator file is absent or has the wrong mode or owner | Restore it from the encrypted package archive; do not invent a replacement |
| `verify_state` rejects an older sequence | Keep the lane offline and restore a coherent same-or-newer recovery group; never delete or reinitialize anti-rollback state |
| Relay is healthy but a SnapshotExact canary fails | Restore source, cache, database publication state, and digest from one group, or publish a newly reviewed generation |
| The database role identity differs after restore | Restore a snapshot that preserves the role catalog or replace the affected instance identity |
| The recovery point may omit acknowledged writes | Keep traffic blocked and recover forward to the last acknowledged write and external audit watermark |

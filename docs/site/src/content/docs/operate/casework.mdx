If you operate Registry Casework, deploy a reviewed policy package against PostgreSQL, verify its activation, then establish the teams that can see and decide its review tasks. Keep the producer's subject mutation separate: Casework returns a review result and has no source write or apply authority.

{/* Evidence: products/casework/README.md; crates/registry-casework-core/src/adapter.rs, ReviewContextProvider. */}

## What you provide

- PostgreSQL 17 or newer, with TLS and separate migration and runtime credentials.
- An OpenID Connect issuer, the intended audience, and an explicit list of admitted clients.
- A private HTTP listener behind an operator-controlled TLS proxy.
- A reviewed package, the matching binaries, and secret references the process can resolve.
- A durable audit destination and an archive you operate.
- A Directory team serving each queue reviewers need to work.

Submitted-context policies need no source service. Current-source policies also need configured read-only context providers. Request, task, decision, replay, and Directory state live in PostgreSQL; a separate broker or cache is not required. The audit journal lives outside the database.

## Install the runtime

Install the matching `casework` and `caseworkctl` binaries on the serving and operator hosts:

```sh
curl -fsSL https://github.com/registrystack/registry-stack/releases/latest/download/casework-install.sh | bash
casework --version
caseworkctl --version
```

Read the installer before running it on a host you operate. It checks downloaded files against the release `SHA256SUMS`; that checksum check does not establish release authenticity. Use the release verification procedure for the version you install.

The container image carries both binaries. Its default entrypoint serves Casework; run operator commands with the entrypoint set to `/usr/local/bin/caseworkctl`. Pin the release manifest's image digest. Mount the package, runtime file, and secret root read-only, and provide durable writable storage for the audit directory.

## Provision PostgreSQL

Use a new database for the current review contract. As your PostgreSQL administrator, create a schema-owning migration role and a separate runtime role:

```sql
CREATE ROLE casework_migration LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE
  NOINHERIT NOBYPASSRLS PASSWORD '<migration-password>';
CREATE ROLE casework_runtime LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE
  NOINHERIT NOBYPASSRLS PASSWORD '<runtime-password>';
CREATE DATABASE casework;
```

In that database, grant connection access and give the migration role ownership of the schema:

```sql
REVOKE ALL ON DATABASE casework FROM PUBLIC;
GRANT CONNECT ON DATABASE casework TO casework_migration, casework_runtime;
ALTER SCHEMA public OWNER TO casework_migration;
REVOKE ALL ON SCHEMA public FROM PUBLIC;
```

Keep the migration credential off the serving host where your deployment permits it. Only `caseworkctl apply` resolves that credential. Runtime requests, maintenance, `plan`, `status`, and `doctor` use the runtime credential. Apply issues runtime table/function privileges and keeps the activation and migration ledgers read-only to a correctly separated runtime role. Casework creates no role or extension itself.

If apply reports `casework.activation.role-mode-weakened`, follow its named ownership, schema, or trigger correction, then plan again. Do not give the runtime role ledger writes to bypass a refusal. When both credentials name one role, the deployment records single-role mode and reports that the runtime credential can activate packages.

## Write the runtime file

Keep the deployment file outside the authored policy. This submitted-context example uses mounted secrets and an operator-controlled TLS edge:

```yaml
apiVersion: id.registrystack.org/formats/casework/runtime/v1alpha1
kind: CaseworkRuntimeConfig
identity:
  databaseId: casework-decisions
package:
  root: /srv/registry-casework/package
listener:
  bind: 10.42.0.7:8100
  tlsTermination: operator-controlled-upstream
  networkExposure: private-address
secretProviders:
  file:
    root: /run/secrets/registry-casework
database:
  runtimeUrlRef: secret:file/runtime-database-url
  migrationUrlRef: secret:file/migration-database-url
authentication:
  oidc:
    issuer: https://identity.example.test/realms/registry
    audience: urn:example:casework
    allowedClients: [casework-console, review-producer]
    scopeClaim: scope
    humanIdentity:
      claim: registry_actor_kind
      value: human
audit:
  path: /var/lib/registry-casework/audit/casework.ndjson
  hashKeyRef: secret:file/casework-audit-key
```

Use absolute resource paths and a selected runtime file that does not pass through a symlink. The file is closed: unknown keys, explicit null values, and malformed references are refused at their source positions. Omit optional members to take their defaults. `identity.databaseId` is your stable logical deployment identity; it must match the activated ledger after a restore or restart.

`package.root` must contain a package produced by `caseworkctl package`, including its verified `SHA256SUMS`. To pin the exact reviewed package, add `package.expectedDigest` with the `packageDigest` that packaging reported. Do not substitute the behavioral policy binding for the package digest.

Have your secret provisioning system mount the database URLs and audit key as owner-only files directly under the declared root. File secrets must belong to the runtime user, have mode `0400` or `0600`, and have no symlink or additional hard link. Keep the audit directory owner-controlled and ship its journal to your archive. [Review retention and audit](../casework-retention/#keep-the-audit-file) covers the key, file rotation, and failure behavior.

### Add a current-source provider

A current-source policy names a provider and exact `{id, revision, schemaDigest}` context contract. Bind its authored `deploymentRef` to a read-only provider in the runtime file:

```yaml
contextProviders:
  facility-registry:
    baseUrl: https://registry.example.test
    statusProfile: casework-review-status
    tokenEndpoint: https://identity.example.test/oauth2/token
    clientAssertionAudience: https://identity.example.test
    resource: urn:breg:facility-registry
    scopes: [registry:proposal:review-status]
    clientIdRef: secret:file/breg-status-client-id
    clientAssertionKeyRef: secret:file/breg-status-client-key
```

This Base Registry Engine (BReg) status reader checks reviewability only. Its `statusProfile` must match the authored service-status profile. Human display uses the caller's current bearer and chosen `Registry-Source-Profile`; source authorization and disclosure still apply. A missing provider binding makes its current-source operations unavailable while submitted reviews can continue. A contract change requires a matching export, schema pin, and reviewed Casework package.

Configure only the capabilities your policies use. Separate routing or task-grant context from human display, and retain the exact purpose/profile bindings their policies require. A Casework approval does not apply a BReg Proposal; that later operation uses BReg's own principal and authority checks.

### Check the runtime file offline

Before contacting a database, check the authored project with the operator file:

```sh
caseworkctl check ./decisions --runtime-config /etc/registry-casework/runtime.yaml
```

This checks configuration without opening the package, database, issuer, provider, or secrets. Add `--environment` when you intend the check to resolve runtime environment expressions. Correct every named field before planning activation; a successful offline check does not establish live readiness.

## Verify the package before it opens the listener

Install the reviewed package in its own directory, retain the reported package digest in your change record, and set `package.root` to that directory. Never edit packaged files in place: both activation and startup verify the manifest's exact file closure and digests. An authored directory without `SHA256SUMS` is refused.

Keep previous package directories available for recovery, but plan every activation, including a rollback. A previous package is not automatically safe for reviews accepted under a successor.

## Refuse a package that strands pinned work

Accepted requests retain their compiled policy closure. A candidate that removes a still-needed policy, producer, profile, team, provider purpose, context contract, or clock destination is refused. Changing behavior under the same policy version is also refused. Let affected reviews finish under the active package, or prepare a successor that preserves their required dependencies. There is no orphan override.

Presentation changes can preserve the policy binding while changing package bytes. Inspect both the behavioral closure and the package digest; do not treat one as a substitute for the other.

## Plan, apply, and serve

From the operator host, inspect the candidate, apply it with the migration credential, and read the resulting activation:

```sh
caseworkctl plan --runtime-config /etc/registry-casework/runtime.yaml
caseworkctl apply --runtime-config /etc/registry-casework/runtime.yaml \
  --operator-reference CHANGE-1234 --backup-reference nightly-before-activation
caseworkctl status --runtime-config /etc/registry-casework/runtime.yaml
```

`plan` reads the database and writes nothing. Inspect its package digest, logical database identity, pending schema changes, role mode, and refusals. An already-active plan exits successfully with no pending change; applying that unchanged package is a domain refusal. A rotated runtime role that cannot read the ledger receives `casework.activation.ledger-unreadable`; use apply with the migration credential to restore its grants, then plan again.

Apply admits the operation through audit before mutation, takes the activation lock, installs pending schema changes, checks retained review dependencies, issues the runtime grants, and records the activation. `--operator-reference` is stored as a keyed hash; `--backup-reference` records your backup reference as text, so use a snapshot identifier without personal data.

If apply returns `casework.activation.applied-unaudited`, the database commit succeeded but its audit response was refused. Restore audit, inspect `status`, and record the recovery; do not assume the package was left inactive. Other refusals name the field or dependency to correct. JSON reports carry diagnostics and suggested actions; exits are `0` for success, `1` for a domain refusal, `2` for usage, and `3` for an operational failure.

After activation, serve as the runtime user:

```sh
casework --runtime-config /etc/registry-casework/runtime.yaml serve
curl --fail http://10.42.0.7:8100/ready
```

Use the listener address reachable from your check host. `/health` reports process health. `/ready` checks the database and audit writer; it does not prove that a human can read current source context or that every queue has a serving team. Verify those with the intended identities before opening your application to reviewers.

### Earlier database and audit state

The current review-only contract refuses retired Casework schemas rather than converting or deleting their data. Keep the previous database with the release that wrote it and provision a fresh database for the current contract. A database newer than the binary also refuses activation. Do not delete ledger rows or run migration SQL by hand to get past either refusal.

A database restore returns review state to its backup point. It cannot reconstruct later requests or decisions from a source, and the external audit journal must not be rewound. Follow [Casework restore and reconciliation](../advanced/back-up-and-restore/#restore-registry-casework) before resuming reviewers.

### Scrape metrics and the running version

Use an optional private telemetry listener, separate from the API:

```yaml
metricsListener:
  bind: 127.0.0.1:9100
```

It serves `/metrics` and `/version`; neither is exposed on the API listener. Keep that listener outside public proxy routes. Metrics report database availability and counts of open review requests, open review tasks, and due tasks. They contain no subject identifiers or context fields. `/version` reports the binary version and package digest for rollout checks.

## Establish directory authority

Use an Administrator token carrying the configured human assertion to bootstrap the first team through `/v1/directory/bootstrap`. Supply issuer-qualified staff and supervisor identities, the team identifier, and a served queue. Select `Registry-Casework-Profile`, send the current Directory revision in `If-Match` (`"0"` for the first bootstrap), and use an `Idempotency-Key`.

Read the resulting Directory revision before replacing a team with `PUT /v1/directory/teams/{team_id}`. A replacement supplies the whole staff, supervisor, and served-queue set. A queue already served by another team is refused; remove its prior service deliberately before moving it. Directory membership and queue service remain live authority for old and new tasks.

Use the authenticated review-task list, next task, holdings, and supervisory views to confirm the intended staff can work their queues. A caseload move and clock recompute each use a bounded preview followed by apply; when task or Directory state changed, create a fresh preview instead of replaying stale authority. A task reference or cursor grants no access.

### Check readiness with doctor

Run the operator preflight as the runtime user:

```sh
caseworkctl doctor --runtime-config /etc/registry-casework/runtime.yaml
```

Doctor checks configuration, the package, database activation constraints, and audit-path writability. It accepts an unchanged already-active package. It does not open a listener, prove live issuer/provider access, or bootstrap the Directory. Use `/ready` on the running process and authenticated task reads for those distinct checks.

If doctor refuses, correct the named input, grants, package, or audit path, then rerun it. For an audit failure during service, the change may already be committed when the response fails. Retry the original mutation with its original body and idempotency key, or inspect its result before choosing another operation.

## Change the active package

Install the successor beside the active directory. Point the operator file to it, plan, apply, then
restart or roll out the matching runtime. A process verifies its package at startup and retains that
policy in memory. Coordinate exact producer pins with the deployed policy. ID-only selectors resolve
at admission; accepted rounds retain their concrete bindings, and recovery uses the original body
and key through the rollout.

Current-source contract changes need matching producer exports and Casework schemas. Transport credential rotation belongs to the runtime bindings and secret store. Existing review clock calculations retain their pinned definitions; holiday recompute is a separate preview/apply operation.

## Troubleshooting

| Symptom | Recovery |
| --- | --- |
| `review.policy-mismatch` on admission | Reconcile the producer's exact pin with the deployed policy before a fresh submission. Preserve the original body and key for recovery. |
| Current-source task is concealed or unavailable | Check the human's source profile, exact context binding, and required provider purpose. Never substitute the status credential for human display. |
| `source.bad-gateway` on a display read | Correct the provider/schema mismatch. The warning identifies the policy and validation reason without source values. |
| `review.query-too-broad` | Narrow the queue, exact subject, or visible reference filter; do not treat a partial walk as the full inbox. |
| `precondition.failed` on a mutation or preview apply | Refresh the task or Directory state and obtain a new preview where required. |
| `service.unavailable` and `/ready` returns `503` | Check the database and audit writer. For a failed file writer, repair its path/space/permissions and restart; inspect whether the original operation committed. |
| `casework.activation.retired-schema` or schema-newer refusal | Preserve the database and use a supported release/database pairing. Never alter the migration ledger to bypass the refusal. |

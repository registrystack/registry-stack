If you operate Registry Casework, this page takes the project from
[Decide your first ReviewRequest](../../tutorials/first-casework/) through the steps a deployment
repeats: check a runtime configuration, package the project, activate the package, and read its
state. You continue in that project, with its development session stopped and retained.

## What you need

A deployment needs PostgreSQL, the [`casework`](/reference/cli/casework/serve/) binary, and one
runtime configuration file: the YAML file that tells the runtime where its package, database,
secrets, token issuer and audit journal are. [`caseworkctl`](/reference/cli/caseworkctl/) checks,
packages and activates against that same file.

## Restart the session

```sh
caseworkctl dev start tutorial-work/casework
```

```json test-excerpt
{"directory": {"revision": 1, "teams": 1}, "state": "ready"}
```

A retained session restarts on the ports it was first given, with its database intact.

{/* Evidence: crates/registry-caseworkctl/src/dev/mod.rs, start and stop. */}

## Read the runtime configuration

The session wrote a runtime configuration for its own runtime:

```sh
cat tutorial-work/casework/.casework/dev/operator.yaml
cfg="$PWD/tutorial-work/casework/.casework/dev/operator.yaml"
```

```text test-excerpt
database:
  migrationUrlRef: secret:file/migration-database-url
  runtimeUrlRef: secret:file/runtime-database-url
  trustedRootCertificateRef: secret:file/database-root.pem
identity:
  databaseId: casework-local-session
kind: CaseworkRuntimeConfig
listener:
  bind: <address>
  networkExposure: private-address
  tlsTermination: development-loopback
package:
  root: <path>
secretProviders:
  file:
    root: <path>
```

Every `caseworkctl` command that reads a runtime configuration takes it as an absolute path, so
`cfg` holds one.

## Write the runtime file

A deployment writes its own file. This is
`products/casework/examples/canonical-review/runtime.example.yaml`:

```yaml
apiVersion: id.registrystack.org/formats/casework/runtime/v1alpha1
kind: CaseworkRuntimeConfig
identity:
  databaseId: casework-canonical-review
package:
  root: /srv/registry-casework/package
listener:
  bind: 127.0.0.1:8100
  tlsTermination: development-loopback
  networkExposure: private-address
secretProviders:
  file:
    root: /run/secrets/registry-casework
database:
  runtimeUrlRef: secret:file/runtime-database-url
  migrationUrlRef: secret:file/migration-database-url
authentication:
  oidc:
    issuer: https://identity.example.test/realms/registry
    audience: urn:example:casework
    allowedClients: unrestricted
    scopeClaim: scope
    humanIdentity:
      claim: registry_actor_kind
      value: human
audit:
  path: /var/lib/registry-casework/audit.ndjson
  hashKeyRef: secret:file/casework-audit-key
contextProviders:
  facility-registry:
    baseUrl: https://registry.example.test
    statusProfile: casework-review-status
    tokenEndpoint: https://identity.example.test/oauth2/token
    clientAssertionAudience: https://identity.example.test
    resource: urn:breg:facility-registry
    scopes: [registry:proposal:review-status]
    clientIdRef: secret:file/breg-status-client-id
    clientAssertionKeyRef: secret:file/breg-status-client-key
```

Every `...Ref` key names a secret, never its value: `secret:file/<name>` resolves under
`secretProviders.file.root`, and `secret:env/<NAME>` only when `secretProviders.environment` is
declared. `tlsTermination: development-loopback` allows plaintext on loopback only; a production
listener sets `operator-controlled-upstream` and sits behind the TLS proxy you run.

{/* Evidence: products/casework/examples/canonical-review/runtime.example.yaml;
    products/casework/generated/runtime/runtime.schema.json, SecretReference and TlsTermination. */}

## Check the project against it

```sh
caseworkctl check tutorial-work/casework --runtime-config "$cfg"
```

```json test-excerpt
{"databaseAccess": false, "filesChecked": 3, "networkAccess": false}
```

The check reads the project and the runtime configuration together, without touching the
database or the network.

{/* Evidence: crates/registry-caseworkctl/src/project.rs, check() and check_runtime_config(). */}

## Package the project

```sh
caseworkctl package tutorial-work/casework --output tutorial-work/package
cat tutorial-work/package/SHA256SUMS
```

```text test-excerpt
<digest>  casework.yaml
```

The [policy package](../../reference/glossary/#policy-package) is the directory a runtime's
`package.root` names. Its [package digest](../../reference/glossary/#package-digest) covers
`SHA256SUMS`, and `secretsIncluded: false` in the report confirms it holds no secret.

{/* Evidence: crates/registry-caseworkctl/src/project.rs, package();
    crates/registry-casework/src/config.rs, RuntimePackageConfig. */}

## Plan, apply, and serve

The database records each activation: which package it runs and which one came before. The
session already applied its package, so applying it again is refused:

```sh test-exit="1"
caseworkctl apply --runtime-config "$cfg"
```

```text test-expect
error[casework.activation.already-active] runtime.yaml:/package
  package sha256:<digest> is already the active package in this database; nothing needs applying
  next: The package is already active. Check caseworkctl status before choosing a different package.
1 error, 0 warnings
```

Change the project, package it again, and point a copy of the configuration at the new package:

```diff test-edit title="tutorial-work/casework/casework.yaml"
   decisions:
-    label: Decisions awaiting review
+    label: Decisions awaiting a reviewer
```

```sh
caseworkctl package tutorial-work/casework --output tutorial-work/package-next
sed "s#^  root: .*/\.casework/dev/package\$#  root: $PWD/tutorial-work/package-next#" \
  "$cfg" > tutorial-work/successor.yaml
next="$PWD/tutorial-work/successor.yaml"
caseworkctl plan --runtime-config "$next"
```

```json test-excerpt
{"changesPending": true, "planKind": "successor", "refusals": []}
```

The plan is read-only. It refuses a successor that would strand pinned work. Apply it under a
reference your change record keeps:

```sh
caseworkctl apply --runtime-config "$next" --operator-reference tutorial-change-1
```

```json test-excerpt
{"applyOrder": 2, "planKind": "successor", "predecessorPackageDigest": "sha256:<digest>"}
```

A running runtime keeps the package it started with, and startup refuses a database whose active
package is not the configured one. Restart the runtime with the successor file:
`casework --runtime-config <absolute path> serve`.

{/* Evidence: crates/registry-casework/src/activation.rs, plan_activation() and apply_activation();
    crates/registry-caseworkctl/src/project.rs, plan() and apply();

## Read the activation history

```sh
caseworkctl status --runtime-config "$next"
```

```json test-excerpt
{"singleRoleStatement": "single-role mode: the ledger check catches a wrong package, but not someone holding this credential"}
```

`history` lists both activations. Single-role mode means the runtime's database role can write
the activation ledger; give the runtime a role of its own in production.

{/* Evidence: crates/registry-caseworkctl/src/project.rs, status();
    crates/registry-casework/src/activation.rs, grant_runtime_role() and observe_role(). */}

## Check readiness

```sh
casework_url=http://127.0.0.1:8182
curl --silent --output /dev/null --write-out 'HTTP %{http_code}\n' "$casework_url/ready"
curl --silent --output /dev/null --write-out 'HTTP %{http_code}\n' "$casework_url/metrics"
curl --silent --output /dev/null --write-out 'HTTP %{http_code}\n' "$casework_url/version"
```

```text test-expect
HTTP 200
HTTP 404
HTTP 404
```

`/ready` answers `200` once the database and audit writer are ready. Counters and the active
package digest are served only on an operator-private listener, which `metricsListener.bind` in the
[runtime configuration](../casework/#casework-runtime-configuration) opens and the session does not
set.

{/* Evidence: crates/registry-casework/src/http.rs, router(), health() and ready();
    crates/registry-casework/src/metrics.rs, metrics_router(). */}

## Establish the directory

The session started with `teams: 1`: its [directory](../../reference/glossary/#directory), the
administrator's record of teams, their staff and supervisors, and the queues they serve. In a
deployment an administrator bootstraps the first team and changes teams through the
[directory API](../../reference/apis/casework/operations/getdirectory/), each write naming the
directory revision it expects.

{/* Evidence: crates/registry-casework/src/assignment.rs, bootstrap_directory() and update_directory_team();
    crates/registry-caseworkctl/src/dev/mod.rs. */}

## Stop and remove the session

```sh
caseworkctl dev stop tutorial-work/casework
```

The project changed after the session started, so the retained session refuses to start again:

```sh test-exit="3"
caseworkctl dev start tutorial-work/casework
```

```text test-expect
error[caseworkctl.dev.inputs-changed] .casework/dev
  The authored project, clients file, or ports differ from the retained development session, which still holds records.
  next: Run caseworkctl dev stop --remove to discard the retained session and start again from the edited inputs, or copy the authored files to a new project directory to keep it.
1 error, 0 warnings
```

Removing the session deletes its database, credentials and audit journal; keep anything you need
first.

```sh
caseworkctl dev stop tutorial-work/casework --remove
```

```json test-excerpt
{"directory": {"revision": 0, "teams": 0}, "state": "stopped"}
```

{/* Evidence: crates/registry-caseworkctl/src/dev/mod.rs, stop and InputsChanged. */}

## Troubleshooting

A relative runtime configuration path is refused before anything is read:

```sh test-exit="1"
caseworkctl doctor --runtime-config tutorial-work/casework/.casework/dev/operator.yaml
```

```text test-expect
error[platform.runtime-config.path] runtime.yaml:
  The runtime configuration was refused.
  next: Give the absolute path of the runtime configuration file, without . or .. components.
1 error, 0 warnings
```

`init` never writes over an existing directory. The report does not say so; pick a path that does
not exist:

```sh test-exit="1"
caseworkctl init tutorial-work/casework
```

```text test-expect
error[caseworkctl.refused] runtime
  The authored input was refused.
  next: Correct the named input or runtime dependency, then retry.
1 error, 0 warnings
```

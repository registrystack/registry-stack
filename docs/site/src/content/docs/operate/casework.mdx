If you operate Registry Casework, deploy a reviewed policy package against PostgreSQL, verify its
activation, then establish the teams that can see and decide its review tasks. Casework returns a
review result; the producer keeps all authority to change its subject.

{/* Evidence: products/casework/README.md; crates/registry-casework-core/src/adapter.rs, ReviewContextProvider. */}

## What you provide

- PostgreSQL 17 or newer, with TLS and separate migration and runtime credentials.
- An OpenID Connect issuer, the intended audience, and an explicit list of admitted clients.
- A private HTTP listener behind a TLS proxy you operate.
- A reviewed [policy package](../../reference/glossary/#policy-package), the matching binaries,
  and secret files the process can read.
- A durable audit destination and an archive for it.
- A [directory](../../reference/glossary/#directory) team serving each queue reviewers work.

Review and directory state live in PostgreSQL; the audit journal lives outside it. A
current-source policy also needs a read-only context provider.

{/* Evidence: crates/registry-casework/src/{config,runtime,store,auth}.rs;
    crates/registry-casework/src/audit.rs. */}

## Connect identity and completion delivery

Establish issuer signing-key trust and TLS trust separately. The
[OIDC connection guide](../advanced/connect-an-oidc-issuer/) explains issuer configuration and
key discovery; the Casework runtime's `authentication.oidc` block binds the accepted resource,
clients, and human identity claim. Configure downstream HTTPS trust through the owning connection's
certificate setting, rather than weakening verification.

Present a resource-specific access token and select the authored profile with
`Registry-Casework-Profile` on Casework task and directory routes. Shared producer Review routes
use `Registry-Review-Profile`. The [Casework API](../../reference/apis/registry-casework/) owns the
route, token, scope, and profile requirements; a scope does not replace an authored access profile.

For a producer completion destination, follow
[completion destinations](../casework-retention/#completion-destinations), then read the result
through the producer's independently authorized client. The wake carries no decision and cannot
approve or apply a source operation. Acknowledge only after accepting the wake under the
[delivery contract](../../configure/module-conventions/#receive-signed-delivery); authentication,
binding, and acknowledgement failures must remain visible to the dispatcher. For released 0.43 behavior, return exactly
`204 No Content` with an empty body after acceptance. The shared delivery contract governs the
next release's acknowledgement behavior; returning an empty `204` remains compatible with both.

## Install the runtime

Install matching `casework` and `caseworkctl` binaries on the serving and operator hosts:

```sh
curl -fsSL https://github.com/registrystack/registry-stack/releases/latest/download/casework-install.sh | bash
casework --version
caseworkctl --version
```

Read the installer before running it. Its `SHA256SUMS` check does not establish release
authenticity; use the
[release verification procedure](https://github.com/registrystack/registry-stack/blob/main/release/VERIFY.md)
for that.

The container image carries both binaries. Its entrypoint serves Casework from
`/etc/registry-casework/runtime.yaml`; run operator commands with the entrypoint set to
`/usr/local/bin/caseworkctl`. Pin the image digest, mount the package, runtime file, and secret
root read-only, and give the audit directory durable writable storage.

{/* Evidence: crates/registry-casework/install.sh; release/docker/Dockerfile.casework, ENTRYPOINT and CMD. */}

## Provision PostgreSQL

Use a new database. As your PostgreSQL administrator, create a schema-owning migration role, a
separate runtime role, and the database:

```sql
CREATE ROLE casework_migration LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE
  NOINHERIT NOBYPASSRLS PASSWORD '<migration-password>';
CREATE ROLE casework_runtime LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE
  NOINHERIT NOBYPASSRLS PASSWORD '<runtime-password>';
CREATE DATABASE casework;
```

In that database, grant connection access and give the migration role the schema:

```sql
REVOKE ALL ON DATABASE casework FROM PUBLIC;
GRANT CONNECT ON DATABASE casework TO casework_migration, casework_runtime;
ALTER SCHEMA public OWNER TO casework_migration;
REVOKE ALL ON SCHEMA public FROM PUBLIC;
```

Only `caseworkctl apply` uses the migration credential, so keep it off the serving host. Apply
grants the runtime role what it serves with and keeps the activation ledger read-only to it.

If apply reports `casework.activation.role-mode-weakened`, make the ownership, privilege, or
trigger correction it names, then plan again; never give the runtime role ledger writes to get past
it. When both credentials name one role, the deployment records single-role mode, and `status`
says the runtime credential can activate packages.

## Write the runtime file

The runtime file is yours, kept apart from the authored policy. This one uses mounted secrets and
a TLS proxy in front:

```yaml
apiVersion: id.registrystack.org/formats/casework/runtime/v1alpha1
kind: CaseworkRuntimeConfig
identity:
  databaseId: casework-decisions
package:
  root: /srv/registry-casework/package
listener:
  bind: 10.42.0.7:8100
  tlsTermination: operator-controlled-upstream
  networkExposure: private-address
secretProviders:
  file:
    root: /run/secrets/registry-casework
database:
  runtimeUrlRef: secret:file/runtime-database-url
  migrationUrlRef: secret:file/migration-database-url
authentication:
  oidc:
    issuer: https://identity.example.test/realms/registry
    audience: urn:example:casework
    allowedClients: [casework-console, review-producer]
    scopeClaim: scope
    humanIdentity:
      claim: registry_actor_kind
      value: human
audit:
  path: /var/lib/registry-casework/audit/casework.ndjson
  hashKeyRef: secret:file/casework-audit-key
```

Every path is absolute, and the runtime file may not pass through a symbolic link. Unknown keys and
explicit nulls are refused at their position; omit a key to take its default.
`identity.databaseId` is your stable name for this deployment: the first apply records it, and
every later apply and start refuses a database that recorded another.

Each `...Ref` key names a secret, never its value: `secret:file/<name>` resolves under
`secretProviders.file.root`. Mount each secret as a file owned by the runtime user, mode `0400` or
`0600`, with no symbolic or extra hard link. `operator-controlled-upstream` requires
`allowedClients` to list its clients. Ship the audit journal to your archive;
[Review retention and audit](../casework-retention/#keep-the-audit-file) covers its key and
rotation.

### Add a current-source provider

A current-source policy names a provider by its `deploymentRef`. Bind it to a read-only provider:

```yaml
contextProviders:
  facility-registry:
    baseUrl: https://registry.example.test
    statusProfile: casework-review-status
    tokenEndpoint: https://identity.example.test/oauth2/token
    clientAssertionAudience: https://identity.example.test
    resource: urn:breg:facility-registry
    scopes: [registry:proposal:review-status]
    clientIdRef: secret:file/breg-status-client-id
    clientAssertionKeyRef: secret:file/breg-status-client-key
```

This Base Registry Engine (BReg) status reader checks reviewability only; its `statusProfile`
must match the authored service-status profile. Human display uses the reviewer's own bearer, so
source authorization and disclosure still apply. A Casework approval never applies a BReg
Proposal.

### Check the runtime file offline

Check the authored project against the runtime file before anything touches a database:

```sh
caseworkctl check ./decisions --runtime-config /etc/registry-casework/runtime.yaml
```

The check opens no package, database, issuer, provider, or secret. Add `--environment` to fill
`${VAR}` expressions from the current environment. A clean check does not prove live readiness.

## Verify the package before it opens the listener

Write the package with `caseworkctl package`, install it in its own directory, and set
`package.root` to it. Record its `packageDigest` in your change record and set
`package.expectedDigest` to the same value, so that replacing files under `package.root` cannot
change what a restart loads. Never edit a package in place: apply and startup both verify every
file against `SHA256SUMS`, and an authored directory without one is refused.

Keep earlier package directories for recovery, and plan every activation, rollbacks included.

{/* Evidence: crates/registry-casework/src/config.rs, verify_casework_package() and expected_digest;
    products/casework/RUNTIME-CONFIG.md, package. */}

## Refuse a package that strands pinned work

An accepted review keeps the policy closure it was admitted under. A candidate that removes a
policy, producer, profile, team, queue, provider, or context contract an open review still needs is
refused with `casework.activation.stranded-work`, and so is a change to pinned policy content under
the same policy version. There is no override. Let the affected reviews finish, have their producer
cancel them, or prepare a successor that keeps what they need.

{/* Evidence: crates/registry-casework/src/pinned_work.rs, compare_pinned_work() and stranded_work_refusal();
    crates/registry-casework/src/activation.rs, stranded-work. */}

## Plan, apply, and serve

From the operator host, read the plan, apply it with the migration credential, and read the
result:

```sh
caseworkctl plan --runtime-config /etc/registry-casework/runtime.yaml
caseworkctl apply --runtime-config /etc/registry-casework/runtime.yaml \
  --operator-reference CHANGE-1234 --backup-reference nightly-before-activation
caseworkctl status --runtime-config /etc/registry-casework/runtime.yaml
```

`plan` writes nothing; read its package digest, pending schema versions, role mode, and refusals.
Applying the package that is already active is refused with
`casework.activation.already-active`. `--operator-reference` is stored as a keyed hash;
`--backup-reference` is stored as text, so use a snapshot identifier without personal data.

If apply returns `casework.activation.applied-unaudited`, the activation committed but its audit
entry did not: restore audit, read `status`, and record the recovery. A runtime role that cannot
read the ledger gets `casework.activation.ledger-unreadable`; apply restores its grants. Exit codes
are `0` for success, `1` for a refusal, `2` for usage, and `3` for an operational failure.

Then serve as the runtime user:

```sh
casework --runtime-config /etc/registry-casework/runtime.yaml serve
curl --fail http://10.42.0.7:8100/ready
```

Startup refuses a database whose active package is not the configured one. `/ready` checks the
database and audit writer only; check source context and queue staffing with real identities.

### Earlier database and audit state

The current contract refuses retired Casework schemas with `casework.activation.retired-schema`,
a database a pre-1.0 release wrote with `casework.activation.beta-schema`, and a database newer
than the binary with `casework.activation.schema-newer`. Keep such a database with the release
that wrote it and provision a fresh one; for a pre-1.0 database, follow
[the upgrade runbook](../advanced/upgrade-and-retire/#upgrade-in-this-order). Never delete ledger rows or run migration
SQL by hand to get past either refusal.

A restore returns review state to its backup point, and the external audit journal must not be
rewound. Follow [Casework restore and reconciliation](../advanced/back-up-and-restore/#restore-registry-casework)
before reviewers resume.

### Scrape metrics and the running version

The API listener serves no metrics. Open a private telemetry listener for them:

```yaml
metricsListener:
  bind: 127.0.0.1:9100
```

It serves `/metrics` and `/version` only, on a loopback or private address that is not the API
listener's. Metrics count open review requests, open tasks, and due tasks, with no subject
identifiers. `/version` reports the binary version and the package digest the process serves, so a
rollout can confirm what each process runs.

## Establish directory authority

A fresh deployment has an empty directory, so no reviewer sees a task until an administrator
bootstraps the first team and its served queues.
[Staff the Casework directory](../../configure/casework-directory/) gives the requests. Each
directory write names the revision it expects, and membership and queue service are live
authority for old and new tasks alike.

### Size the review queue reads

The `inbox` policy in `casework.yaml` bounds each task-list, next-task, and holdings read. Defaults
are `maximumCandidateScan: 100`, `maximumSourceReads: 25`, and `pageDeadlineMilliseconds: 2000`;
counts go up to 10,000 and the deadline to 30,000. An ordinary due-date or subject-order query
selects a bounded database page before it reads current source visibility, so it never scans the
whole queue; concealed candidates still spend the scan budget. Filtering or sorting by live source
reference scans the whole bounded queue, because its keys come from source reads; an exact subject
or queue selector narrows it, a smaller page does not.

Within one page, several task slots for one request share one source observation. Each new page
repeats the source and Directory checks, and a continuation charges its anchor observation to the
same source budget, so a budget of one observation cannot advance past a current-source anchor. A
BReg human context reads each chunk in one bounded HTTP batch under the original caller and source
profile; every subject in it still passes its own disclosure and audit checks.

An ordinary read that exhausts its candidate, source, or time budget is refused whole with
`review.query-too-broad`: narrow the query or reduce the page limit. A source call that reaches the
deadline can instead report the source unavailable. Supervision and own-decision feeds return
bounded partial pages with opaque continuations; follow the cursor with the same caller, profile,
and query, and start the walk again after the cursor expires or its anchor leaves your scope.
Measure representative source latency before raising budgets. A caseload preview refuses more than
100 claimed tasks; split it by queue or move tasks one at a time.

### Check readiness with doctor

Run the operator preflight as the runtime user:

```sh
caseworkctl doctor --runtime-config /etc/registry-casework/runtime.yaml
```

Doctor checks the configuration, the package, the database activation, open reviews against the
configured package, and that the audit path is writable. It accepts the package already active.
It warns when the serving teams cannot supply the distinct reviewers a stage requires; add eligible
members and rerun it to confirm the warning clears. It opens no listener and proves no issuer or
provider access; use `/ready` and an authenticated task read for those.

{/* Evidence: crates/registry-caseworkctl/src/project.rs, doctor();
    products/casework/RUNTIME-CONFIG.md, doctor repeats the pinned-work check. */}

## Change the active package

A running process keeps the package it started with and does not recheck the activation ledger,
so a predecessor left serving after apply goes on admitting work under the old package. Take it out
of your proxy's routing, stop every process serving it, then plan, apply, and start the successor
at once. The successor repeats the pinned-work check before it opens its listener. If it refuses
with `casework.activation.stranded-work`, plan and apply the predecessor again, serve it until the
named reviews finish or are cancelled, and retry the change.
[Change an active package](../change-a-casework-package/) walks the plan and apply against a local
session.

## Troubleshooting

| Symptom | Recovery |
| --- | --- |
| `platform.runtime-config.path` | Give the absolute path of the runtime file, without `.` or `..` components. |
| Startup names a different active package | Plan and apply the configured package, or point `package.root` at the active one. |
| `review.policy-mismatch` on admission | Reconcile the producer's policy pin with the deployed policy. |
| A current-source task is concealed or unavailable | Check the reviewer's source profile, the context binding, and the provider. Never use the status credential for human display. |
| `review.query-too-broad` | Narrow the queue or subject, reduce the page limit, review the `inbox` budgets, or split a caseload move. |
| `precondition.failed` | Read the task or directory again and take a fresh preview where one is required. |
| `service.unavailable` and `/ready` returns `503` | Repair the database or the audit path, space, or permissions and restart. Retry an interrupted write with its original key. |

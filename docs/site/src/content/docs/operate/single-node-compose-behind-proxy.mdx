Use this guide to hand independently approved Registry Relay and Registry Notary bundles to a
single-node Docker Compose deployment, then include that package in an operator-owned application
when needed.
The generated package remains portable after handoff and can run with Docker Compose without
Registryctl.

## When to use this

Use the generated package when:

- One Docker host runs one public Relay, one private consultation Relay, one Notary, and the
  release-owned PostgreSQL state plane
- Docker Compose 2.35.0 or later is available
- Each product lane has an independently signed bundle and trust anchor

The package does not provide high availability, Kubernetes, an external database, or direct
non-loopback host publishing.
Create a separate operator-owned Compose model when the generated choices do not fit.
Registryctl does not verify or manage that model.

## Before you start

You need:

- One verified `ApprovedBaselineSetV1` containing `relay-public`, `relay-consultation`, and
  `notary`
- The released Registryctl installation whose signed release lock authorizes the images
- Operator-owned secret and certificate files
- Durable storage for PostgreSQL and each product's anti-rollback state

The approved set is compatibility evidence and a portable locator.
It is not a fourth signature, trust root, or product activation authority.
If you have unsigned output from `registryctl build`, complete
[Approve the initial product baseline](../approve-initial-baseline/) first.

Run the host checks from the authored project, or select it with the global `-C` option:

```sh
registryctl -C ../registry-project doctor --profile production
```

The command reports authored-environment, release-lock, Docker client, Docker daemon, Compose
2.35.0, and digest-locked image readiness.
It does not fetch a replacement release lock.

## Generate the package

From the operator workspace, generate into an absent or empty directory:

```sh
registryctl deploy generate \
  --approved-set ./approved-set.v1.json \
  --output-dir ./registry-stack
```

The first generation creates a safe `binding.yaml` and transfers that file to the operator.
Registryctl owns `generated/`.
The operator owns `binding.yaml` and `operator/`.

The package has this shape:

```text
registry-stack/
  binding.yaml
  operator/
    secrets/
    certificates/
  generated/
    compose.empty.env
    compose.yaml
    compose.initialize.yaml
    deployment-plan.v1.json
    deployment-manifest.v1.json
    RUNBOOK.md
    inputs/
    bundles/
    anchors/
```

The package copies the three signed product bundles and their anchors into separate,
digest-specific directories.
It does not create secret files, production keys, or anti-rollback state.

Record the approved-set digest and generated closure root printed by the command outside the
package.
Use those values to check the package after transfer.

## Supply operator-owned inputs

Read `generated/RUNBOOK.md`.
Place each required secret and certificate at the package-relative path that the runbook lists.
Use owner-only file modes.

Edit `binding.yaml` only when the visible generated defaults need to change.
The binding can select loopback ports, package-relative secret and certificate locators, durable
state locations, an existing edge network, resource limits, restart policy, and value-free logging
policy.

Do not edit files under `generated/`.
Do not edit generated Relay or Notary configuration.
The signed product bundles remain the configuration authority.

## Verify the generated package

Verify the package before initialization:

```sh
registryctl deploy verify --package ./registry-stack
```

The package-only report identifies:

- Ownership as `managed` or `invalid`
- Freshness as `current`, `stale`, or `not_applicable`
- Verification scope as `package`
- Whether in-place regeneration is safe
- Any generated-package violation

Package-only verification does not inspect or certify an application that includes the package.

## Initialize each product once

Initialization is explicit and product-owned.
Ordinary `docker compose up` does not select an initialization service.

Change to the package directory:

```sh
cd registry-stack
```

Run the complete first-installation block from `generated/RUNBOOK.md` exactly once:

```sh
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml -f generated/compose.initialize.yaml config --no-interpolate --no-env-resolution --quiet
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml run --rm --no-deps registry-runtime-stage-secrets
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml -f generated/compose.initialize.yaml run --rm registry-postgres-bootstrap
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml -f generated/compose.initialize.yaml run --rm registry-relay-public-prepare-state
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml -f generated/compose.initialize.yaml run --rm registry-relay-consultation-prepare-state
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml -f generated/compose.initialize.yaml run --rm registry-notary-prepare-state
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml -f generated/compose.initialize.yaml run --rm registry-relay-public-initialize
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml -f generated/compose.initialize.yaml run --rm registry-relay-consultation-initialize
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml -f generated/compose.initialize.yaml run --rm registry-notary-initialize
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml up --detach --wait --wait-timeout 120
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml ps
```

The secret stager checks and copies the operator files consumed at runtime.
The PostgreSQL bootstrap runs before product state preparation.
Preparation creates or migrates only the owning product's database schema and roles.
Initialization verifies the bundle and anchor, records acceptance audit, and creates only the
owning product's absent anti-rollback state.

Initialization fails when anti-rollback state already exists or does not match.
Do not reset state to make an older bundle start.

## Run the package standalone

Run the ordinary start-and-stop block from `generated/RUNBOOK.md`:

```sh
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml config --no-interpolate --no-env-resolution --quiet
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml run --rm --no-deps registry-runtime-stage-secrets
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml run --rm --no-deps registry-relay-public 'product-action' 'relay-public' 'verify_state'
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml run --rm --no-deps registry-relay-consultation 'product-action' 'relay-consultation' 'verify_state'
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml run --rm --no-deps registry-notary 'product-action' 'verify_state'
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml up --detach --wait --wait-timeout 120
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml ps
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml down
```

The public Relay and Notary application ports bind to host loopback.
The consultation Relay, administration, and posture endpoints have no host port.
The three `verify_state` actions check accepted product state before ordinary startup.
`up --wait` waits for the generated health conditions.
`down` stops ordinary services without deleting durable volumes.

Internet exposure and Transport Layer Security (TLS) termination remain operator concerns.
An application that includes the package remains outside the Registryctl package verification
claim.

## Include the package in an existing application

An operator can add the generated package to an application `compose.yaml` without copying or
merging its services:

```yaml
include:
  - ./registry-stack/generated/compose.yaml
```

Verify the generated package before composing it into the application:

```sh
registryctl deploy verify --package ./registry-stack
docker compose --env-file ./registry-stack/generated/compose.empty.env -f ./compose.yaml config --no-interpolate --no-env-resolution --quiet
```

Registryctl verifies only the generated package.
The application operator owns the include graph, additional services, external Transport Layer
Security (TLS), hostnames, edge request admission, network access, and compatibility with the
generated package.
The package verification result does not extend to the application model.

## Customize the generated package

Use `binding.yaml` for supported generated choices.
After editing it, rerun generation against the same output directory:

```sh
registryctl deploy generate \
  --approved-set ./approved-set.v1.json \
  --output-dir ./registry-stack
registryctl deploy verify --package ./registry-stack
```

Registryctl preserves the operator-owned binding and directories, replaces only the verified
generator-owned closure, and reports the package as current after successful regeneration.

If the binding schema cannot express the required deployment, keep the verified generated package
intact and create a separate operator-owned deployment artifact.
Registryctl does not verify or overwrite that artifact.

Changing a product image, command, entrypoint, verified bundle or anchor mount, anti-rollback
state ownership, private endpoint exposure, user, capabilities, or privilege restriction is
invalid, not an adaptation.

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| Generation refuses a non-empty output | The directory is not an intact verified package. | Select an absent or empty directory, or restore the complete verified package. |
| Verification reports `managed` and `stale` | A managed input changed after generation. | Regenerate the generator-owned closure before startup. |
| The generated binding cannot express the required deployment | The deployment is outside the package profile. | Keep the generated package intact and create a separately governed operator-owned artifact. |
| Verification reports `invalid` | A hard product, secret, state, network, or privilege invariant failed. | Restore the generated boundary. Do not downgrade the failure to an override. |
| Ordinary startup reports missing state | The one-time initialization was not completed or durable state was lost. | Complete first installation, or restore the exact recovery consistency group. Do not reinitialize an existing identity. |
| An including application cannot reach a public service | The operator-owned include graph or network wiring is incomplete. | Correct the application model and rerun the application's Compose validation. |

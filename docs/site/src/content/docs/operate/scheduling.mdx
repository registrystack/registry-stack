Take the project you authored to a running deployment, then change, retain, and upgrade it. Every
step runs `schedulingctl` or `scheduling` against one runtime file.

## What you provide

- PostgreSQL 17 or newer, reachable over TLS. Registry Scheduling requires TLS on every database
  connection and refuses one it cannot protect.
- An OpenID Connect issuer whose access tokens carry the read scope and, for bookings, the
  [task grant](../../reference/glossary/#task-grant) another system issues.
- A directory of secret files owned by the runtime user, each with mode 0400 or 0600 and
  written without a trailing newline.
- A TLS edge in front of the listener. Scheduling serves plain HTTP on a private address and
  refuses a public one.

## Install the runtime

The installer puts `scheduling` and `schedulingctl` in `~/.local/bin`. The runtime is published
for Linux amd64 only; on Linux arm64 and macOS arm64 the installer installs `schedulingctl` alone.

```sh
curl -fsSL https://github.com/registrystack/registry-stack/releases/latest/download/scheduling-install.sh | bash
schedulingctl --version
```

That installer is published with the
[latest release](https://github.com/registrystack/registry-stack/releases/latest) and installs that
release; to install another one, fetch the installer from that release's assets, because a published
installer refuses a different `SCHEDULING_VERSION`. It checks every downloaded asset against the
release's `SHA256SUMS` but does not prove where the release came from. For that, follow the release
verification guide for the tag, then rerun the installer with `SCHEDULING_ASSET_DIR` set to the
verified directory.

The runtime is also published as the image `ghcr.io/registrystack/scheduling:<tag>`. Deploy it by
the digest the release manifest names, not by the tag. The image runs `/usr/local/bin/scheduling`
as UID 65532, reads `/etc/registry-scheduling/runtime.yaml`, and carries the matching
`schedulingctl`. To run an operator command with the image's exact bytes, override the entrypoint
and mount the runtime file, the package, and the secrets read-only and the audit directory
writable, each at the location your `runtime.yaml` names:

```sh
docker run --rm \
  --entrypoint /usr/local/bin/schedulingctl \
  -v /etc/registry-scheduling/runtime.yaml:/etc/registry-scheduling/runtime.yaml:ro \
  -v /etc/registry-scheduling/package:/etc/registry-scheduling/package:ro \
  -v /run/secrets/registry-scheduling:/run/secrets/registry-scheduling:ro \
  -v /var/lib/registry-scheduling:/var/lib/registry-scheduling:rw \
  "ghcr.io/registrystack/scheduling@sha256:<verified-digest>" \
  apply --runtime-config /etc/registry-scheduling/runtime.yaml --operator-reference CHG-1234
```

`apply` needs the migration credential and writes its own audit file beside `audit.path`, and
`records apply` connects with the same credential. Mount the migration credential only for those
two commands, and keep it out of the serving container.

## Write the runtime file

`schedulingctl init` wrote `runtime.example.yaml` beside your policy. Copy it to the host as
`runtime.yaml` and edit it:

- `package.root`: `/etc/registry-scheduling/package`, the directory you pass to
  `schedulingctl package --output`. Every path in the file must be absolute and must not pass
  through a symbolic link. So must the `--runtime-config` path; a relative one is refused with
  `platform.runtime-config.path`.
- `identity.databaseId`: a name for the one database this deployment owns. The first `apply`
  records it, and every later command refuses a database that names another.
- `listener`: `bind`, plus `tlsTermination: operator-controlled-upstream` behind your TLS edge.
  `development-loopback` is refused on any address but loopback.
- `secretProviders.file.root` and the `*Ref` keys: secret references such as
  `secret:file/runtime-database-url`, resolved under that root. Write each file with
  `printf '%s'`: a trailing newline is part of the value, and a URL file that ends in one makes
  `serve` exit 3 with `FATAL: database "scheduling\n" does not exist`.
- `database.runtimeUrlRef` and `database.migrationUrlRef`: two PostgreSQL URLs. Give them
  different roles. With one role for both, the serving credential could rewrite the activation
  record, and `apply`, `status`, and `serve` say so.
- `authentication.oidc`: your `issuer`, `audience`, and the exact `allowedClients` that may call.
- `taskGrantStatus`: either a list of the task authorities Scheduling asks about every grant
  before it books, or `unchecked-final-fifteen-minutes`, which asks nothing and accepts only a
  grant with 15 minutes or less left.
- `audit`: `hashKeyRef`, a key you generate with `openssl rand -hex 32`, plus either a file
  `path` or `destination: stdout`.
- `destinations`: where reminders and the hook events your policy names are delivered.

[Scheduling configuration](../../reference/scheduling-configuration/) lists every key and default.

Check the file offline against your project. Nothing is read from the database or the network:

```sh
schedulingctl check ./scheduling --runtime-config /etc/registry-scheduling/runtime.yaml
```

```text
Authoring check passed.
databaseAccess: false
networkAccess: false
```

## Package the policy

```sh
schedulingctl package ./scheduling --output /etc/registry-scheduling/package
```

```text
Package written.
packageDigest: sha256:<digest>
runtimeConfigurationIncluded: false
secretsIncluded: false
```

`--output` refuses a directory that already exists. The package holds `scheduling.yaml` and a
`SHA256SUMS` file. Set `package.expectedDigest` to the digest if the runtime must refuse any other
package.

## Provision PostgreSQL

Your runtime file already names the roles, their passwords, and the database. They are the URLs in
`database.migrationUrlRef` and `database.runtimeUrlRef`. `provision` reads the runtime file and the
package it names, so write the file and build the package first. Put both database URLs in their
secret files, then run `schedulingctl provision` once as a PostgreSQL role that can create roles and
databases:

```sh
schedulingctl provision --runtime-config /etc/registry-scheduling/runtime.yaml --admin-url-file admin-url
```

The `admin-url` file holds one PostgreSQL URL for that administrator, for example
`postgresql://admin:PASSWORD@db.example.org:5432/postgres`. The administrator needs `CREATEROLE` and
`CREATEDB` and does not need to be a superuser. To pass the URL in an environment variable instead,
use `--admin-url-env NAME`. The connection requires TLS and verifies the server certificate. Set
`database.caBundleRef` in the runtime file to trust a private CA. The command never prints the
administrator URL or a password.

The command:

- Creates the migration role and the runtime role, each with `LOGIN` and no other privilege.
- Creates the database and closes it to `PUBLIC`.
- Grants both roles `CONNECT` on the database.
- Gives the migration role `USAGE` and `CREATE` on the `public` schema, and takes `CREATE` on it
  from `PUBLIC`.

Run it again at any time. It creates only what is missing. It refuses a role that exists with a
different password than its URL holds, and tells you which role.

If a database administrator must run the SQL, add `--print-sql` and leave out the administrator
flags. The command connects to nothing and prints the script. Each `CREATE ROLE` is followed by a
`\password` line that prompts for the password in `psql`, so the script holds no password:

```sql
SET createrole_self_grant = 'set,inherit';
CREATE ROLE "scheduling_migration" LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS;
\password "scheduling_migration"
CREATE ROLE "scheduling_runtime" LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS;
\password "scheduling_runtime"
CREATE DATABASE "scheduling" WITH ALLOW_CONNECTIONS false;
REVOKE ALL ON DATABASE "scheduling" FROM PUBLIC;
GRANT CONNECT ON DATABASE "scheduling" TO "scheduling_migration", "scheduling_runtime";
ALTER DATABASE "scheduling" ALLOW_CONNECTIONS true;
\connect "scheduling"
REVOKE CREATE ON SCHEMA public FROM PUBLIC; GRANT USAGE, CREATE ON SCHEMA public TO "scheduling_migration";
```

The names come from your URLs. Add `--format json` for a report of each statement and its outcome.

`provision` grants the runtime role nothing beyond `CONNECT`. `apply` grants it exactly what serving
needs: usage on the schema, read and write on the Scheduling tables, usage and select on the outbox
identity sequence, and read on the activation ledgers. It reissues the grants on every run, so a
table a later migration adds is covered. The runtime requires TLS on its database connection and
refuses one it cannot verify; `database.caBundleRef` names the CA bundle when a private CA fronts
PostgreSQL.

## Plan and apply

`plan` connects with the runtime credential and writes nothing:

```sh
schedulingctl plan --runtime-config /etc/registry-scheduling/runtime.yaml
```

```text
Activation planned; nothing was written.
changesPending: true
databaseIdCheck: initial
pendingSchemaVersions: [100]
policy: {"activeDigest":null,"candidateDigest":"sha256:<digest>","revision":2,"revisionAdvances":true}
refusals: []
```

`apply` connects with the migration credential and, in one transaction, creates the schema,
publishes the policy, grants the runtime role its access, and records the activation. The operator
reference is kept only as a keyed hash; `--backup REF` records the backup you took first.

```sh
schedulingctl apply --runtime-config /etc/registry-scheduling/runtime.yaml \
  --operator-reference CHG-1234
```

```text
Package activated.
applyOrder: 1
effects: {"policyDigest":"sha256:<digest>","policyRevision":2,"policyRevisionAdvanced":true,"schedulingIdAdopted":true}
schemaVersionsApplied: [100]
```

Callers send the published `policyRevision` with each booking. Applying the active package again is
refused with `schedulingctl.activation.package-already-active`.

For commitment authorisation, use the existing
[task-grant contract](../../reference/scheduling-task-grants/). Resolve any `duplicateKey`
diagnostic in the owning offering and identity configuration before retrying a commitment.

## Apply the environment records

The supply lives in the database, not in the package. Apply `records.yaml`:

```sh
schedulingctl records apply --runtime-config /etc/registry-scheduling/runtime.yaml \
  /etc/registry-scheduling/records.yaml
```

```text
Environment records applied.
applied: {"exceptions":1,"locations":2,"members":3,"pools":2,"windows":0}
```

:::danger
`records apply` replaces every record the database holds with the document you pass. A location,
pool, member, window, or closure the document leaves out is gone. It refuses only to move, remove,
or shrink a window below its live holds and appointments, and names the window and the deficit.
:::

### Publish resource availability and absences

Individual pool members may add `availability` with dated `openings` and `closures`, each a
bounded list of `{start, end}` instants.
Omitted openings add no opening constraint, and `openings: []` publishes no supply.
The union of the openings intersects the member's static `available` flag and the offering's
location calendar.
Overlapping or adjacent openings form continuous supply, closures win, and every interval is
half-open.
Supply must cover the complete occupied interval, including setup and cleanup.
Resolve local calendars and ambiguous or nonexistent local times at the source before sending
RFC 3339 instants.
Each list contains at most 256 intervals, each positive and at most 3,650 days.

Recording an absence blocks new admissions, rescheduling into that absence, and confirmation of an
affected hold.
Existing bookings and holds are not cancelled or reassigned.
`records apply --format json` includes `resourceImpacts`: the first 256 affected live resource
allocations, their claim identifiers and occupied intervals, and the exact total from a current
database snapshot after the apply.
A reservation can appear once for each affected resource, and a window appears through its own
resource reservation without counting each booking in it again.
Removed resources and stock reductions below simultaneous commitments are included alongside
absences.
The report contains no owner identity or absence reason.
It is a current impact read, not a promise that supply stayed unchanged after publication.
Use scoped appointment reads to inspect further bookings and arrange an authorised reschedule or
cancellation; affected holds can be released or expire normally.
Resource catalogue and ordinary availability responses do not disclose these dated facts or
personnel information.

Availability cursors last at most 15 minutes.
Callers deduplicate entries by their start when a policy, records, or runtime change overlaps an
in-flight listing.

## Serve

```sh
scheduling --runtime-config /etc/registry-scheduling/runtime.yaml serve
```

Startup verifies the package against the activation record. It refuses a schema with pending
versions, a package that was not applied, and a database that names another `databaseId`. It logs
`verified Scheduling package` with the digest but not the address it listens on. Ask the readiness
route instead:

```sh
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8105/readyz
```

```text
200
```

`/readyz` answers unavailable while PostgreSQL is unreachable, while the schema is not the one
this release expects, and while the audit destination refuses writes, because no booking proceeds
without its audit entry.

## Read the deployment

`status` names the active package and every activation:

```sh
schedulingctl status --runtime-config /etc/registry-scheduling/runtime.yaml
```

```text
Activation status read.
pendingSchemaVersions: []
schemaVersion: 100
verifiedPackageDigest: sha256:<digest>
```

`intents` lists the intents nobody is delivering: each one that fell due while no reminder
destination is configured, and any intent the destination refused, that failed every attempt, or
that could not be read or rendered. A reminder dropped because its appointment was cancelled or
moved is not listed.

```sh
schedulingctl intents --runtime-config /etc/registry-scheduling/runtime.yaml
```

```text
Undelivered delivery intents listed.
intents: [{"appointmentRevision":1,"attempts":1,"deliveryState":"local","purpose":"confirmation",...}]
```

## Watch the metrics

Add a `metricsListener` block to `runtime.yaml` to serve Prometheus text. The example files carry
one on `127.0.0.1:9105`. Without the block, Scheduling serves no metrics. The socket must be
loopback or private, and must not be the `listener` socket. In a container whose private address is not known when you write the file, set `metricsListener.networkExposure: container-private` to bind `0.0.0.0`: see [Scrape metrics from a container](../stuck-work/#scrape-metrics-from-a-container). `GET /metrics` on that socket answers
the series below and nothing else. The public listener does not route `/metrics`.

| Series | Labels | Meaning |
| --- | --- | --- |
| `scheduling_http_requests_total` | `route`, `method`, `status`: `1xx`, `2xx`, `3xx`, `4xx`, `5xx`, `other` | Answered HTTP requests, by route template and status class |
| `scheduling_outbox_items` | `state`: `pending`, `leased`, `delivered`, `dead-lettered`, `expired`, `unknown`, `cancelled` | Gauge of reminder and notice intents by stored state, read from the database at each scrape |
| `scheduling_outbox_oldest_pending_age_seconds` | none | Gauge of how many seconds the oldest pending intent has been eligible for pickup, which is its due time, or the end of its last retry back-off. An intent that is still waiting out a back-off is not counted. Zero when none is overdue |
| `scheduling_hook_deliveries` | `state`: `pending`, `leased`, `delivered`, `dead-lettered`, `expired` | Gauge of observer-hook deliveries by stored state, read at each scrape |
| `scheduling_hook_oldest_pending_age_seconds` | none | Gauge of how many seconds ago the oldest pending hook delivery's event was captured. Zero when none is pending |
| `scheduling_worker_last_success_age_seconds` | `worker`: `hold-expiry`, `retention` | Gauge of seconds since the worker last finished a pass |
| `scheduling_metrics_sample_failures_total` | `queue`: `outbox`, `hook-deliveries` | Scrapes in which that queue could not be read |

Every state is listed, with a zero when no row is in it. Watch
`scheduling_outbox_items{state="dead-lettered"}` and
`scheduling_hook_deliveries{state="dead-lettered"}`, the work that gave up and needs a person.
A growing `scheduling_outbox_oldest_pending_age_seconds` or
`scheduling_hook_oldest_pending_age_seconds` means work is waiting and nothing is delivering it.
The outbox age leaves out intents that are waiting for a retry back-off to end, so it measures
overdue work only.

The queue gauges are read from PostgreSQL in read-only transactions. Both reads of one scrape share
one 5 second deadline, and each read's statement timeout is the time left, so the server cancels a
slow query. A read that starts after a slower one has used the deadline fails with `no-time-left` and never starts.
When a read fails, the runtime logs a warning with the error class (`sqlstate-<code>`, `connection-closed`, `query`, `timeout`, `no-time-left` or `pool`), adds one to
`scheduling_metrics_sample_failures_total` for that queue, and leaves that queue's series out of
the scrape. A missing series is therefore a failed read, never a zero. Alert on
`absent(scheduling_outbox_items)` as well as on the values.

`scheduling_worker_last_success_age_seconds` covers the two loops that Scheduling owns: hold
expiry, which wakes every 2 seconds, and retention, which runs about every 60 seconds. Retention
counts as a success only when all of its erase passes finish. Until a worker's first success the
gauge counts from process start, so a worker that never succeeds shows an age that keeps growing.
The reminder dispatcher and the hook delivery worker belong to shared platform crates and are not
in this series. Watch their backlog through the outbox and hook gauges above.

Counters and worker ages are per process and restart at zero. The queue gauges read the shared
database, so every replica reports the same values.

## Change the policy

Edit the project and run `schedulingctl test`. Package into a new directory, set `package.root`
to it, then plan and apply. The apply publishes the next policy revision, and a caller still
holding the old one is refused with `policy.changed` and reads the service again.

An offering with live holds or appointments must keep its service, location, mode, and pool or
window. A change to any of them is refused with `schedulingctl.activation.policy-in-use`; let the
bookings end or move them first. Any earlier package can be applied again as a new activation.

## Retention

The runtime runs its own retention sweep. Three keys under `retention` each default to seven
days, a placeholder rather than a recommendation. Each is the longest the data is kept; the sweep
erases it once the period has passed:

- `receiptRetentionDays`: how long an idempotency receipt lasts. A retry after that is refused
  with `idempotency.expired`.
- `claimOwnerRetentionDays`: how long after an appointment ends, or a hold lapses, the caller's
  issuer and subject stay on it.
- `hookPayloadRetentionDays`: how long a hook event's payload is kept, for retries while it is
  undelivered and for inspection, through the database, once it is dead-lettered.

`audit.retentionDays` (default 90) removes rotated audit files.

:::danger
Once `claimOwnerRetentionDays` passes, the appointment no longer belongs to anyone: its former
owner can no longer read, list, or recover it, and no receipt for it can be replayed. Set the key
to the period your callers need to look a booking up again.
:::

## Upgrade

Before 1.0, a release reads only the state its immediate predecessor wrote, so upgrade one release
at a time: install the next release, run `plan`, which lists the pending schema versions, take a
backup, `apply` with `--backup`, then restart `serve`. A runtime started against a schema older
than its own refuses to start until you apply.

:::danger
A schema migration cannot be undone by applying an earlier package. Restore the backup you named in
`--backup` instead. A release that starts a fresh baseline says so in its notes and must be applied
to a new, empty database; the old ledger is not carried over.
:::

If your registry project declares events that name a `webhook` destination, bind each destination
to a receiver, give the receiver the signing key, build it against a sample request, and recover
deliveries that did not arrive. The examples use one event, `contact-created-v1` on the `contact`
[Record type](../../reference/glossary/#record-type), sent to a destination called
`contact-events`.

The project names a destination only by identifier, so the same package runs in any deployment;
the runtime file binds that identifier to a real receiver. Base Registry Engine (BReg) sends an
event after the write that caused it commits, through its
[outbox](../../reference/glossary/#outbox).
[Send registry events to a webhook](../../tutorials/send-registry-events-to-a-webhook/) shows a
first delivery on a local registry.

## Declare an event and when it fires

A Record type declares its events under `hooks`.
An event declares only what changes its meaning:

```yaml
hooks:
  - id: case-approved-v1
    phase: after
    trigger: patched
    projection:
      - status
      - programme
    when:
      type: fields
      changed:
        - status
      beforeEquals:
        status: pending
      afterEquals:
        status: approved
    handler:
      type: url
      destinationId: eligibility-service
```

{/* Evidence: crates/registry-breg/src/contract.rs HookSource, EventConditionSource;
    crates/registry-breg/tests/compiler_webhook.rs
    field_conditions_are_typed_nonempty_and_trigger_compatible. */}

- `id` is the stable external event contract. A breaking payload change uses a new versioned id.
- `phase` is `after`: the event runs after the triggering transaction commits. The compiler refuses
  `before`.
- `trigger` is one of `created`, `patched`, `tombstoned`, or `read`. A `read` event alerts on a logged read and is described under [Alert on reads](#alert-on-reads).
- `projection` is the complete set of Record values that may leave the registry. System event
  metadata does not need to be listed.
- `when` is optional and narrows which changes fire the event.
- `handler` is either `type: url` with the logical `destinationId`, or a local kind: `type: rhai`
  with a reviewed `script` path, or `type: wasm` with a reviewed `module` path. A `url` handler
  delivers to a bound destination, and a local handler runs its program in the post-commit worker.
  The delivery row records the digest of the settled answer, never the answer bytes.

A Wasm hook module whose exported memory declares a minimum above the guest-memory budget is refused at validation.
A negative guest-reported outcome length or pointer is a bounded ABI violation, never an empty success.

An event has at most one handler.
If you need fanout, put an external event gateway behind one destination.
Production compilation refuses an event without a handler (`breg.event.delivery-required`), because
there is no supported outbox consumer API.
A Proposal lifecycle hook is declared on the Action under `execution.proposal.hooks`, selects native
transitions, and uses its own value-free event schema; it is separate from Record field
projections.
A module may add hooks to an existing Record type, and it cannot replace an event another module
owns.

### Conditions

`when` uses `type: fields` for Record mutations.
It takes these tests, all optional and combined with AND:

- `changed`, fields whose value must change. Every listed field must change.
- `changedAny`, two or more fields of which at least one must change
- `beforeEquals`, field values required before the change
- `afterEquals`, field values required after the change
- `beforeIsNull` and `afterIsNull`, fields that must be unset before or after the change

Use `changed` when every listed field must change, and `changedAny` when a change to any one of them
is enough. For example, this condition fires only when both `status` and `reviewer` change:

```yaml
when:
  type: fields
  changed:
    - status
    - reviewer
```

This condition fires when `phone`, `email` or both change:

```yaml
when:
  type: fields
  changedAny:
    - phone
    - email
```

`changedAny` needs at least two fields: for one field, use `changed`. A condition cannot set both
`changed` and `changedAny`.
Both are valid only with the `patched` trigger.

At least one test is required when `when` is present, and every field must be declared on the Record
type.
A comparison value is a scalar of the field's declared type; state an unset value with
`beforeIsNull` or `afterIsNull`, because `null` is refused as a comparison value.
A condition cannot name an encrypted field.
Which tests are valid depends on the trigger: `created` accepts `afterEquals` and `afterIsNull`,
`patched` accepts every test, including `changed` and `changedAny`, and `tombstoned` accepts `beforeEquals` and `beforeIsNull`.
BReg evaluates the condition against the validated before and after snapshots, and an invalid
combination fails compilation.

### Alert on reads

`trigger: read` raises an event for a read, not a change.
It needs `profiles`, the access profiles whose reads produce the event, each declared in the
project, and it takes `projection: []` and no `when`.
`profiles` is refused on any other trigger, and the compiler refuses a read trigger that breaks
these rules (`breg.hook.read-trigger-invalid`).
The event is written with the subject access log entry, so declare it on a Record type with
[`accessLog`](../breg-access-log/). A read hook on a Record type without `accessLog` is refused
(`breg.disclosure.read-hook-access-log-required`), because it would never fire.

The event data carries `recordType`, `recordId`, `revision`, `trigger: read`, an empty `values`, and an
`access` object with `accessProfile`, `operationId`, `requester`, `purpose`, `accessReason` and
`accessLogEventId`.
It carries no record value, so the alert says who read and why without disclosing what.
`accessLogEventId` links the alert to the subject access log entry of the same read.
BReg stores one event per record read per hook in the transaction that writes the access log, so a read it
logs is a read it alerts on.

### Classification and destinations

BReg derives the event classification from the highest-classified field that the projection or a
condition uses, and you do not restate it.
A condition can disclose information through whether an event fires, even when its field is not in
the payload, so activation requires the runtime destination to permit the full derived
classification.
The destination can never add to the compiled projection.
Proposal lifecycle events use a closed value-free binding projection.

Destination URLs, TLS policy, network policy, and HMAC keys are deployment configuration, and the
project refers only to a logical destination id.
The runtime configuration must bind the exact compiled destination set.
It can tighten operational ceilings and can never widen delivery authority.
If the runtime finds a delivery inventory that differs from the governed source, it refuses the
Record change with `503 service.unavailable`; that is a package or server fault, not invalid caller
input.

## Bind each destination

Add a `destinations.hooks` block to the runtime file, with one entry per destination the package
names:

```yaml title="runtime.yaml"
destinations:
  hooks:
    contact-events:
      origin: https://receiver.example.org
      path: /events
      networkProfile: production-https
      dnsFamily: dual-stack-strict
      allowedPrivateCidrs: []
      hmacSha256KeyRef: secret:file/contact-events-key
      classificationCeiling: internal
      deliveryCeilings:
        attemptTimeoutMilliseconds: 1000
        maximumAttempts: 3
```

`bregctl check <project> --runtime-config runtime.yaml` checks the binding's shape offline. The
runtime refuses to start when the bindings and the package disagree: every destination the package
names needs a binding, and a binding for a destination the package does not name is refused.

Some values need a decision:

- `classificationCeiling` must cover the classification of every field the event sends. A binding
  cannot add fields to a payload.
- `production-https` refuses `localhost` and every name under it. Use `loopback-development-http`
  only for a receiver on a development host.
- For a receiver on a private network, list its address ranges in `allowedPrivateCidrs`. Use
  `dnsFamily: ipv4-only` only on a network without IPv6.
- For a receiver behind a private certificate authority, or one that requires mutual TLS, name the
  PEM material with `tls.caBundleRef` and `tls.clientIdentityRef`.
- `deliveryCeilings` may tighten what the package compiled, never widen it. This example tightens
  both values.

`bregctl --format json explain events <project>` shows what the package compiled for each
delivery: by default five attempts of five seconds each, retried after 1, 2, 4, and 8 seconds, then
a dead letter. Retries keep the event id and idempotency key. Any `2xx` response acknowledges a
delivery; redirects, timeouts, and every other response are retried. The
[configuration reference](../../reference/breg-configuration/) lists every key, including
`retention.hookPayloadRetentionDays`.

Run `bregctl doctor` after every change to this block. It opens each binding, key file included,
before the runtime starts.

## Provision the shared key

Generate the HMAC-SHA-256 key as an owner-only file in the runtime's secret directory, as the user
that runs `breg`:

```sh test-skip="writes into the deployment host's secret directory"
(umask 077; openssl rand -hex 32 | tr -d '\n' > /var/lib/breg/secrets/contact-events-key)
```

Give the receiver the same bytes through its own secret store. BReg signs with the file's bytes
exactly as written, so the receiver loads the 64 characters as its key and does not decode them.
The key must be at least 32 bytes, and the file a regular file owned by the user that runs `breg`
with mode `0400` or `0600`; `doctor` and startup refuse anything else.

## Build the receiver against a sample

`bregctl hook sample` prints the request one event produces, without a runtime or a database,
so you can build the receiver before the registry serves:

```sh test-skip="needs your own registry project with an event"
bregctl hook sample ./my-registry --event contact-created-v1
```


The event type, data schema, registry id, and projected field names come from your project.
`bregctl` fills in the rest: fixed placeholder identifiers, time, and signature, and a synthetic
value for each projected field (here `"name":"x"`). `--format json` returns the same request as a
document with the method, request target, headers, body, and canonical body.

The receiver should:

1. Verify `X-Registry-Signature` against the exact request bytes, in the signing-input order the
   [API reference](../../reference/breg-api/#events-and-webhooks) defines.
2. Check `X-Registry-Delivery-Time` for freshness. The Node, Python and Rust verifiers the client
   packages ship refuse a delivery time more than 300 seconds from the receiver clock, either way,
   with the code `stale-delivery`. A receiver that sets no window gets that default. Pass
   `maxSkewSeconds` (Python `max_skew_seconds`, 1 to 3600) for another window, or
   `callerEnforcedFreshness: true` (Python `caller_enforced_freshness=True`) to bound the time
   yourself. Coordinator's own receiver stays at 30 seconds until its signed delivery format
   changes, which is stricter than the verifier we ship and safe to run beside it.
3. Read the Record type from `data.recordType` and the record from `data.recordId`, and order
   events for one record by `data.revision`.
4. Deduplicate by `Idempotency-Key`, and answer `2xx` only after it has durably recorded the event.

## Settle local hooks before go-live

Activation checks local Rhai and Wasm deliveries across captured revisions.
Pending or leased work and operator-replayable dead letters block activation while their payload
is retained and unexpired. This applies to Record and Proposal hooks, even when the successor
leaves the program unchanged. Other terminal metadata, including non-replayable dead letters,
can remain, as can metadata whose payload expired or was erased.
`bregctl plan` and `apply` report `apply.hooks.local-retained` before maintenance starts.
Both name the retained count and compiled delivery identifiers, bounded to 100 deliveries.
A truncated count means at least that many remain.
Plan changes nothing; apply records a refused activation.
The current package stays ready and no target is pinned, so this refusal needs no reconciliation.

If ongoing activity keeps replenishing the queue, you can choose a quiet window.
Use your existing service or container supervisor to stop every `breg` process serving this
registry database, keep all replicas stopped, and wait for process termination.
This stops both HTTP serving and background producers; routing HTTP traffic away alone leaves
background producers running. The registry is unavailable while these processes are stopped.
The quiet window is optional: concurrent work remains retained, and apply rechecks the guard and
refuses activation when local work remains.

Drain runs reviewed Rhai or Wasm handlers in the `bregctl` process using the runtime database
connection. Use the active package's runtime file, handler assets and Wasm execution configuration,
with its configured destination secrets and audit destination and secrets available to that process.
For encrypted fields, provide the existing field-encryption provider and keys.
You can run the CLI on a different authorised operator host with access to those assets, secrets,
and the runtime database. Keep the same secret ownership and field-key custody restrictions as
the serving process, including restrictions on the local-only file key provider.
Drain does not need a migration credential. Listing, replay and discard do not enable the
execution-only Wasm runtime or field-encryption service.

Run the bounded drain:

```sh test-skip="needs the active package runtime file and database"
bregctl --format json hook drain \
  --runtime-config /etc/breg/runtime.yaml \
  --max-attempts 100 --timeout-seconds 30
```

The command attempts only due local work under the active package's existing authority.
That covers all the local work there is: activation refuses while local work that can still run
is retained under any activation, so no earlier package's local work survives a go-live.
It stops when no local attempt is due, after the attempt budget, or at the time budget.
`completedAttempts` counts settled attempts and `stopReason` explains the stop.
`remaining` contains the bounded retained count, compiled delivery identifiers, and `truncated` flag.
A time-budget stop can leave an unfinished lease for normal recovery.
URL deliveries, live leases, retries that are not due, and dead letters remain for their existing
worker or operator recovery; drain never replays or discards them.
The attempt budget accepts 1 to 1000 and defaults to 100; the time budget accepts 1 to 300 seconds
and defaults to 30. A drain can itself produce further governed hook work, so one bounded call
does not guarantee an empty queue.

If work remains, inspect it with `hook list`.
Wait for a live lease or scheduled retry, or correct a runtime failure and explicitly replay
eligible work. Replay uses the captured handler under the active package.
If recovery requires changing governed handler code, assess and explicitly discard that retained
work before activating the successor, as described in the recovery section.
Run `plan` again before [applying the successor](../breg-changes/#activate-the-successor).
Apply checks the retained work again, because new work can arrive after a plan.
If you chose a quiet window, keep the serving processes stopped through drain and apply.
After successful activation, restart them on the successor as the activation procedure describes.
If you defer cutover, restore service on the still-active package.

## Answers that arrive after go-live

A URL receiver can acknowledge an event with `2xx` after a compatible successor goes live.
That acknowledgement does not mean the registry accepted the proposed change in its answer.
An uncommitted proposal captured under the previous activation and first classified after go-live
is dead-lettered with
`proposalCode: hook.proposal.package_unavailable`.
For this superseded-activation refusal, `proposalSummary` names the captured and active activation
IDs, and `replayEligible` is false.
Derive the change again from a fresh event; replay cannot give an old answer successor authority.
An identical answer whose change already committed can still recover its original receipt without
applying the change twice.
A proposal classified before go-live keeps its applied, refused, or dead-lettered result
when delivery completion succeeds afterward. The predecessor worker cannot claim new work.

If the worker is interrupted before recording the proposal result and there is no committed
receipt to recover, final-lease recovery records `worker-interrupted` without a proposal code.
Explicit replay can remain eligible when the captured operator permission, product proposal
policy, active binding, and retained, unexpired payload allow it. A replay sends the event
to the receiver again, and that is all it can do for a delivery captured before go-live.
Any proposal the receiver returns is classified under the successor and dead-lettered as
`hook.proposal.package_unavailable`, so the replay never applies a change.
Inspect the recovered delivery before deciding whether to replay or discard it.

## Inspect and recover deliveries

`hook list` shows deliveries that are pending, leased, dead-lettered, or expired:

```sh test-skip="needs a deployed registry's runtime file and database"
bregctl --format json hook list --runtime-config /etc/breg/runtime.yaml --limit 50
```

```json
{
  "apiVersion": "id.registrystack.org/formats/breg/ctl-report/v1alpha1",
  "kind": "BRegCtlReport",
  "ok": true,
  "command": "hook list",
  "deliveries": [
    {
      "eventId": "<event-id>",
      "deliveryId": "events.contact.contact-created-v1.webhook",
      "generation": 1,
      "state": "dead-lettered",
      "attempt": 5,
      "payloadAvailable": true,
      "payloadExpiresAt": "<expiry-time>",
      "replayEligible": true,
      "discardEligible": true,
      "bindingActive": true,
      "deadLetterReason": "http-non-success"
    }
  ]
}
```

The list carries delivery metadata and no record values; `--limit` accepts 1 to 100. Delivered
events are left out, so an empty list does not prove a delivery arrived: confirm that from the
receiver's own records.

A delivery that runs out of attempts becomes a dead letter with a `deadLetterReason`, and its
payload is retained. `replayEligible` is true only when the captured policy permits replay, its
exact binding is still deployed (`bindingActive`), the payload is retained, and the proposal outcome
permits replay. Payloads are kept for
`retention.hookPayloadRetentionDays`, 7 days by default and at most 30, and erased earlier once
every delivery that needs them has arrived.

After you fix the receiver, replay the dead letter with the ids and generation from the list:

```sh test-skip="needs a dead letter from a deployed registry"
bregctl hook replay --runtime-config /etc/breg/runtime.yaml \
  --event-id <eventId> --delivery-id <deliveryId> --expected-generation <generation>
```

```text
Queued the delivery for replay.
  event id     <event-id>
  delivery id  events.contact.contact-created-v1.webhook
  generation   2
```

Replay keeps the event id and issues a new generation and idempotency key. If you are not sure
whether the receiver acted on an earlier attempt, check its state before replaying. A replay whose
generation is stale, whose payload has expired, or whose destination is no longer bound is refused
with `hook.operation.refused`; list again and use the current generation.

### Discard deliveries pinned to an old binding

When you correct a binding while deliveries still wait under the old one, `doctor` reports
`startup.hook.retained-bindings`, and those deliveries show `bindingActive: false`. The
runtime will not start until they are gone: restore the old binding until they drain, or discard
each one whose `discardEligible` is true:

```sh test-skip="needs a delivery from a deployed registry"
bregctl hook discard --runtime-config /etc/breg/runtime.yaml \
  --event-id <eventId> --delivery-id <deliveryId> --expected-generation <generation>
```

:::danger[Discard prevents every future attempt]
A discarded delivery is never sent again, and discard does not undo a request the receiver may
already have accepted.
:::

```text
Discarded the delivery. It cannot be replayed.
  event id     <event-id>
  delivery id  events.contact.contact-created-v1.webhook
  generation   3
```

The row stays in the list as `expired`, without its payload. A delivery whose lease is still live
is refused: wait for the lease to expire and list again.

The webhook commands connect to PostgreSQL with the runtime file's database settings. If the
database presents a certificate from a private certificate authority, name its PEM bundle with
`database.caBundleRef` in the runtime file.

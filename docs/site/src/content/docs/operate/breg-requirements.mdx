If you are planning a production Base Registry Engine (BReg) deployment, this is what you provide,
what the product does not depend on, and what stays your job once it runs. None of it is needed for
[your first registry](../../tutorials/first-breg/), which starts disposable versions of everything
on your machine.

## What you provide

- **PostgreSQL 17 or newer**, with two login roles: a migration role that owns the schema and
  applies packages, and a runtime role the serving process uses. The migration credential is what
  authorizes an activation; packages carry no signature, and the database records every activation
  in its own ledger. A registry with spatial fields
  also needs PostGIS 3.5 or newer. Your administrator installs the extensions the
  runtime checks for; neither role creates a schema, an extension, or a role. SQLite is not a
  target.
- **A host for one process.** The runtime is a single binary that verifies one package and serves
  its REST API against one database. It runs on the platforms in
  [platform support](../../explanation/known-limitations/#platform-support).
- **HTTPS in front of it.** The process trusts no host or forwarded header; your reverse proxy or
  ingress terminates TLS, and generated links use the public origin you configure.
- **A token issuer.** BReg verifies bearer tokens from one OpenID Connect issuer and issues none.
  Configure a compatible OAuth issuer for this role.
- **A backup of the database before every activation.** A destructive change goes further: its
  activation is refused unless you name each backup the reviewed migration requires, in a
  binding file that states the database it came from and the backup file's digest. The product
  restores nothing itself, and it refuses to serve a logically restored copy until an operator
  adopts it, as
  [back up and restore the database](../breg-changes/#back-up-and-restore-the-database)
  describes. That check reads the cluster's system identifier through `pg_control_system()`,
  which PostgreSQL grants to every role; on a managed service that withholds it, the check falls
  back to the database object identifier alone and still starts.

## What it does not need

The modeling loop needs none of this. Authoring commands check, explain, and generate a project
with no database open, so an author can work on a laptop until the project is ready to test.

## How it ships

Each release publishes the `breg` runtime and the `bregctl` authoring tool as reproducible
binaries, with an installer that verifies them against the release checksums and installs them
together or not at all. Each release also publishes a container image on the distroless
`cc-debian13` base, which has no shell or HTTP client, with pinned Debian `libc6` and `libssl3t64`
packages laid over it. The image runs as the non-root user with UID 65532, holds the `breg`
runtime and the `bregctl` operator tool with their licenses, and starts
`breg --runtime-config /etc/breg/runtime.yaml`; you run `bregctl` by overriding the entrypoint.
The runtime configuration, package, secrets, and migration credential are deployment inputs you
mount read-only. The image carries no writable directory, so file audit needs a writable volume
mounted at `audit.path`, and it declares no health check: probe `GET /health` from outside the
container.

The release ships no Helm chart, Compose file, or hosted offering. Scheduling, TLS termination,
and the proxy in front of the listener are yours. The Docker use in the first tutorial is a
loopback development path, not a deployment pattern.

## What stays your job

**Secrets.** You hold two database credentials, the audit hash key, the cursor secret, one key per
webhook destination, and the issuer's key material when you pin a static key set. The runtime
file names each of them by reference and refuses one that carries a value inline.

**Every production change.** A one-line access widening takes the same path as a new registry: a
production check, a test run against a schema-test database with real tokens, packaging, and a
`plan` and an activation under the migration credential in each environment. A change the tooling classifies as
additive needs no more; one it marks for review needs a reviewed migration with a rehearsal, and a
destructive one names its backup. A failed activation holds the database in maintenance until you
reconcile or restore.

**The audit journal.** Each audited request writes minimized entries through a file or stdout writer.
You ship the streams from every process to append-only storage and verify delivery before local
retention expires. The product does not provide tamper evidence.

**Retention and erasure.** Erasing a record's history is a bounded operator command with no undo.
It removes at most 10,000 revisions per transaction. Restoring snapshot coverage afterwards
verifies every live row in one transaction that holds writes until it commits. Retained webhook
payloads expire after a configurable number of days, at most 30.

## Capacity

No throughput or latency figure is committed. A load-test harness ships with the product and its
own note asks you to run it on a representative Linux host before you cite a number. What is
bounded by construction is easier to state: every request, lock, and migration runs under an
operator-set timeout, the connection pool has a maximum size, spatial responses are capped and
refuse rather than truncate, and metrics label sets are closed. The runtime applies no request rate
limit of its own, so a registry that admits anonymous reads belongs behind one.

## Stability

Base Registry Engine is pre-1.0 Beta software. Its APIs, package formats, and deployment
contracts may change between minor releases, and each break carries a `BREAKING:` entry in
`products/breg/CHANGELOG.md` at the release tag you operate. A pilot holds three conditions: run
`breg` under a process supervisor that restarts it on failure, as
[Serve the container image](../breg/#serve-the-container-image) describes; treat the holder of the
migration credential as the activation gate, because packages carry no signature and most access
changes apply with no reviewed evidence, as
[Test and package the successor](../breg-changes/#test-and-package-the-successor) describes; and
keep to the verified deployment profile, which leaves out Kubernetes, as
[Activate from the image](../breg/#activate-from-the-image) describes.

Registry Stack is pre-1.0, so a minor release may contain breaking changes, announced in the
release note, and security fixes land only in the latest release; see
[API stability](../../reference/api-stability/) and the
[support window](../../security/support-window/). The runtime configuration format is at its first
alpha version. The security posture is fixed: the product's invariant matrix names each package,
role, row, and claim boundary with the negative test that enforces it.

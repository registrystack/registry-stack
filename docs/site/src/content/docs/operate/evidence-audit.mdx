You run a deployed Registry Evidence service and answer for what it disclosed. For every admitted
operation, Evidence writes one entry before any source read and one with its outcome, and refuses
the request when an entry cannot be written. An authenticated request refused at authorisation
writes one refusal entry and no access attempt. Authentication failures, malformed requests,
invalid selectors, and rate-limited requests write nothing. The log
is tamper-evident only once it reaches the append-only storage you ship it to.

## Choose where the audit log is written

You author the `audit` block in the deployment target, not in the runtime file. The
[production example target](https://github.com/registrystack/registry-stack/blob/main/products/evidence/reference/deployment-targets/environments/production/evidence/target.yaml)
declares:

```yaml
audit:
  hashKeyRef: secret:file/evidence-audit-hmac
  hashKeyVersion: 1
  path: /var/lib/registry-evidence/production/evidence.jsonl
```

`evidencectl package` splits the block. `audit.hashKeyRef` and `audit.hashKeyVersion` name the
audit master and its version, and go into the governed package. `audit.destination`,
`audit.path`, `audit.rotateBytes`, and `audit.retentionDays` go into the candidate's
`runtime.yaml`:

- `destination: file`, the default, appends to `path` and acknowledges an entry only after it is
  synced to disk. It rotates the active file at `rotateBytes` (100 MiB by default) and deletes
  sealed files older than `retentionDays` (90 by default).
- `destination: stdout` writes one flushed line per entry on standard output, and refuses `path`,
  `rotateBytes`, and `retentionDays`: durability, rotation, and retention belong to your
  collector. Operational records go to standard error.

One process writes one file. The writer holds `<path>.lock` for its whole life, so give each
replica its own `path` or use `stdout`. The directory must belong to the service user and be
unwritable by group or others.

:::caution[Archive chained logs before the first start]
A runtime that wrote the older chained format left `<path>.<sequence>` segments and an active file
behind. The writer refuses to start on a chained active file, and retention deletes old sealed
segments under the same names. Archive them to append-only storage and point `path` at a
directory that holds no old segments.
:::

## Preflight the audit path

Before you start a candidate, prove its audit file sits on your persistent storage:

```sh
evidencectl doctor \
  --runtime-config /srv/registry-evidence/candidate/runtime.yaml \
  --require-audit-under /var/lib/registry-evidence
```

When every dependency is reachable, doctor prints `Dependency preflight passed for` the runtime
file and a `Proof:` line. When the audit path resolves outside the root, cannot be
resolved, or the root does not exist on the host, it refuses with
`evidence.deployment.audit-outside-root` and exits 3. A `stdout` destination is refused here,
because it has no local file.

A candidate staged beside the instance it replaces meets the running writer's lock:

```text
Evidence runtime dependency preflight refused <runtime-file>
error[evidence.deployment.audit-unavailable] <runtime-file>
  runtime audit initialization failed: another process holds the single-writer lock beside the audit file; stop it before starting this one
  next: Make the audit destination writable by this user and free of another writer, as the message says.
1 error, 0 warnings in <count> files
Next: Another Evidence instance holds this audit destination's writer lock. To check a candidate staged beside it, rerun doctor with --without-audit-lock; otherwise stop the other writer first.
```

Rerun with `--without-audit-lock`. Doctor still checks the destination's ownership, modes, write
access, and final entry, and its `Proof:` line says a second writer is not detected.
See [`evidencectl doctor`](../../reference/cli/evidencectl/doctor/) for every option.

## Ship audit to append-only storage

Tamper evidence comes from where entries end up, not from the file the service writes. Once the
service runs:

1. Pick a store the Evidence host cannot rewrite: object storage with an object lock, a
   write-once archive, or a log pipeline whose retention the Evidence operator account cannot
   change.
2. With `destination: file`, ship every sealed file. Rotation renames the active file to
   `<path>.<sequence>`, an ascending eight-digit number, and the next number is kept in
   `<path>.seq`. Copying a sealed file is safe at any time. Ship each one before
   `audit.retentionDays` deletes it, so set that key in the target's `audit` block longer than
   your shipper can fall behind. Key archived files by host or replica as well as by name: two
   replicas use the same names, and numbering restarts when `<path>.seq` is lost.
3. If a crash left `<path>.torn`, the bytes of an unfinished entry that belongs to no
   acknowledged entry, inspect it, archive it with the sealed files, and then remove it. The
   writer refuses a later torn line while the side file is still there.
4. With `destination: stdout`, point your collector at the store; each line on standard output
   is one entry.
5. Verify, as part of your backup, restore, and incident procedures, that entries reach the
   store: pick an operation and find its entries there by their shared `correlation`.

Restore audit history into that store, never into the live audit directory. The
[operator contract](https://github.com/registrystack/registry-stack/blob/main/products/evidence/OPERATOR-CONTRACT.md#audit-destinations-rotation-and-retention)
is the authority for these rules.

Never rename, edit, or truncate the active file while the service runs: the writer treats that as
tampering, and every later audited request fails closed until a restart. A `stdout` destination
stalls when its collector stops reading. After the writer has held one entry for 5 seconds,
audited requests are refused and readiness fails; standard error carries
`audit stream has held one entry past the write deadline`, and later
`audit stream took the entry it was holding` once the collector reads again. Restore the collector
rather than restarting, which can lose queued entries.

## Read what an entry establishes

Each entry is one JSON line. New authorised operations use
`registry.evidence.audit/v3` or `registry.evidence.audit.request-batch/v3`;
authorisation refusals keep `registry.evidence.audit.authorization-refusal/v2`.
Retained authorised `/v2` entries remain readable history. Entries are not chained. The
[`audit-event.schema.yaml`](https://github.com/registrystack/registry-stack/blob/main/products/evidence/contracts/audit-event.schema.yaml)
and
[`request-batch-audit-event.schema.yaml`](https://github.com/registrystack/registry-stack/blob/main/products/evidence/contracts/request-batch-audit-event.schema.yaml)
contracts define the members and each phase's closed decision values. The record's `phase` says
what the entry establishes:

| Record phase | What it establishes | What it does not establish |
|---|---|---|
| `access-attempt` | Authentication and the complete authority path were accepted before source credentials or data were touched. In a current `/v3` record, `executionBounds` captures the positive operation, deadline, and response-byte limits that govern the acquisition. | That the source returned a record or that anything was released. The bounds carry no endpoint, credential, secret, or source value. |
| `disclosure-release` | The named concepts were serialised and durably recorded before the response bytes left the service. | That the source fact was true or that the caller used it correctly. |
| `denial` | The operation was refused, either as an authenticated authorisation refusal or as an evaluation that decided no answer. | The rejected requirement, selector, or source value behind it. |
| `transient-failure` | An admitted operation failed in one closed, value-free class a retry may clear. | The selector, source value, or credential that triggered it. |

Requester and subject handles are keyed pseudonyms prefixed `hmac-sha256:v<version>:`, derived
from the audit master: protected correlators, not anonymous values. A record never
carries a raw selector, a released or source value, or an access token. No supported tool turns a
person's identifier into their access history, so do not expose the audit master or raw records
to build one. Read audit entries from the configured destination.

The closed `executionBounds` object appears only on current `/v3` access attempts. Its members are
`maximumDataOperations`, `acquisitionDeadlineMilliseconds`, and `maximumResponseBytes`. Evidence captures the
effective values from the immutable runtime configuration before credential resolution or source
effects. When `sourceAcquisition` is omitted, the values are `5`, `30000`, and `1048576`.
Terminal `/v3` records and retained `/v2` records omit the object. The deadline gates admission to
the terminal release append, the disclosure-begin boundary. If that append is admitted before expiry,
it completes without cancellation and the exact audited bytes may return after expiry; this is not
a hard wall-clock response cutoff.
A signed source's verified `validUntil` remains an independent data-validity bound.

## Expose the public check route

`POST /v1/public-check` is experimental (`v1alpha1`) and unauthenticated, and it reads registry data.
A holder, or anyone the holder shows a certificate to, scans a QR code and a static page calls the
route to learn whether the certificate is `valid`, `suspended`, `revoked` or `expired`.
Declaring `publicCheck` in the package does nothing until a target authority activates it; until
then the route is not registered and answers like any unknown route.
The synthetic public check example project in the repository carries the package sources, a pack and a page.

Source failure before the check code is compared (transport, timeout, budget, an error status from
the Source, or protocol, which includes a facts-schema refusal and an extract-script failure) answers
`503 source.unavailable`.
The only statuses are `valid`, `suspended`, `revoked` and `expired`; anything else fails closed.

### The proxy rule

Run Evidence bound privately and put a path-restricted proxy in front of it.
The proxy must:

1. Forward exactly `POST` and `OPTIONS` on `/v1/public-check`.
   The proxy refuses everything else: the fragment below answers 403 to other methods on that path,
   and any other path matches no location and answers 404.
2. Apply a per-client request limit and a cap on the whole path, and answer 429 when either is
   exceeded.
   Evidence has no rate limiter on this route and never reads a client address.
3. Keep no log with client addresses for that location, access or error.
   Nginx writes the client address into error-log lines, including `limit_req` refusals and upstream
   errors.
4. Terminate TLS on the check origin that is printed on the certificate.

The following nginx fragment illustrates the rule.
It is not shipped configuration; adapt it to your proxy.

```nginx
limit_req_zone $binary_remote_addr zone=check:1m rate=10r/m;
limit_req_zone $server_name zone=check_all:1m rate=300r/m;
limit_req_status 429;
limit_req_log_level warn;
location = /v1/public-check {
    limit_except POST OPTIONS { deny all; }
    limit_req zone=check burst=5 nodelay;
    limit_req zone=check_all burst=50 nodelay;
    access_log off;
    error_log /dev/null crit;
    proxy_pass http://127.0.0.1:8090;
}
```

The location-level `error_log /dev/null crit;` keeps `limit_req` refusals (logged at `warn` in the
fragment) and upstream errors out of any file.
The operator gives up the proxy-side upstream error lines for this path; Evidence still audits and
logs its own failures.

Run the check on its own Evidence instance, with only this definition and its own keys.
That keeps institutional signing keys out of an internet-reachable process and stops a flood on the
public path from using admission slots that relying services need.
A shared instance works but is not recommended.

### Write a pack for a public check

The runtime compares the check code only after the Source returns a record, and a number with no
record never reaches a record-content failure.
If a pack refused one record's content before that comparison (a facts-schema refusal, a script
throw), the resulting 503 would show that the record exists.
A register that answers an error status for one record but not for an unknown number has the same
effect.
The example pack therefore keeps its facts schema to member types, declares a record whose number
does not exactly match the requested number as no-match, and checks record content in the
derivation, which runs after the comparison.
There only a caller holding the right check code sees a failure.

Give the Source's inputs schema a pattern for the number, as the example pack does.
A number the inputs schema refuses answers `400`, and the page says the number or code is not in the
expected format.
A number it admits but that the route cannot place in a request path segment (a `/`, a `%`, a dot
segment) answers `503` instead, and the page says the service is unavailable.
If your certificate numbers can contain `/`, bind the number to a query parameter rather than a path
segment.

### Generate check codes

The system that issues the certificate generates the code and stores it on the record; Evidence does
not.
Use 15 bytes from the operating system's random source, encoded as base32 (RFC 4648) without padding.
15 bytes is 120 bits and encodes to exactly 24 characters.

```python
import base64
import secrets

check_code = base64.b32encode(secrets.token_bytes(15)).decode("ascii")
assert len(check_code) == 24 and "=" not in check_code
```

Do not derive the code from the certificate number or from any key.
It is a capability the holder hands to the checker.
A record issued before codes existed has no code and can never match.

{/* Evidence: products/evidence/contracts/public-check-request.schema.yaml pattern;

### Print the QR URL

Print this URL in the QR code, and print the check origin as text beside it so a reader can tell a
genuine paper from one pointing at a look-alike page:

```text
https://check.example.org/#n=<url-encoded number>&c=<code>
```

The number and code are in the URL fragment (after `#`).
Browsers do not send the fragment to the static host, so the host's access log never holds a code.
The page removes the fragment from the address bar and the history entry once it has read it.
The page always shows a two-field form, which a fragment fills in and submits.
The page strips spaces and hyphens from the code before sending it.

{/* Evidence: products/evidence/examples/public-check/page/check.js parseFragment, normalizeCode,

### Serve the page

Serve the example page from any static host on the check origin, or from the same origin as the
proxy.
Then:

- Set the `check-endpoint` meta value in `index.html` to your route, for example
  `https://check.example.org/v1/public-check`.
- Set `connect-src` in the page's Content-Security-Policy meta to that origin.
- Evidence answers `OPTIONS` on the route and sends `Access-Control-Allow-Origin: *`, so the page can
  live on a different origin from the proxy.
  The route carries no cookie or token, so the wildcard grants nothing a plain HTTP client lacks.

The page has no dependencies and no build step.
It writes every value from the network with `textContent`, stores nothing, and loads nothing from a
third party.

## Read a public check entry

The unauthenticated public check route, `POST /v1/public-check`, writes its own entries. Each one
is a platform audit entry with the schema `registry.evidence.audit.public-check/v1`, and the
[`public-check-audit-event.schema.yaml`](https://github.com/registrystack/registry-stack/blob/main/products/evidence/contracts/public-check-audit-event.schema.yaml)
contract defines it. The route has no requester, actor, client, or grant, so no record names one,
and none carries a response protection, an Evidence identifier, or a signing key, because the
public answer is never signed. A check refused before admission (a malformed body, a document
number that fails the selector profile or the Source inputs schema, or a rejected request limit) writes nothing. The entry
phase is `request` for the access attempt and `response` for every other phase, and the entry
`correlation` is the record's `operation`.

| Record phase | Decision | What it establishes |
|---|---|---|
| `access-attempt` | `authorized` | The subject resolved and the record was durably accepted before the Source was read. `executionBounds` carries the effective acquisition budget. |
| `disclosure-release` | `released` | The exact answer bytes were serialised and durably recorded before they were returned. `disclosedConcepts` names exactly the status and fields concepts. |
| `denial` | `no-match`, `ambiguous`, `unresolved`, `fact-missing`, or `code-mismatch` | The check ended in a miss, with a `safeErrorCategory`. |
| `transient-failure` | `dependency-failure` or `evaluation-failure` | An admitted check failed in a value-free class, with a `safeErrorCategory`. A retry may clear a `dependency-failure`. An `evaluation-failure` can be a package fault that a retry does not clear. |

All five miss decisions are answered to the caller with one identical `404 resource.not-found`
problem. The log is where you tell them apart: `code-mismatch` also covers a stored check code that
is absent or malformed, and it is visible to you only. A document number that passes the selector
profile and the inputs schema but that the Source binds to a path segment it cannot occupy is admitted, so it leaves an `access-attempt` record
and a `transient-failure` record with `dependency-failure`, and the caller gets
`503 source.unavailable`; the Source is never contacted.

Every record carries `assuranceProfile`, `eventId`, `occurredAt`, `operation`, `phase`,
`requirement`, `bundleRevision`, `authorityRevision`, `effectiveGrantDigest`, `purpose`,
`subjects`, `sourceId`, `adapterId`, `decision`, `reason`, and `durationMilliseconds`. `reason` is
always `public-check.activated`. `subjects` holds the one presented selector bundle as a role, a
selector profile, and a keyed `selectorBundlePseudonym`. Repeated checks of one document number
share that pseudonym, so you can see one number tried repeatedly without the log holding the number.

A record never carries the presented or stored check code, the document number or any selector
value, request headers, a client address, an inbound trace context, a source value or fact, or a
credential. An audit append failure answers `503 service.unavailable` and releases nothing.

## Rotate the audit master

Every pseudonym carries `audit.hashKeyVersion` in its prefix, so entries under different masters
stay distinguishable in one log and rotation needs no fresh audit path.

:::danger[Raise the version with the master]
The runtime cannot tell a replacement master from the one it replaces. New bytes under an
unchanged `hashKeyVersion` silently change every pseudonym under the same prefix.
:::

1. Generate a fresh, independent master into a new secret file (written `0600`):

   ```sh
   evidencectl keygen secret --output /run/registry-evidence/secrets/evidence-audit-hmac-2
   ```

2. In the deployment target, set `audit.hashKeyRef` to `secret:file/evidence-audit-hmac-2` and
   raise `audit.hashKeyVersion` by one. Record both versions in your change record.
3. Repackage the deployment target into a new candidate and install it with the target-host steps
   in [Build and deploy a Registry Evidence project](../../tutorials/build-and-deploy-evidence-project/).
   Route traffic only after readiness succeeds.
4. Keep the previous master under its secret controls for as long as pseudonyms from its version
   must stay recomputable for an investigation.

The audit master must differ from the subject-binding secret and the signing key.

## Production decisions

Besides where the audit log is written, a production deployment settles the choices below in its
deployment target, its Adapter packs, and its runtime file. None of them changes Evidence's public
schemas. Each key and its bounds are in the
[Registry Evidence configuration reference](../../reference/evidence-configuration/).

### Caller authentication

`authentication.oidc` names one issuer and one audience, and every inbound token must match both.

- `tokenTypes` admits `at+jwt`, `application/at+jwt`, or both.
- `algorithms` admits one to three of `EdDSA`, `ES256`, and `RS256`. A token signed with any other
  algorithm is refused.
- `principalClaim` names the claim that identifies the caller. A token without that claim is
  refused, and no other claim stands in for it.
- `allowedClients` is `unrestricted`, which admits every client the issuer vouches for, or a list
  that admits exactly those clients.
- `requiredScopes` is `unrestricted`, which applies no scope gate, or a list of scopes every token
  must carry. Under `unrestricted`, a correctly signed token for this audience that carries no
  scopes passes this gate.

{/* Evidence: crates/registry-evidence/src/config.rs, OidcAuthenticationConfig and

    extract_context and claim_paths_are_exact_and_do_not_fallback;

### Subject authority

Each authority profile declares its basis as `statutory`, `organizational`, `consent`, `delegated`,
or `explicit-request`, and lists the requester tags a caller's token must carry. Adding a tag
narrows a profile. A token that carries an actor claim matches only a `delegated` profile, and
`actorKind` can restrict a profile to `human`, `agent`, or `service` callers.

A grant binds one requirement, one purpose, an audience origin, and the requirement's whole
subject-role set. Permissions are never combined across grants, so one grant must cover a whole
request. A request that matches no path, or more than one, is denied. A profile whose subjects use
`authenticated-grant` must also name its `requesterClients` and the `grantSourceIssuer` it trusts.

{/* Evidence: products/evidence/contracts/bundle.schema.yaml, authority-profile (kind, actorKind,
    requesterTags, requesterClients, grantSourceIssuer, grants). The deny on zero or multiple paths
    is stated with its evidence in security/evidence. */}

### Selector profiles and value origins

A selector profile is a closed set of up to 16 fields with a combined size cap of at most 8,192
bytes. Each field is a `string`, `date`, `uuid`, `integer`, `boolean`, or `controlled-code`. Evidence applies
no case folding, normalisation, transliteration, or fuzzy matching to a supplied value.

Each grant fixes where a subject role's selector values come from:

- `request` takes them from the caller's request.
- `authenticated-context` refuses caller values and reads them from the verified token claims the
  grant names in `valueClaims`.
- `authenticated-grant` reads the same claims and also requires a verified task grant from the
  trusted issuer that matches exactly one authority profile.

A requirement's `grantCeiling` caps the origins any deployment target may grant. Every subject role
has cardinality `one` in Version 1, so a requirement resolves exactly one subject per role.

{/* Evidence: products/evidence/contracts/bundle.schema.yaml, selector-profile, selector-field,
    grants[].subjects[].valueOrigin, grantCeiling, and subjectRoles[].cardinality. */}

### Source contract and acquisition posture

Each source pins an Adapter pack by id, version, and digest, and names one route. Its acquisition
posture is the reviewed minimisation claim: `source-derived`, `field-projected`, or
`record-transformed`, from strongest to weakest. A source cannot claim a stronger posture than the
pinned route's contract. A source that applies its own projection must claim `record-transformed`.

{/* Evidence: products/evidence/contracts/bundle.schema.yaml, source (pack, route, posture,

    captured_pack_refuses_a_stronger_posture_than_the_selected_route;

### Source authentication

Each source connection names one authentication kind: `none`, `basic`, `static-authorization`,
`static-api-key`, `oauth2-client-credentials`, or `oauth2-private-key-jwt`.

- Every secret is a reference, never a value in the bundle.
- Client credentials travel in the Authorization header or the token request body, never in a
  query string.
- `oauth2-private-key-jwt` signs a client assertion with a private key instead of sending a shared
  secret, and requires `clientAssertionAudience`.
- The runtime file can bind a client certificate and key to a source endpoint as `mtlsIdentity`.
- Outside the local assurance profile, a source endpoint with `none` authentication needs an
  `mtlsIdentity`. Plain HTTP is admitted only under the local profile, at a canonical numeric
  loopback origin.

[Rotate credentials and trust](../advanced/rotate-credentials-and-trust/#rotate-source-credentials-or-trust)
covers changing them.

### Requirements and Evidence Types

Each enabled requirement names one Evidence Type URI, which every assertion issued for it carries,
and one to 16 concepts. Two requirements in one bundle cannot share an Evidence Type: a duplicate
refuses the bundle at startup. The mapping of assertion fields to CCCEV is frozen, so a deployment
chooses which requirements to enable, not how they map.

{/* Evidence: products/evidence/contracts/bundle.schema.yaml, requirements[].evidenceType;
    crates/registry-evidence/src/config.rs, RequirementConfig validation and the unique Evidence
    Type check in check_rules_with_named_map_collisions;
    products/evidence/contracts/cccev-field-mapping.yaml, status frozen and Evidence.isConformantTo. */}

### Observation time zone

A requirement whose derivation uses `legal_local_date` or `legal_local_time` resolves them from the
evaluation instant in its `observationTimezone`, an IANA time zone name. Omitting the key resolves
both in UTC, so near midnight the derived date can differ from the local legal date. An
unrecognised name refuses the bundle.

{/* Evidence: products/evidence/contracts/bundle.schema.yaml, requirements[].observationTimezone;
    crates/registry-evidence/src/config.rs, observation timezone check in RequirementConfig
    validation; crates/registry-evidence/src/kernel.rs, evaluation_context. */}

### Signing key custody

The runtime file's `signer` binds the process to its private key. `local-jwk` reads the key from a
file secret and is accepted only under the `local` assurance profile. `production` and
`evidence-grade` require `transit`, which calls a Vault or OpenBao Transit signing proxy over a
local Unix socket. The runtime passes the proxy no provider token, so token custody and renewal stay
with the proxy.

A Transit signer pins one exact `keyVersion`, so a provider-side rotation cannot replace the key
behind an unchanged key id. It keeps no fallback key: a call that exceeds
`attemptTimeoutMilliseconds` fails the request, and no unsigned assertion is issued.
[Rotate credentials and trust](../advanced/rotate-credentials-and-trust/#rotate-registry-evidence-signing-material)
covers key rotation.

{/* Evidence: products/evidence/contracts/runtime.schema.yaml, signer and the signer deployment rule;
    products/evidence/contracts/bundle.schema.yaml, signing ("no unsigned fallback exists");
    products/evidence/contracts/jws-profile.yaml, Vault/OpenBao Transit key path;
    crates/registry-platform-crypto/src/lib.rs,
    transit_signer_uses_the_common_vault_openbao_es256_wire_contract. */}

### Relying-party trust

Evidence serves its public key set at `/.well-known/evidence/jwks.json`, but that route is not a
trust anchor. A relying party pins the provider's keys through its own configuration. The
`evidence verify` command takes the pinned key set as its complete trust set and opens no network
connection. A deployment may add `signing.certificateChainFile`, a PEM chain certifying the active
key, so relying parties can validate it against their own trust anchors. Without it, credentials and
the served key set carry no `x5c`.

After a rotation, keep the previous public key in `signing.publishedPublicJwkFiles` for at least
the maximum assertion validity plus the verifier clock skew. Evidence does not enforce that period. Relying parties must add the new key to their pinned set to
verify assertions it signs.

{/* Evidence: products/evidence/contracts/bundle.schema.yaml, signing.jwksPath,
    signing.certificateChainFile, and signing.publishedPublicJwkFiles;
    products/evidence/contracts/verification-policy.schema.yaml, command (jwks, network). */}

### Existence disclosure is fixed

`existenceDisclosure` accepts only `collapse-unresolved` in Version 1. A subject that is absent,
ambiguous, or found with inconsistent inputs returns one identical public problem, so no
requirement can be configured to reveal which. The
[Registry Evidence security model](../../security/evidence/) states the timing limit that remains.

{/* Evidence: products/evidence/contracts/bundle.schema.yaml, requirements[].existenceDisclosure. */}

### SQLite extract publication

A source that reads a SQLite extract declares, in its Adapter pack, a logical extract profile and
`maximumExtractAgeSeconds`, from one second to 30 days. The runtime file's `sourceExtracts` binds
each profile to one absolute file path, and startup refuses a missing or unused binding. The extract
states its own publication time and publisher in a one-row metadata table. Its age is measured from
that publication time, not from the file's modification time. An extract older than the maximum age
fails the request as a dependency failure that carries no profile, path, or publisher. The operator
diagnosis names only the extract profile.

The deployment decides who publishes each extract, how often, and to which path, so that
publication stays inside that age. It must also ensure that no process changes a mounted extract
while the source is live.

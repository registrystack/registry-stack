Use this procedure to update a single-node deployment created by
`registryctl deploy generate`. The update unit is a fresh, verified generated package,
not an edited Compose file or an image tag.

The procedure has a manual abort boundary. Before the first successful product
acceptance advances durable anti-rollback state, an operator can stop the candidate
and restart the intact current package. After that acceptance, rollback is unsupported.
The allowed outcomes are to complete the forward update, restore a coherent recovery
group at the same or newer accepted sequence, or replace the affected instance
identity.

The generated `RUNBOOK.md` remains the package-specific authority for service order and
locked commands. This procedure does not certify that a target release is compatible
with an operator's data or deployment.

## Prerequisites

- Keep the current package intact, including `binding.yaml`, `operator/`, `generated/`,
  its approved set, and its externally recorded closure digest.
- Verify the target Registryctl binary and matching release lock with the target
  release's published authenticity and integrity evidence.
- Obtain a reviewed target approved set for the same signed project and environment
  identity as the current package.
- Read the release notes for every applicable product and state transition.
- Complete [Back up and restore a deployment](../backup-and-restore/) for every affected
  `relay-public-state` and `consultation-state` recovery consistency group.
- Keep enough capacity for an isolated candidate package and an encrypted duplicate of
  operator files.
- Remove any unresolved `generated.previous/` only after confirming that every affected
  lane accepted the current sequence and the retention decision is recorded. Package
  generation refuses to overwrite an unresolved preceding closure.

## Prepare a fresh candidate

Run a read-only verification of the current package:

```sh
registryctl deploy verify \
  --package ./registry-stack-current \
  --approved-set ./approved-set.current.v1.json \
  --check-operator-files
```

Compare its reported closure digest with the external record.

Use an operator-owned copy mechanism to create an isolated candidate. The copy contains
secrets, so keep its ownership, mode, encryption, and access boundary unchanged:

```sh
cp -a ./registry-stack-current ./registry-stack-candidate
```

Install the verified target Registryctl and matching release lock. Regenerate only the
candidate package:

```sh
registryctl deploy generate \
  --approved-set ./approved-set.target.v1.json \
  --output-dir ./registry-stack-candidate
```

The command verifies the existing managed package, renders the target closure without
activating it, retains the preceding generated closure as
`registry-stack-candidate/generated.previous/`, and prints a new closure digest. Record
that digest outside both package directories.

Verify the candidate against its approved set, recorded closure digest, and operator
file inventory:

```sh
registryctl deploy verify \
  --package ./registry-stack-candidate \
  --approved-set ./approved-set.target.v1.json \
  --expected-closure-sha256 "$CANDIDATE_CLOSURE_SHA256" \
  --check-operator-files
```

`CANDIDATE_CLOSURE_SHA256` is the exact value recorded from generation. An absent,
unrecorded, or mismatched value is a manual abort.

Read `registry-stack-candidate/generated/RUNBOOK.md`. Render the candidate Compose
model without resolving or printing environment values:

```sh
cd ./registry-stack-candidate
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  config --no-interpolate --no-env-resolution --quiet
```

Return to the parent directory before continuing. Do not edit `generated/`, substitute
mutable image tags, or combine a binding change with this product or evidence update.

## Verify current state before shutdown

From the current package root, follow its `generated/RUNBOOK.md`. Verify the effective
Compose model, run the four owner-isolated stagers, and run all three read-only state checks:

```sh
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  config --no-interpolate --no-env-resolution --quiet
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  run --rm --no-deps registry-relay-public-stage-secrets
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  run --rm --no-deps registry-relay-consultation-stage-secrets
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  run --rm --no-deps registry-notary-stage-secrets
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  run --rm --no-deps registry-postgresql-stage-secrets
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  run --rm --no-deps registry-relay-public \
  'product-action' 'relay-public' 'verify_state'
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  run --rm --no-deps registry-relay-consultation \
  'product-action' 'relay-consultation' 'verify_state'
docker compose \
  --env-file generated/compose.empty.env \
  -f generated/compose.yaml \
  run --rm --no-deps registry-notary \
  'product-action' 'verify_state'
```

Abort before shutdown if package, operator-file, bundle, anchor, Compose, or state
verification fails. Resolve a coherent current-state failure before attempting the
update.

## Preview, accept, verify, and start the candidate

Keep all current services running while you stage candidate operator files and preview every
affected product lane.
The preview actions verify the later candidate without changing durable anti-rollback state.
Do not stop any service unless every preview succeeds.

In the literal generated order below, keep current services running through all three preview
commands.
After those previews succeed, remove externally reachable traffic before the `stop` command and
keep the source and write freeze required by the pre-update recovery groups.
Run the sequence from the candidate package root:

```sh
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml run --rm --no-deps registry-relay-public-stage-secrets
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml run --rm --no-deps registry-relay-consultation-stage-secrets
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml run --rm --no-deps registry-notary-stage-secrets
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml run --rm --no-deps registry-postgresql-stage-secrets
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml -f generated/compose.initialize.yaml run --rm --no-deps registry-relay-public-preview-state
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml -f generated/compose.initialize.yaml run --rm --no-deps registry-relay-consultation-preview-state
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml -f generated/compose.initialize.yaml run --rm --no-deps registry-notary-preview-state
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml stop
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml -f generated/compose.initialize.yaml run --rm --no-deps registry-relay-public-accept-state
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml -f generated/compose.initialize.yaml run --rm --no-deps registry-relay-consultation-accept-state
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml -f generated/compose.initialize.yaml run --rm --no-deps registry-notary-accept-state
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml run --rm --no-deps registry-relay-public 'product-action' 'relay-public' 'verify_state'
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml run --rm --no-deps registry-relay-consultation 'product-action' 'relay-consultation' 'verify_state'
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml run --rm --no-deps registry-notary 'product-action' 'verify_state'
docker compose --env-file generated/compose.empty.env -f generated/compose.yaml up --detach --wait --wait-timeout 120
```

Each `accept_state` action uses the locked audit-before-mutation path.
The first successful acceptance that advances durable anti-rollback state is the manual abort
boundary.
Before that boundary, restart the intact current package if the services were stopped.
After that boundary, only complete the forward update, restore a coherent snapshot at the same or
newer accepted sequence, or replace the affected instance identity.
Keep traffic blocked while the updated services and product canaries are evaluated.
Do not configure an automated rollback across this boundary.

## Verify the updated deployment

- Confirm the expected services are healthy in `docker compose ... ps`.
- Verify PostgreSQL and consultation Relay before admitting a Notary caller.
- Exercise one authenticated canary for each affected public, consultation, evaluation,
  issuance, and status path.
- Exercise every affected SnapshotExact materialization because global readiness does
  not prove execution-time freshness.
- Confirm audit records extend the retained chains without logging their values.
- Confirm every affected lane reports the target accepted sequence before ending the
  change window.

Only after those checks and the operator's soak period may the operator remove the
candidate's `generated.previous/` and retire the intact current package under the
retention policy.

Package verification proves the generated closure, release projection, and structural
operator-file boundary. It does not prove application compatibility, database
freshness, canary coverage, or safe rollback after product acceptance.

## Abort or recover

Before the manual abort boundary, leave the current package running when a preview fails.
If the current services were stopped after successful previews but no acceptance completed,
restart the still-intact current package with its `generated/RUNBOOK.md`.
Verify the current closure and run all three current `verify_state` actions before its ordinary
`up`.

After the boundary, never start the older closure or restore a pre-update accepted
sequence. Choose one of these manual recovery paths:

1. Complete the forward update after correcting the candidate's operator-controlled
   dependency.
2. Restore a complete `relay-public-state` or `consultation-state` group at the same or
   newer accepted sequence, then run all three read-only `verify_state` actions.
3. Provision a new instance identity, review and sign every affected lane, generate a
   new package, and follow first installation.

An anti-rollback rejection is a correct fail-closed result. Do not delete, copy, edit,
or reinitialize anti-rollback state to make an older bundle or closure start.
Reinitializing the same identity is not recovery.

## Troubleshooting

| Symptom | Required response |
|---|---|
| Candidate generation rejects the package as unmanaged or modified | Discard the candidate copy and begin again from the intact verified current package |
| Candidate generation reports an unresolved `generated.previous/` | Resolve the prior change and retention decision; do not delete the closure to bypass the guard |
| Candidate verification reports a closure or approved-set mismatch | Keep the candidate offline and regenerate it from the intended verified inputs |
| `verify_state` rejects the target as older | Keep services and traffic stopped; use a signed target with a higher sequence or restore a coherent same-or-newer group |
| PostgreSQL or consultation Relay does not become healthy | Keep Notary and external dependants stopped; restore or repair the coherent private recovery group |
| A failure appears after product acceptance | Do not restart the previous closure; complete forward, restore same-or-newer coherent state, or replace the instance identity |

You have a checked Document Store project and its package digest, from
[Check your first Document Store project](../../tutorials/first-documents/). Serve it behind your
TLS edge, change it, and recover what it holds. The Registry Document Store is pre-1.0 and held
out of releases, so build `documents` and `documentsctl` from the same source checkout.

## What you provide

- **PostgreSQL 17 or newer**, with one database and two login roles: a migration role that owns
  the schema, and a runtime role that serves. `documentsctl apply` uses the first and grants the
  second what serving needs.
- **Your OpenID Connect issuer.** Every route except `GET /health` takes a bearer access token it
  signed; the token's client, scopes, and actor kind select one access profile in the project.
- **A content verifier**: an HTTP endpoint that receives each stored version's bytes and answers
  approved or rejected. It speaks the same protocol as the Base Registry Engine (BReg)
  [external attachment verification](../../reference/breg-configuration/#external-attachment-verification).
- **A TLS-terminating proxy** in front of the listener, which binds `127.0.0.1:8116` in the
  starter.
- **Optionally, an S3-compatible bucket** for the bytes, used by this deployment alone. Without
  one, the bytes are held in PostgreSQL.

## Write the runtime file

Start from the `runtime.example.yaml` that `documentsctl init` wrote. Every path in it is absolute,
the file may not be writable by its group or by others, and every credential is a `secret:`
reference to a declared provider. The choices that matter most:

| Key | Decide |
| --- | ------ |
| `identity.databaseId` | A name for the one database this deployment owns. The service refuses a database recorded for another. |
| `package.root` and `package.expectedDigest` | The package directory, and the digest `documentsctl package` printed. |
| `storage.type` | `database` (at most 16 MiB per version) or `s3` (at most 64 MiB). The first upload pins the choice: a later start under another backend or bucket is refused. |
| `contentVerification` | `type: http` with the verifier's `url`, `authorizationRef`, and `policyId`. `type: disabled` approves everything and is accepted only on a development loopback listener. |
| `retention.receiptRetentionDays` | How long a retry with the same `Idempotency-Key` gets the same answer. Seven days is a placeholder for your retention schedule to approve. |

Size the host for about 512 MiB of document memory on top of the process's own needs. Uploads,
downloads, and verification attempts share one transfer budget of at least 256 MiB; a transfer
that finds no room is refused with `service.unavailable` and `Retry-After`, and is never queued.

Check the file before you deploy it:

```sh
documentsctl check --project PROJECT --runtime-config /etc/registry-documents/runtime.yaml
```

Add `--environment` to check `${VAR}` values against the current environment. The
[configuration reference](../../reference/documents-configuration/) lists every key.

## Apply and start

```sh
documentsctl package PROJECT --output /srv/registry-documents/package
documentsctl plan --runtime-config /etc/registry-documents/runtime.yaml
documentsctl apply --runtime-config /etc/registry-documents/runtime.yaml \
  --operator-reference CHANGE-123 --backup SNAPSHOT-ID
documents --runtime-config /etc/registry-documents/runtime.yaml serve
```

`plan` reports what `apply` would change and writes nothing. `apply` applies the schema, records
the package digest as active, and grants the runtime role; applying the active package again
records nothing. `serve` never applies the schema. It refuses to start on a database with no
active package, an active package other than the configured one, or a schema from another
release, and names every finding before it binds the socket.

`documentsctl status --runtime-config FILE` shows the active package and the activation history.
The operator commands write their own audit journal beside the service's.

## Change the project

A grant keeps the policy terms it was issued under. To change a policy, a profile, or a hook, edit
`documents.yaml`, check it, and run `package`, `plan`, and `apply` again, then restart `serve`.
Changing only the runtime file needs only a restart, with one exception: a delivery not yet sent
keeps the destination binding it was captured under, and `serve` refuses to start while one waits on
a binding the file no longer holds. To move a hook to a new URL or key, add a destination under a new
id, point the hook at it, apply, and restart; remove the old entry once its deliveries have been sent,
dead-lettered, or expired.

Changing the verifier's `url` or `policyId` changes its binding. At the next start, every version
verified under the old binding is suspended and verified again under the new one, so plan the
change for a quiet period.

## Replay a stuck verification

A verifier that cannot answer is retried for about seven days, then the job is dead-lettered and
its version stays `pending`. List the stuck jobs, oldest first, with their generation:

```sh
documentsctl verification list --runtime-config /etc/registry-documents/runtime.yaml
```

When the verifier answers again, return one job to pending:

```sh
documentsctl verification replay --runtime-config /etc/registry-documents/runtime.yaml \
  --version-id VERSION-ID --expected-generation GENERATION
```

A generation other than the current one is refused, so two operators cannot replay the same job
twice. A version whose removal was requested, or whose bytes are being or have been erased, is
refused too. No HTTP route lists or replays a job.

## Removal and erasure

A custodian removes a document with `POST /documents/{documentId}/erasure`. In one transaction
the Store stops release, revokes every active grant, and marks the version `erasure-pending`,
due after the policy's `cleanupGraceHours`. A sweep every minute erases what is due; a rejected
version's bytes are erased the same way. The record of the document, its versions, and grants
stays.

What "erased" reaches depends on the storage:

| Storage | After erasure |
| ------- | ------------- |
| PostgreSQL | The content row is deleted. Its bytes stay on disk until PostgreSQL overwrites the pages or `VACUUM FULL` rewrites the table. |
| S3 | The object is deleted, and a read must then answer 404 before the version reads `erased`. |

Backups, archived WAL, replicas, and bucket versions keep erased bytes for as long as you keep
them. Set their retention to the longest period your retention schedule allows erased content to
survive; nothing in the runtime file controls it.

An erasure job retries for about seven days before it dead-letters, and its version stays
`erasure-pending`; the sweep never retries it on its own. `documentsctl erasure status` shows
whether erasure is active or paused and counts the versions in their grace, those due, and the
dead-lettered jobs. `documentsctl erasure list` names the dead-lettered jobs with their
generation, and `documentsctl erasure replay`, with the same `--version-id` and
`--expected-generation` options as a verification replay, returns one to pending once the
storage answers again.

To halt erasure without stopping the service, set `cleanup.erasure: paused` and restart. The
service still serves, still takes removal requests, and logs a warning at startup. Due versions
wait until you set it back to `active` and restart.

## Events

A project's `hooks` send after-commit events to a URL destination the runtime file binds under
`destinations.hooks`, with its HMAC key. Each hook lists the `policies` whose documents it hears
about, and hears nothing about a document under any other policy. Three triggers exist:

| Trigger | Sent when |
| ------- | --------- |
| `document-version.ready` | A verdict makes a version releasable |
| `document-version.rejected` | A verdict rejects a version |
| `document-grant.changed` | A grant is issued or revoked, including each grant a removal revokes |

An event carries identifiers, the version digest, and the policy, never content, a label, a media
type, a name, or a subject. A grant event also carries the kind of actor and the grant's `expiresAt`.
A grant reaching its expiry sends nothing; the receiver reads the lapse from `expiresAt`. A failed
delivery is retried with backoff up to the destination's `maximumAttempts` and never delays or
undoes the change it reports. An observer cannot answer with a change of its own: the Store refuses
it and records the refusal.

## Restore from a backup

:::caution
A restore brings back grants revoked and documents removed after the backup. Repeat those changes
from the audit file before you serve traffic again.
:::

1. Set `cleanup.erasure: paused` and stop traffic at your edge.
2. Restore the database, and the audit file from the same point if you have it.
3. Start the service. It erases nothing while paused.
4. Compare the restored state with the audit file, and repeat every revocation and removal newer
   than the backup. A repeated removal gets a fresh due time.
5. On S3, if you restored the database and not the bucket, delete the objects uploaded after the
   backup: no row names them, so no sweep reaches them. The
   [product README](https://github.com/registrystack/registry-stack/blob/main/products/documents/README.md#restore-drill)
   gives the object key layout.
6. Set `cleanup.erasure: active` and restart. The next sweep handles everything that became due.

Rehearse this drill before you rely on it.

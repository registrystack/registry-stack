Use this procedure to add or change an integration, consultation, claim, credential profile,
environment, or fixture in an existing governed Registry Stack deployment.

## When to use this

Use this flow after a product baseline has been approved and deployed.
It preserves unchanged product lanes and identifies the lanes that need new review and signatures.

A typical new external evidence integration changes:

- `relay-consultation`, which owns source access and minimized consultation output
- `notary`, which owns claims, disclosure, rendering, issuance, and signing

`relay-public` changes only when the public records surface or its materialization also changes.
Registryctl computes the affected set from the reviewed authored and generated closures.

## Ownership and trust boundary

The country implementer owns authored project changes.
Independent lane owners retain signing authority for their product lanes.
The approved-set owner assembles verified lane outputs, and the deployment operator owns package
binding, adaptation, activation, state, and recovery.

Registryctl computes affected lanes, but it does not approve a semantic change, sign for a lane
owner, or activate a product.

## Prerequisites

Keep:

- The current authored project unchanged in version control or a separate review copy
- The current `approved-set.v1.json`
- The deployed package and its complete `generated/` closure
- The operator-owned `binding.yaml`, `operator/`, and optional `operator-override.yaml`
- The product-lane-specific anti-rollback state and recovery evidence

Do not modify the only copy of the approved project or package.
Do not edit Compose or generated product configuration to add evidence.

## Verify the current baseline

Verify the existing package and bind the expected approved set:

```sh
registryctl deploy verify \
  --package ./registry-stack \
  --approved-set ./approved-set.v1.json
```

Proceed only when the report identifies the expected package, ownership state, and approved-set
digest.
Resolve a stale, adapted, or invalid result before combining that condition with an evidence
change.

## Make the authored evidence change

Edit the smallest authored surface that expresses the new contract:

1. Update the integration and its wholly synthetic fixtures.
2. Update the evidence service consultation, claims, disclosure, or credential profile when
   Notary behavior changes.
3. Update the environment only for deployment-specific source origins, secret references, trust,
   and resource bindings.
4. Keep consumer eligibility, ranking, workflow, and action policy outside the evidence service.

Do not widen an origin, method, path wildcard, credential, output, source-call count, byte limit,
or deadline merely to make a fixture pass.
Record the source-owner evidence required to change a source version from `unverified` to
`tested`.

## Test and review the change

Run the complete offline fixture set:

```sh
registryctl test
```

The report must pass the changed positive and negative fixtures and the derived
authorization-before-source and output-minimization cases.
Fixture evidence remains synthetic and does not prove live interoperability.

Validate the complete effective plan:

```sh
registryctl check --explain
```

Review the source authority, secret consumers, input mapping, outputs, claims, disclosure, and
bounds.

Compare with the approved set:

```sh
registryctl review compare --against ./approved-set.v1.json
```

The comparison reports value-free semantic change classes and the exact affected lanes.
Comparison is pure.
It does not sign, activate, deploy, contact a source, or modify the project.

Use `--fail-on-change` only when automation treats any detected change as a negative domain
result.
Without that predicate, a successfully reported change exits with status `0`.

## Build only the reviewed replacements

Build against the same approved set:

```sh
registryctl build --against ./approved-set.v1.json
```

The build emits signing inputs only for lanes whose lane-scoped input or cross-lane interface
changed.
It rejects a lane set that disagrees with the reviewed comparison.

Do not copy a generated signing input into another lane.
Each input marker binds the lane, product, project, environment, stream, instance, trust domain,
and reviewed closure.

## Sign each affected lane

The owning signer signs each affected lane into a new digest-specific directory.
For a typical consultation and claim change:

```sh
registryctl trust bundle sign \
  --lane relay-consultation \
  --input ./.registry-stack/build/production/signing-inputs/relay-consultation \
  --anchor ./trust/relay-consultation.anchor.json \
  --key file:./keys/relay-consultation.private.jwk \
  --against ./approved-set.v1.json \
  --output-dir ./approved/relay-consultation-next
registryctl trust bundle sign \
  --lane notary \
  --input ./.registry-stack/build/production/signing-inputs/notary \
  --anchor ./trust/notary.anchor.json \
  --key file:./keys/notary.private.jwk \
  --against ./approved-set.v1.json \
  --output-dir ./approved/notary-next
```

Use an explicitly supported key locator.
The private key remains outside arguments as a value, output, reports, and retained artifacts.
Each signing action verifies the preceding lane entry, advances the sequence, and binds the
previous configuration hash.

Do not sign or replace `relay-public` when the reviewed affected set excludes that lane.

## Assemble the next approved set

Assemble the replacements with verified unchanged lanes:

```sh
registryctl trust approved-set assemble \
  --from ./approved-set.v1.json \
  --relay-consultation ./approved/relay-consultation-next \
  --notary ./approved/notary-next \
  --output-file ./approved-set.next.v1.json
```

The assembler verifies every carried-forward and replacement lane.
It rejects an omitted affected lane, a replacement for an unaffected lane, mixed project or
environment identities, and incompatible cross-lane interface digests.

The unchanged `relay-public` entry remains reusable because its lane-scoped inputs and bound
interfaces did not change.
The next approved set is an operator handoff, not product activation authority.

## Regenerate and verify the package

Regenerate the existing verified package:

```sh
registryctl deploy generate \
  --approved-set ./approved-set.next.v1.json \
  --output-dir ./registry-stack
registryctl deploy verify \
  --package ./registry-stack \
  --approved-set ./approved-set.next.v1.json
```

Registryctl preserves `binding.yaml`, `operator/`, and `operator-override.yaml`.
It stages the new `generated/` closure and retains one verified
`generated.previous/` closure until the update runbook confirms the new accepted sequence.

Copy or publish the complete generated closure.
Do not transfer selected YAML files.
Adding evidence does not require changing a parent application's Compose include.

## Follow the generated update runbook

Use `generated/RUNBOOK.md` for the exact package-specific sequence.
The runbook performs read-only package, model, bundle, anchor, secret, and product-state checks
before stopping a reachable service.

Before the first product accepts a higher sequence, you may abort and restore the verified
preceding generated closure.
After any product advances anti-rollback state, continue forward, restore a coherent snapshot at
the same or newer accepted sequence, or replace the instance.
Do not automatically roll back to an older sequence.

The runbook stops externally reachable dependents before a potentially incompatible private-lane
change, starts and verifies affected dependencies, then resumes dependents.
A mixed consultation Relay and Notary contract must fail before source access.

## Verify the result

After the update:

1. Run `registryctl deploy verify` against the next approved set.
2. Run each product-owned `verify_state` action from the generated runbook.
3. Check value-free health and readiness.
4. Exercise an authorized synthetic evaluation with an operator-owned request file.
5. Confirm the changed claim and minimized output without recording source values.
6. Confirm the parent Compose file is unchanged.

Remove `generated.previous/` only when the generated runbook says the new acceptance is complete.

## Expected evidence

Retain value-free evidence for:

- The passing offline fixture report
- The redacted effective plan and approved-set comparison
- The exact affected lane set
- Each replacement lane's signed bundle verification
- The next approved-set digest
- Package verification before and after activation
- Product-owned state verification at the accepted sequence

Keep source values, credentials, private keys, and private deployment details outside the review
record.

## What this proves

This procedure proves that the authored change was tested against synthetic observations,
reviewed against the selected approved set, signed by each affected lane owner, assembled into a
compatible approved set, and packaged under the reported ownership boundary.

It does not prove live-source interoperability, correctness for an untested source version,
country acceptance, or an operator adaptation the verifier cannot model.

## Roll back or recover

Before any product accepts the higher sequence, stop and restore the complete preceding generated
closure when the update runbook permits it.
After acceptance, continue forward or restore a coherent recovery consistency group at the same
or newer accepted sequence.
Do not reset anti-rollback state or automatically activate an older bundle.

For an orchestration edge case outside the managed renderer:

If the managed renderer cannot express an orchestration need:

1. Keep the managed package unchanged.
2. Copy or export a separate package for operator adaptation.
3. Apply a Compose override or translate the deployment plan.
4. Run `registryctl deploy verify` to learn which invariants remain established.
5. Operate the adapted package with Docker or the target orchestrator under operator ownership.

Registryctl does not merge arbitrary YAML, overwrite an adapted package, or claim managed
freshness for behavior it cannot model.

## Escalate

Stop the update and involve the owning product and security reviewers when:

- Authorization denial performs token or source work
- A mixed Relay and Notary interface reaches source access
- A secret or private key appears in retained output
- Product state reports an unexpected lane identity, sequence, anchor, or configuration hash
- Package verification reports `invalid`
- Recovery cannot restore one coherent product-lane consistency group

## Troubleshooting

| Symptom | Cause | Fix |
| --- | --- | --- |
| Comparison marks an unexpected lane affected | A lane-scoped input or cross-lane interface changed. | Inspect the value-free change classes and the corresponding authored files before signing. |
| Build emits no replacement | The normalized reviewed closure is unchanged. | Do not invent a signing or deployment update. Retain the approved set. |
| Assembly rejects a carried-forward lane | Its identity, closure, anchor, or interface no longer matches the next set. | Rebuild and sign every genuinely affected lane. |
| Regeneration reports an adapted package | An operator-owned or generator-owned file changed the ownership boundary. | Follow the reported in-place safety decision or generate into a separate directory. |
| Product state rejects the update | The lane identity, sequence, configuration hash, or pinned anchor does not advance the accepted state. | Restore the pre-acceptance package or construct a reviewed forward update. Do not reset anti-rollback state. |

Use this runbook when you move a deployment of Base Registry Engine (BReg), Registry Casework,
Evidence, Registry Scheduling, and Registry Messaging to a new release, or take it out of service.
Each product's own guide carries its upgrade command; this page gives the order across products,
the version rule that order enforces, and what each product must leave behind when it is retired.

## Run one release everywhere

Every Registry Stack artifact of a release shares one version: the runtimes, their adopter tooling,
and the Rust, Node.js, and Python clients. Run the same release on every side. There is no
supported version-skew window, between two runtimes or between a client and a runtime, and a
rolling upgrade that mixes releases is not supported:

- **Casework pins the BReg context contract.** The read-only provider checks the exact registry
  revision, context contract, and Proposal identity. A changed contract requires re-pairing; see
  [plan, apply, and serve](../../casework/#plan-apply-and-serve).
- **Adopter tooling is checked.** `evidencectl` refuses an `evidence` or `bregctl` binary of
  another version.
- **Clients are not checked.** Clients send no version, and runtimes accept any caller. Pre-1.0
  client and wire contracts can change incompatibly between releases, so upgrade each client to
  the same release as the runtime it calls.
- **BReg activation is not rolling.** Once `bregctl apply` activates a successor, every `breg`
  process still running the previous package fails readiness until it restarts onto the successor.
  Plan the restart as part of the activation, not after it.

Read the target release's state and package requirements before applying. v0.42.0 starts a
fresh baseline for every product that keeps state: BReg, Casework, Scheduling, and Messaging carry
no state forward from v0.41.0, and Evidence requires its normalized authored project and target.
An upgrade from v0.41.0 is therefore a fresh install beside the deployment it replaces. You stop
each v0.41.0 runtime, keep its database untouched for reconciliation and rollback, and apply the
v0.42.0 package to a fresh database. No product converts v0.41.0 state in place. Casework,
Scheduling, and Messaging refuse a database a pre-1.0 release wrote at `plan`, `apply`, and
startup, naming the fresh-install recovery. BReg names no such refusal, so point it only at a
fresh database. See [Upgrades and state](../../../reference/api-stability/#upgrades-and-state).

## Upgrade in this order

BReg goes first, because Casework and Evidence both read it. Pair Casework with the resulting
exact BReg context contract before starting its runtime. Evidence and its wallet-facing front end come next. Scheduling and
Messaging read none of them and upgrade independently, before the clients. Read the target
release's notes for every deployed product. Complete their required drains and outcome
reconciliation before you stop that product's v0.41.0 runtime, because work left in its database
is not carried to the fresh one, and make the listed project and runtime-file changes in its
upgrade step. Rehearse the whole sequence on a restored copy first, as
[Run a disaster-recovery drill](../back-up-and-restore/#run-a-disaster-recovery-drill) describes.

Version-specific procedures in released notes apply to that release's contracts. They do not
establish a conversion path for a retired model. On native Linux, require glibc 2.34 or newer.
The four product installers start every staged Linux binary before selecting the new toolset,
so a binary that cannot run leaves the installed toolset selected.

1. **Back up every database.** Take the BReg and Casework `pg_dump`s, and the Scheduling and
   Messaging ones when they run. Copy those products' packages and runtime files, and keep the
   previous release's binaries. The v0.41.0 databases themselves are the way back, so leave them
   in place and unchanged; the dumps protect them against damage. Each product's step below
   refreshes its dump after its v0.41.0 runtime stops, so the copy you keep holds its final
   writes. See [Roll back](#roll-back).
2. **Stop `evidence-oid4vci`**, when it runs. Its outstanding offers end here; see
   [Serve](../../../configure/evidence-oid4vci/#serve).
3. **Pause and drain Evidence traffic** for every question that reads BReg, or pause the whole
   instance when you cannot drain one question at a time. Keep the previous Evidence candidate.
4. **Upgrade BReg.** v0.42.0 carries no BReg state forward from v0.41.0: records, revision
   history, change requests, and pending webhook deliveries stay in the v0.41.0 database. Before
   you stop it, close the import authorities still open with `bregctl import-authority close`, and
   check `bregctl webhook list` when receivers must see pending deliveries, because they stop with
   the runtime. Stop every v0.41.0 `breg`, take a final `pg_dump` of its database, and keep the
   database, package, runtime file, audit
   files, and binaries unchanged. Rewrite the project as `recordTypes` and Actions, then test and
   package it with the v0.42.0 tooling. In the runtime file, move retention windows into the
   top-level `retention` block and rename a `taskGrantStatus` entry's `caseworkResource` to
   `statusResource`; each old key is refused with `config.removed-key` naming its new path. Point
   the runtime file at a fresh UTF8 database on PostgreSQL 17 or later, prepared as
   [Provision PostgreSQL](../../breg/#provision-postgresql) describes, and activate the package
   there with `bregctl plan` and `bregctl apply --initial`, as
   [Activate and serve](../../breg/#activate-and-serve) describes. A first activation requires a
   database that has never held a package, so pointing it at the v0.41.0 database fails; give it a
   fresh one instead. Start every `breg` on the exact active package and verify readiness. Load the
   records the registry must hold through
   [Validate the input](../../breg-data/#validate-the-input) and
   [Import with a checkpoint](../../breg-data/#import-with-a-checkpoint).
5. **Upgrade Casework.** v0.42.0 Casework installs its complete schema as baseline version 100
   and refuses a v0.41.0 database: `caseworkctl plan` and `apply` report
   `casework.activation.beta-schema`, and readiness and startup refuse with the same
   fresh-database instruction. Reviews open in the v0.41.0 database are not carried forward, so
   before you stop it, finish them or cancel them through each bound producer's supported
   interface, and record any that remain. Stop the v0.41.0 runtime, take a final `pg_dump` of its
   database, and keep the database, package, runtime file, and audit until its work and accountability obligations are resolved.
   Rewrite the project in the v0.42.0 format; `caseworkctl check` names each old spelling and its
   replacement. Pair the v0.42.0 BReg context export with `caseworkctl provider pair` and verify
   the exact contract before packaging. Point the runtime file at a fresh database prepared as
   [Provision PostgreSQL](../../casework/#provision-postgresql) describes, run
   `caseworkctl plan --runtime-config FILE` and `caseworkctl apply --runtime-config FILE`, then
   `caseworkctl doctor` with the same runtime file, package, and database. Require readiness
   before resuming staff traffic; see [plan, apply, and serve](../../casework/#plan-apply-and-serve).
6. **Upgrade Evidence.** Author the normalized `evidence.yaml`, target, and target authority
   for the current tooling; retired split authoring documents are refused. Re-import changed
   BReg source exports into that project, review the source changes, and run check and fixtures
   before packaging the candidate with its explicit target. Run
   `evidence check --runtime-config FILE --require-runtime-dependencies` on the target host,
   adding `--without-audit-lock` while the previous instance still runs. Stop the previous
   runtime, start the matched `evidence`, and verify a fresh synthetic assertion before
   restarting its wallet-facing adapter.
7. **Upgrade Scheduling**, when it runs. The current release installs its complete schema as a
   fresh baseline and refuses a database a pre-1.0 release wrote at `plan`, `apply`, and startup.
   Holds and appointments recorded in the previous database are not carried forward: retain that
   database, its package, runtime file, and audit journal for reconciliation. Dropping booked
   appointments this way is acceptable only before production.

   Before the cut, record every appointment that must still be honoured. `schedulingctl` has no
   export command, so take a `pg_dump` after the previous runtime stops, and have each booking
   product list its own appointments with `GET /v1/appointments`, which returns only the caller's
   appointments for one exact external reference. An appointment booked without an external
   reference cannot be listed that way: take it from the booking product's own records, and do not
   cut over while an appointment you must honour cannot be accounted for. Tell the products that show those appointments, and the people who hold
   them, that they will not appear in the upgraded deployment until rebooked. After you apply,
   re-establish supply with `schedulingctl records apply` so the carried bookings are not sold
   twice: publish each affected window's `units` net of them, add a `closure` exception for the
   time they occupy, or have the owning products rebook them before you open booking traffic.

   The runtime file requires a top-level `taskGrantStatus`, and each entry names its resource
   `statusResource`. Replace `retention.attemptReceiptRetentionDays` with
   `retention.receiptRetentionDays`, reviewing the value and reducing it to at most 365 days; each
   old key is refused with `config.removed-key`. The
   `authentication.oidc` scope defaults are now `scope`, `scheduling:read`, and
   `scheduling:explain`, so set `scopeClaim`, `readsScope`, or `explainScope` when your issuer
   emits the earlier spellings. List the task authorities whenever Scheduling must check
   current status or revocation, and when it accepts deferred work. The
   `taskGrantStatus: unchecked-final-fifteen-minutes` path checks only remaining lifetime because a
   signed token does not identify its original grant mode. It admits any grant with at most 900
   seconds remaining without checking revocation, including the final 900 seconds of a deferred
   grant. Use it only when the deployment accepts that stale-authority window.
   Run `schedulingctl check PROJECT --runtime-config FILE`, then stop the previous runtime or keep
   its destination bindings until hook deliveries drain. Point the runtime file at a fresh database,
   then run `schedulingctl plan --runtime-config FILE` and `schedulingctl apply --runtime-config
   FILE`. Apply the environment records with `schedulingctl records apply --runtime-config FILE
   RECORDS`, start `scheduling`, then use `schedulingctl status --runtime-config FILE` to confirm
   the activation.
8. **Upgrade Messaging**, when it runs. The current release installs its complete schema as a
   fresh baseline and refuses a database a pre-1.0 release wrote at `plan`, `apply`, and startup.
   Messages still queued in the previous database are not carried forward, so drain them first
   when they must still be sent, as step 1 of [Retire Messaging](#retire-messaging) describes.
   Stop new submissions, and let in-flight senders finish retrying submissions whose answers they
   lost.

   Provider callbacks for messages the previous deployment sent keep arriving at the callback URL.
   The current runtime answers a verified callback that names no message it holds with `204`,
   stores nothing, and counts it as `unmatched` in `messaging_provider_callbacks_total`. A
   provider does not retry a `204`, so that delivery report never reaches Messaging. Choose one
   of two paths before you stop the previous runtime. To keep the reports, leave it serving
   callbacks, with submissions stopped and its queue empty, through each callback provider's
   documented reporting cutoff, as step 2 of [Retire Messaging](#retire-messaging) describes. To
   cut over at once, accept that late reports are lost to Messaging, and reconcile them afterwards:
   compare each provider's records with the retained database, read through the previous
   `messagingctl messages show` while the previous runtime stays stopped.

   Then stop every previous `messaging` runtime, giving graceful shutdown time to finish sends
   already in flight. Refresh the `pg_dump` after every earlier runtime stops, and retain the
   previous database and audit journal for reconciliation.

   Replace `retention.submissionReceiptRetentionDays` with `retention.receiptRetentionDays` in the
   runtime file, reviewing the value and reducing it to at most 365 days and at most
   `recordRetentionDays`; the old key is refused with `config.removed-key`.
   `authentication.oidc.scopeClaim` now defaults to `scope`, so set it explicitly when your issuer
   emits `registry_scopes`. Rebuild
   the package when the release notes require it, update `package.root`, and repin
   `package.expectedDigest` when set. Point the runtime file at a fresh database prepared as
   [Provision PostgreSQL](../../messaging/#provision-postgresql) describes, then run `messagingctl
   plan --runtime-config FILE` and `messagingctl apply --runtime-config FILE`. Confirm the
   activation with `messagingctl status --runtime-config FILE`, start the current `messaging`, and
   require `GET /ready` to answer `200` before you resume submissions.
9. **Upgrade clients, then resume traffic.** Install the v0.42.0 client packages, which still
   require Python 3.11 or later and Node.js 24.11.0 or later, and update applications for these
   changes:
   - **BReg.** Proposals replace Requests: use `startProposal`, `prepareProposal`,
     `executeProposal`, and `recoverProposal` (snake case in Rust and Python), `actions` and
     `selectAction` in place of the immediate-Action methods, and `revision` in place of
     `contractFingerprint`. The client refuses BReg metadata older than version 2, so regenerate
     project packages and clients together. The Proposal list takes `limit` instead of `top`, and
     ingestion run listings page with `cursor` and `nextCursor`. Every Proposal carries `turn`,
     and a Proposal whose Review is rejected ends in `rejected` and answers further commands with
     `409` `proposal.rejected`. Drop any branch on the removed recovery values: `terminal` in
     `BRegRecoveryHint`, and `refresh` and `receipt-only` in `BRegApplicationRecoveryHint`.
   - **Casework.** A review decision names its `outcome`: an approve without one is refused with
     `400` `request.invalid` and reason `outcome-not-declared`, and the clients refuse a decision
     receipt without one. The `AssignmentContext` export is removed.
   - **Discovery.** `validateSelection` and `validate_selection` are removed; call
     `validateSelectionStructure` or `validate_selection_structure`, which behave the same.
   - **Scheduling.** Reminder receivers parse the shared hook envelope that appointment observers
     receive, sent as `content-type: application/json`.

   Roll out every application that embeds a Registry Stack client at v0.42.0 before it calls the
   upgraded runtimes, then resume traffic.

## Roll back

No product migrates backwards, and in v0.42.0 none needs to: the upgrade never touched the v0.41.0
databases you kept in steps 4 to 8. To roll back a product, stop its v0.42.0 runtime and restart
the previous binary, package, and runtime file against the retained database. Never point a
v0.41.0 runtime at a v0.42.0 database: Casework, Scheduling, and Messaging v0.41.0 refuse schema
version 100 as newer than they know. Everything the upgraded deployment accepted after the
cutover exists only in its v0.42.0 database, so keep that database unchanged and reconcile its
work into the retained one before the previous runtime resumes traffic.

- **BReg.** Stop consumer traffic to the v0.42.0 `breg`, and while it still serves, record what
  it accepted after the cutover. Export Records with `bregctl data export` where a profile allows
  it (see [Export with a checkpoint](../../breg-data/#export-with-a-checkpoint)); it exports
  Records only. Read Proposals through the client's Proposal list and submission reads
  (`listProposals` and `readProposalSubmission`) under a grant that may read them. When no grant
  can read a Proposal, it cannot be carried back, so either accept losing it or roll forward
  instead. Stop
  every v0.42.0 `breg` and keep its database. Start the previous
  `breg` with the previous package and runtime file against the retained database; the v0.42.0
  tools cannot read the earlier package or runtime file. Re-enter the recorded changes through the
  previous release's interfaces. When the retained database itself is damaged, restore the final
  `pg_dump` taken in step 4 into a fresh database instead, point a copy of the previous runtime
  file at it, and adopt its claim with the previous release's `bregctl instance-claim adopt --runtime-config FILE
  --acknowledge-original-retired` before starting `breg`; see
  [After a logical restore](../back-up-and-restore/#after-a-logical-restore) for why. To undo
  only a model change within one release, roll forward to a successor that reverts it; see
  [Roll back by rolling forward](../../breg-changes/#roll-back-by-rolling-forward).
- **Casework.** Pause producer submissions and staff mutations to v0.42.0 Casework, and while it
  still serves, record the reviews it accepted and decided after the cutover. `caseworkctl` has no
  review export, so read them through the Casework API under an authorized supervisory grant
  (supervisory review tasks, review results, and review history), or from each producer's own
  records. Then stop the v0.42.0 runtime, keep its database, and start the previous binary,
  package, and runtime file against the retained database. Producers must resubmit the open reviews to the previous deployment, and
  a decision taken after the cutover must be taken again there. BReg and Casework roll back
  together, because each refuses the other's review results across the release boundary.
- **Evidence.** Restart the previous binary with the previous bundle and runtime file.
- **Messaging.** Stop new submissions, then stop the v0.42.0 runtime and keep its database
  unchanged. With the upgraded `messagingctl messages list` and `messages show`, the audit
  archive, and provider records, record every message the v0.42.0 deployment accepted, sent, or
  settled. Keep the previous runtime stopped while you inspect the retained database with the
  previous `messagingctl messages list` and `messages show`. Its supported actions can retry
  `failed`, settle `unknown`, or cancel `queued` messages; apply one only when the retained
  dispatch state is eligible and provider evidence supports the decision, because the previous
  worker resumes queued dispatch as soon as it starts. Then start the previous binary with the
  previous package and runtime file against the retained database, and resubmit through it any
  post-cutover message that was accepted but never sent. A message the v0.42.0 deployment sent
  stays recorded only in its database, and its later provider callbacks reach whichever runtime
  serves the callback URL; the previous runtime answers them as `unmatched`.
- **Scheduling.** Stop the v0.42.0 runtime and keep its database for inspection; no restore is
  needed. Every hold and appointment it accepted after the cutover is absent from the retained
  database. Reconcile each one before the previous runtime resumes booking: rebook it there through
  its owning product, or reduce the affected window's supply with the previous `schedulingctl
  records apply`, and tell the people who hold it. Then start the previous binary, package, and
  runtime file against the retained database.

:::caution[Reconcile Scheduling before resuming bookings]
A rolled-back Scheduling deployment does not know the appointments the upgraded one confirmed. If
you resume booking traffic before you reconcile them, it sells that capacity again and
double-books it.
:::

Because the release rule holds in both directions, rolling back one product means rolling back
every product that must match it: Casework refuses a BReg that went back without it.

## Retire a deployment

Retire the products in the reverse of the upgrade order, so nothing still running depends on what
you have removed. Retiring a product leaves records behind: signatures others still verify,
decisions others may challenge, and audit entries your retention policy holds. None of the products
has a decommission command, so the steps below are yours.

### Retire Messaging

Messaging has no runtime or database dependency on another Registry Stack product, so retire it
independently after its callers stop submitting.

1. Stop routing new submissions to Messaging. Let the runtime drain queued work. Run
   `messagingctl messages list --runtime-config FILE --status unknown --limit 500`,
   [settle each returned message](../../messaging/#settle-an-unknown-outcome) from the provider's
   record, and repeat until the filtered list is empty. Settling `not-sent` queues another send,
   so drain that work too. When the metrics listener runs, require the `pending`, `leased`, and
   `unknown` `messaging_dispatch_jobs` gauges all to reach zero. Without metrics, check that
   `messages list --status queued`, `--status sending`, and `--status unknown`, each with
   `--runtime-config FILE`, return empty.
2. For each callback provider, keep its callback endpoint live through the provider's documented
   reporting cutoff. Compare the provider's records with `messagingctl messages show`, and record
   any submitted messages whose delivery report remains unresolved at the cutoff. Empty dispatch
   gauges prove sends have finished, not that every delivery report has arrived. SMTP has no
   delivery receipts, so its messages remain `submitted`.
3. Stop `messaging` gracefully. It claims no more messages and finishes sends already in flight;
   give it time to finish before the service manager kills it.
4. After final provider reconciliation and shutdown, remove callback registrations for this
   deployment and revoke its dedicated outbound provider credentials. When a credential is shared
   with a system that remains live, rebind that system to another credential before revoking the
   retired one.
5. Ship the active file and every sealed segment for both `audit.path` and its `messagingctl`
   sibling. Keep the secret named by `audit.hashKeyRef` securely through the final archive sweep
   and for as long as your policy requires correlation with known callers or recipients. Destroying
   that secret permanently
   prevents recomputing their audit pseudonyms.
6. Messaging has no export command. After the process stops, take a final `pg_dump`, and retain
   the active package, runtime file, and both matching binaries, `messaging` and `messagingctl`,
   while your policy holds the records. A full dump also holds recipient contacts, rendered parts,
   and submission receipts; a stopped dump never runs the retention sweep. At each remaining
   payload or receipt expiry, restore the dump into an isolated database with the runtime stopped.
   Point a copy of the retained runtime file at that database, keeping its retention values.
   Preview and apply the matching `messagingctl retention erase-expired --runtime-config FILE
   --before TIMESTAMP`, using an RFC 3339 cutoff no later than the operator host's or database's
   clock. Make a replacement dump and destroy the superseded copies. See
   [Erase expired data on demand](../../messaging/#erase-expired-data-on-demand) for the preview
   and `--apply` procedure. Ship the tool's active audit file and every sealed segment after each
   applied sweep. Repeat only through the remaining payload and receipt periods; the content-free
   archive can then remain for the applicable record period.

### Retire Scheduling

Scheduling reads no other product and no other product reads it, so it can retire at any point
in this sequence.

1. Stop routing booking requests to Scheduling, and tell the callers holding appointments how
   those appointments will be honoured.
2. Stop `scheduling`. Reminder and observer-hook deliveries are outbox work its own workers send,
   so every delivery still pending stops with it and is not sent.
3. Scheduling has no export command. Keep a final `pg_dump` for as long as your policy holds its
   appointment records.
4. Ship the final audit file, its sealed files, and the `schedulingctl` sibling of `audit.path`.

### Retire Evidence

1. Stop `evidence-oid4vci`, then stop routing requests to Evidence.
2. Keep the published public keys available. An assertion Evidence issued stays valid for up to
   `maximumAssertionValiditySeconds` (at most one year), and the JWKS is served only by the running
   process, so publish the key set elsewhere or give it to each relying party, and keep it until
   that period and the verifier clock skew have passed since the last issuance.
3. Ship the final audit files after the process stops, and keep every audit master whose
   pseudonyms an investigation may still need; see
   [Rotate the audit master](../../evidence-audit/#rotate-the-audit-master).
4. Retire the signing key in Transit only after step 2's period ends; see
   [Retire the predecessor](../../../tutorials/rotate-evidence-signing-keys/#retire-the-predecessor).
5. Retire or rebind the Evidence provider in every BReg project whose governed actions call it,
   since an action that resolves against a retired provider fails.

### Retire Casework

1. Stop new producer submissions and staff mutations. Finish pending review rounds, or cancel them
   through each bound producer's supported interface. Confirm that consumers have correlated the
   terminal results before removing their review authority.
2. Preserve the retained results and accountability your institution requires. A final `pg_dump`
   contains the retained database state; Casework exposes no general export or source-attempt
   settlement command. Apply the pinned retention policy while the service is still maintained.
3. Stop the runtime, archive its external audit files and key under your retention policy, and keep
   the matching package and binary with retained backups. A database backup does not contain the
   external audit journal.
4. Revoke Casework's status-reader and institutional-agent credentials in the relevant issuers.
   Keep source application credentials under their separate owner's retirement procedure.

### Retire Base Registry Engine

1. Stop every consumer, then close the import authorities still open with
   `bregctl import-authority close`.
2. Export what must outlive the registry. `bregctl data export` exports one entity through one
   access profile, checkpointed; a final `pg_dump` is the only complete copy. See
   [Export with a checkpoint](../../breg-data/#export-with-a-checkpoint).
3. Erase what your policy does not let you keep, before that final backup: see
   [Erase retained history](../../breg-retention/#erase-retained-history) and
   [Erase expired Evidence uses](../../breg-retention/#erase-expired-evidence-uses).
4. Stop `breg`. Pending webhook deliveries stop with it and are not sent; check
   `bregctl webhook list` first if receivers must see them.
5. Ship the final audit files and the `bregctl` companion file.
6. Keep the field-encryption key for as long as you keep any backup that holds sealed values, and
   the audit hash key for as long as you keep the audit archive. Destroy each only when the last
   record that needs it is gone.

Use this runbook when you move a deployment of Base Registry Engine (BReg), Registry Casework,
Evidence, Registry Scheduling, and Registry Messaging to a new release, or take it out of service.
Each product's own guide carries its upgrade command; this page gives the order across products,
the version rule that order enforces, and what each product must leave behind when it is retired.

## Run one release everywhere

Every Registry Stack artifact of a release shares one version: the runtimes, their adopter tooling,
and the Rust, Node.js, and Python clients. Run the same release on every side. There is no
supported version-skew window, between two runtimes or between a client and a runtime, and a
rolling upgrade that mixes releases is not supported:

- **Casework pins the BReg context contract.** The read-only provider checks the exact registry
  revision, context contract, and Proposal identity. A changed contract requires re-pairing; see
  [Change the active Casework package](../../casework/#change-the-active-package).
- **Adopter tooling is checked.** `evidencectl` refuses an `evidence` or `bregctl` binary of
  another version.
- **Clients are not checked.** Clients send no version, and runtimes accept any caller. Pre-1.0
  client and wire contracts can change incompatibly between releases, so upgrade each client to
  the same release as the runtime it calls.
- **BReg activation is not rolling.** Once `bregctl apply` activates a successor, every `breg`
  process still running the previous package fails readiness until it restarts onto the successor.
  Plan the restart as part of the activation, not after it.

Read the target release's state and package requirements before applying. Current BReg and
Casework refuse their retired database models, and current Scheduling and Messaging refuse a
database a pre-1.0 release wrote; keep the previous database and its binaries for accountability,
and start the replacement on a fresh database. Evidence requires its
normalized authored project and target. None of these replacements provides an in-place
conversion of the retired contract. See [Upgrades and state](../../../reference/api-stability/#upgrades-and-state).

## Upgrade in this order

BReg goes first, because Casework and Evidence both read it. Pair Casework with the resulting
exact BReg context contract before starting its runtime. Evidence and its wallet-facing front end come next. Scheduling and
Messaging read none of them and upgrade independently, before the clients. Read the target
release's notes for every deployed product. Complete their required drains and outcome
reconciliation before that product's apply, and make the listed project and runtime-file changes
in its upgrade step. Rehearse the whole sequence on a restored copy first, as
[Run a disaster-recovery drill](../back-up-and-restore/#run-a-disaster-recovery-drill) describes.

Version-specific procedures in released notes apply to that release's contracts. They do not
establish a conversion path for a retired model. On native Linux, require glibc 2.34 or newer.
The four product installers start every staged Linux binary before selecting the new toolset,
so a binary that cannot run leaves the installed toolset selected.

1. **Back up every database.** Take the BReg and Casework `pg_dump`s, and the Scheduling and
   Messaging ones when they run. Copy those products' packages and runtime files, and keep the
   previous release's binaries. These backups are the only way back; see [Roll back](#roll-back).
2. **Stop `evidence-oid4vci`**, when it runs. Its outstanding offers end here; see
   [Operational limits](../../../configure/evidence-oid4vci/#operational-limits).
3. **Pause and drain Evidence traffic** for every question that reads BReg, or pause the whole
   instance when you cannot drain one question at a time. Keep the previous Evidence candidate.
4. **Upgrade BReg.** Preserve a retired Request-based deployment with its old binaries and
   database; activate the current native Registry project on a fresh database. For a deployment
   already using the native model, test and package the candidate with the matched tooling,
   then plan and apply the successor. Keep `database.roles` unchanged when resuming an
   interrupted apply. Restart every runtime onto the exact active package and verify readiness;
   see [Activate the successor](../../breg-changes/#activate-the-successor).
5. **Upgrade Casework.** The current review-only model requires a fresh database when replacing
   a retired WorkItem schema. Preserve the old database, binary, package, and audit until its work
   and accountability obligations are resolved; the new runtime refuses that schema before mutation
   and performs no in-place conversion. For a deployment already on the review-only baseline,
   package the candidate policy and run `caseworkctl plan --runtime-config FILE` before applying.
   Finish affected reviews if the candidate would remove pinned policy or authority; there is no
   orphan bypass. Re-pair a changed native context export with `caseworkctl provider pair` and verify
   the exact contract before packaging. Stop the earlier runtime, run `caseworkctl apply`, then
   `caseworkctl doctor` with the same runtime file, package, and database. Require readiness before
   resuming staff traffic; see [plan, apply, and serve](../../casework/#plan-apply-and-serve).
6. **Upgrade Evidence.** Author the normalized `evidence.yaml`, target, and target authority
   for the current tooling; retired split authoring documents are refused. Re-import changed
   BReg source exports into that project, review the source changes, and run check and fixtures
   before packaging the candidate with its explicit target. Run
   `evidence check --runtime-config FILE --require-runtime-dependencies` on the target host,
   adding `--without-audit-lock` while the previous instance still runs. Stop the previous
   runtime, start the matched `evidence`, and verify a fresh synthetic assertion before
   restarting its wallet-facing adapter.
7. **Upgrade Scheduling**, when it runs. The current release installs its complete schema as a
   fresh baseline and refuses a database a pre-1.0 release wrote at `plan`, `apply`, and startup.
   Holds and appointments recorded in the previous database are not carried forward: retain that
   database, its package, runtime file, and audit journal for reconciliation. The runtime file
   requires a top-level `taskGrantStatus`. List the task authorities whenever Scheduling must check
   current status or revocation, and when it accepts deferred work. The
   `taskGrantStatus: unchecked-final-fifteen-minutes` path checks only remaining lifetime because a
   signed token does not identify its original grant mode. It admits any grant with at most 900
   seconds remaining without checking revocation, including the final 900 seconds of a deferred
   grant. Use it only when the deployment accepts that stale-authority window.
   Run `schedulingctl check PROJECT --runtime-config FILE`, then stop the previous runtime or keep
   its destination bindings until hook deliveries drain. Point the runtime file at a fresh database,
   then run `schedulingctl plan --runtime-config FILE` and `schedulingctl apply --runtime-config
   FILE`. Start `scheduling`, then use `schedulingctl status --runtime-config FILE` to confirm the
   activation.
8. **Upgrade Messaging**, when it runs. The current release installs its complete schema as a
   fresh baseline and refuses a database a pre-1.0 release wrote at `plan`, `apply`, and startup.
   Messages still queued in the previous database are not carried forward, so drain them first
   when they must still be sent, as step 1 of [Retire Messaging](#retire-messaging) describes.
   Stop new submissions, let in-flight senders finish retrying submissions whose answers they lost,
   then stop every previous `messaging` runtime. Give graceful shutdown time to finish sends already
   in flight. Refresh the `pg_dump` after every earlier runtime stops, and retain the previous
   database and audit journal for reconciliation. Rebuild the package when the release notes
   require it, update `package.root`, and repin `package.expectedDigest` when set. Point the
   runtime file at a fresh database prepared as
   [Provision PostgreSQL](../../messaging/#provision-postgresql) describes, then run `messagingctl
   plan --runtime-config FILE` and `messagingctl apply --runtime-config FILE`. Confirm the
   activation with `messagingctl status --runtime-config FILE`, start the current `messaging`, and
   require `GET /ready` to answer `200` before you resume submissions.
9. **Upgrade clients, then resume traffic.** Move Python applications to Python 3.11 or later and
   Node.js applications to Node.js 24.11.0 or later before installing the v0.41.0 client packages.
   Update exhaustive Rust matches on the Scheduling or Messaging `ProblemCode` enums for
   `ReceiptUnresolved`. Treat `CaseworkTaskAssertionSource` `invalid-credential` as a grant refusal:
   request a new approval and stop retrying that credential. In BReg metadata, an unsupported
   `requiredCapabilities` value disables only the affected binding and can make selection report
   `required-capability`. Handle a valid unknown BReg Problem by its HTTP status and trace ID
   without inferring code or extension semantics. Roll out every application that embeds a
   Registry Stack client at v0.41.0 before it calls the upgraded runtimes, then resume traffic.

## Roll back

No product migrates backwards. A Casework binary refuses a database whose schema is newer than it
supports, and a BReg package applies forward only. Evidence refuses a runtime file carrying keys
its release does not know. To return to the previous release:

- **BReg.** To return to the previous release, stop every `breg` and retire the upgraded
  database, restore the step 1 `pg_dump` into a fresh database, and point the previous runtime file copied
  in step 1 at it. The restored copy carries the claim of the database it was dumped from, so
  adopt it with the previous release's `bregctl instance-claim adopt --runtime-config FILE
  --acknowledge-original-retired` (see
  [After a logical restore](../back-up-and-restore/#after-a-logical-restore) for why), then
  start the previous `breg` with the previous package and that runtime file; the new release's
  tools cannot read the earlier package or runtime file. To undo only a model
  change, roll forward to a successor that reverts it, and when the data itself must go back,
  restore the pre-activation backup; see
  [Roll back by rolling forward](../../breg-changes/#roll-back-by-rolling-forward).
- **Casework.** Restore the pre-apply backup and run the previous binary, package, and runtime
  file copied in step 1; see
  [Restore Registry Casework](../back-up-and-restore/#restore-registry-casework) for what that
  restore loses.
- **Evidence.** Restart the previous binary with the previous bundle and runtime file.
- **Messaging.** Stop the upgraded runtime. Before you restore, use the upgraded
  `messagingctl messages list` and `messages show`, the audit archive, and provider records to
  record every message effect after the stopped, pre-apply snapshot. Preserve the upgraded database
  unchanged, and restore that snapshot into a separate fresh database. Point a copy of the previous
  runtime file at the restored database, and keep both runtimes stopped while you inspect the copy
  with the previous `messagingctl messages list` and `messages show`. Its supported actions can retry `failed`, settle `unknown`, or cancel
  `queued` messages; apply one only when the restored dispatch state is eligible and external
  evidence supports the decision. Start the previous binary with the previous package and runtime
  file only after every post-snapshot effect is represented in the restored state. Never point the
  previous runtime at the migrated database: readiness refuses a schema version the binary does
  not know. Do not start it to inspect restored state: its worker immediately resumes queued
  dispatch. A new post-snapshot submission is absent from the restore, and a message sent after the
  snapshot can return as `queued`, which the previous tools cannot mark `submitted`. When either
  gap exists, keep the upgraded database and fix forward: use the upgraded `messages list`,
  `messages show`, and eligible operator actions with provider evidence to reconcile its state,
  correct its package or runtime configuration, and restart a runtime that supports that database.
- **Scheduling.** Restore the pre-apply database backup, then run the previous binary, package,
  and runtime file copied in step 1. Always restore first: an earlier Scheduling runtime may not
  detect a schema newer than its own.

Because the release rule holds in both directions, rolling back one product means rolling back
every product that must match it: Casework refuses a BReg that went back without it.

## Retire a deployment

Retire the products in the reverse of the upgrade order, so nothing still running depends on what
you have removed. Retiring a product leaves records behind: signatures others still verify,
decisions others may challenge, and audit entries your retention policy holds. None of the products
has a decommission command, so the steps below are yours.

### Retire Messaging

Messaging has no runtime or database dependency on another Registry Stack product, so retire it
independently after its callers stop submitting.

1. Stop routing new submissions to Messaging. Let the runtime drain queued work. Run
   `messagingctl messages list --runtime-config FILE --status unknown --limit 500`,
   [settle each returned message](../../messaging/#settle-an-unknown-outcome) from the provider's
   record, and repeat until the filtered list is empty. Settling `not-sent` queues another send,
   so drain that work too. When the metrics listener runs, require the `pending`, `leased`, and
   `unknown` `messaging_dispatch_jobs` gauges all to reach zero. Without metrics, check that
   `messages list --status queued`, `--status sending`, and `--status unknown`, each with
   `--runtime-config FILE`, return empty.
2. For each callback provider, keep its callback endpoint live through the provider's documented
   reporting cutoff. Compare the provider's records with `messagingctl messages show`, and record
   any submitted messages whose delivery report remains unresolved at the cutoff. Empty dispatch
   gauges prove sends have finished, not that every delivery report has arrived. SMTP has no
   delivery receipts, so its messages remain `submitted`.
3. Stop `messaging` gracefully. It claims no more messages and finishes sends already in flight;
   give it time to finish before the service manager kills it.
4. After final provider reconciliation and shutdown, remove callback registrations for this
   deployment and revoke its dedicated outbound provider credentials. When a credential is shared
   with a system that remains live, rebind that system to another credential before revoking the
   retired one.
5. Ship the active file and every sealed segment for both `audit.path` and its `messagingctl`
   sibling. Keep the secret named by `audit.hashKeyRef` securely through the final archive sweep
   and for as long as your policy requires correlation with known callers or recipients. Destroying
   that secret permanently
   prevents recomputing their audit pseudonyms.
6. Messaging has no export command. After the process stops, take a final `pg_dump`, and retain
   the active package, runtime file, and both matching binaries, `messaging` and `messagingctl`,
   while your policy holds the records. A full dump also holds recipient contacts, rendered parts,
   and submission receipts; a stopped dump never runs the retention sweep. At each remaining
   payload or receipt expiry, restore the dump into an isolated database with the runtime stopped.
   Point a copy of the retained runtime file at that database, keeping its retention values.
   Preview and apply the matching `messagingctl retention erase-expired --runtime-config FILE
   --before TIMESTAMP`, using an RFC 3339 cutoff no later than the operator host's or database's
   clock. Make a replacement dump and destroy the superseded copies. See
   [Erase expired data on demand](../../messaging/#erase-expired-data-on-demand) for the preview
   and `--apply` procedure. Ship the tool's active audit file and every sealed segment after each
   applied sweep. Repeat only through the remaining payload and receipt periods; the content-free
   archive can then remain for the applicable record period.

### Retire Scheduling

Scheduling reads no other product and no other product reads it, so it can retire at any point
in this sequence.

1. Stop routing booking requests to Scheduling, and tell the callers holding appointments how
   those appointments will be honoured.
2. Stop `scheduling`. Reminder and observer-hook deliveries are outbox work its own workers send,
   so every delivery still pending stops with it and is not sent.
3. Scheduling has no export command. Keep a final `pg_dump` for as long as your policy holds its
   appointment records.
4. Ship the final audit file, its sealed files, and the `schedulingctl` sibling of `audit.path`.

### Retire Evidence

1. Stop `evidence-oid4vci`, then stop routing requests to Evidence.
2. Keep the published public keys available. An assertion Evidence issued stays valid for up to
   `maximumAssertionValiditySeconds` (at most one year), and the JWKS is served only by the running
   process, so publish the key set elsewhere or give it to each relying party, and keep it until
   that period and the verifier clock skew have passed since the last issuance.
3. Ship the final audit files after the process stops, and keep every audit master whose
   pseudonyms an investigation may still need; see
   [Rotate the audit master](../../evidence-audit/#rotate-the-audit-master).
4. Retire the signing key in Transit only after step 2's period ends; see
   [Retire the predecessor](../../../tutorials/rotate-evidence-signing-keys/#retire-the-predecessor).
5. Retire or rebind the Evidence provider in every BReg project whose governed actions call it,
   since an action that resolves against a retired provider fails.

### Retire Casework

1. Stop new producer submissions and staff mutations. Finish pending review rounds, or cancel them
   through each bound producer's supported interface. Confirm that consumers have correlated the
   terminal results before removing their review authority.
2. Preserve the retained results and accountability your institution requires. A final `pg_dump`
   contains the retained database state; Casework exposes no general export or source-attempt
   settlement command. Apply the pinned retention policy while the service is still maintained.
3. Stop the runtime, archive its external audit files and key under your retention policy, and keep
   the matching package and binary with retained backups. A database backup does not contain the
   external audit journal.
4. Revoke Casework's status-reader and institutional-agent credentials in the relevant issuers.
   Keep source application credentials under their separate owner's retirement procedure.

### Retire Base Registry Engine

1. Stop every consumer, then close the import authorities still open with
   `bregctl import-authority close`.
2. Export what must outlive the registry. `bregctl data export` exports one entity through one
   access profile, checkpointed; a final `pg_dump` is the only complete copy. See
   [Export with a checkpoint](../../breg-data/#export-with-a-checkpoint).
3. Erase what your policy does not let you keep, before that final backup: see
   [Erase retained history](../../breg-retention/#erase-retained-history) and
   [Erase expired Evidence uses](../../breg-retention/#erase-expired-evidence-uses).
4. Stop `breg`. Pending webhook deliveries stop with it and are not sent; check
   `bregctl webhook list` first if receivers must see them.
5. Ship the final audit files and the `bregctl` companion file.
6. Keep the field-encryption key for as long as you keep any backup that holds sealed values, and
   the audit hash key for as long as you keep the audit archive. Destroy each only when the last
   record that needs it is gone.

Use this decision procedure before restarting a generated deployment, carrying reviewed
pre-1.0 intent into a 1.0 project, updating a product or image, or restoring durable
state. The verified package and its `generated/RUNBOOK.md` define the supported runtime
path.

Rollback means a manual abort before a target product accepts a newer sequence. After
the first successful target acceptance advances durable anti-rollback state, rollback
is unsupported.

## Prerequisites

- Retain the exact current generated package, its approved set, and its externally
  recorded closure digest.
- Read the current and candidate `generated/RUNBOOK.md` files.
- Prepare a fresh candidate with a verified target Registryctl binary, matching release
  lock, reviewed approved set, and the same signed project and environment identity.
- Preserve the complete `relay-public-state` and `consultation-state` recovery
  consistency groups affected by the change.
- Keep external traffic blocked while state and candidate services are verified.
- Record the last accepted lane, instance, stream, and sequence identities outside the
  host being changed.

## Ownership and trust boundary

Registryctl generates and verifies `generated/`. It does not activate the package,
coordinate backups, admit traffic, or decide recovery.

The deployment operator owns `binding.yaml`, `operator/`, package retention, the
complete recovery groups, traffic removal, and the manual abort decision. Relay and
PostgreSQL remain in the generated package's declared recovery groups. Do
not copy product state, trust anchors, bundles, audit state, or anti-rollback files
between lanes or instance identities.

Registry Stack 1.0 does not automate migration from a pre-1.0 project. A new 1.0 project
must carry only reviewed authored intent.

## Choose the operation

- For an ordinary restart, verify the exact current package and follow its ordinary
  stop, `verify_state`, and start commands.
- For pre-1.0 authored intent, create a separate 1.0 project and copy only reviewed
  authored intent into it.
- For a product, image, or signed-lane update, generate and verify a fresh candidate
  package. Do not edit the current Compose model in place.
- For state recovery, restore one complete recovery consistency group at the same or
  newer accepted sequence.
- For a candidate failure before target acceptance, manually abort to the intact current
  package.
- For a failure after target acceptance, complete forward, restore coherent same-or-newer
  state, or replace the affected instance identity.

Do not invoke product initialization, schema installation, or state bootstrap commands
directly as an update shortcut. Use only the locked Compose actions and order in the
candidate's generated runbook.

## Preserve the recovery set

Follow [Back up and restore a deployment](../../backup-and-restore/) before changing the
running deployment.

The `relay-public-state` group preserves the public Relay lane, its package, approved
set, bundle, anchor, audit and anti-rollback state, source and materialization state,
and exact instance, stream, and accepted sequence.

The `consultation-state` group preserves consultation Relay, PostgreSQL, their
package and signed inputs, audit and anti-rollback state, complete databases, role and
key-lifecycle records, and exact instance, stream, and accepted sequences.

Quiesce the complete selected group before snapshot or restore. A partial file copy,
schema-only dump, or list of unrelated hashes is not a recovery point.

## Cut over pre-1.0 authored intent

Keep the pre-1.0 source project unchanged. Create a separate 1.0 project from the public starter
that matches the source shape:

```sh
registryctl init <candidate-directory> --template http
# or
registryctl init <candidate-directory> --template spreadsheet
```

Copy only reviewed authored intent into the candidate. Do not copy generated output,
runtime state, compatibility shims, or removed command assumptions. Then validate the
1.0 project:

```sh
registryctl -C <candidate-directory> test
registryctl -C <candidate-directory> check --explain
registryctl -C <candidate-directory> build
```

Registry Stack 1.0 provides no automated pre-1.0 migration command or removed-command
aliases.

## Stage a restart or upgrade

For an ordinary restart, use the exact current package. For an update, follow
[Upgrade and recover a deployment](../../upgrade-and-rollback/) to copy the intact
current package into an isolated candidate and regenerate that candidate from the
target approved set.

1. Verify current and candidate packages against their approved sets and externally
   recorded closure digests.
2. Render both effective Compose models without resolving environment values.
3. Verify operator files, every current and candidate bundle and anchor, and both
   current `verify_state` actions.
4. Quiesce each affected recovery group and close its pre-change recovery record.
5. Stop the current package with its generated Compose `down` command.
6. From the candidate, stage operator secrets and run both read-only
   `verify_state` actions before ordinary startup.
7. When a private-lane contract changed, start and verify PostgreSQL and consultation
   Relay before any externally reachable dependant.
8. Start the remaining candidate services with the generated Compose `up --detach
   --wait --wait-timeout 120` command.
9. Keep traffic blocked until product canaries, audit continuity, and every affected
   target sequence are verified.

The first successful target product acceptance that advances durable anti-rollback
state is the manual abort boundary. Do not configure an automated rollback across it.
Retain the candidate's `generated.previous/` and the intact current package until every
affected lane reports the target accepted sequence and the retention decision is
recorded.

## Expected evidence

Retain:

- Current and target Registryctl, release-lock, approved-set, and package closure
  identities.
- The complete recovery-group inventory, shared recovery point, and integrity record.
- Current and candidate package verification results and value-free Compose render
  checks.
- Separate bundle, anchor, operator-file, and `verify_state` results for all three lanes.
- Stop, staged-start, complete-start, canary, audit, target-acceptance, and traffic
  admission timestamps.
- The pre-1.0 source-to-candidate review when that cutover applies.

Do not record secret values, source-returned values, credentials, restricted rows, or
key material in general logs.

## What this proves

Package verification proves the generated closure, release projection, and structural
operator-file boundary. The three `verify_state` actions prove the read-only state
checks encoded by the released products. A closed recovery record binds the stores and
accepted identities selected for recovery. Staged canaries prove only the exercised
paths before traffic admission.

These checks do not prove backup freshness, coverage of every acknowledged write,
country acceptance, full live interoperability, or safe rollback after target
acceptance. Health and readiness do not prove that a restored database reached the last
external audit watermark.

## Roll back or recover

Before the manual abort boundary, stop the candidate and restart the still-intact
current package. Verify its external closure digest, operator files, Compose model, and
all three current `verify_state` actions before its ordinary start.

After target acceptance, never start the older closure or restore a pre-update accepted
sequence. Choose one of these manual recovery paths:

1. Complete the forward update after correcting the operator-controlled dependency.
2. Restore a complete recovery group at the same or newer accepted sequence, then run
   all three read-only `verify_state` actions.
3. Provision a new instance identity, review and sign every affected lane, generate a
   new package, and follow first installation.

An anti-rollback rejection is a correct fail-closed result. Do not delete, edit, copy,
or reinitialize anti-rollback state to make an older package start.

## Escalate

Escalate to both product owners when the combined topology lacks a complete recovery
group or the candidate runbook does not cover the intended transition.
Escalate to the database owner when role identities, accepted-write coverage, or the
shared recovery point cannot be proved.
Escalate to the release owner when the current or candidate package, approved set,
release lock, or externally recorded closure cannot be verified.

You have a [registry project](../../reference/glossary/#registry-project) that passes
`bregctl check --production`, and you want it serving. This page takes you from an empty
PostgreSQL server to a `breg` process that serves the project's first
[package](../../reference/glossary/#package) and answers `GET /ready`. The examples use the
facility template that `bregctl init --template facility-registry facility` creates.

Two roles take part. The author prepares a package from the project. The operator, holding the
migration credential, activates the package and runs the server. One person may hold both in a
small deployment; the commands stay the same. A package carries no signature: the migration credential is
what authorises an activation, and the database records every activation in its own ledger.

Deployment commands take absolute paths with no `..` component and no symbolic link anywhere in
them. That covers `--runtime-config`, `--credentials`, `--test-receipt`, `--package`, the test
receipt's `--output`, and the directories the runtime file names. When an output path such as the
test receipt's `--output` is refused for a symbolic link, the diagnostic names the linked component
and the target it resolves to. If the linked component is an ancestor, choose an unused final name
under its real directory. If the final component is itself a symbolic link, that final name is
occupied by the link; choose another unused, non-symbolic-link name under the real parent.

## What you need

- **PostgreSQL 17 or newer**, reached over TLS, with two login roles: a migration role that owns
  the schema and applies packages, and a runtime role the serving process uses. A project with a
  `crs84-polygon` field always needs PostGIS 3.5 or newer. A `crs84-point` field needs PostGIS only
  when an access profile grants bbox queries. `bregctl provision` creates the roles, the database, the
  schemas, and the extensions from an administrator's credentials. `breg` and `apply` create none
  of them. SQLite is not a target.
  Ubuntu 24.04 ships PostgreSQL 16 and Debian 12 ships PostgreSQL 15, both too old: install 17
  from the PostgreSQL project's apt repository (PGDG), or run the `postgres:17` image
  (`postgis/postgis` at PostgreSQL 17 when the project requires PostGIS).
- **A host for one process.** The runtime is a single binary that verifies one package and serves
  its REST API against one database, on the platforms in
  [platform support](../../explanation/known-limitations/#platform-support).
- **HTTPS in front of it.** The process trusts no host or forwarded header. Your reverse proxy or
  ingress terminates TLS, and generated links use the public origin you configure as
  `listener.publicOrigin`.
- **A token issuer.** The registry verifies bearer access tokens from one OpenID Connect issuer and
  issues none. Human login, account lifecycle, and multifactor authentication stay with your
  identity provider.
- **A backup of the database before every activation.** The product restores nothing itself. A
  destructive change is refused unless you name the backup its reviewed migration requires, as
  [Change an active registry](../breg-changes/) describes.

Records, their history, Proposals, and the outbox of undelivered events all live in PostgreSQL.
Webhook delivery runs inside the process from that outbox, so there is no message broker and no
cache. The audit journal goes to a local file per process or to standard output. Attachments use
PostgreSQL unless you bind S3-compatible storage. A standalone registry needs no other Registry
Stack service; a composition adds only the services it uses, such as a Review provider for reviewed
Proposals. Authoring commands open no database, so an author works on a laptop until the project
is ready to test.

What stays your job once it runs:

- **Secrets.** Two database credentials, the audit hash key, the cursor secret, one key per webhook
  destination, and the issuer's key set when you pin one. The runtime file names each by reference
  and refuses a value written inline.
- **Every production change.** A one-line access change takes the same path as a new registry:
  check, test against a schema-test database with real tokens, package, plan, and activate under
  the migration credential in each environment.
- **The audit journal.** Ship each process's stream to append-only storage and confirm delivery
  before local retention expires. The product does not provide tamper evidence.
- **Retention and erasure.** Erasing a record's history is an operator command with no undo; see
  [Retain, erase, and audit](../breg-retention/).
- **Rate limits.** The runtime applies none of its own, so put the registry behind one.

No throughput or latency figure is committed. The product bounds what it can by construction:
every request, lock, and migration runs under an operator-set timeout, the connection pool has a
maximum size, and spatial responses refuse rather than truncate. A load-test harness ships in
`products/breg/loadtest`; run it on a representative Linux host before you cite a number.

Base Registry Engine (BReg) is pre-1.0. A minor release may break APIs, package formats, or
deployment contracts, and each break carries a `BREAKING:` entry in `products/breg/CHANGELOG.md` at
the release tag you run. Security fixes land only in the latest release; see
[API stability](../../reference/api-stability/) and the
[support window](../../security/support-window/). A deployment meets three conditions: run `breg` under
a supervisor that restarts it, treat the holder of the migration credential as the activation gate,
and stay inside the verified deployment profile, which leaves out Kubernetes.

## Obtain the runtime

Install the binaries on the host that will serve, and on the operator host that holds the migration
credential:

```sh
curl -fsSL https://github.com/registrystack/registry-stack/releases/latest/download/breg-install.sh | bash
breg --version
bregctl --version
```

The installer checks every binary against the release `SHA256SUMS` before anything reaches the
install directory, and installs `breg` and `bregctl` together or not at all. It does not verify who
published the release; for that, follow the
[release verification procedure](https://github.com/registrystack/registry-stack/blob/main/release/VERIFY.md)
and rerun the installer with `BREG_ASSET_DIR` naming the verified directory. `BREG_INSTALL_DIR`
selects the install directory (default `~/.local/bin`). To pin a release, run that release's
`breg-<tag>-install.sh` from `https://github.com/registrystack/registry-stack/releases/download/<tag>/`.
Binaries are published for `linux-amd64`, `linux-arm64`, and `macos-arm64`.

Test, package, activate, and serve with the same release of both binaries.

Each release also publishes the container image `ghcr.io/registrystack/breg:<tag>` for
`linux/amd64`. The release manifest beside the binaries,
`registry-stack-<tag>-release-manifest.json`, records the image digest; pin that digest rather than
the tag. [Serve the container image](#serve-the-container-image) shows how to run it.

## Write the runtime configuration

The runtime file binds one package to one database, one token issuer, and one listener. It is a
deployment artifact: keep it with the operator, outside the project, and never put a credential in
it. Every credential is a reference such as `secret:file/<name>`, which resolves to a file under the
secret root.

```yaml title="runtime.yaml" test-file
apiVersion: id.registrystack.org/formats/breg/runtime/v1alpha1
kind: BRegRuntimeConfig
listener:
  bind: 127.0.0.1:8080
identity:
  environment: production
  instanceId: facility-registry
  databaseId: facility-registry-db
secretProviders:
  file:
    root: /etc/breg/secrets
database:
  runtimeUrlRef: secret:file/runtime-database-url
  migrationUrlRef: secret:file/migration-database-url
  caBundleRef: secret:file/database-ca
  pool:
    maximumConnections: 4
  roles:
    migration: registry_migration
    runtime: registry_runtime
package:
  root: /var/lib/breg/build-1/package
authentication:
  oidc:
    issuer: https://issuer.example.com
    audience: urn:breg:facility-registry
    allowedAlgorithm: EdDSA
    accessTokenType: JWT
    scopeClaim: scope
    scopeSeparator: " "
    allowedClients: [operator-editor, registrar, reader]
    maximumTokenLifetimeSeconds: 3600
    leewayMilliseconds: 60000
  authorityClaims:
    principal: registry_principal
    purpose: registry_purpose
audit:
  hashKeyRef: secret:file/audit-key
  path: /var/log/breg/audit.jsonl
cursor:
  secretRef: secret:file/cursor-key
```

The [configuration reference](../../reference/breg-configuration/) lists every key. What the
schema cannot tell you:

- **`identity`** names the database this file may serve. The first activation records
  `databaseId` in the database, and every later `plan`, `apply`, and startup refuses a file that
  names another. `instanceId` stamps every webhook event this runtime captures, so keep it stable
  while deliveries are pending.
- **`database`** names the two connection URLs and the two roles. The runtime requires TLS on both
  connections and verifies the server's certificate and host name. `caBundleRef`
  names PEM root certificates to trust in place of the platform roots, for a server whose
  certificate a private authority issued; omit it when a public authority issued it.
- **`package.root`** is the package directory `package` published. Once you have the package,
  you may add `package.expectedDigest` with the reported package digest, and startup then refuses
  any other package at that path.
- **`authentication.oidc.allowedClients`** lists the OAuth clients whose tokens the registry
  accepts, or `unrestricted`. A project that names clients itself, for example in a profile's
  `requesterClients`, needs each of them listed, so `unrestricted` does not start with such a
  project.
- **`authentication.oidc.issuer`** must be `https`; plain `http` is accepted only on an IPv4
  loopback host. The key set comes from the issuer's discovery document unless `jwksSource`
  names a URI or pins a static document.

Three optional sections matter only for some projects. `taskGrantStatus` pins, per task-grant
issuer such as Casework or a chat assistant's task authority, the endpoint and the registry's own credentials it uses to check that a task grant is still
current. `wasmExecution` sets the backend and the module and guest-memory ceilings for WASM
handlers. `authentication.oidc.assertionIssuers` lists, per client, the assertion authorities
that client may exchange a subject token from; once written, a client it does not list may
exchange from none. Webhook destinations are bound in [Bind webhook receivers](../breg-webhooks/), field
encryption in [Field encryption for restricted fields](../../configure/breg-field-encryption/), and
the metrics listener in [Scrape metrics](../breg-monitor/#scrape-metrics).

### Create the secret files

Create the files as the user that runs `breg` and the operator commands. Each must meet the
[secret file rule](../../security/hardening-checklist/#secret-files): for example a regular file
you own with mode `0400` or `0600` and no other hard link. A name starts with a lowercase letter and uses
lowercase letters, digits, `.`, `_`, and `-`. The bytes are used exactly as written, so write them
without a trailing newline:

```sh
install -d -m 0700 /etc/breg/secrets
(umask 077; openssl rand -hex 32 | tr -d '\n' > /etc/breg/secrets/audit-key)
(umask 077; openssl rand -hex 32 | tr -d '\n' > /etc/breg/secrets/cursor-key)
(umask 077; printf '%s' 'postgresql://registry_runtime:<runtime-password>@db.example.org:5432/registry' \
  > /etc/breg/secrets/runtime-database-url)
(umask 077; printf '%s' 'postgresql://registry_migration:<migration-password>@db.example.org:5432/registry' \
  > /etc/breg/secrets/migration-database-url)
(umask 077; cp /path/to/database-root-ca.pem /etc/breg/secrets/database-ca)
```

The audit key and the cursor secret each need at least 32 bytes. Percent-encode a password that
carries reserved characters. The user in each URL must equal the role the file names under
`database.roles`. The URL needs no `sslmode` parameter: the runtime requires TLS itself.

In a container platform that injects secrets as environment variables, declare
`secretProviders.environment` and write `secret:env/<NAME>` instead.

## Provision PostgreSQL

Your runtime file already names the roles, their passwords, and the database. They are the URLs
in `database.migrationUrlRef` and `database.runtimeUrlRef`, and the roles under `database.roles`.
With the secret files in place, run `bregctl provision` once as a PostgreSQL role that can create
roles and databases. The runtime file's `package.root` must be a readable directory, though
`provision` reads nothing from it: create an empty one if the package does not exist yet.

```sh
bregctl provision --runtime-config /etc/breg/runtime.yaml --admin-url-file /etc/breg/admin-url
```

Pass `--posture` to declare the deployment posture. Provision lists all runtime
configuration refusals before it prints SQL or opens a database connection.
Its JSON report includes the resolved `posture` and its source.

{/* Evidence: crates/registry-bregctl/tests/provision_cli.rs, print_sql_reports_all_production_posture_refusals. */}

The `admin-url` file holds one PostgreSQL URL for that administrator, for example
`postgresql://admin:PASSWORD@db.example.org:5432/postgres`. The administrator needs `CREATEROLE`
and `CREATEDB` and does not need to be a superuser. To pass the URL in an environment variable
instead, use `--admin-url-env NAME`. The connection requires TLS and verifies the server
certificate. Set `database.caBundleRef` in the runtime file to trust a private CA. The command
never prints the administrator URL or a password.

The administrator URL must name the same host and port as the two product URLs, or `provision`
refuses it as `platform.provision.target-mismatch`. It must also name a database other than the
product database, such as `postgres`, or `provision` refuses it as `platform.provision.target-invalid`.
Where the administrator may connect only to the product database, `provision` cannot run: add
`--print-sql` and give the script to the person who administers the server.

The command:

- Creates the migration role and the runtime role, each with `LOGIN` and no other privilege.
- Creates the database and closes it to `PUBLIC`.
- Grants both roles `CONNECT` on the database.
- Installs `btree_gist`.
- Creates the five schemas the package fills, `registry_internal`, `registry_data`,
  `registry_source`, `registry_derived`, and `registry_context`, each owned by the migration role
  and closed to `PUBLIC`.

Run it again at any time. It creates only what is missing. It refuses a role that exists with
other attributes, and a role whose URL does not open a session, and tells you which.

Two roles are the split role mode, which production uses. The serving process then cannot write
the activation ledger or registry state, and `apply` and startup both refuse a runtime role that
could, naming the grant, ownership, membership, or trigger to remove. Keep the migration
credential off the serving host when no activation is in progress.

The schema-test database that `test` needs has the same shape. Point a copy of the runtime file
at it, as [Check, test, package](#check-test-package) describes, and run `provision` over that
copy too.

If a database administrator must run the SQL, add `--print-sql` and leave out the administrator
flags. The command connects to nothing and prints the script. Each `CREATE ROLE` is followed by a
`\password` line that prompts for the password in `psql`, so the script holds no password:

```sql
-- provision script, product breg. Nothing was run.
-- For a server where these objects do not exist yet. Review, then run with psql as an
-- administrator that has CREATEROLE and CREATEDB. It stops at the first error.
\set ON_ERROR_STOP on
SET createrole_self_grant = 'set,inherit';
CREATE ROLE "registry_migration" LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS;
\password "registry_migration"
CREATE ROLE "registry_runtime" LOGIN NOSUPERUSER NOCREATEDB NOCREATEROLE NOINHERIT NOBYPASSRLS;
\password "registry_runtime"
CREATE DATABASE "registry" WITH ALLOW_CONNECTIONS false;
REVOKE ALL ON DATABASE "registry" FROM PUBLIC;
GRANT CONNECT ON DATABASE "registry" TO "registry_migration", "registry_runtime";
ALTER DATABASE "registry" ALLOW_CONNECTIONS true;
\connect "registry"
CREATE EXTENSION btree_gist;
CREATE SCHEMA "registry_internal" AUTHORIZATION "registry_migration"; REVOKE ALL ON SCHEMA "registry_internal" FROM PUBLIC;
CREATE SCHEMA "registry_data" AUTHORIZATION "registry_migration"; REVOKE ALL ON SCHEMA "registry_data" FROM PUBLIC;
CREATE SCHEMA "registry_source" AUTHORIZATION "registry_migration"; REVOKE ALL ON SCHEMA "registry_source" FROM PUBLIC;
CREATE SCHEMA "registry_derived" AUTHORIZATION "registry_migration"; REVOKE ALL ON SCHEMA "registry_derived" FROM PUBLIC;
CREATE SCHEMA "registry_context" AUTHORIZATION "registry_migration"; REVOKE ALL ON SCHEMA "registry_context" FROM PUBLIC;
```

The names come from your URLs. Add `--format json` for a report of each statement and its outcome.

The migration role owns only those five schemas. It must not own the database (for example through
`CREATE DATABASE registry OWNER registry_migration`) and must not hold `CREATE` on it, because an
owner holds `CREATE` implicitly. `test` and `apply` check this before changing anything and refuse
with `migration role has database-level administrative authority`, which is also the refusal for a
role that is a superuser or has `BYPASSRLS`, `CREATEDB`, or `CREATEROLE`. If a managed PostgreSQL
service created the database for you, check its owner and its grants first.

`provision` grants the runtime role `CONNECT` on the database, and `USAGE` on the PostGIS schema
when `--package` names a package that needs PostGIS. It grants no `USAGE` on `public`. `apply`
grants the runtime role what serving needs. The package creates every table, function, and policy inside the five schemas. A missing
prerequisite surfaces at `test` or `apply`, never at runtime.

### Install PostGIS

For a project with polygon storage or bbox queries, PostGIS lives in a schema neither registry
role owns, and `CREATE EXTENSION postgis` needs a superuser. Pass the built package, and the
command adds the PostGIS steps for a package that needs them:

```sh
bregctl provision --runtime-config /etc/breg/runtime.yaml \
  --admin-url-file /etc/breg/superuser-url --package /var/lib/breg/build-1/package
```

Without `--package`, no PostGIS step is planned. As a role that is not a superuser, the command
stops at that statement with `platform.provision.statement-needs-privilege` at `extension.postgis`.
Run it with `--print-sql` and give the script to a superuser, or run it with a superuser URL, then
run `provision` again.

A package exists only after `test`, and `test` needs PostGIS in the schema-test database. For that
one database, a superuser runs the PostGIS statements by hand once. If the project grants bbox
queries, the statements also add a bounding-box role named after the runtime role with the suffix
`__spatial_bbox`:

```sql
CREATE ROLE registry_runtime__spatial_bbox NOLOGIN NOSUPERUSER NOCREATEDB
  NOCREATEROLE NOINHERIT NOBYPASSRLS;
GRANT registry_runtime__spatial_bbox TO registry_migration
  WITH INHERIT FALSE, SET TRUE, ADMIN FALSE;
-- in each database
CREATE SCHEMA registry_spatial_ext AUTHORIZATION postgres;
CREATE EXTENSION IF NOT EXISTS postgis WITH SCHEMA registry_spatial_ext;
REVOKE ALL ON SCHEMA registry_spatial_ext FROM PUBLIC;
GRANT USAGE ON SCHEMA registry_spatial_ext
  TO registry_migration, registry_runtime, registry_runtime__spatial_bbox;
```

For a package that stores polygons and grants no bbox queries, the statements above may leave out
the bbox role, its membership, and its name from the final `GRANT USAGE`. `provision --package`
plans the bbox role for every package that needs PostGIS, including that one. The role is unused
there: the runtime checks for it only when the package grants bbox queries. Keep the PostGIS
schema, extension, and grants to the migration and runtime roles.

If `provision` stops with `platform.provision.extension-incomplete` at `extension.postgis`, PostGIS
exists in the database but outside `registry_spatial_ext`, or the migration role cannot `SET` the
bbox role. As a superuser, drop a PostGIS installed in another schema, run the statements of the
`extension.postgis` step that `--print-sql` prints, then run `provision` again.

Size connections, timeouts, and statement statistics once the registry serves; see
[Set a PostgreSQL baseline](../breg-monitor/#set-a-postgresql-baseline).

## What a token must carry

The registry verifies a bearer access token before it reads any claim. Configure the issuer so
that every token for this deployment satisfies the table. Fixture claims from `journeys.yaml` are
never accepted by a running server.

| Token part | Requirement |
| --- | --- |
| `alg`, `typ`, `kid` headers | `alg` equals `allowedAlgorithm`; `typ` matches `accessTokenType` case-insensitively, and `at+jwt` and `application/at+jwt` are accepted for each other; `kid` is in the key set and absent from `revokedKeyIds`. |
| `iss` | Equals `issuer`. |
| `aud` | A string equal to `audience`, or an array of 1 to 16 distinct strings that contains it. |
| `exp`, `iat`, `nbf` | The lifetime is at most `maximumTokenLifetimeSeconds` (at most 7200); clock skew up to `leewayMilliseconds` (whole seconds, at most 300000) is tolerated. |
| `azp` or `client_id` | Listed in `allowedClients`, unless that is `unrestricted`. |
| `scope` | The one claim named by `scopeClaim` covers every required permission: a string split on `scopeSeparator`, or an array of strings. Permissions from several claims are not merged. |
| principal claim | The claim named by `authorityClaims.principal` carries the identity recorded in audit and workflow decisions. It must match each profile's `principalClaim`. |
| purpose claim | The claim named by `authorityClaims.purpose` is required when the profile lists `requiredPurposes`. |
| `registry_actor_kind` | A direct token must carry the configured actor-kind claim as `human`, `agent`, or `service`. A profile that declares `actorKind` requires an exact match; one that omits it accepts any verified direct kind. A verified trusted-actor exchange is always treated as `agent` and requires `actorKind: agent`, regardless of the copied subject claim. |
| assignment claims | Each row boundary or claim-backed lookup names its own claim. An `equals` boundary needs a scalar; an `in` boundary needs an array. |

Use the [Registry Stack access-token contract](../../configure/request-an-access-token/#token-profile-each-service-accepts)
for the canonical token profile and issuer integration rules.

Use a resource audience dedicated to this registry API, distinct from your application's login
client. An ID token issued to the login client is not an API credential. A longer token lifetime
extends how long an issued token may carry permissions you have since withdrawn.

### Identities that survive operations

Choose the principal claim deliberately. `sub` works when both the runtime file and the profiles
select it, and the server never falls back to another claim when the selected one is missing. An
issuer's `sub` usually belongs to that issuer alone, so if you may ever change issuer, prefer an
institutional identifier both issuers carry in a custom claim, and name who guarantees it is unique
and never reassigned. The registry treats the value as opaque and links no accounts across issuers;
changing it changes who is recognised as a submitter or a previous reviewer.

Use the same principal claim in an ownership row boundary when a record's owner field stores that
identifier, and separate claims for district, tenant, or team membership. Have the issuer derive
these claims from trusted assignments, never from values the caller supplies. A client-credentials
token represents a service, not a person signing in.

Rotating keys and changing the issuer are in
[Rotate keys and change the issuer](../breg-monitor/#rotate-keys-and-change-the-issuer).

## Check, test, package

These three commands turn the project into a package the database can activate. Run `check` with
the runtime file you will serve, so it also checks that file against the project:

```sh
bregctl check facility --runtime-config /etc/breg/runtime.yaml --production
```

```text
Production check passed; registry revision sha256:4877be0dd9ded0447278206d829445780bf93a6cee356bc1526773003acad158.
```

Warnings follow the success line. Read each one.

`check --production` declares production and checks package closure. A check
without the flag still defaults to production for the runtime file. Use
`--posture development` to report development settings as warnings in a laptop file.

### Ledger rules and migration authority

Each activation, the initial one included, is one row in `registry_internal.registry_migrations`, keyed by a UUID activation id and ordered by apply order.
A row names the package digest, the predecessor package digest, the registry revision, the plan kind (`initial` or `successor`), the role mode, any backups a destructive migration was bound to, and the keyed hash of `--operator-reference`.
`apply` accepts a successor only when its predecessor digest is the active package, and refuses the active package again and any older package.
The migration credential authorises an activation, and every activation is audited as `breg-activation-audit/v1`.
With separate migration and runtime roles, the runtime role cannot write the ledger, so it cannot change which package the runtime serves.
With one role for both, the ledger check catches mistakes but not someone holding that credential.

Authoring and migration authority are separate.
An author or coding agent can edit configuration, inspect a diff, and run checks, and those commands cannot obtain the production migration credential.
A runtime configuration without that credential is refused before initial production control-plane state or DDL is created.
One package is the unit you promote: plan and apply the same package directory, with the same package digest and registry revision, in each environment.
Only the runtime file's `identity` and database values differ.

The first successor on a database with the legacy 1,024-statement ledger bound widens that constraint when maintenance begins.
This engine catalog change remains if a later precondition or migration step fails.
Correct the cause and retry the exact pinned target; if it cannot complete and reconciliation reports `unresolvable`, restore the pre-activation backup.
A role change re-applies the active package and leaves the ledger bound as that package declares it.

### Row-security policies and catalog drift

Removing or narrowing an access profile removes its obsolete compiled row-security policies during apply.
Activation still requires the exact candidate catalog, and unexpected policies remain catalog drift that BReg does not delete.
A compiled policy whose expression was altered in place while it kept its definition comment is also refused as drift, and the activation fails.
Apply keeps a policy whose comment matches, so it does not repair one.
A database administrator recovers by clearing that policy's comment and applying the exact target package again, which replaces the policy with its compiled definition:

```sql
COMMENT ON POLICY name ON table IS NULL;
```

Do not edit managed tables to make a retry pass.

### Resolve signing keys

OIDC key resolution is deployment configuration, not governed package content.
If `authentication.oidc.jwksSource` is omitted, BReg uses discovery.
Name the key set location directly with `type: uri` and an `https` `uri` (plain `http` only on an IPv4 loopback host), which the verifier fetches and refreshes the way it does a discovered key set.
Or pin a static document through a protected secret reference:

```yaml
authentication:
  oidc:
    jwksSource:
      type: static
      documentRef: secret:file/oidc-jwks
```

The static document must be a bounded, duplicate-free set of public keys that matches the configured algorithm, signature use, verification operation, key identifier policy, and key shape.
BReg resolves it once when the verifier is constructed, so rotation requires a reviewed configuration change and a process restart.

### Plan the reference-lifecycle upgrade window

An active Record can reference only an active target Record.
Create and patch, including batch and import writes, refuse a missing or tombstoned target.
Tombstoning a target refuses while another active Record references it, even when that referencing Record is outside the caller's read permissions.
These refusals use the generic `409 mutation.conflict` response and disclose no referencing Record IDs or values.
Action and Proposal target admission continues to require its independently granted current authority.
A writer authorised to submit a known target ID can still infer whether that target is lifecycle-eligible from success versus conflict, even without target read authority.
The conflict does not distinguish a missing target from a tombstoned one or disclose target fields.

Clear an optional reference, point it at an active replacement, or tombstone the referencing Record before you tombstone its target.
Tombstoned Records and retained history keep their original reference IDs.
A self-reference does not prevent tombstoning that same Record; active references from other Records do.
There is no automatic cascade or clearing of references.

A registry activated by a package built before this release cannot be upgraded in place. Create a fresh database, rebuild the package with this release, and run `bregctl apply --package DIR --initial`. Later successor packages built with the deployed package as `--baseline-package` receive these constraints.
Use `bregctl plan` to check the activation prerequisites.
Before live maintenance, apply the successor to a representative restored-data copy to validate existing links.
If that apply finds an active Record that references a tombstoned target, repair its reference or tombstone that Record through the current package, refresh the restored-data copy, and repeat the validation before you activate the successor in production.

Plan a maintenance window for this upgrade.
Adding the stored generated lifecycle column rewrites each reference source table.
Adding the target's unique lifecycle key and temporarily changing `FORCE ROW LEVEL SECURITY` on the source and target take `ACCESS EXCLUSIVE` locks, and PostgreSQL holds the locks from the force changes while it validates existing links.
An additive activation runs its compiler DDL, runtime grants, and exact target catalog verification in one transaction, so a validation or fingerprint refusal rolls that DDL back.
Maintenance still pins the exact target for recovery, and the check runs during apply, not in a successor `plan` before maintenance.
A reviewed activation commits compiler and authored steps at durable checkpoints.
A later reference validation refusal leaves those earlier checkpoints in place and pins maintenance as failed, so follow the exact-target retry, reconciliation, or backup-restore procedure in [Change an active registry](../breg-changes/#recover-a-failed-activation).

## Serve the container image

The image runs `breg --runtime-config /etc/breg/runtime.yaml` as the non-root user UID 65532,
exposes port 8080, and carries the matching `bregctl` at `/usr/local/bin/bregctl`. It has no shell,
no writable directory, and no health check of its own.

The container serves only a package that activation already recorded. Write a second runtime file
for it, changing exactly four things from the host's: `listener.bind` (to `0.0.0.0:8080`),
`secretProviders.file.root` (to `/etc/breg/secrets`), `package.root` (to `/var/lib/breg/package`),
and the database host name in the connection URLs, because the container mounts its own paths and
reaches the database over its own network.

UID 65532 must own the secrets directory, every secret file in it, and the audit directory, with
mode `0700` on each directory. The mounted package need only be readable by it.

Startup refuses the runtime file unless it and every directory above it, as the container sees
them, are owned by root or the runtime user (UID 65532 in the images) and not writable by group or
others. A symbolic link anywhere in the path is refused. The mount below places one file under
directories the image owns, so only the file itself needs changing:

```sh
chown 65532:65532 /srv/registry/container/runtime.yaml
chmod 0400 /srv/registry/container/runtime.yaml
chown -R 65532:65532 /srv/registry/container/secrets
chmod 0700 /srv/registry/container/secrets
install -d -m 0700 -o 65532 -g 65532 /var/log/breg
chown -R 65532:65532 /var/log/breg
```

Startup refuses an audit directory or audit file owned by anyone else, including a directory Docker
created as root for a missing mount and one a host-run `breg` or `bregctl` left behind. Once the
container owns `/var/log/breg` and the runtime file, a host-run `bregctl` is refused them in turn,
so plan and apply [from the image](#activate-from-the-image).

Then mount the inputs read-only and the audit directory writable:

```sh
docker run --restart on-failure \
  -p 8080:8080 \
  -v /srv/registry/container/runtime.yaml:/etc/breg/runtime.yaml:ro \
  -v /var/lib/breg/build-1/package:/var/lib/breg/package:ro \
  -v /srv/registry/container/secrets:/etc/breg/secrets:ro \
  -v /var/log/breg:/var/log/breg:rw \
  "$BREG_IMAGE"
```

`BREG_IMAGE` is the image digest from the release manifest. Run `bregctl verify` and
`bregctl doctor` from the image against this exact runtime file before you rely on its
`GET /ready`. A fault that recurs on every start makes the container restart repeatedly; the
restart policy's backoff bounds how often.

### Activate from the image

You can plan, apply, and read the ledger from the same image you serve, without installing
`bregctl` on an operator host. Override the entrypoint and pass the arguments
[Activate and serve](#activate-and-serve) uses, with the container's paths:

```sh
docker run --rm \
  --entrypoint /usr/local/bin/bregctl \
  -v /srv/registry/container/runtime.yaml:/etc/breg/runtime.yaml:ro \
  -v /var/lib/breg/build-1/package:/var/lib/breg/package:ro \
  -v /srv/registry/container/migration-secrets:/etc/breg/secrets:ro \
  -v /var/log/breg:/var/log/breg:rw \
  "$BREG_IMAGE" \
  plan --runtime-config /etc/breg/runtime.yaml --package /var/lib/breg/package
```

Run `apply` and `status` the same way. These commands connect with the migration credential, so
mount a secret directory that holds it, and keep that credential out of the serving container's
secret directory. Give UID 65532 that directory and its files the same way as the serving
container's. `apply` writes audit entries beside `audit.path`, which is why the audit directory is
writable here too.

Kubernetes is outside the verified deployment profile. A ConfigMap or Secret volume mounted the
default way presents each key as a symbolic link, which the runtime refuses for the runtime file.
Secret files accept the link chain Kubernetes writes under the
[secret file rule](../../security/hardening-checklist/#secret-files), which gives the volume
settings that rule needs.

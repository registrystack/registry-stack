If you operate Registry Casework, this page sets how long a review is kept, what the audit journal
records, and how a producer collects a result before it is gone. It uses the project from
[Decide your first ReviewRequest](../../tutorials/first-casework/); the commands read a deployment,
so none is replayed here.

## Retention windows

A retention window is how long Casework keeps a part of a review after the request settles. The
policy author sets two of them per `ReviewPolicy`, in `casework.yaml`:

```yaml
    retention:
      terminalRetentionDays: 90
      accountabilityRetentionDays: 365
```

- `terminalRetentionDays` keeps the review itself: submitted context, tasks, notes, decisions and
  the result. It is from 1 to 3,650 days.
- `accountabilityRetentionDays` keeps the [accountability record](../../reference/glossary/#accountability-record):
  who decided and the private reason. It is at least as long as the terminal window and at most
  3,650 days.

Both run from the request's terminal settlement; a request still under review has no expiry. Each
trusted producer also sets how long its admission receipt can be recovered:

```yaml
    retention: {receiptRetentionDays: 30}
```

## Keep erasure running

[Erasure](../../reference/glossary/#erasure) runs inside `casework serve`; there is no separate
job or command. The maintenance worker runs a retention pass about once a minute, and each pass
erases at most 100 eligible requests and skips rows another transaction holds, so a backlog drains
over several passes. Erasure starts only while the audit writer is ready, and each erasure is
recorded in the audit journal.

## Recover before the result window closes

The result carries its own deadline, `availableUntil`: its settlement time plus
`terminalRetentionDays`. Until then the producer reads it, and a request that is still under
review answers `202`. After it, the result read answers `410` with no body.

A producer that lost the admission response retries the same body under the same
`Idempotency-Key` within its receipt window; Casework answers `200` with the request it already
accepted, rather than `201`. A changed body under that key is refused, not admitted.

## Completion destinations

A completion destination is the producer's URL Casework calls when a result is ready. The call
carries no decision; the producer then reads the result. Each destination is declared under
`reviewCompletionDestinations` in the [runtime configuration](../casework/#casework-runtime-configuration),
keyed by the destination id the producer names in `casework.yaml`.

A failed call returns to the queue and is tried again after `retryDelaySeconds` (default 30), up to
`maximumAttempts` (default 12), each attempt bounded by `attemptTimeoutMilliseconds` (default
5000). Delivery stops when the attempts run out or the result window closes; the result stays
readable until `availableUntil`.

## Keep the audit file

The [audit journal](../../reference/glossary/#audit-journal) is the file Casework appends one line
to before each admitted operation and one after it commits. This is the request line of the
decision in the first tutorial:

```sh test-skip="reads a deployment's audit journal; the line was observed in the development session's journal"
rg '"casework.review-decided"' /var/lib/registry-casework/audit.ndjson
```

```text test-excerpt
{"schema":"registry-casework-audit/v1","eventId":"<id>","time":"<time>","phase":"request","correlation":"<id>","record":{"event":"casework.review-decided","principalPseudonym":"<pseudonym>","profileId":"staff"}}
```

The journal names people and records only by keyed pseudonym and carries no context, reason or
result. Its location, key, rotation and local retention are `audit.path`, `audit.hashKeyRef`,
`audit.rotateBytes` and `audit.retentionDays` in the
[runtime configuration](../casework/#casework-runtime-configuration). Entries are neither chained
nor signed, so ship sealed files to an archive you control, and keep the key as long as you need
to recompute pseudonyms; [audit key handover](../advanced/back-up-and-restore/#hand-over-the-casework-audit-key)
covers rotation.

{/* Evidence: crates/registry-casework/src/audit.rs, CASEWORK_AUDIT_SCHEMA and published_audit_record();
    crates/registry-platform-audit/src/writer.rs;
    crates/registry-casework/src/config.rs. */}

A refused audit write fails the operation with `service.unavailable` and `/ready` answers `503`
until you repair the destination and restart. A database restore can bring back data that was
already erased; [Back up and restore Casework](../advanced/back-up-and-restore/#restore-registry-casework)
gives the order of recovery.

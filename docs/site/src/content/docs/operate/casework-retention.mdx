If you operate Registry Casework, choose review retention with the policy author, keep the maintenance worker and audit destination healthy, and make sure producers collect results before they expire. Review payloads, protected accountability, short-lived staffing state, and the external journal have different retention boundaries.

## What Casework retains

Each `ReviewPolicy` declares `terminalDays` and `accountabilityDays`. The terminal period is at least one day; accountability is at least as long and at most 3,650 days. Both periods run from the request's terminal settlement. A request still under review has no terminal expiry yet; an overdue clock does not itself erase or cancel it.

| State | Retention boundary |
| --- | --- |
| Submitted context, result, constraints, notes, drafts, decisions, tasks, history, and clock occurrences | Request terminal time plus `terminalDays` |
| Producer result-feed event and completion wake | The same terminal result availability period |
| Protected deciding identity, private reason, configured outcome, and structured-result digest | Request terminal time plus `accountabilityDays` |
| Producer and initiator identities | Raw until payload expiry, then request-bound identity tombstones until accountability expiry |
| Mutation replay response | Payload erased at terminal expiry; replay metadata persists until accountability expiry |
| Submission recovery reservation | A fixed recovery deadline from admission; accepted reservation retention follows terminal accountability expiry |
| Review/staffing cursors and preview snapshots | Their own bounded expiry, separate from review result retention |
| Audit journal | File rotation/retention settings and your external archive policy |

Current-source business projections are read under the caller's source authority rather than retained as review snapshots. Casework still retains the subject and context binding, policy closure, decisions, and derived task metadata needed for the review. A submitted snapshot is retained review data, so keep its schema and content limited to the purpose.

Each request owns its clock budget. A later request after changes were requested gets a new budget; it does not resume a prior request's clock. Clock erasure follows the request that owns it.

## Keep automatic erasure running

Run the normal serving process to enforce the configured retention:

```sh
casework --runtime-config /etc/registry-casework/runtime.yaml serve
```

The maintenance loop runs review retention about once a minute. A review pass selects at most 100 eligible requests and skips locked rows, so a backlog drains over several passes. At result expiry it erases private payloads and task/history/clock state, scrubs subject and context fields, and retains bounded metadata for expired-operation recovery. At accountability expiry it removes the protected records and remaining request/replay state. An expired unbound recovery reservation has a separate bounded cleanup.

Staffing preview and cursor cleanup runs in the same maintenance cycle, with up to 1,000 expired rows per table in an admitted transaction. An unexpired cursor or preview never extends the review's payload retention.

Erasure starts only while the audit writer is ready. Successful changes publish minimized audit responses; no-op passes add no domain event. If the writer stops, retention pauses without deleting the selected data. If response publication fails after commit, erasure may already have happened; restoring audit and retrying maintenance does not recreate the data or duplicate an erasure event.

Inspect `/ready` and runtime warnings for failed retention, staffing retention, or audit writes. Repair the dependency and let the next bounded pass run. There is no supported command to force immediate per-subject erasure. If you need an earlier terminal boundary, the admitted producer can cancel a review under its existing authority; cancellation starts the configured retention periods rather than deleting the payload immediately.

## Recover before the result window closes

Have the producer store the accepted request identifier, original idempotency key, exact submitted body, and fixed recovery deadline. A lost admission response is recovered by retrying that same body and key. A changed body under the key is a conflict, not another submission.

Fetch the immutable result through the producer's authenticated result endpoint or result feed before its availability deadline. A completion delivery is only a payload-free wake to fetch that result; it does not carry a decision, apply a source change, or start another workflow. The producer must authorize any later mutation independently.

After payload expiry, an exact replay can return `idempotency.expired` with HTTP `410`, while a changed request under the same retained key returns `idempotency.key-reused`. Reconcile the original operation with the producer's records rather than selecting a new key to hide uncertainty. The corresponding tombstone is eventually removed at its retention boundary; a forgotten key is not evidence that the operation never happened.

A serving Supervisor can resolve an authorized accountability event while its protected record remains retained. That record can identify the deciding person and private reason, but does not release the review context or structured result. Ordinary own-decision receipts omit those private fields.

## Keep the audit file

Casework uses the external journal for admitted operations. A requested mutation writes its request entry before the transaction and its response after commit. An idempotent replay has a minimized terminal response. Background clock, absence, retention, and cursor work uses readiness admission and minimized response entries without a caller request. Entries share a correlation and carry `registry-casework-audit/v1`.

The journal pseudonymizes review requests, tasks, grants, teams, queues, and principals. It omits context fields, free-text reasons, structured results, cursor tokens, and preview contents. Retention cleanup may include a generated erased-row count. Protected accountability is a separate database record, not a way to reverse an audit pseudonym. Audit entries are not chained or signed; tamper evidence comes from the archive you operate.

{/* Evidence: crates/registry-casework/src/audit.rs, CASEWORK_AUDIT_SCHEMA, published_audit_record(), and AuditOperation;
    crates/registry-casework/tests/support/maintenance_audit_regressions.rs;
    crates/registry-platform-audit/src/writer.rs. */}

Provide at least 32 bytes of audit key material through a declared secret provider. For a mounted file, create it under the runtime user's controls:

```sh
(umask 077 && openssl rand -hex 32 > /run/secrets/registry-casework/casework-audit-key)
chmod 0400 /run/secrets/registry-casework/casework-audit-key
```

Provision the parent directory first and run the command as the intended owner. Set `audit.hashKeyRef: secret:file/casework-audit-key`. The exact file bytes, including any trailing newline, determine the pseudonyms. Keep the key and its backups protected for as long as you need to recompute references in the archive. A key rotation changes pseudonyms; use a new audit path and record that boundary, as [audit key handover](../advanced/back-up-and-restore/#hand-over-the-casework-audit-key) describes.

With `destination: file`, the writer seals files when the next entry would exceed `audit.rotateBytes`, then opens a new active file. Defaults are 100 MiB per file and 90 days for sealed files. Ship sealed files before local expiry and archive the final active file when retiring a path. With `destination: stdout`, your collector owns collection and retention. Never restore an older journal over the live archive.

## Recover from audit failure

A refused file write fails the sensitive operation with `service.unavailable`, stops that writer, and makes `/ready` return `503`. Repair free space, ownership, permissions, or the single-writer path, then restart the process. A response failure can follow a committed database change: retry with the original key/body or inspect the result before choosing another operation.

A blocked stdout collector can stall the writer. After its write deadline, readiness and audited calls fail until the stream drains. Restore the collector; this transient stall can recover without restarting. Keep process health separate from audit readiness when alerting.

For activation, `casework.activation.applied-unaudited` explicitly means apply committed before its audit response failed. Confirm the active package through `caseworkctl status`, restore audit, and record the recovery instead of treating the failed command as a rollback.

## Verify retention and recovery

Include an expiry and lost-response case in your isolated deployment acceptance checks. Use synthetic review data and the intended producer, reviewer, and Supervisor roles. Confirm that producer polling works before expiry, payload reads stop after expiry, accountability remains available only to its authorized audience, and no role recovers context from the journal. Do not alter production timestamps or database rows to test expiry.

A database restore can reintroduce expired data and lose later decisions. Reconcile the lost window before reviewers resume and let maintenance repeat due erasures. [Back up and restore Casework](../advanced/back-up-and-restore/#restore-registry-casework) gives the operational boundary.

You have a package built with `registry-render package` and callers that need PDFs. When you are
done, one `registry-render serve` process serves that package on a private address behind your
TLS proxy, under API-key authentication, with an audit file you ship to append-only storage.
[Render your first document](../../tutorials/first-render-document/) builds a package.

Registry Render is pre-1.0 and an
[experimental surface](../../reference/api-stability/#experimental-surfaces), outside the
compatibility promise.

## What you provide

- **One package directory, mounted read-only.** Serve verifies it at startup and in the worker on
  every request, and refuses a package that changes while it runs.
- **One API key in an owner-only file.** At least 32 bytes of ASCII. Serve trims one trailing line
  ending and refuses any other whitespace, because a mis-read key would reject every caller while
  health stays green.
- **A writable audit directory, or a log collector on standard output.** Serve refuses a directory
  that group or others can write.
- **A TLS proxy in front.** The listener serves plain HTTP, reads no forwarded header, and accepts
  only a loopback, private, or link-local address.
- **A host for one process and its render workers.** Each render runs in a worker that is killed at
  the timeout and, on Linux, capped in address space.

## Install the binary

Releases from v0.38.0 attach a Linux amd64 binary, `registry-render-<tag>-linux-amd64`. Choose
`<tag>` from the [latest release](https://github.com/registrystack/registry-stack/releases/latest),
verify the asset with that release's `release/VERIFY.md`, then install it. This replaces any
existing `~/.local/bin/registry-render`, so keep a copy first when you need a rollback:

```sh
tag="${TAG:?set TAG to a published tag that includes Registry Render}"
mkdir -p ~/.local/bin
install -m 0755 "registry-render-${tag}-linux-amd64" ~/.local/bin/registry-render
export PATH="$HOME/.local/bin:$PATH"
registry-render --version
```

```text
registry-render <version> (typst 0.15.1)
```

Record that line: every audit entry carries the same version, and a stored PDF's provenance is
this binary plus the package digest. On another platform, build from a checkout as the tutorial
does; the workspace lockfile is part of Render's byte contract, so always build with `--locked`.

The same release publishes the image `ghcr.io/registrystack/registry-render:<tag>`. It runs
`registry-render serve` with `/etc/registry-render/runtime.yaml` from Distroless `cc-debian13` as
the `nonroot` user (UID 65532), with `/var/lib/registry-render` as its working directory, and holds
no package. Mount the runtime file and the package read-only. Keep the API key owned by UID 65532
with mode `0400` or `0600`, and the audit directory owned by UID 65532 with mode `0700`. Deploy by
the digest `release/VERIFY.md` authenticates. A proxy in another container reaches Render on its
private container address, so set `listener.bind` to that address; `0.0.0.0` is refused.

## Write the runtime configuration

Serve reads one YAML file. Unknown keys are refused, and the
[configuration reference](../../reference/render-configuration/) lists every key with its range
and default:

```yaml
apiVersion: id.registrystack.org/formats/render/runtime/v1alpha1
kind: RenderRuntimeConfig
listener:
  bind: 127.0.0.1:8080
  shutdownGraceMilliseconds: 30000
package:
  root: /var/lib/registry-render/package
  expectedDigest: sha256:<package-digest>
secretProviders:
  file:
    root: /run/secrets/registry-render
auth:
  apiKeyRef: secret:file/render-api-key
limits:
  renderTimeoutSeconds: 20
  maximumConcurrentRenders: 4
audit:
  path: /var/lib/registry-render/audit/render.jsonl
```

These rules are not in the tables:

- `package.root` is an absolute path with no `.` or `..` segment; `audit.path` and
  `secretProviders.file.root` are absolute paths.
- In `manifest.yaml`, each document's `entryFile` and `schemaFile` is relative to the bundle root
  and contains no `..`.
- `package.expectedDigest` is optional; when set, serve refuses any other package.
- `secret:file/<name>` resolves under `secretProviders.file.root`. `secret:env/<NAME>` works only
  when `secretProviders.environment: {}` is declared. A reference to an undeclared provider is
  refused.
- A string value may come from the environment as `${VAR}`, `${VAR:-default}`, or
  `${VAR:?message}`, except in `apiKeyRef` and under `secretProviders`.
- `audit.destination: stdout` hands entries to your collector and takes no `path`.
- `shutdownGraceMilliseconds` is how long in-flight renders get to finish on SIGTERM; open
  connections then get the same again. Align it with your supervisor's stop timeout.

## Check the configuration

Check the file before you deploy it. The check runs offline and reads no secret, so the package,
key, and audit directory need not exist yet. Pass the absolute path serve will use, because serve
refuses a relative one that check accepts:

```sh
registry-render check --runtime-config /etc/registry-render/runtime.yaml
```

```text
0 errors, 0 warnings in 1 file
```

A refused file lists every finding with its position and fix, and exits 1:

```text
registry-render check refused the input.
error[render.runtime.public-bind] /etc/registry-render/runtime.yaml:4:9 /listener/bind
  listener.bind is not a loopback, private, or link-local address; Render never listens publicly or on all interfaces
  next: Bind the private address your proxy forwards to; the proxy terminates TLS.
1 error, 0 warnings in 1 file
```

A `${VAR}` value is left for the deployment unless you add `--environment`, which substitutes it
from the current environment first. In a container preflight, add `--require-audit-under
<directory>` to prove the audit file lands on persistent storage:

```text
audit file resolves under /var/lib/registry-render/audit
0 errors, 0 warnings in 1 file
```

It refuses a `stdout` destination, and a path outside the directory with
`error[render.runtime.audit-outside-root]`.

## Start and verify

```sh
registry-render serve --runtime-config /etc/registry-render/runtime.yaml
```

Serve logs JSON lines to standard error, starting with `registry-render serve starting` and the
package and configuration digests. If it refuses the file, it prints the same findings as check,
prefixed `registry-render: runtime-invalid: the runtime configuration was refused`, and exits 20.

Probe both endpoints before you route traffic:

```sh
curl -s http://127.0.0.1:8080/health
curl -s http://127.0.0.1:8080/ready
```

```text
{"bundleHash":"<package-digest>","bundleVersion":1,"rendererVersion":"<version> (typst 0.15.1)","status":"ok","typstPin":"0.15.1"}
{"status":"ready"}
```

`bundleHash` is the package digest without `sha256:`; compare it with what you deployed.
Readiness includes the audit writer, so it fails when the writer stopped or a `stdout` collector
stalled. A stalled collector recovers when it reads again; a stopped writer needs a restart, as
[audit retention](../retention-and-persistent-state/#audit-retention) describes. A supervisor can
run the same probe:

```sh
registry-render healthcheck --runtime-config /etc/registry-render/runtime.yaml
```

```text
healthy at 127.0.0.1:8080
```

One process writes one audit file. A second process pointed at the same path does not start:

```text
registry-render: audit-failed: cannot open audit destination: audit sink single-writer lock is already held by another writer: /var/lib/registry-render/audit/render.jsonl.lock
```

Give each replica its own audit path.

## Answer callers

Callers POST one JSON body to `/v1/render/<document-type>` with the API key. Keep the key off the
command line: write the header to a file only the caller reads, as
[the tutorial](../../tutorials/first-render-document/) does, and pass the file.

```sh
curl -s -X POST http://127.0.0.1:8080/v1/render/<document-type> \
  -H @auth.header \
  -H "Content-Type: application/json" \
  -d '{"issuedAt":"<issuance-time>","data":<document-data>}' \
  -o document.pdf -D headers.txt
```

The answer is the PDF with `x-registry-pdf-sha256`, `x-registry-data-sha256`, and
`x-registry-document-version` headers. With `Accept: application/json` it is a JSON object with
`pdfSha256`, `dataSha256`, `documentVersion`, `warnings`, and the PDF as `pdfBase64`.

Requests must carry `Content-Length`; a chunked body is refused with `invalid-argument`, because
one that passes the limit mid-stream could not be answered. `Idempotency-Key` is echoed and
recorded as an opaque correlation id; rendering is deterministic, so nothing is deduplicated.
`registry-render validate --bundle <package> --type <document-type> --data <file>` checks data
against the document's schema without rendering.

Failures are RFC 9457 problem documents from a closed vocabulary, such as `data-invalid` (400),
`unknown-document` (400), `unauthorized` (401), `body-too-large` (413), `render-timeout` (504),
and `audit-failed` (503).

## Seal documents

Sealing is optional. Without a `signing` block, Render loads no key, makes no timestamp call, and
serves no seal route. With one, `POST /v1/seal/<document-type>` renders the document and returns
it with a PAdES signature made with your institution's key. Render seals only what it just
rendered from the verified package, never bytes a caller sends, and the private key stays in the
serving process, never in a render worker. The seal is PAdES baseline B-B or B-T. Render makes no
claim that it is a qualified seal under eIDAS or any other scheme: that depends on your
certificate, its issuer, and how you hold the key.

### Enable a seal

You need an OIDC deployment (a seal never works with the legacy API key), a seal certificate chain
in a PEM file with the seal certificate first, and its private key as one ES256, ES384, RS256, or
RS384 JWK. Name the seal in the document type's `manifest.yaml` entry with `seal: ministry`, then
bind it in the runtime file:

```yaml
auth:
  oidc:
    issuer: https://issuer.example.invalid
    audience: urn:example:render
    allowedClients: [portal, records-service]
signing:
  seals:
    ministry:
      privateKeyRef: secret:file/seal.jwk
      certificateChainFile: /etc/registry-render/seal/chain.pem
      timestampAuthority:
        url: https://tsa.example.invalid/tsr
        attemptTimeoutMilliseconds: 10000
      allowedClients: [records-service]
```

- `allowedClients` is required and names each client allowed to seal. When `auth.oidc.allowedClients`
  lists clients, each seal client must also be in that list, or Render refuses the file. Keep these
  separate from any citizen-facing client. `unrestricted` and wildcards are refused.
- Callers need the `render:seal` scope. `render:render` does not imply it.
- `timestampAuthority` timestamps each seal (B-T), so it keeps validating after the certificate
  expires. Declare `withoutTimestamp: seal-stops-validating-when-certificate-expires` instead to
  seal without a timestamp (B-B), and accept that the seal stops validating at expiry. Declare
  exactly one.
- A failing timestamp authority fails the request with `timestamp-failed` (502). Render does not
  retry and never returns an untimestamped file in its place. The audit's response entry and one
  `seal refused` log warning name the failing check as `reason`, such as `timed-out` or
  `nonce-mismatch`; the
  [configuration reference](../../reference/render-configuration/#seal-documents) lists them.

Run `registry-render check --bundle <package> --runtime-config runtime.yaml --environment`. It
reads each chain file, never the key, and it fails on an unreadable or malformed chain, a seal
certificate without a signing key usage, or a chain too large for the signature space. It warns
about a certificate that is expired, not yet valid, or expires within 30 days. When `serve`
starts, it also checks that the key matches the certificate, and it refuses to start if it does
not. If the runtime names a seal the package does not use, or the package names a seal the
runtime does not bind, `check` reports it, and `serve` refuses the second case.

Then call the route with a token that carries `render:seal`. The request body is the render
route's. The PDF answer carries `X-Registry-Document-Sha256`, `X-Registry-Signed-File-Sha256`,
`X-Registry-Seal-Id`, `X-Registry-Seal-Level` (`b-t` or `b-b`), and
`X-Registry-Certificate-Sha256`, plus `X-Registry-Timestamp-Time` for B-T. It also carries
`X-Registry-Bundle-Hash` (`bundleHash` in JSON), so a client that holds only `render:seal` can
compare the package with what you deployed without reading `/v1/documents`. A document type that
names no seal is refused with `document-not-sealable` (400). The
[configuration reference](../../reference/render-configuration/#seal-documents) lists the keys,
problems, and response shapes.

### Use a test seal in development

Issue a test certificate from your own test authority and set `trust: test-only` on the seal. The
template then receives `signing.testOnly: true` in its payload on the seal route, and can print a
visible test marking (the payload contract is `products/render/PAYLOAD.md` in the repository); the
`registry-render init` scaffold prints it. Render also says so where a template cannot hide it:
`testOnly: true` in the JSON answer's `seal`, in `/ready` and in the audit, an
`X-Registry-Seal-Test-Only: true` header on the PDF answer, and one `test-only seal` warning per
seal when `serve` starts. Use a loopback timestamp authority (`http://127.0.0.1:<port>/...`
is accepted on loopback only) or `withoutTimestamp` while you develop. Never copy a test seal's
runtime into production.

### Renew the certificate

Run `check --environment` on a schedule. Thirty days before expiry it warns with
`render.runtime.seal-certificate-expiring`. To renew, write the new chain file with the seal
certificate first, point `certificateChainFile` at it (or replace the file), and restart `serve`:
Render reads the chain at startup. After the old certificate expires the seal is unavailable and
plain rendering is unaffected. A file sealed earlier with a timestamp is built to keep validating after the certificate expires,
subject to the validator's trust decisions; a file sealed without one stops validating at expiry.

### Read readiness

When seals are configured, `/ready` adds a `signing` member with one entry per seal id. Each is
`{"status": "ready"}` or `{"status": "unavailable", "reason": ...}`, where the reason is
`certificate-expired`, `certificate-not-yet-valid`, or `provider-not-ready`. A seal never changes
the status code: Render stays ready for plain rendering while a seal cannot sign, and a seal
request answers `signing-unavailable` or `seal-certificate-invalid` (503) until it can. Readiness
reads the certificate validity and the key provider; it never calls the timestamp authority, so a
ready seal can still fail with `timestamp-failed`.

### Reconcile audit hashes with your records

A seal call writes a `request` entry and a `response` entry that share `correlation`, like any
render. Both carry `sealId`. The `response` entry adds `documentSha256` (the first revision, the
document Render rendered), `signedFileSha256` (the whole signed file), `certificateSha256`,
and, for B-T, `timestampTokenSha256`. Store the two document hashes with the record. To check a
stored file against the audit:

```sh
sha256sum signed.pdf
```

The digest must equal `signedFileSha256` in the response entry. A sealed file has no `pdfSha256`;
two seals of the same request differ in their signed bytes, because each carries its signing
time, but their first revision is the same. The audit never holds a certificate subject, a signer
name, a key, or a token.

### What a citizen's PDF viewer shows

A PDF viewer decides trust from its own trust list. When your seal's issuing root is not in a
viewer's list, the viewer may show the signature as "validity unknown". That is the viewer's
verdict on the issuer, not a failure of the file's integrity.

### Know the limits

- The signature field is invisible. A template prints any visible seal block from the payload's
  `signing` member.
- Render embeds no revocation data (no B-LT or B-LTA) and does not pin the timestamp authority's
  identity; validators decide trust in both.
- The seal key comes from a secret reference to a local JWK. That suits development and pilots.
- A render worker starts from an empty environment but is not a sandbox. A worker that gained code
  execution could get arbitrary content sealed, because it renders the content.
- Sealing documents that render to PDF/A-1, A-2, or A-3 has not been verified.

## Keep the audit file

Each line is one entry with `schema` (`render.registrystack.org/audit/v1`), `eventId`, `time`,
`phase`, `correlation`, and a value-free `record`: hashes, versions, the caller's key fingerprint,
and the outcome. To list outcomes:

```sh
jq -c '{correlation, phase, outcome: .record.outcome, problem: .record.problem}' \
  /var/lib/registry-render/audit/render.jsonl
```

A call that reaches the renderer writes a `request` entry before the render starts and a
`response` entry before the answer leaves; both share `correlation`. Data the schema rejects is
found inside the render, so it also writes both. A refusal before the render, such as an unknown
document type or a chunked body, writes one `response` entry. If any of these writes fails, the
call fails closed with `audit-failed`. A wrong key or an oversized body also writes one entry, but
if that write fails the refusal is still answered and the failure is logged. A call whose caller
disconnects is recorded as `unfinished`.

When the active file would pass `rotateBytes`, it is renamed to `<path>.<sequence>` and a new file
opens. At startup and at each rotation, sealed files older than `retentionDays` are deleted. The
file is not chained or signed, so ship sealed files, or the `stdout` stream, to append-only storage
before retention deletes them.

:::danger
Never rename, edit, or truncate the active file while the process runs. The writer then stops, and
every render fails closed with `audit-failed` until a restart.
:::

## Upgrade

A Typst, compression-library, or template change can change output bytes. Build every template
change into a new package directory and point `package.root` at it; `registry-render package`
refuses an existing directory, so a published digest never gains different bytes. Before you
switch to a new binary, render a stored request with it and compare `pdfSha256` with the stored
value. A changed hash means documents rendered after the switch differ from earlier ones.

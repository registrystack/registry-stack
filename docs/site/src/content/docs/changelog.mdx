## v0.43.0 beta-55

  Base Registry Engine (BReg) Records cannot reference tombstoned targets. Build a successor package against
  the deployed baseline, validate it on a representative restored-data copy,
  repair invalid active references through the current package, and repeat
  validation before activating the successor and switching runtimes.
  `bregctl plan` does not inspect live rows. See
  [upgrade and retire](../operate/advanced/upgrade-and-retire/).

{/* Evidence: products/breg/CHANGELOG.md, "enforce active reference integrity";
    release/scripts/rehearse-upgrade.py, FORWARD_PATH_FLOOR. */}

  equivalent peer labels warn unless `--deny-warnings` is selected. Discovery's
  current parser checks `title` and `description`, while its immutable v1alpha1
  schema, context, and SHACL remain unchanged. See
  [configuration files](../reference/configuration-files/).

{/* Evidence: products/platform/CONFIG-CONVENTIONS.md, CFG-VAL-11 and CFG-ID-8;

  to `v1alpha6`, proposals to `v1alpha2`, and lifecycle to `v1alpha7`; select their matching schemas

## v0.42.0 beta-54

- BREAKING: v0.42.0 reads no state that v0.41.0 wrote. The Base Registry Engine (BReg) carries no
  state migration from v0.41.0 and names no refusal for an earlier database, so point it only at a
  fresh one. Casework, Scheduling, and Messaging each install their schema as one baseline
  numbered 100 and refuse a ledger below it at `plan`, `apply`, and startup. Evidence needs a newly authored normalized
  project, target, and target authority. Migration: finish, drain, or record open work, keep each
  v0.41.0 database unchanged for reconciliation and rollback, and apply the v0.42.0 packages to
  fresh databases as [upgrade and retire](../operate/advanced/upgrade-and-retire/) describes. See
  [upgrades and state](../reference/api-stability/#upgrades-and-state).

{/* Evidence: products/breg/CHANGELOG.md, "it carries no state migration from 0.41";

- BReg requires PostgreSQL 17 or later and a UTF8 database. Generated text columns and
  indexes use the built-in `pg_catalog.pg_c_utf8` collation, and a non-UTF8 database is refused
  with recovery guidance. Migration: provision the fresh BReg database on PostgreSQL 17 or later
  with UTF8 encoding.

{/* Evidence: products/breg/CHANGELOG.md, "pg_c_utf8";
    crates/registry-breg/src/postgres/schema.rs, pg_c_utf8. */}

- BREAKING: BReg projects declare `recordTypes` and Actions, and durable Proposals replace the
  entity-backed change-request model and its routes, with no compatibility layer. The Rust,
  Node.js, and Python clients use standalone Proposal methods (`startProposal`,
  `prepareProposal`, `executeProposal`, `recoverProposal`, the Proposal attachment methods,
  `getProposal`, and `listProposals`); `immediateActions` becomes `actions`,
  `selectImmediateAction` becomes `selectAction`, `contractFingerprint` becomes `revision`, and
  BReg metadata is version 2. The Proposal list takes `limit` and refuses `top`; ingestion runs
  take `cursor`, answer `nextCursor`, and refuse `after`. Proposal documents and events carry a
  required `turn`, lists filter by `turn` and `state=rejected`, and a page may hold fewer than
  `limit` items. A Proposal event's `subject.recordReference` is `/v1/proposals/{id}`. A rejecting
  Review ends the Proposal in the terminal state `rejected` and commands answer `409
  proposal.rejected`; a changes-requested result records `review-returned`. Under required Review
  `applicationStatus.state` reads `awaiting-review` until approval, `application-refused` means
  only an executor refusal, and the `apply` link reports `review-changes-requested` or
  `review-ended` with recovery `revise`. `applicationStatus.recovery` is `retry` or
  `correct-input`, and link availability no longer lists `terminal`. `bregctl explain lifecycle`,
  `bregctl explain events`, and `bregctl explain routes` answer `v1alpha6`. Migration: rewrite
  the project, rebuild the package, update clients and receivers together, keep paging while
  `nextCursor` is present, and start a new Proposal after a rejection. See
  [manage changes](../operate/breg-changes/).

{/* Evidence: products/breg/CHANGELOG.md, the Unreleased BREAKING entries for record types and
    Actions, standalone Proposal methods, "refuses `top`", `turn`, `recordReference`,
    `review-returned`, `awaiting-review`, `correct-input`, recovery `terminal`, and `v1alpha6`. */}

- BREAKING: an immediate BReg Action whose declared field guard fails at commit answers `412
  action.guard_failed` instead of `412 precondition.failed` when the current-target admission
  checks pass and the selected profile can read the failed guard's target fields. The code
  confirms that blocker; it does not promise the Action would otherwise succeed. A stale condition
  or a guard the caller cannot read remains `412 precondition.failed`. Migration: clients that
  match `precondition.failed`, for example to offer reload and retry, must accept the new code.

{/* Evidence: products/breg/CHANGELOG.md, `action.guard_failed`;
    products/breg/immediate-actions.md, "Check one target's advisory availability". */}

- BREAKING: a decided Casework ReviewResult and every `ReviewDecisionReceipt` name the selected
  `outcome`, and BReg reads it. An approve without an outcome is refused with `400
  request.invalid` and reason `outcome-not-declared`, a policy with `purpose: approval` must
  declare its approval outcomes, and approvals in one stage must name the same outcome
  (`approval-outcome-differs`). Every outcome declares `publicReason: required`, `optional`, or
  `none`; a decision's `publicReason` is bounded at 2000 bytes and released to the producer. A
  private `reason` over its bound answers `maximum-bytes-exceeded` instead of `text-invalid`.
  Migration: upgrade Casework and every review producer, including BReg, together, because mixed
  versions leave an approved Proposal `submitted`; add `publicReason` to every outcome and send
  `outcome` with every approval.

{/* Evidence: products/casework/CHANGELOG.md, "names the selected `outcome`",

- BREAKING: Casework replaces source-owned WorkItems with one ReviewPolicy, ReviewRequest,
  ReviewTask, Decision, and ReviewResult model and refuses retained legacy schemas. The project
  format follows the cross-product configuration conventions: duration objects such as
  `after: {hours: 48}`, `terminalRetentionDays` and `accountabilityRetentionDays`,
  `retention: {receiptRetentionDays}` for trusted producers, ID-keyed mappings in place of lists,
  `type: stage`, anchor objects, `atRisk: {before: {workingDays: N}}`, and no `completeOn` or
  routing `when: {activity}`. Producer findings read `no-policies`, `too-many-policies`,
  `invalid-policy`, `duplicate-policy`, `receipt-retention-out-of-range`, and
  `receipt-retention-exceeds-result-retention`. Task list, next-task, and holdings reads finish a
  bounded scan or refuse `review.query-too-broad`. In Rust, `ClockPolicyError` gains
  `Calendar { at, reason }` and is no longer `Copy`. Migration: rewrite the project from the
  error each old spelling reports, use a fresh database, update scripts that match the old codes,
  and narrow broad queues. See [change a Casework package](../operate/change-a-casework-package/).

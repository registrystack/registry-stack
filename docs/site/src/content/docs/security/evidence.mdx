Registry Evidence is built so that a caller cannot turn it into a fact-query engine, splice
permissions across grants, redirect source access, learn from an absence, or receive an
unauthenticated response, and so that its configuration cannot change underneath a request. The
operator keeps the duties no service-side control can hold.

## What the runtime guarantees

A caller cannot turn the service into a fact-query engine. It evaluates only
requirements, each pinned by a requirement revision, and the request schema is
closed: no thresholds, expressions, scripts, paths, headers, source fields, or
response projections. The complete enabled package is reviewed as one
disclosure surface, because several safe definitions together can reconstruct a
protected value.

A caller cannot splice permissions. Principals and attributes come only from
configured, validated authentication sources, and missing data denies rather
than falling back to another claim. One authorisation decision binds the
requester, client, requirement revision, purpose, every subject role and
selector profile, authority, and audience, so partial matches across grants
never add up to access. Selector values are lookup inputs, never proof of
authority. A consent, approval, or grant reference a caller supplies never
creates authority either.

Every authorisation refusal is durably audited before the generic `403`. If
that audit fails, the caller receives the generic `503`.

A failed authentication, a malformed request, an invalid selector, and a rate
limit write no native audit entry, even when Evidence decides them after
authorisation. Watch for them in operational logs and metrics instead.

Evidence counts every refused request by the check that refused it, in
`evidence_request_refusals_total{check}` on the private metrics listener. The `check` label is a
closed set of 45 names such as `credential-missing`, `token-signature`, `scope`, `access-profile`,
`purpose`, `revision-pin` and `rate-limit`, every one published at zero, and no caller value becomes
a label. An issuer key set that cannot be reached still answers `401`, and counts under
`key-source-unavailable`. Each refusal also writes one `request refused` log line with
`failed_check` and the request's trace id when it has one, at most five lines per check per minute,
with `suppressed` counting what a window held back. Neither the counter nor the line holds a token,
claim, client, subject, scope or identifier, and recording a refusal changes nothing the caller
receives: the response is the same closed `401`, `403` or `429` it always was.

missing scope or client, a task grant the offer cannot use, an unusable single-use code or access
token, an Evidence refusal, a session read that belongs to another principal, an unknown or foreign
session status, and a spent request budget. An issuer key set that cannot be reached answers `503`

than on a rise in `401`. Capacity answers, unknown routes, malformed requests, the read of a
reference nobody holds and the wallet response protocol refusals are not recorded. The answers a
caller receives are unchanged.

An agent acts only inside its task grant. For an institutional agent task,
Evidence consumes a complete signed grant context issued by an external task
authority, and accepts it only on a configured authority path whose subjects
derive from the authenticated grant (`authenticated-grant` subjects). That path
may carry any authority kind the package's grant ceiling allows. When the token
also carries the separately mapped actor identity, the path must be
`delegated`. A token without that identity can use an `organizational` or
`statutory` path. The agent actor kind, authenticated principal, verified client
and resource, trusted source issuer, purpose, exact Evidence requirement bound,
effective deadline, and signed approver handle must all match that one path. A
partial, malformed, expired, mismatched, or non-agent grant is refused without
falling back to standing authority. Evidence checks the grant deadline, not the
grant's status, so a revoked grant keeps working until its deadline (see
[how long authority outlives a change](../../reference/casework-task-grants/#how-long-authority-outlives-a-change)).

Source access cannot be redirected. Each source selects one reviewed Adapter
pack route, pinned by digest, and the shared engine alone executes it. Named
connection policies fix the endpoints, authentication, and TLS a route may use.
That closes off server-side request forgery (SSRF), credential forwarding, and
script-directed networking.
The route returns one closed lookup result, and the requirement's
[Function](../../reference/glossary/#function) returns declared typed values
only. The core validates both and assembles the public evidence itself.

Absence does not leak. Missing facts, script failures, audit failures, and
evaluation failures fail closed. Raw source responses are never persisted or
logged, and selector, source, and disclosed values never reach logs or audit.
No-match, ambiguous, missing-fact, and declared unresolved outcomes collapse to
one public problem status and body, and the runtime removes the timing differences it can avoid.
It does not pad responses to a constant time, so a source that answers a
no-match faster than a match can still leak membership through latency. Measure
that at your source before you expose a definition to callers who should not
learn it. Audience-scoped subject bindings derive from the audience and the
purpose, so one subject is not linkable across relying parties. A holder-bound
requirement binds to the holder key's thumbprint and the purpose instead: a
holder who presents the same key to several verifiers is linkable across them
for that purpose, and the wallet, not Registry Evidence, decides whether to use
a fresh key.

The response is authenticated. A signed flattened JWS is the default, unsigned
output exists only where the package and the matched grant both permit it, and
failed signing never falls back to unsigned evidence. Private signing material
stays with the core, out of package values, Rhai, logs, audit, and errors. The
exact response bytes exist before the disclosure-release audit is durably
accepted and are the bytes released. A signature authenticates the provider and
the payload. It does not assert legal-signature status or source truth.

Configuration cannot change underneath a request. The package, runtime file,
and active target authority are immutable for the life of the process, and one
process serves one operator-controlled
[trust domain](../../reference/glossary/#trust-domain) with one signer and one
audit boundary. Operational telemetry is off by default and served only on a
separate private listener with closed labels. Public responses carry a W3C
trace identifier but never the internal audit operation identifier, and
`tracestate` is not echoed.

A caller cannot mistake a presentation for a source read. Every assertion carries a signed
`channel`, and nothing a source script emits can set it. A `holder-presented` assertion exists only
when Evidence itself verified the presented credential against the pinned issuer allow-list, never
against a key the presentation supplies, and holder binding is always required. A relying party's
channel policy decides whether to accept one, and the default accepts `source` only. Base Registry Engine (BReg)
refuses a correctly signed `holder-presented` assertion for a governed action with `action.evidence_failed`,
and no configuration key changes that.

## The public certificate check

The experimental `POST /v1/public-check` route is unauthenticated and reads registry data. It exists only when the package declares `publicCheck` and the target authority
activates it. It answers one configured requirement with a status, the printed fields, and the
evaluation time, and nothing else.

- **Enumeration.** The check code is 120 random bits stored on the record at issuance, not derived
  from the number or from any key, so guessing is not feasible. Evidence has no rate limiter on this
  route and never reads a client address. The operator's proxy limits each client and the whole path.
- **Identical miss.** A wrong number, a wrong code, an ambiguous match, a record with no usable
  stored code, and the other unresolved cases return the same `404`, with the same headers and body
  apart from the fresh trace identifier.
- **Code confinement.** The code is compared in constant time and removed from the facts before any
  Function runs, on every route that reads that source. It is never a source input, and it appears in
  no log, audit record, or answer.
- **Timing.** Evidence adds no delay, so a response can take longer when the number exists than when
  it does not. That can reveal whether a number exists. It reveals nothing about the code. The
  certificate number is printed on the paper and is not the secret, so this residual is accepted. If
  the number alone would reveal sensitive membership in your deployment, do not activate the route.
- **Before the comparison.** Evidence compares the check code only after the Source returns a
  record, so a Source failure before that answers `503 source.unavailable`, audited as a dependency
  failure. A number with no record cannot fail that way. A pack that refuses one record's content
  before the comparison (a facts schema that constrains values beyond their type, or an extract
  script that throws on one record's data) lets that `503` reveal that a record exists for the
  number, though neither its status nor its fields. A fault that hits every request answers `503`
  for every number and reveals nothing. Keep the facts schema to types, treat a returned record whose
  number does not exactly match as no-match, and check record content in the derivation, which runs
  after the comparison, so only a caller holding the right code sees its failures.
- **Input errors read as outages.** A number that passes the selector profile but that the Source
  cannot carry in a request path segment answers `503 source.unavailable`, so a caller can make an
  input error look like a registry outage. The audit tells them apart: that refusal is a
  dependency failure recorded after the access attempt, while a number the selector profile or the
  Source inputs schema refuses writes nothing.
- **Checker privacy.** The number and code travel in a POST body, never in a path or query. Evidence
  mints its own trace identifier on this route, ignores inbound trace context, and reads no request
  header except `Content-Type`. The audit record holds a keyed pseudonym of the number, not the number.
  The operator's proxy keeps no client addresses for this location.
- **Unsigned answer.** The answer carries no signature, subject identifier, or nonce. The checker
  trusts the page origin and its TLS, so print that origin as text beside the QR code. A party that
  needs a provable answer uses the signed relying-service path.
- **Blast radius.** Run the check on its own Evidence instance with its own signing, audit, and
  subject-binding keys, so a flood or a compromise on the public path does not reach institutional
  keys or starve relying services.

## Replay protection

Registry Evidence holds no credential or presentation replay state. Its request-binding checks do
not consume a credential or prevent its reuse. Evidence and its verifiers check signatures, expiry,
audience, nonce equality, and other request bindings. Those checks alone do not consume a
credential, so Registry Evidence does not claim replay prevention or single-use enforcement.

Replay prevention for one-time credentials belongs to the surrounding protocol or issuer that
creates and validates a one-time challenge. Issuing a challenge, retaining it, and retiring it
belong to the relying party, as RFC 9901 section 7.3 places the challenge lifecycle in the
surrounding protocol.

- The request nonce is uninterpreted correlation data. An audience-scoped assertion echoes it
  under its signature, and a holder-bound one does not carry it. Evidence never stores a nonce or
  checks it against earlier requests. Nonces inside one batch must differ. A nonce becomes a
  freshness check only when a verifier keeps the value it sent.
- Evidence issues no key-binding JWT and keeps no challenge state.
- Nonce equality is not nonce consumption. The same presentation bytes verify again, and again,
  against the same stateless policy. `evidence verify-presentation` keeps no state between runs.
- For a wallet presentation, the separate `evidence-oid4vp` verifier front end creates each
  session's nonce and holds sessions in memory only. The first successful read of a session's
  result consumes that result, and a restart ends every session.
- Evidence refuses a wallet presentation whose stated receipt time falls outside a bounded window
  around the read. That limits how long a held presentation stays usable. It does not make a
  presentation single-use.

Other products may retain operation receipts or replay recovery state under their own contracts,
as [Retention and persistent state](../../operate/retention-and-persistent-state/) describes.

## Subject binding and presentation

Evidence can encode an assertion as SD-JWT VC, with digests in place of disclosable values. That is
a serialisation of the same bounded assertion. Revocation, status, presentation replay state, and a
general wallet lifecycle are outside that assertion format. The separate OID4VCI adapter provides
its documented delivery profile without changing those limits.

A requirement in the immutable bundle declares which subject binding mode it issues under. The
vocabulary is closed at two values. A requirement that declares nothing issues audience-scoped
assertions, and no caller input selects a mode.

| Boundary | `audience-scoped` (absence of a declaration) | `holder-bound` (declared per requirement) |
| --- | --- | --- |
| Subject binding scope | The audience taken from the authenticated context | The RFC 7638 thumbprint of the holder key the caller supplied |
| Cross-verifier use | None. The assertion is meaningful to the one relying party it names. | Deliberate. The holder decides which verifiers see one credential. |
| Holder key | Optional, echoed into `cnf`, verified by nothing | Required, and `cnf` is required in the credential |
| Possession proof | None at any point | A key-binding JWT the relying party verifies at presentation |
| Correlation across verifiers | Prevented by the service | Delegated to the holder, who chooses which key to reuse and where |
| Response formats | Signed JWS, SD-JWT VC, or the unsigned envelope, as permitted | Narrowed to the SD-JWT VC serialisation and its batch envelope |
| Value forms | All twelve | Ten. Bundle validation refuses `audience-scoped-entity-reference` and `entity-reference-list`, because both take the audience as a derivation input. |
| Contract status | Frozen Version 1 | Frozen, and every negative test the profile names resolves to an executable test |

- The audience-scoped holder key is unverified. A single-credential request may carry an optional
  `holderKeys` array containing one public key, which is echoed into the `cnf` member. Under this
  mode Evidence issues no holder key, binds none, and verifies none. `cnf` is a caller-supplied
  convenience for whatever presentation layer the operator runs elsewhere.
- Audience-scoped assertions are not multi-verifier. The subject identifier is an audience-scoped
  pseudonym, so the same person requested for a different audience yields a different identifier.
  Purpose is an input to every subject binding and audit pseudonym as well, so one subject is not
  linkable across purposes.
- A holder-bound credential accepts cross-verifier correlation. The binding does not take the
  audience as an input, so the same holder key, trust domain, purpose, subject role, selector
  profile, and selector values yield the same binding for every caller and every verifier. Holder
  key reuse is the correlator, and Evidence can neither prevent nor detect it. The declared purpose
  is a low-cardinality attribute disclosed to every verifier the credential reaches. Repeating the
  same request with the same key returns the same binding.
- Batch issuance reduces linkability but does not remove it. A holder-bound
  [batch release](../../reference/glossary/#batch-release) may carry one member per distinct holder
  key under a ceiling the bundle declares. That removes the
  deterministic key-based link. The members still share an issuance timestamp, purpose,
  requirement, Evidence Type, configuration revision, and disclosed values. The issuer knows one
  requester submitted those keys together.
- The holder-bound audit pseudonym is stable across issuances. It omits the audience, so repeated
  issuance for the same subject records the same pseudonym.
- Presentation-time audience is verifier-asserted. The relying party puts the audience and nonce in
  its own challenge, and neither is issuer-signed. No issuance record names the verifier a
  holder-bound credential later reached.

The portable verifier library and `evidence verify-presentation` check issuer and key-binding
signatures, the expected audience and nonce, and independently pinned expectations.

- A verified key-binding JWT proves the presenter held the private key of the credential's
  confirmation key when that JWT was signed, over exactly the presented bytes, for the audience and
  nonce the relying party chose. It proves nothing else.
- A valid issuer signature alone does not prove possession. A presentation whose issuer signature
  verifies and whose key binding does not is rejected, never reported as an issuer-only success.
- The verifier checks the key-binding JWT before it compares any relying-party expectation, so a
  failed possession proof never reveals whether the policy would have matched.
- Every key-binding failure reports one `key-binding` class: an absent key-binding JWT, a signer
  other than the confirmation key, a rejected header member or algorithm, a mismatched audience,
  challenge, or `sd_hash`, or an `iat` outside the accepted window.
- A stored credential ends in a trailing tilde, and the verifier refuses it as a presentation
  instead of verifying it without possession.
- The relying party cannot derive a subject binding under either mode, because the derivation is
  keyed by a deployment secret it does not hold. Expected subject bindings are pinned from
  independent trusted state. An expected holder key thumbprint is an optional extra expectation for
  a pre-established holder, not what proves possession.
- Wallet compatibility is unclaimed. Full SD-JWT VC and OID4VCI conformance are not claimed, and no
  test in this repository covers a wallet storing or presenting a Registry Evidence credential.
  The pinned OID4VCI runner covers sanitised metadata and wire shapes, service-side key binding,
  and independent presentation verification. Its opt-in upstream half runs focused source tests at
  exact Inji revisions, not Android or iOS user-interface or device automation.

## Limits a deployment accepts

- A released assertion has no revocation, status-list, or presentation-time callback. It remains
  verifiable until `validUntil`. Rotating a signing key does not invalidate an assertion while its
  public key remains available. The bounded OID4VCI adapter does not add assertion revocation or a
  general wallet lifecycle.
- A `holder-presented` assertion proves that Evidence verified a presented credential, not that a
  source holds the fact. Status checking is not available for presented credentials. A
  `wallet-presentation-v1` configuration must state `status: not-checked`, so a revoked credential
  is not detected at presentation. Only `dc+sd-jwt` credentials are requested, and mdoc is not
  supported. No wallet is verified against the OpenID4VP verifier until a reviewed device-run
  receipt exists, and none does. See [Verify a wallet presentation](../../configure/evidence-oid4vp/#check-wallet-interoperability).
  {/* Evidence: crates/registry-evidence/src/wallet_presentation.rs, StatusMode,
       status_required_is_refused_with_a_message_that_says_why;
       products/evidence/contracts/oid4vp-profile.yaml, not_built, interoperability_target;
       products/evidence/examples/wallet-presentation/README.md, Limits. */}
- With a cross-device flow, a holder can present into a session someone else started, by relay or by
  cooperation. `possession` proves that a credential from a trusted issuer was presented into the
  session, not that the presenter is the applicant. With `attribute-match`, the requirement's
  derivation must compare the disclosed claims with the one expected record. Only that comparison
  turns another person's credential into a mismatch. Evidence checks only that the wallet
  configuration names at least one disclosed claim.
  {/* Evidence: crates/registry-evidence/src/wallet_presentation.rs, subject_link,
       AttributeMatchWithoutClaims. */}
- The relying party that calls Evidence states the session reference and the presenting
  principal. Evidence refuses a principal that did not create the session, but it cannot tell which
  relying party a session was meant for. Run one relying party per Evidence deployment that serves
  wallet channels.
  {/* Evidence: crates/registry-evidence/src/wallet_presentation.rs, ReadRequest,
       WalletPresentationVerifier::verified (created_by);
       products/evidence/examples/wallet-presentation/evidence.yaml, wallet-session selector
       profile. */}
- Unsigned output is transport-authenticated convenience, not later-verifiable evidence. The
  strict verifier refuses it.
  {/* Evidence: crates/registry-evidence-verifier/src/verifier.rs,
       unsigned_envelope_is_rejected_by_the_strict_jws_verifier. */}
- `disclosureGuard` families are operator attestations, not semantic classification. The runtime
  cannot detect two differently named families that disclose equivalent information.
- There is no cumulative disclosure budget. Rate controls are keyed by principal, and
  the failed-selector budget by principal and authority profile. They are in-memory and per process. Replicas multiply them and a restart resets them. Per-client quotas belong at
  the gateway. A gateway or exchange layer in front of Evidence can add quotas and transport
  controls. It never replaces Evidence's own token check, authorisation and audit.
- One process serves one token issuer and one set of claim names. Mutually distrustful issuers, or
  clients whose authority uses different claim names, need separate deployments, bundles, signers,
  and audit boundaries.
- Access tokens are bearer tokens. A token carrying a proof-of-possession confirmation claim is
  denied because Evidence validates no sender proof.
- Startup does not detect overlapping authority paths. Zero paths and multiple paths both deny at
  request time, so overlap appears as a refusal rather than a deployment-time error.
- Readiness checks the audit sink, the subject-binding key, the signer, and each source's
  credentials. It probes the token issuer's key set only to log an issuer that has gone quiet, and
  that probe does not decide readiness. Readiness sends no evidence-data request and does not prove
  that a source returns data.
- Evidence implements no source protocol of its own. A reviewed Adapter pack route reads the
  source and returns bounded facts. No component parses FHIR or implements another protocol's
  search, subscription, or conformance behaviour.
- Lookup has four outcomes: match, no match, ambiguous, or declared unresolved. A route may read a
  bounded number of pages, but Evidence never exposes or chooses candidates.
- Production signing supports Vault or OpenBao Transit through a workload-local Unix-socket proxy.
  Local assurance supports a file-backed private JWK. There is no PKCS#11 or cloud-KMS plugin layer.
- `/health`, `/ready`, `/openapi.json`, `/catalog.jsonld`, the issuer JWKS, issuer metadata, and
  protected-resource metadata are unauthenticated. So is the
  [public certificate check](#the-public-certificate-check) when the operator activates it. Every
  route that returns an assertion or a protected definition requires a verified access token.

## How the guarantees are held

The [invariant matrix](https://github.com/registrystack/registry-stack/blob/main/products/evidence/contracts/security-invariant-matrix.yaml)
holds the complete, normative text: numbered invariants and named cross-cutting controls, each
with its rule, threat, enforcement, and negative test, including those for holder-bound responses,
request batches, and the OID4VCI front end. An invariant the matrix adds is binding from the change
that adds it. Every invariant is held by a named test, and the
[traceability contract](https://github.com/registrystack/registry-stack/blob/main/products/evidence/contracts/security-test-traceability.yaml)
links them, and the build fails when an invariant drops its test.

## What the operator must uphold

The matrix describes what the `evidence` binary enforces.
The [operator contract](https://github.com/registrystack/registry-stack/blob/main/products/evidence/OPERATOR-CONTRACT.md)
holds the duties no service-side control can hold for you:

- Keep every secret file below `secretProviders.file.root` a regular,
  non-symlink file owned by the service identity with mode `0400` or `0600`.
  The file provider refuses anything else.
- Generate the audit and subject-binding masters independently, at least 32
  bytes each, under distinct references. The runtime refuses equal references
  or equal bytes.
- Mount the package and `runtime.yaml` read-only and unwritable by the service
  process. Evidence refuses to start from a file with any write permission
  unless its filesystem is mounted read-only. There is no upload, reload, or
  override: a change is a new candidate.
- Pass source credentials and signing material only through secret
  references, never in YAML values, Rhai, command arguments, logs, or
  snapshots.
- Sign production and evidence-grade deployments through a workload-local
  Transit key that stays non-exportable, and retire signing keys as

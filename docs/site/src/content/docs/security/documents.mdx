This page states what the Document Store guarantees, what it does not, and what you must do for the
guarantees to hold.
The enforced invariants, with threats, enforcement points and test names, are rows
`DOCUMENTS-SEC-01` to `DOCUMENTS-SEC-54` in the
[security invariant matrix](https://github.com/registrystack/registry-stack/blob/v0.46.0/products/documents/contracts/security-invariant-matrix.yaml);
this page does not repeat them.
Configuration is in the [Document Store configuration reference](../../reference/documents-configuration/),
and the restore drill is in
[Deploy and operate the Document Store](../../operate/documents/#restore-from-a-backup).

## Scope and trust boundaries

- The unauthenticated surface is only `GET /health` and `GET /ready`.
  Readiness answers `200` or `503` with no cause; the cause goes to the operational log.
- The issuer: every document route verifies the bearer token (issuer, audience, `at+jwt`, allowed
  clients, signature from the configured key set) and resolves exactly one access profile before it
  reads a body or the store.
  An unreachable key set answers 503, never 401.
  The deployment trusts one issuer.
  `allowedClients` is required in every runtime file. `allowedClients: from-package` admits the sorted
  union of the access profiles' `requesterClients` and nothing more, so the package and the runtime
  file cannot disagree. An explicit list must include every client an access profile names, or the
  runtime refuses to start with `documents.runtime.profile-client-not-allowed`.
  `allowedClients: unrestricted` and an empty list are refused in every mode.
  Declared issuer and key addresses are trusted on the operator's word (DOCUMENTS-RES-17).
  A static key set (`jwksSource: static`) holds public keys only.
  The runtime refuses to start on a set that carries a private member (`d`, `p`, `q`, `dp`, `dq`,
  `qi`, `oth` or `k`), a symmetric key, a repeated member name, or a key without a unique `kid`.
  The startup error names the rule it broke, and the key's position for a rule about one key, never a key value.
  Members it does not know, such as `x5c` or `ext`, are ignored.
- The operator's view of a refusal: the answer to the caller names a problem code and no cause, so
  an operator tells the causes apart from the private metrics listener and the log.
  The Document Store counts every refused request by the check that refused it, in
  `documents_request_refusals_total{check}` on the private metrics listener.
  The `check` label is a closed set of 45 names such as `credential-missing`, `token-signature`,
  `scope`, `actor-kind`, `access-profile`, `operation`, `ownership` and `visibility`, every one
  published at zero, and no caller value becomes a label.
  The counter covers a missing or refused credential, a token that resolves to no access profile, a
  refused custody placement, a caller that sees a document but may not act on it, a document or
  upload the caller may not see, and a verifier that cannot reach or use its key source
  (`key-source-unavailable`). A key set the verifier cannot fetch, read or use answers 503. A key
  endpoint the verifier refuses to contact answers the refusal a bad credential gets, and is counted
  the same way.
  Each refusal also writes one `request refused` log line with `failed_check`, at most five lines per
  check per minute, with `suppressed` counting what a window held back.
  A scope refusal's line also carries `scope_claim`, `required_scope` and `access_profile`, the
  values the deployment configured, never the token's own scope, and a fixed remedy that names
  `authentication.oidc.scopeClaim`.
  Neither the counter nor the line holds a token, claim, client, subject, scope or identifier, and
  recording a refusal changes nothing the caller receives.
- The custodian alone removes a document and issues, lists and revokes its grants.
  Under citizen delivery the citizen is the custodian and the reserving system keeps metadata and
  status only.
  Under institutional custody the institution stays custodian and a named person is only the
  represented principal, with no standing until granted.
- A grant holder: a grant names one exact version and one recipient by issuer, subject and actor
  kind.
  Release reads the stored grant row only.
  A caller with no standing gets the same 404 as for an unknown identifier.
- The content verifier: a version is released only after a verifier approved those exact bytes
  under the binding currently recorded for it.
  An unavailable verifier never releases.
- The migration credential holder holds authority over the schema.
  `documentsctl apply` is the only path that changes it or records an activation; the serving
  process never does.
  Package authority is checked against the activation ledger on every authenticated request.
- The runtime credential holder serves requests and, through `documentsctl`, lists and replays
  dead-lettered jobs.
- The database superuser and object storage are trusted completely.
  The storage binding is pinned at the first write; a start under another backend, bucket or scope
  is refused.
- Hook observers are untrusted.
  They receive closed, content-free events for the policies a hook names, at destinations the
  operator binds, and cannot change a document, version or grant.
- Host users who can write audit files are trusted; the journal is only as strong as the storage it
  is written to.

Production refuses a disabled verifier and private-network plaintext
PostgreSQL before binding. Both postures refuse non-loopback HTTP storage,
verifier and hook URLs, environment expressions in secret references and
undeclared secret providers. Findings name the member and rule.

Use one posture across a deployment. Development responses carry
`Registry-Posture: development`, which the Document Store Rust client refuses. Development can
approve finalized versions with `contentVerification: {type: disabled}`.
Loopback HTTP storage, verifier and hook URLs are valid in either posture.
A development hook capture includes `"posture":"development"` inside the signed canonical body.
The shared Standard Webhooks verifier refuses that mark with `development-peer`.
The production worker dead-letters a retained development-marked envelope with `payload-refused` before signing or sending it. A development worker can send the same captured bytes. Envelopes stored before the mark was introduced retain their original form.

## Operator obligations

The guarantees hold only when you meet these obligations.

1. Treat a database restore as a security event.
   Restore the audit file written since the backup with the database, re-apply every revocation and
   repeat every erasure request it records (DOCUMENTS-RES-01, DOCUMENTS-RES-02).
   Follow the restore drill: serving stopped, `cleanup.erasure: paused`, compare restored state with
   the audit file.
2. Keep the migration credential off the serving host and use split roles in production.
   With one role for both, the runtime keeps schema authority.
3. Collect both journals.
   `documentsctl` apply and replay write to a companion journal on the host where they run.
   Ship it and the runtime journal to append-only storage.
4. Finish a verifier change by restarting every instance (DOCUMENTS-RES-05).
5. Drain before activating a changed package.
   Apply waits at most five seconds for the activation lock; busy old workers may need draining.
6. Replay dead letters deliberately.
   A dead-lettered verification leaves the version pending and unservable; a dead-lettered erasure
   leaves it pending; the sweep re-arms neither.
   Use `documentsctl verification list` and `replay`, and `documentsctl erasure status`, `list`
   and `replay`.
7. Alarm on `storage-integrity` audit entries (digest or length mismatch, 503, no byte sent).
   Outages write `storage-unavailable` instead.
8. Bind hook destinations only for observers entitled to the timing of document and grant events
   (DOCUMENTS-RES-12).
9. Provision memory for the transfer budget shared by uploads, downloads and verification;
   [Deploy and operate the Document Store](../../operate/documents/) states the figure.
10. Resume erasure after a pause.
    `cleanup.erasure: paused` stops the erasure worker, arming and the orphan sweep; serving,
    removal requests and upload expiry continue.
11. Render labels as untrusted text (DOCUMENTS-RES-08).
12. Do not reuse a subject for another person at the issuer (DOCUMENTS-RES-07).
13. Use an HTTPS issuer and leave `allowInsecureHttp` unset.
    Declare only issuer and JWKS addresses you intend the Store to reach (DOCUMENTS-RES-17).

## Accepted residuals

Related rows are the neighbouring enforced behaviour, not the residual itself.

### DOCUMENTS-RES-01: restoring a backup resurrects revoked grants

- Condition: a backup older than a grant revocation is restored.
- Consequence: the revoked grant is active again unless the audit journal written since the backup
  is restored and its revocations are re-applied.
- Mitigation: obligation 1.
- Related: DOCUMENTS-SEC-24 to DOCUMENTS-SEC-26.

### DOCUMENTS-RES-02: restoring a backup loses newer erasures

- Condition: a backup older than an erasure request or erasure is restored.
- Consequence: the version is servable again and its bytes are back.
- Mitigation: obligation 1; repeat the requests from the audit file.
- Related: DOCUMENTS-SEC-37 to DOCUMENTS-SEC-46.

### DOCUMENTS-RES-03: "erased" bytes persist in PostgreSQL pages, WAL and backups

- Condition: erasure of content held in PostgreSQL or S3.
- Consequence: "erased" means the Store can no longer serve the bytes.
  Vacuum only marks space reusable, so bytes stay on their pages until overwritten or `VACUUM FULL`
  rewrites the table.
  Backups, WAL archives, replicas, and S3 versioning or replication outside the Store's key keep
  them as long as those copies are retained.
- Mitigation: match backup, WAL and bucket-version retention to the erasure promise made to
  custodians; run `VACUUM FULL` where on-disk removal is required.
- Related: DOCUMENTS-SEC-37 to DOCUMENTS-SEC-46.

### DOCUMENTS-RES-04: an admitted transfer finishes after revocation or removal

- Condition: a download is admitted, then its grant is revoked or removal is requested.
- Consequence: the download is not interrupted; it finishes within its transfer deadline.
  No release that starts after the commit serves the version.
- Mitigation: size `transfers.minimumDeadlineSeconds` and `transfers.mebibyteAllowanceSeconds` to
  bound the window.
- Related: DOCUMENTS-SEC-28, DOCUMENTS-SEC-37 to DOCUMENTS-SEC-46.

### DOCUMENTS-RES-05: a verifier rollout leaves an older instance releasing

- Condition: instances run different verifier bindings during a rollout.
- Consequence: an older instance can finalise a version after a newer one swept, and release it
  under the older binding until the next restart sweeps it.
  A worker under the newer binding only retries its job.
- Mitigation: obligation 4.
- Related: DOCUMENTS-SEC-14 to DOCUMENTS-SEC-20.

{/* Evidence: crates/registry-documents/tests/postgres_documents.rs
    a_verifier_binding_change_at_restart_suspends_and_verifies_again;
    products/documents/contracts/security-invariant-matrix.yaml DOCUMENTS-SEC-14,
    DOCUMENTS-SEC-20. */}

### DOCUMENTS-RES-06: the runtime credential can replay dead-lettered jobs

- Condition: a holder of the runtime credential runs `documentsctl`.
- Consequence: a verification replay only re-queues verification and releases nothing (verifier
  load, no disclosure).
  An erasure replay re-queues an erasure already armed by a custodian or a rejection; it cannot
  choose what is erased.
  No HTTP route lists or replays a job.
- Mitigation: keep the runtime credential on the serving host.
- Related: DOCUMENTS-SEC-34 to DOCUMENTS-SEC-36.

{/* Evidence: crates/registry-documents/tests/postgres_operator.rs
    replay_refuses_an_unknown_version_and_an_unactivated_database;
    crates/registry-documentsctl/src/lib.rs VerificationCommand, ErasureCommand;
    products/documents/contracts/security-invariant-matrix.yaml DOCUMENTS-SEC-34,
    DOCUMENTS-SEC-36. */}

### DOCUMENTS-RES-07: a grant follows the subject

- Condition: the issuer reuses a subject for another person.
- Consequence: the new holder receives what the grant releases.
  A grant names its recipient only by issuer, subject and actor kind; the recipient resolver and
  display names are out of scope.
- Mitigation: obligation 12.
- Related: DOCUMENTS-SEC-24, DOCUMENTS-SEC-54.

{/* Evidence: crates/registry-documents/tests/postgres_documents.rs

### DOCUMENTS-RES-08: the label is caller text

- Condition: a client renders the label as markup or trusts it to describe the bytes.
- Consequence: the client can mislead its user.
  The Store returns the label as written and makes no claim about it.
- Mitigation: obligation 11.
- Related: DOCUMENTS-SEC-21 to DOCUMENTS-SEC-33.

{/* Evidence: crates/registry-documents/tests/postgres_documents.rs
    a_label_is_bounded_and_returned_untouched;
    products/documents/contracts/security-invariant-matrix.yaml DOCUMENTS-SEC-21,
    DOCUMENTS-SEC-33. */}

### DOCUMENTS-RES-09: a document whose policy is no longer declared is inaccessible

- Condition: the deployed package no longer declares a document's policy.
- Consequence: the document is shown to nobody, custodian included, each access logs a warning, and
  the custodian cannot remove it.
  It stays in custody until the policy is declared again.
- Mitigation: do not drop policies that still have documents in custody.
- Related: DOCUMENTS-SEC-21 to DOCUMENTS-SEC-33.

{/* Evidence: crates/registry-documents/tests/postgres_documents.rs
    a_document_under_an_undeclared_policy_cannot_be_removed. */}

### DOCUMENTS-RES-10: lists can return short pages

- Condition: a caller lists documents under standing rules.
- Consequence: the list filters each fetched row, so a page can be shorter than its limit while a
  next cursor remains.
  The received-grants list selects only redeemable grants before its limit and is not affected.
- Mitigation: clients follow the cursor until it is absent.
- Related: DOCUMENTS-SEC-21 to DOCUMENTS-SEC-33.

{/* Evidence: crates/registry-documents/src/service.rs next_cursor,
    the_next_cursor_is_set_only_when_a_further_row_exists. */}

### DOCUMENTS-RES-11: grants after rejection and removal

- Condition: a version is rejected, or removal follows a rejection.
- Consequence: a rejection alone revokes no grant; a grant on a rejected version releases nothing
  and stays listed as active until it expires or is revoked.
  A removal after a rejection is a first removal: it revokes every active grant on the document,
  and the version keeps the rejection's due time.
  Only a repeat of a recorded removal changes nothing.
- Mitigation: none needed for release.
- Related: DOCUMENTS-SEC-37 to DOCUMENTS-SEC-46.

{/* Evidence: crates/registry-documents/tests/postgres_documents.rs

    erasure_outranks_every_other_dimension_but_a_rejection. */}

### DOCUMENTS-RES-12: observers learn timing

- Condition: a hook destination is bound for a policy.
- Consequence: the observer learns that a document exists, when it became ready or was rejected,
  and when grants on it change, keyed by stable ids.
  No event carries content, label, media type, name or subject.
- Mitigation: obligation 8.
- Related: DOCUMENTS-SEC-48 to DOCUMENTS-SEC-53.

### DOCUMENTS-RES-13: grant expiry emits no event

- Condition: a grant reaches its expiry.
- Consequence: expiry is not a recorded transition.
  A receiver that forgets the `expiresAt` an `issued` event carried treats an expired grant as live
  until it is revoked.
  Release checks expiry and is unaffected.
- Mitigation: receivers keep `expiresAt` from the `issued` event.
- Related: DOCUMENTS-SEC-49.

{/* Evidence: crates/registry-documents/src/hooks.rs expiresAt, Issued;
    crates/registry-documents/tests/postgres_hooks.rs
    grant_issue_and_revoke_each_capture_one_event_and_repeats_capture_none;
    products/documents/contracts/security-invariant-matrix.yaml DOCUMENTS-SEC-49. */}

### DOCUMENTS-RES-14: terminal delivery payloads are not pruned

- Condition: a hook delivery reaches a terminal state.
- Consequence: a captured payload stops being sent after `retention.hookPayloadRetentionDays`, but
  the delivery row and payload stay in the database; the Store does not call the shared pruning.
  Payloads hold ids and timing, no content.
- Mitigation: include the delivery tables in database retention planning.
- Related: DOCUMENTS-SEC-48 to DOCUMENTS-SEC-53.

{/* Evidence: crates/registry-documents/src/config.rs hook_payload_retention_days;

    products/documents/contracts/security-invariant-matrix.yaml DOCUMENTS-SEC-48,
    DOCUMENTS-SEC-53. */}

### DOCUMENTS-RES-15: a paused deployment keeps due bytes

- Condition: `cleanup.erasure: paused`.
- Consequence: due bytes remain while paused, and orphan S3 objects accumulate.
- Mitigation: obligation 10.
- Related: DOCUMENTS-SEC-37 to DOCUMENTS-SEC-46.

{/* Evidence: crates/registry-documents/tests/postgres_documents.rs a_paused_deployment_erases_nothing;
    crates/registry-documents/tests/postgres_s3.rs
    the_orphan_sweep_erases_only_old_uncommitted_objects. */}

### DOCUMENTS-RES-16: an empty directory created during `documentsctl init` is replaced

This residual concerns development tooling.
`documentsctl init` refuses an existing path, stages the starter and publishes it with one rename.
An empty directory another local process creates at that path before the rename is replaced by the
starter.
The window needs write access to the parent directory and loses no content.

{/* Evidence: crates/registry-documentsctl/src/lib.rs
    init_reports_the_files_it_wrote_and_refuses_an_existing_directory. */}

### DOCUMENTS-RES-17: declared issuer and key endpoints are trusted

- Condition: the runtime file names an issuer or JWKS URI, or sets
  `authentication.oidc.allowInsecureHttp: true`.
- Consequence: The Store trusts a declared issuer or JWKS URI on the operator's word.
  Under `allowInsecureHttp: true`, an attacker on the network path to the issuer can substitute
  keys and mint tokens the Store accepts.
  Startup logs a fixed warning when the setting is on.
  The residual is shared across products and set out in [Token issuer and key endpoints](../#token-issuer-and-key-endpoints).
- Mitigation: obligation 13; or pin keys with a static `jwksSource`.
- Related: DOCUMENTS-SEC-10.

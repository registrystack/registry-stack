This page states what Registry Coordinator holds, what it does not hold, and what you must do for
its guarantees to hold.
Each guarantee carries a stable identifier from `COORDINATOR-INV-01` to `COORDINATOR-INV-15`, and
each accepted residual risk one from `COORDINATOR-RES-01` to `COORDINATOR-RES-27`.
Terms follow [Author a Coordinator workflow](../../configure/coordinator/).
Deployment steps are in [Deploy Registry Coordinator](../../operate/coordinator/).

## Scope and trust boundaries

- The operator owns the runtime configuration: connection base URLs, the external command path,
  credentials, issuer settings, the Base Registry Engine (BReg) connection profile and the Registry
  Adapter payment connection.
  Operator configuration is trusted; workflow data is not.
- A workflow author writes a project that Coordinator freezes into a definition.
  The author supplies bodies, mappings and pure Functions.
  The author does not choose destinations, headers, credentials or recovery behaviour; the closed
  operation catalogue does.
- Providers decide every effect a run requests: Registry Casework, Registry Scheduling, BReg, the
  Registry Adapter payment host and external HTTP providers.
  Coordinator holds workload identity, not decision authority, and each receiving product still
  authorises the call.
- A caller authenticates with an access token verified against the configured OIDC issuer.
  Coordinator authenticates and authorises every protected route and reapplies the caller's owner
  and workflow scope on every list page.
  Admission accepts a token only when its caller policy lists the token's exact `sub`, and refuses
  a delegated token (COORDINATOR-INV-10).
  Start input is the caller's assertion: Coordinator does not compare it with the caller's `sub`.
- Coordinator counts every refused request by the check that refused it, in
  `coordinator_request_refusals_total{check}` on the private metrics listener.
  The `check` label is a closed set of 45 names, every one published at zero, and no caller value
  becomes a label.
  The counter covers a refused credential, a policy denial after authentication, a refused signed
  event delivery or completion callback, a key source the receiver cannot reach or use (the
  access-token verifier's keys or the signed-event key), and a run the caller cannot see.
  Each refusal also writes one `request refused` log line with `failed_check` and the request's
  trace id when it has one, at most five lines per check per minute, with `suppressed` counting what
  a window held back.
  Neither the counter nor the line holds a token, claim, client, subject, scope or identifier, and
  recording a refusal changes nothing the caller receives.
  The older `coordinator_authentication_refusals_total{reason}` counter is unchanged.
- Host users run `coordinatorctl`, which is local operator tooling for a trusted single-user
  machine.
- PostgreSQL holds run, wait and job state.
  Coordinator does not defend against a database superuser.
  Plaintext PostgreSQL is admitted only to a Unix socket, a loopback address literal or the name
  `localhost`, in any letter case.
  Coordinator matches `localhost` by spelling and does not pin its resolution, so a host that maps
  that name elsewhere redirects the connection.

## Guarantees

Each guarantee names the threat it answers, how Coordinator enforces it, and what it refuses.

### COORDINATOR-INV-01: lapsed leases retry only reads

Threat: a worker can exit after leasing a read but before recording its result.
Holding every such job delays a workflow, though repeating the operation is safe.
Treating every lapsed lease as retryable could instead repeat a mutation, evaluation or
same-command effect whose remote outcome is unknown.
A late completion from the original worker could race the replacement attempt.

Enforcement: Coordinator opens the authenticated definition snapshot for the run and resolves the
exact leased step.
Only a call whose catalogue recovery is `read-again` is retried.
Every mutation, evaluation, same-command call, wait and local step is held.
A retried read uses the existing backoff, a ten-attempt limit and the original run deadline.
When the attempts or the deadline run out, the job becomes `unknown`, so repeated failure reaches
operator review.
The `lease-lapsed` transition audit commits before the job is released, and completion is fenced by
generation, attempt and lease token.

Refused: a lapsed mutation, evaluation or same-command call is never re-sent automatically.
A stale worker cannot commit after the replacement attempt starts.
Recovery does not extend the attempt or deadline budget.

### COORDINATOR-INV-02: Scheduling commands are never replayed on inference

Threat: Coordinator can lose the response after Scheduling committed capacity.
A fresh command, an ordinary current-state read, or replay of an unkeyed release could duplicate or
misstate that effect.

Enforcement: each Scheduling lifecycle operation declares its recovery behaviour in the operation
catalogue.
Reads run again.
Appointment creation and hold confirmation keep the exact key and request and may use Scheduling's
original-result receipt.
Hold creation, rescheduling and cancellation keep the exact keyed command but have no receipt
lookup, and current appointment state does not settle them.
Hold release carries no key, so an ambiguous dispatch is held.
Every commitment obtains fresh task-bound Scheduling authority per durable attempt.
The Scheduling client performs no hidden mutation retry inside Coordinator.

Refused: an unkeyed hold release is never sent twice.
Standing reads never authorise a commitment.

### COORDINATOR-INV-03: the external command is bounded and sent once in effect

Threat: `external.command/v1` is an outbound mutation to a provider outside Registry Stack, with a
recovery path that can send it again.
Workflow data could try to steer the request to another host, path or credential.
A lost acknowledgement, timeout, redirect or server error (including a busy 503 whose retry never
settles) could be misread as failure, so a fresh command would apply the effect twice.
A response, body, request id or credential could leak through logs, problem details, `status` or
`inspect`.

Enforcement:

- The destination is operator configuration.
  The connection holds one exact relative `commandPath` beside `baseUrl` and `authorization`; the
  workflow supplies only a JSON object body.
  Coordinator sends one POST, follows no redirect, and validates the destination under the same
  fetch policy as `external.get/v1`.
  A connection without `commandPath` is read-only, and `coordinatorctl check` refuses a command
  alias bound to it or to another connection type (`workflow-binding`).
- The command and its request id are frozen and persisted before the first send.
  The id derives from the run's start identity and the step, and is sent as `Idempotency-Key` on
  every attempt.
  The catalogue declares same-command recovery, so `retry-same` and restart replay the frozen request
  and never mint a new id.
- Request bodies and responses are limited to 65,536 bytes, and each attempt to the connection's
  timeout, at most 2,000 milliseconds, which also covers DNS resolution and token acquisition.
  Only status 429, and status 503 before the final attempt, are retried automatically.
  A 429 is trusted to mean the command was not processed.
  A 503 may follow an effect, so the worker records the attempt as uncertain while it retries.
  A deadline or retry limit reached before a later attempt settles it holds the run with the
  effect unknown, and Coordinator never reports such a run `expired` or `failed`.
  The worker keeps the retry only when the longest wait the schedule allows, counted from the end
  of the attempt's lease, clears the run deadline.
  Otherwise it reports the attempt uncertain without a retry, so the job is held `unknown` and
  `retry-same` can send the same command under the same id while the deadline is in the future.
  `Retry-After` is honoured only as one delta-seconds value of at most 86,400.
  Once the request may have left, a lost or broken exchange, a timeout, a redirect, any other 5xx,
  and an oversize, malformed or schema-invalid response are uncertain and hold the run.
- Coordinator checks the response against the alias's `responseSchema`, then runs the project's
  pinned pure Function.
  Only `accepted` with a result matching the step's declared output, or `refused` with a declared
  code, leaves the hold; everything else, including a Function error, is uncertain.
  The worker and offline scenarios use the same Function, and scenario validation
  (`scenario.reply`) refuses a `success` or `declared-refusal` reply to the step, so no scenario
  reaches a result or refusal route the Function would not produce.
  Transport and scenario validation share one status classification, so a `response` reply with a
  status the worker holds or retries before interpretation (a redirect, a 429 or any 5xx) is
  refused too.
- Outcomes carry fixed failure codes only.
  No body, response, request id or token is logged or placed in a problem, `status` or `inspect`.

Refused: a workflow-chosen destination, header or credential; a redirect; a fresh request id on
recovery; an oversize or unusable response; any outcome that would claim a provider failure after
the request may have left.

### COORDINATOR-INV-04: `coordinatorctl --token-file` reads only a regular file

Threat: an authenticated `coordinatorctl` command reads `--token-file` before it calls the service.
A blocking read of a FIFO can hold the command indefinitely, and following a symbolic link means
the named path does not identify the file the operator intended.

Enforcement: on Unix, `coordinatorctl` opens the token path read-only with `NOFOLLOW`, `NONBLOCK`
and `CLOEXEC`, then verifies from the opened descriptor that it is a regular file before reading
any byte.
Other platforms reject a symlink or non-regular path before opening it and verify the opened
handle.
The read is bounded at 16,384 bytes, the token is validated as a compact token, and diagnostics
carry no value.
The check applies only to `--token-file`; ordinary authored input files keep their own contract.

Refused: a symbolic link, a FIFO, or any non-regular file as a token path.

### COORDINATOR-INV-05: the raw API command grants no workflow authority

Threat: an operator assumes the raw API command reuses the token reader of the other authenticated
commands, or assumes a saved bearer or `private_key_jwt` connection grants workflow authority by
itself.

Enforcement: Coordinator retains no local caller session, so `coordinatorctl api` refuses
`--client`.
The operator selects a saved connection or an explicit one-off URL.
A saved connection authenticates by exactly one of anonymous, a referenced opaque bearer, or
renewable `private_key_jwt`, under the shared
[command-line API security boundary](https://github.com/registrystack/registry-stack/blob/v0.46.0/crates/registry-cli-api/README.md#security-boundary).
Anonymous supplies no automatic credential, though the raw command may still carry one explicit
`Authorization` header.
The helper confines destination and headers, acquires any selected credential, and releases only
the raw bounded response.
It carries no caller policy, workflow, run ownership or downstream product authority.
Coordinator still authenticates and authorises each protected route, and every receiving product
still decides an effect a run requests.

The two token readers differ on purpose.
The authenticated Coordinator commands keep the 16,384-byte compact-token validation and the Unix
`NOFOLLOW` open (COORDINATOR-INV-04).
Direct `api --url --token-file` uses the shared opaque-bearer contract: at most 8 KiB, and a
symlink to a regular file is accepted.
Saved bearer and private-key references use the platform secret resolver's separate strict file
policy.

Refused: `--client` on the raw API command; a report format before any network access.

### COORDINATOR-INV-06: OIDC discovery and key fetches cannot be steered inward

Threat: Coordinator fetches discovery and signing keys for `deployment.authentication`.
A fetch an attacker can steer may reach internal services or cloud metadata.
A key set read over plain HTTP can be substituted by an on-path attacker, whose keys would then
mint access tokens Coordinator accepts.

Enforcement: Coordinator fetches under the shared issuer network policy that Casework, Registry
Messaging and Scheduling use, or the development loopback policy under `development-loopback`:

- The declared issuer and a declared `jwksSource.uri` may resolve to a private or loopback address
  on any origin; both are operator configuration.
- A discovered `jwks_uri` inherits that allowance only on the issuer's own origin.
  On another origin it must use HTTPS and is refused when it resolves to a private or loopback
  address, under `development-loopback` too.
- Cloud metadata and link-local addresses are refused for declared and discovered endpoints alike.
  Redirects are disabled.
- Plain HTTP is accepted at load only with `deployment.authentication.allowInsecureHttp: true`, or
  on loopback under `development-loopback`.
  The setting never extends plain HTTP to a discovered endpoint on another origin.

When the runtime file is loaded, Coordinator refuses a plain-HTTP issuer or key URI these rules do
not admit, naming the member and the setting that would admit it.
It builds the issuer network policy from the same block, fetches discovery under it, and keeps the
endpoint policy that discovery settled for every later key refresh; a declared key URI keeps the
declared-endpoint fetch policy.
When the opt-in is set, startup logs a fixed warning.

Refused: a plain-HTTP issuer or key URI without the opt-in; a discovered key endpoint on another
origin that is plain HTTP, private or loopback; cloud metadata and link-local addresses anywhere;
redirects.

### COORDINATOR-INV-07: a run never decides, and cancels only what it opened, a BReg Proposal

Threat: a workflow uses Coordinator's workload identity to decide a request that a person or review
authority must decide; cancels a request the run did not open; sends a second start or submit on
retry and opens a duplicate request; or settles a follow from a stale or forged signal and routes
the run as if a request were applied.

Enforcement:

- The catalogue has `breg.read-proposal/v1`, `breg.start-proposal/v1`, `breg.submit-proposal/v1` and
  `breg.cancel-proposal/v1` and no operation that approves, rejects, decides or applies a Proposal.
  `breg.invoke-action/v1` refuses a Proposal Action, and the Proposal operations refuse an
  immediate Action, at check time and again at preparation against the live contract.
- Start and submit are frozen commands.
  Submit sends the start command and then the empty submit transition under a second idempotency
  key derived from the first (`<key>:submit`); a retry replays both, so BReg returns the original
  receipts instead of opening a second request.
- Cancel freezes the current Proposal's cancel transition, rebinds it to a fresh read before
  sending, and sends nothing when the Proposal is already cancelled.
  Check refuses a cancel whose `proposalId` is not mapped from the output of a start or submit step
  in the same workflow (`definition.proposal-not-run-owned`); BReg's own cancel grant still decides.
- A follow settles only from the current Proposal Get under the connection profile's get grant,
  never from an event.
  A 401, 403, 404 or missing get grant holds the run with `proposal-unreadable`; a Proposal of
  another Action holds with `completion-invalid-response`.
  A submit follow holds with `proposal-handoff-refused` when the review authority refused the
  hand-off; only the allowlisted refusal code is read.
- The settled output carries only what BReg discloses to the profile: the outcome, ids, submission
  version, Action revision, the decision's status, time and public reason, and the input members
  the profile may read.
- A follow's wait keeps only the latest read's Proposal state, turn, submission version and
  allowlisted hand-off refusal code, with when it was read and when that state and turn were first
  seen.
  These columns are not encrypted: they hold no person's value and no Proposal id, and the row is
  deleted with the wait.
  Inspection adds the connection's `requestLink` with the Proposal id filled in, only for a caller
  already authorised to inspect the run; the id grants nothing without BReg's own grant.
  The link must be `https` unless its host is a loopback IP address, the same rule as a connection
  endpoint.
  Loopback means an address in `127.0.0.0/8`, `::1` or an IPv4-mapped form of a `127.0.0.0/8`
  address.
  Coordinator accepts no name as loopback, not even `localhost`, because name resolution is outside
  its control.
- The run list finds waits on one Proposal through the keyed wait commitment over the database
  identity and the Proposal id, so neither the database nor the list cursor holds the id in clear.
  Each page reapplies the caller's owner and workflow scope, and a cursor is refused unless its
  version, owner, workflow scope and every filter match.
- Doctor counts Proposal waits by turn from stored rows and calls no product.

Refused: any decide or apply of a Proposal; a cancel of a Proposal the run did not open; a second
start or submit on retry; settlement from an event.

### COORDINATOR-INV-08: BReg control metadata has its own response ceiling

Threat: applying the 64 KiB business-response ceiling to caller-filtered BReg control metadata can
prevent preparation of an otherwise valid Action.
Treating that oversize answer as a transient transport error repeats an unchanged failure.
Widening the response limit globally would admit larger business data.

Enforcement: Coordinator derives a separate client only for BReg contract metadata reads, using
the BReg client's metadata ceiling of 8 MiB.
The derived client reuses the same immutable credential provider, HTTP pool and source binding.
The original 64 KiB client still sends target-condition, Record, Action and Proposal requests.
Oversized reads are refused with `invalid-response`.
Mutation classification first preserves the BReg client's unknown-outcome signal, so an oversized
mutation answer stays uncertain.
No new transport retry, authority, key, condition or Action revision is created.

Refused: a metadata answer beyond 8 MiB; any business answer beyond 64 KiB.

### COORDINATOR-INV-09: the pure Function profile is bounded and deterministic

Threat: a pure Function runs author-supplied code inside the worker.
An argument-controlled loop or allocation could hold a worker thread or exhaust memory.
A host-dependent result could differ when a wait replays or a job attempt recomputes, and a changed
engine could reinterpret a frozen definition.

Enforcement:

- The engine is Rhai pinned exactly (`=1.27.0`) with the `compact_str` backend, which keeps
  Coordinator strings, `ImmutableString` values, identifiers and object-map keys off
  `smartstring`'s reported unsound conversion.
  Rhai still declares `smartstring` unconditionally, so the unused package remains in the resolved
  dependency and advisory graph under a scoped workspace exception (COORDINATOR-RES-18).
- Limits: 100,000 operations (every authored lower limit applies), 32 calls, 64 expression levels,
  65,536 source bytes, 16,384-byte strings, 256 array items, 256 map members, 131,072 JSON bytes
  and depth 32.
  The profile has no clock, sleep or I/O.
- `curry` is disabled, because Rhai does not count data curried into a function pointer against
  these limits and every copy of the pointer copies that data.
  Check refuses a source that uses it and names `curry`.
- The interpreter identity in each frozen definition names Rhai 1.27.0 and ABI `v3`, because the
  callable set is part of what a definition means.
  A definition frozen under another identity is refused with `definition.abi`, and a live run under
  it is held (COORDINATOR-INV-12).
  Coordinator never reinterprets an old snapshot under changed engine semantics.
- The profile adds Rhai's `MoreStringPackage` and a hand-picked set of math helpers.
  Neither registers a clock, file, network or callback-invoking function.
  Coordinator registers no native helper that invokes a script callback, and its maintained Rhai
  files use no callback-based collection method.
  Rhai charges operations performed by such a callback, so an authored workflow that uses one
  reaches its declared limit sooner; run `coordinatorctl test --project <directory>` on it before
  promotion (operator obligation 8).
- Coordinator's overloads of `pad` and `replace` work out the result length in bytes before
  building anything, so a result over the string budget is refused before allocation.
  `pad` with an empty padding string is refused with an execution error, because the package loop
  would never end.
  `pad` with a character loops once per missing character, after the engine checks that character
  count against the byte limit, so the most it builds before the final check is four times the
  limit.
  The other string helpers shrink their input, are bounded by it, or grow it by a constant factor,
  and repeat-like growth through `+=` stays under the limit.
- Rhai's `BasicMathPackage` is not registered whole, because its floating-point transcendental
  functions take results from the platform math library and may differ in the last digits between
  operating systems, CPU architectures or library versions.
  Results are recomputed, not only read back: a held wait is recomputed when waits replay, the next
  WaitUntil is evaluated again, and each job attempt runs the Function again.
  A deadline computed with such a function could therefore land a second apart on two hosts.
  Coordinator registers only deterministic functions: `sqrt`, `floor`, `ceiling`, `round`, `int`,
  `fraction`, `is_nan`, `is_finite`, `is_infinite`, `to_degrees`, `to_radians`, `PI`, `E`,
  `parse_int`, `parse_float`, `to_int` and `to_float`, next to the arithmetic package's `abs`,
  `sign`, `min` and `max`.
- A Function result holding NaN or an infinite float (`0.0 / 0.0`, `sqrt(-1.0)`) is refused with
  `function.execution` where results turn into JSON, instead of becoming `null`.
- The unknown-call check walks the syntax tree and function table, which Rhai exposes only under
  its `internals` feature, enabled in the build.
  It is an authoring aid, not a security boundary: the engine refuses any name it lacks when the
  Function runs.

Refused: empty-padding `pad`; `pad` or `replace` results over the string budget; NaN and infinity
results; a definition frozen under another interpreter identity; any function outside the
registered set.

### COORDINATOR-INV-10: only listed subjects start runs, and delegated tokens are refused

Threat: a run's start input names the records, subjects and recipients the workflow reads, changes
or notifies, and every downstream call runs under the connection's own service credential or a
task grant.

could name another person's record and the workflow would act on it with Coordinator's authority:
a confused deputy.

Enforcement: every caller policy lists `subjects`: one to sixty-four distinct exact token `sub`

named people who operate the deployment.

### COORDINATOR-INV-12: a run whose retained definition does not restore is held alone

Threat: a retained run executes the definition frozen in its snapshot.
When a later version refuses that definition on restore, for a structural rule or an interpreter
ABI change, running it anyway could take an effect the rule now forbids, such as withdrawing a
review another run submitted.
Refusing the whole deployment for one such run turns every other run and every admission into an
outage.

Enforcement: the serving check at startup and in readiness restores every live run's snapshot
under the admission lock.
Restoring a definition is pure, so its refusal is a property of the snapshot: the run is held with
reason `definition-refused` and the scan continues.
Coordinator writes the durable audit request (`action: definition-refused`, the keyed run and step
references and the static `findingCode`) before the hold commits, then sets the run to `attention`
with failure code `definition-refused`.
A run already held, erased or terminal is skipped, so each run is audited once.
Dispatch never claims a held run and does not expire it at its deadline.
A worker that meets a refused definition holds the run the same way before it prepares or sends
anything.
`retry-same`, `reconcile` and `cancel` restore the snapshot first and refuse with 409
`run.definition-incompatible` before any command or cancel step, authored cleanup included, is
routed.
A hold changes no uncertain outcome, prepared command, spent key or restore-review mark.
Held runs appear in `attention=true`, the doctor report and `deployment-status` (`heldRuns`).

Refused: any step, retry, reconcile or cancel of a held run.
A snapshot that cannot be opened, a failed query or a failed transaction verification still fails
the serving check and holds nothing.
A pinned package this version does not restore still stops startup, naming its package digest,
workflow and finding code.

### COORDINATOR-INV-16: payment completion requires exact authoritative evidence

Threat: a workflow could supply an amount, provider route, header, receipt or registry destination;
reuse an acceptance for another bill, collection, instruction or disbursement; treat pending,
unknown or a timed-out wait as payment; or start a fresh provider effect after an ambiguous

The maintained payment client validates strict typed responses against the exact bill, collection,
instruction or disbursement identity before returning them.
A request is durably keyed, and reconciliation uses only the Adapter's read-only original-request
endpoint with that saved key and body under current connection authorisation.

durable key.

simulation marker, and each observation performs a fresh authorised read through the same logical
payment connection.

collection attempt, and only Adapter-verified `confirmed` state can satisfy the separate, keyed

## Operator obligations

The guarantees hold only when you meet these obligations.
The residuals refer to them by number.

1. Provide idempotency for external commands: the provider must deduplicate on `Idempotency-Key`
   and must not answer 429 for a command it applied.
   Do not use `retry-same` against a provider that lacks deduplication.
   [External provider connections](../../reference/coordinator-configuration/#external-provider-connections)
   states the provider requirements.
2. After a held external command, check the provider's own records, then `retry-same` or cancel the
   run.
   `reconcile` cannot settle it.
3. Resolve held Scheduling runs (hold creation, rescheduling and cancellation past idempotency
   expiry, and any ambiguous hold release) by investigating and resolving or cancelling the run.
4. Declare only issuer and key addresses you intend Coordinator to reach.
   A declared private address is honoured; set `allowInsecureHttp: true` only where the path to the
   issuer is trusted.
5. For a discovery document that names a key endpoint on another private origin, declare the
   endpoint as `jwksSource.uri` or serve it from the issuer's origin.
6. Grant the BReg connection profile the Proposal get grant in addition to the Action's start
   grant.
7. Run `coordinatorctl` only on a trusted single-user machine, and keep token files as regular
   files.
8. Run `coordinatorctl test --project <directory>` before promoting a workflow that uses a
   callback-based collection method.
   Watch for held runs in `attention=true`, the doctor report and `deployment-status`
   (`heldRuns`).
   A live run whose retained definition a version does not restore, under another interpreter
   identity or a restore rule it breaks, is held with `definition-refused`, and only a release
   that accepts its definition can end it (COORDINATOR-INV-12).
9. Treat a project's Function as reviewed code: a Function that maps an ambiguous provider answer
   to `accepted` is an authoring defect that scenarios and review must catch.
10. List in each caller policy's `subjects` only the identities it is meant to admit: a producer
    client's own service-account subject, or the named operators.
    Update the list after the identity provider changes a client's subject, for example when the
    client or its service account is recreated.
    [Deploy Registry Coordinator](../../operate/coordinator/) says how to find it.
11. A backend that starts runs must already have authorised, for the person it acts for, every
    record, subject and recipient identifier it passes, and any input digest it computes.
    Coordinator and the destinations cannot check this.
12. Run workflows that must not share a Casework producer identity in separate deployments: one
    deployment is one trust domain.
13. Set each connection's `clientAssertionAudience` to the authorization server's issuer
    identifier, exactly as its metadata publishes it.
    Finish live Runs on the earlier release before upgrading to one that requires the audience: a
    Run admitted without it no longer matches its binding, so `deployment-status` reports
    `live-binding-conflict` and normal serving refuses while it remains.
    `coordinator --recovery-only` inspects it (COORDINATOR-INV-15).
14. Give Coordinator only the Adapter payment capability.
    Keep the BReg bill and instruction binding and reporting grants with the authorised Adapter
    identities.
    Investigate an unresolved original-request receipt before any same-command recovery or
    cancellation decision (COORDINATOR-INV-16).

## Accepted residuals

Each residual names the condition under which it applies, its consequence, and the mitigation.

### COORDINATOR-RES-01: a replacement read may observe newer state

- Condition: a lapsed `read-again` call is retried after its lease lapses.
- Consequence: the replacement can observe newer source state than the interrupted read would have
  returned; `read-again` promises a safe current observation, not a historical replay.
- Mitigation: do not model a read whose answer must equal an earlier one.

### COORDINATOR-RES-02: a misconfigured read can have side effects

- Condition: a source that is wired as a read has side effects.
- Consequence: it is retried after a lapsed lease.
  Coordinator cannot prove a provider's implementation is read-only; the closed operation catalogue,
  fixed HTTP method and reviewed package are the boundary.
- Mitigation: review providers before binding them as reads.

### COORDINATOR-RES-03: a read that keeps losing its worker stops at `attention`

- Condition: the read's existing attempt or deadline bound is spent.
- Consequence: the run holds for operator review; recovery does not extend either budget.
- Mitigation: investigate the worker failure and resolve the run.

{/* Evidence: crates/registry-coordinator/tests/read_lease_recovery.rs

### COORDINATOR-RES-04: Scheduling mutations without a receipt stay held

- Condition: Scheduling exposes no original-result receipt for hold creation, rescheduling or
  cancellation, and idempotency expires.
- Consequence: the run is held; Coordinator does not infer an outcome from later state.
- Mitigation: investigate in Scheduling, then resolve or cancel the run.

### COORDINATOR-RES-05: Scheduling hold release stays uncertain

- Condition: hold release is unkeyed, and a timeout, broken exchange, invalid response or server
  failure follows dispatch.
- Consequence: the outcome stays uncertain and is never re-sent.
- Mitigation: resolve or cancel the held run after checking Scheduling.

### COORDINATOR-RES-06: same-command recovery trusts provider deduplication

- Condition: the provider does not deduplicate on `Idempotency-Key`.
- Consequence: `retry-same` can apply the effect twice; Coordinator cannot verify deduplication.
- Mitigation: operator obligation 1.

### COORDINATOR-RES-07: no receipt settles an uncertain external command

- Condition: `external.command/v1` has no original-result receipt.
- Consequence: `reconcile` cannot settle an uncertain command.
- Mitigation: check the provider's records, then retry or cancel the held run.

### COORDINATOR-RES-08: an accepted result is the Function's reading

- Condition: Coordinator does not independently verify the provider's effect.
- Consequence: a Function that maps an ambiguous answer to `accepted` records an effect that may
  not have happened.
- Mitigation: cover ambiguous answers in scenarios and review.

### COORDINATOR-RES-09: a refusal or 429 after an uncertain attempt is held

- Condition: a later declared refusal or 429 follows an uncertain attempt; a retried 503 counts as
  one.
- Consequence: the answer is held, not routed or retried, so a provider that replays a refusal for
  a repeated key leaves the run for an operator to cancel.
- Mitigation: cancel the run after checking the provider.

### COORDINATOR-RES-10: lease-versus-expiry window for a retried 503

- Condition: the check that keeps a 503's retry counts from the end of the attempt's lease, by
  which a live worker normally records its answer.
  A worker that records its answer after its lease has ended can still see the job expire.
- Consequence: the run shows `attention` with the effect unknown, and `retry-same` refuses the
  expired job.
  Closing the window needs the job queue itself to hold, rather than expire, a retryable answer
  that may follow an effect.
- Mitigation: check the provider's records, then cancel the run.

### COORDINATOR-RES-11: a 429 that followed an applied command ends the run `failed`

- Condition: the provider answers 429 after applying the command.
- Consequence: the final attempt ends the run `failed` with `external-rate-limited`, though the
  effect happened.
- Mitigation: the provider must not answer 429 for an applied command (operator obligation 1).

### COORDINATOR-RES-12: the token-file open guards only the final path component

- Condition: `coordinatorctl` runs on a machine where another local user can alter directory
  components of the token path.
- Consequence: the Unix open is race-safe for the final component only; broader filesystem and
  directory-component races are not guarded.
- Mitigation: use a trusted single-user machine.

{/* Evidence: crates/registry-coordinator/src/cli.rs NOFOLLOW;

### COORDINATOR-RES-13: declared OIDC addresses may be private

- Condition: outside `development-loopback`, the declared issuer and a declared key URI may resolve
  to a private address.
- Consequence: an operator who declares an internal address points Coordinator at it.
  The residual is shared across products and set out in [Token issuer and key endpoints](../#token-issuer-and-key-endpoints).
- Mitigation: declare only intended addresses (obligation 4).

### COORDINATOR-RES-14: plain-HTTP issuer allows key substitution

- Condition: `allowInsecureHttp: true` is set and an on-path attacker sits between Coordinator and
  the issuer.
- Consequence: the attacker can substitute keys (see [Token issuer and key endpoints](../#token-issuer-and-key-endpoints)).
  The setting is explicit, named in the startup warning, and confined to the issuer's origin and
  the declared key URI.
- Mitigation: keep the setting unset outside trusted networks.

### COORDINATOR-RES-15: a cross-origin private key endpoint is refused at startup

- Condition: a discovery document names a key endpoint on another private origin.
- Consequence: startup refuses it; this is an availability cost, not an integrity loss.
- Mitigation: operator obligation 5.

### COORDINATOR-RES-19: float `**` is not on the deterministic math list

- Condition: a Function uses float `**` (`powf`, in the arithmetic package).

### COORDINATOR-RES-20: a trusted backend can pass an identifier it has not authorised

- Condition: a listed backend passes a record, subject or recipient identifier it has not
  authorised for the person it acts for.
- Consequence: Coordinator cannot tell, because the input is the backend's assertion.
  Destinations check the connection's service identity, task grant and their own policy, not the
  person a run concerns, so they do not catch it either.
- Mitigation: operator obligation 11.

### COORDINATOR-RES-21: a listed subject is trusted for everything its policy names

- Condition: a listed backend credential is compromised.
- Consequence: the subject binding does not contain it: the holder can start every workflow and
  action the policy names.
- Mitigation: keep each policy's workflows and scopes to what its client needs, and protect the
  client credential.

### COORDINATOR-RES-23: a consent read before a Messaging send is advisory

- Condition: in the reviewed-notice pattern, the workflow reads consent (`noticeAllowed`) again
  immediately before the Messaging send.
- Consequence: the read is advisory at commit time: consent revoked between the read and the send
  is not seen.
  Messaging does not own consent to be contacted (see
  [Registry Messaging](../../start/messaging/)).
- Mitigation: where revoked consent must stop a send, the source of record or Messaging's own
  policy has to refuse it.

### COORDINATOR-RES-24: an input digest is the starter's assertion

- Condition: in the reviewed-notice example, the trusted starter computes `applicationDigest` over
  the bounded projection and the workflow passes it to Casework as the review subject's digest.
- Consequence: the workflow checks only that the record's identifier and revision still match the
  input, so the digest is an input trust assumption, not a consent check.
- Mitigation: operator obligation 11.

{/* Evidence: crates/registry-coordinator/tests/catalog_scenarios.rs

### COORDINATOR-RES-25: workflows in one deployment share a Casework producer

- Condition: several workflows run in one deployment.
- Consequence: they call Casework under one producer identity.
  The review-cancel rule (COORDINATOR-INV-11) is structural over the reviewed, pinned definition and
  adds no runtime check, and Casework remains the authority for each cancel.
- Mitigation: operator obligation 12.

{/* Evidence: crates/registry-coordinator/src/definition.rs cancel_not_run_owned. */}

### COORDINATOR-RES-26: this version cannot end a held run

- Condition: a live run is held with `definition-refused`.
- Consequence: `retry-same`, `reconcile` and `cancel` refuse it, and nothing runs for it; only a
  release that accepts its definition can end it.
  A run held while an earlier process's lease on its step is still open keeps that lease until it
  lapses.
  The lapse holds the step with its own failure code, replacing `definition-refused` on the run,
  and the next serving check holds the run again with a second audit record.
  Nothing runs for it in between, because every path restores the snapshot before acting.
  A held run that had failed and is still recoverable keeps its job failure code, while the run's
  failure code becomes `definition-refused`.
- Mitigation: operator obligation 8.

### COORDINATOR-RES-27: a held run's finding code is recomputed

- Condition: a report lists a held run.
- Consequence: the finding code is not stored on the run: it is in the hold's audit record, and
  each report recomputes it from the retained snapshot.
  Doctor restores retained snapshots to list held runs, so a snapshot that cannot be opened fails
  the doctor report as it fails the serving check.
- Mitigation: none needed; an unreadable snapshot is already a serving-check failure to
  investigate.

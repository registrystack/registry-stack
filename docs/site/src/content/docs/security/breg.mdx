This page states what the Base Registry Engine (BReg) security invariants assume, what you must do
for them to hold, and which limits a deployment accepts.
The operator obligations are numbered 1 to 22, and each accepted residual risk carries a stable
identifier from `BREG-RES-01` to `BREG-RES-27`.
The invariants themselves, each with its threat, enforcement point, refusal, and negative test, are
the rows of the machine-checked BReg security invariant matrix in the registry-stack repository.
This page does not repeat those rows; it names them by identifier (`BREG-SEC-NN`).
Deployment steps are in [Deploy and serve](../../operate/breg/).

## Scope and trust boundaries

BReg is trusted to keep a registry's Records inside the row boundary of the caller's access
profile, to refuse rather than guess, and to leave an audit trace of what it released.
It is not trusted to defend against the parties in this table, who hold more authority than the
product can take back.

| Party | Trusted for | Not defended against |
| --- | --- | --- |
| Holder of the migration credential | Applying a reviewed package and running operator commands (`bregctl apply`, `adopt`, `hook discard`, erasure). | Applying any valid successor of the active package. Packages are unsigned (`BREG-SEC-02`). |
| Holder of the runtime credential | Serving reads and writes through the generated row-level security policies. | In split-role mode, nothing beyond what the grants allow (`BREG-SEC-04`, `BREG-SEC-118`, `BREG-SEC-119`); the grants include reading any row by setting the transaction context the policies read (see [Read boundary](#read-boundary)). In single-role mode, rewriting the activation ledger. |
| Database superuser | Nothing is withheld from a superuser. | Editing the ledger, the instance claim, or any row. The activation audit stream is the independent trace. |
| Operator who writes the runtime file | Naming the issuer, JWKS source, listeners, secret references, and destinations. | Naming a private-network issuer, or a non-loopback HTTP issuer in development with `allowInsecureHttp` set. |
| Token issuer | Authenticating callers and signing the claims the access profiles map to authority. | An issuer that signs wrong claims. BReg verifies signature, issuer, audience, and lifetime; it does not second-guess the claims. |
| Review, evidence, and function providers | Their own decisions, within the exact bindings BReg freezes. | A provider that decides wrongly. BReg binds the result to the frozen request but does not judge it (`BREG-SEC-34`). |
| Host users who can write audit files | Nothing. | Rewriting or removing lines of a local audit file. Ship the stream to append-only storage (obligation 2). |
| Package authors | Authoring the project under review. | A reviewed package that is wrong. Deployment-only values (environment, instance, database) are refused in a package, so the same bytes are promoted unchanged (`BREG-SEC-01`). |
| BReg's in-process refresh worker | Running each configured refresh plan as that plan's service principal, inside the worker profile's root List boundary, its pinned row claims, and its `refreshExternalProjections` grant (`BREG-SEC-204`). | A plan that names a wider identity than intended. The worker presents no token from the issuer, so revoking that identity at the identity provider does not stop it. Removing the plan from the runtime file and restarting does. |

No runtime API edits access profiles, Record types, or webhook destinations. A running process
reloads no package and no runtime file. Of its own settings, it refetches only the token issuer's
signing keys. An
access profile or a Record type changes through a new package applied under the migration
credential. A webhook destination's endpoint and secret change in the runtime file and apply at
restart.

The signature covers `webhook-id`, `webhook-timestamp` and the exact body, leaving the method,
the URL and `Registry-Recipient-Binding` outside the signed input. The binding only selects a key,
so a substituted binding selects a key the sender does not hold, and BReg requires separate keys
per destination and per review authority because a captured delivery verifies wherever its key is held.
Startup refuses shared key bytes and identifies both configuration paths.
BReg refuses a timestamp more than 300 seconds from its clock and stores one completion per
authority and `webhook-id` for the recovery window.

An accepted completion only makes a result lookup due.

### In-process refresh worker

Indexed external views are refreshed by a worker inside BReg, not by an outside client.
This moves a trust boundary: the operator who writes the runtime file now chooses the identity
each refresh plan acts as (`externalRefresh.plans.<id>.worker`), and BReg builds that caller's
claims itself, as it does for record timers.
The worker acts with the profile's required scopes and purposes, the configured principal, and
the pinned row claims.
`bregctl check` refuses a profile that lacks root List or `refreshExternalProjections`, declares
`requireConsent`, does not admit the requester client, or leaves a row-boundary claim unpinned.
It also refuses a plan whose configured identity the profile would refuse on a request, such as
two values pinned for an `equals` boundary or a principal over 512 bytes, as
`breg.external-refresh.worker-not-admitted`.
At startup such a plan is logged and skipped while other plans run.
A configuration change, not an identity-provider revoke, stops the worker.
Each attempt and terminal settlement is audited as `external-refresh-plan-step`, and the terminal
entry carries the same pseudonymous principal and record references as its attempt.

### Supply chain

Packages are verified by the SHA-256 of `SHA256SUMS`, with every listed file re-hashed before the
digest is trusted.
No signature or trust anchor is consulted.
The Wasmtime build that runs WASM hook handlers is pinned and built without its default features.
No automated check pins that feature set, so a change that unifies a default feature back on is
not caught by CI.

### Applicant review progress

A current caller-owned status grant can opt in to a provider-authored code (`BREG-SEC-208`).
BReg authorises and audits the read before using the configured Review producer credential for a
single bounded lookup.
It compares the whole accepted review binding, then rechecks Proposal visibility and the live
round before the response audit and release.
Failure to observe the exact round yields the authorised local status with progress omitted.
A code is display data.
It grants no approval or application authority.

### Read boundary

Row-level security on the Record tables is the single read boundary, and
`FORCE ROW LEVEL SECURITY` is on for every one.
Record source views are created `security_invoker=true` and deliberately without
`security_barrier`, so a list page can be served from an index.
That does not let a row the caller cannot read reach a predicate: PostgreSQL applies a table's
policies as security conditions before any predicate that is not leakproof, whether or not a view
over the table is a barrier, and every read policy carries `record_lifecycle = 'active'` itself.
The runtime also sends only SQL the engine generates (`BREG-SEC-143`).
An executed proof reads the view through a non-leakproof predicate that raises on a hidden Record
and shows it is never shown one.
The view options are part of the managed schema fingerprint, so a database that regains
`security_barrier` or loses `security_invoker` is drift and startup refuses it.
Derived views and the spatial candidate view keep their barrier.
The generated policies defend against application mistakes and pooled-context leakage.
They do not constrain a party holding the runtime database credential, which can set the same
transaction context the policies read; that credential's custody and rotation are operator controls.
See `BREG-RES-16` for what remains.

A `--require-value` rule in a generated Evidence source runs in the Evidence adapter, after BReg
has returned the Record.
It is not a BReg authorisation boundary.
The access profile's row boundary is the only place BReg withholds a Record from the Evidence
workload.
An Evidence caller receives the same answer for a Record the rule refuses and a Record that does
not exist.
Only the Evidence audit record of a single request and the `evidence_source_lookups_total` metric
record the difference (`no-match` versus `unresolved`).
An operator, or anyone who reads that audit, can tell from it that a refused Record exists.
A request batch audits both items as not available, and the metric still counts them apart.

BReg counts each request it refuses by the check that refused it, in `breg_request_refusals_total{check}` on the private metrics listener.
The `check` label is a closed set of 45 names, every one published at zero, and no caller value becomes a label.
Each refusal also writes one `request refused` log line with `failed_check` and the request's trace id when it has one, at most five lines per check per minute, with `suppressed` counting what a window held back.
A request that BReg answers `404 resource.not_found` because the caller may not see the target reads the same to the caller whatever the reason.
The operator can tell the reasons apart: the counter holds the request under the rule that refused it, for example `scope`, `purpose`, `requester-client`, `row-boundary`, `task-grant-binding`, `disclosure` or `visibility`.
A refused write the engine answers with `write.outside-boundary` counts under `row-boundary`, and a Proposal outside the caller's scope counts under `ownership`.
A batch of Proposal review contexts answers `200`, and each concealed item counts once under its own check.
A `412` for a stale version and a request for an unknown route are not counted.
A failed field guard counts under `action-guard`, also when it answers the generic `412`.
A refusal on the `scope` check also names the claim that carries scopes, the scope the operation needs and the access profile, each as the configuration or package declares it.
Neither the counter nor the line holds a token, claim, client, subject, scope or identifier from the request, and recording a refusal changes nothing the caller receives.
A `visibility` count is a record that is absent or outside the boundary, and BReg does not say which, so it also counts a caller probing for identifiers.
The audit journal's `refusalReason` stays the three values it lists below.

### Public check export

`bregctl generate evidence-source --public-check` exports the Source of an Evidence [public check](../evidence/#the-public-certificate-check).
Evidence compares the check code only after the Source returns a record.
A failure on one record's content before that comparison would show a caller without the code that the record exists.
The generated adapter therefore states only each fact's scalar type and omits missing, null and mistyped facts.
It answers no match when the returned identity is missing or differs from the request.
The derivation and output contract of the Evidence definition enforce content requirements after the comparison.
The export is another pack version: `publicCheck` is part of the behaviour the pack version digests, with the selected lookup contract and the artifact digests.

Two signals remain before the comparison.
A malformed response envelope fails as a Source error.
So does a response over the pack's limit of 65,536 bytes.
The exporter refuses a public check when the selected fields' declared bounds can exceed that limit.
A response that exceeds the registry's declared bounds can still fail before the comparison.

Review the public Source, the Evidence derivation and the target activation together.

### Disclosure conditions

A disclosure condition withholds a Record, its history, or named fields from every access profile it
does not exempt, while the Record's current values match the condition.
A `record` condition is a restrictive row-level security policy on the Record table.
It binds every query under a bound profile, read paths, lookups and counts included, so a hidden row
never reaches a filter, a sort, or a count.
A `history` condition is applied in Rust to revisions and snapshots, which answer as not found.
A `fields` condition is applied in Rust after the SQL query.
Reads, revisions, and Proposal review show each named member as `null`, and a write response never
carries it.
Filtering and sorting run in SQL before that step.
`bregctl check` therefore refuses each surface that would let a bound profile filter, sort, look up,
export, count, project, or derive from a withheld field (`breg.disclosure.*`), read path grants
included.
It also refuses a `record` condition on a consent Record type that a `requireConsent` names.
The consent check reads that type under the gated profile, so a hidden revocation would let an
earlier consent stand.
Writes are checked in Rust against the writing profile.
A bound profile cannot lift a mark, write a withheld field, or tombstone a marked Record, and a write
whose result a `record` condition would hide from the writer is refused.

`exemptProfiles` is the only authority over a condition.
An exempt profile reads and writes as if the condition did not exist, and only an exempt profile can
lift it.
The record timer runs under the reserved `system-record-timer` profile, which every condition
exempts.
The compiler therefore refuses a timer that reads a withheld field.
On a Record type with a `record` condition, it also refuses a timer that creates a Record a bound
profile can read.
An automatic Proposal is checked against the profile that submitted its version, but it reads and
writes under `system-proposal-apply`, which no condition can exempt.

A profile with `requireAccessReason` must send a `Registry-Access-Reason` header on each Record read
and direct write.
BReg refuses a missing or invalid header with `400 request.access_reason_required` before any Record
is read, and stores the reason on the subject access log entry of a Record type with `accessLog`.
The compiler refuses the key on a profile that grants an operation that does not check the header.
BReg writes no subject-log entry for a Proposal attachment download or a Proposal review read, even
when the review shows fields of a Record type with `accessLog`.
Those reads are recorded only in BReg's [audit records](../../operate/breg-monitor/#read-audit-records).
A Record attachment download records a returned read in the subject access log when its Record type has `accessLog`.
It also writes a read audit record.
See obligation 22 and `BREG-RES-27` for what remains.

### Record history and Proposals

A revision written by applying a Proposal carries an optional `proposal` member with the Action
identifier, the Proposal identifier and the submission version.
The member discloses a Proposal identifier only under Proposal read authorization.
BReg resolves the link from the Proposal's stored application results, then keeps it only when the
selected access profile could read that Proposal: the same grant, ownership and row-boundary check a
Proposal read applies, run by the same code.
A profile that reads the Record's history but holds no `get` grant on the Proposal, a caller who does
not own a caller-owned Proposal, a caller whose row boundaries exclude a target, a caller under
a task grant and a standing agent all receive the revision without the member.
That response is the one a revision no Proposal produced would get.
Operator erasure of a Proposal's detail keeps the link, because the identifier and state survive and
the Proposal read already reports that its detail was erased.
History erasure removes the link with the revision it erases.
The Proposal keeps its state and application, and a current Proposal read leaves that revision out
of `resultLinks`.
The receipt of the original apply is not rewritten.
While the registry holds that response, a retry by the same authorised caller with the same
idempotency key returns the receipt as first issued.
It names the record and the revision number, and carries no field values.
`bregctl proposal-retention erase` for that Proposal removes the held response with the rest of the
Proposal's detail, where the Action's retention mode allows it.
A Proposal read still checks every record the application wrote, including a record whose revision
was erased.
The check reads the Proposal without locking its row, because an applied Proposal no longer changes.
All the checks of one read share one deadline.
If a check cannot finish, because of a conflict, a store failure or that deadline, the read answers
`503 source.unavailable` instead of leaving out the member.
The caller-filtered OpenAPI document declares the member only on the revision routes where the
caller would receive it.

The link has these known limits:

- A caller who holds a Proposal `get` grant for the Action but fails its ownership or row-boundary
  check makes BReg run one extra short transaction for each linked Proposal.
  That caller may infer from the response time that a Proposal wrote a revision.
- The check writes no Proposal-read audit entry.
  Only the revision read is audited.
- The member disappears once a record the Proposal targeted is tombstoned, because the Proposal
  target check sees only active records.
- Each distinct Proposal on a page costs one short read transaction, up to 100 on a full page.

### One-call writes

An immediate Action that patches an existing Record normally asks the caller for a condition:
a token that proves which revision the caller saw.
An Action that declares `concurrency: current-revision` sends no condition.
BReg then evaluates the Action's commit guards against the Record it has locked for the write,
and applies the patch to that same locked row.

On such an Action the guard is the only protection against a stale write.
The author owns choosing a guard that the Action's own write makes false, so a second, stale call
finds the guard false and answers `412`.
`bregctl check` refuses the Action unless every Record it patches has an `equals` or `isNull` guard
that its write falsifies.
It also refuses a `revision: unchanged` guard, a function plan that writes an existing Record, and
any value from `fromInput` or `fromEffect` written into an existing Record, because a value the caller chose
from a stale view would silently overwrite a concurrent update.
A create effect may still take caller values.
A Proposal cannot declare the setting.

A missing Record and a Record outside the caller's row boundary answer with the same body, as they do for a conditioned Action.
A caller who holds no read grant on the guarded field gets the generic `412 precondition.failed`.

### Record files

A Record type's file slot is written once.
The create effect of an immediate Action writes it, or an applied Proposal promotes one of its files into it.
The file commits in the transaction that writes the record, its history, the idempotency receipt and
any hook event.
BReg checks the media type, the size and the SHA-256 digest before it writes anything.
A slot that already holds a file refuses a second one with `409 attachment.slot-write-once`.
Erasing the slot's reference leaves a marker, so the slot is never filled again.
The marker keeps the file's SHA-256 digest, media type and size and the revision that filled the slot.
It drops who filled the slot and when.
The runtime role can only add and read references, so it cannot replace or remove one.
Hook events never carry file bytes.
When file verification is configured, BReg refuses an immediate Action's file if its stored verdict is already rejected.
An unseen or pending file commits before the verification worker checks it.
Until the worker approves the file, it cannot be downloaded.
A later rejection leaves the slot unreadable, and the slot cannot be filled again.
Field disclosure conditions and field encryption do not cover file slots.
BReg stores file bytes unencrypted, in PostgreSQL or in external storage.

A download needs the slot in the selected profile's `readableAttachments`, and `bregctl check` accepts
that grant only beside `get` on the Record type.
BReg checks the grant and a keyed principal before any I/O.
It then finds the record through the Record type's ordinary read relation, so row boundaries,
consent and lifecycle apply as they do on `GET`.
It loads the reference and the bytes in the same transaction, under the lock that deletion takes.
It releases the bytes only when they match the stored size and digest.
A profile without the grant gets `404 resource.not_found`, with no digest.
So do a record outside the boundary, an empty slot and a file that verification has not approved.
A download is recorded in BReg's read audit and, when the Record type has `accessLog`, in the
subject access log.
Both name the operation after the record's `get` operation and the slot, such as
`records.application.get:attachment:evidence`.
A refusal before byte access names the declared slot too.
An undeclared slot uses only the `:attachment` suffix, so caller-supplied names do not enter the audit.
A download that fails after it starts is audited as refused and is not logged for the subject.

History erasure keeps current files, including files a Proposal promoted.
It clears their attaching actor and timestamp when the boundary reaches the revision that attached them.
It removes a file only when the request names its slot in `eraseFiles`.
BReg checks those names against the verified active Record type before any erasure.
An erased slot keeps only its identity and erasure timestamp, so it cannot be filled again.
It retains no digest, media type, size or attachment revision.
An erased Proposal file reference also drops its digest, media type, size and uploader metadata.
A still-live Proposal keeps its file metadata and held responses until its own detail is erased.
History erasure removes Proposal links to erased revisions.
Its report and audit count those links and kept or erased file references.
BReg deletes the bytes only when no other record and no Proposal refers to them.
Proposal erasure and attachment cleanup count record references too.
The verification worker also checks files that only a record holds.

A promotion adds a record reference to the bytes that the frozen Proposal file already holds.
`bregctl check` accepts it only when the record slot accepts every media type and size the Proposal slot accepts.
The record slot must also be classified at least as restricted as the Proposal slot, so a promoted
file's classification label never drops.
The label is checked once, by `bregctl check`.
Who can download the promoted file is then decided by the record grants' `readableAttachments`.
Promotions are part of the Action's definition revision, so changing one changes the Action.
So are the request-file bindings of an immediate Action.
Apply rebuilds the Proposal's file manifest and refuses a file that verification has not approved.
Inside the apply transaction it checks the frozen file again, under the lock that deletion takes.
A file whose verdict turns to rejected after the manifest check is still refused.
It then adds the reference beside the record revision the effect wrote.
An unapproved file answers `412 precondition.failed`.
A filled slot answers `409 attachment.slot-write-once`.
Either refusal rolls back the whole apply.
Erasing the Proposal keeps the promoted bytes and removes files that nothing promoted.

## Accepted residuals

The residuals are ordered by operator impact.
Each lists the condition, the consequence, the mitigation, and the related matrix identifiers.

### `BREG-RES-01`: physical copies are not detected (instance claim)

- Condition: the database is restored by point-in-time recovery, a storage snapshot, a base backup,
  or a promoted replica.
- Consequence: these keep the system identifier and database oid, so the copy matches the claim and
  serves without adoption.
  A physical restore serves without the adopt that supersedes reopened authorities, so an import
  authority closed after the backup point is open again.
  Nothing enforces the adopt.
  Where the system identifier is unreadable (a managed service), the claim compares the database
  oid alone, which is weaker.
- Mitigation: fence the original, run `bregctl instance-claim adopt` on the copy before it serves
  (obligation 3).
- Related: `BREG-SEC-114`, `BREG-SEC-115`, `BREG-SEC-116`, `BREG-SEC-117`.

### `BREG-RES-07`: statistical datasets give no confidentiality guarantee

### `BREG-RES-23`: a revoked task grant keeps reading until its token expires

- Condition: Casework revokes a task grant, or the task ends, while the agent still holds a token

### `BREG-RES-24`: exact releases trust the declared classification

- Condition: a dataset is released under `exact-public-values`.

  A Record type or field wrongly classified `public` is released exactly, cells of one included.
  The release is immutable and readers can copy it. Withdrawal erases only the engine's stored content.
  BReg trusts a derived relation's SQL to read only the source Record types it declares.
  The check is per Record type, not per column.
  So a derived field classified `public` whose SQL reads a restricted field of a public Record type
  is released exactly.
- Mitigation: review a classification change as a disclosure decision.
  Review a derived field's SQL before you classify it `public`.

### `BREG-RES-26`: released sums keep inference paths the rules do not close

- Condition: a dataset releases a sum under `minimum-count-and-rounding`, with a declared
  `contributor` and `dominancePercent`.
- Consequence: the contributor count and the p% rule protect contributors from each other inside one
  dataset and one version.
  A suppressed sum also suppresses the same measure in every total that contains it.
  These paths stay open:
  - The compiler refuses two protected releases of a sum of the same field over the same unit
    (`breg.statistical-dataset.sum-field-released-twice`).
    It does so whatever their dimensions, populations, and granularities, because any two share a
    total that the totals rule cannot see across datasets.
    An `exact-public-values` release of the same field still publishes what the protected release
    withholds.
    That release needs the field classified `public` (`BREG-RES-24`).
  - A count withheld by the contributor minimum does not blank its totals.
    A reader can estimate it from the rounded total and its rounded siblings, to within about half the
    rounding base per cell used.
    The contributor minimum protects a count only as far as rounding does (`BREG-RES-07`).
  - Revised versions of the same period can be differenced against each other.
    Changing `dominancePercent` between versions does not start a new series.
  - The p% rule does not protect against a reader who already knows several contributors' values.
  - A decimal sum is exact, so it sits beside a rounded count of the same cell.
    A reader learns the exact amount, though not the exact number of contributors.
  - A cell of at least `minimumCount` contributors publishes a sum of zero with status `exact` in two
    cases.
    One is when no contributor has a value for the field.
    The other is when the field is `decimal` and every value is zero.
    Either tells every reader that no contributor in the cell has a positive value.
    An `int64` sum of zero with status `rounded` says only that the sum is under half the rounding base.
    A smaller cell is suppressed, whether or not its Records have a value.
- Mitigation: release a sum only after a statistician has reviewed the rules and their
  implementation.
  Until then, the compiler refuses a `publish` or `read-releases` grant on such a dataset.
  Release every sum of a field in one dataset, and keep the revisions of a period few.
  Use the publisher's dry run to see which cells and totals will be blank before you publish.
  Serve values that must stay exact, or that can be negative, through `read-exact`.
- Related: `BREG-RES-07`.

### `BREG-RES-27`: a disclosure condition does not hide every trace

- Condition: a disclosure condition binds a profile that reviews, writes, or references the Records
  it withholds.
- Consequence: the condition hides values, not every effect of their existence.
  A Proposal's reviewers see its inputs, even for a field their own profile would not read.
  Their review reads and attachment downloads write no subject-log entry.
  A `409 mutation.conflict` on a unique value confirms that a hidden Record or a withheld value
  exists, and a reference write confirms that its target exists.
  A `403 write.outside-boundary` tells a bound writer that a condition matches the Record.
  A `history` condition answers the revisions of a readable Record as not found.
  An automatic Proposal cannot change a Record a `record` condition matches, or set a `record` mark,
  even for an exempt submitter.
  It ends `blocked` with no retry, and the Record is unchanged.
  A refresh profile a `record` condition binds skips the marked roots, so their external projections
  are not kept current.
  Every route that would read a withheld value directly is refused at compile time instead (see
  [Disclosure conditions](#disclosure-conditions)).
- Mitigation: keep withheld fields out of uniqueness constraints, or accept the
  `breg.disclosure.withheld-field-probe` finding only when the profiles that create or patch these
  Records are trusted.
  Grant review of protected Record types narrowly.
  Apply such Proposals by hand under an exempt profile, or use an immediate Action.
  Exempt the refresh profile, or accept `breg.disclosure.external-refresh-withheld-root` to leave the
  marked roots out.
- Related: `BREG-RES-12`, `BREG-RES-14`.

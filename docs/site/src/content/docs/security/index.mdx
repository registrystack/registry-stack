Registry Stack protects data through product-specific authorisation, closed configuration, bounded
source access, explicit disclosure, package integrity, and accountable audit.

The [threat model](../explanation/threat-model/), [known limitations](../explanation/known-limitations/),
and [release trust evidence](openssf-evidence/) provide review context and public evidence.

## At a glance

| What | Where it stands |
| --- | --- |
| Evidence authentication on every assertion or definition route | Built in. Operational, discovery, and metadata routes and the activated public check are the exceptions |
| Evidence inbound authentication | OIDC bearer with one governed issuer profile. No API-key or static-credential mode |
| Deny-by-default authorisation before source access | Built in |
| Only public verification material is published | Built in |
| Evidence person-level access audit | Built in and fail-closed, with no best-effort switch |
| Evidence disclosure | Fixed by the requirement: only its declared concepts, each in one closed [value form](../explanation/how-evidence-works/). A caller cannot select or widen it |
| SD-JWT VC assertion serialisation | Built in as an encoding. The assertion format itself is not a credential lifecycle |
| Holder-bound presentation | Declared per requirement and verified by the relying party |
| Replay prevention for presentation | Not provided. The relying party owns challenge issuance, retention, and consumption ([replay protection](evidence/#replay-protection)) |
| Key custody, audit retention, isolation, TLS, and edge quotas | Operator responsibilities |
| Compliance with cited external standards | Not claimed |

## The Evidence request in one pass

- **Authenticate.** Evidence verifies the bearer signature, issuer, audience, token type, and
  algorithm against one governed OIDC profile. It never trusts a proxy identity header or falls
  back to an alternate principal claim.
- **Authorise.** One complete grant and authority path must match the requester, requirement,
  purpose, subject roles, selector profiles, origin, authority, and audience. Authorisation finishes
  before source credential resolution or source access.
- **Serve.** The core runs only the governed source routes, validates typed concepts, and
  constructs an answer that carries only the requirement's declared concepts, each in its closed
  value form. Caller input cannot add a source request, expression, disclosure field, or output
  projection.
- **Audit.** An access-attempt record is durably accepted before each source acquisition and a
  disclosure-release record before the response leaves. Audit failure blocks the corresponding
  action. Entries are minimised and value-free. Tamper evidence depends on shipping them to
  append-only storage.

Every Evidence route returning an assertion or its protected definition requires a verified access
token. `/health`, `/ready`, `/openapi.json`, `/catalog.jsonld`, the issuer JWKS, issuer metadata,
and protected-resource metadata are public because they contain no person-level result or grant
inventory. The [public certificate check](evidence/#the-public-certificate-check) is
unauthenticated and reads registry data. It exists only when the operator activates it. An issuer
publishes only the public half of an assertion-signing key, so a verifier needs no source or
service credential.

Subject binding, presentation verification, and replay limits are set out in the
[Registry Evidence security model](evidence/#subject-binding-and-presentation).

## An AI assistant acting for a citizen

A citizen can ask an AI chat assistant to read their own Base Registry Engine (BReg) record and
prepare a correction to it through the `breg-mcp` gateway. BReg decides what the gateway, acting as
the citizen's delegated agent, may read or change.
[What the design guarantees](../configure/breg-mcp/#what-the-design-guarantees) states each
property with its enforcement point. These points complete it:

- A call the gateway answers or refuses without a registry request, such as `describe_service`,
  makes no token exchange.
- BReg refuses an actor it is not configured to trust for that client.
- A standing agent without a task grant cannot invoke immediate effects or publish a statistical
  release.
- The `breg-review` page calls BReg only to read the registry contract, the draft, and the draft's
  target, and to submit.
- BReg records an agent's calls with keyed pseudonyms for the agent, the citizen it acts for, and
  the client.
- What the assistant says in conversation is outside these controls. The review page shows the
  canonical draft BReg holds, not the assistant's summary of it.
- BReg ties a Proposal's target to the requester only through the `targets` row boundaries its
  access profile declares. A profile that declares no such boundary gets none of this from BReg.
- A delegated token that leaks stays valid at BReg until it expires, so the authorization server
  must keep exchanged token lifetimes short.

## Maintained boundaries

- BReg authenticates callers and applies compiled access profiles to its own records, changes,
  history, and events.
- Registry Evidence authorises before contacting a fixed source and signs only the concepts its
  reviewed requirement declares.
- Registry Manifest publishes static metadata and grants no runtime authority.
- Registry Discovery returns inert public metadata. The application owns provider trust.
- Registry Platform supplies shared primitives while each product owns policy and configuration.

## Token issuer and key endpoints

Every product that validates access tokens fetches the issuer's keys under one shared issuer
network policy:

- The declared issuer and a declared key set URI may be on a private network or on loopback.
  Loopback means an address in `127.0.0.0/8`, `::1` or an IPv4-mapped form of a `127.0.0.0/8`
  address, or the name `localhost` in any letter case, which the product connects to only through
  the loopback addresses it resolved. `a.localhost` and `localhost.` are ordinary named hosts. Any
  other name that resolves to a loopback address is refused. The operator who writes the runtime
  file is trusted to name them.
- Cloud metadata and link-local addresses are refused for declared and discovered endpoints alike.
- A key endpoint discovered on the issuer's own origin inherits the issuer's policy. On another
  origin it must use HTTPS and is refused when it resolves to a private or loopback address.
- Redirects are not followed.
- Plain HTTP beyond loopback needs the product's `allowInsecureHttp: true` setting. The setting
  never extends plain HTTP to a discovered key endpoint on another origin. Startup logs a fixed
  warning when it is on.
- `jwksSource` sets where the keys come from: `discovery` (the default), a declared `uri`, or
  `static` keys read from a secret for a deployment with no network access to the issuer.

Under `allowInsecureHttp: true`, an attacker on the network path to the issuer can substitute keys
and so mint tokens the product accepts. An HTTPS issuer, an unset `allowInsecureHttp`, or keys
pinned with a static `jwksSource` each close that path. The security models for Base Registry
Engine, Casework, Coordinator, Document Store, Messaging and Scheduling name their own setting path
and any stricter rule, such as Coordinator's loopback rule.

Registry Evidence is stricter. It accepts only a declared `uri` key source, and it refuses
`allowInsecureHttp` outside the local assurance profile. Registry Render and the `evidence-oid4vp`
verifier front end log no startup warning when `allowInsecureHttp` is on.

## Refused requests

Each runtime counts every refused request by the check that refused it, in
`<product>_request_refusals_total{check}`, with a closed set of 45 checks that start at zero.
Each refusal also writes one `request refused` log line with `failed_check`, at most five lines per
check per minute, and no token, claim, scope value or client identifier.
The answer a caller receives does not change, so the counter is how an operator tells apart refusals
that look the same to the caller.
Alert on the counter, and not on a log line, because the line is rate limited.
The counter names the check and never the caller.
The labels `ownership` and `visibility` tell apart a target that exists from one that does not, so
keep metrics to the operator.
The product pages say what each counter covers:
[BReg](breg/), [Casework](casework/), [Coordinator](coordinator/),
[Document Store](documents/), [Evidence](evidence/), [Messaging](messaging/), [Render](render/) and
[Scheduling](scheduling/).

## Operator responsibilities

Operators provide identity issuance, TLS and network controls, secret storage, key rotation, durable
audit storage, database security, backups, monitoring, and incident response. The software keeps
secrets out of distributable artifacts and supplies the enforcement primitives that the operator
provisions and runs.

This document defines the Registry Stack 1.0 compatibility contract for `registryctl`: adopter
authored files, the ten root commands and their ownership boundaries, machine-readable reports,
the generated deployment package, and process exit statuses. The implementation meets these
requirements, but the document remains `draft`; the compatibility promise takes effect with
Registry Stack `v1.0.0`, not with a pre-1.0 release.

## 1. Scope and conventions

The key words in this document are interpreted per [RS-DOC](../rs-doc/) Section 2.
This specification refines the command-line compatibility promise in the
[API stability and versioning reference](../../reference/api-stability/).

This specification covers:

- Authored project files rooted at `registry-stack.yaml`.
- Public commands and their source-access, mutation, and authority boundaries.
- Versioned JSON reports intended for automation.
- Generated deployment-package ownership and discovery.
- Success, domain, usage, and operational exit statuses.
- Authorization-before-source and the Registry Relay evidence boundary.

Human-readable output, private build or development layouts, hidden worker protocols, and
operator-owned orchestration outside a generated package are not compatibility surfaces.

REQ-PR-REGISTRYCTL-001: Every machine-readable report MUST identify its schema with a
`schema_version` or a public `schema_id` and `schema_version` pair.
A report schema MUST remain backward compatible within the 1.x release line.

## 2. Command surface and project selection

Registryctl 1.0 exposes these root commands:

| Command | Contract |
| --- | --- |
| `init` | Create a project from a tested embedded template |
| `test` | Execute authored fixtures offline through production semantics |
| `dev` | Build and run an isolated disposable development environment |
| `check` | Validate and explain authored intent without writing build state |
| `build` | Emit deterministic unsigned product-lane signing inputs |
| `deploy` | Generate or verify a governed deployment package |
| `doctor` | Diagnose host, released-artifact, and product prerequisites |
| `review` | Compare authored intent with an approved baseline |
| `trust` | Inspect and create independently owned trust artifacts |
| `tooling` | Print schemas and references or install editor support |

REQ-PR-REGISTRYCTL-002: Registryctl MUST expose exactly `init`, `test`, `dev`, `check`, `build`,
`deploy`, `doctor`, `review`, `trust`, and `tooling` as public root commands.
Registryctl MUST NOT perform an automatic update check, expose an update-check command, or contact
a release service when printing `--version`.

REQ-PR-REGISTRYCTL-003: Global `-C <project-directory>` and
`--project-dir <project-directory>` MUST select the project before discovery, whether the option
appears before or after a root command.
Without that option, Registryctl MUST select the nearest parent that contains
`registry-stack.yaml`.
The option MUST NOT replace the positional `init` destination.

REQ-PR-REGISTRYCTL-004: Environment selection MUST use, in order, an explicit `--environment`,
`REGISTRYCTL_ENVIRONMENT`, the project default, or the sole declared environment.
Otherwise Registryctl MUST fail and name the declared environment identifiers.
Signing, approved-set, deployment, and initialization authority inputs MUST remain explicit.

## 3. Authored project contract

A project root references adopter-owned environment, integration, fixture, and entity files.
Strict schemas embedded in Registryctl define those files.

REQ-PR-REGISTRYCTL-005: Registryctl MUST treat `registry-stack.yaml` and every referenced authored
file as adopter-owned input.
Initialization MUST accept only an absent destination or an empty real directory and MUST NOT
overwrite an existing project.

REQ-PR-REGISTRYCTL-006: The public 1.0 template selections MUST be
`registryctl init <project-directory> --template http` and
`registryctl init <project-directory> --template spreadsheet`.
Initialization MUST be offline and MUST copy the selected tested template embedded in the
installed release.
OAuth-backed Rhai and domain-specific integrations MUST be authored adaptations, not additional
templates.

REQ-PR-REGISTRYCTL-007: Initialization MUST validate the embedded project and its editor setup in
private staging before publishing the complete project.
If validation or publication fails, an absent destination MUST remain absent.
A pre-existing empty destination MUST remain empty.

REQ-PR-REGISTRYCTL-008: The project, environment, integration, fixture, and entity schemas MUST
reject unknown fields.
Authored paths MUST remain inside the project root.
Registryctl MUST reject traversal, symbolic links, and unsupported file types before compilation,
fixture execution, or source access.

## 4. Workflow boundaries

REQ-PR-REGISTRYCTL-009: `test` MUST execute fixtures offline without Docker, secrets, or source
access.
`check` MUST validate without writing build state or contacting a source.
Its ordinary explanation MUST redact secret references and source-returned values.
Directly authored non-secret values MAY appear only when a user selects
`--show-authored-values` in local human output.

REQ-PR-REGISTRYCTL-010: `build` MUST publish a deterministic complete unit of unsigned signing
inputs for the closed lanes `relay-public` and `relay-consultation`.
It MUST NOT sign, assemble, deploy, activate, or contact an authored source.

REQ-PR-REGISTRYCTL-011: `dev` MUST use the installed release lock and exact digest-locked images,
isolate disposable development trust, credentials, and state, and bind public endpoints to
loopback.
It MUST reject production and evidence-grade environments.
Authorization MUST succeed before Registry Relay contacts an operator-bound source.

REQ-PR-REGISTRYCTL-012: `doctor` MUST be read-only and MUST NOT fetch replacement artifacts or
contact an authored source.
`review compare` MUST perform no signing, deployment, source access, or project mutation.
`tooling` MUST require no Docker, source access, secret, or deployed product.

## 5. Trust and approved-set boundaries

REQ-PR-REGISTRYCTL-013: `trust bundle inspect` MUST NOT grant trust.
Bundle verification MUST use an explicit anchor for the same product lane and acceptance identity.
Signing MUST consume one generated lane input, an explicit anchor, and explicit supported key
locators, then create a fresh closed bundle directory without editing the input or anchor.

REQ-PR-REGISTRYCTL-014: Anchor creation and rotation MUST preserve product-lane ownership.
Rotation MUST create a next anchor and authenticated transition without editing the current anchor.

REQ-PR-REGISTRYCTL-015: Initial approved-set assembly MUST accept exactly the independently
verified `relay-public` and `relay-consultation` lanes.
An update MUST bind to the preceding approved set and replace every affected lane.
The approved set MUST remain a handoff record, not a third signature or activation authority.

## 6. Machine-readable reports

REQ-PR-REGISTRYCTL-016: A command in JSON format MUST write one versioned report and no human
progress text to standard output.
Warnings outside the report MAY use standard error.

REQ-PR-REGISTRYCTL-017: `registryctl.init.v1` MUST contain `schema_version`, `status`, `project`,
`project_kind`, `output`, `source`, and `artifacts`.
Automation MUST use `output` and `artifacts` instead of assuming an initialization layout.

REQ-PR-REGISTRYCTL-018: `registryctl.project_command.v1` MUST satisfy the committed
`registryctl.project_command.v1.schema.json` contract.
When `output` is present, automation MUST treat that field as the supported complete build root
and MUST NOT construct a private path below it.

REQ-PR-REGISTRYCTL-019: `dev smoke --format json` MUST emit `registryctl.dev_smoke.v1` with
`schema_version`, `project`, `environment`, `results`, and `passed`.
Each result MUST contain `scenario_id`, `status`, `token_counter_delta`,
`source_counter_delta`, `minimized_claim_ids`, and `passed`.
The report MUST contain no credential or source-returned value.
Counter deltas MUST be unavailable for operator-bound sources.

REQ-PR-REGISTRYCTL-020: `doctor --format json` MUST emit `registryctl.doctor.v1` with
`schema_version`, `status`, `environment`, `profile`, and `checks`.
Each check MUST contain `id`, `status`, `category`, and optional `remediation`.
The aggregate status MUST be `ready` only when every check is ready.

REQ-PR-REGISTRYCTL-021: A 1.x release MUST NOT remove or rename a versioned report field, change a
field's type or meaning, make an optional field required, add a field where the schema rejects
additional properties, or reuse a schema version for a different shape.

## 7. Generated deployment package

Registryctl owns the generated closure.
The operator owns the binding, secret and certificate inputs, and any parent application.

REQ-PR-REGISTRYCTL-022: `deploy generate` MUST consume one verified two-lane approved set and the
installed signed release lock.
It MUST NOT sign bundles, create production secrets, initialize product state, start a product, or
activate a deployment.

REQ-PR-REGISTRYCTL-023: The public package root MUST contain:

- Operator-owned `binding.yaml`.
- Operator-owned `operator/` directories for inputs named by the package inventory.
- Registryctl-owned `generated/compose.empty.env`, `generated/compose.yaml`,
  `generated/compose.initialize.yaml`, `generated/postgresql-server.env`,
  `generated/deployment-binding.v1.yaml`, `generated/deployment-plan.v1.json`,
  `generated/operator-files.v1.json`, `generated/deployment-manifest.v1.json`, and
  `generated/RUNBOOK.md`.
- Registryctl-owned `generated/inputs/`, `generated/bundles/`, and `generated/anchors/` closures.

Names below the three generated closure directories remain private unless a public schema names
them.

REQ-PR-REGISTRYCTL-024: The deployment manifest MUST authenticate every Registryctl-owned generated
file and its canonical manifest content.
Generation MUST report a closure digest for recording outside the package.
Verification MUST fail when an explicitly expected closure digest does not match.

REQ-PR-REGISTRYCTL-025: `deploy verify` MUST verify only the generated package.
Its `io.registrystack.deployment_ownership_report` version `1.0` report MUST set
`verification_scope` to `package` and `ownership` to `managed` or `invalid`.
The report MUST NOT certify an operator-owned Compose application, include graph, or override.

REQ-PR-REGISTRYCTL-026: Package verification MUST NOT read operator-file values by default.
Explicit `--check-operator-files` MAY check existence, isolation, mode, and owner without reporting
values.
Safe regeneration MUST preserve `binding.yaml` and `operator/` and replace only the verified
generated closure.
An edited or incomplete generated closure MUST be `invalid` and unsafe to regenerate in place.

## 8. Exit statuses

| Status | Meaning |
| --- | --- |
| `0` | The requested operation completed and every selected predicate passed. |
| `1` | The parsed operation completed with a negative domain result. |
| `2` | Usage or a portable contract version is invalid or unsupported. |
| `3` | An operational dependency, file operation, Compose operation, or explicit secret provider failed. |

REQ-PR-REGISTRYCTL-027: Registryctl MUST return exactly `0`, `1`, `2`, or `3` according to this
table.
A command MUST NOT return `0` when its machine-readable report has a selected failure status.

## 9. Pre-1.0 removals and unstable surfaces

REQ-PR-REGISTRYCTL-028: The removed public roots `add`, `start`, `stop`, `restart`, `status`,
`open`, `smoke`, `logs`, `preflight`, `capabilities`, `compare`, `promote`, `migrate`, `bundle`,
`anchor`, `authoring`, `project`, `bruno`, and `update-check` MUST be usage failures.
The removed `init relay`, `init --from`, and `test --live` forms MUST also be usage failures.

The following surfaces remain outside the 1.0 compatibility promise:

- Generated build and development layouts below a project root.
- Editor staging, backup, and transaction artifacts not returned by a versioned report.
- Human-readable output text, whitespace, ordering, and terminal formatting.
- Hidden commands, worker processes, and their input or output protocols.
- Operator-owned files and orchestration outside a generated deployment package.

REQ-PR-REGISTRYCTL-029: Automation MUST use a versioned report, a committed schema, or the public
generated-package contract in Section 7.
Documentation MUST NOT present an unstable path or human-readable value as an automation contract.

## 10. Authorization and evidence boundaries

REQ-PR-REGISTRYCTL-030: Registryctl MUST reject a declared consultation that does not derive from
exactly one declared integration, and MUST reject typed consultation input that does not bind that
integration's input set exactly and injectively.
An attribute-release claim MUST declare exactly one of `source_field` or `expression`, so a released
value derives from the authorized source read and never from caller-supplied data.

REQ-PR-REGISTRYCTL-031: Development source access MUST preserve authorization-before-source.
The denial scenario MUST reach no token endpoint and no authored source.
The authorized scenario MUST use the exact integration scope.
The smoke report MUST expose no source-returned value.

## Conformance

A Registryctl release conforms to this specification when it:

- Exposes only the ten public roots, honors global project selection, and performs no update checks
  (REQ-PR-REGISTRYCTL-002 through REQ-PR-REGISTRYCTL-004).
- Preserves authored ownership, strict schemas, bounded paths, and atomic HTTP-template
  initialization (REQ-PR-REGISTRYCTL-005 through REQ-PR-REGISTRYCTL-008).
- Preserves offline authoring, deterministic build, disposable development, independent lane
  trust, and read-only review boundaries (REQ-PR-REGISTRYCTL-009 through
  REQ-PR-REGISTRYCTL-015).
- Emits compatible value-free reports (REQ-PR-REGISTRYCTL-016 through
  REQ-PR-REGISTRYCTL-021).
- Generates and verifies only the governed package while leaving operator orchestration outside
  that result (REQ-PR-REGISTRYCTL-022 through REQ-PR-REGISTRYCTL-026).
- Returns exact process statuses and keeps removed or unstable surfaces outside the promise
  (REQ-PR-REGISTRYCTL-027 through REQ-PR-REGISTRYCTL-029).
- Preserves authorization-before-source and refuses non-Relay claim evidence
  (REQ-PR-REGISTRYCTL-030 and REQ-PR-REGISTRYCTL-031).

## Evidence

This specification is `verified`: the requirements describe implemented behavior with automated
tests.

- `crates/registryctl/src/main.rs` defines the ten-root parser, global project selection, command
  ownership, report rendering, and exit mapping.
- `crates/registryctl/tests/cli_contract.rs`, `cli_exit_codes.rs`, and `cli_doctor.rs` pin the
  public roots, pre-1.0 removals, global `-C`, doctor report, and four exit statuses.
- Project-authoring command and integration tests pin initialization reports, staged publication,
  authored path checks, deterministic generation, and complete publication.
- `crates/registryctl/schemas/project-reports/registryctl.project_command.v1.schema.json` pins the
  shared authored-project report shape.
- `crates/registryctl/src/dev_runtime.rs` and `tests/dev_runtime_core.rs` pin disposable runtime
  ownership, exact image locking, source ordering, and `registryctl.dev_smoke.v1`.
- `crates/registryctl/src/deployment.rs` and `tests/deployment_seams.rs` pin package ownership,
  closure integrity, package-only verification, operator-file isolation, and safe regeneration.
- Trust, approved-set, and project-authoring compiler tests pin lane identity, anchor verification,
  two-lane assembly, and the Registry Relay evidence boundary.

Registry Coordinator runs a reviewed, declared flow of calls to other Registry Stack products'
public HTTP APIs, and keeps that flow going across durable waits, service outages, and worker
restarts. Use it when a sequence such as "read the application, wait two days, read it again, then
send a notice" has to continue without a person or a script holding it open. Each product a flow
calls keeps authorization and ownership of what that call does.

## What a flow is

A flow is a finite, acyclic graph of steps written in YAML. Mappings carry values between steps,
and bounded pure Rhai functions compute values and pick branches; a function cannot make a call or
acquire a credential. You check a flow offline, test it against fake product replies, and package
it into an immutable artifact an operator pins by digest. A run keeps the definition it was
admitted under, so upgrading a flow never changes a run in flight.

{/* Evidence: products/coordinator/PRODUCT-CONTRACT.md, Execution and authority;
    crates/registry-coordinator/src/deployment.rs, package. */}

Every step has one of five types:

- `call` sends one of ten fixed operations over a connection the operator configured, such as
  reading a Base Registry Engine (BReg) record, booking a Registry Scheduling appointment,
  submitting a Registry Messaging message, or submitting a Registry Casework review request.
- `choose` picks the next step from one value, such as a field of an earlier call's output.
- `wait-until` waits until an instant. The wait is stored in PostgreSQL, so it survives a
  restart.
- `wait-for` waits, up to a timeout, for the result of a review request an earlier step submitted
  to Casework. The run reads that result itself. Casework's completion event only brings the next
  read forward.
- `finish` ends the run with a declared outcome and output, which the caller reads from the run's
  status.

{/* Evidence: crates/registry-coordinator/src/authoring.rs, AuthoredStep;
    crates/registry-coordinator/src/operations.rs, CATALOG;
    products/coordinator/README.md, Waits and polling. */}

No step leads back to an earlier one, so a poll is written out as a fixed number of rounds. The
last round finishes with an outcome saying the answer is not there yet, and the caller decides
whether to start a new run later.

## When to use it

Use the Coordinator when a sequence of product calls has to outlast time and failure: a follow-up
after a delay, a notice once a human review approves, a booking after an approved deferral. It is
an optional service with its own PostgreSQL 17 or newer database, where a run's progress and
prepared commands are stored encrypted. A call is retried only after an answer the receiving
product says it did not act on, and an uncertain effect waits for an operator rather than being
sent again.

Look elsewhere when the work needs SQL, arbitrary HTTP methods, a loop, or a number of calls known
only at run time. The Coordinator has no SQL steps, no dynamic fan-out, no automatic compensation,
and no distributed rollback.

## What it never does

- **It never starts a run from an event.** A run starts only when a caller asks, through
  `POST /v1/runs` or `coordinatorctl start`. A completion event wakes a run already waiting on
  that review request, and starts nothing.
- **It never inherits authorization.** A caller allowed to start a run is not thereby allowed the
  effects its flow requests. Each call uses the identity the operator configured for that
  product's connection, acquired when the call is attempted, and the receiving product decides the
  call under its own policy. A wait or a retry never renews an approval.
- **It never writes to another product's database.** It reaches each product over that product's
  public HTTP contract.
- **It never rolls back.** Cancelling a run stops future calls where it can, and leaves every effect
  a product already accepted in place.

The Coordinator is pre-1.0, so use the binaries and documentation of one release together. The
[reviewed notice example](https://github.com/registrystack/registry-stack/tree/main/products/coordinator/examples/reviewed-notice)
shows a whole flow: it submits a Casework review, waits up to fourteen days, sends a notice on
approval, and withdraws the request on timeout. A tutorial is tracked in
[issue #1997](https://github.com/registrystack/registry-stack/issues/1997).

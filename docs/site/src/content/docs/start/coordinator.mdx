Registry Coordinator runs a reviewed, declared workflow of calls to other Registry Stack products'
public HTTP APIs, and keeps that workflow going across durable waits, service outages, and worker
restarts. Use it when a sequence such as "read the application, wait two days, read it again, then
send a notice" has to continue without a person or a script holding it open. Each product a workflow
calls keeps authorization and ownership of what that call does.

## What a workflow is

A workflow is a finite, acyclic graph of steps written in YAML. Mappings carry values between steps,
and bounded pure Rhai functions compute values and pick branches; a function cannot make a call or
acquire a credential. You check a workflow offline, test it against fake product replies, and package
it into an immutable artifact an operator pins by digest. A run keeps the definition it was
admitted under, so upgrading a workflow never changes a run in flight.

{/* Evidence: products/coordinator/PRODUCT-CONTRACT.md, Execution and authority;
    crates/registry-coordinator/src/deployment.rs, package. */}

Every step has one of five types:

- `call` sends one versioned host operation over a connection the operator configured, such as
  reading a Base Registry Engine (BReg) record, booking a Registry Scheduling appointment,
  submitting a Registry Messaging message, or submitting a Registry Casework review request.
- `choose` picks the next step from one value, such as a field of an earlier call's output.
- `wait-until` waits until an instant. The wait is stored in PostgreSQL, so it survives a
  restart.
- `wait-for` waits, up to a timeout, for a named completion of an earlier accepted call: a Casework result, exact BReg
  Proposal application, or bounded external read. The host reads authoritative evidence within a
  durable observation budget. A completion wake-up only advances an eligible read.
- `finish` ends the run with a declared outcome and output, which the caller reads from the run's
  status.

A project separates generated contracts, reusable types, named pure Functions, and local Operation
aliases from its one Workflow graph. Functions take one typed object of named inputs. A bounded
completion poll repeats a saved read under host scheduling; the graph remains acyclic.

## When to use it

Use the Coordinator when a sequence of product calls has to outlast time and failure: a follow-up
after a delay, a notice once a human review approves, a booking after an approved deferral. It is
an optional service with its own PostgreSQL 17 or newer database, where a run's progress and
prepared commands are stored encrypted. A call is retried only after an answer the receiving
product says it did not act on, and an uncertain effect waits for an operator rather than being
sent again.

Look elsewhere when the work needs SQL, arbitrary HTTP methods, a loop, or a number of calls known
only at run time. The Coordinator has no SQL steps, no dynamic fan-out, no automatic compensation,
and no distributed rollback.

## Authority boundaries

A run starts from an authorized caller, an accepted Review request, or a configured authenticated
product event. Completion events only advance eligible observations on existing waits.
Each downstream call acquires the operator-configured identity, and its receiver
checks current authority. A wait or retry preserves the original approval deadline. Public HTTP
contracts separate products; each owns its database. Cancellation stops future dispatch where
possible and leaves accepted effects in place.

The Coordinator is pre-1.0, so use the binaries and documentation of one source version together.
[Author a Coordinator workflow](../../configure/coordinator/) to check and package one reviewed
sequence. The applicant drives a BReg Proposal in BReg, and a workflow follows it by product
event or record read; a notice still needs Messaging authority. Standalone Casework review and
external job observation work independently of that path.

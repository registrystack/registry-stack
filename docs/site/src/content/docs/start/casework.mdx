Registry Casework is an unreleased candidate in the current development source.
It gives a team one accountable inbox for source-owned work and for small human
decisions requested by another service. Build and evaluate it from a reviewed
source revision until a future Registry Stack release lists Casework artifacts.

## Choose the work source

Casework supports two independent shapes:

- A Base Registry Engine (BReg) source contributes governed change requests.
  Casework keeps assignment, routing, clocks, drafts, and recovery state, then
  uses the person's token and selected BReg profile for each source decision.
- A hosted kind lets a Requester service create a bounded item directly in
  Casework. The requester can read, note, cancel, and poll only its own items.
  A person completes the item under Casework's team and kind authority.

A project may declare either shape or both. Standalone hosted work needs no
BReg deployment or source adapter.

## Keep human and service authority separate

Staff and Supervisor are human profiles. Their tokens must contain the exact
human-identity assertion configured by the operator. Staff work eligible items;
Supervisors control assignment and caseload for teams they currently lead.
Administrator is also a human profile, but directory and holiday administration
grant no item payload access.

Requester is a service integration profile. It does not require the human
assertion, cannot claim or decide work, and gains no human authority when its
token happens to contain that assertion. A source-backed decision also requires
the caller's explicitly selected source profile. Casework does not choose a more
privileged source profile to make an operation succeed.

## Plan the deployment boundary

One Casework process needs PostgreSQL, one OpenID Connect issuer, a private HTTP
listener behind operator-controlled TLS, and a keyed audit file. Production
loads a reviewed policy package and verifies its adjacent manifest before the
listener opens. The deployment operator owns selecting that package and rolling
out or restarting the process. Policy replacement does not rewrite running
clock occurrences; holiday changes use a separate Administrator preview and
apply operation.

The App Kit provides the current staff interface for BReg-backed work. A
standalone deployment supplies the HTTP API and maintained clients, with no
stack-provided standalone staff screen.

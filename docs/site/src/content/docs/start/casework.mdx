If people in your institution must answer or approve something before another system acts on it,
[Registry Casework](../../reference/glossary/#registry-casework) gives them that review and returns
their answer to the system that asked.

## What Casework decides

Casework runs one lifecycle, and `caseworkctl` prints it:

```sh
caseworkctl lifecycle
```

```json test-excerpt
{
  "id": "review-request",
  "label": "Casework review request lifecycle"
}
```

A system sends Casework a [ReviewRequest](../../reference/glossary/#review-request): the subject to
review and the policy to review it under. The request stays `reviewing` until a person's decision
settles it:

```json test-excerpt
{
  "event": "settle",
  "from": "reviewing",
  "guard": "an answer, which as a non-approving decision settles the request at once regardless of quorum",
  "to": "answered"
}
```

A [Decision](../../reference/glossary/#decision) is one reviewer's recorded choice of an outcome the policy declares. Casework counts
decisions, settles the request, and keeps the result for the system that sent it.

## What Casework never owns

The system that sent the request keeps the subject and decides any later change to it. Casework has
no write or apply authority over that source, and a settled request grants none. When reviewers
need current data, the source decides what each reviewer may see, under that reviewer's own
credential.

Casework serves an API, so your application supplies the reviewers' screens. It keeps review state
in PostgreSQL and verifies tokens from your own OpenID Connect issuer.

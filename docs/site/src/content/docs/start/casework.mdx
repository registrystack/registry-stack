If you need people to review a bounded request before another system continues, Registry Casework
provides the team inbox, assignments, decisions, and result. Your system keeps the business object
and authorizes any later change independently.

## Choose how reviewers see context

Use submitted context when your producer can supply an immutable snapshot for the review round.
Casework stores the admitted snapshot and runs without a source service.
[Decide your first review request](../../tutorials/first-casework/) takes you from a local starter to
one human answer and the producer's result.

Use current-source context when the source must decide which fields a reviewer can see now.
A Base Registry Engine (BReg) Proposal is one such context.
Casework keeps an exact reference and asks a read-only provider for current disclosure under the
reviewer's bearer token and selected source profile.
[Review BReg changes in Casework](../../tutorials/review-breg-changes-in-casework/) explains the
native Proposal integration and its separate application authority.

Both modes use one model: a `ReviewPolicy` governs a `ReviewRequest`, one or more `ReviewTask`s
collect human `Decision`s, and the producer receives a `ReviewResult`.
The accepted policy stays pinned while new policies shape newly admitted requests.

## Decide whether it fits

Staff claim and decide eligible tasks. Supervisors assign work and manage caseloads for their
serving teams. Administrators maintain the Directory and calendars. Trusted producers submit,
cancel, and read results only inside their admitted binding.
A profile name or task identifier grants no authority by itself.

Casework serves an API, so your application supplies the staff interface.
It uses PostgreSQL for retained review state and your OpenID Connect issuer for authentication.
Its completion wake tells a producer to fetch a result; it grants no authority to apply that result.

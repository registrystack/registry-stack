The [Registry Document Store](../../reference/glossary/#registry-documents) holds document bytes
in custody for the system that owns them, and releases one exact, verified version to each
recipient the custodian names. Use it when an issued certificate, an uploaded supporting
document, or a scanned record has to be kept and handed to a named person later, without that
system serving files itself.

{/* Evidence: products/documents/README.md, introduction and Routes. */}

## What you write, and what runs

You write a `documents.yaml` project: the access profiles callers resolve to, and one or more
**document policies**. A policy says who may place a document in custody, who holds it, which media
types and sizes it admits, who may be granted it, and for how long. The operator packages that
project, pins it by digest, and runs the `documents` service over its own PostgreSQL database,
with the bytes in PostgreSQL or in an S3-compatible bucket.

An owning system reserves a **[document](../../reference/glossary/#document)** under a policy and
then sends its bytes. Each upload is one immutable
**[document version](../../reference/glossary/#document-version)**, checked against the digest
and length the reservation declared.

{/* Evidence: crates/registry-documents-core/src/project.rs, DocumentPolicy;
    products/documents/RUNTIME-CONFIG.md, Keys. */}

## Who holds a document

Every document has one custodian, fixed by its policy's `custodian` setting.

| Setting | Custodian |
| ------- | --------- |
| `represented-principal` | The person the document was placed for, such as a citizen |
| `institution` | The institution whose system reserved it |

The custodian is the only caller who may remove the document. Under `institution`, the person the
document concerns has no standing on it until a grant names them. Under `represented-principal`,
the reserving system keeps the document's record but is not released its content. A policy may
also let the represented person place documents or issue grants. This is
**[document custody](../../reference/glossary/#document-custody)**.

{/* Evidence: crates/registry-documents-core/src/project.rs, CustodianRule and
    RepresentedPrincipalGrants. */}

## What gets released

A version is released only after **[content verification](../../reference/glossary/#content-verification)**:
the Store sends the stored bytes to a verifier the operator configured, and only an approval
bound to that version's digest, media type, and the current verifier releases it. A rejection
keeps it from ever being released. A verifier that cannot answer is retried for about seven
days; the version then waits for an operator, neither approved nor rejected.

| Status | Means |
| ------ | ----- |
| `awaiting-content` | Reserved, with no bytes stored yet |
| `pending` | Bytes stored, waiting for an approval |
| `ready` | Approved and releasable; the only status that is |
| `suspended` | Approved once, not releasable now |
| `rejected` | The verifier rejected it; it stays rejected until its bytes are erased |
| `erasure-pending` | The custodian asked for removal |
| `erased` | Bytes erased; the record remains |

A **[document grant](../../reference/glossary/#document-grant)** releases a `ready` version to
someone else: it names one recipient, one exact version, and an expiry within the policy's
bounds. The custodian can revoke it at any time.

## Removal and erasure

Nothing expires on a timer. A document stays in custody until its custodian removes it or the
verifier rejects it, and a grant that expires or is revoked erases nothing. Removal stops
release at once and revokes every grant; the bytes are erased after the policy's grace period,
at least one hour, so an operator can still restore from a mistaken request. Erasure reaches
what the Store serves, not backups, replicas, or archived database logs.

{/* Evidence: products/documents/README.md, Retention and erasure. */}

## What stays with the owning system

The Document Store owns custody records, grants, stored bytes, verification state, and its audit
journal. Why a document exists, who it concerns, and whether a recipient is entitled to it stay
with the system that reserved it. Other products reach the Store over its public HTTP API like
any caller, and inherit none of its authority. A Base Registry Engine (BReg)
[Proposal attachment](../../reference/glossary/#proposal-attachment) is held by BReg itself,
not by the Store.

## When to look elsewhere

The Store does not render documents, which is
[Registry Render](../../reference/glossary/#registry-render)'s job, and it holds no wallet
credential. It is pre-1.0 and held out of releases: build it from a source checkout, and use the
binaries and documentation of one source version together.

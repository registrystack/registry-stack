Use Registry Stack when an institution needs controlled record access, bounded signed answers,
or a configuration-defined system of record. Relay and Evidence Gateway work over existing sources.
[Base Registry Engine](../../reference/glossary/#base-registry-engine) owns records in PostgreSQL
and supports writes.

    crates/registry-breg/src/postgres/mutation.rs. */}

## Registry Stack is a good fit when

- The source must remain authoritative and under the institution's control.
- Callers need a reviewed interface instead of direct database or file access.
- Each caller must have an explicit purpose, permission, and limited result.
- The institution needs to test source behavior with synthetic fixtures before
  connecting a runtime environment.
- Operators need separate control over endpoints, credentials, token issuers,
  and deployment.

## Choose the result you need

| Caller needs | Use | Result |
| --- | --- | --- |
| To read specific data | Registry Relay | A protected, read-only API response |
| To learn only a fact | Evidence Gateway | A signed assertion carrying the answer, not the source record |
| To own and update registry records | Base Registry Engine | A configuration-defined PostgreSQL registry and REST API |

The three are separate products. One institution can run all of them, but each has its own
source, authorization, configuration, and audit boundary, and Evidence Gateway does not need Relay
as its source.

### Who does what

- The assertion provider is the institution that answers requests with signed facts through
  Evidence Gateway.
- The data publisher is the institution that exposes records through Registry Relay or
  maintains a registry through Base Registry Engine.
- The consumer or verifier is the relying service that calls a product's API and verifies the
  answers it receives.
- The operator is whoever runs the deployment.

## Registry Stack is not the right tool when

- You need a workflow, eligibility, ranking, or case-management engine.
- You need Registry Stack to decide legal authority, data ownership, or
  institutional approval.
- You want to publish unrestricted open data.
- The records you want to publish through Relay cannot be exposed as a reviewed
  read-only SQLite view.

Registry Stack makes these boundaries visible, but the responsible
institutions still make and approve the underlying decisions.

## What each product needs to run

Every product runs as one process behind your own TLS termination, and protected access needs
bearer tokens from one OpenID Connect issuer, or from Registry Mint when you have none. The rest
differs:

| | Registry Relay | Evidence Gateway | Base Registry Engine |
| --- | --- | --- | --- |
| Source | Reviewed read-only SQLite views; a raw table is never a source | One fixed request per question to a system you already run | An authored data model; the records live in the registry |
| Database | None | None | PostgreSQL 15 or newer, two roles |
| Durable state | Audit log on disk | Audit log on disk | Everything in PostgreSQL |
| Production signing | Sealed package, no signature | Vault or OpenBao Transit key for assertions | External signatures on every package |
| Plan a deployment | [Run a deployment](../../operate/relay/) | [What you need to run Evidence Gateway](../../operate/evidence-requirements/) | [What you need to run Base Registry Engine](../../operate/breg-requirements/) |

The local tutorials need none of this; they start disposable versions of everything on your machine.

## What you need to adopt it

Before moving beyond a local sample, identify the source owner and update process, the fields and
operations the integration may use, the callers and purposes each service may serve, and the
operator responsible for endpoints, credentials, deployment, recovery, and audit retention. Start
with non-personal data. A successful local tutorial is not production approval.

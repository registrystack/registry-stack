If your registry hands people printed letters, receipts, or certificates,
[Registry Render](../../reference/glossary/#registry-render) turns record data into those PDFs.
Fixed inputs produce identical PDF bytes, on one machine and across machines.

## What a caller gets

A caller sends the document's data and its issuance time, and receives the PDF with two hashes: one
for the file (`pdfDigest`), one for the exact input it was rendered from (`dataDigest`). A re-render
from the same inputs on the same renderer months later is byte for byte the same file, so a hash in an audit log still
matches the paper in the folder, and a retry of a plain render never yields a different document.

## What you define

A bundle. Its `manifest.yaml` declares each document type with a version and a Typst entry file. A
document type can also declare a JSON Schema for its data and the label locales it uses. Label
tables hold the words a template prints in each language, and every table carries the same keys. A
template uses the fonts built into the binary and any fonts the bundle ships.
`registry-render check` checks the bundle offline, and `registry-render package` turns it into a
package whose digest names its exact files.
[The configuration reference](../../reference/render-configuration/) lists every key.

A template reads one envelope. It holds the request's `data` and its image `assets`, as the base64
text the caller sent. It also holds the label tables, the locale when one is sent, the issuance
time, and the document's id and version. On the seal route it also holds a `signing` member. The
template reads each decoded image as a file under `/assets/`, beside the bundle's own files. Nothing
else reaches it: no host fonts, no environment, no clock, no network.

## What fixes the bytes

Render hashes the exact canonical input the template reads, and the issuance time in the request is
the only clock a template sees. Each render starts a fresh Typst world, fonts load in a fixed order,
and the PDF names a fixed creator with no version. [What a Render template
receives](../../reference/render-payload/#what-fixes-the-bytes) gives the rules.

## What runs

`registry-render compile` renders one document at a terminal, for authoring and for printing at a
counter without a service. `registry-render serve` is a small HTTP service that admits callers by
OIDC access token, or by a legacy API key, and serves one package. `registry-render package` copies
validated source into a new directory and writes a sorted `SHA256SUMS` file covering every file,
plus an optional `REVISION`. The package digest is the sha256 of that checksum file. The package
writer refuses an existing directory, so a digest never gains different bytes.

At startup serve verifies the checksums and, when configured, `package.expectedDigest`. Each render
runs in a worker process that verifies the package again, so a file changed after startup is refused
by name. [Deploy Registry Render](../../operate/registry-render/#what-you-provide) lists what a
worker is held to.

The service keeps no database and no rendered document, and it makes no outbound call while
rendering. A timestamped seal calls the timestamp authority you configure. It writes only the audit
log, to a file or to standard output. It writes a `request` entry before each render starts. It
writes a `response` entry, with the document's hashes, before the PDF leaves. If either write fails,
the call fails and no document is returned.

## What Render refuses

Render refuses data its schema rejects, a request without an issuance time, a package whose files
changed, a caller whose token or API key it does not accept, and a public listening address. A
served render never reads the host's clock, fonts, or network. `registry-render compile --now` is
the one preview option that takes the issuance time from the clock.

## Who owns the result

The caller does. Render returns the PDF and forgets it. The record the document was made from should
keep `pdfDigest` for the file and `dataDigest` for the exact input. A sealed file has no
`pdfDigest`, so keep its `documentDigest` and `signedFileDigest` instead. The audit log holds
hashes, versions, and a fingerprint of the caller's credential, never data values or image bytes. What a template
prints is a disclosure decision that belongs to its author: once on paper, it has left every access
profile behind. Render does not store documents, issue credentials, or decide who may see a field.
It can add an optional PAdES seal to a document it just rendered, as described in
[Deploy Registry Render](../../operate/registry-render/#seal-documents), but it makes no
qualified-signature claim. A seal takes its signing time from the host's clock, so each sealed copy
of one request differs in its signed bytes.

## How to check a document later

Re-render it. On the same renderer, the same package, document type, locale, data, assets, and
`issuedAt` reproduce the stored `pdfDigest` of a plain render byte for byte. That makes a replay
after a failure safe and lets an auditor match paper to the log. `GET /health` gives the live
package digest as `bundleHash`, in hex without the `sha256:` prefix that `package.expectedDigest`
carries. Every audit entry carries the renderer version, and every entry for a render that started
also carries the bundle hash.

When a hash moved, one of three things changed: an input, the package, or the renderer. A Typst or
compression upgrade can change the bytes, so
[check a new binary before you switch to it](../../operate/registry-render/#upgrade).

Compare packages, not source directories: the hash of an unpackaged source directory is not a package
digest. [Deploy Registry Render](../../operate/registry-render/#upgrade) says what it covers.

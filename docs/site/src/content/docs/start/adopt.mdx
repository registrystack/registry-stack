There are four ways to adopt Registry Stack.
You can:

- Configure a Base Registry Engine (BReg) project
- Add a small extension
- Write an application
- Run a separate module

Choose the ones that fit your institution's systems and team.
You can combine them.
None of them is a prerequisite for another.

## Choose an adoption path

| Path | Use it when | You own | Start here |
| --- | --- | --- | --- |
| Configure a register | A starter's Records, Actions, and review policy fit | Model, access, deployment, data, and acceptance | [BReg quickstart](../breg-quickstart/) |
| Add a small extension | A documented rule, route, or page seam fits | Extension code and its decision | [BReg extension guidance](../../configure/breg/) |
| Build an application | You need your own journey or integration | Interface, credentials, correlation, and recovery | [Client API](../../reference/client-api/) |
| Run a module | The work needs an independent lifecycle | Service, storage, release, and policy | [Module conventions](../../configure/module-conventions/) |

## Build an application in your language

Build on the released clients or on the public HTTP contracts.
You own:

- The journey
- The credentials
- Correlation
- Recovery

Each product you select keeps its own authorisation and effects.
The [access-token guide](../../configure/request-an-access-token/) explains how to integrate with
your token issuer.

The starter collection and App Kit are private.
To read their instructions, ask a maintainer for access.
You need that access to open the
[reviewed licensing starter guide](https://github.com/registrystack/breg-registry-starters/blob/main/docs/reviewed-licensing.md)
and App Kit's private guide, `project/docs/customization.md`.
For a public first run, use the [first registry tutorial](../../tutorials/first-breg/).

An extension, application, or module still needs authority that the receiving product accepts.
A review in [Registry Casework](../../reference/glossary/#registry-casework) does not write a BReg
Record.
BReg applies the reviewed Proposal under its own authority.

Add [Registry Coordinator](../../reference/glossary/#registry-coordinator) only when the journey
needs a durable sequence.
Add [Registry Messaging](../../reference/glossary/#registry-messaging) only when the journey needs
reviewed delivery.

A module can publish a static
[Registry Manifest description](../../products/registry-manifest/reference/#adopter-owned-modules).
Publishing that metadata does not enable the module or certify it.

## Choose what goes in the registry

Hold the facts your law makes you the source of and the decisions you are accountable for.
Leave these in the systems that own them:

- Payroll
- Documents
- Generic workflow

Review these with your programme and legal colleagues:

- Rules
- Tables
- Formulas
- Deadlines

Write "not stated" where nobody has stated the legal basis.
Do not guess it.
[Modelling patterns for registries](../../explanation/registry-modeling-patterns/) covers the record
and authority choices.

Work that spans any of these is a process and not only a register:

- More than one record
- Weeks
- Money
- A legal clock
- Agreement between parties

Before you add custom workflow, check [where each rule lives](../../explanation/where-each-rule-lives/).

## Work with other institutions

Start from the partner and the situation.
Then pick the product.
"Do not integrate" is always a valid answer.

| Situation | What you do | Product |
| --- | --- | --- |
| Others need a fact about your records | Publish a narrow answer, not the record | [Registry Evidence](../../explanation/how-evidence-works/) |
| A partner needs to read or change your records | Publish a governed record API | [BReg](../../explanation/configuration-defined-registry/) |
| You need a fact held by someone else | Ask for the narrowest answer that does the job | [Evidence, as the consumer](../../tutorials/verify-an-assertion-as-a-consumer/) |
| You must load another system's data | Copy it in through a reviewed translator | [Registry Adapter](https://github.com/registrystack/registry-stack/blob/e05a43a55ba5a9a178e088d6b8c686b0f89b659f/products/adapter/README.md) packs (the ingestion job is not yet released) |
| A standard or national system fixes the wire contract | Serve it at the edge | Adapter facade profile |
| The person can carry the proof | Let them bring it as a credential | Evidence with [OID4VCI delivery](../../configure/evidence-oid4vci/) |
| Integration is not justified | Do not integrate, and write down why | None |

For each partner, write down:

- The legal basis
- Who defines the question
- What crosses between you
- The serving product
- Who owns changes

Write "not stated" for any gap.

Promise Read first.
Promise Write only when the source can:

- Refuse a stale update
- Retry a create safely
- Return a version

See `If-Match` and `Idempotency-Key` in the [BReg API](../../reference/breg-api/).

Point to records that another office keeps.
Do not copy them.
Store each record's identifier with its scheme.
When a decision needs the fact, ask for it through Evidence.

In BReg, the subject or source of an event record can hold an identifier that another system owns.
Declare that subject or source with `external: {namespace}`.
See the [event records guide](../../configure/breg-event-records/#declare-the-descriptor).

You own your payment policy and your contracts with payment providers.
You can implement them directly in an application or module.
Or Coordinator can send a configured POST to the payment provider through its generic
`external.command/v1` operation.
None of the maintained products is a payment product.
None of the maintained operations is specific to payments.

To decide how much to share, see [the disclosure ladder](../../explanation/data-minimization-and-purpose-limitation/#ask-for-the-weakest-answer-that-does-the-job).

## Choose the next step

Combine the smallest set of paths that meets the job.
For example, a configured register can have one custom route and a reminder worker that you
deploy separately.
Add [Coordinator](../coordinator/) only when a durable, reviewed sequence across waits is useful.
Before you deploy, use the [operator handoff](../../operate/) to assign each of these to a named
operator:

- Credentials
- Backups
- Retention
- Recovery

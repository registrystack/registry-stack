If an application knows what it must establish about a person but not which institution can
answer, [Registry Discovery](../../reference/glossary/#registry-discovery) tells it which Evidence
types meet that requirement and which [Registry Evidence](../../reference/glossary/#evidence-gateway)
services assert them. An application asks two questions over plain HTTP: what a requirement
resolves to, and which provider serves each answer. The Discovery namespace of the
[Registry Stack client](../../reference/client-api/#registry-discovery) does this from Rust,
Node.js, or Python.

## What an operator maintains

An operator keeps one project directory: the HTTPS origins it approved, one per provider, in
`origins.yaml`. Mapping files say which Evidence types meet which requirement. A runtime file
completes the project. `discoveryctl` checks the project offline, then fetches each approved
description once and writes an immutable, digest-sealed package. `discovery` serves that one package
read-only, needs no database, and never contacts a provider while it runs.

    crates/registry-discovery/src/startup.rs, load_runtime(). */}

## Why the index is curated

A Registry Evidence deployment can publish a public description of itself: its service identifier,
its endpoint, the Evidence types it asserts, its jurisdictions, and optional publisher, operator,
and issuer identifiers. Private configuration never enters that description. Anyone can publish such
a file, so Discovery lists only the descriptions an operator approved, by URL.

Approval is the whole meaning of a listing: the operator chose that origin, and the provider
published those bytes. Discovery does not authenticate the provider, rank one provider above
another, or attach trust to the publisher and issuer identifiers. They describe a service and do not
vouch for it. Discovery is a curated index, not a trust broker. It holds no credentials and proxies
no call.

## What a requirement resolves to

The operator writes the answer to "which Evidence types prove adult status" as a mapping: a
requirement, an optional jurisdiction, and one or more alternatives. Each alternative is a list of
Evidence types that are all required together. The application satisfies the requirement by meeting
any one alternative.

A resolve request matches a mapping by its exact requirement and jurisdiction. Identifiers are
compared exactly, with no normalisation, so a request for another jurisdiction finds nothing rather
than a near match. Every alternative carries the `mappingId` and the `mappingAuthorityId`, the body
that stated the mapping. The response also carries `mappingRevision`, a SHA-256 digest of every
mapping in the index. It changes only when what the mappings say changes.

{/* Evidence: crates/registry-discovery/src/query.rs, resolve_evidence_types() and

## Which provider serves it

For each Evidence type in the chosen alternative, the application searches for services that assert
it, optionally narrowed by jurisdiction, service identifier, or conformance profile (an identifier a
service lists in its `conformsTo` member for a profile it claims to follow). Every filter is an exact
match and the results are not ranked. When more services match than the configured limit allows,
Discovery refuses the search instead of returning a partial list. Each result carries the provider's
public endpoint and its `originContentDigest`, described below.

Each result is one record: one exact capability of one service, as one approved origin published it.
Its `bindingId` is a digest of the service identifier, endpoint, profiles, and Evidence types, and
its `recordId` is a digest of the origin and the binding. Two origins that describe the same service
produce two records that never merge, so an application always knows which publication it read.

The response carries `catalogRevision`, a SHA-256 digest of what every service record says. Fetch
times and the raw bytes are left out, so packaging the same descriptions again gives the same
revision.

## What a selection holds, and what it does not do

The application saves a selection for each type it needs: the chosen record and binding, the
Evidence type it matched, the whole alternative it came from, both revisions, and the origin's
provenance. The Registry Stack client refuses a selection whose binding no longer matches its
fields, whose service does not assert the matched type, or whose service does not cover the resolved
jurisdiction. Keeping the whole alternative stops a set of types required together from shrinking to
one.

A selection is inert public metadata, never a credential or a trust decision. Before calling the
provider, the application applies its own policy to the selection. Only when that policy accepts it
does the client hand over the provider's base URL, and that handoff exists in memory only: it is
never saved, so the policy runs again each time. The application then calls Registry Evidence
directly, with its own credentials and its own Evidence trust configuration. Discovery is never on
that path.

## When a provider republishes

Nothing changes until the operator packages again. Each record keeps `originContentDigest`, the SHA-256 of the exact bytes that fetch
received, and the time of the fetch. The digest lets anyone compare what the index was built from
with what the provider publishes now. It is not a signature: it records which bytes were fetched,
not who wrote them.

A republish that changes only formatting moves `originContentDigest` but leaves `catalogRevision`
and every record identity alone. A change to an endpoint or a type changes the binding, and any
change to what a record says changes `catalogRevision`. A saved selection can be renewed from a fresh
search only when everything that bears on trust is unchanged. The
[operator guide](../../configure/discovery/#maintain-the-index) lists what counts.

## Why a new revision needs a new package

An index that changed in place would be one nobody reviewed, so a revision always means a new
package, a new pin, and a restart. `discovery` recomputes the package before it listens and refuses
a changed, missing, or extra file. [Package and run a Registry Discovery index](../../configure/discovery/#restart-on-the-new-package)
shows the commands.

## When it is not the right product

An application that already knows its provider needs no index. Discovery describes only Registry
Evidence services. [Registry Manifest](../../products/registry-manifest/) describes a registry's
datasets and services for catalogues.
